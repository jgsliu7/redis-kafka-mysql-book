# 问题处理流程 v1

> 2026-07-24 与用户对齐定稿。适用于本书接近完工阶段的所有修改类工作。
> 总原则：**批量处理——一次流程解决一类问题，而不是一个问题。**

## 一、设计思路

本书已近完工，后续修改的核心矛盾是：改，有引入连带问题的前科（上一轮修完连带出 13 处新问题）；不改，残留问题已查明。因此用多 agent 共识把每一步的错误率压下去，用"按类分批"把成本压下来。

**AI 味改造的认识论**（用户确认）：
- AI 的痕迹 = 过度均匀（每条启示同构、每节必金句、三家必等长）
- 改造 = 恢复人类写作自然的不均匀性，**不是为变而变**
- 检验标准：每处详略变化都能回答"为什么这里多写"——变化从内容里长出来
- 章节级骨架（导读→三软件→对比→取舍→启示）**一个字不动**，松的只是填充节奏

## 二、七步流水线（每一批走一轮）

```
① 问题确认：3 个不同人设 agent 独立投票，≥2 确认才立项
② 方案征集：3 个 agent 各自输出修改方案
③ 方案合并：1 个 agent 合并 3 方案 —— 只取舍拼接，禁止新增
④ 方案评审：3 个不同人设 agent 投票，≥2 通过才动手
⑤ 执行修改：1 个 agent 落地（Edit 精准替换）
⑥ 修改验证：3 个 agent 按四条标准验收，≥2 通过才算完
⑦ 不过 → 重试（≤2 次）→ 仍不过 → 升级用户裁决，记录卡点
```

### 各步硬约束

**① 问题确认**
- 3 个投票 agent 必须用**不同人设**（如 ai-writing-detector + tech-editor + interviewee-reader）。纯同质 3 票 ≈ 1 票投 3 次，防同源偏差。
- 立项时标出与已执行/待执行批次的**重叠点位**（同一处文字不能被两批各改一遍）。

**③ 方案合并**
- 合并 agent 戴镣铐：产物的每一个字都能溯源到某个输入方案，**只能取舍拼接、不能顺手创作**。

**⑤ 执行修改**
- 单人执行，Edit 精准替换；改字词不改意思。
- 绝对保留第一人称案例与判断锋芒（锚点清单见 0724v1.md 第三节）。

**⑥ 修改验证 —— 四条固定验收标准（防止 agent 自造标准）**
1. 原问题确实消除（引原文对比）
2. 没改变原意（改字词不改意思）
3. **没引入连带问题**（硬检查项，本项目有前科）
4. 没误伤锚点段落（第一人称案例、判断锋芒）

**⑦ 重试刹车**
- 最多重试 2 次。仍不过 = 问题定义可能错了，升级用户裁决，卡点记录在案。禁止无限重试。

### 轻流程（机械替换类问题专用）

性质接近机械替换的问题（如删"GPT 生成版"字样）降级为：
**发现 → 单人执行 → 3 验证（同四条标准）**，不走 ①–④。

## 四、成本估算

- 一批 ≈ 14 个 agent 调用（3+3+1+3+1+3），并行后墙钟约一轮
- 全书 9 批 ≈ 110–140 次调用（对比按单点走的 700+，降一个数量级）
- B1 试点跑完后，用真实耗时/token 数据校准后续批量大小

## 五、执行纪律

1. 总调度只做调度，任何实质性分析/审查派子 agent（AGENTS.md §6）
2. 每批的①④⑥三步投票，记录各 agent 票型和理由到 `问题检查/` 下对应批次文件
3. 每批完成后在 0724v1.md 对应点位标注状态（已改/不改/用户裁决）
4. 试点先行：B1 完整跑通并验收后，再启动后续批次
