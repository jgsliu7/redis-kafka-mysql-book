## 2. 典型数字前提核对

### 2.1 Redis "单核十万级 QPS"（ch6:24 + ch6:143）— P0

**位置**：ch6 §6.1 第一段："Redis 的内核追求极简和单核十万级 QPS"；ch6 §6.2.1 第二段同一表述。

**现状**：全文出现两次，均无任何前提。

**缺失前提**：
1. **版本前提**：Redis 6.0 引入了可选多线程 I/O，**7.x 默认关闭**。"单核十万级"在 6.0+ 多线程 I/O 开启后可超出单核；但默认配置下确实只是单核；
2. **负载前提**："小包 GET/SET 场景"——每条消息仅数字节时单核 QPS 可达 10–20 万；大 Value（数 KB）时 QPS 急剧下降至万级甚至更低；
3. **硬件前提**：x86_64 现代 CPU（非 ARM），非虚拟化或云实例（云实例网络吞吐本身有限制）。

**风险**：读者可能误以为所有 Redis 操作都能达到单核十万级 QPS，在大 Value 或复杂命令场景下据此做容量规划。

**修改建议**（old → new）：

> ~~Redis 的内核追求极简和单核十万级 QPS~~
> Redis 的内核追求极简，单线程执行时小包 GET/SET 可达十万级 QPS（Redis 7.x 默认配置，空载基准；大 Value 或复合命令下 QPS 显著下降）

### 2.2 Kafka 单分区约 10MB/s 或约 1 万条/秒（ch7:150 + ch7:关键数字框）— P0

**位置**：ch7 §7.4.1 关键数字框 + 正文："单分区吞吐受消息大小、批量、压缩、确认条件和硬件影响"，但在关键数字框中又给出了"约 10MB/s 或约 1 万条/秒"。

**现状**：给出了"约 1 万条/秒"，但**没有消息大小前提**；10MB/s 与"1 万条/秒"暗示的是不同场景但未说明。

**缺失前提**：
1. **负载前提**（最关键）：1 万条/秒的前提是**小消息（100 字节级）**；若每条 1KB，则约 1,000–5,000 条/秒；若每条 10KB，则约 100–500 条/秒；若开启压缩（同批次压缩），throughput 可提升 2–6 倍；
2. **硬件前提**：NVMe SSD、万兆网络（10GbE）；机械盘顺序写约 100–280MB/s，远低于 NVMe；
3. **配置前提**：`acks=1`（不等 Follower）、无压缩或 LZ4（压缩比低但 CPU 低）。

**风险**：读者可能据此估算分区数，导致分区数严重低估（实际大消息场景需要 10–100 倍分区数）。

**修改建议**：将"约 10MB/s 或约 1 万条/秒"改为：

> 单分区吞吐无通用基准，实际值受负载影响极大。以下为小消息（≈100B）、`acks=1`、无压缩、NVMe SSD 环境下的量级参考：**顺序写约 50–200 MB/s**；**小消息约 1–5 万条/秒**（压缩开启时吞吐量提升，消息越大提升幅度越小；大消息 1KB+ 时条速率降至万级以下）。若无实测条件，建议先在目标消息大小和确认条件下实测单分区吞吐，再反推分区数。

### 2.3 Redis RDB 压缩比 300–500MB/GB（ch8:46）— P1

**位置**：ch8 §8.1.3 关键数字框："1GB 内存实例（字符串/列表型负载，典型场景）≈ 300–500MB 快照"。

**现状**：括号内已有"字符串/列表型负载，典型场景"，但未说明这是**最紧凑场景**，其他场景差距极大。

**前提分析**：
- 字符串型（短 Value）：压缩比接近 300MB/GB（变长整数编码 + LZF 压缩效果好）；
- 列表/哈希型（含元数据开销）：约 400–500MB/GB；
- **Set/ZSet 型（带分值/成员指针开销）**：实际压缩比可能仅 500–700MB/GB；
- **大 Value 场景（MB 级字符串）**：RDB 存储的是二进制内容，压缩比趋近 1:1（几乎没有压缩空间）；
- **ziplist/listpack 紧凑编码 vs hashtable**：编码不同压缩比差距 2–3 倍。

**风险**：读者以为所有 Redis 实例都约 300–500MB/GB，据此估算 RDB 文件大小，在大 Value 场景严重失准。

**修改建议**：括号扩展为：

> 1GB 内存实例（**小 Value 字符串/列表型负载**）≈ 300–500MB 快照（变长整数 + LZF 压缩；实际压缩比因数据类型差异悬殊：大 Value 场景趋近 1:1，带指针开销的 Set/ZSet 约 500–700MB/GB）

### 2.4 "命中率在数据量低于缓冲池 10% 时断崖下跌"（ch4:33）— P0

**位置**：ch4 §4.3 第一段："命中率在工作集（频繁访问的数据集合）接近或超过缓冲池大小时急剧下降；1TB 数据库用 64GB 缓冲池，一次未命中 ≈ 一次磁盘随机 I/O，延迟比缓存命中时高三个数量级"。

**现状**：段落中有"接近或超过缓冲池大小时急剧下降"，但**没有给出"10%"这个数字的来源**。

**缺失前提**：
1. **无来源**：这个"10% 断崖"数字在正文中从未标注来源，疑似作者估算或行业经验值，未经验证；
2. **MySQL vs Redis 语境混淆**：此段在 MySQL（InnoDB）语境下，但"10% 工作集 vs 缓冲池"的比例判断来自 Redis 场景还是 MySQL 场景未说明；
3. **访问模式依赖**："断崖"是否存在、出现在哪个比例，取决于访问分布的均匀程度（Zipf 分布 vs 均匀访问）；
4. **版本前提**：InnoDB 5.7 vs 8.0 的缓冲池行为差异未标注。

**风险**：读者会把这个无来源的比例当精确阈值用于容量规划，导致错误判断。

**修改建议**（old → new）：

> ~~命中率在工作集（频繁访问的数据集合）接近或超过缓冲池大小时急剧下降~~
> 命中率随工作集占缓冲池比例上升而下降，**具体比例取决于访问分布的均匀程度**：在访问高度集中（热点 key 占比高）的场景下，少量缓冲池容量即可覆盖大部分访问；在访问均匀分散的场景下，缓冲池需接近工作集大小才有稳定命中率（"断崖"是否出现及出现在哪个比例，取决于 Zipf 分布参数，无法给出通用百分比）。**建议实测：监控 `Innodb_buffer_pool_reads` 与 `Innodb_buffer_pool_read_requests` 比例**，而非依赖经验比例。

### 2.5 InnoDB 缓冲池"生产典型 8–128GB"（ch4:32）— P2

**位置**：ch4 §4.1 关键数字框："InnoDB 缓冲池：生产典型 8–128GB"。

**现状**：给出了一个跨度极大的范围（16 倍），既无上限解释也无版本标注。

**前提分析**：
- **8GB**：小规模业务/虚拟机/开发测试环境；
- **64GB**：中等规模 MySQL 单机常见配置；
- **128GB 及以上**：大型 OLTP 场景（如金融、电商）配合大容量服务器；
- **无版本标注**：MySQL 8.0.3 起支持**巨型页（Huge Pages）** 和 **开放装甲（OpenArmor）** 内存优化，内存使用效率不同；
- **无硬件前提**：服务器物理内存总量（128GB/256GB/512GB）决定了缓冲池的上限。

**修改建议**：改为：

> InnoDB 缓冲池：生产典型 **8–128GB（受服务器物理内存总量约束），建议值为物理内存的 70–80%**（预留给连接、临时表、操作系统缓存等）。极大规模（数百 GB 缓冲池）需评估 huge page 配置（MySQL 8.0+）以降低页表开销。

### 2.6 Kafka 2014 LinkedIn 基准 200 万次写入/秒（ch1:67）— P1

**位置**：ch1 §1.1.2："LinkedIn 2014 年公开的基准里，3 台廉价机测到约 200 万次写入/秒（Kafka 0.8.1、100 字节消息）"。

**现状**：已标注"Kafka 0.8.1"和"100 字节消息"，但仍有两个缺失前提。

**缺失前提**：
1. **硬件前提（未标注）**：2014 年"廉价机"具体指什么硬件（可能是双路 CPU、16–64GB 内存、SATA SSD 或甚至机械盘）？网络是 1GbE 还是 10GbE？这直接影响该数字在 2026 年的可参考性；
2. **版本时效**：Kafka 0.8.1（2014）→ Kafka 3.x（2026），12 年间架构多次演进，相同硬件上 Kafka 3.x 的单分区吞吐通常高于 0.8.1（更好的批量和零拷贝），但 12 年硬件代际更替使该基准参考价值大幅下降；
3. **消息大小**：100 字节是极小消息，1KB+ 消息的条速率约低 5–10 倍。

**已有标注**：✅ 版本（Kafka 0.8.1）、✅ 消息大小（100B）、✅ 机器数量（3 台）、✅ 标注为"历史参考"。

**修改建议**：扩展标注：

> LinkedIn 2014 年公开的基准里，3 台廉价机测到约 200 万次写入/秒（Kafka 0.8.1、100 字节消息）—— **此为 2014 年基准，2026 年请勿直接套用**（Kafka 3.x 吞吐量通常更高，但硬件代际更替影响更大；实操建议以目标版本的实测数据为准）。

### 2.7 Redis fork 开销 1ms/GB 实例内存（ch4:32 关键数字框）— P1

**位置**：ch4 §4.1 关键数字框："Redis fork 开销：约 1 ms/GB 实例内存"（ch4:32）；正文另有"几十 GB 实例可达数百毫秒"。

**现状**：给出了数量级，但未注明关键前提。

**缺失前提**：
1. **THP（大页）前提**：开启透明大页（Transparent Huge Pages，THP）时，fork 拷贝页表开销显著增加（THP 开启时实测可达 **3–5ms/GB**，关闭时约 0.5–1ms/GB）；
2. **内核版本**：Linux 5.x 内核的 fork 性能优化与 4.x 有差异；
3. **实例内存结构**：内存碎片率影响实际页表大小（`used_memory` vs 实际 RSS）；
4. **COW 期间写入压力**：fork 后 COW 开销与写入速率正相关，纯读负载 COW 极低。

**风险**：读者以为所有 Redis 实例 fork 都约 1ms/GB，在 THP 开启的生产环境中会遭遇 3–5 倍的超时告警。

**修改建议**：改为：

> Redis fork 开销：约 **0.5–1 ms/GB 实例内存**（THP 关闭、Linux 5.x 实测参考值）；**THP 开启时可升至 3–5 ms/GB**，大实例（数十 GB）fork 可能阻塞主线程数百毫秒（生产环境建议关闭 THP：`echo never > /sys/kernel/mm/transparent_hugepage/enabled`）。
