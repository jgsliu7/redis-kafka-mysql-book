### P1（建议修复，影响比较质量）

**P1-1：ch4 与 ch8 的"持久化/写方式"口径不统一**
- **位置**：ch4 表4-3 行"持久化机制" vs ch8 表8-2 行"写方式"
- **问题**：ch4 称"持久化机制"，ch8 称"写方式"，对同一技术现象（追加写 vs 原地改）用了不同维度名；且 ch4 的解释是"AOF 是命令日志 / redo log 是混合日志 / Kafka 日志即数据"，ch8 的解释是"全量重写(RDB)/ 追加与重写(AOF) / 原地改页+WAL / 新消息追加+压实"，语义有重叠但口径粒度不同
- **根因**：ch4 是"存储哲学"视角（内存-磁盘分工），ch8 是"文件格式"视角（磁盘上的字节组织）
- **修复建议**：在 ch4 或 ch8 的解读段加一句说明——"ch4 的'持久化机制'和 ch8 的'写方式'讨论的是同一组取舍的不同层次：ch4 关注数据最终存放在哪一层介质，ch8 关注数据在磁盘上以什么形态写入"；或在索引/术语表加一条关联注释
- **优先级**：中（两章分属不同主题，读者通常不会跨章对比这行，可低优先级处理）

**P1-2：ch4 "随机访问能力"与 ch8 "索引形态"维度语义有重叠**
- **位置**：ch4 表4-3 行"随机访问能力" vs ch8 表8-2 行"索引形态"（两条独立行）
- **问题**：ch4 将 B+ 树的随机访问能力隐含在"随机访问能力"中，ch8 显式拆出"索引形态"和"文件组织"两条；读者若跨章对比，会觉得"ch4 只有一行、ch8 有两行"，误以为 ch4 少了一个维度
- **根因**：ch4 是存储哲学总览，ch8 是文件格式深讲，粒度不同
- **修复建议**：在 ch4 表4-3 该行加一个括号说明——"（索引形态详见 ch8 表8-2）"
- **优先级**：低（两章主题差两级，读者通常不会直接跨章比较）

**P1-3：ch3 解读段第二条"关闭可配置性"描述 MySQL 参数时未对齐 Kafka 和 Redis**
- **位置**：ch3 N.5 解读段第二段
- **描述**：原文——"Redis 给出 SAVE/NOSAVE 两个开关，因为它要同时服务缓存和主存两种用户。MySQL 给出三档参数，让 DBA 按场景在关机和开机之间分摊工作。Kafka 不给单机选项，因为它的关闭本来就是集群事件……"
- **问题**：解读段描述 Kafka 时说"不给单机选项"——这是事实，但表述方式可能让读者觉得"Kafka 在这点上做得不如 MySQL"，而实际上 Kafka 是因为不需要（单机关闭不影响数据一致性，副本会接住），MySQL 才需要给参数让用户选择
- **修复建议**：将"Kafka 不给单机选项，因为它的关闭本来就是集群事件"改为"Kafka 不需要单机选项，因为关闭是集群事件，单机层面的持久化不构成问题——副本机制承担了数据可靠性"
- **优先级**：中（解读段本身的判断是对的，但措辞可以更中立）

**P1-4：ch9 表9-1 与 ch7 表7-1 的"位点语义"行口径差异**
- **位置**：ch7 表7-1 行"故障检测与 Leader 选举" vs ch9 表9-1 行"位点语义"
- **问题**：ch7 讨论集群拓扑和选主，ch9 讨论数据同步和位点，两处都涉及"怎么记录进度"但用了不同措辞；ch7 用"元数据管理"涵盖，ch9 显式列出"位点语义"
- **修复建议**：无需修改，两章主题不同，读者不会跨章对比此行；同口径清单中列出仅供记录

**P1-5：ch6 表6-1 规模（14 行）是其他表的两倍，可能造成"安全维度过细"的感知偏差**
- **位置**：ch6 表6-1（14 行 vs 平均 7 行）
- **问题**：ch6 的 14 行来自安全四维的子维度展开（每个安全维度下拆出 3-4 个子项），其他章的表多为 6-8 行；规模差异可能让读者觉得"MySQL 的安全机制更复杂/更丰富"，而实际上是 ch6 的维度拆得更细，不是 MySQL 本身更优越
- **分析**：14 行中 MySQL 占了更多描述性文字（因为 MySQL 的安全机制确实更丰富：TDE、列级权限、企业审计插件等是 Redis 和 Kafka 原生不具备的），这是技术事实而非偏差

### P2（文本/表达优化）

**P2-1：ch2 表2-2 "人机可读性"行表述不对称**
- **位置**：ch2 表2-2 Redis 列——"✓ nc 连上直接交互"；MySQL 列——"部分（SQL 与默认文本结果集明文，预编译结果集二进制）"；Kafka 列——"✗ 二进制+编码，不可读"
