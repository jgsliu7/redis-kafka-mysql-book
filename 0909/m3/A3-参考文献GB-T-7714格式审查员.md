## 4. 发现的问题（11 个，按 P0/P1/P2 分级）

### P0（必须修，3 项）

**P0-1：4 个"同 [N]"条目违反 GB/T 7714 格式规则**

GB/T 7714-2015 顺序编码制中，**没有"同 [N]"这一格式**。重复引用应完整著录或以尾注/脚注形式处理，不应在参考文献正文条目中使用"同"字引导。

涉及条目：
- `[32] 同 [1]` —— DDIA
- `[33] 同 [22]` —— CAP 定理
- `[35] 同 [1]` —— 综合推荐节，重复引用 DDIA
- `[36] 同 [2]` —— 综合推荐节，重复引用 I Heart Logs

**改写方案（二选一）**：

方案 A（推荐）：将"同 [N]"条目改写为 GB/T 7714 合规的简短引用格式，利用文献类型标识 `[M]` 的特性，在题名后加注"同 [N]"说明：
```
[32] Kleppmann M. Designing Data-Intensive Applications[M]. Sebastopol: O'Reilly Media, 2017.（同第 1 章引用）
[33] Gilbert S, Lynch N. Brewer's Conjecture and the Feasibility of Consistent, Available, Partition-Tolerant Web Services[J]. ACM SIGACT News, 2002, 33(2): 51-59.（同第 7 章引用）
[35] Kleppmann M. Designing Data-Intensive Applications[M]. Sebastopol: O'Reilly Media, 2017.（同第 1 章引用）
[36] Kreps J. I Heart Logs[M]. Sebastopol: O'Reilly Media, 2014.（同第 1 章引用）
```

方案 B：将重复引用从正文条目中移除，在注释中说明"本书多次引用"，由出版编辑决定是否保留。

---

**P0-2：正文引用与文末条目缺少对应关系**

全书正文（10 章 + 序言/后记）未使用 `[N]` 编号引用标注，读者无法从正文直接跳转到文末具体条目。这意味着参考文献部分实质上是"延伸阅读"而非"引用证明"——不符合 GB/T 7714"参考文献"的功能定位。

**整改方向**：可选路径——
- 路径 1（轻量）：在参考文献序言段落中说明"本书正文无编号引用，参考文献为延伸阅读用途"，声明此为技术书惯例
- 路径 2（合规）：全书正文补充 `[N]` 引用（工程量大，涉及全 10 章修改）

**建议**：对于技术类自出版书，采用路径 1，在参考文献页开头加注说明，声明为延伸阅读型参考文献，与正文编号引用型有所区别。此做法在 O'Reilly/Manning 系列技术书中常见。

---

**P0-3：在线资源访问日期格式不统一**

26 个 `[EB/OL]` 条目的访问日期格式存在不一致：

| 格式 | 示例 | 条目 |
|------|------|------|
| `. [日期]. URL.` | `[2026-08-14]. http://...` | 多数条目 |
| `(年份)[日期]. URL.` | `(2015)[2026-08-14]. http://...` | [37] |
| `[EB/OL]. 日期. URL.` | `[EB/OL]. [2026-08-14].` | 全部 |

GB/T 7714-2015 规定：**更新日期/修订日期用圆括号，访问日期用方括号**。因此：
- 有原始发布/修订日期时：`(原始年)[访问日期]`
- 无原始日期时：`[访问日期]`（如 [37] 应为 ` (2015)[2026-08-14]` —— 但缺少前导空格）

**需统一**：全文 `[2026-08-14]`、`[2026-09-09]` 格式统一（已统一为 `[YYYY-MM-DD]`，✅ 基本合格；问题在于与圆括号的原始日期混用时的空格一致性）

**P1-3：机构类作者著录格式需规范**

以机构名（Redis、Apache Kafka、MySQL）作为主要责任者的条目，GB/T 7714-2015 允许直接以机构名作为责任者，但应**不加句点、保持完整机构名**。

当前格式：
```
[4] Redis. Redis Serialization Protocol (RESP) Specification[EB/OL]. ...
```
问题：`Redis.` 后有句点，在 GB/T 7714 中机构名后不加点（除非是缩写句点）。

**建议改写**：
```
[4] Redis. Redis Serialization Protocol (RESP) Specification[EB/OL]. ...
```
改为：
```
[4] Redis. Redis Serialization Protocol (RESP) Specification[EB/OL]. ...
```
实际上，机构名后加句点（`Redis.`）是英文句法惯例，GB/T 7714 §5.1.1 允许"机构名称以其名称表达其责任时，直接著录"——是否加句点取决于对英文标点的接受程度。考虑到本书为中文技术书，建议统一为：

```
[4] Redis. Redis Serialization Protocol (RESP) Specification[EB/OL]. ...
```
→ 可保留（`Redis.` 中的句点是作者名的一部分，与机构缩写不同）；但如果机构名本身是全大写缩写（如 `IBM`），则不加句点。建议对全文机构类作者做一致性审查。

**P1-4：在线资源更新日期/版本日期标注不完整**

部分 `[EB/OL]` 条目有 URL 但无版本/更新日期，而 GB/T 7714-2015 §4.8 规定：电子资源应尽可能标注更新日期或修改日期。

典型问题条目：
- [4] `https://redis.io/docs/latest/develop/reference/protocol-spec/` —— 未标注文档版本（`latest` 是浮动版本，应标注实际版本如 `7.2` 或抓取日期）
- [5] `https://github.com/redis/redis/tree/7.0.0/src` —— 已有版本 `7.0.0`，✅
- [7] `https://dev.mysql.com/doc/dev/mysql-server/latest/PAGE_PROTOCOL.html` —— `latest` 浮动，未标注实际版本

**建议**：对所有 GitHub/官方文档 URL，在 URL 后加 `(访问日期)` 或在正文注释中说明版本。

### P2（建议改进，4 项）

**P2-1：注释分隔符不统一**

条目末尾用 `——`（em dash + 空格）引导阅读说明，如：
```
[1] Kleppmann M. Designing Data-Intensive Applications[M]. ... —— 跨系统比较架构取舍的方法论范本。
```

GB/T 7714-2015 本身未规定"阅读说明"字段的存在，但业界通行做法有两种：
1. `——` + 说明（中文技术书通行，如 O'Reilly/Manning 中文译本）
2. 不用分隔符，直接以句号收尾（GB/T 7714 严格格式）

**现状**：`——` 用于所有 39 条，为统一做法，✅ 不影响合规性但需确认是否符合出版社要求。

**建议**：在参考文献开头加注"条目末的 `——` 后的说明为编者补注，供延伸阅读参考，不属于 GB/T 7714 格式部分"。

---

**P2-2：3+ 作者条目"et al"使用不一致**

GB/T 7714-2015 §5.1.1 规定：作者超过 3 人时，只著录前 3 人，后加"，等"（中文文献）或"，et al"（英文文献）。

检查结果：
- [9] `Mohan C, Haderle D, Lindsay B, et al.` —— ✅ 4 人，只列前 3，加 "et al"
- [12] `O'Neil P, Cheng E, Gawlick D, et al.` —— ✅ 4 人，正确
- [37] `Bailis P, Hellerstein J M, Stonebraker M.` —— ⚠️ 3 人，全列，符合规范 ✅

**结论**：多作者处理均合规，无需修改。

**P2-3：部分条目 URL 使用缩写不完整**

[37] `http://www.redbook.io/` 使用 `http://` 而非 `https://`。建议统一为 `https://`（更安全，也是现代标准）。
