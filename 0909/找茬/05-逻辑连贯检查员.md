## 问题 4
- 位置：chapters/03-lifecycle/chapter.md（3.6 架构启示·启示四「分层 + 依赖先行」）
- 引文：「这三个软件的启动都遵循"配置 → 基础设施 → 核心服务 → 数据恢复 → 对外服务"的顺序。三家分段粒度不同——MySQL 的崩溃恢复就嵌在 InnoDB 启动段里——但每段都能对到这条线上，先后不乱。」——而 3.4 节 Kafka 八阶段的实际排序是「3. **日志管理器启动（恢复的主要环节）。**」在前，「4. **三层网络架构**」「5. **副本管理器启动**」在后；MySQL 的崩溃恢复也在网络层与权限系统段之前。
- 病灶：五步序把"核心服务"排在"数据恢复"之前，但 Kafka（恢复→网络→核心服务）与 MySQL（恢复嵌在引擎段、先于网络层）两家都是数据恢复在前；"先后不乱"是对反序实例下了顺序一致的全称断言，"粒度不同"的补丁盖不住顺序本身的出入。
- 判据：③结论超论据（§1.3af 近亲：全称"都遵循同一顺序"被实例反序）
- 严重度：中
- 改法建议：把五步序改成弱序（"配置在最前、对外服务在最后，中间的基础设施/核心服务/数据恢复各家次序不同"），或直接以"配置→恢复→对外"三点硬边界表述。

## 问题 5
- 位置：chapters/04-memory-disk/chapter.md（4.3 MySQL 的做法·「核心假设」）
- 引文：「所以 InnoDB 的一切设计都围绕一个目标：尽量让访问命中内存，尽量减少对磁盘的随机 I/O。」
- 病灶：论据只支撑弱断言（缓冲池、midpoint、change buffer、AHI 这些缓存相关设计围绕命中率），"一切设计"是全称——本章自己列举的 redo log/undo log、事务、MVCC、双写缓冲的存在理由是持久性与正确性，不是"命中内存"。把断言推到极端（事务回滚设计围绕命中内存吗？），论据兜不住。
- 判据：③结论超论据（§1.3af：全称量词"一切"超出论据覆盖面）
- 严重度：中
- 改法建议："一切设计"改"缓存与 I/O 路径的设计"，或"缓冲池及围绕它的各辅助结构"。

## 问题 6
- 位置：chapters/04-memory-disk/chapter.md（4.6 架构启示·启示二「缓存层该建在哪一层」）
- 引文：「Redis 和 MySQL 自己管理内存，是因为内核的 PageCache 策略无法满足它们在淘汰精度上的需求：Redis 要的是按键、可配策略的淘汰（近似 LRU 与 LFU，见 4.2 节）」——而 4.2 节开头的定位是：「Redis 在官方文档里把自己定义为"内存数据结构存储（in-memory data structure store）"，而不是"带内存的缓存"。」本节同段开头也自注：「Redis 把缓存建在进程内（它自己就是缓存）；」
- 病灶：三处口径打架——4.2 明说 Redis 的内存是正本不是缓存（Redis 不用 PageCache 的首要原因是延迟量级，4.1 的数量级论证正为此设），启示二却把 Redis 自管内存归因于"PageCache 淘汰精度不够"，还把 Redis 塞进"把缓存建在进程内"的并列里。用"淘汰精度"解释一个"内存即正本"的系统，是例证推不出的归因。
- 判据：⑥例证脱节（归因与前文口径不一致）
- 严重度：中
- 改法建议：把 Redis 从该并列中拆出（"MySQL 自管内存是因为淘汰精度；Redis 的内存根本不是缓存、是正本，自管是因为内存即存储本身"），或删去"淘汰精度"归因改回延迟归因。

## 问题 7
- 位置：chapters/04-memory-disk/chapter.md（4.6 架构启示·启示五「快慢介质之间放一层缓存」）
- 引文：「把层次拉开看：CPU 用 L1/L2 缓存内存的数据，MySQL 用缓冲池缓存磁盘的页，Kafka 借 OS 的 PageCache 缓存日志文件，Redis 直接把整份数据放进内存、反过来用磁盘兜底。介质快慢悬殊的地方，就会长出一层缓存，命中率决定整体速度。」
- 病灶：四项枚举里前三项同构（快介质做慢介质数据的缓存层，有命中率概念），第四项 Redis 不同构——它把数据全部放进快介质、磁盘做兜底，没有"缓存另一层"的结构，也就没有"命中率"可言。收口"命中率决定整体速度"对四项做全称，第四项落空。
- 判据：⑤并列破绽（并列项不同构，收口全称失配）
- 严重度：中
- 改法建议：收口限定为前三例（"凡有缓存层的，命中率决定整体速度"），Redis 单独一句（"Redis 干脆取消这一层，让全部数据常驻最快介质"）。

- 改法建议：5.1 总论加限定（"通常每穿过一层都做一次交换——Redis 的看点恰在于把这次交换压到零"），顺势把 5.2 的"零抽象"接成对总论的显式回应。

## 总体印象

四章的论证骨架整体扎实：三家对比的主线清晰，绝大多数取舍论证做到了"机制—代价—适用场景"三件套齐备，作者第一人称案例与收口呼应（如第 3 章开头事故的 3.6 回扣）形式完整。残余断点集中在两类：一是全称收口句（"一切/都/每一分/就看一件事/先后不乱"）系统性超出前文论据，且多在同段或同章内就有自家反例（问题 2、4、5、7、14、16）；二是跨节/跨章的指认失真——启示节的例证指认、章末预告的映射、导读抛出的框架，声称的依赖关系在目标位置找不到对应内容（问题 1、3、8、11、12）。修复方向以收窄断言量词、对齐跨节口径为主，均不动技术事实。
