## 问题 1

- 位置：chapters/04-memory-disk/chapter.md（4.6 启示二"缓存层该建在哪一层"第二段，L282）
- 引文：「Redis 和 MySQL 自己管理内存，是因为内核的 PageCache 策略无法满足它们在淘汰精度上的需求：Redis 要的是按键、可配策略的淘汰（近似 LRU 与 LFU，见 4.2 节），MySQL 要的是抗扫描污染的新老分区 LRU。」
- 病灶：把"淘汰精度需求"写成 Redis 自管内存的原因，对 Redis 不成立——这是用一个下游需求顶替了真正的结构性原因。
- 正确机制：PageCache 缓存的是文件内容，淘汰策略只作用于"文件页缓存"这一层。MySQL 的数据主存形态就是磁盘文件，所以它真实面临"用内核页缓存还是自建缓冲池"的选择，淘汰精度（midpoint LRU）是自建的理由之一，此半句成立。但 Redis 的数据不以文件为主存形态：磁盘上的 RDB/AOF 只是持久化产物，读路径从不经过文件系统，PageCache 根本不在 Redis 的选择集里，谈不上"内核策略满足不满足淘汰精度"。Redis 自管内存的根本原因是它的设计定位就是内存主存的数据结构服务器——数据本身住进程内存；"按键、可配策略的淘汰"是数据住内存之后才产生的管理需求，是结果不是起因。检验：去掉"因为"句，Redis 自管内存仍然为真（且更强地由其定位决定），因果链是假的。
- 判据：⑥单因压缩失真 + ②相关当因果（对 Redis 半句）；亦属 §1.3af"关系误置"变体（需求与原因错挂）
- 严重度：中
- 改法建议：Redis 半句改为"Redis 的数据就住在进程内存里（磁盘只是持久化产物），淘汰是内存主存自带的管理问题"；MySQL 半句可保留"淘汰精度"表述。

## 问题 2

- 位置：chapters/04-memory-disk/chapter.md（4.4"核心假设"节，L190）
- 引文：「这个假设下，Kafka 的设计不支持随机访问，换来几乎零成本的内存管理。这也是 Kafka 不能当数据库查的根本原因：它只能按偏移量区间顺序消费，不能像 MySQL 那样按主键随机点查。」
- 病灶："换来"把两个并列的结果写成交换关系，"根本原因"一句随后落进循环——不能当数据库查的根本原因是它不能随机查，同义反复。
- 正确机制：因果方向是：为吞吐选择 append-only 日志作为存储抽象 →（结果一）日志按 offset 组织、没有按键/按内容的二级索引，只有偏移量定位（`.index` 二分）加局部顺序扫描 →（结果二）数据天然经内核顺序读写，无需用户态缓冲池。不支持随机访问与内存管理简单是同一选择同时导出的两个结果，不是"为省内存管理而放弃随机访问"。且"不能当数据库查"的直接机制是"没有按键的二级索引"，"只能按偏移量区间顺序消费"是它的复述，放在"根本原因"位上构成循环论证。另，严格说 Kafka 并非完全不支持随机访问——按 offset/timeindex 定位就是受支持的随机寻址，不支持的是按键、按内容定位。
- 判据：①因果倒置（交换关系错向）+ ⑥单因压缩；"根本原因"句兼有机制链自循环
- 严重度：中
- 改法建议：改为"日志按偏移量组织、没有按键的二级索引，这是它不能当数据库查的原因；内存管理简单与不支持按键随机访问，都是选择日志抽象同时带来的结果"。

## 问题 3

- 位置：chapters/01-introduction/chapter.md（1.1.3 三条核心设计列表，L49）
- 引文：「**Redis**：用"内存 + 单线程命令执行"换极简与低延迟，代价是复杂聚合要靠客户端多次网络往返拼出来。」
- 病灶：代价被记到错误的账上——"复杂聚合要客户端拼"不是"内存 + 单线程"的代价。
- 正确机制：复杂聚合与多表关联要拉回应用层，源于 Redis 的抽象是"每条命令作用于一个结构的原子操作"、没有跨键查询语言（数据结构服务器只有原语、无查询引擎）——加一个多线程的内存数据库照样没有 JOIN，单线程与否、内存与否都与此无关。"内存"的真实代价是容量受物理内存约束（1.2.1 自己写了）；"单线程"的真实代价是单核吞吐上限与重计算阻塞（1.2.1 也写了）。同章 1.2.1（"复杂聚合与多表关联不是它的强项……这些短板是刻意留下的：这些场景该交给别的系统"）给的是正确归因，本句与之打架。
- 判据：⑥单因压缩失真/错位归因 + ②（去掉因果连词："复杂聚合要客户端拼"独立为真，与"内存+单线程"无因果）
- 严重度：中
- 改法建议：代价句改为"代价是容量受内存约束、单核吞吐有上限"；聚合一条并入"核心抽象是数据结构原语、无跨键查询"的表述，或删。

## 问题 4

- 位置：chapters/01-introduction/chapter.md（1.3.2 看演化，L153）
- 引文：「Redis 从单机到哨兵（Sentinel）再到 Cluster，是因为单机扛不住可用性与可扩展性的双重压力」
- 病灶："双重压力"整段压到三步演化的每一步上，而哨兵那一步只回应了其中一重。
- 正确机制：Sentinel 解决的是可用性（主库故障后的自动故障转移与选主），完全不提供容量扩展——客户端仍连单个主库，数据量与写吞吐上限与单机时相同。可扩展性（分片）是 Cluster 才引入的。链条正确的因果是两步各对应一重压力：单机→Sentinel 回应可用性压力；Sentinel→Cluster 回应可扩展性（及可用性的进一步强化，多主分片各自的故障转移）。原文的压缩方式会让读者把"上了哨兵就能扛更多数据"读出来，这是真实世界里高频的选型误判。
- 判据：⑥单因压缩失真 + ④机制链断裂（把两步各自的原因合并成一个总原因）
- 严重度：中
- 改法建议：改为"是因为单机扛不住可用性的压力，数据量上来后又扛不住可扩展性的压力，于是先有哨兵管故障转移、再有 Cluster 管分片"。

## 问题 5

- 位置：chapters/03-lifecycle/chapter.md（3.2 第三段"AOF 优先于 RDB"的解释段，L48）
- 引文：「AOF 优先是因为它携带的信息严格多于单独的 RDB。」
- 病灶："严格多于"是把"通常更新"绝对化成"严格更多"，可构造反例。
- 正确机制：AOF 与 RDB 的差别不在信息量而在丢失窗口的有界性：AOF（everysec）的恢复点距崩溃至多约 1–2 秒，与 save 触发周期无关；RDB 的恢复点距崩溃可达整个快照间隔（默认 save 规则下可达数分钟）。但"严格多于"不成立：若某次 BGSAVE 的 fork 时点落在 AOF 最后一次 fsync 之后、崩溃之前，RDB 携带的状态就比 AOF 的恢复点更新（AOF 还没来得及刷那一段）。这不妨碍"AOF 优先"是正确工程默认（期望丢失窗口小且有界），但它成立靠的是窗口有界性，不是"严格更多"。紧接着的"完整优先于快"才是对的表述逻辑。
- 判据：③充分/必要混淆（绝对因果量词）+ §1.3af"断言超出证据"（把概率优势说成严格优势）
- 严重度：中
- 改法建议：改为"AOF 优先是因为它的丢失窗口有界（everysec 下至多秒级），而 RDB 的窗口是整个快照间隔"，删去"严格多于"。

## 问题 6

- 位置：chapters/03-lifecycle/chapter.md（3.1 问题的本质首段，L13）
- 引文：「一个数据库启动后如果你还能看到崩溃前那一刻已经提交的事务，是因为它在启动期重放了日志。」
- 病灶：把一个"通常执行的手段"写成看到已提交事务的原因（必要条件化），实际上重放不是必要条件。
- 正确机制：崩溃后还能看到已提交事务，根本原因是提交时 redo log 已先行持久（WAL 的提交协议：commit 等待 redo 落盘），这保证了"已提交"这个事实先于崩溃落在了持久介质上。启动期重放只是把"已写日志、未刷脏页"的那部分补回数据页的手段：若崩溃前脏页恰好已全部刷盘，恢复无需（对那些页的）重放，已提交事务照样可见。因果应为"因为提交时日志已落盘（必要时启动期重放补齐）"，现文把补齐手段当成了可见性的原因。
- 判据：②相关当因果/把充分手段当必要原因（去掉"因为"句，已提交事务可见仍真）
- 严重度：低
- 改法建议：改为"是因为这些事务提交时，日志已经先落了盘，启动期再把没来得及刷页的部分重放补齐"。

## 问题 7

- 位置：chapters/03-lifecycle/chapter.md（3.3 崩溃恢复两段，L96 与 L100）
- 引文：「一进一退之后，缓冲池里的数据页状态正好停在事务一致点上。」（L96）；「InnoDB 做完必要的 redo 恢复、定下事务边界之后，未提交事务的逐条回滚可以留给后台线程，实例不必等它走完。」（L100）
- 病灶：前后两句机制口径有张力——L96 说 redo+undo 之后数据页"正好停在事务一致点"，L100 又说 undo 回滚可以延到对外服务之后，则就绪时刻物理页并未停在一致点上。
- 正确机制：redo 重放完成后，缓冲池里的页恢复的是"崩溃瞬间的物理状态"，其中仍含未提交事务的修改；真正保证一致性的是"事务边界已定 + 未提交记录持有行锁挡住新读 + 后台逐步回滚"。即：一致点是靠锁与延迟回滚在逻辑上守住的服务语义，不是物理页在就绪瞬间"正好停"在某一点。L96 的"正好停在事务一致点上"描述的是理想化终点，与 L100 的延迟回滚机制并排读会让较真的读者卡住。
- 判据：④机制链断裂（终点状态与达成路径的时序没接上）+ ⑤时序错位
- 严重度：低
- 改法建议：L96 改为"一进一退之后，数据页恢复到崩溃瞬间的状态；未提交的部分由行锁挡住、后台回滚收尾，对外呈现的就是事务一致点"。

## 问题 8

- 位置：chapters/02-data-structures-protocols/chapter.md（2.6 小结首句，L225）
- 引文：「访问模式的基本面同样在这里定型：Redis 点查最热所以用哈希；MySQL 范围扫描多所以用 B+ 树；Kafka 几乎只有顺序追加，append-only Batch 就够用。」
- 病灶：小结把三家的结构选择各压成一个访问模式原因，其中 MySQL 半句与本章 2.2.2 自己的口径不一致。
- 正确机制：2.2.2 的口径是"MySQL 要的是通用查询能力，B+ 树把所有常见的查询模式都覆盖了"——点查、范围扫描、排序三类都要支持，B+ 树的胜点是全覆盖而非"范围扫描多"（纯范围场景上 2.2.1 也说了跳表更直接）。"范围扫描多所以 B+ 树"是把"通用覆盖"压成单一负载画像。Redis 半句同样压缩：字典只覆盖键查找路径，有序集合主力是跳表（本章开头排行榜例子用的正是跳表），"Redis 用哈希"以偏概全。作为小结的收束句，压缩可以，但压完与正文论据对不上就成了误导。
- 判据：⑥单因压缩失真（且与正文 2.2.2 自相矛盾）
- 严重度：低
- 改法建议：改为"Redis 键查找最热所以有哈希、有序场景配跳表；MySQL 要点查、范围、排序通吃所以用 B+ 树；Kafka 几乎只有顺序追加，append-only Batch 就够用"。

## 问题 9

- 位置：chapters/04-memory-disk/chapter.md（4.2"内存淘汰的真实实现"首段，L75）
- 引文：「这个方案准确但代价大：每次访问都要动链表指针，访问量上去之后链表操作的 CPU 开销不可忽视。」
- 病灶：近似 LRU 的动因只列了 CPU 一条，漏掉了 antirez 原文的首要动因——精确 LRU 的每对象额外内存开销。
- 正确机制：antirez《Random notes on improving the Redis LRU algorithm》（antirez.com/news/109，2016）给出的完整动因有两条：其一，真 LRU 需要给每个对象额外维护链表 prev/next 指针等簿记信息，对以省内存为第一约束的 Redis 是显著的每键开销（近似方案复用 redisObject 里既有的 24 位字段存时钟，零额外指针）；其二，每次访问移动链表节点的 CPU 代价。书里只写了第二条，把"内存开销"这半边丢了——而本章 2.2/4.2 反复强调 Redis 的第一约束就是省内存，缺了这半条理由反而和全书的约束主线脱节。
- 判据：⑥单因压缩失真
- 严重度：低
- 改法建议：在该句补一小句："还要给每个对象多存两个链表指针，对省内存优先的 Redis 不划算"。

## 问题 10

- 位置：chapters/04-memory-disk/chapter.md（4.5 横向对比"崩溃恢复代价"段，L260）
- 引文：「MySQL 重放 redo log 较快（redo log 设计上就是为了快速恢复）」

- 判据：⑥单因压缩/目的与效果错置
- 严重度：低
- 改法建议：括注改为"（redo log 顺序追加，恢复时按位点线性重放，所以快）"。

## 问题 11

- 位置：chapters/02-data-structures-protocols/chapter.md（2.2.1 SDS"预分配/惰性释放"段末，L36）
- 引文：「这组策略把频繁操作中的系统调用次数降到最低，让 Redis 在最常用的操作上做到摊还 O(1)。」
- 病灶：机制名词错位——这套策略压低的是内存重分配次数，不是系统调用次数。
- 正确机制：SDS 的预分配/惰性释放避免的是逐次 `realloc`；而 Redis 的内存来自 jemalloc 分配器，malloc/realloc 绝大多数在用户态完成（arena 内切分复用），只有向上扩段时才偶尔陷入 mmap/brk 系统调用。把"减少分配次数"说成"把系统调用次数降到最低"，量词对象错了：真正被摊还掉的是分配器调用，系统调用本来就是稀疏事件。摊还 O(1) 的正确主语是"追加操作的内存开销"。
- 判据：④机制链断裂（把分配器行为错接到内核边界）
- 严重度：低
- 改法建议：改为"把频繁操作中的内存重分配次数降到最低"。

## 问题 12

- 位置：chapters/02-data-structures-protocols/chapter.md（2.2.1 intset"编码升级"段，L74）
- 引文：「编码只升不降：哪怕后来所有大值都被删了，编码仍然是宽的。因为降级要多出一次全量重分配，而"删掉大值"的概率太低，不值得。」
- 病灶：给出的差异化理由不构成差异——升级同样要做一次全量重分配，"要多出一次全量重分配"无法解释"升就做、降就不做"。
- 正确机制：真正的成本不对称在触发路径：升级由"必须装下新值"强制触发，重分配躲不掉，属被迫一次；降级则是可选优化——每次删除大值时都要先扫描全数组求剩余最大值、才能确定能否收窄编码，然后才谈得上重分配。即降级多付的是"每次删除都要判定"的常态成本，去换低概率的内存收益。原文把常态判定成本错写成一次性重分配成本，读者照它推理会得出"升级也同样不划算"的结论。
- 判据：⑥单因压缩失真（差异点抓错）
- 严重度：低
- 改法建议：改为"因为降级要先扫一遍剩余元素才能确定新编码，等于给每次删除都加一次扫描，而删掉大值的概率太低，不值得"。

## 问题 13（存疑）

- 位置：chapters/01-introduction/chapter.md（1.1.2 Kafka 段，L40）
- 引文：「它把整个系统构建在追加写日志（append-only log）之上，这种设计影响了后面的 Pulsar、各种事件溯源（Event Sourcing）方案和 CDC（Change Data Capture）管道等一大批系统。」
- 病灶：存疑项。"后面的"统摄三个宾语，但其中两个的时间线不对——事件溯源与 CDC 作为方案/实践早于 Kafka。
- 正确机制：Event Sourcing 的成型表述（Fowler，2005）与 CDC 实践（Oracle/Sybase 的变更捕获，2000 年代初）都早于 Kafka（2010 内部、2011 开源）。Kafka 确实影响了后来一大批以日志为中心的实现（Pulsar、以 Kafka 为载体的事件溯源落地、Debezium 类 CDC 管道），影响判断本身成立；但"影响了后面的……事件溯源方案"读起来像 Kafka 是这些方案的前身，方向反了——它们是"把既有的 ES/CDC 方案落到了 Kafka 这类日志系统上"。属于时序归属含糊，非硬错，故标存疑放低。
- 判据：⑤时序错位（影响方向与先后关系含糊）
- 严重度：低（存疑）
- 改法建议：改为"这种设计影响了后面的一大批系统：Pulsar，以及以日志为载体的事件溯源实现与 CDC 管道"。

## 总体印象

四章的技术因果链整体成色很高：绝大多数"目标 → 结构 → 代价"的推理都能落到可核验的机制上（渐进式 rehash、WAL、doublewrite、受控关闭、midpoint LRU、零拷贝等段的机制描述逐条核对均成立），此前多轮审查明显压掉了大硬伤。本次残余问题集中在两处：一是"归因记账"——把真实存在的代价/需求记到错误的设计元素头上（问题 1、2、3、9、10），二是收束处的绝对化与小结构志压缩（问题 4、5、8、12），其中三条与章节内部自己给过的正确口径互相矛盾，属"正文对、收口错"的同型病。无高危项，但问题 1/2/3 涉及读者会带走的架构观（Redis 为何自管内存、Kafka 为何不能点查、Sentinel 管什么），建议优先处理。
