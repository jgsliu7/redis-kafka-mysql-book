## 逐条裁定

**1｜L128↔L130 字节串字面量相邻两遍**
原文（L130）：体积比二进制大：`SET key value` 变成 [同一串 RESP 数组转义字面量] 有三十多个字节。（该字面量与 L128 数组示例逐字节相同）
裁定：改。
最小改法：L130 中"变成 [完整转义串] 有三十多个字节" → "编码成上面那串字节，有三十多个字节"（拟稿基础上补一个逗号停顿）。
理由：转义串是全章最难扫读的排版，相邻两段完整重印逼读者二次解码；回指的歧义被"`SET key value` 编码成"锁死——L128 的数组示例是该完整体在 2.3.1 的唯一出处，且紧邻上文。

**2｜L23↔L189 RecordBatch 句骨架重演＋"新旧格式可以共存"逐字重复**
原文（L189 段末）：……于是 RecordBatch 把一批消息当成一个不可分割的存储与传输单元，压缩、校验、读写全部以 Batch 为单位，格式还带 magic 版本号让新旧格式可以共存。
裁定：改（段末收缩，且比清单拟议更进一步：magic 半句一并删）。
最小改法：删"，压缩、校验、读写全部以 Batch 为单位，格式还带 magic 版本号让新旧格式可以共存"，句号收在"……当成一个不可分割的存储与传输单元。"
理由：三动词串是 L23"压缩、传输、落盘都以 Batch 为单位"的换词重播，"新旧格式可以共存"与 L118 逐字撞车；magic/共存还是启示四的题眼，留在启示一既重复又抢戏。"不可分割的存储与传输单元"是该句唯一的新海拔，收束其上正好与 Redis 句"换来实现的简洁"、MySQL 句"范围扫描不用回头"形成三家各一句收拍的节奏。若作者坚持保留 magic 一笔，须换措辞避开 L118 原句；本席建议径删。

**3｜版本兼容命题四连播（L23/L150/L181/L193）**
原文（L193）：请求/响应头用 api_key + api_version，让同一集群同时服务不同版本客户端。
裁定：改 L193；不改 L150、L23、L181。
最小改法（L193）："Kafka 有几十种请求类型、以 Batch 为单位收发。请求/响应头用 api_key + api_version，让同一集群同时服务不同版本客户端。" → "Kafka 有几十种请求类型、以 Batch 为单位收发，头部就给每种请求留了独立的版本号。"
理由：L193 是四播中唯一零新角度的一播，且"客户端混版本共存"偏离启示二正题；改为"请求类型多 → 逐请求版本号"的映射表述恰好落回"协议是数据结构的外部映射"。L150 内部两播不判复读——"同一类请求可同时存在多版本"是机制、"3.0 的 Broker 可以和 0.11 的客户端对话"是部署后果，中间有"这意味着"明示层级；L23 是 2.1 概览预告（体裁职能），L181 有"做进格式本身"的新角度，均保留。附注：L23 尾巴"演进能力直接靠版本号字段实现"是四播里最空的一句，但不在本条拟议范围，不扩刀。

**4｜"解析只做一次"四播（L22/L142/L175/L193）**
原文（L193）：预编译 + 二进制结果集，把"解析一次、复用千万次"的优势发挥到最大。

最小改法（若联动）：→ "预编译把解析成本压到一次，二进制结果集把传输体积压到最紧。"

**6｜L157 图注三连"服务"**
