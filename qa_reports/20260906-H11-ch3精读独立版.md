## 七、边缘存疑（两难并列，不硬定罪）

- **E1 L15** "没做完这两件事就退出，下次启动就要补做这些清理工作"——对 MySQL 成立（档位 2→启动补做），对 Redis 缓存场景"落盘没做完"是永久丢失而非补做。两难：通用化表述简洁 vs 以 MySQL 逻辑概括三家。倾向改："下次启动要么补做这些清理工作，要么承担丢失"。
- **E2 L13** "一个数据库启动后如果还能看到……一个缓存启动后看到的是……"——主语漂移（数据库/缓存充当"看"的施事）。两难：口语流畅、拟味轻 vs 严格主语错位。倾向改"启动后你还能在数据库里看到……"。
- **E3 L241** "本章 3.3 节 MySQL 关闭慢的排障、3.4 节 Kafka 受控关闭的超时定位，都依赖这些里程碑日志"——3.3 排障段（L130）实际工具是 `SHOW PROCESSLIST`；里程碑日志在 3.3 的真实用例是 L97 的 `ready for connections`（后台回滚仍在进行）。两难：论点成立但引证半错位 vs 概括性引用可容忍。倾向把引证改指 L97/L155 的用法。
- **E4 表 3-2 Row5** Redis 栏"仅刷脏"——"脏"是 MySQL 脏页词汇，Redis 语境实为 AOF 缓冲/可选 RDB。两难：三栏同用"刷脏"便于对读 vs 跨系统借词失真。倾向"仅刷未落盘部分"。
- **E5（转交）启示二 L229 关闭顺序的三方口径错位。** 启示二："单机系统的关闭是先完成请求、再落盘、再释放"；3.2 实述 Redis 顺序：刷 AOF→SAVE/NOSAVE→关客户端连接→释放（落盘先于关连接）；fig-3-3 侧栏："数据先于连接先于身份"（与 3.2 一致）。图＋正文 3.2 同口径，启示二与之错位；反而 Kafka 顺序（处理完在途请求→……→刷盘）吻合启示二。两难：启示二是抽象概括（"完成请求"可释为整个服务阶段）vs 读者回对 3.2 必卡。倾向加"大体"或改"先停收新请求、再落盘、再释放"。
- **E6（转交）L119** "这些工作对正确性没有任何贡献"——purge/修改缓冲合并"晚做不影响正确性"≠"对正确性没有任何贡献"（purge 终究关乎旧版本回收）。两难：与后句"零正确性收益"构成修辞闭环、锋利好读 vs 措辞过强可辩。倾向"这些工作晚做不影响正确性"。
- **E7（转交）L148** "收发慢也不会饿死处理线程"——网络层慢则 handler 无请求可取，字面即可辩为饿死。两难：对仗句好记 vs 逻辑可挑。倾向"收发慢也不会把处理线程拖死在半途"。
- **E8 L28** "MySQL 是关系型加 WAL 的系统"——压缩过狠（WAL 属 InnoDB，server 层无）。两难：三软件一句一像的排比需要等长 vs 精度。可不改，登记即可。
