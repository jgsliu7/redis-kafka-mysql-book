## 0. 背景原文与提议

现行文本（L35）：

> 模型成立有一个前提：同一条输入在每个副本上必须产生相同的状态变化，执行必须是确定性的。带随机性或依赖本地时间的命令会让三列到不了同一个 S5——Redis 为此在复制链路上改写了哪些命令，见 9.2 节。

作者提议末句改为：

> 而带随机性或依赖本地时间的命令会带来各节点执行同一条命令的结果不一致，所以为了保持最终一致性还需要一些特殊处理，比如Redis为解决此问题就在复制链路上改写了一些命令，具体见9.2节。

## 1. 术语判定（核心）

**SMR 的前提是确定性（determinism），不是最终一致性（eventual consistency）。两者不是同一概念，不可互换。**

- **状态机复制（SMR）**：Lamport（1978，*The Implementation of Reliable Distributed Multiprocess Systems*）与 Schneider（1990，ACM Computing Surveys，*Implementing Fault-Tolerant Services Using the State Machine Approach*）的经典表述：相同初始状态 + 输入按相同顺序送达 + **每个副本对输入的处理是确定性的** ⇒ 终态相同。确定性是**执行性质**：同一个（状态，输入）对必须映射到唯一后继状态，不允许隐式依赖本地时钟、随机数、线程调度。它回答的问题是"同一输入在两台机器上会不会算出同一结果"。
- **最终一致性（eventual consistency）**：弱化的一致性模型，Vogels（2009，CACM，*Eventually Consistent*）与 Dynamo（2007，SOSP）一脉：停止新写入后，经过有限时间，所有读都会返回同一个（最后的）值。它是**可见性/传播性质**：回答"一个已发生的更新何时能被读到"，其成立**预设**被传播的更新本身值是确定的。Dynamo/Cassandra 的最终一致由异步传播 + read repair / anti-entropy 收敛实现，与"改写非确定性命令"毫无关系。
- **二者正交，且因果方向恰好相反**：最终一致性修饰的是**传播时延**上的收敛（异步复制迟早送到）；确定性保证的是**重放语义**上的收敛（送到之后算出同一结果）。若非确定性命令被原样传播，各副本将**永久**持有不同值——连"最终一致"这个承诺本身都不成立。因此"改写命令是为了保持最终一致性"把"满足 SMR 的确定性前提"误挂到"一致性模型的保证"上；正确挂法是"改写命令是为了满足确定性前提、消除分歧、保证各副本收敛到同一终态"。
- **语境自检**：本段上一句刚刚写明"模型成立有一个前提：……执行必须是确定性的"。现行句"Redis **为此**……改写了哪些命令"的"此"干净地回指这个确定性前提；提议版把目的换成"最终一致性"，指代链断裂，且换进来的是另一个概念体系（CAP/一致性模型）的词。

## 3. Redis 事实（源码/文档层面的目的表述）

- 本书 9.2 L57 既有表述（`EXPIRE`/`EXPIREAT` 改写为绝对时间戳 `PEXPIREAT`；Lua 效果复制 effects replication 5.0 起默认；verbatim 7.0 移除）与 Redis 7.x 事实相符，且本书核查轨迹已有背书：docs/verify/verify-results-08.md L79-81 记录 "`EXPIRE key 100` → 复制为 `PEXPIREAT key <absolute_ms>`"，目的表述为"使用绝对时间戳（PEXPIREAT/PXAT）确保主从 TTL 一致性"。
- 源码层面：db.c 的 `expireGenericCommand` 在传播（复制流 + AOF）时把 EXPIRE 家族改写为带绝对毫秒时刻的 PEXPIREAT——理由是相对 TTL 依赖各副本本地时钟与执行时点，独立重放会算出不同到期时刻；t_set.c 把带 count 的 SPOP 的传播改写为 SREM 具体元素（主节点弹出哪些就传播哪些）。
- 文档层面：Lua/EVAL 文档对 verbatim 复写的要求历来是"脚本必须具有确定性"；效果复制的引入理由是"只复制写命令效果"以摆脱对脚本确定性的要求（3.2 引入 `redis.replicate_commands()`，5.0 默认，7.0 移除 verbatim）。
- **口径归纳**：源码注释与官方文档对这组机制的目的表述全部落在"确定性/消除分歧/副本复现相同结果"框架，无一处用 eventual consistency 表述命令改写的目的。
- 「为保持最终一致性」能否成立：**不能作为目的表述成立**。最宽容的辩护是"副本最终要收敛到同一状态"——但那是 SMR 由确定性推出的收敛结论，且 eventual consistency 里的"最终"修饰传播时延而非重放语义。另外还有一处机制归因错位：Redis 复制"异步、传播迟早送达"的性质来自"单向异步"设计（9.2 另一小节），与命令改写无关；提议版把一致性模型层面的功劳记到了确定性机制头上。

## 4. 结论

1. **判定：术语误用，属事实错误级别**（T1 技术准确性 / T2 跨章自洽范畴，不是 C4 文风问题）。三重问题叠加：(a) 概念替换——SMR 前提是确定性而非最终一致性；(b) 机制归因错——异步传播才对应"最终"语义，命令改写对应重放语义；(c) 与 9.2 L57 及全书词汇线冲突，并在 ch9 首次引入与 ch7 同词异义的用法。这不是"合理 nuance"：读者会困惑"改写命令到底保的是哪个性质"。
2. **建议**：不采纳"为了保持最终一致性"措辞，维持现行句。若该句确有其他重写需求，锚定词必须留在"确定性"系（非确定性/分歧/同一终态）；如需软化可写"为了让各副本收敛到同一个状态"——"收敛/同一状态"是 SMR 语境词，不与一致性模型术语撞车。
3. **附带回归点**（若采纳提议版还会连带发生，供调度参考）：
   - 删掉"三列到不了同一个 S5"会断正文对图 9-2 的锚定——fig-9-2.svg 内有 S0–S5 状态标记（S5 为汇合点，重复出现 6 次），这句是图文互证（T5 关切）。
   - "具体见9.2节"丢失数字两侧空格，违反本书引用约定（应为"见 9.2 节"）。
   - 原句"为此"回指前句的确定性前提，指代干净；提议版"还需要一些特殊处理"比"在复制链路上改写了哪些命令"更含糊，信息量回退。
