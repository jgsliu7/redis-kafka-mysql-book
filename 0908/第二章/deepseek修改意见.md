## 1. 建议直接改（多 agent 交叉命中 / 明显硬伤）

### 1.1 清单挤句·主语连跳（L148）

原文：

> 报文里的整数编码分两套：定长小端整数（低字节在前；int<1>/int<2>/int<4>/int<8>）和首字节分档的变长整数（`LengthEncodedInteger`，首字节小于 0xFB 时它就是值本身占 1 字节，0xFC/0xFD/0xFE 前缀分别后跟 2/3/8 字节，总长 1/3/4/9 字节），字符串用长度前缀（`LengthEncodedString`），结果集列信息先发列数和每列的类型/长度元数据，再发行数据（0xFB 不是长度编码，在结果集行里它标记 NULL）。

问题：一句话里塞了四个互不相干的主语（整数编码 → 字符串 → 结果集列信息 → 行数据），每过一个逗号就要重新找"这句在讲谁"。这是"主语偷换"的清单化变体：不是中途换一次，而是连着换三次。参数罗列段是全书高发区。

改法（拆句，不动信息）：

> 报文里的整数编码分两套：定长小端整数（低字节在前；int<1>/int<2>/int<4>/int<8>），以及首字节分档的变长整数（`LengthEncodedInteger`，……）。字符串用长度前缀（`LengthEncodedString`）。结果集列信息先发列数和每列的类型/长度元数据，再发行数据（0xFB 不是长度编码，在结果集行里它标记 NULL）。

问题：前半句逐块复述图里画了什么（看图即得），末句"不用背结论"是读法指令、不是新信息；整段基本重复图注。

改法：

## 2. 改前需复核（单 agent 命中，按铁律需二次核对再改）

### 2.1 归一模板句（"这和 X 是同一个思想/逻辑/思路"）—— L52 / L70 / L160

- L52：`这与前文 SDS 的做法是同一个思想：**用摊还替换集中，把省不掉的工作分摊到后续每次操作里**。`
- L70：`这和 Hash 类型小数据编码 listpack → hashtable 的升级是同一套逻辑。`
- L160：`这和 RecordBatch 在存储层的设计是同一个思路：协议层不做单条操作，是 Kafka 把吞吐放在第一位的必然结果。`

问题：三处用几乎相同的骨架把两个对象判定为"同一个东西"，单句合理，连读三次成了固定收口模具。

改法示例：
- L52 → `前文 SDS 的扩容也是这个办法：把省不掉的工作分摊到后续每次操作里。`
- L70 → `Hash 类型小数据编码的升级路径同样如此：listpack → hashtable。`
- L160 → `存储层的 RecordBatch 同样不做单条操作，协议层也一样。这是 Kafka 把吞吐放在第一位的必然结果。`

### 2.2 巧合副词包装（"恰好/正好"）—— L124 / L138

- L124：`但 Kafka 根本不需要随机点查，写入永远追加、消费永远按序，Batch 恰好和顺序写入、批量拉取这两条最常走的路径对齐。`
- L138：`**但 RESP 的"简单"恰好匹配了 Redis 的核心目标。**`

问题：用"恰好"把设计后果说成"正好撞上"的运气。事实是设计者按目标选的，不是巧合。

改法：
- L124 → `顺序写入和批量拉取是 Kafka 最常走的两条路径，Batch 与它们对齐。`
- L138 → `RESP 的简单，正对上 Redis 的核心目标。`

### 2.3 句内同义补刀 —— L64

原文：`连锁只向后传播，因为每个元素只依赖前一个元素的长度——依赖是单向的，传播也只能单向。`

问题：破折号前的因果已说完整，后面换词重述一遍，信息增量为零。

改法：`连锁只向后传播，因为每个元素只依赖前一个元素的长度。`

### 2.4 总结句提前收口 —— L70 / L94

- L70：粗体总结句 `**数据量小时用紧凑结构省内存，膨胀后自动切换到复杂结构**` 夹在段中，后面又追加"512 门槛"这条新例外，总结落空。建议顺序改为：升级机制 → 512 例外 → 总结 → "所有升级对上层命令透明"。
- L94：`数据结构会随访问模式自动调整。` 同属此型（见 1.3）。

### 2.5 括号取舍标签对 —— L19

原文：`第二，客户端和服务端怎么对话。有三个关键点：发纯文本还是紧凑二进制（可读 vs 紧凑），每条消息独立处理还是批量打包（简单 vs 效率），协议固定还是带版本号可演进。`

问题：三个并列项各拖一个"（A vs B）"标签对，像 PPT 卡片副标题，清单模板感。

改法：删括号，信息已在选项里。

### 2.6 "最容易被低估的是 X"式价值排序 —— L189

原文：`这张表里最容易被低估的是"版本演进方式"一行：……`

问题：先替读者排优先级，再讲内容，属读法指令腔。

改法：`版本演进方式常被忽略：……`

### 2.7 "X 的是 Y"焦点句连用 —— L150 / L165

- L150：`这和 Redis Pipeline 不同：Pipeline 省的是网络往返（RTT，Round-Trip Time），预编译语句省的是服务端 CPU。`
- L165：`文本行换的是人眼可读与实现简单，二进制省的是带宽与解析开销，版本化请求头保的是演进兼容。`

问题："省的是/换的是/保的是"本章连用多次；L165 又是三个同构短句，节奏模板化。

改法（L165 打散对称）：`文本行换来人眼可读和实现简单，二进制省下带宽和解析开销，版本化请求头则保证演进兼容。`

### 2.8 插叙缺一句引导 —— L102

原文：`每个分区有多份副本，同一时刻只有一台 Broker 当 Leader、写入都落在它身上；Leader 宕机就换任，partitionLeaderEpoch 随换任加一，标记的是这批数据出自哪一任。`

## 4. 可复用的检查方法（不需要懂语法）

**动作 A：读出声，逐句三问**

1. 骨架齐不齐？（谁—做什么—落在哪。缺谓语/宾语、或"摊到…里"落点装不下 → 压缩断腿、介词落点乱）
2. 这个"它/这/那"我能不能立刻指认？这段话的话题句盖得住整段吗？（指代、话题句太窄）
3. 这句是在讲内容，还是在教我"怎么读/重点看哪/给现象贴标签"？（助教腔、段末拔高）

**动作 B：段落三测试**

- **遮句测试**：遮住某句，信息量不变 → 它是填充。
- **抽段测试**：抽掉一段若前后仍连贯、但读者猜不出它为什么在这 → 插叙缺一句引导（L102）。
- **收口测试**：一段里像结论的句子后面还有新信息 → 收口位置错了。
