# 第二章语言组织修改意见

日期：2026-09-08  
范围：第二章《数据结构与协议》的语言组织。以下整理本轮已讨论、已核对的四个示例，供修改正文时参考。建议稿尚未应用到正文；行号对应本次审读版本。

第二章部分句子的阅读阻力，来自必要成分被省略、词语搭配不合适、说明顺序被打断，以及连接词没有准确表达前后关系。读者虽然认识每个词，却需要在脑中补成分、调整顺序，才能把意思接起来。这种额外的理解过程，就是“读起来怪”的一个具体来源。

可以把这次检查称为**语言组织检查**：先确认句子把意思交代完整，再看信息出现的顺序和相互关系。现有的去 AI 味分类可以帮助记录问题，实际修改仍要回到每句话本身。

## 1. 搭配错位：成本被写成了次数

位置：[第二章第 201 行](/Users/liu/dev/demos/redis-kafka-books/chapters/02-data-structures-protocols/chapter.md:201)。以下只示范原句的第一分句。

原文：

> 预编译把解析成本压到一次

“一次”计量的是解析动作发生的次数，“解析成本”通常指解析消耗的时间或计算资源。原句把两件有关联的事压成了一件：读者必须自行还原为“解析只做一次，因此减少了反复解析的开销”。

建议改为：

> 同一条预编译语句反复执行时，解析只需做一次。

“同一条预编译语句反复执行”的限定承接本章前面对预编译的解释。它明确了“一次”的适用范围，避免把局部省略改成另一种含糊说法。

**检查问法：这个数量到底在数什么？动词、宾语和数量是否配得上？**

## 2. 成分省略：完整关系被压成了词组

位置：[第二章第 41 行](/Users/liu/dev/demos/redis-kafka-books/chapters/02-data-structures-protocols/chapter.md:41)。

原文：

> 平均 O(log N) 的查找、插入、删除；范围扫描只需沿底层链表前进（O(log N + M)），比红黑树的中序遍历更直接；

“平均 O(log N) 的查找、插入、删除”只是一个名词短语，没有把“这些操作的平均时间复杂度是多少”说完整。后面的“范围扫描只需……”却是完整陈述，两部分接在一起，前半句像从提纲中直接取出的要点。

只需把第一分句补全：

> 查找、插入和删除的平均时间复杂度都是 O(log N)；

后面的范围扫描说明可以保留。“平均”是原文的技术限定，补句时也要保留。

**检查问法：这句话是在完整陈述一件事，还是只列出了几个词？读者需要替作者补出什么关系？**

## 3. 顺序中断：基本结构还没讲完，就插入了实现细节

位置：[第二章第 92 行](/Users/liu/dev/demos/redis-kafka-books/chapters/02-data-structures-protocols/chapter.md:92)。

原文：

> 以默认的 Dynamic 行格式为例：行头存变长字段长度列表（字段长度倒着排、解析指针从右往左走，每读到一个长度就恰好落在下一个字段的边界上，一趟扫完）和 NULL 位图，后面是各列数据。

句子主干是“行头存 A 和 B，后面是 C”。读者刚读到 A，还没看到 B，就进入了一整段解析过程。等括号结束，读者又要找回“和 NULL 位图”是在与什么并列。

可以先交代存储结构，再解释解析顺序：

> 以默认的 Dynamic 行格式为例，行头存变长字段长度列表和 NULL 位图，后面是各列数据。长度列表中的字段长度倒着排，解析指针从右往左走；每读到一个长度，就恰好落在下一个字段的边界上，一趟即可扫完。

这次调整保留了所引句的信息，只把括号中的说明后移。阅读顺序变成“先知道有哪些部分，再理解其中一部分如何工作”。

**检查问法：进入补充说明之前，句子的基本意思已经讲完整了吗？**

## 4. 关系不清：几个并列项共用“所以”，理由却不同

位置：[第二章第 197 行](/Users/liu/dev/demos/redis-kafka-books/chapters/02-data-structures-protocols/chapter.md:197)。

原文：

> Redis 要快，所以 SDS 取长 O(1)、字典做渐进式 rehash、跳表在缓存局部性上付出了代价，换来实现的简洁。

前两项在解释如何降低操作开销，第三项在解释如何为实现简洁接受缓存局部性上的代价。三项都接在“要快，所以”之后，读者会以为它们共享同一个理由，但第三项需要另作说明。

可以拆成两句，保留三项内容：

> Redis 要快，所以 SDS 取长度是 O(1)，字典采用渐进式 rehash。跳表则优先考虑实现的简洁，代价是缓存局部性较差。

这里调整的是因果关系的组织：前两项继续回应“要快”，第三项单独说明它的取舍。

**检查问法：把“因为……所以……”分别接到每个并列项上，关系都成立吗？**

## 一个值得保留的好例

位置：[第二章第 7 行](/Users/liu/dev/demos/redis-kafka-books/chapters/02-data-structures-protocols/chapter.md:7)。

> 读是快了，改分和查名次没有跟着快。

上一段刚讲完“给 score 建索引后，查询变快”，这句承接已经解决的问题，紧接着引出尚未解决的两种操作。接下来要讲什么，读者自然就明白了。

它的顺畅来自信息衔接明确。短句在这里有效，是因为一句话恰好完成了一次话题推进。修改其他段落时，也应保留这种具体、直接的表达。

## 可以复用的四项检查法

| 检查项 | 具体问法 | 本章示例 |
|---|---|---|
| 成分 | 句子把要说的关系交代完整了吗？是否需要读者自行补词？ | “平均 O(log N) 的查找、插入、删除” |
| 搭配 | 谁对什么做了什么？动词、宾语、数量是否配得上？ | “把解析成本压到一次” |
| 顺序 | 基本意思是否先于补充细节出现？读者是否要跨过长说明才能接回主句？ | 行格式说明中，长度列表与 NULL 位图被长括号隔开 |
| 关系 | 并列、因果、转折是否准确？同一个连接词是否适用于后面的每一项？ | “Redis 要快，所以……”同时统领两种不同理由 |

实际检查时，可以先顺着读，标记需要停顿或回读的地方，再用这四项解释卡顿发生在哪里。每次只调整造成卡顿的部分，然后连同前后文重读，确认技术限定和原来的意思都还在。句子长短、括号数量、口语多少都需要结合具体内容判断。
