确认强度、故障条件与一致性不能排成无条件单线

第 109 行

它只是把"主可以完全单点"约束成"主至少有 N 个跟得上的副本"，否则拒绝写入。这是一个事实上的门槛：达不到门槛的写会被拒绝，但已通过的写仍然可能丢失（因为副本是异步追赶）。这背后是 Redis 的取舍：不追求理论上的强一致，但在关键路径上设一道可观测、可配置的弱保证，避免数据在没人察觉时丢失。

第 155 行

半同步（semi-sync）是 MySQL 在异步和强一致之间的中间点：主节点等至少一个副本的 ACK（确认应答；副本 I/O 线程把事件写入 relay log 并落盘后即回 ACK，不等本地回放）才返回成功。它有两档提交时点。AFTER_SYNC（8.0 默认）是先等副本 ACK 再提交，所有副本看到的事务顺序与主一致。AFTER_COMMIT 反过来：先在引擎层提交，再等 ACK。这一档有个危险窗口：事务先在引擎层提交，其他会话已经能读到它；若此刻副本 ACK 还没回来主就崩了，晋升的新主上并没有这笔；之前读到它的会话，等于看见数据凭空消失——这是提交可见性与副本确认之间的窗口，不是隔离级别意义上的幻读。

第 188 行

这正是状态机复制在 MySQL 里的强一致形态：每个事务在主节点发起，经过多数派节点的 Paxos 确认后写入各节点的 binlog，再由各节点本地回放。因为多数派都确认过，所以任何一个少数派节点的故障都不会丢事务：只要多数派存活，已确认的事务就一定在。

第 190 行

代价是延迟：每一次提交都要多走一次跨节点的共识往返。但这是换取强一致的必要代价，是延迟-一致性曲线上靠 CP 的一端。MGR 还把一致性级别做成了参数 group_replication_consistency，默认 EVENTUAL（不额外等待）。从弱到强有几档：BEFORE_ON_PRIMARY_FAILOVER（仅主切换时等追平）、BEFORE（读前等本节点追平）、AFTER（写后等全组追平）、BEFORE_AND_AFTER（读写都等）。读写是否要等本节点追平，按场景选。

有界延迟非异步通用保证；min-replicas准入非逐写确认；半同步AFTER_SYNC与MGR默认EVENTUAL不等于所有副本已应用；unclean可能丢HW以下已确认记录；SMR须相同初态及确定执行；CAP不能由单参数无条件推出。

核查方向：分别核准入、接收、落盘、事务提交与可见性；结合失败条件和版本解释，而非把所有选项排成单一强度曲线。L245 的 unclean 丢失范围已有上方执行稿，其余同族尚待核。

P3 · 待核

MySQL ROW事件、GTID集合及并行恢复

第 133 行

选 ROW 而非语句，是因为语句复制有歧义：UPDATE t SET x = x + 1 在不同副本上可能影响不同行数（如果副本上数据状态不同），还可能因为非确定性函数产生不同结果。ROW 格式把"最终状态变化"作为事实下发，绕开了所有歧义。这和 Redis 处理非确定性命令是同一类思路：在源头把歧义消掉。

第 169 行

GTID（Global Transaction Identifier，全局事务标识）把位点升级成 source_id:transaction_id 的形式：source_id 是发起事务的源节点的 UUID，transaction_id 是该节点上单调递增的事务序号。每个事务在 binlog 里都有一个全局唯一的 GTID。

第 177 行

多线程并行复制（基于 LOGICAL_CLOCK 的组提交并行）提供了一个有效的解法。它利用了主节点上的一个事实：同一组提交（group commit）内的事务，本身就没冲突过（否则不可能同组落盘；主节点把每个事务的锁区间以 last_committed / sequence_number 标记写进 binlog，副本按这些标记划定可并行窗口）。既然它们在主节点上是并行无冲突的，那在从节点上也可以并行回放：这是基于"既成事实"的并行，不需要副本自己再做依赖分析。

第 194 行

新成员加入 MGR 时，状态和老成员差很多，默认先走增量恢复：从现有成员（donor）拉取缺失区间的 binlog 补差。只有补差所需的 binlog 已不可得（被清理）时，才改用 8.0.17+ 提供的 clone 插件（参数 group_replication_clone_threshold 看似按缺失事务数触发，默认值实为 int64 上限，默认配置下从不因缺口大小而 clone）：直接从现有成员物理克隆一份完整的数据目录，跳过漫长的 binlog 回放，克隆完再用 binlog 增量追平期间的新事务。这是"先全量再增量"的标准做法：先克隆拿到基线，再用 binlog 补上这期间的增量，思路和 Redis 的"fork RDB + 期间增量补发"一样。

一行不等于一个event、id<100不必100行；接收与回放非永不阻塞；GTID比较是按UUID的集合而非全局线性101；LOGICAL_CLOCK受依赖追踪模式影响非仅提交组；clone可用性/阈值非必然自动全量；日志保留不足不同于位点丢失。

核查方向：按 MySQL 8.0 核 ROW、GTID 集合、依赖跟踪、半同步与组复制的不同阶段，以及 clone 的启用条件。L135 与 L317 已有上方执行稿，其他相关段落不因此一并通过。

P4 · 待核

Kafka读路径、HW、任期与事务边界

第 214 行

Follower 的 FETCH 请求和消费者的 FETCH 请求走的是同一条读路径（对本地日志段成立，Tiered Storage 的例外见下段）。Leader 不区分对面是副本还是消费者，统一按"给我从偏移量 X 开始的日志"来响应——只有一处读上界的差别：普通消费者被截在高水位 HW 以下，Follower 可以一直读到 LEO（区分标志是请求里的 replica_id 取值：Follower 填自己的 broker id，消费者填 -1）。这种复用让 Leader 端只需要一套日志读取逻辑：副本同步和消费读取共享同一份代码、同一套优化（零拷贝、页缓存命中、批量返回）。第 5 章的分层思想在这里收敛成一个具体结论：读路径不分副本还是消费者。

第 222 行

从同步视角看，LEO 是每个副本的本地位点，HW 是 Leader 据此计算出的"已确认边界"：HW 等于当前 ISR 中所有副本（含 Leader 自己）的最小 LEO，HW 以下才算已提交，消费者才读得到。副本间的同步进度，由 ISR 里最慢的那一个决定。只要有一个副本变慢，HW 就被拖慢；变慢的副本掉队到 replica.lag.time.max.ms 阈值之外就被移出 ISR，HW 重新由剩下的较快副本决定。所以 HW 始终反映"当前 ISR 集合的实际同步进度"，而 ISR 的动态进出是在做可用性与一致性之间的实时权衡。Leader、Follower、ISR 与 HW 的时间关系见图 9-7。

第 231 行

Kafka 用 leader epoch（单调递增的任期号）来截断这种不一致的尾部。每个任期对应一段"权威日志"，落盘到分区的 leader-epoch-checkpoint 文件里（一行 = 任期号 + 该任期起始偏移量）。副本恢复或重新追随时，在 FETCH 请求里带上自己最后一个已知的 (epoch, offset)；Leader 据此判断这段日志是否已被新任期否决，并在响应里回一个 EndOffsetForEpoch（"该 epoch 的权威日志到哪为止"）。副本尾部一旦超过这个权威边界，就干净地截掉。这样老 Leader 的脑裂尾部被切掉，副本状态回到与新 Leader 一致。

第 252 行

Kafka 用 KRaft（Kafka Raft）替代 ZooKeeper 管理集群元数据：KRaft 自 2.8 作为预览特性引入，在 3.3 达到生产可用。元数据本身也是一条 Raft 复制日志（由 Controller quorum 维护），它的复制机制和数据分区的复制同构：都是日志 + 副本 + Leader + epoch（Raft 用 term）。这种统一让 Kafka 在去掉 ZooKeeper 后依然自洽：它复用了自己已有的那一套同步机制。

共享底层读取不等于不区分调用者，事务消费者还有LSO；HW计算非同步时刻ISR实际最小LEO简单恒等；epoch响应字段与协议版本需核；KRaft共性非复用同一套数据复制；幂等不是消费恰好一次，事务可见依read_committed。

核查方向：按 Kafka 3.9 的角色分支与隔离级别区分 FETCH 上界；核 HW 获知/推进、epoch 协议、KRaft 与数据复制差异，以及生产者幂等和消费者事务边界。

章内框架与结尾推论

第 13 行

单机迟早达到容量、可用性或读扩展的上限，加副本势在必行。副本之间的同步强度是一档一档的取舍：异步最快，但主挂了可能丢已提交的写；同步（全等）不丢，但任何一个慢副本都会拖垮写；中间是多数派确认：要多少一致性，就付多少延迟。本书不在此重复这条权衡的全谱推导，直接说工程问题：数据同步到底在同步什么。先把导读里那个问题归位：缓存和数据库谁为准，不是多副本之间的一致性问题——那是正本与派生数据的关系，本章小结与第 10 章会回收这个答案。本章先讲清楚副本之间怎么对齐。

第 311 行

把"导致当前状态的那串操作"按相同顺序重放到副本上，输入序列和执行顺序都相同，终态就必然相同。这不排斥状态快照：追赶落后太多的副本时，三家都用快照打底（RDB、clone、分区日志拷贝），再用增量序列续传。快照决定同步的起始位置，有序重放保证此后每一步对齐。

第 315 行

同步进度怎么表示，是这个机制要解决的头一个问题（三个软件的位点形态见 9.5 解读二）。没有位点，副本断了就无从续传；有了它，增量同步、故障恢复都成了对齐位点的简单操作。多份副本要对齐，靠的就是同一套度量标准。

第 349 行

一致性不是要么有要么无，而是一连串档位上的取舍。这三个软件把档位做成了参数和默认值，让使用者按延迟预算选择。

导读四子问题与小结四部件映射不一；位点不能单独解决日志缺失/脑裂；GTID全局比较大小不成立；延迟预算不单独决定保证；缓存数据库正本的个案应限定不作为所有系统必然模型。

核查方向：对照本章开篇的问题分解与小结逐项映射；状态机复制补初始状态和确定性条件，增量恢复同时考虑位点身份与日志可得性；保留作者具体取舍。
