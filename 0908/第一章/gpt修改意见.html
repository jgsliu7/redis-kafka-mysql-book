T-MVCC-WAL · 待核

MVCC 的可见性条件与日志恢复边界

第 76 行

支撑 MySQL 设计哲学的是一整套为正确性服务的机制。InnoDB 提供完整的 ACID（原子性、一致性、隔离性、持久性）事务、靠 MVCC 实现的非阻塞读、行级锁。MVCC 的原理一句话说清：改一行时保留旧版本，读事务持有一个 Read View 判断哪些版本对它可见（Read View 在事务首次读时拍下快照，记下当时的活跃事务集合；判断方式是沿 undo log 串起的版本链从新到旧，找第一个对自己可见的版本），于是读不加锁、不阻塞写，写也不阻塞读；undo log（回滚日志）里串起来的那条旧版本链，就是它的载体。

第 80 行

这套取向的代价，从提交延迟到调优门槛都摆在明面上：为保证持久性，事务提交要做日志落盘（fsync，把缓冲的写强制刷到磁盘的系统调用）；为保证一致性，写操作伴随 redo log 与 binlog 的内部两阶段提交开销（两份日志分属存储层和服务层，提交时按 prepare、commit 两步对齐，保证崩溃后两边一致）；为支持 MVCC 保留的旧版本链，让长事务拖累性能；调优门槛高，缓冲池、刷新策略、隔离级别都需要根据负载仔细配置。此外，单机扩展有上限，纵向加内存、加 CPU 容易，横向分库分表则代价不菲。

第 158 行

第一，先写日志还是先改数据？ 可靠存储系统的常见做法是先写日志（WAL）。原因是日志是顺序写，恢复时按顺序重放，比直接改散落各处的数据页快得多、也安全得多。

第 162 行

逻辑日志紧凑、跨版本友好，但重放时要重新执行操作，速度慢，还要小心幂等性；物理日志啰嗦、占空间，但重放就是机械地改页，又快又稳。三家各用了一套方案。

第 164 行

MySQL 走 redo log 加两阶段提交，redo log 记的是"页上哪个字节改成什么样"（严格说是物理到页、逻辑到操作的混合日志，详见第 8 章），恢复时机械重放，再配合 binlog 这种逻辑日志做复制。

第 165 行

Kafka 最彻底，数据就在日志里：它没有"日志"和"数据"之分，消费者从日志里读，副本把日志复制过去，连重放回滚这些步骤都不需要了。

第 167 行

三种方案，一条共同主线：顺序写的日志保证故障后可恢复，落盘粒度调节安全与吞吐的平衡。 这条主线贯穿第 4 章（内存与磁盘）与第 9 章（数据同步），并在后续多章里以不同的面貌重新出现。

两席独立通读均识别出以下范围疑点。此处不提供伪定稿，后续以官方文档及对应版本源码确认。

核查方向：Read View 生成时机需区分隔离级别和一致性读；WAL 的落盘先后不能混同内存修改顺序；逻辑/物理日志速度与 Kafka 无需任何恢复工作的总括需核实。先保留原文，不用语言改稿掩盖机制差异。

T-KAFKA · 待核

吞吐、延迟与副本保证的适用范围

第 49 行

- Kafka：用"追加写日志 + 顺序 I/O + 分区并行"换高吞吐与线性扩展，代价是延迟偏高、不适合随机查询。

第 92 行

把日志抽象推到工业级，Kafka 依赖的是一组围绕吞吐设计的机制。分区水平扩展，吞吐随节点数线性增长；磁盘 I/O 走顺序写，配合操作系统的页缓存（PageCache）与零拷贝（sendfile），换来很高的单机吞吐。可靠性靠副本（replica）与 ISR（In-Sync Replicas，同步副本集合）保障，只有落在 ISR 中的副本才算"安全"。

第 94 行

只追加的代价：随机查询不是它的强项；批量与顺序优先，单条消息的延迟也天然高于内存型系统；消息默认按时间或大小保留，删除与更新要靠压实（compaction）这种间接方式实现。这些约束在 Kafka 中被视为合理代价，它优先保证吞吐与可扩展性。

第一，看约束。 任何设计都是在特定约束下的取舍。要理解一个决策，先还原它面对的约束：目标场景是什么、性能要求多高、可靠性要求多严、维护成本能不能承受。Redis 用单线程执行命令，背后的约束是"内存访问远快于网络往返，CPU 不是瓶颈，单线程能省掉所有锁的开销"；MySQL 用 B+ 树而不是哈希索引做主索引，背后的约束是"要支持范围查询和排序，磁盘随机访问昂贵，需要一种能批量读相邻键的结构"。不问约束就评价设计好坏，等于白评；同一个选择换个约束，可能就成了灾难。

第二，看演化。 架构是需求逼出来的。Redis 从单机到哨兵（Sentinel）再到 Cluster，是因为单机扛不住可用性与可扩展性的双重压力；MySQL 从 MyISAM 到 InnoDB 默认化再到 MGR，是因为业务对事务与高可用的要求不断抬高。Kafka 则是从依赖外部 ZooKeeper 走到内置 KRaft（Kafka Raft，Kafka 自带的共识元数据管理），原因是外部元数据依赖在大规模部署下成了运维负担与单点风险。理解"为什么变"，关键是看到约束在变，设计就得跟着变。今天看起来"不合理"的旧设计，往往只是被新约束淘汰了而已。
