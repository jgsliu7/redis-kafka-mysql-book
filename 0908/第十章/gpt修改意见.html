P1 · 待核

正本、恢复来源与消费者进度不能合并为一个保证

第 39 行

> 一个有状态的系统只能有一份数据是正本（source of truth），其他数据都是它的副本或派生结果。副本丢了可以重建，正本丢了就找不回来。

第 41 行

它们用不同的说法讲同一句话。在 Redis 中，内存是正本，RDB/AOF 只是派生的快照，所以 Redis 崩溃可以容忍丢几秒（取决于 appendfsync），但不能容忍内存里的键值对算错。在 MySQL 中，磁盘上的数据页和 redo log 共同构成正本，缓冲池里的脏页只是它们的内存派生数据，所以缓冲池脏页丢了无所谓，已落盘的 redo log 不能丢；innodb_flush_log_at_trx_commit=1 保证 redo log 每事务落盘不丢，双写缓冲则保证"脏页刷盘时不被撕裂"（撕裂的页 redo log 也救不回来）。在 Kafka 中，磁盘上的日志段是正本，PageCache 与消费者偏移量都是派生数据，副本只是拷贝，消费者偏移量甚至可以丢，因为它可以重放日志重新算出来。

物理上只有一份与逻辑权威来源混用；AOF不是单纯快照，脏页尚未持久的修改并非无所谓，双写修复与预防撕裂不同，业务处理进度也不能仅从消息日志重新计算。

核查方向：复用已核Redis持久化、MySQL WAL/双写和Kafka提交offset依据，分别说明运行态、恢复依据、派生数据的重建条件；同族包括表10-2正本行、练习一和小结。

P2 · 待核

分层、批量、访问与WAL的归纳需要核对比较对象

第 49 行

层是工程上对付变化的手法，Redis、MySQL、Kafka 各自用层解耦了不同维度的变化。Redis 的 redisObject 把"语义类型（type）"和"底层编码（encoding）"解耦，同一个 hash 语义底层可以是 listpack 也可以是 hashtable，逻辑层只认 type、存储层管 encoding，于是 Redis 能根据数据大小动态换底层结构而不动上层逻辑，付的代价是一次类型检查的间接寻址。MySQL 的 Handler API 把存储引擎做成可插拔的层，Server 层（解析、优化、执行）稳定、InnoDB/MyISAM 可替换，同一个 SQL 能在引擎间迁移，因为契约落在 Handler 接口上，代价是虚函数调用与跨层上下文（THD）传递。Kafka 把 Log 抽象成接口，UnifiedLog / Partition / Segment 分层，上层 API 不关心 Segment 怎么切，Tiered Storage 能把冷段挪到对象存储而无需改动上层读写路径，同样背上了分层带来的间接性。

第 57 行

Redis 的 pipeline 把 N 次网络往返合并成 1 次；MULTI/EXEC 提供的是原子性而非网络收益（两者通常连用），AOF 重写把碎片化的历史命令重新合并成一份快照。MySQL 的修改缓冲把对二级索引的随机写合并成批量，组提交把多个事务的 redo log 一次 fsync，预读把随机页请求变成顺序预取。Kafka 的 RecordBatch 把多条消息打包成一个存储单元，生产者攒批 + 副本 FETCH 也批量拉，零拷贝（sendfile）让一批数据跳过用户态直接从页缓存到网卡。

第 61 行

这条规律的根，在更底层的存储层次结构里。CPU 的寄存器、L1/L2 缓存、内存、磁盘，本身就是一套"快而小"与"慢而大"交替的分层，每一层替下一层挡掉大部分访问，顺序和批量因此在所有层级上都占便宜。第 4 章启示五讲的是同一件事在软件层的对应：缓冲池、PageCache、Redis 的内存主存储，都是这条老规律在另一个刻度上的版本。图 10-1 把这两个刻度画在了一起。我们在架构上反复遇到的存储取舍，计算机组成里几十年前就给过答案，这也是观察三个软件时最让我在意的一条线索。

编码解耦不表示所有实现代码无需适配，远程存储仍改变Broker访问路径；预读不等于把随机请求直接变顺序，存储层级也不都只是下层缓存。

P3 · 待核

持久性、复制确认、CAP与恰好一次不能排成同一参数强度轴

第 70 行

> 每一次更强的一致性，都是用一次额外的同步等待换来的。代价是明确的，是否接受由设计者决定。

第 72 行

Redis 的 appendfsync 把这个代价标成三档：always（每条命令都落盘，最慢但最不丢）、everysec（每秒落盘一次，开启 AOF 后的默认值）、no（交给操作系统决定，最快但可能丢较多），对应"丢多少 vs 慢多少"。MySQL 的 innodb_flush_log_at_trx_commit（控制 redo log 提交时是否 fsync）与 sync_binlog（控制 binlog 提交时是否 fsync）组成双 1 / 双 0 档位（两个都设 1 为"双 1"，最耐断电；都设 0 为"双 0"，最快但断电可丢），是"持久性 vs 吞吐"的取舍。半同步与异步复制的切换，是"延迟 vs 恢复点目标（Recovery Point Objective，RPO）"的取舍。Kafka 的 acks=0/1/all 配合 min.insync.replicas，是"吞吐 vs 不丢"的取舍。幂等与事务，靠额外的 Broker 状态机和协议往返，达到了"恰好一次"这个更高的一致性档位。

第 74 行

所谓"强一致"都是某个参数从 0 调到 1 的结果。我应用这条规律时，会把这个参数的代价暴露给真正在意它的人（业务方、SRE），让"愿意付多少延迟"和"能容忍多少丢失"成为一次明确的取舍，而不是默认把所有参数调到最严。规律四的另一面：被默认设成最严却没人真正需要的参数，是在浪费吞吐。

第 100 行

维度二：一致性 vs 可用性（CAP 的工程体现）。网络分区一来，你要么写对要么继续服务，没有两全。Redis Cluster 默认偏 AP（归类见 7.2.3 节），分区时持有多数主节点的分区继续服务、少数派分区的槽短暂不可用，故障切换时可能丢失少量已确认的写（异步复制的固有代价）；MySQL MGR 偏 CP，少数派分区直接拒绝写，宁可停服也不写错；Kafka 可调，用 ISR 选主 + min.insync.replicas 控制一致性强度，业务能在 CP 倾向和可用性之间自己调。AP 优先高可用，代价是故障切换时可能丢少量写；CP 优先强一致，代价是分区时部分请求失败。金融核心偏 CP（宁可拒绝服务也不能错账），社交 feed 偏 AP（少量数据可修，但不能不活）。

第 108 行

五个维度不是孤立的，它们会互相牵扯。比如维度一（速度 vs 持久性）和维度二（CP vs AP）常常联动：你越偏持久性，越倾向于 CP。这种联动是真实的工程现实，不必强求每个维度都独立打分。

每一次更强一致性都增加一次等待、参数0改1即可强一致、持久性越强越偏CP，都把不同故障与读取保证混为一谈；每命令/每事务独立fsync和无条件断电不丢也需核。

核查方向：复用本轮已核appendfsync批量刷盘、双1配置、acks/ISR与minISR、半同步和MGR事实，按具体保证正面讲代价；同步表10-1/表10-2及L98/L115/L123/L163/L171直接同族，不消除作者业务取舍立场。

P4 · 待核

位点与故障恢复需要历史范围，不能只比全局数字

第 80 行

一个有状态的系统，运行时都在维护一堆隐式或显式的状态。三个软件的做法如出一辙：把这些状态一一收进显式模型，为每个状态提前写定恢复路径。Redis 启动就是按 RDB/AOF 把状态重放回去。MySQL 把活跃事务、锁等待、LSN 当运行时状态，用 ARIES 式恢复（3.3 节展开的重放 redo 与回滚 undo）当崩溃恢复流程，用 GTID 给复制状态一个全局可比的位点，让从节点确定自己该重做哪些事务、跳过哪些事务。Kafka 把 HW/LEO、ISR、Controller 任期（epoch）当运行时状态，用"按 leader epoch 截断分叉尾部 + Controller 重新分配 leader"当恢复路径，于是 Broker 重启后能精确地界定"哪段日志算数、哪段要丢"。

第 27 行

| 第 9 章 数据同步 | 怎么让两个状态机一致 | PSYNC2（部分重同步 + 全量回退） | binlog + GTID（基于事务的精确位点） | ISR + leader epoch 截断 + acks/幂等/事务 | 复制是用可比的位点（复制偏移量/GTID/偏移量）对齐状态机 |

核查方向：复用第7/9章已核GTID集合、复制历史和任期事实，保留显式建模/可恢复的主张；同族L163和末章总结同步，不引入新的协议推导。
