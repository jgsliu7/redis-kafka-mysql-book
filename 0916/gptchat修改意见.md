## 一、总体结论

**建议先完成关键技术修订与证据补齐，再锁定出版稿；不建议再进行一轮全书风格重写。**

这本书已经形成了清楚的组织方式：让三个软件回答相同的架构问题，再讨论选择及其代价。第 7、9 章对“副本确认、读取可见性、故障转移后的数据保留”的区分，第 9 章对复制历史、续传窗口与净追赶速率的解释，以及第 10 章对权威来源和物理副本的区分，都应保留。这些内容比笼统的“Redis 快、MySQL 稳、Kafka 吞吐高”更有价值。

现在最需要处理的不是零散错别字，而是以下三类问题。

**第一类是会改变读者理解或操作的技术表述。** 例如 RESP 不能被概括为“读到一行就处理一行，不需要等整个命令到齐”；MySQL MEMORY 引擎不能被归入“内存终究只是磁盘页缓存”；Kafka 返回写入异常不能直接推导为“消息没有写入”。这些应先于文风润色处理。

**第二类是正文已经加了限制，但导读、对比表、启示和小结又把限制删掉。** 例如正文区分了复制与持久化，后面又用“不丢、不错”“强一致”“严格多于”等短语做总体判断。终校不能只修机制段，还必须同步修图注与总结。

**第三类是多轮编辑留下的重复与论证过度。** 很多段落先解释机制，随后再说一遍“这是取舍”，图后又复述一次，小结继续重复。问题不是“取舍”这个词不能用，而是后一段没有增加条件、例外、判断方法或作者的新观察。

## 二、技术核查与高优先级修改

### T01｜P1｜RESP 的分帧与命令执行被混为一谈【已核实】

**位置**：`chapters/05-layered-architecture/chapter.md`，5.2.1；联动第 2 章协议部分、图 5-1。

**原文**：

> 用 `\r\n` 分隔……读到一行就处理一行，不需要等整个命令到齐。对 `SET key value` 这种短命令，协议处理几乎是一次零成本的拼接。

**问题**：RESP 的一些头部以 CRLF 结束，但 bulk string 的内容由显式字节长度界定，其内容本身可以包含 CRLF。增量解析与提前执行命令是两回事：解析器可以保存半包状态，命令执行仍需要完整参数及相应检查。“拼接”也不能准确描述接收端的解析工作。

**建议替换**：

> RESP 的类型前缀和长度字段让解析器能够逐步识别输入。bulk string 按声明的字节长度读取，内容可以包含换行或其他二进制数据。输入不足时，解析器保留状态，等待后续字节；完整命令解析并通过检查后，才进入执行路径。

删去“零成本”。第 2 章若使用五类 RESP 类型的概括，应明确这里讨论的是 RESP2 的基本类型，而不是 RESP3 的全部类型。

**依据**：[R1]。

### T02｜P1｜MySQL 权限层级不能被解释为逐层收窄授权【已核实】

**位置**：`chapters/06-security/chapter.md`，MySQL 授权部分及对应权限层级图。

**问题**：需要把“检查对象的范围逐步细化”与“权限逐层收窄”分开。普通授权在适用层级之间是叠加关系；低层级未授予某权限，不会自动抵消高层级已经授予的权限。也不能把一条涉及多个对象、多个操作的 SQL 简化成“命中任意权限就放行”。

**建议表述**：

> MySQL 可以在全局、数据库、表、列及存储程序等范围授权。对于某项操作，有效权限来自适用范围中的授权组合；低层级没有授予，不等于否定高层级授权。MySQL 8.0 的 `partial_revokes` 另提供了特定的全局权限按数据库限制机制，需要单独说明。

图中若用逐级向下的箭头表示检查路径，图注应写“权限检查范围”，不要让箭头暗示低层级天然覆盖高层级。补一个反例即可：已经全局授予 SELECT，不能靠不给某张表单独授权来禁止查询该表。

**依据**：[R2]。

### T03｜P1｜必须区分进程崩溃、操作系统崩溃与掉电【已核实】

**位置**：`chapters/03-lifecycle/chapter.md` 导读及恢复语义；`chapters/04-memory-disk/chapter.md` 持久化部分；`chapters/10-summary/chapter.md` 10.4.3 实验。

**原文定位**：第 3 章以 `kill -9` 解释“没来得及落盘的写入就此丢失”。

**问题**：SIGKILL 终止进程，并不顺带清空仍在运行的内核的页缓存。留在用户态缓冲中的数据，与已经通过 write 进入内核、尚未完成持久化的数据，故障后果不同。因此不能用一次强杀进程实验代表掉电实验，也不能用未观察到丢失证明持久性。

**建议替换**：

> 强杀进程会丢失尚未交给操作系统的进程内状态，但不等同于操作系统崩溃或掉电。已经进入页缓存的数据可能在进程退出后继续写回；它们能否经受掉电，还取决于刷盘是否完成以及存储系统是否兑现持久化要求。

第 10 章实验增加一行：记录故障类型，并在被测系统之外保存“客户端已收到成功响应”的业务 ID 清单，再与恢复结果核对。不要只比较总行数。

**依据**：[R3]、[R4]。

### T04｜P1｜Linux 脏页阈值不是固定缓冲深度，更不是持久化时间上限【已核实】

**位置**：`chapters/04-memory-disk/chapter.md`，4.1“关键数字”中的 Kafka PageCache 长段。

**原文定位**：

> 脏页累计到约 6.4GB……才触发后台刷盘。
>
> 稳态脏页量通常由写入速率×脏页过期时间（默认约 30 秒）决定。

**问题**：该段把多个内核机制压缩成一个过于确定的模型。后台回写不只在达到比例阈值后才发生；还涉及周期性回写、脏页年龄、设备与 cgroup 的写回控制、比例或字节数配置等。`dirty_expire_centisecs` 表示脏数据达到可被相应回写处理的年龄，不是“最多保留这么久”或“必定积累这么多”的保证。写入节流也不宜讲成跨过一个百分比后才突然开始的唯一动作。

**建议处理**：保留参数承担什么职责，删去“64GB 机器先攒满 6.4GB”和“稳态量＝速率×30 秒”的确定化推导。可以改为：

> Linux 通过脏页比例或字节阈值、回写周期和写入节流等机制管理页缓存。参数影响后台回写与写入等待，但不能直接换算为 Kafka 的固定缓存容量或掉电丢失时间上限。需要保证持久性时，应另外检查应用刷盘和副本策略。

如保留默认值，应注明内核与发行版口径，并提醒检查实际配置；不要把某组常见配置当作所有 Linux 环境的事实。

**依据**：[R4]。

### T05｜P1｜MySQL 半同步 ACK 的刷盘语义存在重要证据冲突【待核验，不建议直接反向改写】

**位置**：`chapters/07-cluster/chapter.md` 7.3、7.3.2；`chapters/09-data-sync/chapter.md` 9.3“半同步复制”；`chapters/10-summary/chapter.md` 10.2.4。

**原文**：

> 这份 ACK 只保证事件已写入 relay log 文件，是否 fsync 由副本的 `sync_relay_log` 决定……设为 1 才是确认即持久。

**本轮查到的情况**：MySQL 8.0 官方手册明确描述为：副本在事务事件写入 relay log 并刷盘后才确认。另一方面，本轮读取的 `mysql-8.0.36` 标签源码中，`repl_semi_slave_queue_event` 根据半同步状态与应答标志调用 `slaveReply`，其形参中的同步标志未直接用于这个判断。这些材料提示必须继续检查上游队列写入、flush/sync 和回调时序，不能只看到一个回调就得出整条路径的结论。

**本轮结论**：这是必须核定的冲突项，而不是本报告已经证明的“书稿错误”。本轮没有完成整条刷盘调用链证明，也没有系统调用跟踪实验，不能确认书稿中的参数推导对该发行版成立。

**出版前建议**：

1. 固定发行版和插件版本，而不只写“MySQL 8.0”。
2. 核对 `sql/rpl_replica.cc` 的事件入队与 relay log 刷盘路径、`sql/rpl_handler.cc` 的回调转发，以及 `plugin/semisync/semisync_replica_plugin.cc` 的 ACK 发送路径。
3. 如结论确实与手册不同，正文应给出源码定位及最小复现实验；不能只留下一个与手册相反的无来源断言。
4. 三章统一修改，并同步检查图 9-5。无论最终确认哪种刷盘行为，都应保留“ACK 不等于 SQL 回放已完成”“超时可能降级”“选主必须保留已确认事务”这些边界。

在完成核验前，尤其不宜继续把“默认 10000，所以 ACK 不持久”扩散为全书结论，也不宜机械替换成“半同步在所有配置下必然不丢”。

**依据**：[R5]、[R6]。

### T06｜P1｜Kafka 写入返回异常，不等于消息确定没有进入日志【已核实】

**位置**：`chapters/09-data-sync/chapter.md`，9.4“acks 参数”；联动第 7 章 7.4.3、第 10 章可靠性讨论。

**原文定位**：

> Kafka 在 ISR 不足最低要求时会拒绝这类写入。
>
> 宁可写失败让业务立刻感知……

**问题**：这段指出“不能满足确认要求时，不自动按异步成功返回”的差别是有价值的，但缺少“失败结果是否确定”的下一步。Kafka 既有追加前的副本不足错误，也有追加后的副本不足错误；响应超时还可能使客户端不知道服务端是否已完成写入。错误响应不提供业务回滚保证。

**建议补充**：

> 这里的“失败”是生产者未获得所要求的成功确认，不一定表示消息没有写入。副本不足可能在追加前被发现，也可能在追加后确认阶段发生；响应丢失或超时还会产生结果未知。应用重试时仍需处理幂等与业务去重，不能把异常直接当成“服务端什么都没做”。

作者偏好明确失败而不静默降低保护的判断可以保留，但应比较“确认要求不被自动降低”，而不是暗示失败一定没有副作用。

**依据**：[R7]、[R8]。

### T07｜P1｜Sentinel 故障转移授权不只是简单多数派【已核实】

**位置**：`chapters/07-cluster/chapter.md`，7.2.2；联动相关故障转移图和术语表。

**原文定位**：`quorum 判定客观下线 + 多数派 Raft-like 选举 Leader`。

**问题**：当前解释在常见的小 quorum 配置下容易理解，但遗漏了 quorum 大于多数派时的条件。授权需同时满足多数派以及配置的 quorum 要求，而不是第二阶段就不再受 quorum 约束。

**建议补充**：

> 在已知 Sentinel 集合中，故障转移授权至少需要简单多数派；若配置的 quorum 更大，还必须达到该 quorum。可将要求理解为两者取较大值。例如 5 个 Sentinel、quorum 为 5 时，不是获得 3 票就能执行转移。

同时检查 `docs/book-bible.md` 的术语表：它把 `quorum` 统一译为“多数派”，与正文已经解释的 Sentinel 配置语义不一致。不要让后续术语统一工具把正确的区别又改没。

**依据**：[R9]。

### T08｜P1｜第 4 章用 InnoDB 的特点反驳 MEMORY 引擎，论证对象发生替换【已核实】

**位置**：`chapters/04-memory-disk/chapter.md` 导读；联动第 5 章 5.3.3。

**原文**：

> MySQL 有内存表和 Query Cache……MySQL 的内存终究是磁盘页的缓存，命中才快……

**问题**：后半句讨论的是 InnoDB 缓冲池，不能用于否定前半句提到的 MEMORY 表。MEMORY 引擎确实把表数据放在内存中；第 5 章自己也这样写。因此这不只是简化，而是对比对象前后不同。

**建议替换**：

> 这里要分开讨论 MEMORY 表、旧版 Query Cache 与 InnoDB 缓冲池。MEMORY 表的数据确实驻留内存，但它提供的是另一组表、索引和持久性语义；InnoDB 缓冲池才是磁盘页的缓存。我的比较应落到业务所需的数据结构操作、事务能力、淘汰机制与访问路径，而不能只看是否用了内存。

亲历中的选择结果可以保留，但把“表一摊开争论就结束”的理由改正确。第 5 章介绍 MEMORY 时，也宜补明它支持 HASH 与 BTREE 索引，避免读者误以为只有哈希索引。

**依据**：[R10]。

### T09｜P1｜AOF 优先加载，不等于其信息严格多于独立 RDB【逻辑错误，可由反例直接识别】

**位置**：`chapters/03-lifecycle/chapter.md`，Redis 启动恢复部分；联动第 8 章的独立 RDB 与 AOF base 区分。

**原文定位**：`AOF 优先是因为它携带的信息严格多于单独的 RDB`。

**问题**：不同时间、不同配置、不同备份来源的独立 RDB 与 AOF，不存在天然的严格包含关系。AOF 的加载优先级是一项恢复策略，不能据此推导任意一份 AOF 都比任意一份 RDB 更新、更完整。AOF 内部的 RDB base 与额外生成的独立 RDB 也不是同一份对象。

**建议替换**：

> 启用 AOF 时，Redis 启动按 AOF 恢复路径加载其有效文件组合。正常持续记录的 AOF 通常比周期性快照提供更新的恢复点，但不能仅凭文件类型判断备份的新旧和完整性。独立 RDB 备份与 AOF 内部的 RDB base，需要分别识别。

这里不需要增加复杂教程，只需删去“严格多于”这个不成立的因果解释。

**依据**：[R11]；包含关系的反例分析。

### T10｜P1｜后记中的库存修复方案，不能让“双 1”承担防超卖职责【机制边界与案例完整性】

**位置**：`chapters/10-epilogue.md`，“一个真实的故事”；联动第 7 章导读、第 10 章练习一及选型图。

**原文定位**：`用采用双 1 配置的 MySQL 保存数据正本，Redis 只做预扣减的前置层……账只认 MySQL`。

**问题**：“双 1”主要处理提交日志的持久化，不自动解决并发扣减、订单重复、库存不能为负、预占超时和补偿。把正本转入 MySQL 是架构方向，不是完整的防超卖证明。

**建议在真实方案允许的范围内补三件事**：最终扣减怎样检查库存；订单与扣减如何保持事务或业务一致；重试和 Redis 预占如何去重、释放与对账。可以用一句说明机制，而不必把后记扩成实现教程：

> 最终是否成交，由数据库中的条件扣减和订单状态决定；双 1 保护的是相应日志的持久化。Redis 预占不能直接作为成交依据，重试、超时释放和对账另有处理。

这段只能按作者实际做过的方案补写。**不要为了补技术完整性，虚构团队已经实施了某个机制。** 若当年只做了部分处理，应如实说出当时方案的边界。

## 三、其他技术与论证问题

### T11｜P2｜排行榜导读需要同时修正 filesort、排序语义与性能因果

**位置**：`chapters/02-data-structures-protocols/chapter.md` 导读。

**原文定位**：`把整张表捞出来排序（filesort）`、`名次一条 ZREVRANK`、`改分不过是动几个指针`。

没有可用排序索引时，通常仍需要检查候选行，但 `ORDER BY ... LIMIT` 可以采用 Top-N 等优化；不能把 filesort 一概解释为“所有完整行全部放进内存完整排序”，也不能从名字推导必然发生磁盘排序。建议改成“缺少可用排序索引，需要扫描候选数据并执行额外的排序或 Top-N 选择”。

同时明确名次定义。`ZREVRANK` 从 0 开始，同分成员还有反向字典序次序；“比他分高的人数＋1”则是另一种并列名次口径。迁移数据库排行榜时，不能只比较复杂度而忽略结果语义。

B+ 树适合有序索引的查找和更新，不能因为更新索引有维护成本，就说改分不属于它擅长的范围。真正值得解释的是：InnoDB 常规索引没有直接提供 ZSET 那样的秩查询接口；维护一个带跨度的内存有序结构，在该负载下可能更合适。

保留作者测试，补测试条件或删除“秒级变毫秒级”的泛化暗示。复杂度说明限定为文中讨论的大集合 skiplist 编码，不把小集合的紧凑编码也说成同一实现。

**依据**：[R12]、[R13]。

### T12｜P2｜SDS 不是“不用 char*”，Redis 7.0 的字典字段也需与源码口径一致【已核实】

**位置**：第 2 章 2.2.1。

原文“不用 C 语言的 `char*`”不准确：Redis 7.0 源码中 `sds` 正是 `typedef char *sds`。区别在于它指向的数据前面有长度、分配容量等头部信息，而不是抛弃字符指针。建议改成“仍以字符指针访问数据，但在数据前保存额外头部，不再依靠扫描终止符获取长度”。`sdshdr5` 把长度编码在 flags 中，维持当前的例外说明。

字典段用 `ht[0]`、`ht[1]` 解释双表，作为概念标记可以保留，但 Redis 7.0 的真实字段已包括 `ht_table[2]`、`ht_used[2]` 和 `ht_size_exp[2]`。应注明“下文以旧表/新表表示逻辑上的两张表”，或改用与固定标签一致的字段，避免看起来是在展示不存在的 7.0 结构体。

“每次操作都搬第一个非空桶”也应说明是简化模型，不能承诺每个操作都无条件推进或无限跳过空桶。

**依据**：[R14]、[R15]。

### T13｜P2｜Redis“零抽象成本”与 MySQL“虚函数无法内联”的对比不成立【已核实】

**位置**：`chapters/05-layered-architecture/chapter.md`，5.2、5.2.1、5.2.4、5.3.3；联动第 10 章。

原文包括“跨层不花任何抽象成本”“你不可能……换掉 Redis 的网络层”“每一次定位……无法被内联优化”。

Redis 的命令分派本身用函数指针，7.0 的 `ConnectionType` 也通过函数指针区分连接操作。C 没有 C++ 的虚函数语法，不等于没有间接调用和抽象边界。Redis 不提供与 MySQL 存储引擎完全相同的公共插件契约，也不等于网络模块不能独立重构。

C++ 编译器可以在满足条件时去虚拟化并内联。因此可以说“存在潜在的间接调用开销，具体取决于调用点及编译优化”，不能说“无法内联”。是否是性能瓶颈，需要测量，不宜通过语言特性直接推导吞吐差距。

**建议统一表述**：

> Redis 的常见路径以进程内共享对象和函数调用衔接，不需要为这些层间交互重新序列化数据。MySQL 的引擎接口提供更明确的可替换契约，也可能增加间接调用及跨层协作成本；实际开销取决于实现、编译优化与负载。

**依据**：[R16]、[R17]。

### T14｜P2｜MyRocks 的归属、RocksDB 与引擎发行版要分开【已核实】

**位置**：第 5 章 5.3.3、图 5-4。

原文“RocksDB（Percona 的 MyRocks）等数十种，可以在同一个 MySQL 实例里并存”，容易混淆底层 RocksDB 库、MyRocks 引擎、开发来源以及具体发行版支持。

建议改为：

> MyRocks 是以 RocksDB 为底层存储的 MySQL 引擎项目，最初由 Facebook 开发，部分 MySQL 兼容发行版提供集成。可用引擎取决于发行版、构建和安装配置，并不是 Oracle MySQL 默认同时包含图中全部引擎。

“同一实例不同表可以使用不同已安装引擎”可以保留；删去缺少统计口径的“数十种”。图中应区分默认内置、特定发行版和生态扩展，NDB 也不要画成任何普通 MySQL 安装都现成可选。

**依据**：[R18]。

### T15｜P2｜RecordBatch 是批组织单元，不是所有操作中不可分割的原子单位【已核实】

**位置**：第 2 章 Kafka 数据结构、协议与启示；第 8 章 8.4.3。

针对“不可分割”“消费必须以 Batch 为边界”等概括，应限定场景。RecordBatch 支持共享元数据、批压缩和成批传输，但一个批可以只有一条记录；客户端仍向应用提供记录；消费位置与提交进度按分区 offset 管理；压实还可能过滤记录并重写批。

建议用“批量编码与压缩单元”“日志中的批组织形式”代替无条件的“不可分割单元”。不要把批边界写成业务事务边界或要求消费者一次处理完原生产批。

第 8 章“约三条起才反超”的固定开销比较，应标明仅比较哪几项字段、单条记录的假设、是否压缩及有无 headers；不能让读者当成任意负载的通用阈值。

**依据**：[R19]、[R20]。

### T16｜P2｜页类型标记不等于格式版本号【概念边界明确】

**位置**：`chapters/08-storage-format/chapter.md`，8.4.5、8.6.5、8.6.6。

**原文定位**：`跟 RDB 的 version、InnoDB 的页类型字段是同一类机制`。

类型字段回答“这是什么对象或页”，版本字段回答“按哪一版约定解释这些字节”，两者不能直接互换。它们都参与格式识别，但作用不同。仅有类型、Magic 或保留位，也不能自动推出可以平滑升级或向前兼容。

建议改成：

> RDB 的版本号、Kafka 的 Magic 格式版本，以及 InnoDB 的页类型和格式标记，分别帮助识别格式版本或数据类别。兼容性还需要解析规则、升级限制和旧格式读取路径共同实现。

本章首次出现“向前/向后兼容”时，直接定义“新程序读旧文件”与“旧程序读新文件”，避免不同读者对术语方向的理解相反。对未知格式安全拒绝，可能正是正确设计，不应把“旧程序拒绝新版文件”本身当作失败。

### T17｜P2｜ROW 复制的例子不要暗示它能修复已分叉的初始数据

**位置**：第 9 章 9.3“传播单元：binlog event”。

原文用 `UPDATE t SET x = x + 1` 在副本原有数据不同的情况下解释语句复制的问题。这个例子混入了“初始状态已经不同”这个独立条件，也削弱了前面状态机复制所强调的共同初始状态。

建议把论证放在语句中的非确定性、执行环境差异或缺少确定顺序等情形上：ROW 记录已经确定的行变更，减少副本重新解释 SQL 带来的差异。另补一句：行复制不等于自动修复已有数据分叉，仍可能报错或出现不一致，需要独立核验与修复。

这里不必强行换成一个未经验证的新 SQL 示例；删掉不合适的例子，比再引入一个复杂例外更稳妥。

### T18｜P2｜授权示例应明确初始状态，避免“重复执行后仍是最小权限”的错觉【已核实】

**位置**：第 6 章 Redis ACL 示例。

**原文**：`ACL SETUSER alice on >pwd ~keys:* +get +set`。

书稿已经提示了交互式 redis-cli 与 shell 重定向的差别，这点保留，不必重复报为遗漏。本轮新增的问题是：对既有用户，SETUSER 通常是增量修改，旧密码、命令或键模式授权不一定因此消失。

建议写明“以下在隔离测试环境创建一个此前不存在的用户”；需要演示可重复的完整策略时，显式展示 reset 并解释它会清除原有配置，不让读者对生产用户盲目重置。把 `pwd` 改为明显的随机密码占位说明，而不是可误用的弱口令。

配置后增加 `ACL GETUSER` 或相应允许/拒绝测试，验证一个应允许的键和一个应拒绝的键。不要只展示命令成功返回 OK。

**依据**：[R21]。

### T19｜P2｜消费者提交规则应落到“每分区、下一个 offset”【已核实；属于补足而非推翻】

**位置**：第 9 章 9.4“幂等与事务”。

书稿“只能提交处理完成的前缀”这个方向正确，建议保留。再加一个三行示例，能够避免实际应用中的 off-by-one 错误：

> 同一分区交付了 offset 100、101、102。若 100 和 102 已完成，但 101 未完成，只能提交 101，表示下一次应从 101 继续；三条都完成后才能提交 103。

注明这是示例中的连续 offset。实际日志可能有压实、控制记录等导致的可见记录间隙；“前缀”指该分区已交付记录的完成顺序，不是要求所有整数 offset 都对应一条业务消息。不要把不同分区强行合成一个全局前缀。

**依据**：[R20]。

### T20｜P2｜“MySQL 强一致、不丢不错”的概括需缩小范围

**位置**：第 1 章 1.1.3、1.2.2；第 3 章恢复表；第 10 章导读与汇总表。

`B+ 树 + WAL + MVCC` 不能单独推导出跨副本线性一致性。B+ 树组织索引，WAL 支撑恢复，MVCC 管理版本可见性；事务隔离、提交持久性和复制读取各有条件。第 7、9 章已经做了细分，开头不应又用“换强一致”覆盖这些区别。

建议以“事务处理、持久化与通用关系查询”为定位，保留后面的具体保证。描述 Redis 和 Kafka 时也不要隐含“快或吞吐高，所以正确性较差”的价值排序；应说清各自提供的语义和故障模型不同。

第 1 章把锁、购物车、缓存和库存计数放入同一组时，补一句：这些只是可能的使用场景，对可重建和互斥保证的要求并不相同，不能统一按“尽力而为”处理。

### T21｜P2｜统一“运行时状态、持久化恢复依据、逻辑权威来源”三个概念

**位置**：第 4 章导读；第 8 章 8.1.3、8.3.1、8.4.1；第 10 章 10.2.1。

第 10 章已经写得更严谨：MySQL 的数据页与已持久化 redo 共同提供恢复依据，Kafka 的权威日志可以有多个物理副本。建议以这套表述校准前文。

需要处理的短语包括：“缓冲池只是磁盘页的缓存副本”“Kafka 消息只有一份正本”“磁盘文件只是备份”。脏页可能比对应数据文件页新，日志与数据页承担不同恢复职责；逻辑上一个权威来源，不代表物理上只能有一份文件；AOF 也不是通常意义上的可有可无副本。

建议在第 4 章先定义：运行时由谁处理读写、持久化材料如何恢复、业务冲突时以谁为准。后面使用“正本”时，明确是在讨论逻辑权威来源，不要再用一个内存/磁盘权重比例代替这些关系。

### T22｜P2｜量化数字需要说明是测量、推导还是示意

**位置**：第 2 章导读；第 4 章表 4-1及“关键数字”；第 8 章压缩比及批开销。

建议集中处理以下数字，而不是在每句话后堆“取决于具体情况”：

- 排行榜“秒级/毫秒级”：给出数据规模、索引、SQL、机器与执行计划，或改为无绝对时间的亲历描述。
- “InnoDB 生产典型 8—128GB”“同价位磁盘容量是内存上百倍”：没有统计口径或选定产品对比时，删去精确范围与倍数。它们不是机制成立的必要前提。
- “2—6 倍压缩比”：注明来自哪组数据、压缩算法和级别；没有数据就写“压缩收益依内容而变”，不保留像测量结论的范围。
- “约三条记录起 V2 反超”：给出明确字段口径和假设，否则删去固定转折点。
- 硬件数量级表：可以作为教学示意保留，但不要把示意值同时称为“生产典型”。延迟、吞吐、请求大小、并发数与缓存状态应分开。

第 9 章 `覆盖时长＝保留字节数÷写入字节速率` 以及 `B/(C-W)` 的净追赶模型，是解释了前提的推导，应保留。这类数字比无来源的“生产典型”更符合本书定位。

### T23｜P2｜优雅关闭不等于完成每一个已接收请求，也不一定生成快照

**位置**：第 3 章“关闭的本质”、对比表与架构启示；序言“怎么关闭不丢请求”。

关闭流程可能完成、拒绝或回滚请求，还可能出现客户端未收到最终响应的结果未知。MySQL 的事务回滚、Kafka 的职责交接，也不能统一归为“做一次状态机快照”。本章自己的具体机制比这个总括更准确。

建议改成：

> 优雅关闭要停止接受新工作，按协议处理在途请求，完成必要的持久化与职责交接，再释放资源。它尽量减少状态损失和不确定结果，但不能替代客户端的超时与重试处理。

检查表格里的 `SAVE/NOSAVE`：NOSAVE 主要影响是否生成 RDB，不能写成所有持久化都可被它跳过；正文对 AOF 的说明已有区分，表格应跟上。避免把任一固定关闭宽限时间写成普遍安全值。

**依据**：[R22]，并与本章已经列出的 MySQL、Kafka 关闭语义互校。

### T24｜P2｜版本基线需要细到足以支撑具体断言，而非改追最新版本

**位置**：序言或第 1 章的阅读说明、参考文献、各章源码与配置断言；范围外联动 `README.md`、`docs/book-bible.md`。

“Redis 7.x / MySQL 8.0.x / Kafka 3.x”作为覆盖范围可以保留，但不足以独立支撑每个默认值和源码字段。本书已经分别涉及 Redis 7.0/7.2/7.4、MySQL 8.0.20/8.0.26/8.0.30、Kafka KRaft 与 Tiered Storage 的不同阶段。

建议增加一张简短的“阅读基线”：源码示例按哪个固定标签；机制描述覆盖哪个版本范围；超出基线的特性如何标注。书稿中已经明确使用的 Redis 7.0.0、MySQL 8.0.36 和 Kafka 3.9，可以据实际核验记录整理，而不要事后声称所有例子都在它们上运行过。

保留历史版本作为架构样本完全合理，没有必要为追新重写全书。应删改的是“当前主流稳定版”等易失效标签，以及没有标明是历史升级建议的旧补丁版本推荐。

### 第 6 章还应补一次“安全论证”检查

这部分不是要求增加更多安全术语，而是避免推理跳步。

首先，不要把“内网”本身当成可信的充分理由。内部服务也需要按主体、权限与连接路径明确控制；保护强度可以依威胁模型调整，但不能从“只在内网”直接推出“可以不做身份认证”。

其次，审计采样与异步输出需要说明丢失策略。性能诊断可以抽样；用于关键操作追责的审计记录是否允许丢失，应先由场景要求确定。异步写出还要回答队列满了怎么办、进程崩溃时缓存记录怎么办，而不是把“异步”本身写成兼得方案。

最后，“Redis 为什么不提供某种角色机制”“Kafka 为什么选择某种认证”等设计动机，没有原始材料时，应明确是作者根据架构所作的解释，不要替项目作者下确定结论。参考 [R23] 的威胁边界思路即可，不需要把本书扩成安全实施手册。

## 五、语言、文字与“AI 味”专项意见

### 5.1 不要把“AI 味”处理成词语封禁或作者身份鉴定

仅凭措辞不能可靠判断某段是否由 AI 生成。本轮指出的是可观察的阅读问题：重复、空泛结论、过度对称、论证跳步、故作权威和同一节奏反复出现。

本书的第一人称经验，是定位的一部分。**不建议把“我做过”“我会先问”“这次吃了亏”等一律改掉，也不建议为降低 AI 味增加未经作者确认的事故和人物。** 真正值得保留的是当时的错误判断、决策依据与仍未解决的限制，而不是规定每章必须拥有同样结构的“踩坑故事”。

### S01｜序言保留个人起点，减少对正文的提前复述【P3】

当前序言同时解释横向学习、架构与使用的差别、三个层次、读者对象、AI 时代价值；第 1 章又重复其中多项。建议序言重点留下“为什么想写、后来为什么改用横向观察、希望读者形成什么习惯”。软件机制的概览交给第 1 章。

原文“这是永远都不会过时的取舍之道”可改为：

> 具体方案会变化，但识别约束、比较代价的方法，仍值得反复练习。

这是收窄论断，不是否定作者对长期价值的判断。

### S02｜删去与核心议题无关的时代口号【P3】

**位置**：序言。

“远古编程时代”“后端工程师（这是古老的叫法，也许以后不存在了）”会把读者引向岗位是否消失的另一个争议，本书后文并不展开。建议删掉括注，把“无论……时代”改成“工具变化并没有取消架构决策中的现实约束”。

“多用 AI 帮你快速了解”可保留为学习建议，但补“关键机制回到官方文档核对”，与后记的技术责任说明一致。

### S03｜自谦不应替代清楚的表达【P3】

**位置**：序言“第二层”。

原文“受限于我有限的表达能力，我可能无法准确传递这种感悟”既有“受限／有限”的重复，也在读者开始阅读前削弱预期。建议改为：

> 这部分很难靠一句结论讲清，我会把每种选择所面对的条件和代价尽量展开。

末句“是为序”与本书现代技术散文的约定不一致，可直接删除，不需要另补一条格言式结尾。

### S04｜每个机制不必再配一句“这就是取舍”【P3】

**位置**：第 2—9 章机制段落、横向解读与架构启示。

常见节奏是“解释收益—解释代价—这是一个取舍—图中又显示这个取舍”。收益和代价已经具体说明后，最后一句往往没有信息增量。

判断是否保留的标准：它是否新增了适用条件、反例、选择依据或作者实际判断？如果没有，删去即可。不要简单统计“取舍”出现多少次，更不要把它全部换成“权衡”“折中”来掩盖重复。

### S05｜保留章节路标，减少图前图后的机械复述【P3】

**位置**：各章“下面这张图……”“图中可见……”“这张图把上面几句画出来……”等段落。

图前说明读者该看什么；图后解释最容易误解的关系。两者不要都复述图中对象的名称。第 8 章图 8-1 的“权重对比”，还应先明确是否存在可定义的权重指标，不能把图形面积当成事实比例。

例如图 9-4 后，与其再复述“窗口内增量、窗口外全量”，不如直接保留后文区分“历史还在不在”与“副本追不追得上”的预算解释。这才是图后的增量信息。

### S06｜抽象结论改成可识别的条件，而不是换一组口号【P3】

**位置**：第 5 章。

“**MySQL 顶上的分层边界是虚的**”建议改为：

> 连接层与服务层共享 THD，因此职责虽然分开，状态访问仍有较强耦合；独立修改这些模块时，需要检查共享字段及其生命周期约定。

“**接口稳定了，实现可以一个一个换，而不会牵一发动全身**”建议改为：

> 接口稳定可以缩小修改范围，但还需要验证行为语义、错误处理和资源管理是否兼容。

后一种表达没有前一种响亮，却更能指导读者识别实际问题。

### S07｜把“永远、全都、只有、零成本”留给确实成立的命题【P2/P3】

具体候选包括第 2 章“随机访问几乎免费”、第 5 章“跨层不花任何抽象成本”、第 8 章“格式发布即定型”，以及第 10 章某些“规模可控就要简单、需求多变宁可复杂”的二选一判断。

“随机访问几乎免费”可改为“相较磁盘，内存随机访问不需要设备寻道，但仍受缓存局部性和内存访问延迟影响”。

“格式发布即定型”可改为“格式发布后，修改必须考虑已有文件和旧解析器”。

不要在每句话结尾添加“取决于实际情况”。应指出究竟取决于哪一个条件；指出后也不必反复补同一层免责声明。

### S08｜减少不公平的对照，避免让另一个方案只承担缺点【P2/P3】

排行榜、内存表、接口抽象等例子都有这种风险：被替换的方案只写开销，选中的方案只写最短路径，然后用“争论结束”收束。

建议同一例子至少对齐目标与语义。例如排行榜同时核对名次定义、更新与查询比例、数据量及持久性要求；分层同时讨论调用成本、可替换范围和维护收益。作者可以坚持自己的选择，但读者应能看见它在哪些条件下成立。

### S09｜架构启示要提出选择依据，不必重新概括三家实现【P3】

第 2—9 章的“横向对比—架构启示—小结”容易连续总结三遍。建议保留当前章节模板，但重新分工：对比段解释差异；启示段回答作者面对新项目会先验证什么；小结只收束本章问题。

例如“日志与位点可用于恢复”已经在机制段解释过。启示可以进一步问：历史是否可核对、日志保留窗口是否覆盖中断、恢复吞吐能否超过新增写入。没有新增判断时，不必为保持相同条数继续扩写。

### S10｜作者声音应保留，但避免变成每段的固定收口【P3】

“我设计系统时先问……”“我会先想清楚……”有真实判断时应保留；若只是把上一句一般原则改成第一人称，就没有增加作者声音。

例如第 8 章的文件兼容事故，可以保留当时漏掉的具体约束；后面不必再多次重复“我先把兼容性想清楚”。删去重复句，比把全部第一人称改成客观说明更符合本书定位。

### S11｜第 10 章与后记不要反复宣布结束【P3】

第 10 章已经总结五条规律、给练习、给自检表、给学习建议并收束全书；后记又复述规律、故事、下一步行动和总结。建议后记集中在作者经历与尚未解决的判断，不再完整重讲五条规律。

“使用者—理解者—设计者—创新者”四阶段图可以作为作者的自我观察，但不宜把它写成普遍的职业等级。它与全书核心技术论证的关系较弱，若最终版面紧张，优先压缩这一部分，而不是删具体机制的边界。

### S12｜出版文字与格式统一清单【P2/P3】

1. **中英文间隔**：序言中的“有了AI”“多核CPU”“学习Redis”等，与正文章节间隔风格不一。统一为“有了 AI”“多核 CPU”“学习 Redis”。代码、URL 和标识符不要做机械插空。
2. **引号**：叙述文本的直引号与中文弯引号统一；代码字符串、协议示例中的 ASCII 引号保持原样。
3. **单位**：确定 KB/MB 是按十进制还是二进制使用。描述 16 KiB 页、1 MiB 配置时可以给出字节数；不应把代码里的配置字面量统一替换成出版单位。
4. **标识符**：`PageCache`、`page cache`、`页缓存` 选择稳定的叙述写法；`MEMORY`、`InnoDB`、`MyISAM`、`MyRocks`、`RecordBatch` 等按专名统一。
5. **flush 与 fsync**：项目术语表直接把 flush 译为“刷盘”，有可能再次混淆用户态缓冲写出、进入内核和持久化同步。建议按对象和调用语境解释，不做一对一机械替换。
6. **小节引用**：统一“第 7.3.2 节”或出版社约定的形式，避免“见 7.3”“第 7 章 7.3.2 节”等多种格式混用。
7. **相对日期**：后记“去年”由作者确认实际年份后改成明确年份，避免新版出版后时点漂移。“今晚就动手”可改为“选择一个隔离实验开始验证”。
8. **代码标注**：区分“可直接执行”“仅示意”“源码节选”；伪代码不能让读者误认为是固定版本的原始结构体。

本轮未建立可靠的逐字机械校对统计，因此不报“发现多少处错别字”之类数字。可定位的间隔、引号、重复和表述问题已经列出；最终排版产生的断行、表格溢出和图中文字错误，仍需对成品检查。

## 八、建议保留、不应在下一轮又改坏的内容

以下内容在当前稿中已经有价值，不建议为了“更简洁”“更有冲击力”再次删掉边界。

1. 第 7 章不把 Redis Cluster、MGR、Kafka 简单归成三个 AP/CP 标签，而是比较哪些操作在什么条件下可继续。
2. 第 9 章明确区分 `min-replicas` 准入门槛、`WAIT` 对此前写入的确认等待，以及落盘保证。
3. PSYNC2 同时核对复制历史与字节位置，不把所有 offset 当成可跨历史比较的数字。
4. backlog 覆盖窗口与副本净追赶能力分开计算；`C > W` 的条件不能为缩短文字而删去。
5. MGR 的组内排序与认证，不等于每个成员同时应用完成；跨成员读取有独立一致性配置。
6. Kafka 幂等生产不等于业务去重或外部系统恰好一次；幂等与事务不是同一开关。
7. 第 8 章已经区分独立 RDB 与 AOF 内部 RDB base，也已经标注旧单文件重写图的历史范围。
