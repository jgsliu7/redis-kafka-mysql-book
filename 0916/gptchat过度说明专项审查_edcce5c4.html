4.1｜关键数字：Kafka PageCache
可选精简
局部压缩
GitHub 原文 ↗chapters/04-memory-disk/chapter.md
Kafka PageCache：Linux 默认 vm.dirty_background_ratio=10%、vm.dirty_ratio=20%。脏页占比达到前者时，内核 flush 线程异步后台刷盘、写进程不阻塞；达到后者时，写进程被同步阻塞强制刷盘。这个百分比的分母是可用内存（free 页加可回收页，不是总内存），64GB 机器内存空闲时脏页累计到约 6.4GB（按 10% 计）才触发后台刷盘——这个数字是触发线，不是一块预留的缓冲区深度，内存吃紧时随可用内存一起缩小，写满前内核批量刷盘；6.4GB 还是机器级全局阈值，多盘按写入带宽份额分摊，稳态脏页量通常由写入速率×脏页过期时间（默认约 30 秒）决定，JBOD 单盘对应的窗口更小。这是 Kafka 不强制 fsync 仍能达到磁盘吞吐上限的物理基础。
Kafka PageCache：由操作系统安排回写。 Kafka 借助页缓存合并写入，内核按回写策略把脏页写回磁盘。脏页积压过多时，写入也会受阻。

5.2.1｜再次介绍 RESP
建议精简
局部压缩
GitHub 原文 ↗chapters/05-layered-architecture/chapter.md
Redis 与客户端之间用 RESP（REdis Serialization Protocol，Redis 序列化协议）通信。RESP 的设计极简：每段数据用前缀字符区分类型（+ 简单字符串、- 错误、: 整数、$ 批量字符串、* 数组）；简单类型以 \r\n 结尾，批量字符串按声明的字节长度读取，内容可以包含换行等二进制数据。这种结构让解析器可以边接收边解析：收齐一段处理一段，不用等整个命令到齐；完整命令解析通过后，才进入执行路径。对 SET key value 这种短命令，协议处理的开销很小。
Redis 与客户端之间用 RESP（Redis 序列化协议）通信。类型和长度信息使解析器能够边接收边解析，收齐一条命令并通过检查后再执行。具体编码见第 2 章，这里关注网络处理怎样衔接命令执行。

练习二："日志采集系统，要不要上 Kafka 的事务？" 先看日志场景能容忍什么：如果少量重复可以由消费端去重处理，也能接受一定乱序，又不要求跨分区原子写入或输出与消费进度一起提交，那么 Kafka 事务增加的 Broker 状态、提交协议和隔离读取开销，就换不回对等的业务价值。用规律四（看可靠性代价）的判据：enable.idempotence=true（在 Kafka 3.9 中默认开启，未设置冲突配置时无需手动打开）可排除同一生产者会话内因重试造成的重复写入，并维持分区内重试顺序；它要求 acks=all、重试次数大于 0，且 max.in.flight.requests.per.connection 不超过 5，只有显式设置 enable.idempotence=true 时，冲突配置才会报错；如果只是依赖默认开启，冲突配置可能让幂等性被关闭。在这些约束下，再上跨分区事务就是过度设计。
练习二："日志采集系统，要不要上 Kafka 的事务？" 先看日志场景能容忍什么。如果业务允许的少量重复可以由消费端去重，也能接受一定乱序，又不需要跨分区原子写入或把输出与消费进度一起提交，事务增加的开销就未必值得。生产者幂等可以处理重试造成的重复追加，但不等于业务去重，也不会自动开启事务。用规律四的判据：先明确需要哪种保证，再决定是否承担事务的状态与提交开销。
