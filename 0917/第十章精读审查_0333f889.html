C10-04
10.2.2｜分层规律中的实现清单
建议调整总结密度原章 · 0333f889
chapters/10-summary/chapter.md
层是工程上对付变化的手法，Redis、MySQL、Kafka 各自用层解耦了不同维度的变化。Redis 的 redisObject 区分"语义类型（type）"和"底层编码（encoding）"，同一种 hash 类型，底层编码可以是 listpack，也可以是 hashtable。编码转换保持命令的语义，内部实现仍需识别和处理具体编码，引入新编码时还要适配相关代码。MySQL 的 Handler API 把存储引擎做成可插拔的层，Server 层（解析、优化、执行）通过共同接口访问 InnoDB/MyISAM；引擎能力不同，同一个 SQL 能否迁移仍取决于它使用的功能，代价是虚函数调用与跨层上下文（THD）传递。Kafka 通过 UnifiedLog / Partition / LogSegment 等对象分离职责，分段细节由日志层管理。Tiered Storage 保持客户端按分区和 offset 读写日志的接口，在 Broker 内增加远程段的访问实现，同样背上了分层带来的间接性。
分层要隔离具体的变化。Redis 区分数据类型与底层编码，让内部表示可以改变，而命令语义保持稳定；MySQL 用 Handler 接口分开 SQL 处理与存储引擎；Kafka 在增加远程存储后，客户端仍按分区和 offset 读取日志。它们保留的是对外约定，把需要调整的实现放在内部。

第 5 章已说明 THD、编码适配、引擎能力与远程日志对象。本段不必再列这些细节；留下三种“什么变、什么不变”的例子即可。后面作者先抽接口的判断保留。

10.2.3｜例子应当共同说明顺序与批量
建议调整例子与论点原章 · 0333f889
chapters/10-summary/chapter.md
Redis 的 pipeline 把 N 次逐条等待合并成一批请求的等待；MULTI/EXEC 提供命令不被其他客户端请求穿插的执行保证，两者可以连用。AOF 重写根据当前数据生成恢复所需的精简表示。MySQL 的修改缓冲暂存适用的非唯一二级索引页修改，在页读入时合并，减少立即读取这些页的随机 I/O；组提交让多个事务共享日志刷盘，预读则把预计将访问的页提前读入。Kafka 的 RecordBatch 把多条消息打包成一个存储单元，生产者把消息积累成批，副本 FETCH 也批量拉取；符合条件的日志发送路径通过零拷贝（sendfile）减少用户态数据复制。
Redis 的 pipeline 连续发送多条命令，减少逐条等待网络往返。MySQL 的修改缓冲延后适用的二级索引页修改，减少立即读页的随机 I/O；组提交让多个事务共享日志刷盘。Kafka 把消息组织成 RecordBatch，生产与副本拉取都可以成批进行。它们共同做的，是把原本反复发生的开销合并承担。

MULTI/EXEC 的执行隔离、AOF 重写的日志压缩和 sendfile 的少拷贝各有价值，但不都在直接证明“顺序与批量”这一条。不是说原机制错误，而是总结需要选更对应的证据，避免重新罗列所有优化。

C10-07
10.2.4｜刷盘档位不必再完整复述
建议调整跨章重复原章 · 0333f889
chapters/10-summary/chapter.md
Redis 的 appendfsync 提供三种刷盘策略：always（每批写命令追加后刷盘，返回前等待完成）、everysec（约每秒刷盘，开启 AOF 后的默认策略）、no（不主动调用 fsync，交给操作系统刷盘）。这是持久性与写入开销的取舍。MySQL 的 innodb_flush_log_at_trx_commit 控制提交时 redo log 的写入和刷盘，sync_binlog 控制 binlog 的刷盘；两个都设为 1 是"双 1"，都设为 0 是"双 0"，此外还有其他组合。双 1 在提交确认前等待相应日志落盘，组提交可以让多个事务共享刷盘；双 0 减少提交时的刷盘等待，但增加故障后的数据丢失风险。
Redis 的 AOF 刷盘策略和 MySQL 的提交日志配置，都把持久性要求放进了写入路径：更早等到日志落盘，就要更早承担等待；放宽等待，则要接受更大的故障丢失窗口。第 4 章已经比较过具体档位，这里要记住的是每种保证由谁付出代价。

此处任务是提炼成本，后面 10.3.1 还会再次列默认值。可把档位表留在第 4 章，总结章保留一段设计意义。原文中的组提交并无错误，本项只是篇幅分配，不要求全书去掉参数。

10.3.1 维度一｜从参数复盘转向业务判断
建议调整架构判断原章 · 0333f889
chapters/10-summary/chapter.md
维度一：速度 vs 持久性。数据写下去多久才持久保存，是这一维度要问的问题。Redis 开启 AOF 后默认采用 appendfsync=everysec，故障时可能丢失最近约一秒的写入，实际窗口受刷盘进度影响；使用默认 RDB 快照时，恢复点取决于最近一次成功快照。MySQL 的 innodb_flush_log_at_trx_commit=1 与 sync_binlog=1 均为默认值，合称"双 1"：提交确认前等待相应日志落盘，组提交可让多个事务共享一次刷盘；断电恢复还依赖操作系统和存储设备正确履行刷盘承诺。Kafka 的 acks=all 等待 ISR 复制确认，带来副本同步等待；它不要求所有副本同时 fsync，保护范围还受最小 ISR 要求、存活副本和选主策略影响。允许丢失的缓存、计数器和限流数据可偏速度端；账本、订单、支付必须按业务要求保证持久性。核心问题是"这个场景丢得起吗"。
维度一：速度 vs 持久性。核心问题是“这个场景丢得起吗”。数据丢失后能否重建、最多允许回退到哪个时点、愿意为此多等多久，要先由业务给出要求，再选择刷盘策略。副本确认还要单独判断：多台机器收到了写入，不等于每台都已经刷盘。
