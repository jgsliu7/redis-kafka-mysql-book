6.2｜Redis 角色层
建议调整不公平对照原章 · 0333f889
chapters/06-security/chapter.md
Redis 实例上的用户数通常很少，几台应用机器各对应一个用户就够，引入"角色—用户"两层语义会让内核背上不必要的复杂度。把组角色这类复杂语义留给外部的身份管理系统（IAM），是 Redis 一贯划分边界的做法。

不要用“用户通常少”替所有部署证明角色层没有价值，更不宜让账号跟机器数量简单绑定。这里应同时写出少一层的好处和代价；不需要介绍完整 IAM 架构。

C06-11
6.3｜Redis default 与保护模式
可选精简配置细节原章 · 0333f889
chapters/06-security/chapter.md
Redis 的默认策略仍然偏向兼容。7.x 里 default 用户的内置规则是 user default on nopass ~* &* +@all：启用、无密码、全键、全通道、全命令，客户端无需显式认证就能以 default 身份操作。protected-mode（保护模式，3.2.0 起引入，默认开启）提供另一道限制：在 Redis 7.0 的实现中，保护模式开启、default 用户带有 nopass 标记、对端连接不来自回环地址（loopback），三个条件同时满足即拒绝该连接。6.2 及更早版本此判定还要求未显式 bind，显式 bind 后保护模式整体失效；7.0 起移除该条件。保护模式不替代账号和权限配置。加固时仍需显式给 default 设置密码，或用 ACL SETUSER default off 禁止新的 default 用户认证；也可用 ACL SETUSER default resetpass 清空密码并移除 nopass 标记，此后要重新设置密码才能以密码认证为 default。
Redis 的 default 用户保留了兼容旧客户端的开放规则，保护模式则在特定条件下拒绝非本地连接。两者是不同的控制：保护模式不能替代账号和权限配置。部署时应检查 default 的开放权限，并为应用建立必要的独立账号。

旧版本判定条件、三种修改用户方式占据了整段。可以整段改为边界说明；但如果作者保留可执行加固步骤，就必须保留相应条件，不能只删警示。本建议是不在思想章提供完整加固流程。

6.3｜MySQL 权限分类
建议调整归类与判断原章 · 0333f889
chapters/06-security/chapter.md
权限语义按风险分四类：数据操作（DML，包括 SELECT、INSERT、UPDATE、DELETE）、结构变更（DDL，包括 CREATE、ALTER、DROP，更危险）、管理（SUPER、PROCESS、FILE、RELOAD，高度敏感）、复制（REPLICATION SLAVE、REPLICATION CLIENT，专用于复制拓扑）。这种按风险归类的命名本身就是安全设计：它让 DBA 一眼能看出哪些权限该谨慎授予。
可以按职责把权限分为数据操作、结构变更、管理和复制等类别，再结合具体对象评估风险。类别方便梳理授权，但不是风险高低的固定排序：读取敏感数据、删除记录和修改结构，都可能造成严重后果。

原文把功能类别直接当风险等级，并把作者的归类说成产品命名本身的安全设计。用“按职责分类、按对象判断风险”即可讲清。后面的 FILE 高敏权限例子保留。

6.3｜Kafka ACL 与 Ranger
优先修正扩展机制原章 · 0333f889
chapters/06-security/chapter.md
Kafka 原生只有 ACL，没有 RBAC，和 Redis 一样；但理由不同：流平台的主体通常是"应用或服务"而不是"人"，服务身份相对稳定，角色层收益不大。企业真要 RBAC 时，通常外接 Apache Ranger 这类统一管控层，把 Kafka 的 ACL 作为底层落地点。
Kafka 的内置授权器提供 ACL 模型，授权框架也允许接入其他实现。原生没有角色模型，不代表服务账号不需要角色管理；当权限关系复杂时，可以引入统一管理或外部授权实现。

不从“服务身份稳定”推导“角色收益小”。也不把所有 Ranger 集成都说成必然把策略翻译为 Kafka 原生 ACL：Kafka 有可插拔 Authorizer，具体集成路径应分开。此处保留框架层次即可。

C06-14
6.4｜Redis TLS 历史
建议调整设计因果原章 · 0333f889
chapters/06-security/chapter.md
这是一次明确的取舍：Redis 的设计目标是单核十万级 QPS，TLS 的握手开销和每个包的加解密都会直接拉低吞吐，把这种代价推到内核之外，能让绝大多数不需要加密的内网用户不受影响。
外置代理让 Redis 核心不必自己实现 TLS，但加密成本并没有消失，只是由代理承担。原生支持之后，则可以减少一个外部组件，代价是服务进程要承担相应的加解密工作。

这里最值得比较的是实现职责和部署复杂度。既不需要无来源 QPS 数字，也不应把“内核之外”与操作系统内核混用，更不能让读者以为外置就消除了成本。

C06-15
6.4｜Kafka TLS 开销
可选精简术语密度原章 · 0333f889
chapters/06-security/chapter.md
副本同步是大流量长连接，TLS 加解密会增加处理开销。长连接稳态下需要持续处理记录层的对称加解密（AES-GCM 等 AEAD 套件），证书采用 RSA 还是 ECDSA 则影响握手阶段的认证运算。一次握手的开销会被后续通信摊薄；在短连接、频繁建连的场景下，证书算法和证书链大小的影响更明显，具体收益仍取决于实现与硬件。优化手段要对应这些来源：用硬件指令（AES-NI）降低对称加解密成本、启用 TLS 会话恢复（session resumption，减少重复完整握手），或在专用硬件上做加密卸载。内部通信和外部通信还可以用不同监听器配置不同证书，分别管理内部信任关系和外部 CA 信任关系。
TLS 的成本可以分成建连时的握手和持续传输时的加解密。长连接能摊薄握手开销，但不会免去每批数据的加解密。不同监听器还可以使用不同证书，分别管理内部与外部连接的信任关系。

这两类成本值得保留；算法名、指令集、会话恢复和硬件卸载连续出现，则偏向调优说明。无需在本章展开优化清单，先把成本分清就够了。

6.5｜Redis 日志
建议调整日志职责原章 · 0333f889
chapters/06-security/chapter.md
Redis 只提供 ACL LOG（记录被拒命令的详情，包括时间戳、客户端 IP、被拒命令，不含命令参数）和 SLOWLOG（记录执行时间超过阈值的命令）。这两样加在一起，只覆盖"谁被拒了"和"什么慢了"，但距离完整的审计轨迹（谁在什么时候做了什么操作、改了什么数据）还差得远。

ACL LOG 不只记录被拒命令，还记录认证失败等事件。“只提供”也不必要：本段只需说明这两种日志为什么不能替代完整审计，不必列齐所有诊断工具。
