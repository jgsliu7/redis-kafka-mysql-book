C05-03
5.1｜Redis 的约束
优先修正架构因果原章 · 0333f889
chapters/05-layered-architecture/chapter.md
Redis 的约束是单机最低延迟。它要把每条命令的端到端时间降到亚毫秒，于是层数越少越好，跨层调用最好是直接函数调用，连虚函数的开销都要避免。对 Redis 来说，薄本身就是目标。
Redis 侧重常见命令的低延迟。它尽量让模块在进程内通过共享对象和函数调用衔接，减少额外的数据转换与线程交接。这里的“薄”，指的是请求路径简短，不是源码模块越少越好。

不能从目标延迟直接推导“层数越少越好”。Redis 本身有函数指针分派；避免 C++ 虚函数语法不等于没有间接调用。这处收准的是本章的比较基础，而不是要求讲编译原理。

C05-04
5.2.1｜同线程路径
优先修正技术表述原章 · 0333f889
chapters/05-layered-architecture/chapter.md
这套设计的关键是"没有跨层线程切换"。交互层和逻辑层在同一线程中运行，命令从解析到执行到写回，全程不用锁、不用队列，也没有上下文切换。Redis 看起来分层薄，根子就在这里。
这套设计的关键是：交互层和命令逻辑在同一线程中衔接，不必为每次模块调用增加工作线程交接。数据结构可以保持串行访问，层与层之间主要传递对象和调用函数。

“没有额外工作线程交接”是正确的观察方向，“全程没有上下文切换”则把操作系统 I/O 等动作也抹掉了。无需补例外列表，直接把句子限定到本段真正比较的层间衔接。

C05-05
5.2.1｜多线程 I/O
可选精简重复说明原章 · 0333f889
chapters/05-layered-architecture/chapter.md
6.0 引入、7.x 沿用的多线程 I/O，可以把网络 I/O 工作分配给一组线程，命令执行依然在主线程串行。启用多个 I/O 线程后，默认只辅助处理响应发送；读取与协议解析还需开启 io-threads-do-reads。串行执行使键空间更新不必在多个命令执行线程之间加锁；若引入命令并发，则需要重新处理共享对象和数据结构的同步。7.x 默认仍只使用主线程完成这些 I/O 工作，多线程 I/O 是需要显式启用的可选优化，启用它也不会改变命令串行执行的前提。
Redis 6.0 起可以选择启用多线程 I/O，分担网络收发等工作，但普通命令仍由主线程串行执行。它把一部分 I/O 工作并行化，却保留了键空间更新的串行路径。

“命令仍串行”重复三次；配置项和默认读写分工也打断分层论证。保留两个边界：I/O 可以并行，命令执行仍串行。需要调参的读者查配置即可。

5.2.2｜client 对象
建议调整讲解补足原章 · 0333f889
chapters/05-layered-architecture/chapter.md
图里右边那个贯穿全程的虚线框是 client 结构体。它持有查询缓冲区、参数数组、当前命令指针等会话状态。整个会话上下文都在这一个对象里。交互层往里写、逻辑层从里面读、存储层从里面取 db 索引，三段之间不传参数，只传这个对象。这与 MySQL 的 THD 是同一种思路。在 Redis 的单线程执行路径中，交互层和逻辑层在同一线程内共享这个对象。

“不传参数，只传对象”在语义上不成立，对象本身也是参数；反复说“同一对象”仍未解释共享的代价。新增一句字段依赖，才为后面的 THD 讨论打下基础。

C05-09
5.3.1｜线程池
可选精简旁支细节原章 · 0333f889
chapters/05-layered-architecture/chapter.md
以 MySQL 8.0 企业版为例，连接分配到不同线程组，慢查询可能延迟同组后续请求；线程池检测到阻塞或长时间运行后，会继续调度其他语句，并非等待慢查询结束才处理整个队列。两种模型需要在每连接独立线程与线程复用、调度开销之间取舍。
线程池减少了大量连接各自占用工作线程的成本，但也引入排队与调度。取舍在于：每个连接独立执行，还是让多个连接复用一组工作线程。

这里说明两种线程组织即可，不必深入企业版对慢查询的调度细节。改文没有说一个慢查询会堵死整组，因此也不需要再写“并非等待……”。

5.3.3｜图 5-4 后
优先修正接口边界原章 · 0333f889
chapters/05-layered-architecture/chapter.md
这张图的关键在中间那条粗黄线：Handler API 接口契约，它把服务层与引擎层彻底切开。下层各引擎分别实现这套接口，互不干扰，可并存。InnoDB 自己又是多层：事务管理 → 锁与 MVCC → 缓冲池 → redo log 与 undo log → 页与 B+ 树。这些子层全部封装在 InnoDB 内部，对服务层不可见。服务层看到的只是一个"实现了 Handler 接口的黑盒"。表空间、日志与双写缓冲的文件布局，见第 8 章。
图中最重要的是 Handler API：服务层通过共同接口访问不同引擎，不必自己实现每个引擎的页组织和恢复机制。引擎仍需向服务层报告自身能力和统计信息，所以接口隔离的是实现细节，不是让双方彼此毫无了解。文件布局见第 8 章。

“彻底切开”“全部不可见”容易让读者误解优化器与引擎的协作。也不宜把锁、缓冲池、日志、B+ 树列成一条必经的严格层级链。保留共同契约的主线，用一句补清能力协作即可。

C05-11
5.3.3｜多态开销
建议调整论证不公平原章 · 0333f889
chapters/05-layered-architecture/chapter.md
生态和多态开销是一体两面。handler 通过虚函数（vtable）多态调用，每次行操作都过一次虚函数表。这意味着一个全表扫描的每一行、一个索引查找的每一次定位，都是一个间接调用点，往往难以被内联优化。这是可插拔接口相对"引擎与执行器一体化"数据库的固有开销——PostgreSQL 12 起的 table access method 同属抽象层，行访问一样要过函数指针，差别只在接口契约的宽窄。MySQL 拿这个代价换来了可插拔。划不划算，取决于你怎么用 MySQL：如果你只用 InnoDB，这笔开销就是纯成本；如果你需要混合引擎（比如热数据 InnoDB、冷数据 RocksDB），这笔开销换来的是生态收益。
Handler 的多态调用可能增加间接调用开销，换来不同引擎共用服务层的能力。即使一个实例只用 InnoDB，这个边界仍有维护和演进价值；是否值得，不能只看安装了几种引擎，还要看接口收益与实际热点路径的成本。

新版已把“无法内联”改成“往往难以”，不再重复报那项旧错。剩余的问题是把只用一种引擎写成“纯成本”，忽略分离职责的收益。删去 PostgreSQL 旁支，不用语言机制直接推导实际性能排名。

5.4.2｜协议与领域逻辑
建议调整无用精确数字原章 · 0333f889

分开的原因是协议版本演进和领域逻辑演进节奏不同。协议格式演进慢，一次修改的影响面大；副本管理算法可能半年调整一次。两者耦合时，修改其中一方也需要修改另一方。

C05-14
5.4.3｜写入路径
可选精简章节职责原章 · 0333f889
chapters/05-layered-architecture/chapter.md
写入路径很简单：生产者发来一批消息，Broker 把它顺序追加到当前活跃 LogSegment 末尾，写入页缓存（PageCache），可选地按策略刷盘（fsync）。常规追加无需维护 B+ 树，也避免了逐条原地更新；副本复制和日志压实仍会带来额外写入。顺序追加便于批量 I/O，在机械盘上还能减少寻道。刷盘策略可配：log.flush.interval.messages（每多少条刷一次）或 log.flush.interval.ms（每多少毫秒刷一次），也可以保持默认设置，依靠 OS 和 Kafka 的后台刷盘完成落盘。副本机制的数据保护还取决于确认与故障条件：acks=all 等待当前 ISR 确认，并受 min.insync.replicas 限制；在不启用非同步副本选主、且始终至少有一个同步副本存活的前提下，Kafka 能保证已提交消息不丢。增加副本数本身不等于满足这些条件。
写入时，Broker 把消息批追加到活跃日志段。Log 层组织文件与索引，刷盘和副本确认则分别处理持久化与复制保证。这里关注的是职责分工；具体保证和参数见第 4、7、9 章。

在分层章重复一整段刷盘、ISR 与选主配置，会把读者从“Log 承担什么”带走。移走整段保证讨论，而非留下“不丢数据”再删除它的条件。

5.4.3｜Log 复用结论
建议调整启示增量原章 · 0333f889
chapters/05-layered-architecture/chapter.md
存储层和复制层共享底层日志读取代码。Kafka 不需要为副本同步另写一套本地日志读取实现，但副本进度、任期和截断仍有独立的状态处理。对共享读取部分的优化（零拷贝、索引、缓存）和 bug 修复，可以同时惠及消费与复制。很多系统的"主从复制"是独立模块，复制代码和读写代码各写一份，长年累月就会漂移、出 bug。
存储与复制复用底层日志读取，所以索引、缓存和文件读取的优化可以同时惠及两条路径。副本进度、任期和截断仍由复制逻辑处理。复用的是共同工作，不是把不同职责合成一个模块。

前文两段都在说复用，这里应给出更具体的判断：共享哪些工作、保留哪些差异。删掉对“很多系统”必然漂移出 bug 的笼统反衬。

C05-19
5.7｜三家经验汇总
建议调整小结联动原章 · 0333f889

Redis 的经验是：性能敏感处，分层要薄，跨层要直接。它用极少的层和函数调用把延迟降到亚毫秒，代价是放弃存储的可插拔。MySQL 走的是另一端，用 Handler API 接入几十种引擎，标准化接口能支撑起生态，但多态有开销。Kafka 需要处理跨 Broker 的网络通信，分层要为水平扩展服务：交互层是三者中最重的，用来利用多核；存储层做得最薄，以此支撑高吞吐。
Redis 提醒我关注请求路径的开销，MySQL 提醒我为真实的替换需求保留接口，Kafka 则提醒我把功能职责、线程交接和跨机器通信分别看清。分层不是比较谁的层数少，而是判断每一道边界换来了什么。

前文已不再按统一口径数层，小结却再次给出“最重／最薄”的排名，并重复“几十种引擎”。改成三种观察收束，比恢复旧排名更一致。下方“分层的价值，是让每次修改都有明确的改动位置”值得保留。
