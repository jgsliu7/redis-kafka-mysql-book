目标不同，选的数据结构和用的协议也不同。这一章的核心问题是：每个系统为了自己的目标，选了什么样的内部数据结构、用了什么样的通信协议。 数据结构决定了它能做什么、不能做什么；协议决定了客户端和服务端怎么互相理解。三家的取向第 1 章的雷达图已经画过，本章每个结构与协议的选择，都是那三个目标的推论。 没有全能的数据结构：不同结构擅长的访问模式不同，超出主要优化目标时，操作成本可能上升。协议也一样，三家的选择都在为各自的目标优化。后面七章的内存管理、磁盘布局、数据同步，都从这里的结构选择出发。

Redis 要的是极低延迟。所以它的数据结构全部在内存里，常用的点查和有序定位可分别做到 O(1) 和 O(log N)，内存紧凑是第二考量。协议选了 RESP，类型和长度使用可读的前缀，参数也能包含二进制数据，服务端解析几乎不费 CPU。
Redis 侧重低延迟，数据结构驻留内存，常用的点查和有序定位分别由哈希表、跳表等结构支持。它也会为小数据采用紧凑编码，减少内存占用。RESP 用可读前缀表示类型和长度，兼顾解析简单与二进制数据传输。

预分配：追加触发的扩容默认走翻倍策略，新长度小于 1MB 直接翻倍，超过 1MB 则每次只多申请 1MB，连续追加时不会每次都触发 realloc。网络层读客户端命令缓冲（querybuf）的大参数是个例外：走 sdsMakeRoomForNonGreedy 按需扩容，知道读多少就分配多少，不为单个大参数白占一倍内存。 惰性释放：对带 alloc 字段的 SDS，sdsclear、sdsrange 等缩短操作会保留原有分配，把多余空间留作未来的追加缓冲。它们会更新长度和结尾 \0，截取子串时还可能搬移保留的字节；真正收缩分配可显式调用 sdsRemoveFreeSpace 等接口。预分配与空间复用减少了反复分配，但各操作的复杂度仍不同：获取长度是 O(1)，追加和截取的成本还取决于复制的字节数与是否需要重分配。图 2-1 把两种字符串的内存布局并排画出来。

收准表述

这套设计同时满足三个查询需求：点查（从根走到叶，O(log N)，两到三次 I/O）、范围扫描（定位到起始叶子后顺着链表往后扫，不需要反复从根定位）、排序（叶子层天然有序，B+ 树的键序就是排序顺序）。如果换哈希索引，点查 O(1) 更快，但范围和排序完全做不到。MySQL 要的是通用查询能力，B+ 树把所有常见的查询模式都覆盖了。第 8 章会展开 InnoDB 页内七段布局和 Page Directory 的细节。
这套设计兼顾点查、范围扫描和按索引键顺序读取。点查从根走到叶，树越矮，需要访问的页越少；页在缓冲池中时，不必再读磁盘。范围扫描找到起点后，可以顺着叶子链继续读取。哈希索引擅长等值查找，却不维护这种键顺序。B+ 树因此适合同时需要点查和有序访问的关系查询。第 8 章再展开页内布局。

树层数不等于固定磁盘 I/O 次数

“两到三次 I/O”把逻辑访问层数写成固定设备访问次数，属于值得修正的基本模型。“O(1) 更快”也不能单凭复杂度符号判断实际速度。只补“缓存命中不用读盘”，再把比较落到等值／有序访问即可，不需要展开缓存和磁盘队列。

行格式（Row Format） 决定了一行数据在页内怎么存放。以默认的 Dynamic 行格式为例，行头存变长字段长度列表和 NULL 位图，后面是各列数据。长度信息按与字段相反的顺序存放，解析时从记录头附近读取这些长度，再确定各字段的边界。行太长放不下时才动用溢出页，且按整行判定：超限就把最长的变长列（VARCHAR/BLOB/TEXT）整列挪去独立溢出页、行内只留一个指针，很短的 TEXT/BLOB 始终留在行内（字节级阈值与挪列顺序见第 8 章）。这是"页内紧凑"与"大对象不污染整页"的折中。
行格式（Row Format） 决定一行数据怎样放进页里。以 Dynamic 为例，行太长时，可以把部分较长的变长列移到溢出页，行内留下指针。这样让索引页能容纳更多记录，代价是读取移出的内容还要访问额外的页。具体布局留到第 8 章。

2.2.3 Kafka／RecordBatch
收准表述
技术
查看固定版本原稿
RecordBatch 就是 Kafka 的基本存储单元。 生产者会把消息积累成一批（积累到 batch.size 字节，或等到 linger.ms 毫秒）再组成一个 Batch 发到 Broker，而不是一条一条往外发。Broker 收到后把整个 Batch 原样追加到日志段末尾。不对单条消息做任何拆分或索引。消费者拉取时，拿到的也是一整个 Batch。原样追加的前提是生产者的压缩类型与 topic 的 compression.type 一致；不一致时 Broker 要逐批解压再重新压缩，老版本客户端拉取时还要触发格式降级转换。这两处都是 Broker 端 CPU 尖刺的常见来源。
RecordBatch 是 Kafka 组织消息的基本单元。 生产者把同一分区的消息组织成批发送，一个批也可以只有一条消息。Broker 校验后按批追加到日志段，消费者再成批拉取。协议与日志复用批格式，减少了重新组织数据的工作；需要改变压缩方式时，仍会增加重新编码的成本。

按批追加，不等于完全原样、不校验

“原样”容易被理解为 Broker 不检查、不修改任何字节；官方设计文档说明了批校验，消息格式也有 Broker 赋值的字段。主题 compression.type 默认是 producer，意为沿用生产者算法，不能直接比较配置字符串是否相等。这里写“校验后按批追加”即可，不需要保留全部重压缩、旧客户端路径。批只含一条是普通情况，不是偏门例外。

2.3.1 RESP／五种前缀
可选精简
排版与节奏
查看固定版本原稿
RESP 根据序列化数据的首字节区分数据类型。+ 是简单字符串（如 +OK\r\n），- 是错误（如 -ERR unknown command\r\n），: 是整数（如 :1000\r\n），$ 是批量字符串（如 $5\r\nhello\r\n，先告知长度再跟内容，天然二进制安全），* 是数组（如 *3\r\n$3\r\nSET\r\n$3\r\nkey\r\n$5\r\nvalue\r\n，先告知元素个数再逐个展开）。五种前缀字符就够用了：既无固定头部，也无版本号；长度信息只出现在两处——数组首行的元素个数和批量字符串的内容长度，都是内容自述，不是固定协议头。
以 RESP2 为例，首字节区分五种基本类型：+ 是简单字符串，- 是错误，: 是整数，$ 是批量字符串，* 是数组。数组先给出元素个数，批量字符串先给出内容的字节长度，解析器据此识别边界。 例如，SET key value 是一个包含三个批量字符串的数组： *3\r\n $3\r\nSET\r\n $3\r\nkey\r\n $5\r\nvalue\r\n

2.3.2 MySQL／整数编码
建议调整
补足解释
查看固定版本原稿
报文里的整数编码分两套。定长小端整数低字节在前，类型为 int<1>/int<2>/int<4>/int<8>。另一套是首字节分档的变长整数（LengthEncodedInteger）：首字节小于 0xFB 时，它就是值本身，占 1 字节；0xFC/0xFD/0xFE 前缀分别后跟 2/3/8 字节，总长 1/3/4/9 字节。 字符串用长度前缀（LengthEncodedString）。结果集先发列数和每列的类型/长度元数据，再发送各行数据。0xFB 不是长度编码，在结果集行里它标记 NULL。接收方先按首字节确定长度字段的编码，再读出字符串长度，随后按该长度接收内容。
MySQL 经典协议包先有一个 4 字节头：3 字节记录后面载荷的长度，1 字节记录包序号。接收方因此知道这一包有多少字节。 包内的整数再按字段选择定长或变长编码。小整数可以少占字节，大整数再使用更长表示；字符串先给长度，再放内容。固定包头解决整包边界，长度编码解决包内字段边界，这是两个层次。

“二进制封帧”先给读者一个具体对象

原文反复强调“二进制封帧”，却没有先解释帧边界，马上进入 0xFC／0xFD 的编码表。用四字节包头建立直觉，再讲字段编码，比记一串前缀更切题。不是要求补更细的拆包教程；超大报文和序号回绕无需在此展开。官方协议页为滚动文档，本条只采用经典包头与长度编码的基础定义。

2.3.3 Kafka／请求头
可选精简
实现细节
查看固定版本原稿
Kafka 的请求头有自己的版本。常见的 v1 包含四个字段：api_key（2 字节，标识这是什么类型的请求，如 Produce = 0、Fetch = 1、Metadata = 3……）、api_version（2 字节，标识用哪个版本的 Schema）、correlation_id（4 字节，客户端自定义，服务端原样写入响应，用来匹配请求和响应）、client_id（变长字符串，标识客户端身份）。v0 请求头没有 client_id，v2 则在这四个字段后增加 tagged fields 区域。请求头版本由 API 及其版本决定。api_key + api_version 让同一类请求可以同时存在多个版本，Broker 根据客户端声明的版本号调整解析方式和返回字段。这意味着不强制所有客户端同步升级。3.0 的 Broker 可以和 0.11 的客户端对话，双方用彼此都支持的最高版本号做协商。
Kafka 请求头中值得关注的是四个字段：api_key 标识请求类型，api_version 指定这类请求使用的格式版本，correlation_id 用来匹配请求和响应，client_id 便于识别请求来源。每类请求可以独立演进，客户端选择双方支持的版本，不必让所有客户端同时升级。

保留四个字段的职责，压缩版本枝节

本节要解释的是“逐 API 版本化怎样降低联动升级成本”，不是请求头 v0／v1／v2 的完整演进。字节数、历史客户端组合和 tagged fields 可以保留在图或资料索引；正文不必一起背负。“客户端身份”顺手改成“请求来源”，不另开认证话题。

2.3.3 Kafka／批量优先
收准表述
技术
查看固定版本原稿
批量优先 是 Kafka 协议区别于 Redis 和 MySQL 最根本的特征。Produce 请求把多条消息打成一个 RecordBatch 一起发给 Broker，Fetch 请求一次拉取指定 (topic, partition, offset) 起始的一段数据（min_bytes + max_bytes 控制拉取量），常规路径上数据要在磁盘、内核、用户态、socket 缓冲之间来回搬，零拷贝让一批消息不进用户态，直接从页缓存送到网卡。一切以 Batch 为单位。这和 RecordBatch 在存储层的设计是同一个思路：协议层不做单条操作，是 Kafka 把吞吐放在第一位的必然结果。
批量优先 主要体现在 Kafka 的消息写入与读取路径上。Produce 可以携带多个分区的消息批，Fetch 按分区和 offset 拉取一段记录。把多条记录合并处理，可以摊薄请求与传输开销；同一批格式贯穿生产、日志存储和拉取，也减少了重新组织数据的工作。

批量是数据路径的组织方式，不是整个协议只有批操作

本节前面刚列出 Metadata、JoinGroup 等请求，后面却用“一切”“协议层不做单条操作”概括整个协议。应把范围收回消息数据路径，并区分一个请求与一个批：一次 Produce 可携带多个批。零拷贝是另一项优化，这里不必再次解释，更不能写成所有路径无条件适用。
