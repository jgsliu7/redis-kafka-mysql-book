C07-05
7.2.1｜复制实现抢占拓扑篇幅
可选精简细节位置原章 · 0333f889
chapters/07-cluster/chapter.md
Redis 最朴素的集群化，是主从复制（replication）。在从节点上执行 REPLICAOF host port（旧版叫 SLAVEOF），从节点发起连接，建立后由主节点把数据推送过来。首次同步时，主节点 fork 子进程生成 RDB 快照；快照可以先写文件再传输，也可以通过无盘同步直接传给副本。期间产生的写命令保留在复制缓冲中，快照传完后再补发。Redis 7.0 让副本输出与复制积压区（replication backlog）引用共享缓冲块，各副本维护自己的发送进度；backlog 为断线后的续传保留近期历史。短暂断线后，如果复制 ID 仍能匹配相应历史，所需字节也还在 backlog 中，就可以只补差量，这叫部分重同步（partial resync）。这里只看它在集群中扮演的角色。
Redis 最基础的复制拓扑是一个主节点带若干从节点。在从节点执行 REPLICAOF host port，即可指定上游。首次同步先取得快照，再补上期间的写入；短暂断线后，条件满足时可以只补差量。具体同步过程见第 9 章，这里先看这种拓扑解决了什么、还缺什么。

共享缓冲块、无盘同步、复制 ID 都有价值，但本节接下来讲的是异步、单主写入与人工转移。把实现细节交给第 9 章，主线更连续。

7.3｜主从术语插叙
可选精简术语与节奏原章 · 0333f889
chapters/07-cluster/chapter.md
MySQL 集群最核心的机制是主从复制：一台主节点（Master，8.0.22/8.0.23 起官方改称 source，新增 START REPLICA、CHANGE REPLICATION SOURCE TO 等语句别名）处理所有写请求，把每一条数据变更记进 binlog（二进制日志）；一台或多台从节点（Slave，同期改称 replica）通过订阅主节点的 binlog 来保持数据同步。
MySQL 主从复制的基本结构是：主节点（source）处理写请求，将变更记录到 binlog；从节点（replica）订阅这些日志，逐步同步数据。

先给读者一个主从结构，再讲机制。新旧名称、命令别名和补丁版本不必都塞在第一句话里；这也比用“所有 MySQL 集群都如此”概括更贴合本节对象。

C07-13
7.4.1｜粘性分区的讲解深度
可选精简实现细节原章 · 0333f889
chapters/07-cluster/chapter.md
没有 key 时，Kafka 2.4 经 KIP-480 引入默认粘性分区；在本章的 3.9 基线中，默认逻辑向一个分区累计发送至少 batch.size 字节后再切换，以改善成批发送的效率。逐条轮询会把记录分散到更多分区，批量效果因负载而异。
没有 key 时，默认采用粘性策略：先向一个分区积累一批消息，再切换目标。这样比逐条分散发送更容易形成较大的批。

此处讲清“为何不是逐条轮询”即可，首次引入版本和精确触发量可放配置资料。前面有 key 的公式及后面扩分区会改变顺序边界的说明都保留。

C07-14
7.4.2｜ISR 与多数派的比较
建议调整重复与比较原章 · 0333f889
chapters/07-cluster/chapter.md
ISR 定义了 Kafka 副本同步的边界，和 MGR 的多数派通信、Redis 的候选副本筛选解决的并非同一个问题。MGR 在读写事务提交前进行组内排序与冲突认证；Kafka 用 ISR 维护跟得上 Leader 的副本集合，再由生产者选择确认范围。Sentinel 也会排除长时间断线等不合格副本，然后按优先级、复制偏移量和 runid 选择新主。比较这几种机制，关键是确认成功时副本保存了什么，以及故障转移允许选择哪些副本。
ISR 不是多数派的另一个名字。它回答哪些副本跟得上 Leader，再参与写入确认和新主选择。比较它与 MGR、Sentinel 时，我会看两件事：成功确认时副本保存了什么，换主时允许选择哪些副本。

第一句的区别很重要，但接着又复述三家的完整机制。保留区别，再直接落到两条判断标准，避免为了说明“不能直接比”再列一遍材料。
