C04-03
4.2｜LFU 示例
建议调整例子与保证原章 · 0333f889
chapters/04-memory-disk/chapter.md
LFU 看频率、LRU 看时间，这是两者的本质差异。举个具体场景：你跑一次全表扫描把一批冷数据读进 Redis，过几秒又来一波真正的热点查询。LRU 下，刚被扫到的冷数据"最新"，会淘汰前面的热数据；LFU 下，冷数据的计数器还是低值，热数据的计数器则因高频访问而爬高，被淘汰的会是冷数据。所以全表扫描后再来热点查询，LFU 能保住热数据不被冷数据淘汰。
LFU 更看重访问频率，LRU 更看重最近一次访问。假设应用集中读取一批平时很少访问的键，LRU 会把它们看成“最近用过”；LFU 仍能区分一次性访问与长期高频访问，因而更有机会保住原来的热点。它不是保证热键永不淘汰，而是换了一种判断热度的依据。

“全表扫描读进 Redis”混在一起讲了外部数据库扫描、缓存填充和键访问，读者不易看清比较条件。换成已有键的一次性访问，例子就集中在算法差异上。原文“被淘汰的会是冷数据”也说得过满，近似算法不能作此保证。

4.2｜RDB
建议调整叙述次序原章 · 0333f889
chapters/04-memory-disk/chapter.md
RDB（快照文件） 是某一时刻内存数据的全量二进制快照。生成方式是 fork 一个子进程，子进程拿到父进程内存的副本（依赖操作系统的写时复制 COW 机制），把这份副本序列化写盘。fork 之后父进程继续接写请求，子进程专心写快照，父子进程通过 COW 隔离，互不干扰。这套机制在理想路径上确实不阻塞主线程，但有一个真实代价：fork 本身在父进程这一侧是同步的，实例内存越大，fork 拷贝页表的时间越长。
RDB（快照文件） 保存某一时刻的全量数据。后台保存时，Redis 先 fork 子进程，再由子进程写出快照，父进程继续处理请求。写时复制（COW）保留了快照所需的内存视图，但 fork 本身仍会暂停主线程，后续复制被修改的页也有开销。

先说“互不干扰”“不阻塞”，再用后半段收回，读起来绕。直接区分“fork 阶段”和“后台写快照阶段”，同样通俗而且更短；也与第 3 章已经介绍的同步 SAVE 区分开。后面的真实卡顿与排障观察可以保留。

C04-11
4.3｜WAL 与崩溃恢复
优先修正机制因果原章 · 0333f889
chapters/04-memory-disk/chapter.md
InnoDB 用顺序日志替代直接随机写数据页，因为顺序写远快于随机写。一个事务的修改可能散落在表空间的多个页上，直接刷这些页是大量随机 I/O；而把这些修改先打包成顺序日志追加写，只产生顺序 I/O。日志落盘后这个事务就算"持久了"，脏页可以慢慢往后刷。这个设计把"事务提交"的延迟从"随机写一堆页"降到了"顺序写一条日志"。
一个事务可能修改多个分散的数据页。采用 WAL 后，提交时不必等这些页全部写回：先持久保存恢复所需的日志，脏页再由后台逐步刷回。随机写并没有消失，只是不必每次都挡在提交路径上；同一页的多次修改也有机会合并后再写。

“只产生顺序 I/O”容易被理解为整个数据库不再写数据页。真正值得读者带走的是“改变等待位置”和“合并页修改”，不是把随机 I/O 全部消除。这是修正核心因果，不是追加特殊例外。

4.4｜零拷贝图后
建议调整过度说明原章 · 0333f889
chapters/04-memory-disk/chapter.md
传统路径：磁盘 → 内核缓冲 → 用户缓冲 → Socket 缓冲 → 网卡，4 次拷贝加 4 次上下文切换，数据要穿过用户空间。零拷贝路径（基于 sendfile / Java NIO transferTo）：磁盘 → 内核 PageCache → 网卡（由 DMA 完成实际搬运），数据全程不进用户空间，只剩 2 次上下文切换；在支持 scatter-gather DMA 的现代网卡上（生产环境基本默认满足），剩余的 2 次拷贝（磁盘到 PageCache、PageCache 到网卡）都由 DMA 完成，CPU 不参与数据搬运，因此被称为零拷贝；页缓存命中可以省去磁盘读取；冷数据仍需先等磁盘 I/O，但也可以沿这条路径传输。
传统文件发送先把数据读到用户缓冲，再写入 socket。sendfile 把中间这次用户态往返省掉，让内核直接组织文件数据的发送。这里的“零拷贝”不是数据完全不搬运，而是不必先复制到应用自己的缓冲区；Kafka 本地日志直接发送、无需 TLS 等字节处理时，可以利用这条路径。

本段最该讲清的是“省掉哪一次搬运”，不是要求读者记住四个次数和 scatter-gather DMA。精确计数可留图中作为所绘路径示例，文字保留适用的本地直接发送场景。图 4-6 若未标明普通与 TLS 路径差异，可只补图注。

C04-18
4.6｜启示二
优先修正架构因果原章 · 0333f889
chapters/04-memory-disk/chapter.md
Redis 和 MySQL 自己管理内存，是因为内核的 PageCache 策略无法满足它们在淘汰精度上的需求：Redis 要的是按键、可配策略的淘汰（近似 LRU 与 LFU，见 4.2 节），MySQL 要的是抗扫描污染的新老分区 LRU。Kafka 不需要这种精度，所以它直接利用了 OS 缓存可被多个进程复用、进程重启后仍然有效的特点。
先看内存中要管理的是什么。Redis 直接保存并操作键值对象；InnoDB 管理带有冷热和脏状态的数据页；Kafka 的消息已经组织为文件日志，可以较直接地利用 PageCache。是否自己做缓存，既取决于淘汰策略，也取决于上层数据表示和写回职责。

这是本章比较关键的因果修正：Redis 并非只因“嫌内核淘汰不精确”才自管内存，InnoDB 也不只是在选择一种 LRU。用“内存里管理什么对象”连接前三节，能获得真正可迁移的判断方法。后面的作者自问句仍可保留。

这些参数都影响可靠性与性能，但控制的环节并不相同。4.4 节已把 acks 三档和另外两家的刷盘参数对照过一次。相关参数包括 Redis 的 appendfsync（always / everysec / no）、MySQL 的 innodb_flush_log_at_trx_commit（1 / 2 / 0）、Kafka 的 acks（all / 1 / 0）与 log.flush.*。Kafka 的 acks 控制写入确认，log.flush.* 控制本地刷盘；acks=all 等待当前 ISR 中的全部副本确认，写入成功还受 min.insync.replicas 约束。这种复制保证以至少一个同步副本存活为前提，不等于每条消息都已落盘，因此不能把这些档位按"每条都落盘"到"交给 OS"一一对应。
持久化与复制都要付出等待成本，但等待的对象不同：刷盘等待数据进入持久介质，副本确认等待数据传播到其他节点。调参之前，先分清业务要防的是哪种故障，再判断哪些等待可以减少。

4.4 已解释 acks 与刷盘的区别。启示段可以把参数细节上提为两类问题，不必再列全部档位和副本条件。不是删除这些条件：它们仍留在相应机制段。

理解了这些参数分别控制什么，调参才有方向。我自己会先问"愿意为多强的持久性牺牲多少吞吐"。很多时候答案是各自的中间档：Redis 的 everysec、MySQL 的 2（写 OS 缓存、每秒 fsync 一次）减少同步刷盘等待；Kafka 的 acks=1 不等待 Follower 的复制确认，Leader 确认后若在复制完成前故障，消息可能丢失。Kafka 3.0 起默认已是 acks=all，这里说的是主动下调确认要求的场景。
