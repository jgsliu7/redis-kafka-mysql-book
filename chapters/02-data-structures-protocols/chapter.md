# 第 2 章 数据结构与协议 — 为各自的目标而设计

## 本章导读

我做过一个测试：MySQL 一张没有 score 索引的表跑 `ORDER BY score DESC LIMIT 100`，数据量小的时候跑得很快，当表中数据涨到数百万级之后，每次刷新排行榜都要扫描大量数据并做额外排序（filesort），查询落到秒级。当然，给 score 建了索引之后，这个查询走索引有序扫描、毫秒级就能返回。

前 100 名查得快了，查某个人的名次却还是麻烦。普通 B+ 树索引记录键的顺序，却不直接记录排名；要算名次，通常还得统计排在前面的记录。后来我把整张榜挪到 Redis 的有序集合（ZSET）上，用 ZREVRANK 查名次。它的跳表额外维护了跨度信息，能在定位元素时一并算出位置。对这个排行榜来说，关键不只是有没有索引，而是名次查询是不是现成的能力。选数据结构，要看它是否匹配最常做的操作。

这一章就从访问方式出发，看 Redis、MySQL 和 Kafka 怎样组织数据、怎样与客户端通信。重点不在于记住所有字段，而在于理解：一种结构或协议方便了哪些操作，又增加了哪些成本。

## 2.1 问题的本质

任何一个有客户端和服务端的软件，都绕不过这两个问题：

第一，数据用什么格式来组织。这个问题直接关系到操作复杂度、内存开销以及"哪些查询快、哪些查询慢"。跳表适合范围扫描和有序操作，哈希表适合 O(1) 点查，B+ 树为磁盘页对齐和范围扫描而设计，紧凑列表胜在内存密度。

第二，客户端和服务端怎么对话。有三个关键点：发纯文本还是紧凑二进制（可读 vs 紧凑），每条消息独立处理还是批量打包（简单 vs 效率），协议固定还是带版本号可演进。

Redis 侧重低延迟，数据结构驻留内存，常用的点查和有序定位分别由哈希表、跳表等结构支持。它也会为小数据采用紧凑编码，减少内存占用。RESP 用可读前缀表示类型和长度，兼顾解析简单与二进制数据传输。
MySQL 的核心目标是**通用可靠**。它要支持任意 SQL、事务 ACID、磁盘持久化，所以 InnoDB 用 B+ 树组织索引，以默认 16KB 的页为单位读写。内部节点在一页内保存多个键和子页指针，提高分支数、减少查找需要访问的页；页内仍有管理信息和供后续写入使用的空闲空间。协议选了二进制封帧——经典查询的结果行走文本，减少传输体积的收益，要到预编译语句的二进制结果集才体现出来；重复执行预编译语句通常还可以复用解析结果。
Kafka 把**高吞吐**当成第一目标。所以它的核心数据结构 RecordBatch 把多条消息打成一个包，压缩、传输、落盘都以 Batch 为单位，批量化成了格式本身的内置属性。协议选了带版本号的请求/响应模型。统一头部 + 逐 API 版本化，让不同版本客户端可以和同一个 Broker 对话，演进能力直接靠版本号字段实现。

## 2.2 内部数据结构：为核心目标而设计

### 2.2.1 Redis：驻留内存的简洁数据结构

Redis 的数据结构都受同一个约束限制：**全部驻留内存**。内存意味着随机访问的成本远低于磁盘、对 CPU 开销比对 I/O 更敏感、容量有物理上限，所以数据结构要尽量省内存、尽量少 CPU 操作。下面五个结构都是对这条约束的回应：SDS、跳表、字典（dict）偏重查询效率，ziplist/listpack 和 intset 偏重内存密度。

**SDS（简单动态字符串）** 是 Redis 最基础的字符串实现。它仍用 C 语言的 `char*` 访问数据，但在数据前增加了记录长度等信息的头部。C 语言的字符串取长度要遍历到 `\0` 才能知道，SDS 读取头部的 `len` 字段就能得到长度。SDS 还能存储任意二进制数据，不需要依赖终止符。

它的头部（header）记录了 `len`（当前字符串长度）、`alloc`（已分配的总字节数，不包括头部和结尾 `\0`）和 `flags`（标记 SDS 类型）。Redis 按长度分 sdshdr5/8/16/32/64 共五种，短字符串用小头省内存。其中 sdshdr5 最省，整个头只有 1 字节，长度直接嵌在 flags 的高 5 位里。实际存数据的 `buf` 紧跟在头部后面。

**预分配**：追加需要扩容时，SDS 通常会多申请一些空间，减少连续追加时反复分配的开销；字符串较大时则限制额外预留量。

**空间复用**：缩短字符串时，可以保留已分配的空间，供后续追加使用。这样少做分配，却可能暂时多占内存。图 2-1 把 SDS 与 C 字符串的内存布局并排画出来。

![图 2-1 SDS 与 C 字符串的内存布局对比](diagrams/fig-2-1.svg)
图 2-1　SDS 与 C 字符串的内存布局对比：同一个 hello 的两种存法，差别集中在 SDS 的头部。

两种字符串的开销位置不同：C 字符串省了头部，代价摊在每次取长度的遍历里；SDS 多存一个头部，取长度变成读一个字段。Redis 选的是后一种：增加固定的小开销，免去每次取长度时的遍历。

**跳表（skiplist）** 是 Redis 有序集合底层两种结构之一。skiplist 编码的 ZSET 内部是 dict + 跳表两个结构并联：member→score 的查找走 dict，ZSCORE 是 O(1)；按顺序读取一段元素走跳表，ZRANGE 是 O(log N + M)，M 为返回元素数。单一结构无法兼顾两种访问需求，因此并联两个结构，分别支持一条访问路径。

跳表是多层有序链表，最底层是一条完整的有序双向链表，上面几层是抽稀的索引层，每隔几个节点保留一个指针。查找时从最顶层快速定位到目标附近，再逐层下沉到精确位置。查找、插入和删除的平均时间复杂度都是 O(log N)。范围扫描只需沿底层链表前进（O(log N + M)），比红黑树的中序遍历更直接。插入时按新节点的随机层数，逐层更新前驱节点的前向指针和跨度（span），不需要旋转或再平衡。节点层数按随机结果决定，跳表高度大概率落在 O(log N)。每条向前指针还记录一个跨度（span），表示沿它前进跨过了多少个元素。查找时，把实际前进路径上的跨度累加，就能算出元素的位置，不必从表头逐个计数。排行榜的名次查询，靠的正是这份额外信息。

选跳表而非红黑树，是因为实现更简单、范围操作更直接。多层索引长什么样、查找怎么走，见图 2-2。

**字典（dict）** 是 Redis 哈希类型的底层结构，也是 Redis 内部键空间（实例里所有 key 组成的整体）本身。它是一个链式哈希表，用 SipHash 做哈希函数（Redis 4.0 起为防哈希洪泛攻击，从 MurmurHash2 改用带随机种子的 SipHash），冲突用链表解决。

渐进式 rehash 是 Redis 字典最特别的设计，实现上依赖一个双表结构：每个字典内部同时持有两张哈希表，这里分别记作 `ht[0]` 和 `ht[1]`。正常情况下只用 `ht[0]`，`ht[1]` 是空的。当负载因子（`used / size`）超过扩容阈值（通常为 1）或低于缩容阈值（0.1）时，Redis 不会一次性把所有键从 `ht[0]` 搬到 `ht[1]`，因为那会阻塞主线程。它先给 `ht[1]` 分配一个更大的（或更小的）空间，设一个游标 `rehashidx = 0`，表示"搬迁进行中"。此后在字典的增删改查中，Redis 会顺带迁移少量数据，并推进 `rehashidx`，逐步完成整张表的搬迁。同时，新写入的键直接进 `ht[1]`，查找和删除则先查 `ht[0]` 再查 `ht[1]`。当 `rehashidx` 走完所有桶，`ht[1]` 变成新的 `ht[0]`，旧表释放，`rehashidx` 重置为 -1，rehash 结束。

这套机制把搬迁工作分摊到后续操作里，减少一次性搬迁造成的长停顿；但一次搬迁需要处理一个桶中的全部元素，并不构成单次操作延迟的硬上限。除命令触发外，定时任务也会推进部分字典的 rehash。这里值得借鉴的是：**把集中发生的搬迁工作分散完成**。这套双表搬迁画出来就是图 2-3。

![图 2-3 渐进式 rehash 的双表搬迁过程](diagrams/fig-2-3.svg)
图 2-3　渐进式 rehash 的双表搬迁过程：以旧表桶 2 的一次搬迁作前后对照。

搬迁不是整桶平移：旧表从 4 个桶扩到 8 个桶时，桶 2 里的 k7、k3、k9 只能落在新表的桶 2 或桶 6。键要用同一个哈希值和新表的掩码重新计算桶号，原来在同一桶里的键可能因此分开。这部分计算和搬移一起，摊在每次操作顺带的那一小步里。

**压缩列表（ziplist）与紧凑列表（listpack）** 是 Redis 用来提高内存密度的数据结构。ziplist 是一块连续内存，所有元素紧挨着存，没有指针开销。每个元素存的是"前一个元素长度 + 自己的编码 + 自己的数据"。这带来较高的内存密度，但也带来连锁更新问题：一个元素变长后，下一个元素里记录"前一个元素长度"的字段可能从 1 字节扩成 5 字节，再后面的元素又因此逐个跟着扩。早期实现（如 Redis 6.0）每扩一个字段都搬移后方字节，最坏会出现 O(n²) 的累计搬移；6.2 已改为先统计扩张量，再集中扩容和搬移，但元素之间的长度依赖仍在。listpack（7.0 起取代了 ziplist 的全部内部用途，旧格式代码保留兼容）把"前一个元素长度"改成了"自己的长度"。每个元素只记录自身长度，不再依赖前一个元素的长度，因此消除了连锁更新；插入时仍可能搬移后方字节。连锁怎么发生、怎么被消除，并排画在图 2-4 里。

![图 2-4 ziplist 连锁更新与 listpack 的消除](diagrams/fig-2-4.svg)
图 2-4　ziplist 连锁更新与 listpack 的消除：同一个元素变长，在两种格式里的不同后果。

触发点在 254 这个长度上（0xFF 留作整个 ziplist 的结束标记，0xFE 用作 5 字节编码的信号，1 字节能自由编码的长度只有 0–253）：比它短的长度用 1 字节就装得下，跨过它，字段要从 1 字节扩成 5 字节。连锁只向后传播，因为每个元素只依赖前一个元素的长度。

**整数集合（intset）** 是 Redis 集合类型在小数据且全为整数时的底层编码。它是一块连续的有序整数数组，查找用二分。intset 的升级有两条路径。

第一条是**编码升级**。intset 内部用统一的整数编码存储所有元素：能存 int16 就不上 int32，能存 int32 就不上 int64。但一旦插入一个值越过了当前编码的范围（比如当前所有元素都是 int16，突然插入一个 50000），intset 不会报错，而是把整个数组的所有元素统一升级到更宽的编码（int16→int32 或 int32→int64），然后插入新值。编码只升不降：哪怕后来所有大值都被删了，仍保留较宽的编码。这样省去了自动降级时的判断和数组调整，代价是可能多占一些空间。

第二条是**底层结构转换**。当集合里插入一个非整数元素时，intset 作为纯整数结构无法表示该元素，会自动转换编码：7.2 起，只有插入后元素数与成员长度都满足 listpack 阈值时才转为 listpack，默认限制分别为 128 个元素和每个成员 64 字节；否则直接转为哈希表。listpack 后续写入超出这些限制时也会转为哈希表。7.2 之前，intset 遇到非整数元素直接转为哈希表。

纯整数集合另有元素数量阈值——元素数超过 set-max-intset-entries（默认 512）时直接转哈希表，不经 listpack，与 listpack 的 128 个元素阈值对应不同的转换路径。

listpack → hashtable 的转换，和 Hash 类型小数据编码的升级是同一套逻辑。**数据量小时用紧凑结构省内存，膨胀后自动切换到复杂结构**。所有升级对上层命令透明。五种结构与它们的切换关系，汇总在图 2-5。

### 2.2.2 MySQL：面向磁盘页和通用查询的 B+ 树与行格式

MySQL（InnoDB）的数据结构受到一个关键限制：**数据在磁盘上，一次 I/O 取一页（16KB）**。这个限制是决定性的。内存访问是纳秒级，而磁盘 I/O 是微秒到毫秒级，差着三到五个数量级。所以 InnoDB 的核心数据结构要解决的正是这个问题：**让每一次磁盘 I/O 读上来的 16KB，每一个字节都有用**。

**B+ 树** 是 InnoDB 唯一的主索引结构。一棵 B+ 树从上到下：根节点、内部节点（非叶子）、叶子节点。内部节点只存键和子节点指针（一个 16KB 页就能容纳几百个键，两层内部节点、每叶几十行，千万行的表整棵树也只有三层，树极矮），叶子节点存完整行数据——这是聚簇索引，InnoDB 的表本体就按主键组织成树。二级索引的叶子保存索引键和主键值；需要读取索引之外的列时，再用主键回到聚簇索引取数据，这一步叫回表。叶子之间用双向链表串联。

这套设计兼顾点查、范围扫描和按索引键顺序读取。点查从根走到叶，树越矮，需要访问的页越少；页在缓冲池中时，不必再读磁盘。范围扫描找到起点后，可以顺着叶子链继续读取。哈希索引擅长等值查找，却不维护这种键顺序。B+ 树因此适合同时需要点查和有序访问的关系查询。第 8 章再展开页内布局。

B+ 树的代价在写路径：插入新键可能触发页分裂（页满时一拆为二，级联向上），分裂会增加页修改和日志记录，之后还可能增加脏页刷盘的工作量。跳表插入只做局部的指针更新，没有页分裂；页分裂是 B+ 树按页组织节点所带来的代价（这里采用 InnoDB 默认的 16KB 页），也是 MySQL 为通用查询能力付出的成本。图 2-6 画了一棵三层的示例树。

![图 2-6 MySQL InnoDB B+ 树结构](diagrams/fig-2-6.svg)

**行格式（Row Format）** 决定一行数据怎样放进页里。以 Dynamic 为例，行太长时，可以把部分较长的变长列移到溢出页，行内留下指针。这样让索引页能容纳更多记录，代价是读取移出的内容还要访问额外的页。具体布局留到第 8 章。

**自适应哈希索引** 是 InnoDB 在 B+ 树之上的额外一层。InnoDB 根据索引页上的查询模式，按合适的索引键前缀在内存中建立哈希索引；能够命中它的查询，可以通过平均 O(1) 的哈希查找直接定位记录，省去 B+ 树 O(log N) 的逐层查找。冷数据留在磁盘，热点页进缓冲池，被反复点查的页再由自适应哈希接管。数据结构会随访问模式自动调整。这层哈希也要占内存、维护自身结构，并可能带来锁竞争。查找省下的时间抵不过维护成本时，关闭它反而更合算。

### 2.2.3 Kafka 的 RecordBatch：批量、顺序、演进

Kafka 的数据结构要同时满足三件事：**磁盘顺序追加 + 批量压缩 + 格式可演进**。满足这三件事的结构就是 RecordBatch，一个专为"把多条消息打成一个包"设计的结构，既不是树也不是哈希。

**RecordBatch 是 Kafka 组织消息的基本单元。** 生产者把同一分区的消息组织成批发送，一个批也可以只有一条消息。Broker 校验后按批追加到日志段，消费者再成批拉取。协议与日志复用批格式，减少了重新组织数据的工作；需要改变压缩方式时，仍会增加重新编码的成本。

每个分区有多份副本，同一时刻只有一台 Broker 是 Leader，所有写入都由它处理；Leader 宕机后会切换，`partitionLeaderEpoch` 随切换加一，标记这批数据对应的 Leader 任期。

从 V2（KIP-98，0.11 引入）起，一个 Batch 的头部字段如下：

**表 2-1　Kafka RecordBatch V2 头部字段**

| 字段 | 作用 |
|---|---|
| `baseOffset` / `batchLength` | 这批消息的起始偏移量 / 整个 Batch 除最前 12 字节（`baseOffset` 与 `batchLength` 自身）外的字节长度（用于快速跳到下一个 Batch） |
| `partitionLeaderEpoch` / `magic` | 哪一任 Leader 写了这批 / 格式版本号（V2 = 2） |
| `CRC` | 整批一条校验，而非每条消息各自 CRC |
| `attributes` | 压缩类型 + 时间戳类型 + 事务标记 |
| `lastOffsetDelta` | 最后一条消息距离 baseOffset 的差值 |
| `baseTimestamp` / `maxTimestamp` | 时间戳差值的基准 / 批内最大时间戳（CreateTime）；LogAppendTime 模式下后者记录 Broker 的追加时间 |
| `producerId` / `producerEpoch` / `baseSequence` | 幂等 + 事务所需的 Producer 状态（Broker 按序列号对重试去重） |
| `recordsCount` | 这批有几条记录 |

头部之后是实际的消息记录。每条记录只保存相对批头的偏移量和时间戳差值。例如偏移量为 1000000、1000001、1000002，批头记录 1000000，记录里只需保存 0、1、2。差值通常较小，配合变长整数编码，才会少占字节。V2 把可以共享的信息集中到批头，减少逐条重复保存的元数据，见图 2-7。

![图 2-7 Kafka RecordBatch V2 字段分组](diagrams/fig-2-7.svg)
图 2-7　RecordBatch V2 字段分组：按功能分组，不表示磁盘字节顺序。61 字节头部共享整批元数据，每条 Record 只存与 base 的差值。

相似消息聚成一批，压缩收益通常可达数倍，具体取决于消息内容相似度与压缩级别；差值编码把每条记录的元数据开销降到个位数字节；CRC（循环冗余校验）由逐条保存改为整批共享，减少重复保存的校验字段；`magic` 字段标明格式版本，新旧格式可以共存。Kafka 重点优化追加写与按 offset 定位后的连续读取，不提供按业务 key 的点查。Batch 与成批写入、成批拉取相配合，正好服务于这条主要路径。

## 2.3 通信协议：客户端和服务端怎么对话

三家的协议各有值得观察的重点：RESP 的类型与长度前缀便于解析和调试；MySQL 的预编译语句复用重复工作；Kafka 将批量传输与请求版本管理结合起来。下面分别看这些设计方便了什么，又付出了什么代价。

### 2.3.1 Redis RESP：能被人眼读懂的极简协议

Redis 的协议叫 RESP（REdis Serialization Protocol）。它的设计目标非常明确：实现简单（服务端解析不费 CPU）、便于人工调试（文本参数可以直接辨读，也能用 `nc` 手工发送简单命令）、能表达所有 Redis 命令和返回值。

以 RESP2 为例，首字节区分五种基本类型：`+` 是简单字符串，`-` 是错误，`:` 是整数，`$` 是批量字符串，`*` 是数组。数组先给出元素个数，批量字符串先给出内容的字节长度，解析器据此识别边界。

例如，`SET key value` 是一个包含三个批量字符串的数组：

```text
*3\r\n
$3\r\nSET\r\n
$3\r\nkey\r\n
$5\r\nvalue\r\n
```

但简单也有代价。RESP 用文本表示类型、长度和部分数值，这些前缀也占空间：`SET key value` 编码成上面那串字节，有三十多个字节。每条命令独立，没有 Batch 概念（Pipeline 只是多条命令一起发，每条仍然独立编码和返回）。版本演进靠手工约定。Redis 6.0 之前没有版本协商，客户端假设服务端支持什么就发什么，不支持就报错。

**但 RESP 的"简单"恰好匹配了 Redis 的核心目标。** 对于短小的 Redis 命令，RESP 的解析较简单；可读的前缀与文本参数也便于人工检查，能降低协议调试的成本。用 `redis-cli` 连上实例敲命令，就是其协议的原生交互方式。RESP 保留可读前缀，同时用长度信息简化解析。它没有把每个字段都压到最小，而是保留了实现和调试上的便利。

Redis 6.0 引入的 RESP 3 补上了版本协商这个缺口：客户端用 `HELLO` 命令在握手时声明协议版本，服务端始终兼容 RESP 2；切到 RESP 3 后部分命令的返回类型会变（如 `HGETALL` 从扁平数组变为 Map），需要客户端显式适配。MySQL 和 Kafka 的版本协商是内建的，RESP 用了十年才补上，补的形式还是一条文本命令。

### 2.3.2 MySQL 二进制协议：封帧与预编译

MySQL 采用**二进制封帧**，但经典查询的结果行主要按文本编码；预编译语句则使用二进制结果集。在高并发 OLTP（联机事务处理）中，预编译通常可以复用解析结果，二进制结果集也能减少部分数据类型的传输开销。

MySQL 协议分为几个阶段：握手（服务端发送能力标志和认证随机数、客户端按认证插件要求回传认证响应）、命令（客户端发送 SQL 或预编译语句 ID）、响应（服务端返回结果集或 OK/ERR）。

MySQL 经典协议包先有一个 4 字节头：3 字节记录后面载荷的长度，1 字节记录包序号。接收方因此知道这一包有多少字节。

包内的整数再按字段选择定长或变长编码。小整数可以少占字节，大整数再使用更长表示；字符串先给长度，再放内容。固定包头解决整包边界，长度编码解决包内字段边界，这是两个层次。

**预编译语句** 是 MySQL 协议在"效率"上的关键设计。客户端先用 `COM_STMT_PREPARE` 把一条带占位符 `?` 的 SQL 模板发给服务端，服务端完成解析与语义检查、返回一个 `statement_id`。此后每次执行只需发 `COM_STMT_EXECUTE` + `statement_id` + 占位符的值。解析结果通常可以复用，执行计划则在每次执行时按当时的统计信息重新生成，反复执行时省掉的是逐次解析的 CPU 开销。这和 Redis Pipeline 不同：Pipeline 省的是网络往返（RTT，Round-Trip Time），预编译语句省的是服务端 CPU。同一类效率问题，两种解法对应两个不同的瓶颈。

**二进制结果集** 按列类型编码行数据，可以减少部分数值与日期时间数据的传输开销。具体是否比文本表示更小，取决于类型和值；短小整数的文本表示也可能更省字节，字符串列两种编码几乎一样大。按二进制编码的整数、浮点数与日期时间字段不再能直接按文本辨读，需要结合列元数据与协议规则解析。这是在 OLTP 场景中为传输和解析效率作出的取舍。

### 2.3.3 Kafka 请求/响应协议：统一头部、版本化、批量优先

Kafka 的协议按请求类型组织。Produce、Fetch、Metadata、JoinGroup、SyncGroup……几十种请求类型，每种请求有自己独立的 Schema，每种 Schema 有自己的版本号。

Kafka 请求头中值得关注的是四个字段：`api_key` 标识请求类型，`api_version` 指定这类请求使用的格式版本，`correlation_id` 用来匹配请求和响应，`client_id` 便于识别请求来源。每类请求可以独立演进，客户端选择双方支持的版本，不必让所有客户端同时升级。

**批量优先** 主要体现在 Kafka 的消息写入与读取路径上。Produce 可以携带多个分区的消息批，Fetch 按分区和 offset 拉取一段记录。把多条记录合并处理，可以摊薄请求与传输开销；同一批格式贯穿生产、日志存储和拉取，也减少了重新组织数据的工作。

## 2.5 架构启示

数据结构和协议是软件最底层的两个决策，一旦确定就难以更改。

### 启示一：数据结构服务于核心目标

Redis 要快，所以 SDS 取长度的时间复杂度是 O(1)，字典做渐进式 rehash。跳表让有序操作的实现更简洁。MySQL 走另一条路，为了对齐磁盘页，B+ 树内部节点只存键不存数据（树必须矮），叶子和叶子之间用双向链表串起来，范围扫描不用回头。Kafka 又不一样，它的吞吐需求最大，于是 RecordBatch 把一批消息当成一个批量存储与传输单元。

### 启示二：协议设计要呼应访问方式

协议不必暴露内部的数据结构，但应减少常见访问中的重复工作。Redis 用长度前缀简化解析，MySQL 用预编译复用解析结果，Kafka 用批量传输摊薄请求开销。我设计协议时，会先看一次请求重复了什么：是网络往返、解析，还是数据搬运，再决定该复用哪一部分。

### 启示三：简单协议的接入成本最低

RESP 2 只有五种类型前缀，基础协议解析较容易实现，降低了不同编程语言接入的门槛。评估一个服务端的对外接口时，看文档页数不如看写个客户端要几行代码。

### 启示四：版本字段是为未来演进预留的扩展点

MySQL 在握手时交换能力标志，Kafka 在每个请求头里带版本号。没有版本协商的协议（如 6.0 之前的 RESP）只能通过后续手工约定来补，而一旦客户端生态已经铺开，Breaking Change 几乎是不可能的。我自己设计新协议，会先从第二个版本开始——第一个版本很少有人能把边界想全。留出能力标志或版本字段，是为了将来想做改动时不必推倒重来。

## 2.6 小结

三个软件的结构和协议，都围绕常见访问方式组织。Redis 为不同操作选择不同的内存结构，InnoDB 用页式 B+ 树兼顾点查和有序访问，Kafka 用批组织追加与传输。回到开头的排行榜，增加索引解决了查榜问题，但名次查询还需要合适的结构支持。所以我自己定数据结构或协议前，先把最热的两三种访问模式列出来，再对着结构核对；顺序反过来，挑中的多半是最近用熟的那个。

内存怎么管、分层怎么切、同步怎么追平，都被这里的结构选择限定，第 4、5、9 章会接着展开；下一章先看进程，从启动、崩溃到恢复，三家在进程这一层另有各自的对策。
