# 后记

九章走完，这本书讨论了三个软件、八个主题，贯穿它们的是同一种视角。

如果要在结尾留一句话，我会留一个方法：下次面对设计决策时，先弄清它解决了什么约束、代价由谁来承担。能把这两点弄清楚，选型往往就不言自明。关注 Redis、MySQL、Kafka 各自放弃了什么，比关注它们各自做到了什么更有信息量。

全书反复出现几条线索：先确定唯一正本，其余数据都能从它重建；用层把易变的部分隔开，接口保持比实现稳定；硬件对顺序和批量访问友好，性能优化多半是在把随机改成顺序、把单条攒成批；更强的可靠性要付性能代价，先弄清代价再决定；故障总会发生，状态不显式建模，恢复就不可预测。这些规律不只属于这三个软件。管理状态、权衡性能与可靠性的系统都适用；在分布式里维持一致性，靠的也是这些规律。

从使用者到设计者，关键在养成一种习惯：遇到任何设计决策，先还原它面对的约束，再判断它的取舍是否值得。这本书如果能帮你养成这个习惯，就够了。

---

**一个真实的故事**

去年我在一个项目里犯了错。第 7 章开头那次库存事故就出在这个项目，这里完整复盘一遍。那个项目是一个活动库存系统，业务方说"要快"，我们就选了 Redis Cluster 做主存储。上线第一个月一切正常，响应时间在个位数毫秒，业务方很满意。

大促那天出了事。一个网络分区刚好把负责库存那个槽的主节点从集群里割了出去，Redis Cluster 自动选举了新主，但老主在被割出去的少数派分区里还在短暂地接受写入。网络恢复后，这部分写入被新主的数据覆盖了，库存多卖了。

事后复盘，团队所有人的第一反应是"Redis 丢了数据"。但 Redis 其实没出 bug，是我们把一个默认形态偏 AP（异步复制可丢写；分区时少数派超时后其实会停写，CAP 归类在社区有争议，见 7.2.3）的系统用在了必须保证一致性的场景上。库存属于交易数据，交易系统必须有一个在任何故障下都不被质疑的正本。Redis 不是那个正本，MySQL 才是。

我后来把库存系统改成了 MySQL 双 1 配置做正本，Redis 只做预扣减的前置层（SETEX + INCR，吸收大部分读流量）。架构设计就是在自己的约束条件下，选择承受得起的代价。

这个故事回头看，全书九章其实都在说这一件事。

---

**下一步做什么**

这本书的价值在于读完之后的动手。从自己维护的系统入手，先找出它的正本：是数据库、是日志，还是消息队列？然后问自己：如果这个正本丢了或坏了，哪些东西能重建、哪些东西就永久丢了？

接下来，可以挑一个天天在用但从来没动过的参数，把它往反方向调一次，看看结果：`innodb_flush_log_at_trx_commit` 从 1 调到 2，吞吐能涨多少；`appendfsync` 从 everysec 调到 always，延迟会增加多少；Kafka 的 `acks` 从 all 调到 1，吞吐又能涨多少。"可靠性要付性能代价"这句话读十遍，不如在自己的终端里实际观察一次。

在下一次技术评审时，试着先说约束再说方案。把"我们选 Kafka 因为它快"换成"我们的峰值写入是 XX MB/s、消费者可以接受 YY 秒延迟、数据允许丢不超过 ZZ 条，在这些约束下，Kafka 的追加日志 + 顺序写是合适的"。方案质量会在这些细节里体现出来。

这三件事本身不难，缺的只是动手去做。

剩下的，希望你在自己的系统里去印证。
