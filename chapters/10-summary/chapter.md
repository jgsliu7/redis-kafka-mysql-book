# 第 10 章 总结：架构设计的共性规律与取舍

## 本章导读

前九章——第 1 章引入三个样本、第 2 到 9 章每章一个主题——三个软件在八个主题上有截然不同的方案。Redis 侧重低延迟，MySQL 偏正确性，Kafka 偏吞吐。但这些差异底下是同一套基本结构。设计一个新系统时，该借鉴 Redis 的极简、MySQL 的严谨还是 Kafka 的可调，要看具体约束。知道特性不等于会做架构决策。只有把"它们为什么这样选"抽象成规律，规律才能迁移到实际系统中。这一章把前九章的启示串成一条主线。

## 10.2 共性规律：三个软件背后的同一套基本结构

下面把九章启示提炼为五条可复用的架构共性规律。这些规律并非本书首次发现，价值在于用三个软件的实证把它们变成可操作的工具。

### 10.2.1 规律一：先确定唯一正本

> **先为每类数据确定权威来源（source of truth），再区分副本和派生结果。权威来源可以由多个物理副本共同保存；保留它和必要的恢复材料，其他数据才有重建依据。**

在 Redis 中，内存键空间是运行时处理命令的依据，RDB 保存快照，AOF 保存恢复数据所需的日志。崩溃后能恢复到哪里，取决于已保存的持久化内容；能否容忍数据丢失由业务决定，但不能容忍内存里的键值对算错。

在 MySQL 中，磁盘上的数据页和已持久化的 redo log 共同提供崩溃恢复依据，缓冲池里尚未刷回的修改可以通过 redo 恢复。`innodb_flush_log_at_trx_commit=1` 在提交时等待 redo log 刷盘；存储系统正确执行刷盘请求，是这一保证成立的前提。双写保存完整页副本，用于修复不完整的页写入，再由 redo 恢复后续修改。

在 Kafka 中，消息保存在分区日志中，PageCache 缓存日志内容，多个副本共同提供容错能力。消费者偏移量记录消费组处理到哪里，需要单独保存；只保留消息日志，并不能重新算出业务已经完成了哪些处理。

我设计一个有状态系统时，第一件事就是回答"哪份数据是正本"。这个答案一旦模糊，故障恢复就会失控，因为恢复时你不知道该信谁。一个常见的反例是把缓存和数据库都当正本，结果两者不一致时系统行为不可预测。

### 10.2.2 规律二：用"层"隔离可变性

> **稳定的契约留在层间，多变的实现隔离在层内——这是一个比"高内聚低耦合"更可操作的判据。**

层是工程上对付变化的手法，Redis、MySQL、Kafka 各自用层解耦了不同维度的变化。Redis 的 redisObject 区分"语义类型（type）"和"底层编码（encoding）"，同一种 hash 类型，底层编码可以是 listpack，也可以是 hashtable。编码转换保持命令的语义，内部实现仍需识别和处理具体编码，引入新编码时还要适配相关代码。MySQL 的 Handler API 把存储引擎做成可插拔的层，Server 层（解析、优化、执行）通过共同接口访问 InnoDB/MyISAM；引擎能力不同，同一个 SQL 能否迁移仍取决于它使用的功能，代价是虚函数调用与跨层上下文（THD）传递。Kafka 通过 UnifiedLog / Partition / LogSegment 等对象分离职责，分段细节由日志层管理。Tiered Storage 保持客户端按分区和 offset 读写日志的接口，在 Broker 内增加远程段的访问实现，同样背上了分层带来的间接性。

当我在两套实现之间犹豫，我会先抽接口。接口稳定了，实现可以一个一个换、一个一个演进，而不会牵一发动全身。

### 10.2.3 规律三：把访问改写成顺序和批量

> **顺序访问可以减少定位开销，批量处理可以摊薄系统调用和网络往返的成本；收益最大的一项性能优化，往往是把随机访问改写成顺序、把单条操作合并成批量。**

Redis 的 pipeline 把 N 次逐条等待合并成一批请求的等待；MULTI/EXEC 提供命令不被其他客户端请求穿插的执行保证，两者可以连用。AOF 重写根据当前数据生成恢复所需的精简表示。MySQL 的修改缓冲暂存适用的非唯一二级索引页修改，在页读入时合并，减少立即读取这些页的随机 I/O；组提交让多个事务共享日志刷盘，预读则把预计将访问的页提前读入。Kafka 的 RecordBatch 把多条消息打包成一个存储单元，生产者攒批，副本 FETCH 也批量拉；符合条件的日志发送路径通过零拷贝（sendfile）减少用户态数据复制。

这条规律能跨越多个软件，是因为机械盘寻道、存储 I/O、网络往返和系统调用，都有值得摊薄的固定开销。对软件架构师来说，应用这条规律时，往往先改写访问模式以适应硬件。靠堆 CPU 收益有限。性能优化先问"这里能不能批、能不能顺序"，再去想换更快的硬件。当我发现自己在一个循环里反复单条调用，就该考虑把单条操作合并成批。

这条规律还可以放到更底层的存储层次结构里看。CPU 的寄存器、L1/L2 缓存、内存、磁盘，在访问延迟和容量之间作出不同取舍。缓存利用局部性减少对下层的访问，其他层次则承担计算中的数据暂存、主存储或持久化等职责。第 4 章启示五讲的是软件怎样安排内存与磁盘：MySQL 的缓冲池和 Kafka 使用的 PageCache 缓存磁盘内容，Redis 的内存则直接保存运行时数据。图 10-1 对照的是这些存储位置与职责。我们在架构上反复遇到的存储取舍，计算机组成里几十年前就给过答案，这也是观察三个软件时最让我在意的一条线索。

缓存未命中的访问可能需要读取更慢的存储；Redis 直接访问内存中的数据，持久化文件主要承担恢复职责。三个软件在这里的差异，是内存与磁盘怎样配合。

### 10.2.4 规律四：更强的可靠性要付性能代价，先弄清代价再决定

> **提高可靠性，常要增加同步等待、复制或持久化工作。具体代价取决于要提供的保证和实现方式，是否接受由设计者决定。**

Redis 的 `appendfsync` 提供三种刷盘策略：`always`（每批写命令追加后刷盘，返回前等待完成）、`everysec`（约每秒刷盘，开启 AOF 后的默认策略）、`no`（不主动调用 fsync，交给操作系统刷盘）。这是持久性与写入开销的取舍。MySQL 的 `innodb_flush_log_at_trx_commit` 控制提交时 redo log 的写入和刷盘，`sync_binlog` 控制 binlog 的刷盘；两个都设为 1 是"双 1"，都设为 0 是"双 0"，此外还有其他组合。双 1 在提交确认前等待相应日志落盘，组提交可以让多个事务共享刷盘；双 0 减少提交时的刷盘等待，但增加故障后的数据丢失风险。

半同步复制按配置等待副本收到事务并刷入 relay log，超时可退回异步。它与异步复制的差别，是确认等待与恢复点目标（Recovery Point Objective，RPO）之间的取舍。Kafka 的 `acks=0/1/all` 决定生产者等待多大范围的确认，`min.insync.replicas` 则为 `acks=all` 设置最小 ISR 数量要求。这些复制确认与本地 fsync 是不同的保证。幂等写入处理生产者重试造成的重复，事务则可以把多个分区的输出和消费进度一起提交；配合 `read_committed`，可以实现 Kafka 内部的恰好一次处理，写入外部系统还需要对方配合。它们增加的 Broker 状态与协议开销，也需要按业务需求判断是否值得。

这些参数控制的是不同保证，选择时要先说明希望防住哪类故障。我应用这条规律时，会把所选保证的代价暴露给真正在意它的人（业务方、SRE），让"愿意付多少延迟"和"能容忍多少丢失"成为一次明确的取舍，而不是默认把所有参数调到最严。规律四的另一面：为业务不需要的保证承担额外等待和处理开销，是在浪费性能。

### 10.2.5 规律五：复杂状态必须显式建模，故障恢复要可预测

> **复杂状态必须显式建模，并为每个状态预先写定恢复路径；能写出来才算可控，写不出来的状态，故障时很可能演变成事故。**

一个有状态的系统，运行时都在维护一堆隐式或显式的状态。三个软件都把重要状态记录下来，并安排相应的恢复过程。Redis 启动时按 RDB/AOF 恢复数据。MySQL 维护活跃事务、锁等待、LSN 等运行时状态，崩溃后重放 redo、用 undo 回滚未完成事务；复制则用 GTID 集合标识已接收或执行的事务，在复制源仍保留所需日志时补齐缺失的事务。Kafka 维护 HW/LEO、ISR 和分区 leader epoch，结合副本日志历史处理分叉尾部；Controller 负责分区 Leader 的选举与管理。日志内容、复制进度和元数据共同决定恢复动作。

应用到自己的系统，我会先问"它最坏会处于哪些状态"，再为每个状态写"如何进、如何出"。规律五是规律一的延伸：正本之所以能守住，靠的就是把它的状态显式建模出来、把恢复路径提前写定。

### 10.2.6 规律小结

五条规律互相配合：确定数据的权威来源，用分层控制变化，用访问方式改善效率，权衡可靠性的代价，再把状态与恢复过程说明白。

> **适用边界**：这五条规律来自三个有状态存储软件的观察。其中的分层与批量处理也适用于无状态服务、分析系统和多写者场景。无状态微服务的数据权威来源通常在外部；边缘计算/Serverless 函数需要处理短暂驻留与生命周期变化；纯分析型系统更重视列存和批量扫描。把规律用到这些场景时，要重新判断数据归属、访问模式和恢复要求。框架的作用，是帮助列出这些问题，具体方案仍由实际约束决定。

## 10.3 从规律到权衡框架

上一节讲规律是什么，这一节把规律变成可操作的取舍框架：五个反复出现的权衡维度，加上一张选型问题图和三道判断练习题。

### 10.3.1 五个反复出现的权衡维度

**维度一：速度 vs 持久性**。数据写下去多久才持久保存，是这一维度要问的问题。Redis 开启 AOF 后默认采用 `appendfsync=everysec`，故障时可能丢失最近约一秒的写入，实际窗口受刷盘进度影响；使用默认 RDB 快照时，恢复点取决于最近一次成功快照。MySQL 的 `innodb_flush_log_at_trx_commit=1` 与 `sync_binlog=1` 均为默认值，合称"双 1"：提交确认前等待相应日志落盘，组提交可让多个事务共享一次刷盘；断电恢复还依赖操作系统和存储设备正确履行刷盘承诺。Kafka 的 `acks=all` 等待 ISR 复制确认，带来副本同步等待；它不要求所有副本同时 fsync，保护范围还受最小 ISR 要求、存活副本和选主策略影响。允许丢失的缓存、计数器和限流数据可偏速度端；账本、订单、支付必须按业务要求保证持久性。核心问题是"这个场景丢得起吗"。

**维度二：一致性 vs 可用性（CAP 的工程体现）**。网络分区时，若要求所有操作仍满足线性一致性，就不能同时保证每个非故障节点都能完成请求。Redis Cluster 的少数侧会在超时后拒绝写入，多数侧恢复服务也要有可晋升的副本；窗口内已确认的写入仍可能在故障切换时丢失。MySQL MGR 无法取得多数派时，不能继续确认组内写入，读取行为还取决于配置。Kafka 默认从 ISR 中选主；使用 `acks=all` 时，ISR 数量不足 `min.insync.replicas` 会使写入失败，允许非 ISR 副本当选则可能损失已提交数据。它们需要分别评估分区时哪些操作还能完成、能维持什么保证。金融核心宁可拒绝操作，也要避免错账；社交 feed 则可以在业务允许的范围内接受暂时不一致，以维持服务。

**维度三：空间 vs 时间**。用更多存储结构减少查找工作，或用更多扫描和计算减少额外存储，是常见的取舍。Redis 让运行数据驻留内存，简单键查询可用哈希表快速定位，具体操作复杂度仍取决于命令和数据结构；MySQL 用 B+ 树索引和缓冲池减少查找与磁盘访问，索引和缓存需要额外空间；Kafka 用稀疏索引省空间，先定位附近的日志位置，再顺序扫描到目标。空间换时间的代价是内存和存储，时间换空间的代价是 CPU 与延迟。热点读、低延迟访问要往空间换时间上靠；冷数据归档、高吞吐追加反过来，往时间换空间上靠。

**维度四：简单 vs 灵活**。固定部分决策可以减少运行时开销，保留开关和接口则增加调整空间。Redis 的普通命令执行路径以单线程为主（6.0 起可开启多线程 I/O 卸载网络写），减少了这条路径的数据并发控制，代价是命令执行难以直接利用多个 CPU 核心；MySQL 的 Handler 接口留了灵活性，支撑可插拔存储引擎，但背上虚函数开销和跨层上下文传递；Kafka 把副本、偏移量、事务做成显式原语，灵活但概念多、学习曲线陡。简单难演进，灵活易误用：这是一种长期存在的张力。规模可控、需求稳定的，要简单；需求多变、要长期演进的，宁可复杂也要灵活。

**维度五：通用 vs 专用**。做一个什么都能做的系统，还是聚焦一类需求做到最强。MySQL 偏通用，事务、SQL、多种存储引擎、多种复制模式都支持，所以它能在很多场景都用上，但每个维度都很难做到最强；Redis 与 Kafka 偏专用：Redis 专攻内存快速存取与计算，Kafka 专攻高吞吐日志，专用系统在单一目标上性能很强，但覆盖不了边界需求。业务域宽、需求杂，倾向通用；性能决定成败、需求聚焦，倾向专用。

五个维度不是孤立的，它们会互相牵扯。一次写入可以同时等待本地刷盘和副本确认，两种等待共同影响延迟；但本地持久化与网络分区时的复制选择，处理的是不同故障。评估时可以结合它们的成本，同时分别核对它们提供的保证。

图 10-2 从"我要建一个有状态的系统"出发，分别问四个问题：数据能丢吗、需要哪些确认与读取保证、读写模式是什么、是否需要长期演进。每个分支给出可以参考的设计，需要结合实际约束使用。**先回答清楚自己的约束**，再去理解对应保护机制为什么被设计成那个样子。比如秒杀库存系统，既需要保住已确认的订单，也要防止并发扣减造成超卖：可以研究 MySQL 的双 1 配置、事务约束，以及需要副本容错时的 MGR，但这些机制解决的是不同问题，具体方案还要落实到库存更新与故障切换的处理。

### 10.3.3 三道判断练习

下面三道练习，用这套框架分析具体约束下的选择。

**练习一："做一个网约车系统，司机位置上报和派单该放 Redis 还是 MySQL？"** 常见的思路是"都是核心系统，统一放 MySQL"。但这两个子问题的访问模式完全不同。司机位置每几秒上报一次，读写都高频，丢一次，等下一次上报就补回来，这是"快"的问题，适合放 Redis（GEO 地理位置结构直接支持附近司机查询）。而派单成单属于交易数据：同一单派给两个司机就是事故，状态迁移必须可审计，这是"对"的问题。用规律一的判据，可以让 MySQL 保存订单的权威状态，通过事务与业务约束保护状态迁移，并按持久性要求配置刷盘；Redis 保存司机位置，提供位置索引与派单候选的快速过滤。订单派生数据可按 MySQL 重建，位置则由后续上报更新，最终派单仍需核验订单状态。借鉴的是明确数据归属，以及用快速筛选减少交易处理的候选范围。

**练习二："日志采集系统，要不要上 Kafka 的事务？"** 先看日志场景能容忍什么：如果少量重复可以由消费端去重处理，也能接受一定乱序，又不要求跨分区原子写入或输出与消费进度一起提交，那么 Kafka 事务增加的 Broker 状态、提交协议和隔离读取开销，就换不回对等的业务价值。用规律四（看可靠性代价）的判据：`enable.idempotence=true`（自 Kafka 3.0 起默认开启，未设置冲突配置时无需手动打开）可排除同一生产者会话内因重试造成的重复写入，并维持分区内重试顺序；它要求 `acks=all`、重试次数大于 0，且 `max.in.flight.requests.per.connection` 不超过 5，冲突配置会报错。在这些约束下，再上跨分区事务就是过度设计。

**练习三："一个新业务，要不要一上来就分库分表？"** 分片牺牲了单机事务、JOIN、外键约束，换来水平扩展——这笔账对新业务几乎必亏：过早分片等于为一个还不需要的容量去付昂贵的灵活性代价。用维度四（简单 vs 灵活）和维度五（通用 vs 专用）的判据：先用单机 MySQL + 读写分离顶住，到瓶颈真的出现时再切，切的时候按第 7 章集群架构的演进路径逐级升级。早分片省的是将来从单机迁到分片的那一次大迁移，背上的是从今往后每次跨片事务的复杂度。

## 10.4 给实践者的建议：从使用者到设计者

### 10.4.1 架构设计 checklist：动手前先回答的 12 个问题

把 10.3 的五个维度拆成 12 个具体问题，按"数据 / 性能 / 可靠性 / 运维"四类组织。表 10-2 把每个问题连同"三个软件的答案"和"你的答案"放在一起，作为动手前的自检工具。

**表 10-2　架构设计 checklist（12 问）**

| 类别 | 问题 | Redis 的答案 | MySQL 的答案 | Kafka 的答案 | 你的答案 |
|---|---|---|---|---|---|
| 数据 | 哪份数据是正本？ | 运行时以内存键空间为准，RDB/AOF 用于恢复 | 数据页与已持久化 redo 提供恢复依据 | 分区日志；消费进度另行保存 | 按数据类别写清权威来源和派生数据 |
| 数据 | 读写比例与访问模式？ | 内存键查询与各类数据结构操作 | 随机点查 + 范围扫描，读写比例依业务 | 顺序追加 + 偏移量定位 | 标出热点路径是读还是写、是随机还是顺序 |
| 数据 | 增长上限与冷热比例？ | 运行数据受内存容量约束 | 数据主要存磁盘，缓冲池缓存常用页 | 日志主要存磁盘，PageCache 缓存近期访问内容 | 估算 1 年 / 3 年后的量，标出冷热分界 |
| 性能 | P99 延迟要求？ | 低延迟优先 | 稳定延迟优先 | 高吞吐下的可接受延迟 | 写一个具体数字，含尾延迟目标 |

| 性能 | 是否存在热点？ | 单 key 易成热点 | 单行/单页易成热点 | 单分区易成热点 | 标出最热的 key/行/分区与分担方案 |

| 运维 | 故障排查路径是否清晰？ | slowlog + latency monitor | slow log + performance_schema | Broker log + 消费者 lag | 写下你出问题第一时间看哪个指标 |

### 10.4.2 从使用者到设计者的四个阶段

读这本书的过程，是换一套看问题的方式。这套方式的养成分四个阶段。

![图 10-3 从使用者到设计者的四个阶段](diagrams/fig-10-3.svg)
图 10-3　从使用者到设计者的四个阶段：四级台阶自下而上，两个虚线标注框标出本书各部分覆盖的阶段。

四个阶段的差距不在掌握的名词多少，在能独立产出什么：使用者交出一份能跑的配置；理解者能写出机制解释，能判断一次慢查询慢在哪一层；设计者能给出自己系统的结构与取舍方案；创新者定义新的范式。常见的问题有两种。一种是产出停在使用者一级，却借用理解者的词汇：配置照抄别人的结论，说不出适用约束。另一种是机制没吃透就自建系统：往往只复刻了表面结构，原设计要避开的难点照样撞上。每上一级，检验标准都一样：能不能独立产出这一级的东西。

设计者阶段的核心能力可以拆成三项，每一项都能在三个软件里找到印证。

**抽象能力**：能从 B+ 树、跳表、稀疏索引里看出组织查询路径的不同方式，从 redo log、AOF、Kafka 日志里看出日志在恢复和复制中的不同职责；更进一步，能结合 Redis 复制历史与偏移量、MySQL 的 GTID 集合、Kafka 的分区 offset 与 leader epoch，理解副本怎样确认进度并补齐数据。抽象能力让你把大量细节归纳成少数几条模式。

**权衡能力**：理解每个选项的机会成本。比如 Redis 让普通命令在单线程中执行，以减少数据并发控制，代价是这条路径难以利用多核；MySQL 用提交刷盘降低故障丢失风险，代价是等待存储同步；Kafka 的多副本增加容错能力，也带来同步与管理开销。权衡能力让你能说清"为什么不选另一个方案"。

**工程直觉**：快速识别瓶颈（是 CPU、是 I/O、是网络还是锁），预判规模放大后的表现（数据量翻十倍哪个组件先崩）。直觉来自反复实验，不能只靠读。

### 10.4.3 持续学习与全书收束

读完本书只是起点。还可以沿三条路径继续学习。

读源码。从 Redis 起步，它的代码量小、数据结构清晰，C 语言的直白让你能从命令处理一路追到内存表示，几周就能通读核心路径。再读 InnoDB，重点看页结构、B+ 树、redo log/undo log、MVCC，这部分代码厚但思路连贯。最后读 Kafka 的 Log 与 ReplicaManager，理解"以日志为正本"的工程实现。读源码的方法是带着问题去：比如"双 1 真的能保证不丢吗，看代码怎么 fsync 的"。

改参数看行为，能帮助理解机制。在隔离的测试环境里，先开启 Redis AOF，把 `appendfsync` 从 `everysec` 改成 `always`，用 `redis-benchmark` 对比吞吐。再把 MySQL 的 `innodb_flush_log_at_trx_commit` 从 1 改成 0，在持续写入时强杀进程，重启后核对已确认事务的保留情况。最后，在关闭幂等的 Kafka 测试生产者上，把 `acks` 从 all 改成 1，使用多副本分区，对比 Leader 故障并由副本接管后的已确认消息，同时记录 ISR 状态和 `min.insync.replicas` 设置。是否观察到丢失，取决于故障发生时的刷盘和复制进度。亲手观察这些变化，你对参数的代价就有了直观感受。

跨领域对照。数据库、消息队列、缓存、搜索引擎共享底层原理，都在解决同一组问题：正本在哪、怎么批量、怎么一致、怎么恢复。读完三本不同领域的书，把它们放到 10.2 的五条规律下一一对照，它们表面不同、底层一致。这种对照能力，是设计者阶段重要的资产。

三个值得留意的倾向。一是先选技术再找场景：先定了技术再去凑适用场景，是很容易不知不觉形成的惯性。二是追求面面俱到：什么都想要、每个参数都拧到最紧，结果系统在每个维度都平庸。三是把一致性当信仰而不看代价：盲目追求"强一致"，却不问业务是否需要，背上了不必要的延迟和复杂度。

回到第 1 章的组织方式：三个软件对同一批问题有三份不同方案，但做决策的步骤是同一套。理解共性之后，剩下的判断是：哪个方案适合自己的约束。

顺着这一判断推下去：架构设计的本质，是在摸清约束之后选出最简洁的方案。简洁意味着组件、参数、每一层抽象，背后都对应一个被明确列出的约束；去掉就会违反约束的组件，才是必须保留的。

## 10.5 小结

导读强调三个软件的差异底下有共同结构，这一章把这些共性整理为五条规律。从 10.1 的九章启示总表出发，主线仍是：约束决定哪些选项可行，目标决定在可行选项里怎么选。确定数据的权威来源、设计分层与访问方式、权衡可靠性的代价、安排状态恢复，都是沿着这条主线作判断。读完这本书，如果你下次做选型时，能先想"这个系统的约束是什么、取舍在哪里"，本书的目的就达到了。这也回应了序言提出的三个层次：知道解法、理解取舍、学会决策。
