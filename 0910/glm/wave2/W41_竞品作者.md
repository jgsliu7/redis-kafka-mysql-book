| 1 | ch8 L50 | > **本书为什么没讲 LSM 树**：日志结构合并树（LSM-tree）是现代存储系统的另一个重要范式，RocksDB、LevelDB、HBase、TiDB 都在用它。它通过"内存写入 + 分层 SST 文件（Sorted String Table，排序字符串表）+ 后台合并（compaction）"实现高写入吞吐。本书这三个软件（Redis/MySQL/Kafka）无一采用 LSM 树作为默认引擎（MySQL 虽有 MyRocks 引擎但非默认），因此 LSM 范式不在本书深度覆盖范围内。读者若需要理解这一范式，Kleppmann《Designing Data-Intensive Applications》第 3 章是很好的起点。 | 一章题为"磁盘存储格式的设计哲学"，快照、页式、追加日志三种范式讲齐，第四种主流范式用一个提示框打发、把读者推向 DDIA。这不是锦上添花的缺失：本书 8.4.2 讲了 Kafka compaction 重写日志段，8.2.3 讲 AOF 重写时亲口说这是"追加日志如何做在线 compaction 的经典手法"，8.6.2 讲"定长 vs 变长是写读路径的根本选择"——LSM 就是这套手法的系统化（追加写 + 分层后台合并，写放大换读放大，恰与 MySQL 双写的读路径保护形成对称），素材全被推到门口，唯独不开这扇门。用 RocksDB/TiDB 的读者翻到这里会觉得"写路径"这条线断在最关键处，只能去找别书补。我认这本书 8.6 那套"三问决策树"比我当年写得利落，但把凑不进三家对比表的题材整体扔给"延伸阅读"，是主题式结构反过来绑架内容——我自己写书时也抵制过同样的诱惑：凡是凑不齐对照的题材都想裁掉。改进方向：不必加整节，在 8.6.2 处用半页把 LSM 定位成"compaction + AOF 重写的一般化"，让提示框从"出门左转 DDIA"变成"本章的工具已经能拆解它"。 | 结构 |

| 6 | ch5 L109 | **优化器（Optimizer）** 是 MySQL 挑选执行策略的组件。它接受查询树，输出一个执行计划。优化手段包括常量折叠、范围优化、直方图辅助索引选择、JOIN 顺序搜索等。8.0 引入的直方图让优化器能对没有索引的列做数据分布感知的判断。这个执行计划是一组结构化的"该按什么顺序、用什么索引、走什么 JOIN 策略"的指令，不是 SQL，也不是机器码。 | 同一节三段切分里，解析器有机制（bison 生成、token、语义检查三步走），执行器有机制（主循环：读一行→评估 WHERE→聚合→再读一行，每次行操作一次虚函数调用），唯独优化器只有四个名词的列举，每个都不解释——读者读完带走零。而优化器恰是这一层最有取舍可讲的部分：基于成本 vs 基于规则、JOIN reorder 为什么是 NP-hard 只能贪心剪枝、统计信息为什么 8.0 才补直方图（维护统计信息的代价），每一个都能挂到全书"取舍"主线上。同一段落里，解析器和执行器写得像看过代码，优化器写得像看过目录。写书人为什么犯我太清楚了：优化器的代价模型讲错会被内行一眼抓包（代价系数、扇出估计），列举名词是零风险写法——但零风险就是零信息，这是"知识边界暴露"的标准形态，同类读者（面试官）一眼能认出来。改进方向：要么补一百字讲清"基于成本"的最小闭环（扫描行数估计→代价加和→JOIN 顺序贪心），要么砍掉列举、诚实一句"优化器内部超出本书范围"，别用名词清单伪装覆盖。 | 可懂性 |

## 总评（同行视角，两句）

这本书的"档位"叙事（appendfsync / innodb_flush_log_at_trx_commit / acks 三档同构）和主题式对比结构，是我当年想出来又没敢用的——它赌赢了大部分：第 3、8、9 章的洞察密度确实压过同类。但主题式结构收的税也很明显：凡凑不齐"三家对照"的题材（LSM、消费者组、隔离级别）成片缺位，这三块恰好都是读者会拿着别书回来补的硬通货。二版优先补这三块，其余都是小修。
