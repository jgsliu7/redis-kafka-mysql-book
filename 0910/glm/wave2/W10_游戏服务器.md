# W10 · 游戏服务器阿磊 · 读者报告

背景：游戏服务器开发 9 年，MMO + 竞技对战。日常：Redis 是每帧都在碰的内存（排行榜/背包/会话），Kafka 走战斗日志和活动消息，MySQL 落档。亚毫秒预算、在线热更是常态、一个服一个有状态单元。以下意见全部从这个视角出发。

| 1 | ch2 L7 | 后来换成 Redis 的有序集合（ZSET），底层的跳表把插入和按序拉取都保持在 O(log N)，ZRANK 一条命令给出名次。 | 本章开篇就是排行榜，但 ZSET 这条线通篇没提 score 的类型：它是 IEEE 754 double，只有 53 位安全整数。游戏排行榜最常见的记分法恰恰是大整数拼接（战力×10^10 + (MAX_TS-时间戳) 之类，用来保证同分先到先得），一旦拼出的数超过 2^53，ZADD 写进去的分数和传入的不一致，名次静默错乱——这是新人做排行榜必踩的坑，而且表现是"偶现、无法复现"。我拿这本书校准团队新人，就是希望这类"结构说了但关键边界没说"的地方补上。改进方向：在 2.2.1 跳表段或导读加一句"score 是 double，53 位安全整数上限，大整数拼分要先验证精度，必要时用 (score, member 字典序) 兜底同分排序"。 | 事实 |
| 2 | ch2 L41 | skiplist 编码的 ZSET 内部是 dict + 跳表两个结构并联：member→score 的查找走 dict，ZSCORE 是 O(1)；按序拉段走跳表，ZRANGE 是 O(log N)。 | 两处问题。其一，ZRANGE 的复杂度是 O(log N + M)（M 为返回元素数），不是 O(log N)——同一段后面自己就写了"范围扫描只需沿底层链表前进（O(log N + M)）"，同段前后矛盾。其二，这个 M 在排行榜场景是主导项：赛季结算拉前 1 万名发奖，M=10000，这个量级才是成本主体；说成 O(log N) 会让新人以为拉多大一段都一样快。我们见过结算脚本一把 ZRANGE 拉全榜（百万 member），单线程 Redis 上卡住所有命令，同服玩家全部超时。改进方向：把"ZRANGE 是 O(log N)"改为"ZRANGE 是 O(log N + M)"，并顺着排行榜的例子点一句"拉榜的 M 是结算脚本要自己分页控制的量"。 | 事实 |
| 3 | ch2 L177 | \| 核心目标 \| 极低延迟（微秒级） \| 通用可靠（ACID + SQL） \| 高吞吐（每秒几十万条） \| | "微秒级"没有前提限定，和后文口径打架：ch4 L67 写"本地或同机房访问通常落在亚毫秒到毫秒级"，ch5 L24 写"把每条命令的端到端时间降到亚毫秒"。三处三个说法。微秒级只在"命令执行本身/同机 pipeline"的口径下成立，真实部署里一跳内网 RTT 就 100–300μs。我们做帧预算时，每帧分给存储的额度是几百微秒，如果新人按表格里"微秒级"做规划，预算会系统性偏乐观，等压测才发现 P99 超帧。改进方向：表格该格统一成"命令执行微秒级，同机房端到端亚毫秒到毫秒（见 4.2）"，或全书统一延迟口径并注明测量条件（执行 vs 端到端、同机 vs 同机房）。 | 一致性 |
| 4 | ch3 L228 | 优雅关闭做三件事：完成已接受的请求、把脏状态落盘、释放占用的资源。在分布式系统里还要加第四件：把职责移交给别人（Kafka 受控关闭）。 | 这个定义只讲了服务端半边。游戏服停服维护的真实链条是：踢人→停写→落盘→重启→数万客户端同时重连风暴+冷缓存，最后这一段恰恰最容易把前面的"优雅"毁掉：就绪日志打印了，但连接风暴把 CPU 打满、AOF 刚加载完缓存全冷，玩家体验到的是"维护完了进不去"。3.3 节 MySQL 后台回滚那段（"进程存活、连接成功，还不等于业务延迟已经回到正常水位"）是全书唯一接近这个问题的讨论，但没有被收进"优雅关闭"的定义。改进方向：在启示二补半句边界说明——服务端兑现保证只是闭环的一半，客户端侧的重试幂等、重连退避、就绪后的预热窗口，属于设计者同样要回答的问题；这比加"第五件事"更轻。 | 结构 |
| 5 | ch3 L242 | 开头说的那次事故就是这样：图省事，觉得"Redis 重启就好了"，没等 AOF 刷完就杀了进程，第二天丢了十几条订单数据。Redis 本来是会落盘的，问题出在我没给它落盘的时间。 | 两个问题。其一，"订单数据"的正本在哪没交代——按上下文这批订单只存在 Redis 里、没有 MySQL 兜底，而这正是第 10 章规律一（L43"一个常见的反例是把缓存和数据库都当正本"）和后记（"库存属于交易数据……MySQL 才是"）要防的反例。按顺序读书的新人会在第 3 章先接受"订单放 Redis"是正常操作，到第 10 章才被推翻，中间没有一句回指。其二，开了 everysec 的 AOF 丢失窗口是 1–2 秒，"十几条订单"要么说明当时写入速率很高、要么当时根本不是 everysec 配置，书里没交代，数字对不上机制。改进方向：事故复盘里补一句"当时订单只存了 Redis、没有正本兜底——这正是第 10 章规律一要防的反例"，顺带交代当时的 appendfsync 档位。教训反而会更完整。 | 一致性 |
| 6 | ch4 L264 | 消费速度低于生产时，消费者读的数据被挤出 PageCache，落到磁盘读，延迟从亚毫秒级掉回磁盘读量级（SSD 百微秒、机械盘十毫秒） | "从亚毫秒级掉回"的口径没说明测的是哪一段。亚毫秒成立的前提是 broker 读路径页缓存命中；端到端消费延迟还叠加生产端攒批（linger.ms）、fetch 往返和批处理节奏，实战里 Kafka 消费延迟的常驻水位就是毫秒级——我们收战斗日志的消费 P99 常年在个位数毫秒，这不代表 PageCache 没命中。冷热落差这个现象本身是真的（我们也在监控里看过 lag 和磁盘读 I/O 齐涨），但从"亚毫秒级"掉落的表述会让新人对消费延迟的正常基准预期偏低，等真出问题反而分不清"这是正常毫秒"还是"掉盘了"。改进方向：加三个字级别的限定——"broker 读路径从亚毫秒级掉回"，或注明"此处指 Broker 端读取，端到端消费延迟另计"。 | 数字 |
| 7 | ch4 L312 | 第一，避免用 Redis 存储全量业务数据。 | 这句一刀切和游戏服务器的经典架构直接冲突。国内大量游戏服的形态就是"Redis 持有全量玩家状态（内存为正本）+ 异步落 MySQL 档"，因为背包/技能/战斗状态的访问在帧内，MySQL 的延迟和锁语义都接不住；这种架构能成立靠的是一串护栏：AOF everysec 或 always、maxmemory-policy 设 noeviction、关掉自动 save（fork 会卡主线程，快照交给从节点做）、控制单实例容量。本书自己的素材其实都齐了（4.2 节讲 fork 阻塞、noeviction、AOF 档位），但没有组装成"如果你必须让 Redis 当正本，该配什么"的分支，只在小结给了一句"避免"。目标读者里"有状态低延迟服务"的架构师拿到这句话没法执行。改进方向：改成条件式——"除非你的访问模式要求内存级正本（如游戏内玩家状态），此时必须 AOF+noeviction+关自动快照+容量上限；否则避免用 Redis 存全量业务数据"。 | 结构 |
| 8 | ch5 L74 | 第三是惰性删除（lazy free），4.0 引入：删除大对象（比如一个百万元素的集合）时不在主线程里同步释放内存，而是把它交给后台 BIO 线程异步释放，避免阻塞主线程。 | 这段缺了最关键的触发条件：DEL 命令默认仍是同步释放，要走 BIO 异步必须显式用 UNLINK，或打开 lazyfree-lazy-expire / lazyfree-lazy-user-del 之类开关（内存淘汰和过期路径另有默认）。照现在这段的写法，新人会以为"删除大对象"天然不阻塞——而合服、删档、清理过期活动榜时拿 DEL 去删百万元素的 ZSET，主线程一卡几分钟、整服超时，是游戏运维里真实发生过很多次的事故形态。这和第 1 章"避免 KEYS *"是同一类知识点，但那处给了命令名，这处没给。改进方向：补一句"注意默认的 DEL 仍是同步释放，删除大对象要用 UNLINK（或开启对应 lazyfree 配置），Redis 只对显式指定的路径走异步"。 | 事实 |

| 10 | 后记 L23 | 上线第一个月一切正常，响应时间在个位数毫秒，业务方很满意。 | 作为"一切正常"的证据，这个数字会给新人校准出错误的基线：同机房 Redis Cluster 单命令正常应在亚毫秒量级（ch4 L67 自己也是这么写的），个位数毫秒已经说明链路里有东西偏慢——跨可用区、代理层、大 value 或客户端连接池问题。"业务方很满意"当然可以是真实叙事，但书里把它当作无事发生的佐证原样呈现，读者会默认"Redis 的正常水平就是几毫秒"。改进方向：加半句作者后见之明，比如"（这个数字对 Redis 来说其实偏慢，当时没人细看）"，既保住叙事真实，又把基线校准回来；这也和第 7 章库存事故"上线第一个月一切正常"的铺垫形成呼应。 | 数字 |
