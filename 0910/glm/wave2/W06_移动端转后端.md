# W06 · 移动端转后端小杨 · 读者报告

读者画像：3 年 Android 开发，转后端半年。写过 HTTP 客户端、知道进程线程和一点 Linux 命令，但没做过 Unix 服务端编程、没运维过 K8s、分布式全是入职后硬啃的。以下是我按顺序通读全书时真实卡住或被带偏的地方，原文均逐字摘自文件。

| 1 | ch3 L42 | 信号处理器里，SIGTERM/SIGINT 触发优雅关闭，SIGPIPE 则忽略；RDB/AOF 子进程的退出不由信号驱动，serverCron 每轮用非阻塞 waitpid(WNOHANG) 轮询回收。 | 这一句话里埋了三个我都不熟的点，其中最伤的是 serverCron：它是 Redis 周期性后台任务的总入口（默认约每 100ms 跑一轮，过期键扫描、超时客户端清理都在里面），但全书到这儿以及后面 2.2.1 节"定时任务每周期还给每个字典最多 1ms 的搬迁预算"都用它，却从没说过它是什么、"每轮"是多久。我读到字典那段时只能停下来搜资料。SIGPIPE 为什么网络程序必须忽略（写已关闭连接会触发默认终止行为）也是服务端常识、客户端盲区。改进：serverCron 首次出现加一个括号说明"Redis 的周期性定时任务，默认约每 100ms 执行一轮"；SIGPIPE 加半句"（往已断开的连接写数据时内核会发它，不忽略会误杀进程）"。 | 可懂性 |
| 2 | ch3 L185（另见 ch4 L34） | fork 拷贝页表（小实例几十毫秒、大实例数百毫秒）的成本发生在这一步而不是关闭流程里，且此时 Pod 已摘流、无新写入，写时复制（COW）几乎为零 | "页表"和"写时复制（COW）"这里首次出场，括号只展开了缩写没展开机制。序言和 1.4.1 列的前置要求是"进程与线程、内存层次、I/O 模型"，没包含虚拟内存/页表；对从客户端转过来的人，fork-页表-COW 是一整条我从来没有的知识链，而它恰恰是理解"Redis 大实例为什么要控制容量""RDB 为什么不阻塞"这几处核心论述的钥匙。我读这句时"无新写入→COW 几乎为零"这个因果推不通（不知道父子进程共享物理页、写时才复制）。ch4 L34 关键数字框又用了"页表大小、透明大页（THP）"。改进：在 ch3 首次出现处补两句——"fork 创建子进程时需复制父进程的页表（进程的虚拟地址→物理地址映射表，大小与内存成正比）；子进程起初与父进程共享物理内存页，哪一页被写才复制哪一页，即写时复制（COW）"。 | 可懂性 |
| 3 | ch2 L158 | `correlation_id`（4 字节，客户端自定义，服务端原样抄到响应里用来匹配请求和响应） | 作为习惯了 HTTP 一问一答的人，我第一反应是"TCP 本来就保证顺序，为什么还需要一个 ID 来匹配"。书只说了 correlation_id 用来匹配，没说为什么需要匹配。真实原因是：Kafka 允许一条连接上同时挂着多个未完成请求，服务端多线程处理、完成顺序和请求顺序可以不一致，响应里必须带 ID 客户端才知道哪个响应对应哪个请求。缺了这半句，客户端思维的读者会把这条略过去甚至形成"TCP 序号不够用才加 ID"的错误联想。改进：补一句"（同一条连接上可以有多个在途请求，处理完成顺序与请求顺序可能不同，需逐个配对）"。 | 可懂性 |
| 4 | ch3 L193（首次出现 L185） | **实践清单：** preStop hook 主动检查条件而非 sleep；grace period 给到刷盘/迁移耗时加 30 秒余量。 | "实践清单"是给读者照着做的，但这条清单的第一要素 preStop hook 全书没有任何解释（它是 Kubernetes 在终止容器前先执行的钩子命令）。L185 首次出现时同段的"摘流"（把 Pod 从负载均衡端点摘除，不再接新请求）也没解释。容器化这一节对"没碰过 K8s 的转后端读者"几乎每一行都带一个新黑话（grace period 前文讲过、startup/liveness/readiness 探针讲过，这两个反而讲得好），偏偏最 actionable 的清单卡在入口词上。改进：L185 首次出现 preStop 时加括号"（K8s 在杀容器前先执行的钩子，常用来做收尾动作）"，"摘流"加"（从 Service 端点列表移除，不再接新流量）"。 | 可懂性 |
| 5 | ch9 L45 | 后来我们加了一个写后读一致的路由层，但前提是必须先知道这道窗口的存在。 | "写后读一致"是分布式一致性的经典术语（同一用户写完后，自己的后续读必须能看到这次写），这里裸用没解释。我是靠上下文（"主节点写入新订单，从节点还没同步到，用户的查询恰好落在了从节点上"）反推出来的意思，但反推和确切定义是两回事——这类词面试和文档里高频出现，第一次遇到就拿到准确定义价值很大。改进：首次出现加括号"（read-your-writes：用户发起的写被确认后，同一用户随后的读必须能看到这次写，常通过把该用户的读路由到主节点实现）"。 | 术语 |
| 6 | ch1 L80（与 ch9 L260 冲突） | 为保证一致性，写操作伴随 redo log 与 binlog 的内部两阶段提交开销（两份日志分属存储层和服务层，提交时按 prepare、commit 两步对齐，保证崩溃后两边一致） | 全书"两阶段提交"在两处指两种不同的机制：这里是 MySQL 单实例内 redo log 与 binlog 的对齐，ch9 L260"靠 transaction coordinator 和两阶段提交（对消费者暴露 `committed` 标记）实现"是 Kafka 生产者跨分区分布式事务的经典 2PC（prepare/commit 由协调者跨节点驱动）。我读到第 9 章时以为"又是那个两阶段提交"，把它们当同一件事理解了半天，直到查资料才发现一个是实例内两份日志对齐、一个是跨节点原子提交，参与者、协调者、目的全不同。作为初学者我恰恰是最容易被同名不同物带歪的人群。改进：ch9 L260 处加半句"（注意与第 1 章 redo log 与 binlog 的内部两阶段提交不是一回事，这里协调的是跨分区的多个写入方）"。 | 一致性 |

## 总体感受（供编辑部参考，不算正式意见）

这本书对我这种读者意外地友好：PSYNC 命令"不是能在 redis-cli 里直接敲的命令"、ACL 密码前缀">"不是 shell 重定向、共识算法一分钟直觉框，这些地方都精确补到了我的盲区。上面的意见集中在两类系统性缺口：一是 Unix 服务端编程常识（fork/页表/COW/SIGPIPE/serverCron）——序言声明"不讲基础知识"没问题，但页表这类词连展开都没展开过，与 fsync、filesort 这类"用时就地括注"的体例不一致；二是同章内"先用后定义"或跨章概念提前裸用（LEO、任期、GEO），建议统一过一遍首现点。
