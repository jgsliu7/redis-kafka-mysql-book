# W29 · 内核工程师聂工 · 读者报告

审阅人：聂工（Linux 内核方向，块层与文件系统）。重点核对了 ch3/ch4/ch8 的内核机制段（page cache、fsync/writeback、dirty ratio、fork/COW、扇区原子性、顺序写语义），其余章节通读。总体说一句公道话：这本书的内核相关段落水准在我读过的国产架构书里不算差——零拷贝的 scatter-gather 细节、everysec 的 2 秒窗口、dirty ratio 的分母口径、MySQL 档位 2 的 write/fsync 区分，这些都写对了。但下面几处是实现级读者一眼能看出的偏差。

| 1 | ch3 L242 | 开头说的那次事故就是这样：图省事，觉得"Redis 重启就好了"，没等 AOF 刷完就杀了进程，第二天丢了十几条订单数据。Redis 本来是会落盘的，问题出在我没给它落盘的时间。 | "杀了进程"和"丢 AOF 数据"之间的因果在内核语义上不成立。kill -9 杀掉的是进程，而 AOF 的 write()（把 aof_buf 写入 fd）是主线程每次事件循环同步做的，everysec 模式下只是 fsync 交给后台每秒一次——已 write 的数据落在 page cache，属于 OS 不属于进程，进程死后 writeback 线程照常把它刷回磁盘。所以纯 kill -9（OS 存活）下 everysec 的丢失窗口只有"还没来得及 write 的 aof_buf"，是毫秒级，装不下"十几条订单"。"丢最近 1 秒"对应的是整机断电/OS 崩溃这个不同的故障域。ch3 L7"同样是 kill -9，对 Redis 通常只是丢掉最近一小段时间的数据"是同一个毛病。这次事故若真实发生，能解释丢失的要么是整机/虚机重启（page cache 整体没了），要么当时其实是 RDB-only、AOF 并没开。作者第一人称案例我不动，但建议：导读和 3.2 节把"进程被杀"与"OS/整机崩溃"两个故障域分开表述，案例的归因措辞留一点余地（比如"没等 AOF 落盘就重启了机器"）。这个区分对读者是实打实的运维知识：AOF everysec 下，杀进程比断电安全得多。 | 事实 |
| 2 | ch8 L151 | 512 字节匹配传统磁盘扇区的原子写粒度：一次 512 字节的写要么完整要么不发生，不会留下半个扇区的撕裂。 | 断言过强。断电时磁盘并不保证扇区级原子性——半扇区写入（torn write）乃至 shadow write（旧数据也被写坏一半）在 SATA/SCSI 设备上是已知现象，这正是 PostgreSQL 要做 full_page_writes 的原因：PG 社区明确不信任"扇区原子写"。InnoDB redo 按 512B 块对齐 + 每 redo block 自带 checksum，真正的机制是"对齐扇区提高大概率 + 校验和兜底检出"：恢复时逐块验校验，尾部不完整的块直接丢弃，所以即使撕裂也能识别日志边界。把"要么完整要么不发生"写成硬件保证，是把设计动机当成了硬件承诺。改进方向：改为"512 字节对齐扇区，让断电时 redo 大概率不撕裂；即便撕裂，逐块校验和也能把不完整的尾部块检出并丢弃"——这才是双保险的真实结构，也和本书 8.6.4"每层可靠性机制要知道防的是哪类故障"的立场更自洽。 | 事实 |
| 3 | ch4 L196 | 由于文件只追加、不修改、按段清理，磁盘始终在做顺序写，随机 I/O 在写路径上基本不存在。 | 混淆了逻辑顺序与物理顺序。Kafka 单分区内"只追加"确实是逻辑顺序写，但一个 Broker 上几百个分区各自在追加自己的活跃段，ext4/xfs 延迟分配下多个文件的 extent 互相交错分配，机械盘上磁头要在几十个段文件末尾之间来回寻道——块层看到的写请求就是分散的，"随机 I/O 基本不存在"从块层视角不成立。SSD/NVMe 上寻道代价消失、影响缩小，但写放大与 GC 的友好度也依赖 extent 的连续程度。这不是苛求：书把"顺序写"论证为 Kafka 吞吐的物理根基（ch1 L92、ch4 启示四同此论述），根基处就应把限定条件说准。改进方向：加半句"单分区内逻辑顺序；多分区并发追加时块分配会交错，靠大日志段与 SSD 把开销摊薄"——这也顺便解释了为什么实践上建议控制单盘分区数，比"基本不存在"更有解释力。 | 事实 |
| 4 | ch4 L164 | 图 4-5 的时序：事务提交时先把 redo log 写到日志文件并落盘（保证持久性）。脏页随后进入 Flush List。后台线程把脏页先写到双写缓冲再写到表空间。 | 时序说反了。InnoDB 里脏页不是在事务提交后才进入 Flush List：页被修改时（事务执行中，mtr 提交那一刻）就把页挂入 Flush List 并记下 oldest_modification LSN，此后多次修改只更新 latest_modification。事务提交动作本身只负责 redo 的 write+fsync，与 Flush List 无关——一个大事务执行期间它的脏页就一直在 Flush List 里排队等刷。这个错误还和 4.3 节自己的正文冲突：L140 写"被改过但还没刷盘的页按最早修改时间排队"，"最早修改时间"恰恰说明入队发生在首次修改时而非提交时。顺序搞反会误导读者推断 checkpoint 语义（flush list 的 LSN 水位早于提交 LSN，这正是 fuzzy checkpoint 能推进的基础）。改进方向：图注改为"修改页时即进入 Flush List（记最早修改 LSN）；事务提交时只做 redo 的 write+fsync；后台线程随后刷脏页（先双写再正式位置）并推进 checkpoint"。 | 事实 |
| 5 | ch4 L38 | 前者达到时内核 flush 线程异步后台刷盘、写进程不阻塞；后者达到时写进程被同步阻塞强制刷盘。 | dirty_ratio 那半句的主语错位。达到 vm.dirty_ratio 后，写进程是在 balance_dirty_pages() 里被节流（TASK_KILLABLE 睡眠等待），等的是各 backing device 自己的 writeback 线程把脏页比例拉回限值以下，被节流的写进程自己并不去执行刷盘——"被同步阻塞"对，"强制刷盘"会让人读成"写进程开始自己刷脏页"。改进方向：改为"写进程被同步节流等待，直到后台回写把脏页比例降回限值以下"。另外这一框末句"写满前内核批量刷盘"插在解释分母的两句之间，没头没尾，建议并进前半句："达到 10% 即开始后台批量刷盘，正常情况下到不了 20% 的阻塞线"——这样两个阈值的关系也顺带讲清了。 | 事实 |
| 6 | ch10 L145 | \| 可靠性 \| 可接受最大丢失量（RPO）？ \| 默认约 1–2 秒量级窗口（开启 AOF 后） \| 双 1 接近 0 \| acks=all 接近 0 \| 写一个 RPO 数字，并说清谁能拍板 \| | 表里两个"接近 0"不是同一层的承诺，并排陈列抹掉了层次。MySQL 双 1 的接近 0 是本地逐事务 fsync，单机断电也不丢；Kafka acks=all 的确认条件是"ISR 内所有副本写入本地日志"，而副本写入默认只到 page cache、并不 fsync（ch4 L216 明说默认不强制 fsync，L312 明说兜底是副本机制而非本地 fsync）——它防的是单机失效，防不了多副本同时断电，"接近 0"建立在"ISR 多副本不同时失效"的假设上。本书 ch4 自己把这点讲对了，到总结章的表里简化成同一档"接近 0"，前后出现层次滑移。改进方向：表格 Kafka 列写"接近 0（依赖副本不同时失效，副本确认不要求 fsync）"，或在表注里点明与双 1 的差别。这条差别在金融场景选型时是真金白银的：双 1 的 RPO 不依赖概率假设，acks=all 依赖。 | 一致性 |

## 总评（一句话）

内核机制段总体准确度高于预期，零拷贝、everysec 两秒窗口、dirty ratio 分母、write/fsync 故障域区分（MySQL 档位 2 与档位 0 的差别）这些细节都站得住；主要残留问题是第 1 条的"杀进程丢 AOF"因果错位和第 4 条的 Flush List 时序，都是实现级读者会当场停下来的那种；第 2、3 条是把"设计动机/逻辑视角"写成"硬件保证/物理事实"，与本书"知道每层机制防的是什么故障"的自我要求相比差了一口气。
