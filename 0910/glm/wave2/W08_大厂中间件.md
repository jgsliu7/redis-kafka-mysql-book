| 1 | ch7 L44 | **Kafka 单分区吞吐：约 10–50MB/s**（视硬件与消息大小；1KB 消息约 1–5 万条/秒，小于 100 字节消息可达 10 万条/秒以上）。 | 这个量级是机械盘时代的口径，现代 NVMe + 大页缓存下单分区顺序写普遍过 100MB/s，数字本身偏旧。更要命的是它与 7.4.1（L160）"经验值取 7.1 关键数字框的单分区吞吐（保守规划按下限），用你的峰值吞吐对照反推分区数"合起来用：按 10MB/s 下限反推会把新人直接推向分区超配。而我们平台接手的万分区集群，病根几乎全是分区过多而非过少——controller 元数据膨胀、broker 滚动重启数小时、低流量分区堆小文件、每分区固定吃文件句柄和内存结构。分区加容易减难（减分区即丢数据），超配是单向门。建议：数字框补一句现代硬件量级（百 MB/s 级）；7.4.1 规划建议明确"分区是单向决策，超配代价通常大于吞吐不足"，引导按实测吞吐的 50%–70% 规划而非按下限反推。 | 数字 |

| 5 | ch7 L84 | MOVED 表示"这个槽已经永久不在你这了，去这个新地址"，客户端收到后更新本地映射表，以后都走新地址；ASK 表示"这个槽正在迁移中，本次请求请去临时地址试一下"，是一次性重定向，客户端不更新映射表，因为迁移完之后这个槽还会回来或换地方。 | 这段把 MOVED/ASK 的路由语义讲得很清楚，但槽迁移只讲了"搬家时请求怎么走"，没讲搬家本身的执行代价：迁移按 key 走 MIGRATE，是同步阻塞命令，源节点要序列化并传输整个 key。带大 key 的槽（百万元素的集合、几十 MB 的 string）迁移时源节点卡秒级到分钟级，期间该节点上所有租户一起抖。我们平台每次 reshard 前都要先做大 key 扫描和拆分，这是热迁移的标准前置动作；而本书 10.4.1 表格写"Cluster 在线 reshard"，给新人的印象是扩容就是平滑把槽挪过去。建议：在 ASK 语义后补一小段——迁移按 key 同步执行、大 key 是迁移第一大事故源，大规模 reshard 前先做 MEMORY USAGE 扫描；10.4.1 该行加注"大 key 需先拆分"。 | 事实 |

| 8 | ch7 L216 | MySQL 加副本只扩可用性和读吞吐，扩容量要靠上层分片中间件。Kafka 加分区和 Broker 同时扩数据吞吐和总容量。 | 结论没错，但会被新人读成"加了 broker 存量就自动均衡了"。实际上新 broker 只承接新建分区的默认分配，存量分区必须手动触发 reassignment（或靠 Cruise Control 类工具），而大规模 reassign 是 Kafka 平台最重的运维操作之一：副本重建占满磁盘 IO 和网络带宽，必须配限速、分批、错峰。这层"扩容的第二半工程"全书没提，而"在线扩容"四个字恰恰是最容易被业务方拿去当承诺用的。建议在该句后补一句："注意加 broker 只自动承接新分区，存量分区需手动再分配；大规模再分配要配带宽限速分批执行，否则会打满集群 IO。" | 事实 |

## 总体判断

书里"机制为什么这么设计"的主线是扎实的，我认可它当培训教材的底子。但按平台视角通读下来，它的隐含读者是"自己搭一套、自己运维"的中小规模使用者：数字口径（单分区吞吐、缓冲池、每 broker 分区数）停在几年前的量级，多租户/配额/热迁移/滚动升级窗口这些"规模上去之后才存在"的维度基本空白。全书最典型的模式是：机制语义讲得对，失效边界不标——槽迁移不讲 MIGRATE 阻塞、ZSET 不讲单 key 上限、加 broker 不讲手动 reassign。当教材用，建议每个"方案"补一句"到什么规模它开始不成立"，这一句话比多讲一个机制对新人更值钱。

另：书也有做得比同类书好的地方——万分区启动瓶颈（3.4）、fork 阻塞与大实例控容（4.2）、Gossip 收敛上限（7.1）都主动标了边界，这些正是培训时最需要的段落，只是量还不够。
