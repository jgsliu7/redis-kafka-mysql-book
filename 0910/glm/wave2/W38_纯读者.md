# W38 · 纯读者小乔 · 读者报告

审阅视角：机场/高铁上读纸书的工程师，无电脑、无环境，所有"动手试试"环节只能用眼睛和脑子过。检验标准只有一条——命令给了输出吗、实验给了预期现象吗、参数给了"这个值意味着什么"吗。没给输出的命令和没给预期结果的实验，对纯读者等于天书或死路。

| # | 位置 | 原文 | 意见 | 类型 |
|---|------|------|------|------|
| 1 | ch2 L100 | **RecordBatch 就是 Kafka 的基本存储单元。** 生产者会把消息积累成一批（攒够 `batch.size` 字节，或等到 `linger.ms` 毫秒）再打成一个 Batch 发到 Broker，而不是一条一条往外发。 | 攒批是 Kafka"用延迟换吞吐"的核心机制，但这两个参数只给了"攒够 X 或等到 Y"的机制语义，没给默认值和量级。纯读者由此建立不起时间尺度：攒批发生在微秒、毫秒还是百毫秒级？这直接影响对全书反复出现的"Kafka 延迟偏高"到底高在哪的理解。全书其他参数几乎都带默认值（`maxmemory-samples` 默认 5、`innodb_old_blocks_time` 默认 1000 毫秒、`replica.lag.time.max.ms` 默认 30 秒），此处缺席显得突兀。改进：括注默认值（batch.size 默认 16KB、linger.ms 默认 0 即默认不主动等待），再补一句方向说明，如"想拿一点延迟换吞吐，就把 linger.ms 调到几毫秒到几十毫秒"。 | 可懂性 |
| 2 | ch2 L132 | Redis 的协议叫 RESP（REdis Serialization Protocol）。它的设计目标非常明确：实现简单（服务端解析不费 CPU）、人眼可读（协议就是文本，用 `nc` 连上 6379 端口直接打字就能交互）、能表达所有 Redis 命令和返回值。 | "用 nc 连上直接打字就能交互"对纯读者是个断头路：打什么字？会看到什么？下一节 L134 给了 RESP 类型前缀样例和一条 SET 的完整请求编码，但全书从未把它们拼成一次最小会话——"敲 SET foo bar 回车，服务器回 +OK"或"发 `*3\r\n$3\r\nSET...`，收到 `+OK\r\n`"。协议字节样例与"nc 直接交互"的断言之间缺一步连接，无环境的读者没法在脑中完成这次握手，也无法体会"打的是普通命令行还是那串星号编码"（RESP 的 inline 命令对纯读者是完全不可见的存在）。改进：补一个两三行的最小会话示例（输入一行、响应一行），把 L134 的编码样例与 nc 交互接起来——这本来就是"人眼可读"论点最直接的证据，现在论点有了，证据链断着。 | 命令 |
| 3 | ch3 L132 | `SHOW PROCESSLIST` 在关闭期的输出，对着这四类根因看，就能定位卡点。 | 上一小节列了四类根因（大量脏页待刷、长事务、从库等复制线程、FTS 索引优化），这句承诺"对着输出看就能定位卡点"，但既没给关闭期 PROCESSLIST 的输出长什么样（有哪些列、什么状态值），也没说四类根因各自对应输出里的什么特征。纯读者合上书完全无法复述这个排障动作，甚至会产生"脏页在 PROCESSLIST 里能看到"的错觉。改进：给一段三四行的示例输出（可缩略），用一句话点出"State 列长时间停在 X 对应根因 Y"；或退一步说明四类根因里哪些能在 PROCESSLIST 看到、哪些要看别的视图。 | 命令 |
| 4 | ch4 L79 | 关键参数 `lfu-log-factor` 控制增长快慢，`lfu-decay-time`（分钟）控制衰减速率。 | `lfu-decay-time` 给了单位，`lfu-log-factor` 只剩一句"控制增长快慢"：值调大，计数器是涨得更快还是更慢？纯读者读完整节 LFU，对这个旋钮仍然没有方向感——不知道往哪拧、拧了会看到什么现象，前文精心铺垫的"8 位概率计数器、按对数增长"的机制落不了地。改进：补默认值并点明方向（如"默认 10，值越大同样访问次数下计数值越小、越难被判为热数据"），一句话即可与本段计数器机制扣上。 | 可懂性 |
| 5 | ch6 L43 | `ACL SETUSER alice on >pwd ~keys:* +get +set`<br>（L48）这条语句创建用户 alice，启用状态、设置密码、允许访问匹配 `keys:*` 的键、授予 `GET` 和 `SET`。 | 命令各项含义拆得细，但没给执行结果（ACL SETUSER 成功返回 `OK`），也没给后续验证动作的命令：怎么用 alice 登录（`AUTH alice pwd`）、被拒时客户端看到什么。预期现象其实写在 50 行之后图 6-3 的描述里（"alice 执行 GET keys:1 通过，但执行 FLUSHALL 会被拒绝"），但与命令块之间没有形成闭环，纯读者能懂"这条规则做了什么"，却串不起"创建用户→切换身份→验证被拒"的完整链路，脑子里跑不完这个实验。改进：命令块后补返回 `OK`，再跟两行验证：`AUTH alice pwd` 切过去，`GET keys:1` 正常返回，`FLUSHALL` 收到一条 NOPERM 权限错误——让这条命令当场闭环。 | 命令 |
| 6 | ch7 L65 | 每个 Sentinel 周期性地给主从节点发心跳，超过 `down-after-milliseconds` 没回应，这个 Sentinel 把主节点标记为**主观下线**（SDOWN，subjectively down）：这只是单个 Sentinel 基于本节点视角的判定。 | `down-after-milliseconds` 只给了名字，没给默认值或量级。它是决定"主真挂之后 Sentinel 多快发现"的关键参数，纯读者读完仍回答不了"从宕机到主观下线大概要多久"——而这正是 7.2.2 节故障转移时间线的第一环。同章对 `cluster-node-timeout` 明确写了"（默认 15 秒）"，第 3 章对 `shutdown-timeout` 写了"（默认 10 秒）"，唯独这个超时参数裸着。改进：括注默认值（官方 sentinel 样例配置为 30000 毫秒）并补一句量级含义，"调小发现更快但更容易误判"，与同章其他超时参数对齐。 | 可懂性 |
| 7 | ch10 L171 | 改参数看行为，是最快的理解方式。把 Redis 的 `appendfsync` 从 `everysec` 改成 `always`，用 `redis-benchmark` 看吞吐怎么跌。把 MySQL 的 `innodb_flush_log_at_trx_commit` 从 1 改成 0，强杀进程看丢多少。最后把 Kafka 的 `acks` 从 all 改成 1，断一个 Broker 看消息丢不丢。亲手制造一次"丢数据"，你对参数的代价就有了直观感受。 | 这是全书唯一成体系的"动手实验"环节，后记（L39"第 10 章 10.4.3 给了三个现成的实验，挑一个今晚就动手"）还二次引用，但它恰恰是预期现象缺失最重的地方："看吞吐怎么跌"跌到多少算正常？"强杀进程看丢多少"丢的是哪些、怎么判定丢了？"断一个 Broker"断 Leader 还是 Follower、已收到成功响应的消息算不算丢？三个实验全是开放式观察，一个预期结果都没有。无环境的纯读者连"想象实验"都做不了：读完仍答不上 always 比 everysec 慢多少、0 档强杀后消失的是最近一秒的已提交事务还是别的什么。改进：每个实验补一行预期现象（如"always 档吞吐通常掉一个数量级上下""0 档强杀重启后，崩溃前最后一秒内提交的事务消失""acks=1 时 Leader 宕机，生产者已收到成功响应的部分消息消费者再也读不到"），让做不了的读者也能在脑中跑一遍并校验理解。 | 命令 |

补充说明（非计条）：第 3 章三家的就绪日志（`Ready to accept connections` / `ready for connections` / `[KafkaServer id=0] started`）、第 4 章"告警间隔等于 save 周期即可定位 fork"、第 9 章 backlog 覆盖时长与追赶耗时公式 `B/(C-W)` 附算例，这些是全书对纯读者做得最好的样板——给了值、给了"看到 X 说明 Y"，本报告未列正条，供修改时参照对齐。
