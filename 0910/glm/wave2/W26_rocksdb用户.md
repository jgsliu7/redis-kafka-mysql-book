# W26 · RocksDB用户韩工 · 读者报告

阅读人设定：LSM-Tree 阵营工程师，用 RocksDB 做过存储引擎与 TiKV 类系统。立场：B+ 树 vs LSM 之争尊重事实，既不许本书贬低 LSM，也不希望它无脑吹。敏感点：写/读/空间三大放大的三角、compaction 的真实代价、页缓存在 LSM 场景的行为差异。

先说总体印象：这本书对 B+ 树本身的讲解（页内七段、双写、redo）是扎实的，对"追加日志"范式（Kafka）的论述也基本准确，没有神化 append-only。问题出在范式地图上：全书把存储世界画成"快照 / 页式 / 追加日志"三分，而 LSM 这个恰好横跨后两者、并支撑着 RocksDB/TiKV/Cassandra 一大类生产系统的范式，只在 8.1.3 一个免责框里出现了一句话，正文的推论、决策树、小结定性都没有兑现这个框的承认。下面逐条列出。

| # | 位置 | 原文 | 意见 | 类型 |
|---|------|------|------|------|
| 1 | ch8 L291 | 选择定长还是变长，取决于一个问题的答案：我会不会原地改这块数据？会原地改，就定长：MySQL 的行会被 UPDATE，所以页必须定长可原地改；不会原地改，就变长：Kafka 的消息从不改写，所以可以放心用变长 Batch 把空间用到最小。 | "行会被 UPDATE，所以页必须定长可原地改"这个"所以……必须"不成立。业务上数据会被更新，推不出物理层必须原地改：RocksDB 更新一个 key 是往 memtable 追加新版本、SST 文件不可变、compaction 时归并丢弃旧值，物理上从不原地改；LMDB 的 COW B+ 树同样不原地改。InnoDB 选原地改是一个设计选择（点查路径最短、无需版本归并），不是从"行会被 UPDATE"推出的必然，代价是页内整理、页分裂与脏页随机刷盘（这些书里都写了，恰恰说明它是选择而非必然）。"必须"二字把 InnoDB 的路线写成了物理定律，也直接支撑了 8.6.6 决策树的根节点，读者会据此把页式当成"数据会变的系统"的唯一解。改进方向：改为"InnoDB 的选择是原地改——读路径最短、不用版本归并；另一条路线是追加新版本加后台归并（LSM），用写路径顺序化换读路径多层查找"。 | 事实 |
| 2 | ch8 L323 | 第二问，访问是随机定位要快，还是批量流式进出？随机定位要快，走定长页加索引（B+ 树加页内稀疏槽）。批量流式进出且写远多于点查，走追加日志结构（像 Kafka，纯追加 + 稀疏索引）。既不原地改也不批量流式、只需要崩溃后整体重建，走快照结构（像 Redis 的 RDB 加 AOF）。 | 这棵决策树（连同图 8-8）只有三个出口，漏掉的恰好是"随机定位要快 + 写吞吐也要高"这个组合——LSM 的家。时序、监控指标、大容量 KV、消息系统的索引层，大量走的就是这条路（RocksDB 系）。按第二问的走向，"随机定位要快"被直接送进定长页框，读者会以为这个组合只有 B+ 树一个出口，或者根本没出口；而"批量流式 + 写远多于点查"被送进纯追加日志框，读者也不会知道 LSM 在"追加写 + 可随机读"之间搭的桥。这不是要求本书深讲 LSM，而是决策树作为"可直接带走的选型工具"（本书自己的定位）不能少一条主路径。改进方向：在"随机定位要快"分支下补一层判别（写多读少时还有第四条路：追加 + 分层归并 + 随机读），或在图 8-8 该节点加注指引到 8.1.3 的说明框。 | 结构 |
| 3 | ch8 L50 | **本书为什么没讲 LSM 树**：日志结构合并树（LSM-tree）是现代存储系统的另一个重要范式，RocksDB、LevelDB、HBase、TiDB 都在用它。它通过"内存写入 + 分层 SST 文件（Sorted String Table，排序字符串表）+ 后台合并（compaction）"实现高写入吞吐。本书这三个软件（Redis/MySQL/Kafka）无一采用 LSM 树作为默认引擎（MySQL 虽有 MyRocks 引擎但非默认），因此 LSM 范式不在本书深度覆盖范围内。读者若需要理解这一范式，Kleppmann《Designing Data-Intensive Applications》第 3 章是很好的起点。 | 不讲的理由（样本软件没用）我接受，但这个框有三个问题。其一，它是免责框不是地图的一部分：正文的三范式框架和 8.6.6 决策树完全不接它的话，框承认"另一个重要范式"，正文却持续输出"随机定位要快→定长页"的必然性论断（见第 1、2 条），框变成了免罪牌。其二，框内对 LSM 的介绍只有收益没有代价——"实现高写入吞吐"六个字像免费午餐，没有提 LSM 的核心权衡正是本书最该讲的那笔账：用读放大与空间放大换写放大，compaction 后台 I/O 对前台延迟的扰动、对磁盘带宽的挤占。后记里作者自己的方法论是"关注各自放弃了什么，比关注它们各自做到了什么更有信息量"，介绍 LSM 却只讲做到了什么，不符合本书自己的写法。其三（小），TiDB 的 SQL 层本身不用 LSM，用 RocksDB 的是其存储层 TiKV，严格表述应为"TiDB 的存储层 TiKV"。改进方向：框内补一句定位（"LSM 是顺序写的吞吐与随机读的索引结构的结合，代价是读放大与 compaction 的持续 I/O"），并让正文决策树与这个框互相指认。 | 结构 |
| 4 | ch1 L48 | **MySQL**：用"B+ 树 + WAL + MVCC"换强一致与通用查询，代价是写放大（同一份数据被物理写入多次）、事务开销和调优门槛。 | 这句本身对 MySQL 不算错（redo log、binlog、脏页、双写确实是多份物理写），问题在全书语境造成的不对称：写放大这个概念在书里只挂在 B+ 树/MySQL 头上，而它恰恰是 LSM 讨论的中心词——LSM 用 compaction 归并旧版本，同样"同一份数据被物理写入多次"（典型 workload 下 10–30 倍，取决于 compaction 策略），Kafka 的 compaction/重写日志段也是一类放大。由于 LSM 全书缺席，读者形成的概念地图是"B+ 树有写放大、别的范式没有"，拿这个地图去评估 RocksDB/TiKV/Cassandra 时会犯方向性错误。另外 ch4 L53 还有一处"写放大"（"SSD 没有机械结构，但顺序写仍然比随机写对闪存更友好，因为它能减少写放大与擦除开销"），那是 SSD FTL 层的内部放大，与这里的应用层写放大是两个概念，全书未区分。改进方向：在此处或 ch8 L50 框内补半句对照（InnoDB 的放大来自多份日志与脏页；LSM 的放大来自 compaction 重写），并区分应用层与 FTL 层两层写放大。 | 事实 |
| 5 | ch4 L45 | Kafka 采用顺序写，InnoDB 用 WAL 把随机写改造成顺序写，这套设计诞生于机械盘时代，到 SSD 上收益变成了高吞吐与低写放大。 | "InnoDB 用 WAL 把随机写改造成顺序写"过强，且与本书自己的表述冲突：WAL 改造的只是事务提交路径，脏页 16KB 随机刷盘仍是随机写——ch3 L127 写得很清楚（"大量脏页待刷。缓冲池大、写入密集，刷盘是随机 I/O，吞吐有上限"），ch4 L156 也承认"脏页可以慢慢往后刷"。准确说法是"WAL 把提交延迟与随机写解耦"或"把提交路径变成顺序写"。顺带说，这句把 InnoDB 与 Kafka 并列讲"到 SSD 上收益"，漏了 SSD 时代这条收益最大的受益者恰恰是 LSM——把随机写彻底逐出写路径正是 RocksDB 兴起的背景，这又是 LSM 缺席造成的一半真相。改进方向：改为"InnoDB 用 WAL 把提交路径改造成顺序写（脏页仍是随机刷，只是被推迟"），SSD 一句可补"顺序化写路径的思路推到底就是 LSM"。 | 一致性 |
| 6 | ch4 L282 | 能交给操作系统的缓存，通常不必在用户态再造一份，除非你需要它给不了的精度。 | 这条启示以 Kafka 的论据立普适规律，但 Kafka 的访问模式（纯顺序、读紧贴写尾、预读全命中）是 PageCache 的理想情况；启示的"除非"口子开得太含糊，读者不知道什么算"给不了的精度"、谁需要它。LSM 场景正是活反例：后台 compaction 持续产生大流量顺序读写，会把业务热块从 PageCache 挤出去（缓存污染），且 compaction 与前台读写共享磁盘带宽、需要显式限速与 I/O 配额，所以 RocksDB 自建 block cache 并普遍配 Direct I/O——"能交给 OS"在这个场景恰恰不成立。这不是要求书讲 RocksDB，而是启示作为"可迁移规律"应写清适用边界，否则读者拿去套读写混合加后台整理任务的系统会踩坑。改进方向：补一句边界："访问模式纯顺序且读紧贴写尾时交给 OS 最优；读写混合且存在后台整理任务时，OS 缓存的淘汰与 I/O 调度精度不够，通常要自建缓存与限速。" | 可懂性 |
| 7 | ch8 L336 | 存储格式的选择会长期绑住一个系统：页式再调优也追不上追加日志的写吞吐，追加日志再优化也做不了原地事务。 | 前半句基本成立；后半句把"追加式结构"与"事务能力"绑死了。字面上"追加日志"指 Kafka 的纯消息日志，但放在"存储格式的选择会长期绑住一个系统"这句全书定性里，读者会外推到一切追加式结构——而 RocksDB 在不可变 SST 上提供事务（悲观事务/WritePrepared），TiKV 在其上实现 Percolator 模型分布式事务，MyRocks 之上跑的就是完整的 MySQL 事务语义。追加式结构做不了的只是"原地改"这个物理动作，事务语义不需要原地，靠版本链与墓碑在追加之上就能另建。这句是我这种读者最在意的那种表态——两大结构之争里最容易说错的那半句。改进方向：改为"追加日志再优化也做不了原地改；更新与事务要靠版本与墓碑在追加之上另建一层（LSM 的做法）"，或收窄主语为"Kafka 这种纯消息日志"。 | 事实 |
| 8 | ch5 L121 | 此外还有 Archive（压缩归档）、NDB（Cluster）、第三方引擎如 RocksDB（Percona 的 MyRocks）等数十种，可以在同一个 MySQL 实例里并存。 | 归属与派生关系说拧了：挂进 MySQL Handler API 的引擎叫 MyRocks，它是基于 Facebook 开发的 RocksDB 库的封装，由 Facebook 发起（2016 年起），Percona Server 与 MariaDB（10.2+ 内置）先后集成。括号写法"RocksDB（Percona 的 MyRocks）"读作"RocksDB 即 Percona 的 MyRocks"，既把引擎与库画了等号，又把主要开发方记到了 Percona 头上。小问题，但正好在我专业范围内，且这是全书两处 RocksDB 之一（另一处 ch8 L50"MySQL 虽有 MyRocks 引擎但非默认"是对的）。改进方向：改为"第三方引擎如 MyRocks（基于 Facebook 的 RocksDB，Percona Server 与 MariaDB 均提供）等数十种"。 | 事实 |

## 补充说明（非计分项）

- 全书对 Kafka"追加日志"的论述没有神化：4.4 节讲了消费者追不上时读落到磁盘的隐性代价，8.4 节讲了 compaction 是重写而非原地改，9 章讲了更新删除要靠 tombstone。这些在我这个阵营看来是公允的。
- ch4 L274"要随机读写又得扛大容量，缓存磁盘范式（MySQL）更合适"与第 2 条同源（随机读写+大容量被默认引向 B+ 树），未单列，建议与决策树一并处理。
- ch4 L53 对 SSD 上顺序写减少 FTL 写放大的表述是准确的；第 4 条中提到的两层"写放大"未区分，是编校层面可顺手修的点。
