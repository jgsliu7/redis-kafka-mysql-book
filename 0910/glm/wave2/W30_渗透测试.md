| 1 | ch6 L36 | 6.0 之前的 Redis 只有一个 `requirepass` 全局密码，所有客户端共享，无法区分身份。这是"安全让位给极简内核"的取舍：内核不知道调用者是谁，只校验一个共享口令。这种模型在内网可信环境里够用，但一旦 Redis 被错误地暴露到公网，攻击者拿到密码就等于拿到最高权限，历史上未授权 Redis 写 SSH 公钥、写定时任务导致远程代码执行（RCE）的案例非常多见。 | 这句把 Redis 未授权的经典杀伤链一笔带过：读者只知道"有 RCE 案例"，不知道一个"缓存"为什么能变成 RCE。机制层缺位导致两个后果：一是读者无法自评风险（"我跑在容器里、不挂 SSH 是不是就安全"这类问题无从回答）；二是导读案例（L9"把我们的实例当成了免费缓存"）与这句并置后，全书对未授权 Redis 的危害量级停留在"被蹭缓存/被写公钥"的印象上，而真实公网无认证实例的常见结局是清库勒索与植入挖矿——危害描述被无害化了。改进方向：在 6.2 或 6.3 补一小段机制层说明（不写可复现步骤）：未授权的杀伤本质是"持久化落盘的路径与文件名可被远程控制 + 服务进程具备文件系统写权限"，于是"任意路径写文件"成立，再借操作系统/服务的自动加载点升级为代码执行；4.0 引入的模块机制让这条链进一步变短，所以"收敛危险命令面"（业务账号用 ACL 摘掉危险与管理的命令类别）应作为一条明确的生产动作。这也正好补上 6.3 讲了 @dangerous 分类却始终没告诉读者"该用它把危险命令从业务用户手里摘走"的断点。 | 结构 |
| 2 | ch6 L104 | 真正起作用的是 `protected-mode`（保护模式，3.2.0 起，默认开启）：当 Redis 绑定全部网卡且没有配置任何密码、`AUTH` 等认证手段时，它只接受本地回环连接，对外网连接直接拒绝。换句话说，protected-mode 拦的是"裸监听被外网命中"，不替代认证本身。 | 对 protected-mode 的触发条件描述是对的，但漏了攻击者视角最关键的一个拐点：只要配置了任何密码/ACL 用户，protected-mode 就整体退出保护，从那一刻起实例的安全性完全等于口令熵——而 Redis 没有失败锁定、没有在线尝试限速、登录成功也不告警，公网 + 弱口令等于可无限次在线爆破（L50 讲的是拖库后的离线字典风险，在线无限尝试这条全书没写）。运维读者按本节理解容易得出"我设了密码就比裸奔安全一个量级"的虚假安全感，实际只安全了一个口令长度。改进方向：在这句后面补一句拐点说明——配置任何认证手段后 protected-mode 即不再拦截，Redis 亦无在线尝试限速，口令强度是唯一防线，因此公网可达的实例必须叠加网络层隔离（呼应第 3 条）。 | 事实 |
| 3 | ch6 L191 | Redis 的安全取向是"内网优先、按需叠加"。实用底线：开启 ACL 并为每个应用建独立用户、关闭 default 用户、开启 protected-mode、按需开 TLS、用 ACL LOG 加外接采集补审计，补完这套，Redis 才算从"能用"进入"敢上生产"。 | 这份"敢上生产"底线清单五项全是应用层（认证/授权/加密/审计），没有一项网络层动作，与本章启示二自相矛盾——L209 写着"把安全做成多层叠加：网络隔离、传输加密、认证、授权、审计、存储加密"，L211 还说"只押一层的方案，无论多厚，我都打回"。从对抗视角看，只配 ACL 的 Redis 在凭据泄露或服务进程漏洞面前没有第二道防线，而 bind 指定内网地址 + 防火墙/安全组白名单恰恰是 Redis 安全里性价比最高、最该排第一的一层。清单与自己的启示打架，会误导读者把"配齐五项"当作终点。改进方向：底线清单第一项加"网络层硬隔离：bind 内网地址、安全组/防火墙白名单，Redis 永不直接监听公网"。 | 一致性 |
| 4 | ch6 L187 | 姿态差异的来源是数据模型和请求要跨的跳数。姿态没有高下，错配才有事故——把内网姿态放到公网，就是本章开头那个爬虫事件的根因。 | 全章的威胁叙事只有"错误暴露到公网"一种模式（我通读并检索确认：SSRF、内网横穿、安全组等词全书零出现），这是 2015 年的威胁模型。2026 年的真实主力打点路径是：外网应用的一个 SSRF/RCE 漏洞 → 内网 → 中间件无认证横穿。落到三家：Kafka 明文 listener 的真实威胁从来不是"9092 挂公网"（很少有人这么干），而是内网任意一台失陷机器都能全量读写所有 topic——凭据、PII、审计流水整批送出去，还能建删 topic、改配置；L74 已经点出"出厂默认 inter-broker 是 PLAINTEXT"，说明作者意识到了问题，但"错配=公网"的框架把纯内网的明文实例描述成了安全态。启示里"内部工具可以更开放"（L205）同样会按公网/内网二分法给读者宽慰。改进方向：在 6.1 或 6.6 补一小段现代攻击路径校准：内网不等于可信域，评估明文/无认证 listener 的风险时应按"内网任意主机可达 + 一台跳板机失陷"计算，而不是按"是否暴露公网"计算。 | 结构 |

| 7 | ch6 L117 | 注意：FILE 权限能读写服务器文件系统，配合 SQL 注入可读任意文件，是高敏权限的典型。 | 这句在 8.0 基线下有两处不准：其一，"可读任意文件"夸大了——8.0 默认 `secure_file_priv` 把 LOAD_FILE/LOAD DATA/INTO OUTFILE 全部限制在单一目录内，SQL 注入拿到 FILE 权限也出不了那个目录，这是 8.0 对这类老攻击链的关键默认缓解，书里讲了攻击能力却只字不提默认缓解，读者（尤其防御方）会对风险量级产生错判；其二，方向上也就漏了该讲的内容——评估 FILE 权限风险、加固生产库时，secure_file_priv 恰是第一检查项（我们判断可利用性的第一步就是看它）。改进方向：这句改为提及 8.0 默认受 secure_file_priv 目录限制，并注明显式放开该参数时"可读任意文件"才成立；顺带点明这是"默认缓解已内置、但常被运维无意中放开"的典型参数。 | 事实 |
| 8 | ch2 L132 | Redis 的协议叫 RESP（REdis Serialization Protocol）。它的设计目标非常明确：实现简单（服务端解析不费 CPU）、人眼可读（协议就是文本，用 `nc` 连上 6379 端口直接打字就能交互）、能表达所有 Redis 命令和返回值。 | 这一节（含启示三"简单协议的接入成本最低"）把"人眼可读、nc 直接交互、写个客户端只要一下午"全部当作纯优点讲，通读全书没有任何一处指出同一特性的安全代价：纯文本、无帧头、命令以换行结尾的协议，既是调试福音，也是扫描与利用门槛极低的来源——不需要专用客户端就能操作，命令序列还能被嵌进其他协议的请求体里发往内网端口（这正是 Web 侧 SSRF 能打到 Redis 的协议层原因）。ch2 不必改（那里讲的是技术事实），但 ch6 作为安全章理应回收这个伏笔，建立跨章呼应。目前 ch6 讲 Redis 攻击面时对"为什么 Redis 特别好打"的协议层根源完全没有触及。改进方向：ch6 Redis 部分加一句呼应第 2 章的话：RESP 的极简文本形态同时决定了它被探测和被伪造的低成本，这也是网络隔离对 Redis 比对口令更重要的原因之一。 | 结构 |
