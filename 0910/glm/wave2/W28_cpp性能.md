# W28 · C++性能武工 · 读者报告

审阅人设定：C++ 高频/性能方向 12 年，关注缓存行、伪共享、分支预测、内存分配器（jemalloc/tcmalloc）。审阅重点：全书"为什么快"的微观归因是否站得住。宏观简化接受，归因错误较真。通读全部 13 个文件，重点核了第 2、4、5、8 章的性能归因段。

| # | 位置 | 原文 | 意见 | 类型 |
|---|------|------|------|------|
| 1 | ch5 L24 | 它要把每条命令的端到端时间降到亚毫秒，于是层数越少越好，跨层调用最好是直接函数调用，连虚函数的开销都要避免。 | 这句归因不成立，而且同章自己就推翻了它。5.2.4（L82）写"全程无序列化、无虚函数……命令分派用的是函数指针（`cmd->proc(client)`），就是一张静态表里的一次跳转"——通过函数指针的间接调用在机器码层面就是一次 `call *reg`，与 C++ 虚函数派发同价（一次间接跳转、无法内联），L82 一边说"无虚函数"一边描述了一次间接调用，前后拧着。量级上，间接调用 1-2ns，对端到端亚毫秒（百微秒级）延迟占比约 10^-5，把"避免虚函数开销"列进 Redis 低延迟的成因是想当然。Redis 快的真实微观原因是：数据结构在内存（访存即 DRAM/L2）、单线程无锁无上下文切换、命令路径除网络 read/write 外无系统调用、无序列化。改进方向：L24 删去"连虚函数的开销都要避免"；L82 把"无虚函数"改为"无跨线程、无序列化、无队列中转"，并把"这正是延迟降到亚毫秒的原因"的功劳记给内存访问与免锁，而不是记给"零抽象"的层间调用形式。 | 事实 |
| 2 | ch2 L34 | 这组策略把频繁操作中的系统调用次数降到最低，让 Redis 在最常用的操作上做到摊还 O(1)。 | realloc/free 是用户态内存分配器的库函数，不是系统调用。Redis 默认链 jemalloc，追加触发的扩容绝大多数在用户态 arena/thread cache 内完成（切分已有 span），不陷入内核；只有分配器向 OS 要新内存（brk/mmap）那一步才是系统调用，而预分配恰恰是为了让这条路径几乎不发生。前文 L33 自己用的是正确措辞（"连续追加时不会每次都触发 `realloc`"），总结句却把它升格成"系统调用次数"，把百纳秒级的分配器调用说成了微秒级、要上下文切换的陷入，量级和机制都错了。改进方向：改成"把内存分配（realloc）次数降到最低"，或加半句"Redis 的 jemalloc 下多数分配在用户态完成、不进内核"。 | 事实 |
| 3 | ch2 L41 | 跳表的缓存局部性确实不如红黑树，但在 Redis 的典型数据规模下，这点差异不是主导因素。 | 微观归因用错了词。跳表和红黑树同为堆上离散分配的节点结构，单个节点的空间局部性没有本质差异；真正的差别是查找路径上平均要 touch 的节点数——跳表每层"前进+下沉"都是指针追逐，期望比较/访存次数约 2×log₂N，红黑树约 1×log₂N，这是常数因子（访存次数约 2 倍）的亏，不是"局部性"的亏。局部性差的是和 B 树、有序数组这类连续内存结构比，不是和红黑树比。顺带一提，antirez 选跳表的三条理由（内存省、范围查询直接、实现简单）里不但没有"认了局部性亏"，还把跳表标为更省指针（p=0.25 时平均每节点 1.33 个前向指针，少于平衡树的 2 个）。书里前半句"选跳表而非红黑树，是因为实现更简单、范围操作更直接"是对的，补的这半句平衡站不住。改进方向：改成"跳表查找平均要访问约两倍于树高的节点，每次都是一次指针追逐，访存次数的常数因子比红黑树大；但在 Redis 的典型数据规模下，这点差异不是主导因素"——亏在次数，不在局部性。 | 事实 |
| 4 | ch5 L44 | 整个内存模型（无锁数据结构、惰性删除、对象共享）都建立在"单线程修改"的前提上，一旦放开并发，要么大面积加锁牺牲延迟，要么重写全部数据结构。 | "无锁数据结构"（lock-free）是并发编程的专有名词：指用 CAS/原子操作实现、多线程可以无锁并发访问的结构。Redis 的 dict、skiplist 恰恰相反——它们是普通非线程安全结构，因为单线程独占访问才不需要锁。这两者从设计目标到实现手法都相反，懂并发的读者读到"Redis 的无锁数据结构"会以为里面满是 atomic CAS，而实际上打开多线程 I/O 后 Redis 反而要在引用计数等处引入原子操作（那才是真正的"锁"的开销）。改进方向：改成"免加锁的数据结构（单线程独占，不需要锁）"或"非线程安全的数据结构"；括号里三项并列时避免用 lock-free 术语占位。 | 术语 |
| 5 | ch10 L102 | Redis 用内存换 O(1) 访问，把数据全部驻留内存，把"空间换时间"做到了头。 | 两个问题。其一，O(1) 不是内存给的：哈希点查的 O(1) 是结构性质，数据放磁盘的哈希表照样 O(1) 次寻址（InnoDB 的自适应哈希索引就是磁盘世界里的 O(1)）；内存买的是每一步访存的延迟（DRAM 百纳秒 vs 磁盘微秒到毫秒），不是渐近复杂度等级。"内存换 O(1)"把两个正交的维度焊在一起了。其二，与全书自己的口径不一致：第 2 章 L21 与第 4 章表 4-3 都写 Redis 是"O(1) 到 O(log N)"（ZSET 跳表、范围操作都是 O(log N)，跳表是 Redis 招牌结构），这里收窄成 O(1)。改进方向：改成"Redis 用内存换每次访问的低延迟（结构复杂度 O(1) 到 O(log N)），把'空间换时间'做到了头"。 | 一致性 |
| 6 | ch2 L21 | Redis 要的是**极低延迟**。所以它的数据结构全部在内存里，操作复杂度 O(1) 到 O(log N)，内存紧凑是第二考量。 | 低烈度，但因果链排布有误导。"所以"的辖域里并列了三件事，"操作复杂度 O(1) 到 O(log N)"会被读成"放进内存"带来的收益——复杂度是所选结构（哈希、跳表）的性质，与驻留介质无关，磁盘哈希表也是 O(1) 寻址、B+ 树也是 O(log N)；内存换的是每步访存代价低。这正是第 5 条（ch10 L102）那处硬伤的源头，两处一起改才能断根。改进方向：拆开因果，例如"所以它的数据结构全部在内存里，每步操作的访存代价都是 DRAM 级；这些结构本身的复杂度是 O(1) 到 O(log N)，内存紧凑是第二考量"。 | 事实 |
