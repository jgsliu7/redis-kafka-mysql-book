# W23 · PG用户老魏 · 读者报告

读者人设：PostgreSQL 深度用户 10 年，公司核心库全在 PG，MySQL 是配合客户的第二语言。买这本书要的是"三家取舍的思想"，读时逐处判断：书里说"MySQL 如何如何"而 PG 不是这样的地方，是书写错了、还是 MySQL 真这样、还是 MySQL 特例被当成了普遍规律。以下 8 条均为"MySQL 特例未标注，PG 读者迁移思想时会被绊住"的点（第 8 条为此问题的全书结构性汇总）。

| # | 位置 | 原文 | 意见 | 类型 |
|---|------|------|------|------|
| 1 | ch1 L36 | 它的 InnoDB 引擎几乎成了关系型存储的标准实现：事务、MVCC（多版本并发控制，Multi-Version Concurrency Control）、B+ 树聚簇索引（clustered index）、WAL（预写日志，Write-Ahead Log）。更难得的是它的演化史就是一部关系库架构演进史，从早期的 MyISAM 到 InnoDB 默认化，再到组复制（MGR，MySQL Group Replication） | 两处过度泛化。其一，"标准实现"清单里的"B+ 树聚簇索引"恰恰不是关系库的普遍形态：PostgreSQL 和 Oracle 的表都是堆表（heap），数据无序存放、索引与数据分离，走聚簇组织（表即主键 B+ 树）的主要是 InnoDB 和 SQL Server 一路。PG 读者会把聚簇索引当关系库标配带进认知，之后读 ch2 L81"InnoDB 的表本体就按主键组织成树"的推论（回表路径、二级索引存主键值）会误以为 PG 同构，而 PG 的二级索引直接指向行物理位置、布局与代价模型完全不同。其二，"演化史就是一部关系库架构演进史"：MyISAM→InnoDB 的"无事务到事务"之路是 MySQL 自己的历史，PG 自 POSTGRES 一脉演化从未有无事务引擎时代，谈不上"关系库的"演进史。改进：把"标准实现"改为"主流实现之一"，并在首次提到聚簇索引处加半句"PostgreSQL/Oracle 采用堆表组织，索引与数据分离" | 事实 |
| 2 | ch1 L76 | MVCC 的原理一句话说清：改一行时保留旧版本，读事务持有一个 Read View 判断哪些版本对它可见（Read View 在事务首次读时拍下快照，记下当时的活跃事务集合；判断方式是沿 undo log 串起的版本链从新到旧，找第一个对自己可见的版本），于是读不加锁、不阻塞写，写也不阻塞读；undo log（回滚日志）里串起来的那条旧版本链，就是它的载体。 | 以"MVCC 的原理"开篇，内容却全是 InnoDB 的实现。MVCC 是一类技术，至少两条实现路线：InnoDB 的"原地改 + undo 链存旧版本 + Read View"，和 PG 的"旧版本直接留在表内（tuple 头带 xmin/xmax）+ 快照判断可见性 + VACUUM 回收"。PG 没有 undo log，也没有 Read View 这个结构。说"原理一句话说清"然后只讲 undo 链，等于把一条实现路线升格为原理。后果不止此处：ch3 L128 正是用这条"原理"推出"回滚逐条撤销、事务越长越慢"（见第 3 条）。改进：加一句限定"这是 InnoDB 的实现路线；PostgreSQL 走另一条路（新版本追加进表、靠 VACUUM 回收），同样做到读不阻塞写"，一句话即可防止原理与实现混淆 | 事实 |
| 3 | ch3 L128 | 2. **长事务在跑。** 关闭时这些事务会被回滚。回滚走 undo log 的逻辑逆操作逐条撤销，通常比正向写入更慢，事务越长越慢。 | 把"回滚比正向写入慢、事务越长越慢"当普适事实列进排障清单。这是 undo log 路线特有的代价：InnoDB 回滚要沿 undo 链逐条做逻辑逆操作。PG 的回滚近似 O(1)——abort 只在提交状态位图里打标记，旧版本留着等 VACUUM，百万行大事务回滚也是瞬间。PG 用户若把这条"MySQL 经验规律"套到自己库上（比如为避免关机慢而预先拆大事务），会发现前提根本不存在。反过来，这条规律其实是指纹级信息——它直接暴露了一个数据库是否用 undo 实现 MVCC，书把它当普适事实反而丢掉了这层信息量。改进：此条后补半句标注"这是 undo 路线的代价；PostgreSQL 无 undo，回滚近似 O(1)，代价转为死元组空间膨胀与 VACUUM 压力" | 事实 |
| 4 | ch5 L230 | MySQL 的存储介质差异很大（事务型、内存型、归档型各有各的访问方式），所以它必须做可插拔，否则无法覆盖这些场景。 | "必须做可插拔，否则无法覆盖"因果过强，PG 是现成反例：从 1997 年到 2019 年（v12 引入 table access method 之前）只有一种内置堆存储，事务、归档等场景照样覆盖，扩展生态（PostGIS、pgvector、Citus）反而比 MySQL 的引擎生态更繁荣。MySQL 走可插拔更多是历史与商业产物（MySQL AB 靠引擎差异化竞争）。书在同章 L128 明明知道 PG 的存在（"PostgreSQL 12 起的 table access method 同属抽象层"），却没让这个反例来校准这条论断。这恰是 PG 读者最深的不服点：一对照，"必须"不成立，5.5 节"第三条根因"（实现多样性真实存在才做接口）的论证质量随之打折。改进：改成"MySQL 选择了用可插拔来覆盖这些场景"，并可加注脚：单一存储引擎 + 可扩展类型/索引/操作符（PostgreSQL 路线）同样是被验证过的路 | 事实 |
| 5 | ch6 L5 | Redis 可以在无认证状态下运行很多年，MySQL 从第一天就把权限做到列级，Kafka 则必须在每一跳都重新进行一次身份认证。 | "从第一天就把权限做到列级"与史实不符：MySQL 1995 年发布时权限只有 user/db/host 三张表（库级粒度），列级权限表 columns_priv 是 3.22（1998 年前后）才引入的。且与本章正文 L54 的口径自相打架——正文说"从早期就把安全纳入了核心设计"（这个说法准确），导读却升格为"第一天"。导读这句三家对比是读者建立安全姿态的第一锚点，锚点上有夸大，PG 读者还会顺带质疑比较级本身的成色（PG 同样支持列级 GRANT）。改进：改为"很早就把权限做到列级"，与正文对齐 | 事实 |
| 6 | ch8 L110（另见 L291） | 必须支持原地修改（in-place update）：一行被 UPDATE，对应的那一页就被原地改写，不能像 Kafka 那样只追加。 | 8.3.1 把"原地改"写成磁盘为主的页式格式的必然要求，8.6.2（L291"会原地改，就定长：MySQL 的行会被 UPDATE，所以页必须定长可原地改"）又把它规律化成决策准则。PG 是直接反例：同样是定长页（默认 8KB）+ 磁盘为主 + WAL，PG 的 UPDATE 从不原地覆盖——它写入新版本 tuple（HOT 时同页追加），旧版本保留供 MVCC 读，靠 VACUUM 回收。"行会被 UPDATE"与"原地改"之间没有必然性，原地改只是 InnoDB（配合 undo 链）的选择。这一条对迁移读者最致命：图 8-8 决策树的第一问就是"数据会被原地改吗"，PG 读者拿自己系统的 UPDATE 语义作答，会被引上"页式+原地改"这条 InnoDB 单行道，而不知道还存在"页式+版本追加+VACUUM"的第二条路（同样满足随机读写，代价形态完全不同：空间膨胀而非 undo 链）。改进：在 8.6.2 决策准则处补一句"原地改是 InnoDB 的选择；PostgreSQL 用定长页 + 写新版本 + 后台回收同样实现事务安全的随机读写，'改一行'未必等于'原地改'" | 事实 |
| 7 | ch8 L147、L149 | 更糟的是 redo log 假设页本身完整：redo log 记录的是"对完整页做的物理修改"，重做的前提是页已处于某个一致状态。半写的页连"完整"这一关都没过，redo log 救不了它。……InnoDB 的解法是双写缓冲（doublewrite buffer）。 | 半写页（torn page）这道题，书里只给了 InnoDB 的 doublewrite 一个答案，而论证口吻（"物理 redo + 页式 ⇒ 必须有双写"）会让读者以为凡页式 WAL 系统都得这么解。PG 用完全不同的方法解决同一问题：full_page_writes——每个检查点后首次修改某页时把整页镜像写进 WAL，恢复时先贴整页再重放后续修改。两种解法代价形态不同：doublewrite 是脏页双倍顺序写，FPW 是检查点后首改页的日志体积放大。本书立意是"取舍思想可迁移"，"同一道题的两种标准答案"正是取舍教学最珍贵的素材：只给一种，迁移者要么误以为自己系统缺 doublewrite 就不安全，要么自造 doublewrite 而不知还有代价更低的 FPW 路线。改进：在双写缓冲段加一句对照："PostgreSQL 对同一问题选了另一条路（WAL 内记整页镜像 full_page_writes），代价从双倍页写入变为日志膨胀；答案不唯一" | 事实 |
| 8 | 序言 L15 | 但样本只是样本，我真正想记录的是观察的方法。这套方法的适用面也不止这三个软件 | 序言承诺"方法适用面不止这三个软件"，但全书没有一处告诉读者：MySQL/InnoDB 的描述里哪些是普适规律、哪些是这一家实现的特例。本报告前 7 条全部由此而来——聚簇索引、undo 版本链、回滚逐条撤销、原地改、doublewrite、可插拔引擎，全是"InnoDB 这样"而非"关系库都这样"，但行文多以"原理/必须/标准"的口吻出现。这类书最可能拿去迁移的读者恰恰是 PG/Oracle/SQLite 用户：标注特例丝毫不影响 MySQL 读者的阅读，却能让迁移读者免于把实现细节当规律带回去；缺这一层，"思想可迁移"的承诺只兑现了一半（坦白说，第 10 章五条规律本身在 PG 上全部对得上，正本/层/顺序批量/代价/状态建模无一例外，这更说明该标注的是中途的实现细节，不是结论）。改进：在 1.4.3 版本基线处（那里已声明"本书讨论 MySQL 时以 InnoDB 为主"）扩三五个句子的"迁移提示"，点名最易误迁移的几处（存储组织、undo 与回滚、原地改、引擎可插拔），说明其余论断（WAL、五条规律、各取舍谱系）可放心迁移 | 结构 |

## 总体判断（给编辑部的一句话）

书里 MySQL 的描述绝大多数在 MySQL 语境内是准确的，问题集中在"把 InnoDB 的实现路线用'原理/必须/标准'的口吻讲"而未标注边界——对只用 MySQL 的读者无碍，对 PG 背景读者则是连续的理解陷阱；第 10 章五条共性规律在 PG 上全部成立，迁移价值真实，建议用低成本的一处"迁移提示"把陷阱变成学习机会。
