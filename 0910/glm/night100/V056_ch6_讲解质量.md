| 1 | L72 | 长期凭证（SCRAM 密码、Kerberos 票据）在客户端和 Broker 之间反复传会有泄露风险，委托令牌是短期有效的令牌，由已认证的客户端向 Broker 申请，之后用令牌做认证，到期自动失效。 | 与 L68 直接冲突。L68 刚讲完 SCRAM 的核心优点是"客户端要持有密码本身，但密码从不上网——客户端用密码加上服务端下发的盐和双方的随机数算出证明"，即 SCRAM 在线路上传的只是证明值、密码本身从不传输；L72 却说"SCRAM 密码……在客户端和 Broker 之间反复传会有泄露风险"。读者两段连读必然糊涂：SCRAM 的密码到底上不上网？面试时被追问"SCRAM 的泄露风险到底是什么"就答不上（真实风险是：长期凭证要静态配置在每台客户端机器上、配置面即泄露面，以及无 TLS 时握手报文可被嗅探后离线暴力破解）。"反复传"只对 Kerberos 票据成立（票据确实随请求反复出示）。建议改为："长期凭证（SCRAM 密码、Kerberos 票据）要静态配置在每个客户端、在跳与跳之间反复使用，泄露面大；Kerberos 票据更是随请求反复出示"，把两种凭证的风险分开说。 | 一致性 |
| 2 | L219 | Kafka 的委托令牌、服务账户、代理传递三种方案各有取舍：委托令牌短期有效但需要刷新机制；服务账户丢弃了原始客户端身份；代理传递依赖服务之间的信任。 | "服务账户"和"代理传递"两个方案在第 6 章正文从未出现过——6.2.3 只讲了委托令牌（L72），启示四却以"三种方案各有取舍"的总结口吻直接给出后两种的取舍结论。读者脑中缺的是整块拼图：服务账户指什么（中间服务用自己的身份收发消息）？代理传递指什么（原始身份随请求携带、下游信任上游）？没有任何铺垫，这两句取舍判断读完就忘、费曼检验必挂。建议：要么在 L72 委托令牌段补两句另两种方案的示意（例如"除此之外还有两条路：中间服务换成自己的服务账号收发，代价是原始客户端身份丢失；或把身份随请求透传，代价是下游必须无条件信任上游"），要么在启示四里用插入语带出定义。 | 结构 |
| 3 | L104 | 真正起作用的是 `protected-mode`（保护模式，3.2.0 起，默认开启）：当 Redis 绑定全部网卡且没有配置任何密码、`AUTH` 等认证手段时，它只接受本地回环连接，对外网连接直接拒绝。 | "当 Redis 绑定全部网卡"这个触发条件表述会构建错误心智模型。protected-mode 的真实触发条件是"没有显式配置 `bind` 指令（默认监听全部网卡）且 default 用户无密码"；一旦显式写了 `bind 0.0.0.0`，Redis 视为管理员有意暴露，protected-mode 不再兜底。而"绑定全部网卡"完全可以被读成"显式 bind 0.0.0.0 也算"——这恰恰是最危险的误读：很多运维显式 bind 0.0.0.0 后以为自己还有 protected-mode 兜底，实际没有。建议改为："当 Redis 没有显式配置 `bind`（此时默认监听全部网卡）且没有配置任何密码……一旦显式写了 `bind`——哪怕是 `bind 0.0.0.0`——就视为有意暴露，protected-mode 不再拦截"。 | 事实 |
| 4 | L104 | 要真正加固，还得运维自己动手：显式给 `default` 用户设密码或直接禁用（例如 `ACL SETUSER default off` 禁用用户，或 `ACL SETUSER default resetpass` 清空密码并同时移除 nopass 标记——此后没有密码就再也没法认证成 default）。 | 两个卡点。其一，正文给出两个选项"设密码或直接禁用"，括号里两个例子却是 off 和 resetpass——resetpass 既不是设密码也不是字面禁用，读者要自己猜它对应哪个选项、或者以为它是第三个选项。其二，"移除 nopass 标记——此后没有密码就再也没法认证成 default"这个推论完全依赖 nopass 的含义（该用户允许免密认证的开关标记），但同段前句规则串 `user default on nopass ~* &* +@all` 里的 nopass 从未解释（顺带 `&*` 与 L102 通道权限的对应也没点破）。不知道 nopass 是"免密许可"，就无法理解为什么移除它就没人能认证。建议：在规则串讲解处补一句"其中 nopass 表示允许无密码直接认证，这正是'无认证状态'的技术来源"；例子与选项一一对齐（设密码给 `ACL SETUSER default >新密码`，禁用给 off），resetpass 单独说明其"清空一切登录手段"的效果。 | 可懂性 |
| 5 | L203 | Redis 默认开放（假设内网）、MySQL 默认收紧（假设企业网络暴露）、Kafka 的默认是中性（假设混合云）。 | "中性"一词全书此处仅见且无定义，读者无法复述它指什么。对照本章已给的事实：Kafka 认证默认 PLAINTEXT 监听器（不设防），授权默认一边 AclAuthorizer 无 ACL 放行、一边 StandardAuthorizer 拒绝（L127、表 6-1）——按"开放/收紧"的坐标轴，前者是开放、后者分裂，哪一处也推不出"中性"。费曼检验："Kafka 的默认是中性"——具体中性在哪？讲不出来。缺的拼图是"中性"想表达的真实含义（认证加密全靠显式配置、默认行为由所选授权器决定，Kafka 不替部署者预设立场），但这个解码书里没写。建议换成可复述的表述，如"Kafka 默认不设防但把定级工具全交给配置（认证、加密、授权三者都默认关闭，全靠显式启用）"。 | 可懂性 |
| 6 | L15 | 这四个层面在一次"客户端发起请求到数据落盘"的链路上各覆盖一段，审计则贯穿全程。 | 句内自相矛盾：主语"这四个层面"包含审计，前半句断言四者"各覆盖一段"，后半句又单独把审计拎出来说"贯穿全程"——同一句话给了两个互斥的图景。L22 的准确版本是"认证、授权、加密各覆盖链路中的一段，审计以旁路贯穿全程"，图 6-1 也是三段加旁路的画法。读者先在 L15 建立"四段接力"的错误心智模型，读到 L22 和图 6-1 才被迫修正。建议 L15 改为"前三个层面在一次'客户端发起请求到数据落盘'的链路上各覆盖一段，审计则贯穿全程"。 | 一致性 |
| 7 | L5 | Redis 可以在无认证状态下运行很多年，MySQL 从第一天就把权限做到列级，Kafka 则必须在每一跳都重新进行一次身份认证。 | "每一跳都重新进行一次身份认证"的粒度不明：是每条消息/每请求认证一次，还是每条连接建立时认证一次？按后文（L70 控制面认证、L74 监听器分层、L100 会话级认证一次），Kafka 的真实机制是"每条链路（每跳）各自建立连接、各认证一次"，同一连接内仍是会话级一次。导读的字面读法（每跳重新认证）加上 L219 又强调"认证一次、授权每操作"的模型在多跳下"不够用"，两处连读会强化"Kafka 每发一条消息都要重新认证"的误解——面试照这个讲，被追问"Kafka 每条消息都握手吗"就翻车。建议改为"Kafka 则因为一次数据流动要跨客户端、Broker、控制面好几条链路，每条链路都要各自完成一次身份认证"。 | 可懂性 |
| 8 | L50 | 凭证存储上，密码以 SHA-256 摘要形式存（通过 `ACL SAVE` 持久化到 `aclfile` 指定的文件，默认无 aclfile，需显式设置；在外部编辑过 aclfile 后，用 `ACL LOAD` 让服务端重读——内存中的运行时改动会被文件覆盖），不存明文。 | 一句话的括号里同时塞了四件事（摘要存储、ACL SAVE、默认无 aclfile、ACL LOAD 与覆盖语义），主线（密码怎么存）被不断岔开。更关键的是读者最自然的追问没有答案：`ACL SETUSER` 改完之后重启会不会丢？书里缺的拼图是改动的两条去向分支——未配置 aclfile 时 SETUSER 只改内存、重启即丢（且此时 ACL SAVE 会报错）；配置了 aclfile 时 SETUSER 也只改内存，要 ACL SAVE 才落盘。这两个分支书里都没明说，读者只能从"内存中的运行时改动会被文件覆盖"反推一半。建议把括号拆成两句正文："aclfile 配置与否决定改动的去向：没设 aclfile，`ACL SETUSER` 只改内存，重启即丢；设了 aclfile，也要再执行 `ACL SAVE` 才写入文件，外部改文件则用 `ACL LOAD` 让服务端重读。" | 可懂性 |
