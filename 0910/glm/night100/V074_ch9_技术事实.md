| 1 | L69 | 触发 `BGSAVE`，fork 出一个子进程把当前内存快照写成 RDB 文件。 | 与 7.x 基线不符。Redis 7.0 起 `repl-diskless-sync` 默认改为 yes（GitHub issue #9992 / PR #10092，收录于 7.0 官方 changelog）：默认路径下 fork 出的子进程把 RDB 直接经 socket 流给副本，主节点不写 RDB 文件；"先写文件再传文件"是 repl-diskless-sync=no 的旧行为（≤6.x 默认）。L71"RDB 文件传给副本"、L76"RDB 文件在网络上的传输"连带同样不准确。fork 本身、COW 内存翻倍风险、出口带宽消耗三项代价在无盘路径下同样成立，不必删，只需把"写成文件"改准。改进文本：'触发 `BGSAVE`，fork 出子进程生成内存快照——7.0 起默认无盘复制（`repl-diskless-sync=yes`），快照不落主节点磁盘，由子进程直接经 socket 发给副本；写盘再传文件是更早版本的默认路径'。 | 事实 |
| 2 | L135 | 代价是日志更重：一条 `UPDATE ... WHERE id<100` 影响一百行，ROW 格式会产生一百条事件。 | "一百条事件"不成立。ROW 格式下一个 Rows event 可包含多个行镜像（row image），官方文档明言"a rows event may contain multiple rows"，按 `binlog_row_event_max_size`（默认 8KB）打包，超限才切分新事件。影响一百行的 UPDATE 通常产生 1 个或少数几个 UpdateRows 事件、内含一百个行镜像，不是一百条事件。"事件"（binlog event）在 MySQL 里有明确定义，资深读者会当场出戏。L131"记录的是'行 k 从值 v1 变成了 v2'这样的行级事件"也容易固化"一行一事件"的印象，可一并留意。改进：'一条 `UPDATE ... WHERE id<100` 影响一百行，ROW 格式会产生一百个行镜像，按 `binlog_row_event_max_size`（默认 8KB）打包成一个或少数几个事件'。日志更重的结论不变。 | 事实 |
| 3 | L311 | 这不排斥状态快照：追赶落后太多的副本时，三家都用快照打底（RDB、clone、分区日志拷贝），再用增量序列续传。快照决定同步的起始位置，有序重放保证此后每一步对齐。 | 对 Kafka 不成立。Kafka 复制没有"快照+增量"两段式：落后但日志完好的副本只是继续从自己的 offset FETCH，落后再远也不会触发"快照打底"；只有 fetch 位点早于 Leader 的 log start offset（数据被保留策略清掉）时才整段重拷，而重拷的是日志本身——完整重放历史，不是某一时刻的状态快照。RDB/clone 的价值恰是绕过历史重放、直接拿状态；Kafka 恰好没有这个机制（日志即序列，无需快照）。把"分区日志拷贝"塞进"快照打底"框架机制上说不通，还丢掉一个更锋利的对照点。建议：把 Kafka 移出"三家都用快照"的并列，或反向利用——'Redis 和 MySQL 用状态快照跳过历史重放，Kafka 的日志本身就是全量历史，无需快照，这是它复制机制简洁的另一个来源'。L323"Kafka 则要拷整个分区日志"单看没错，问题只在 L311 的框架表述。 | 事实 |
| 4 | L287 | Kafka 最简单，日志本身就是序列，复制天然有序无需额外排序，只是更新和删除都要靠追加 tombstone（墓碑消息，标记删除的特殊消息）或新版本去表达。 | 缺限定，把 compacted topic 的语义写成了 Kafka 消息单元的普遍属性。tombstone 删除与"同 key 新版本覆盖"的更新语义只在启用 log compaction 的 topic 下成立；普通 topic 的数据按 retention 到期直接淘汰，不产生 tombstone，追加型 topic 也没有"更新"语义。建议加限定：'在 compacted topic 里，更新和删除才靠追加同 key 新版本或 tombstone 表达；普通 topic 的数据按保留期直接淘汰'。 | 事实 |
