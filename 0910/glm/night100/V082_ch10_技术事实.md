# V082 · ch10 · 技术事实视角

审读对象：`chapters/10-summary/chapter.md`（第 10 章总结）。视角：总结章对前九章机制的浓缩复述是否失真、横向对比表断言是否与实际（本书基线 Redis 7.x / MySQL 8.0.x / Kafka 3.x）相符。引文均逐字复制自 Read 输出；涉及前章原文处已回查对应章节文件核对。

| 1 | L21 | RDB/AOF 重放重建内存 | "重放"用不到 RDB 上。RDB 是二进制快照，启动时是整块加载/反序列化，不存在逐条重放；"重放"只适用于 AOF 的命令流（7.0 multi-part AOF 中也仅是 incr 文件部分，base 同样是 RDB 格式快速加载）。第 3 章原文严格区分了两者（3.2 节："把数据一条条加载回内存"、"先按 RDB 二进制快速加载 base，再重放 incr 里的命令"；表 3-2："文件加载（AOF 加载 base+incr / RDB 读）"），且本章 L146 自己写的就是"RDB 加载或 AOF 重放"——同章前后两个版本，L21 属复述失真。建议改为"RDB 加载 / AOF 重放重建内存"。 | 事实 |
| 2 | L57 | 预读把随机页请求变成顺序预取 | 机制描述失真。MySQL 8.0 默认生效的 InnoDB 线性预读（innodb_read_ahead_threshold=56）检测的是**顺序**访问模式——一个 extent 内按序读满 56 页才异步预读下一个 extent 整段，它不消费"随机页请求"；能由无序访问触发整段预读的随机预读（innodb_random_read_ahead）默认 OFF。预读的本质是"批量预取"（把未来多次小读合并成一次大读），不是"把随机改写成顺序"。此句作为规律三"把随机访问改写成顺序"的 MySQL 例证，例子的机制与规律对不上；且第 4 章正文讲的预读全是 Kafka 语境的 OS 预读，MySQL 预读在前章无出处。建议改为"预读在识别出顺序访问模式后，把整段页提前成批读入"，或换成真正"随机变顺序"的 MySQL 例子（redo log 把随机数据页写转成顺序日志写，第 4 章启示四已有）。 | 事实 |
| 3 | L163 | 能从 PSYNC2、GTID、ISR 里看出"用可比位点对齐两个状态机"这个共性 | ISR 不是位点。ISR（in-sync replicas）是"哪些副本同步达标"的副本集合，Kafka 中与 Redis 复制偏移量、GTID 对应的"可比位点"是 leader epoch + 位移。第 9 章导读原话是"三个软件用三套不同的机制（PSYNC2、GTID、leader epoch）……用可比较的位点对齐两个状态机"，本章 L27 表 10-1 的同类括号也是"复制偏移量/GTID/偏移量"——L163 把 leader epoch 偷换成 ISR，属对第 9 章核心论断的复述失真。建议改为"能从 PSYNC2、GTID、leader epoch 里看出……"。 | 事实 |
| 4 | L145 | acks=all 接近 0 | 缺前提，断言不成立。acks=all 单独并不保证 RPO 接近 0：Kafka 默认 min.insync.replicas=1，ISR 收缩到只剩 leader 时（仍满足 min.insync.replicas=1），acks=all 只等 leader 自身确认，leader 宕机且消息未同步到 follower 时照样丢。本章 L72（"acks=0/1/all 配合 min.insync.replicas"）与 L100 都把两者绑定表述，表格单元格却丢了前提；对比同行 Redis 列都带了"（开启 AOF 后）"的条件。建议改为"acks=all + min.insync.replicas≥2 接近 0"。 | 事实 |
| 5 | L147 | MirrorMaker / Cluster Linking（均为 Kafka 官方跨集群复制工具） | "均为 Kafka 官方"不成立。MirrorMaker 2 是 Apache Kafka 官方组件（KIP-382）；Cluster Linking 是 Confluent Platform / Confluent Cloud 的**专有商业特性**（Confluent Platform 6.0 起），Apache Kafka 开源发行版中没有该功能，社区讨论多年未落地为 KIP。本书基线是 Kafka 3.x（Apache 版），读者在自建的 Apache Kafka 集群里根本找不到 Cluster Linking，按"官方工具"去查文档会困惑。建议改为"MirrorMaker 2（Apache 官方）/ Cluster Linking（Confluent 专有）"。 | 事实 |
| 6 | L80 | 用 ARIES 式恢复（3.3 节展开的重放 redo 与回滚 undo）当崩溃恢复流程 | 术语问题有二。（a）"ARIES"是全书首次出现，未给全称（Algorithms for Recovery and Isolation Exploiting Semantics，IBM 提出的经典数据库恢复算法框架，InnoDB 崩溃恢复借鉴了它），没听过 ARIES 的读者无法判断这四个字母是算法名还是拼错的单词；（b）括号"3.3 节展开的"暗示第 3 章 3.3 节讲过 ARIES，但 3.3 节乃至第 3 章全文从未出现"ARIES"一词（已全文检索确认），那里展开的是重放 redo 与回滚 undo 的操作本身。建议首次出现补全称，并把指引改为指向实际内容，如："用 ARIES 式（ARIES，Algorithms for Recovery and Isolation Exploiting Semantics，IBM 的经典恢复算法，InnoDB 借鉴之）恢复——重放 redo、回滚 undo（3.3 节展开）"。 | 术语 |
