# V035 · ch4 · 命令实操视角

审读对象：`chapters/04-memory-disk/chapter.md`（基线版本 Redis 7.x / MySQL 8.0.x / Kafka 3.x）。本轮逐条核对了章内全部参数名、默认值与行为断言：`maxmemory-samples`=5、八种淘汰策略、`appendfsync` 三档及 7.x 出厂 `appendonly no`、7.0 multi-part AOF、`innodb_old_blocks_time`=1000ms / `innodb_old_blocks_pct`≈3/8、`innodb_flush_log_at_trx_commit` 三档、doublewrite 8.0.20 独立文件、`log.segment.bytes`=1GB、`log.index.interval.bytes`=4096、KIP-679（3.0 默认 `acks=all`）、`vm.dirty_background_ratio`=10/`vm.dirty_ratio`=20 等均无误，未列入下表。以下 6 条为有把握的问题，其中 Query Cache 与 aof-use-rdb-preamble 两处已经 WebSearch 核实。

| 2 | L67 | 所有数据默认驻留在内存中，跳表、紧凑列表（listpack）、哈希表等结构（详见第 2 章）的操作复杂度是 O(1) 到 O(log N)。 | listpack 是连续字节序列，查找/插入按 entry 线性扫描，严格复杂度是 O(N)，不在 O(1) 到 O(log N) 区间；它"近似常数"是因为小对象编码阈值把元素数压小（如 `list-max-listpack-entries` 默认 128）。把 listpack 与哈希表 O(1)、跳表 O(log N) 并列进这个区间，懂行的读者会当场停住。同句式还出现在 L250（表 4-3"原生支持（O(1) 到 O(log N)）"）。建议改为：哈希表 O(1)、跳表 O(log N)、紧凑列表（listpack）严格是 O(N)，靠编码阈值把元素数压小，实际开销近似常数。 | 事实 |
| 3 | L164 | 图 4-5 的时序：事务提交时先把 redo log 写到日志文件并落盘（保证持久性）。脏页随后进入 Flush List。 | "脏页随后（提交后）进入 Flush List"与实现顺序不符：页在事务执行期间被修改、mini-transaction（mtr）提交时就挂上 Flush List，未提交的长事务的脏页同样会被后台线程刷盘；事务提交只决定 redo log 的 write/fsync 时机。这个顺序写反会让读者解释不了"长事务还没 commit，为什么脏页已经在被刷"（这正是运维里刷脏与 purge 交互的常见观察）。建议改为：页在被修改时（事务执行中）即进入 Flush List；事务提交只决定 redo log 何时落盘。后台线程随后把脏页先写到双写缓冲再写到表空间，最后推进 checkpoint。 | 事实 |
| 4 | L83 | `noeviction` 是内存满了直接报错、不淘汰，适合"数据不能丢"的场景。 | 实际行为是：maxmemory 打满后，会占用更多内存的写命令返回 `(error) OOM command not allowed when used memory > 'maxmemory'`；读命令（GET/LRANGE 等）照常执行，键也照常过期。"内存满了直接报错"不加限定，会让读者以为实例整体不可用；而实际排障时写报错、读探活仍通，正是 noeviction 打满的典型指纹。建议改为：`noeviction` 是内存满后拒绝会增内存的写命令（返回 OOM 错误），不淘汰任何键、读不受影响，适合"数据不能丢"的场景。 | 可懂性 |
| 5 | L170 | InnoDB 的页是 16KB，操作系统和磁盘的扇区通常是 4KB 或更小。 | 术语混用：磁盘扇区只有 512B 或 4KB（高级格式）两种规格，"4KB"这个粒度对应的是文件系统块（通常 4KB），操作系统层面没有"扇区"这个单位。双写缓冲防的是 16KB 页在最小原子写入单位不足时的部分写（页撕裂）。建议改为：InnoDB 的页是 16KB，而磁盘扇区只有 512B 或 4KB，文件系统的一次原子写入通常也只有 4KB，写一半断电就会撕裂 16KB 的页。 | 术语 |
| 6 | L108 | `aof-use-rdb-preamble` 在 5.x–6.x 中默认即为 `yes`。 | 该参数 4.0 引入时默认 `no`，5.0 起改为默认 `yes`，到全书基线 Redis 7.x 仍然保留且默认 `yes`（multi-part AOF 中控制 base 文件用 RDB 格式，已核实）。文中止步于 5.x–6.x，恰好漏掉基线版本的去向——而 7.0 刚好大改了 AOF 文件组织，读者有充分理由怀疑这个参数在 7.0 是否失效，此处不给交代会留疑。建议改为：`aof-use-rdb-preamble` 自 5.0 起默认即为 `yes`，7.x 沿用（作用于 multi-part AOF 的 base 文件）。 | 一致性 |
