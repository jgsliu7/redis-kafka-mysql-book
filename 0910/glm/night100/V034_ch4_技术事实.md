| 1 | L77 | 这个方案准确但代价大：每次访问都要动链表指针，访问量上去之后链表操作的 CPU 开销不可忽视。……这是一次典型的精度与性能取舍：取 5 个随机样本就足以近似真实 LRU，代价只是常量级的随机采样。 | 设计动机错置。Redis 官方文档与作者 antirez 给出的一手原因是**内存**，不是 CPU：精确 LRU 要为每个键维护双向链表的前后指针（外加索引结构），而近似 LRU 复用每个 redisObject 里已有的 24 位 lru 字段存最后访问时钟，采样淘汰不需要任何额外指针。redis.conf 原文写明近似算法是 "in order to save memory"；官方 eviction 文档："The reason for not using a real LRU implementation is because it takes more memory"。CPU 开销只是次要附带理由，本段只字未提内存，并把取舍总结成"精度与性能"，应为"精度与内存"。建议改写：先讲"每个键多出两个指针的内存代价"（对 Redis 每键几十字节的对象模型，这才是主因），CPU 开销作次要点带过。 | 事实 |
| 2 | L164 | 图 4-5 的时序：事务提交时先把 redo log 写到日志文件并落盘（保证持久性）。脏页随后进入 Flush List。后台线程把脏页先写到双写缓冲再写到表空间。最后推进 checkpoint，标记之前的日志可以回收。 | 时序说反。真实顺序：页在**语句执行**被修改的那一刻（mtr 提交时）就作为脏页进入 Flush List，这发生在事务提交**之前**；事务提交做的是把 log buffer 里的 redo 写入日志文件并 fsync（innodb_flush_log_at_trx_commit=1 时）。WAL 约束的是"脏页刷到磁盘之前，对应 redo 必须已落盘"，而不是"脏页进 Flush List 之前 redo 要先落盘"。按现文读者会推出"页先提交落盘、之后才变脏"，因果倒了。建议改为："语句执行时修改缓冲池页，页变脏随即进入 Flush List，redo 写入 log buffer；事务提交时把 redo log 写盘并 fsync（保证持久性）；后台线程随后把脏页先写双写缓冲、再写表空间；最后推进 checkpoint。" | 事实 |
| 3 | L172 | 修改缓冲的做法是：先把这次修改记下来（缓存），等这个页因为别的原因被读入缓冲池时，再把缓存的修改合并（merge）进去。 | 简化到失真：把被动路径说成唯一路径。merge 不只发生在"页因别的原因被读入"时——InnoDB 后台线程会**周期性地主动**把 change buffer 中有缓存修改的页读入缓冲池执行 merge（空闲时也做，慢关机时还会把剩余变更 merge 完再关）。若只有被动路径，长期不被访问的二级索引页的变更会无限堆积——innodb_change_buffer_max_size 参数存在的意义正是控制这个堆积。建议补一句："后台线程也会定期主动执行 merge，不等有人恰好读到这个页。" | 事实 |
| 4 | L202 | 因为它的读本身就是顺序的，操作系统预读机制能把"消费者将要读的下几 MB"提前加载进 PageCache，命中率天然就高。 | "下几 MB"与内核默认值差一个数量级以上。Linux 块设备默认 read_ahead_kb = 128KB（预读窗口上限也约 128KB），MB 级预读是生产调优（调大 read_ahead_kb，RHEL 调优指南建议顺序读场景调到 4–8MB）之后的效果，不是默认能力。且本章 L258 自己把"预读大小"列为 OS 可调参数，与这里的"天然"表述矛盾。建议改为"提前加载接下来要读的数据（默认 readahead 128KB，调优后可到 MB 级）"或弱化量级表述。 | 数字 |
| 5 | L30 | 纳秒、微秒、毫秒之间相差三到五个数量级，存储软件要在内存的纳秒和磁盘的毫秒之间跨过这个数量级差距，所有"内存-磁盘"设计都从这里起步。 | 数量级对不上。相邻两档（ns→μs、μs→ms）各差 3 个数量级，ns→ms 整体差 **6** 个数量级；"三到五"匹配的其实是前文两个换算例子（内存 vs SSD 随机 ≈ 10³，内存 vs 机械盘 ≈ 10⁵），与这三个时间单位对不上。建议改为："从内存的百纳秒到 SSD 的百微秒差三个数量级，到机械盘的十毫秒差五个数量级"，把比较对象（介质）而不是单位（纳秒/微秒/毫秒）作为落点。 | 数字 |
| 6 | L251 | 进程重启极快（数据在磁盘，无重放；上万分区时例外），但 PageCache 冷热影响读性能 | 把异常关闭的恢复条件写成了分区规模。干净关闭后重启确实几乎零恢复；但**异常关闭**（kill -9、断电、OS 崩溃）后 broker 要对**每个分区**做日志恢复——校验段内消息、重建 .index/.timeindex——这与分区数无关，只是分区少时快（秒级）、上万分区时到分钟级。现文"无重放；上万分区时例外"会让读者以为恢复工作只在上万分区时才发生。L262"例外是分区数巨大时（如上万分区）的日志段校验与索引重建要数分钟"同病。建议改为："干净关闭重启零恢复；异常关闭需逐分区校验日志、重建索引（分区多时分钟级）；无重放，但 PageCache 冷热影响读性能"。 | 事实 |

## 已核实无误的高风险断言（未列入表格）

- KIP-679 确为 Kafka 3.0 把 `acks` 默认从 1 改为 `all`（连同 enable.idempotence 默认 true）的提案——L218/L290 引用正确（经 KAFKA-10619 核实）。
- `vm.dirty_background_ratio`=10%、`vm.dirty_ratio`=20% 为 Linux 默认，且分母是可脏页内存（free + 可回收）而非总内存——L38 正确。
- InnoDB LRU 新老子链约 5/8 : 3/8（innodb_old_blocks_pct 默认 37）、innodb_old_blocks_time 默认 1000ms——L142 正确。
- MySQL 8.0.20 起双写缓冲从 ibdata1 移到独立 doublewrite 文件——L170 正确。
- Redis：八种淘汰策略、maxmemory-samples 默认 5、appendfsync 默认 everysec 且出厂 appendonly no、everysec 最坏丢约 2 秒、7.0 Multi-Part AOF（base/incr + manifest）、aof-use-rdb-preamble 5.x 起默认 yes、LFU 8 位计数器 + 懒衰减——均正确。
- Kafka：segment 默认 1GB、log.index.interval.bytes 默认 4KB、零拷贝路径 2 次上下文切换 + SG-DMA 下两次搬运均由 DMA 完成——均正确。
- 表 4-1 的换算（内存 1 秒 → SSD 17 分钟、机械盘 28 小时）数学上成立。
