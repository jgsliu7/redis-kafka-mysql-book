| 1 | L57 | 主节点 `fork` 出子进程，把内存数据写成一个 RDB（快照文件）发给从节点 | 基线 Redis 7.x 下默认行为不是"写成文件"。`repl-diskless-sync` 自 Redis 7.0 起默认改为 `yes`（6.x 及以前默认 no，GitHub issue #9992 变更）：全量同步时主节点 fork 子进程后把快照以 RDB 格式**直接经网络流写给从节点**，不在主节点磁盘上生成快照文件；只有显式配 `repl-diskless-sync no` 才是"先落盘成文件再发送"。fork、RDB 格式、增量存复制缓冲区的描述都对，唯"快照文件"是旧默认。建议改为："主节点 `fork` 出子进程，把内存数据以 RDB 格式直接经网络流发给从节点（7.0 起默认无盘复制 `repl-diskless-sync yes`，不在主节点落盘；设为 no 时才先写磁盘文件再发送）" | 事实 |
| 2 | L119 | 半同步只等从节点 I/O 线程把 binlog 写入 relay log 并落盘即确认，不等 SQL 线程回放完毕 | "并落盘"是加戏，半同步 ACK 不等 relay log 刷盘。MySQL 半同步的确认语义是 I/O 线程"收到事件并写入 relay log"即回 ACK；relay log 的落盘由 `sync_relay_log` 独立控制，**默认 10000**（每 1 万个事件才 fsync 一次，其余靠 OS 写回）。也就是说主机掉电时 relay log 中未刷盘部分照样丢，半同步从没承诺过 relay log 落盘。正确写法：去掉"并落盘"，或写明"写入 relay log 即确认（不要求落盘，落盘由 `sync_relay_log` 控制，默认 10000）"。这句是在抠"确认的成色"，恰好抠错了一分 | 事实 |
| 3 | L156 | 没有 key 时，生产者（Kafka 2.4 起经 KIP-480 改为默认）用"粘性分区"（sticky partitioner），把一批消息都发到同一个分区，积累够一批再换分区 | 只对 Kafka 2.4–3.2 成立，基线 3.x（本章 7.4.4 自己以 3.3+ 为准）已变。Kafka 3.3 起 KIP-794（Strictly Uniform Sticky Partitioner）改掉了无 key 记录的默认行为：不再"攒满一批才随机换分区"（linger.ms 提前 flush 时分布不均正是被修的病），而是**每个分区建好一批就切换、批间按分区轮转**，严格均匀，且默认带自适应避慢逻辑（`partitioner.adaptive.partitioning.enable` 默认 true；`DefaultPartitioner`/`UniformStickyPartitioner` 类自 3.3 弃用）。读者在 3.3+ 实测无 key 消息分布，看到的是"每批换分区"，与"积累够一批再换"矛盾。建议补版本边界："Kafka 2.4（KIP-480）起默认粘性分区，一批消息发往同一分区、攒满再换；3.3（KIP-794）起改为严格均匀：批与批之间按分区轮转、并偏向速度正常的 broker" | 事实 |
| 4 | L172 | 只要 ISR 非空且 ISR 全部收到，这条消息就不会丢 | 表述过强。`min.insync.replicas` 默认 **1**：当 ISR 收缩到只剩 Leader 一个副本时（两个 Follower 因 lag 被移出 ISR），acks=all 的发送只要 Leader 本地写入即满足"ISR 全部收到"并返回成功——此时保证强度与 acks=1 无异，Leader 所在 broker 磁盘一坏这条消息就丢。"不丢"的实质成立条件是 acks=all 且 ISR 内副本数 ≥ min.insync.replicas ≥ 2（官方推荐组合 replication.factor=3 + min.insync.replicas=2）。建议改为："只要 ISR 里的副本数不少于 `min.insync.replicas` 且全部收到，这条消息就不会因正常的 Leader 切换而丢（注意 `min.insync.replicas` 默认 1，ISR 缩到 1 个副本时 acks=all 的保证会退化，实质不丢需配 min.insync.replicas≥2，精确交互见第 9 章）" | 事实 |

| 7 | L129 | 当网络分区发生、组内凑不齐多数派时，少数派分区里的成员会**直接停止服务**：宁可不可用，也不允许脑裂写出脏数据 | MySQL 8.0 默认配置下不是"直接停止服务"，而是"写阻塞、无限期等待"。`group_replication_unreachable_majority_timeout` 默认 **0**：少数派成员不会主动退出，新事务在共识阶段被阻塞——应用写入 hang 住、既不返回也不报错（读查询照常），直到网络恢复；只有显式设置该参数，超时后成员才主动离组进入 ERROR 状态停止接受查询。这是 MGR 生产分区事故里应用连接堆积的经典根因，方向上"写不可用、不脑裂"没错，但"直接停止服务"把"默认阻塞等待"写成了"立即停服"。建议改为："少数派分区里的成员凑不齐多数派，写事务会被阻塞、无法提交（默认 `group_replication_unreachable_majority_timeout=0` 时是无限期等待而非立即报错，设置了该参数超时后才会主动退出停服）"。L200 对比表"MySQL…少数派分区停服"同源，可一并核对 | 事实 |
