| 1 | L13 | Redis 写盘不是最快的，Kafka 随机查询也不是最快的，但这本来就不是它们的核心目标。 | 前半句成立，后半句是能力边界表述失真。Redis 确实提供写盘（RDB/AOF）只是不追求极致写盘吞吐，是"有但不最优"；而 Kafka 根本不提供"随机查询"（按键/任意条件的点查）这个能力——它只支持顺序消费加按 offset/时间戳定位，按键查找在 compacted topic 上也要扫段文件或靠 Kafka Streams 状态存储这类外部设施。说"Kafka 随机查询不是最快"预设了 Kafka 能做随机查询、只是做得不快，把"没有的能力"说成了"有但不最优"，与作者要举例的"非核心环节不取局部最优"（能力存在但不优化）不是同一类现象。建议二选一：(a) 改为"Kafka 压根不做随机查询"，把论点从"不最优"改成"主动不做"，反而更贴合"放弃什么、换回什么"的主题；(b) 换成 Kafka 真实"有但不最优"的例子，如"Kafka 按时间戳回溯定位一条旧消息也不是最快的"。 | 事实 |

## 补充说明

- 以上三条均有把握：第 1 条基于 Kafka 公开能力边界（无点查 API）；第 2 条基于三家公开发布史（MySQL 1995 / Redis 2009 / Kafka 2011 开源）；第 3 条的 Kafka 4.0（2025-03-18，移除 ZK）与 Redis 8.0 GA（2025-05）已经 WebSearch 核实（kafka.apache.org 官方发布公告、redis.io 官方博客与 GitHub release）。
- 曾考虑未列入的弱项：L5"后端基础设施的大部分核心工作都落在它们身上"中"大部分"偏强（后端基础设施还含网关、对象存储、搜索等），但属修辞概括而非可证伪的事实错误，把握不足，不提。
