核实方式：40 名核实 agent，每个质疑对象 2 个独立视角——语境核实（读者是否误读原文）与事实核实（技术主张本身对错）。事实核实实际返回两票独立判断（fact1/fact2），故每项共 3 票；全部 60 票置信度均为「高」。结论用语约定：

- **读者成立（书需修）**：三票同判读者成立，书中表述需修改；
- **书无误（读者误读）**：技术核实为书正确，读者误读语境或误引外部材料；
- **部分成立**：读者技术事实基本对，但指控定性或范围过头（或反之），修改属呈现/措辞层；
- **视角分歧**：语境与事实两视角结论不同（事实侧两票一致，实质可裁，倾向以括注标明）；
- **存疑待作者裁决**：事实侧两票互相矛盾，编纂员无从裁决。

## 逐项详情

### V01 半同步 ACK「落盘」措辞过强（7.3/7.3.2 与 9.3 正文及图 9-5）

- **质疑内容**：MySQL 半同步复制的 ACK 条件被写成「写入 relay log 并落盘/刷盘」，给出过强的持久性保证；读者主张 ACK 只要求 write 不要求 fsync。
- **书中原文关键句**：7.3.2「从节点 I/O 线程把 binlog 事件写入 relay log 并落盘后就回 ACK」（chapters/07-cluster/chapter.md:119）；9.3「副本 I/O 线程把事件写入 relay log 并落盘后即回 ACK，不等本地回放」（chapters/09-data-sync/chapter.md:157）；图 9-5 图内标「回 ACK 给主（已写 relay log 并落盘）」（fig-9-5.svg:71）；另有 7.3 开头「半同步等待指定数量的副本将日志接收并刷盘」（ch7:100）与图 7-1「副本日志落盘确认」——共五处同口径。
- **读者主张**：半同步 ACK 实际只要求事件 write 到 relay log，是否 fsync 由 sync_relay_log 另行控制；「落盘」措辞过强。

**语境核实（读者成立，高）**：读者对两处原文均为逐字准确转述，非断章取义。完整语境没有任何限定词能消解质疑：sync_relay_log 在全书 chapters/ 目录 grep 零出现；紧邻的「适用边界」段只谈超时降级与故障转移选副本，不触及 ACK 落盘强度；「事务暂时停留在 relay log 中，并不等于已经丢失」反而预设了 relay log 内容是持久的。反向佐证：本书对 Redis（9.2「返回确认也不等于副本已落盘」）和 Kafka（7.4.1「收到确认不等于每条消息都已在各副本上执行 fsync」、9.4 同口径）都做了 fsync 免责限定，且 7.1 自立标准「确认的是收到、落盘还是应用，也必须分清」——按书内自身词汇体系，「落盘」被用作 fsync 级持久档，唯独 MySQL 半同步把它写成肯定的 ACK 条件。读者「两处同查」的提醒准确（实际五处）。

**事实核实（两票均读者成立，高）**：MySQL 8.0 源码（本书基线）：sql/binlog.cc 的 after_write_to_relay_log() 调 flush_and_sync(false)→sync_binlog_file(false)，fsync 仅当 force 或 ++sync_counter>=sync_period 时执行；sql/rpl_rli.cc 把 sync_period 挂到 sync_relay_log（sql/sys_vars.cc 默认 10000）；sql/rpl_replica.cc 的 queue_event（write+条件 sync）返回后才 RUN_HOOK(binlog_relay_io, after_queue_event)，源码留着未实现的注释「XXX: 'synced' should be updated by queue_event to indicate whether event has been synced to disk」、synced 恒为 false；plugin/semisync/semisync_replica_plugin.cc 的 slaveReply() 仅凭主端 kPacketFlagSync 请求标志即发 ACK，不看任何 sync 状态。官方手册 §17.4.2「written to its relay log and flushed to disk」的 flush 是 write() 而非 fsync；MariaDB 文档明说「Writing is not the same as syncing……默认每 10,000 个事件才同步一次 relay log……副本会丢掉主节点已计为安全复制的事件」。结论：副本整机掉电（OS 页缓存丢失）时已 ACK 事务可丢；mysqld 进程级崩溃则不丢（write 已离开用户态缓冲）。版本口径属 (b)：5.5–8.0 一贯如此，对基线 8.0 书也错。读者仅一处可微调：代码在 ACK 前确实做了 flush（write 系统调用）而非仅写内存缓冲，但读者的「（write）」括注本就是这个意思。

**综合结论与建议改法方向**：三票一致，读者成立，书需修。把五处「落盘/刷盘」改为「写入 relay log 文件后即回 ACK」，并在 9.3 半同步节补一句边界——是否 fsync 由副本 sync_relay_log 控制（默认 10000 个事件才同步一次），默认配置下副本整机掉电仍可能丢失已 ACK 事务（sync_relay_log=1 才确认即持久）；这与书对 Redis/Kafka 的 fsync 免责限定及 7.1 自立标准保持同一口径。两章正文加两张图必须一次改齐。

### V02 acks 语义边界与表 4-3 归类（4.4/4.5/4.6、7.4.2/7.4.3、9.1/9.4、表 4-3）

- **质疑内容**：表 4-3 把 acks 列入 Kafka「持久化机制」格，与正文「acks 不能与本地刷盘档位等同」自相矛盾/诱导误读；且 min.insync.replicas=1 时 ISR 收缩至只剩 Leader、acks=all 退化为 acks=1 这一组合陷阱全书未点破。
- **书中原文关键句**：表 4-3 该格「OS 异步刷盘 + 生产者 acks + 副本」（ch4:246）；4.4「控制的是写入确认，不能与 appendfsync、innodb_flush_log_at_trx_commit 的本地刷盘档位等同」（ch4:218）；4.5「Kafka 默认依赖 OS 刷盘、本地可能丢但靠副本兜底」（ch4:254）；4.6 启示三「等待当前 ISR 中的全部副本确认……不等于每条消息都已落盘」（ch4:286）。
- **读者主张**：一半指表格与正文矛盾；一半指 min.insync.replicas 默认 1、Leader-only 时 all 等价 acks=1，书「没讲透」。

**语境核实（部分成立，高）**：三位读者转述全部准确；退化组合经 grep 全书（第 1/4/5/7/9/10 章所有 min.insync 出现处）确认无一处点破，9.4 只给了 RF=3/min=2/all 正例——「没讲透」属实。但「自相矛盾」的定性被完整语境部分消解：书的一贯口径是把「副本+acks」当作与本地刷盘并列的另一环节的不丢兜底（4.7「不丢数据的兜底是副本机制（acks=all 配合 min.insync.replicas）而不是本地 fsync」、第 5 章、第 10 章同口径），表格用「+」并列三个组件并未断言「acks=落盘」，正文反对的是把 acks 三档与刷盘档位一一对应，表格没做这种对应；且「all 不等于绝对不丢」书里已用条件句反复讲过（7.4.3「在至少一个同步副本持续存活……的条件下，已提交消息才有相应的保留保证」），缺的只是 min=1 这个具体边界组合。更接近读者自己说的「诱导误读」的呈现/分层问题（同行另两格均为纯本地机制且无脚注分层），而非逻辑矛盾。

**事实核实（两票均部分成立，高）**：读者技术事实全部正确——min.insync.replicas 默认 1（官方文档默认值），follower 落后超 replica.lag.time.max.ms（默认 30s）被移出 ISR 后，ISR 可收缩到只剩 Leader，此时 acks=all 实际只等 Leader 确认，确认范围与 acks=1 相同；官方对 acks=all 的保证本就是条件式（"will not be lost as long as at least one in-sync replica remains alive"）。但「自相矛盾」不成立：Kafka 官方文档自己就把 acks+min.insync.replicas 描述为 "durability guarantees" 并推荐 RF=3+min=2+acks=all，把「acks+副本」列入持久化行与官方口径一致；表 4-3 格内已用「+」分列本地刷盘与复制兜底，4.5 紧接表格有「本地可能丢但靠副本兜底」自洽收口。三列不对称（Redis/MySQL 列只列本地机制、仅 Kafka 列混入复制）确实会削弱正文刚划清的界限，编排性批评有道理。版本口径：基线 Kafka 3.9 下上述语义全部适用，不属 (a)(b)(c) 任一硬错误，属完整性/呈现层改进。

**综合结论与建议改法方向**：三票均部分成立。表 4-3 该格拆两层写（本地：OS 异步刷盘；跨节点：acks+副本兜底），并在 9.4 acks 节补一句 min.insync.replicas 默认 1、ISR 收缩到 Leader-only 时 acks=all 等价 acks=1。

### V03 protected-mode 生效条件与官方文档口径冲突（第 6 章）

- **质疑内容**：书说 7.0 保护模式判定「是否绑定全部网卡不是条件」，与 redis.io 官方文档口径冲突且未给出处；加固建议跨版本给出会误导 6.x 读者。
- **书中原文关键句**：6.3「在 Redis 7.0 的实现中，保护模式开启且 default 用户带有 nopass 标记时，会拒绝非本地连接，是否绑定全部网卡不是这一判断的条件」（ch6:112）。
- **读者主张**：官方文档写的是「默认配置（绑定全部网卡）且无密码」才触发，书与之对不上；且 6.x 里显式 bind 会使保护模式失效，检查 bind 一条在加固清单里的去留随版本相反。

**语境核实（读者成立，高）**：读者逐字引对，其质疑是书与 redis.io 官方文档口径冲突且未给出处，而非否认 7.0 源码行为（读者 051 核源码后还确认书对 7.0 的描述是对的）。全章 grep 确认「绑定网卡」仅此一处、此前零铺垫（否定句悬空，「本地」也无定义）；全章无一处交代 6.x 差异，该句还自引「3.2.0 起引入」打开历史维度却止于 7.0。书内五处 protected-mode 表述口径一致，读者所指「两个口径」确为书 vs 官方文档，非书内自相矛盾。唯一可辩语境是表 6-1 表头标「Redis（7.x）」提供版本坐标系，但不足以消解「加固建议跨版本给出、6.x 读者会误判」的核心质疑。

**事实核实（fact1 书无误/高；fact2 部分成立/高）——两票核心一致：书对 7.x 完全正确**。7.0 源码 src/networking.c clientAcceptHandler（约 L1247）条件仅为 server.protected_mode && DefaultUser->flags & USER_FLAG_NOPASS，再判非本地（Unix socket 与对端 127.0.0.1/::1 之外），无任何 bind 条件；7.2/7.4/8.0 同口径（connIsLocal 变体）。7.0 官方 Release Notes（#9034）明说「Modifying the bind parameter to a non-default value will no longer implicitly disable protected-mode」；随发的 7.x redis.conf 注释与书完全同口径。读者与书「对不上」的 redis.io 在线 security 页至今保留 3.2–6.x 旧措辞（"binding all the interfaces"），是官方文档滞后，不是书写错；读者拿它反推书错属过度引申。但读者两点辅助主张事实成立：其一，6.2 及更早源码同一检查多一项 server.bindaddr_count == 0，显式 bind（哪怕 bind 0.0.0.0）会让保护模式整体失效、nopass 远程连接放行，两个版本下「检查 bind」在加固清单里去留确实相反；其二，书的反直觉结论没给出处，读者无从裁决信任哪边。fact2 判此带 (c) 成分：线上大量 6.x 存量读者按书会误判自己仍受保护。

**综合结论与建议改法方向**：视角分歧（语境=读者成立；事实=书对 7.x 无误）。维持原结论不动，补一句版本边界与出处——「6.2 及更早版本此判定还要求未显式 bind，显式 bind 后保护模式整体失效；7.0 起（Release Notes #9034）移除该条件」，可同时化解出处诉求与 6.x 误保风险；并建议把否定式改写为正向判定（protected-mode 开 + default 用户 nopass + 对端非 127.0.0.1/::1 非 Unix socket 即拒绝；注意 7.0 的「本地」严格只认 loopback，容器网桥 IP 不算）。

### V04 零拷贝被写成无条件属性（2.3.3、图 4-6、8.4）

- **质疑内容**：2.3.3 与图 4-6 把零拷贝写成无条件/全链路属性，TLS 失效与方向（仅消费侧 Fetch）前提缺席。
- **书中原文关键句**：2.3.3「零拷贝让一批消息不进用户态，直接从页缓存送到网卡」（ch2:172）；图 4-6 标题「Kafka 生产-存储-消费的零拷贝数据流」而 SVG 实测只画磁盘→网卡→消费者、无生产写入路径；4.4 图注只限定了 SG-DMA 与 PageCache 命中（ch4:212）。

- **质疑内容**：书说 COMMIT_ORDER「不只限于同一次组提交」，读者认为可并行边界就是同组共享 last_committed、跨组扩大是 WRITESET 独有——书把两机制说混/说反。

**事实核实（两票均书无误，高）**：MySQL 8.0 手册 §19.1.6.4 对 COMMIT_ORDER 的定义与书几乎逐字对应：「Two transactions are considered to be independent if the commit-time window of the first transaction overlaps with the commit-time window of the second transaction……The commit-time window begins immediately following the execution of the last statement of the transaction, and ends immediately before the storage engine commit ends」。源码核实（5.7.22 引入该参数起至 8.0 设计相同）：last_committed 在事务 prepare 阶段（最后一条语句执行完之后）读时钟写入，时钟要到 commit 阶段才推进——因此前一组还在 sync/commit 阶段时 prepare 的后一组事务读到旧时钟、会与前一组共享 last_committed；并行边界确实是「提交窗口重叠」而非组提交成员资格；反过来同组事务也不必然共享 last_committed。读者「同组共享 last_committed 才可并行」对应的是 logical clock v1（仅 5.7.2–5.7.5，hackmysql 专文明确记载 5.7.6 的 v2（WL#7165）已打破组提交耦合，8.0 沿用），属过时口径/经验简化；读者天天看到同组事务 last_committed 相同的现象仍成立（同组窗口必然重叠），错在「才可并行」这个唯一性推断。WRITESET 的真正增量（源码 commit_parent = std::min(last_parent, commit_parent) 把 parent 压低）是让提交窗口完全不重叠、仅写集不冲突的事务也能并行，书中「WRITESET 还可以扩大可并行范围」的分工表述正确。版本口径属 (a)：书对基线 8.0.x 正确，读者以更旧口径批评。

**综合结论与建议改法方向**：视角分歧（语境=转述准确；事实=书无误）。无需修改；若想消除实践读者的疑虑，可选加半句「低并发时窗口重叠的事务基本就是同一次组提交的成员」。另注：该变量 8.0.35 起弃用、8.4 移除（已由 Q15 单独覆盖，非本项）。

### V19 RDB 300–500MB 归因疑点（第 8 章 RDB 段）

- **质疑内容**：书把 RDB 磁盘远小于内存单一归给「紧凑二进制编码（变长整数+LZF）」，漏掉内存元数据开销这个大头；LZF 有阈值，短字符串根本不触发。
- **书中原文关键句**：8.1.3 关键数字框「Redis RDB 压缩比：1GB 内存实例（字符串/列表型负载，典型场景）≈ 300–500MB 快照。紧凑二进制编码（变长整数 + LZF）使磁盘文件远小于内存实际占用，恢复时快速加载」；8.2.2 沿「紧凑二进制路线」展开。
- **读者主张**：大头是每键值对内存态结构开销（dictEntry/robj/SDS 头/分配器对齐）不落盘；LZF 对短字符串不生效。

**语境核实（读者成立，高）**：框标题即自称「压缩比」，归因句括注明写「变长整数+LZF」，归因范围就限定在编码/压缩手段上，读者转述准确无断章。8.2.2 整节没有一处提到内存侧每键值对的 dictEntry/robj/sds 头/分配器对齐不落盘；第 5 章讲 robj 与 jemalloc 只作架构抽象，从未与 RDB 尺寸记账连线；框内限定词「字符串/列表型负载、典型场景」限定的是数字的适用范围，不是归因。最接近的 8.2.2「不是把整个内存对象原样写入文件」讲的是编码衔接和兼容路径，并非尺寸归因，消解不了质疑。全书无别处补「内存元数据开销」这一因。

**事实核实（两票均读者成立，高）**：源码 rdb.c：LZF 仅当 rdb_compression 且 len>20 才尝试（注释原话「under 20 bytes it's unable to compress even aaaaaaaaaaaaaaaaaa so skip it」），且 rdbSaveLzfStringObject 要求至少节省 4 字节才采用（outlen=len-4，压不动回退原样存储）；len≤11 字节整数字符串走整数编码。内存侧每顶级键值对固定开销：dictEntry 24B + robj 16B（type/encoding/lru:24/refcount/ptr）+ SDS 头 1–5B + jemalloc 尺寸类取整——官方 Memory optimization 文档实测 10 万个净荷约 15B 的小键占 11MB（约 110B/键），redis/redis issue #10802 逐项列出同口径；而 RDB 每条只写 1 字节类型码+键+净荷，这部分开销完全不落盘——典型小值负载（缓存/会话/计数）下这是内存-磁盘差的大头，变长整数每个长度字段只省 1–3 字节、LZF 对短值不触发，解释不了 500–700MB 的差距。需保留的平衡：值到 KB 级以上的文本负载中 LZF 确实转为大头，300–500MB 数值本身量级不差（读者也未质疑该数）。属 (b)：dictEntry/robj 结构与 LZF 阈值在基线 7.x 全程如此（Valkey 8.0 才把 dictEntry 每条省 8B），非版本口径差异。

**综合结论与建议改法方向**：三票一致，读者成立，书需修。数字框补归因修正：主因「内存态每键 66–110B 的 dictEntry/robj/SDS/对齐开销不落盘（小键值负载下占内存大头）」，次因「变长编码与 LZF（仅对 >20 字节且能省 ≥4 字节的值生效）」；框题「RDB 压缩比」宜改为「内存/磁盘占用比」之类口径，300–500MB 数字本身作为典型场景估算可保留。
