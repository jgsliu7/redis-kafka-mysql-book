### Q1【P0|4人共鸣|覆盖4条原始意见】表 4-1"相对内存"列延迟/吞吐两种口径混用，参照数缺失且"NVMe 接近内存带宽"的结论随口径翻转
- 定位：4.1 表 4-1（"相对内存（延迟以内存为 1）"列、顺序写吞吐行、"高代际 NVMe 已进入内存带宽的一个数量级以内"句）；关联 4.4"内存随机读单线程约几百 MB/s"

### Q2【P0|3人共鸣|覆盖3条原始意见】启示三把 everysec / trx_commit=2 / acks=1 并列"中间档"：与 4.4"不能等同"的告诫自相矛盾，且三者丢失语义不同质
- 定位：4.6 启示三（对照 4.4 acks 相关段落）
- 摘要：4.4 刚强调 acks 不能与本地刷盘档位一一对应，启示三又对称推荐"各自的中间档"；且 everysec/2 丢的是有界的约 1 秒时间窗，acks=1 丢不丢取决于 Leader 故障这个随机事件（无界），丢失粒度不同质；trx_commit=2 只防进程崩溃，掉电/内核崩溃照样丢约 1 秒。三者并列会被读成风险等级相当，读者拿错误风险模型评估。
- 代表意见：「前一段刚强调"不能把这些档位按'每条都落盘'到'交给 OS'一一对应"，下一段又对称地推荐"很多时候答案是各自的中间档：everysec / MySQL 2 / acks=1"。但前两者的代价是丢"最近约 1 秒"（有界时间窗），acks=1 在 Leader 故障时丢的是所有尚未复制的消息（无界，取决于复制延迟），丢失粒度不同质，三者并列成"各自的中间档"容易被读成风险等级相当。」（读者119·GPU农场）
- 其他提出者：读者118·Mongo叔（"2 只防 MySQL 进程崩溃，掉电/内核崩溃照样丢约 1 秒已提交事务……这一段至少应标明 2 的保护边界，否则读者会当成三家的等价三选一"）、读者120·HiFi爷（"把'按时间丢'和'按故障丢'并列，读者会拿错误的风险模型去评估"）

### Q3【P0|2人共鸣|覆盖2条原始意见】表 4-3/4.5 MySQL 崩溃恢复漏了 undo 回滚未提交事务阶段，"重放 redo log 较快"口径不严谨
- 定位：4.5 表 4-3（MySQL 栏"重放 redo log + 恢复脏页"）、4.5 正文"重放较快"（对照第 8 章 8.7）
- 摘要：崩溃恢复的第二阶段——undo 反向回滚未提交事务（大事务回滚以小时计并不罕见，开 binlog 后还有内部 XA 恢复判定）——全章未出现；"恢复脏页"措辞也别扭（崩溃后内存脏页已没了，redo 重做的是磁盘页）；"重放较快"与 8.7 按 checkpoint 之后日志量重放的口径不一致。对做容量规划的人有误导。
- 代表意见：「表 4-3 崩溃恢复代价 MySQL 一栏只写"重放 redo log + 恢复脏页"，漏了恢复的第二阶段：undo 回滚未提交事务。Oracle 的 crash recovery 前滚 + 回滚两阶段是我们吃饭的常识，InnoDB 大事务崩溃后的后台回滚同样可能拖几个小时；且"恢复脏页"这个说法也别扭——崩溃后内存脏页已经没了，redo 重做的是磁盘页。」（读者116·Oracle老）
- 其他提出者：读者117·PG酱（"崩溃时未提交的大事务要靠 undo 反向回滚，这一步可以远慢于 redo 重放（大事务回滚以小时计并不罕见），开 binlog 后还有内部 XA 的恢复判定。'MySQL 恢复快'的印象对做容量规划的人是有误导的"）

### Q7【P0|1人共鸣|覆盖1条原始意见】双写缓冲段把"physiological redo 救不了撕裂页"表述成 redo log 通则，读者会带走错误的一般化结论
- 定位：4.3 双写缓冲段（"redo log 也救不回来，因为它记录的是'怎么改这个页'，前提是这个页本来是好的"）
- 摘要：这是 InnoDB 无整页镜像的 physiological redo 的性质，不是 redo 通则；PG 的 WAL 开 full_page_writes 后把整页镜像写进 WAL，恰能从"页写到一半"的损坏中恢复。不点明前提，读者会以为所有 redo/WAL 都救不了撕裂页。
- 代表意见：「这是 InnoDB physiological redo 的性质，却被表述成 redo log 的通则。PG 的 WAL 开启 full_page_writes 后，checkpoint 后首次修改某页会把整页镜像写进 WAL，恰好就能从"页写到一半"的损坏中恢复。不点明"没有整页镜像的 redo 才救不了撕裂页"，读者会带走一个错误的一般化结论。」（读者117·PG酱）
- 其他提出者：无

### Q9【P1|1人共鸣|覆盖1条原始意见】4.3 LRU 新老分区写成 InnoDB 自己的改良，不点 Oracle midpoint insertion + touch 计数的谱系出处

### Q11【P1|1人共鸣|覆盖1条原始意见】4.4"双份缓存"被当作不言自明的坏处，没有论证代价是什么（PG 双份缓存是官方推荐姿势）

- 摘要：PostgreSQL 长期跑在 shared_buffers + OS PageCache 双份缓存上且是官方推荐姿势（shared_buffers 通常约 25% 内存），双份缓存本身是可以成立的取舍；书里把重复当不言自明的坏处，推理不闭环。
- 代表意见：「"为什么不做自己的缓冲池"的第二条理由只说"自己管内存会和 PageCache 形成双份缓存"，把重复当成了不言自明的坏处，没有论证代价是什么。PostgreSQL 就是长期跑在 shared_buffers + OS PageCache 双份缓存上，而且是官方推荐姿势（shared_buffers 通常只给约 25% 内存）——同一份数据确实占两处，但换来的是 OS cache 的灵活调度。双份缓存本身是可以成立的取舍，书里的推理在懂 PG 的读者这里不闭环。」（读者117·PG酱）

### Q15【P1|1人共鸣|覆盖1条原始意见】4.3 change buffer 的 merge 只写了被动路径，漏了后台主动 merge
