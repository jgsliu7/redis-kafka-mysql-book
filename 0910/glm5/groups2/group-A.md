## 问题簇（按严重度 P0→P1→P2、再按共鸣人数降序）

### Q1【P0|3人共鸣|覆盖3条原始意见】物理/逻辑日志口径前后自我矛盾，二分框架被 redo 混合形态打破
- 定位：1.2.2（redo log 括注）与 1.3.3（第三层追问「日志记什么」）
- 摘要：1.3.3 先立「逻辑/物理」二分尺子（物理=「记哪个字节改成什么样」），紧接着承认 MySQL redo 是「物理到页、逻辑到操作的混合日志」；1.2.2 又先把 redo log 括注为「记录物理修改」。读者指出三家没有一家是这把尺子上纯粹的例子，二分刚建立即作废；且「哪个字节」把物理日志粒度说绝了，InnoDB 是页级不是字节级。合上书不知道该记哪个定义。
- 代表意见：「这一节先发给我一把尺子：日志分『记做了什么操作（逻辑）』和『记哪个字节改成什么样（物理）』两类，紧接着又说 MySQL redo『严格说是物理到页、逻辑到操作的混合日志』。结果是三家谁都不是纯粹的那把『物理』尺子上的例子——Redis 是逻辑，Kafka 根本不重放，MySQL 是混合。刚建立的二分立刻作废，我没明白这个分类到底想让我理解什么。」（读者102·数花）
- 其他提出者：读者101·药匣子（1.2.2「记录物理修改」与 1.3.3「严格说是混合」相隔十来页，「术语首次定调就该给准确口径……不等于第 1 章可以先给一个会自我否定的简化版」）、读者105·COBOL叔（「二分框架在自家例子里就破了，且『哪个字节』把物理日志的粒度说绝了，InnoDB 这类页级日志并不记到字节」）

### Q2【P0|3人共鸣|覆盖3条原始意见】三范式「尽力而为/可重建」归类与分布式锁、库存等「快而准」场景冲突，框架边界未交代
- 定位：1.1.1（三类范式对持久化要求的定性）波及 1.2.1（Redis 角色清单）
- 摘要：1.1.1 把缓存/计数/锁类能力归入「对持久化的要求往往是尽力而为或可重建」，但三位读者各自用一手事故经验指出：分布式锁一旦因丢数据失效，破坏的是互斥性本身，无法靠事后重建兜住；库存计数是「既要快又要准」的混合场景（Redis 原子扣减 + MySQL 正本，主从切换丢写即超卖）。框架在「快而准」混合场景上的边界在哪、正本归谁，第 1 章立框架时未交代，读者会带着错误印象往下读。
- 代表意见：「锁恰恰是语义一旦被破坏（主从切换丢锁、过期误删）并发保护就失效的场景。我维护过并发原语库，深知锁语义和『尽力而为』不兼容——这里不提跨范式借用的风险（Redlock 争论正出在此），读者会以为一把 SET NX 就有了锁。」（读者103·Go布道）
- 其他提出者：读者101·药匣子（「锁一旦因丢数据而失效，破坏的是互斥性本身，不是事后『重建』能兜住的……我们 HIS 里两个护士站并发改同一份医嘱就靠这把锁，丢一次就是双写事故」）、读者104·大促守护（「大促预扣用 Redis 原子扣减、正本在 MySQL，Redis 主从切换丢写引发的超卖就是这类组合方案的经典事故……读者容易带着『快桶里的数据都可以尽力而为』的印象往下读」）

### Q3【P0|2人共鸣|覆盖2条原始意见】表 1-1/图 1-1 MySQL「可舍弃：写性能」与正文口径矛盾，会导出「MySQL 写入很慢」的错误结论
- 定位：1.2.4 表 1-1、图 1-1 对照 1.1.3（代价清单）与 1.2.2（提交延迟）
- 摘要：表 1-1 和图 1-1 把 MySQL 的可舍弃项压成「写性能」三个字，与 1.1.3 的「写放大、事务开销和调优门槛」、1.2.2 的「提交延迟」口径不一致。两位读者均以亲身压测/灌数经验指出：批量提交下 InnoDB 写吞吐并不差，MySQL 舍的是「每次提交都刷盘的那种写延迟」而非泛化的写性能，压缩表述会误导转行读者。
- 代表意见：「我拿 pandas 往 MySQL 批量灌过几百万行（to_sql / LOAD DATA），单机每秒几万行毫无压力——MySQL 舍的不是『写性能』，是『每次提交都刷盘的那种写延迟』。压成三个字，转行的读者会得出『MySQL 写入很慢』的错误结论。」（读者102·数花）

### Q9【P1|3人共鸣|覆盖3条原始意见】1.2.2 提交刷盘句主语混乱、近同义反复且无参数名，三位读者各读各地卡住
- 定位：1.2.2（事务提交等待日志落盘句）
