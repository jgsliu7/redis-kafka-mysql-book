### Q1【P0|3人共鸣|覆盖3条原始意见】定盘事故两次讲述不一致：kill -9 归因、AOF 配置、丢失量级均未说清
- 定位：本章导读 × 3.6 复盘（111、115）；导读「通常只丢一小段」句（112）
- 摘要：导读以「敲下 kill -9 丢数据」定盘，3.6 复盘却说「没等 AOF 刷完就杀了进程」。111 与 115 指出这是两种不同的故障注入（SIGKILL 无从刷 AOF vs 优雅关闭中途被打断），且两次讲述都没交代 AOF 开没开、刷盘策略是什么，丢失窗口因此差几个量级；112 另从出厂默认（AOF 关闭、save 3600 1）指出「丢一小段时间」对 RDB-only 默认部署是危险低估。三人合读：教训到底是「别用 kill -9」还是「该配 AOF」，因果链不闭合。
- 代表意见：「导读说事故是「敲下 kill -9」丢了数据，结尾复盘却说「没等 AOF 刷完就杀了进程」「问题出在我没给它落盘的时间」。kill -9 是 SIGKILL，Redis 根本没有任何机会刷 AOF，不存在「给它时间」的问题；「没等 AOF 刷完」描述的更像是优雅关闭进行到一半被补刀强杀。」（读者111·混沌猴）
- 其他提出者：
  - 读者115·车站哥：「做事故复盘时这两个参数决定丢失窗口差几个量级（everysec 最多丢一两秒，纯 RDB 丢的是上次快照以来的全部），因果链不闭合，我判断不出教训到底是「别用 kill -9」还是「该配 AOF」。」
  - 读者112·容量姐：「出厂默认是 AOF 关闭、save 规则最长 3600 秒才落一次盘（save 3600 1 300 100 60 10000），我压测过的 RDB-only 实例被 kill -9 后丢满一小时写入并不罕见。……「一小段」这个开篇印象对默认部署是危险的低估。」

### Q2【P0|3人共鸣|覆盖3条原始意见】3.2「存不存数据由用户显式指定」与 SIGTERM 默认路径相互矛盾
- 定位：3.2「关闭：两种触发，一套流程」+ 图 3-3 侧栏 ↔ 3.4 容器化（默认行为迟到补充）
- 摘要：3.2 说「存不存数据」由用户通过 SHUTDOWN SAVE/NOSAVE 显式指定（图 3-3 侧栏同口径），但运维最常见的 SIGTERM / systemctl stop / K8s 滚动重启路径带不了任何参数，落不落盘实际由 save 配置默认决定——这一事实要到 3.4 才间接补出。三人从不同岗位（混沌演练注入预期、物联网网关 systemd 部署、维护窗口评估）同指：单读 3.2 会误判信号关闭的落盘行为与停机时间。
- 代表意见：「SIGTERM 路径带不了任何参数，落不落盘实际由 save 配置决定（3.4 才补上"只要配了 save 点、出厂默认就配"就会在退出前全量落盘）。我们网关上的 Redis 全走 systemd stop，发版窗口没人能发 SHUTDOWN NOSAVE，那"由用户决定"的决定权到底在哪个入口？3.2 的框架与 3.4 的现实没接上，单读 3.2 会误以为信号关闭能秒退。」（读者114·物联网）
- 其他提出者：
  - 读者111·混沌猴：「此时到底走 SAVE 还是 NOSAVE，本节没有交代……「由用户显式指定」的说法与默认行为相互矛盾。混沌平台注入 SIGTERM 前最需要的就是这个预期：注入后 Redis 会不会先做一次同步全量 SAVE。」
  - 读者115·车站哥：「照 3.2 的正文和图 3-3 读，我会误以为 SIGTERM 重启不触发全量 RDB 落盘，从而低估大实例在维护窗口里的停机时间。」

### Q8【P1|2人共鸣|覆盖2条原始意见】kill -9 与断电的破坏面差异／介质断电原子性前提未点破
- 定位：3.3 图 3-4 前提与全章 kill -9 用法（111）；3.4 追加写日志「CRC 截尾」段（114）
- 摘要：全章用 kill -9 贯穿但从未区分进程级故障（OS page cache 还在、文件不会半写）与节点级断电（缓冲一并丢失、可能 torn page），而这正是图 3-4「redo 无差别重放」与 Kafka「CRC 截尾不存在中间状态」能成立的前提；114 进一步指出 SD/eMMC 断电时 FTL 映射表回滚、丢的常不是尾部，单副本边缘部署上「截尾恢复语义依赖介质断电原子性」这层假设并不自动成立。
- 代表意见：「从未区分 kill -9（进程级故障：OS page cache 还在，文件不会半写）与断电（节点级故障：OS 缓冲一并丢失，可能产生 torn page）的破坏面差异。而这正是图 3-4「redo 无差别重放」能成立的前提——物理重放要求页本身完整，InnoDB doublewrite 就是为这个边界存在的；不点破这条边界，读者会误以为 kill -9 也能造成物理页损坏。」（读者111·混沌猴）
- 其他提出者：
  - 读者114·物联网：「SD/eMMC 突然断电时 FTL 映射表回滚，丢的常常不是尾部而是更早的块，CRC 截尾救不了这种洞；网关现场跑单副本 Kafka/Redis 时这个前提并不自动成立，建议点明「截尾恢复语义依赖介质断电原子性」这层假设。」

### Q15【P1|1人共鸣|覆盖1条原始意见】「redo log 里未落盘的修改」指代歧义：应为 checkpoint 之后的积压
