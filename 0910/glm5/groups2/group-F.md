### Q1【P0|3人共鸣|覆盖3条原始意见】TDE/存储加密的威胁模型只画了一半：密钥与密文同盘击穿「磁盘被盗也无法读取」承诺，且对在线查询/导出全程透明
- 定位：6.4 存储加密（对照 6.1 威胁模型）、表 6-1
- 摘要：6.1 给存储加密立的威胁模型是「磁盘被盗也无法直接读取」，但 6.4 推荐的社区版 `keyring_file` 密钥文件与密文同盘存放，整盘被盗时两者一起到手，恰好击穿该承诺，且书未提这两个组件官方定位是「仅供开发测试」；另有一面是 TDE 对所有走 SQL 进程的正常查询透明，DBA 直查、备份导出、SQL 注入拿到的都是明文，敏感字段的合规加密必须靠应用层落地。读者指出威胁模型只画了「密钥丢失致不可读」这一半。
- 代表意见：「6.1 给存储加密立的威胁模型是"磁盘被盗也无法直接读取"，6.4 又说社区版可用本地文件型 `keyring_file`——密钥文件和密文在同一台机器的磁盘上，整盘被盗时两者一起到手，恰好击穿 6.1 立的模型。书里只提醒了"密钥丢失导致数据不可读"这一半，没提密钥与密文同盘共址这一半（MySQL 文档自己也声明 keyring_file 不适用于合规场景）。」（读者128·公链喵）
- 其他提出者：130·气象站（keyring_file 官方定位「仅供开发测试、不建议生产」没提；「我在树莓派上琢磨 SD 卡被拔的场景，这个缺口一眼就看到了」）；129·保险嫂（TDE 对正常查询透明，「身份证、银行卡号这类字段的加密要求（个保法/密评）必须靠应用层加密或脱敏落地，TDE 单独过不了检查——威胁模型只画了一半」）。

### Q2【P0|2人共鸣|覆盖2条原始意见】Redis ACL「命令维度」解释与示例对不上：按命令名授权的 alice 规则被「命令类别」表述讲矛盾，一命令多类别的求值语义未点破
- 定位：6.2 alice 规则示例、6.3 授权检查解释与图 6-3
- 摘要：6.2 给 alice 的规则用 `+get +set`（按命令名授权），6.3 图 6-3 的解释却说检查「命令类别（GET 属于 @read）和键模式两个维度」——规则里根本没有 `+@read`，照书的解释 GET 应被拒，示例与解释直接冲突；另一面，FLUSHALL 同属 @keyspace/@write/@slow/@dangerous 四个类别，ACL 判定是「任一已授类别命中即放行」，书只归因于 @dangerous 会让人形成「一命令一类别」的错误心智模型，配了 +@keyspace 或 +@slow 的用户照样能 FLUSHALL，`-@dangerous` 防不住。
- 代表意见：「6.2 给 alice 的规则是 `ACL SETUSER alice on >pwd ~keys:* +get +set`（按命令名授权），但 6.3 图 6-3 的解释说授权检查「分别检查命令类别（GET 属于 @read）和键模式两个维度，两项都命中才放行」——alice 的规则里根本没有 `+@read`，照这个二维检查逻辑 GET 应该被拒才对。……书把「命令维度」统一说成「命令类别」，示例和解释对不上，我在这停了五分钟。」（读者130·气象站）
- 其他提出者：127·合约审（「FLUSHALL 同时属于 @keyspace/@write/@slow/@dangerous 四个类别，ACL 的判定是"任一已授类别命中即放行、规则按书写顺序求值"。这层语义不点破，读者会形成"一命令一类别"的心智模型」）。

### Q3【P0|2人共鸣|覆盖2条原始意见】客户端拦截器补审计补不上最需要的一块：看不到 Broker 端 ACL 拒绝事件，审计点放在被审计方进程里也不满足审计与被审计分离
- 定位：6.5 Kafka 审计「外挂补全手段」段
- 摘要：书把 ProducerInterceptor/ConsumerInterceptor 写审计主题列为生产环境的补全手段，但客户端拦截器只能看到客户端自己发出/收到的消息，Broker 端被 ACL 拒绝的请求根本不经过它——恰是同段承认 Authorizer 日志默认级别覆盖不到的部分；从内控合规看，审计点放在被审计方自己的客户端进程里、可被不加载或改写，审计主题同集群也可被动，按「审计与被审计分离」原则不能算合规审计。
- 代表意见：「客户端拦截器只能看到客户端自己发出/收到的消息——Broker 端被 ACL 拒绝的请求根本不经过它，而"谁被拒了"恰是同段承认 Authorizer 日志在默认级别下覆盖不到的部分。拿客户端拦截器补审计，补不上的正是最需要审计的那一块。」（读者128·公链喵）
- 其他提出者：129·保险嫂（「审计点放在被审计方自己的客户端进程里，被审计者完全可以不加载拦截器或改写逻辑……按内控"审计与被审计分离"的原则这不能算合规审计。希望作者说明这个方案的适用边界……或把 Ranger/服务端方案作为主推荐」）。

### Q4【P0|2人共鸣|覆盖2条原始意见】三家凭证存储的安全属性交代不完整：「不存明文」对 requirepass 存量部署不成立，MySQL/Kafka 的盐与迭代未交代导致表 6-1 三家并列不可比
- 定位：6.2 凭证存储段、表 6-1「凭证存储」行
- 摘要：「密码以 SHA-256 摘要形式保存，不存明文」只对 ACL 用户密码成立，走 `requirepass` 的存量部署密码明文躺在 redis.conf 里（CONFIG REWRITE 按明文回写、CONFIG GET 可回显），这句话会让人把 Redis 静态凭证的暴露面估小；同时只有 Redis 被点了「无盐、不迭代」的风险，caching_sha2_password 的加盐 5000 轮迭代、SCRAM 自带盐和迭代轮数都没交代，读者最想知道的「凭证库被拖走后离线猜解成本差几个数量级」只有一半答案。
- 代表意见：「"凭证存储上，密码以 SHA-256 摘要形式保存，不存明文"只对 ACL 用户密码成立；走 `requirepass` 的存量部署密码是明文躺在 redis.conf 里（CONFIG REWRITE 也按明文回写），`CONFIG GET requirepass` 还能直接回显。做入侵复盘我第一步就是 cat 配置文件，这句话会让人把 Redis 静态凭证的暴露面估小。」（读者126·逆向仔）
- 其他提出者：127·合约审（「caching_sha2_password 存的是加盐、5000 轮迭代的 SHA-256（`$A$005$` 格式），SCRAM 凭证自带盐和迭代轮数。于是表 6-1"凭证存储"一行三家并列却不可比」）。

### Q5【P0|2人共鸣|覆盖2条原始意见】Redis ACL LOG 的取证价值刻画不准：「不含命令参数」断言过强（reason=key 时键名入日志），而更要害的「证据不存活」（128 条环形缓冲、重启即清、可被挤出）未点破
- 定位：6.5 Redis 审计（ACL LOG 描述与「弱」的评价）
- 摘要：书说 ACL LOG「不含命令参数」说得过强——官方文档里键模式越权（reason=key）时被拒的键名会写进 object 字段，而键名正是命令参数，对做轻量取证的人「能否看到越权者试图摸哪个键」是关键差别；另一面，评 Redis 审计「弱」没点到最要害一层：ACL LOG 是默认 128 条（acllog-max-len）的内存环形缓冲，重启即清空，攻击者灌几百条被拒命令就能把入侵痕迹挤出缓冲——「弱」弱在证据不存活，比覆盖不全更严重。
- 代表意见：「官方文档里 object 字段记录的是"用户试图访问而无权访问的资源"，键模式越权（reason=key）时被拒的键名会写进日志，而键名正是命令参数。对拿 ACL LOG 做轻量取证的人，"能否看到越权者试图摸哪个键"是关键差别。」（读者127·合约审）
- 其他提出者：126·逆向仔（「ACL LOG 是默认 128 条（acllog-max-len）的内存环形缓冲，重启即清空，攻击者自己灌几百条被拒命令就能把入侵痕迹从缓冲里挤出去。真到取证时它多半已经不在了——"弱"弱在证据不存活，这比"覆盖不全"严重」）。
