# 读者134 · DNS大爷
身份：DNS/LVS 工程师，18年，爱好：抖空竹
主读：第 7 章

## 五个问题
1. 【7.2.3|深度广度】导读的库存事故说少数派老主"超时窗口内还在接写"，7.2.3 只给了 cluster-node-timeout 默认 15 秒一个数。从分区发生到少数派真正停写、再到多数派一侧新主就位，这个窗口由哪几个超时叠加、最坏多少秒，书里没算账——我写容灾预案时这个数就是 RPO，不能只有"超时窗口"四个字。
2. 【7.4.1|读不懂】"在本章的 3.9 基线中，默认逻辑向一个分区累计发送至少 batch.size 字节后再切换"——3.9 指什么？本章前文没有任何交代（是 Kafka 3.9 版本基线？还是某节的 3.9？），我在这一句上直接卡住，只能靠猜。
3. 【7.1|表达可读】CAP 段"它不是'数据是否落盘'，也不能直接换算成产品的快慢排序"——"快慢排序"是谁按快慢给谁排座次？一句话连着两个否定，我读了三遍也没拼出这句要排除的到底是哪种误解。
4. 【7.2.2|逻辑论证】"通常部署 3 个或更多，奇数个便于投票"太含糊：判客观下线的 quorum 是人工配置的票数，跟奇偶无关，真正要多数派的是 Leader Sentinel 选举。我管 VRRP/keepalived 时"偶数防的是平票脑裂"，但 Sentinel 选举是 Raft-like、有任期和随机超时，平票自己能解开——那"奇数便于投票"到底防什么没说清，而偶数部署实际只是白养一台机器，容错能力一点没涨。
5. 【7.3.3|深度广度】容错公式 ⌊(N-1)/2⌋ 只算到节点数，没落到机房维度：双机房对等部署（4 成员 2+2）时任一机房整体故障只剩 2 票、凑不够多数派，整组直接停摆——这是同城双活里最常见的部署形态，公式在这用不上，书里也没提醒故障域要跨机房打散。

## 五个建议
1. 【7.5|案例示例】建议加"故障域与副本放置"一小节（或并入启示一）：MGR 多数派要 3 个机房才容得下 1 个机房故障；Redis Cluster 主从得手工跨机房打散（它本身没有机架感知）；Kafka 有 broker.rack 做机架/机房感知分配。做容灾的人第一问就是"挂一个机房剩几票"，这一维全书缺位。
2. 【导读|深度广度】把库存事故补成一条时间线：分区发生 → 少数派停写（约一两个 cluster-node-timeout）→ FAIL 判定 + 从节点选举授权 → 新主就位，窗口多长、窗口内的写就是 RPO；最好给 MGR、Kafka 同口径的"故障到恢复"量级对比（文字或在图 7-5 加耗时标注），容灾评审张口就是 RTO/RPO。
3. 【7.3.5|深度广度】补 MySQL Router 感知新主的机制与延迟来源（metadata 缓存与探测间隔），并点破切换时刻在途连接必须应用自己报错重连——Router 不像 LVS+conntrackd 能同步连接表；顺带在表 7-1 加一行"路由决策在哪一层"：Redis 在客户端映射表加重定向、MySQL 在集中式 Router、Kafka 在生产者自算分区，这是做流量调度的人最想看的对比。
4. 【7.3.2|术语使用】半同步段落请点名参数和档位：rpl_semi_sync_source_wait_point（旧名 rpl_semi_sync_master_wait_point）的 AFTER_SYNC / AFTER_COMMIT 两档及 8.0 默认档；并提一句 AFTER_COMMIT 档下其他会话可能在发起者收到 ACK 前就已读到这笔数据。正文只写"默认等待点下"，想落地的读者对不上旋钮。
5. 【7.2.2|案例示例】补 Sentinel 的部署拓扑：Sentinel 放在哪一侧（与客户端同机房、别和数据节点同机架同路径），防止检测路径与数据路径一起断造成误判或漏判；顺带点名 down-after-milliseconds 和 failover-timeout 这两个决定切换时间与转移冷却的大头参数。
