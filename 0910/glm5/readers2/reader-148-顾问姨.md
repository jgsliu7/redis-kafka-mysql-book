# 读者148 · 顾问姨
身份：独立技术顾问，15年，爱好：马术
主读：第 10 章 + 全书结构（序言/后记/抽读导读）

## 五个问题
1. 【序言 / 10.4.1 表10-2｜结构导航】序言承诺第三层是"周期、成本、团队状况、遗留系统、公司硬性约束"下的组合决策，但第 10 章把它落成 12 问（表 10-2）时全是技术维度（数据/性能/可靠性/运维），没有一问涉及团队运维能力、预算与上线死线。我给 CIO 做选型时，组织约束往往先于技术约束把选项筛掉一半——承诺与交付对不上。
2. 【10.3.3 练习三｜逻辑论证】"到瓶颈真的出现时再切，切的时候按第 7 章集群架构的演进路径逐级升级"——第 7 章图 7-1 给 MySQL 的演进是异步→半同步→MGR，那是复制与容错的路线，不含容量分片；MySQL 生态也没有 Redis Cluster 槽迁移式的原生分片，"逐级升到分库分表"这条路在书里和现实里都不存在。
3. 【10.4.1 表10-2 运维行｜逻辑论证】"扩容是否停机"一行，Redis 答 Cluster 在线 reshard、Kafka 答"加 Broker 可在线"，都是容量扩容；MySQL 答"MGR 在线加成员（全员全量、无数据再均衡）"——MGR 加成员不增加一字节容量，是容错/读扩展，括号里自己都承认"无数据再均衡"。三列答的不是同一个问题，拿这张表做 MySQL 容量规划会落空。
4. 【10.2.4 规律四｜深度广度】规律断言"更强的可靠性要付性能代价，先弄清代价再决定"，可同节正文自己举出组提交让多个事务共享刷盘、生产者攒批摊薄确认成本——说明同步代价经常能摊薄到接近无感。缺一个"什么条件下摊得掉、什么条件下摊不掉"的判据，这条规律作为决策工具还差最后一层。
5. 【后记"一个真实的故事"｜案例示例】修复方案"Redis 只做预扣减的前置层，吸收大部分扣减请求，账只认 MySQL"被讲得近乎零代价，但做过交易系统的人都知道前置预扣的坑在对账与回补：下单未支付怎么释放预扣、Redis 与 MySQL 的差额怎么监控、前置层故障时直查 MySQL 的降级路径。全书立场是每个方案都有代价，作者复盘自己的修复方案时却没按同一标准披露代价。

## 五个建议
1. 【10.4.1 表10-2｜深度广度】12 问增加一组"组织与治理"问题：RPO/RTO 由谁签字拍板、团队是否养得起所选组件（MGR 与 KRaft 的运维门槛差别很大）、预算与上线窗口约束。现在只有 RPO 行提了半句"谁能拍板"，把序言第三层的承诺补进表里才算闭环。
2. 【10.3.3 练习三｜案例示例】如实改写 MySQL 的容量演进：先垂直扩、再读写分离，真到分片要靠中间件/应用层，且单机到分片是一次性迁移（双写、回填、切流），不是逐级演进；建议给三五行迁移要点，别让"到瓶颈再切"的建议把读者撂在切换那天。
3. 【10.1 表10-1｜结构导航】第 1 章行的启示"范式互补才有研究价值，差异越大共性越容易看出来"讲的是本书选样本的方法论，与第 2-9 章各行的机制性启示不同质。建议改成机制表述或移作表注，让九行启示同一语义层级，这张总表才配得上被读者复印贴墙。
4. 【7.1 关键数字 / 1.1.2｜深度广度】我读到的部分里只有 Kafka 有吞吐量级锚点（1.1.2 的 LinkedIn 3 台机约 200 万写/秒，7.1 又说"分区容量要按负载实测"），Redis/MySQL 没有对应数字。建议在"关键数字"框各补一个保守的规划区间（如 Redis 单实例十万级 QPS、MySQL 单机数千到数万 TPS 视负载、Kafka 单分区 MB/s 级）——CIO 的第一版容量预算就靠这种量级锚点。
5. 【10.2.5 规律五｜表达可读】"为每个状态预先写定恢复路径；能写出来才算可控"很好，但"写出来"缺个抓手。建议附一个最小状态登记模板（状态×进入条件×恢复动作×谁执行×上次演练时间），并取第 7 章 Sentinel 的 SDOWN→ODOWN→故障转移链示范填一行，把口号变成读者可直接照抄的表格。
