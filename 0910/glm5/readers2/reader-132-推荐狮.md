# 读者132 · 推荐狮
身份：推荐系统工程师，8年，爱好：麻将
主读：第 7 章

## 五个问题

1. 【7.2.3|技术事实】「按约 100 个主节点平均分配，16384 个槽能让每个主节点分到约 160 个槽」与本章关键数字框「官方建议的最大规模约为 1000 个节点」两套基准并存。antirez 当年解释 16384 的著名答复（Redis GitHub issue #2576）是按 1000 节点、每主约 16 个槽粒度已够来论证的；7.2.3 改用 100 主节点/每主 160 槽来支撑「两边都过得去」，来源存疑且与本章另一处口径不一，到底按哪个基准论证？

2. 【7.2.3|逻辑论证】哈希标签一段只讲收益不讲代价：`{user:1001}` 把同一实体的全部 key 压进同一个槽，等于亲手制造热点。我们做特征存储时，大V画像、爆款 item 特征这类 key 本来就是读写大户，hash tag 一上，倾斜直接落到单个节点上；7.1 说「哈希分片分布均匀」，可均匀的前提是访问均匀——推荐场景恰恰不均匀，这段论证只取了一面。

3. 【7.4.1|版本时效】书里说「在本章的 3.9 基线中，默认逻辑向一个分区累计发送至少 batch.size 字节后再切换」。我印象中 Kafka 3.3 起 KIP-794 对无 key 粘性分区做过改进：不再等攒满一个 batch 才切换，而是每个发送周期就轮换分区以获得更均匀的分布；若如此，3.9 基线下这句描述的是 2.4–3.2 时代的行为，请核实。

4. 【第7章导读|读不懂】「刚扣减的库存在网络恢复后被新主的数据覆盖了」的时间线我没读顺：多数侧在分区期间就完成了选主，那批写在选主完成时就已不在集群视图里，「网络恢复后覆盖」只是老主以副本身份被新主全量重同步的物理过程。数据「什么时候算丢了」这个复盘定责的关键时点，案例没点明。

5. 【7.4.1|结构导航】「在本章的 3.9 基线中」这个说法首次出现且无解释：第 7 章小节全是 7.x，我第一反应是去找第 3 章的 3.9 节（并不存在），猜了半天才知道指的应该是 Kafka 3.9 版本基线（第 1 章约定的？）。单章阅读不自足，读者会在这里卡壳。

## 五个建议

1. 【7.5|深度广度】横向对比缺「热点倾斜」维度：表 7-1 六个维度都隐含流量均匀的假设，而 7.1 自己也承认「实际效果还取决于热点是否分散」，之后就再没跟进。推荐场景里爆款 item、大V 的 key 天然倾斜——Redis 是单个槽把整节点 QPS 打满，Kafka 是 keyed 路由打满单分区；建议表 7-1 加一行「热点倾斜下的行为与缓解」，或在 7.2.3/7.4.1 各补一个框注（检测看槽/分区级指标，缓解谈本地缓存、热 key 拆分）。

2. 【第7章导读|案例示例】库存事故建议补量化时间线与客户端视角：少数派停写要等 cluster-node-timeout（默认 15 秒）加选主授权，这个窗口乘以大促写量就是丢的库存数。给一条时间轴（分区发生→15s 超时→多数派转移→恢复后覆盖），并说清窗口内客户端看到的是什么错误，读者才能对照自己的重试与对账预算——我们大促复盘最缺的就是这个数。

3. 【7.4.1|案例示例】「扩分区是一次语义迁移」判断很对但太抽象，建议配一个具体业务例：按 user_id 做 key 的行为序列/实时特征，扩分区后同一用户的新事件落到另一个分区，下游按 key 开窗聚合的特征直接算错。做流式特征的人看到这个例子，立刻会回去查自己改分区数的变更流程。

4. 【图7-5|图示】三条故障转移泳道对齐了决策路径，但全程没有时间量级。在线推理的可用性预算是毫秒级，读者最关心的是「这一栏典型停多久」（Redis 从 15s 超时起步、Kafka 由 session/replica.lag 参数决定、MGR 看组检测节奏）；建议每列加一个耗时量级标注，让图从「怎么决策」升级到「决策要多久」。

5. 【7.5|结构导航】表 7-1 建议把「横向扩展能力」拆出读路径、单独加一行「读扩展方式」。高并发读场景（我们在线特征读取是十万级 QPS）第一关切就是读流量能否分摊：Redis 从节点可读但有复制新鲜度问题、MySQL 读从库要接受复制延迟可见性、Kafka 消费者默认只读 Leader；7.5 正文已散着提到（「单纯增加 Follower 不会自动分摊消费者流量」），入表后对比价值更大。
