# 读者106 · 流媒体
身份：视频转码后端，6年，爱好：穿越机
主读：第 2 章

## 五个问题
1. 【2.2.3/2.3.3|深度广度】"批量优先"一路被写成近乎纯收益，2.2.3 的代价清单只有"消费必须按 Batch 边界来、随机点查做不到"，唯独没提延迟：linger.ms 是生产端故意引入的等待，消费端 min_bytes 加 max_wait 再叠一层。我做直播转码时端到端预算按百毫秒管，这两层等待是每天要面对的真实成本——吞吐的对价就是毫秒级延迟，这一条不该从代价清单里缺席。

2. 【2.3.3|技术事实】"零拷贝让一批消息不进用户态，直接从页缓存送到网卡"说得太满：sendfile 只覆盖消费方向的 Fetch 路径，且监听器一开 TLS，加密必须回到用户态做，零拷贝直接失效（Kafka 官方设计文档、Zendesk 的 mTLS 生产记录都写明这一点）。我们生产 Kafka 全走 TLS，读到这句的第一反应是"那我这套集群根本没享受到"，应补上边界条件。

3. 【2.2.2|技术事实】"高并发点查的竞争又集中在它的保护锁上，5.7.8 起拆成 8 个分区"——版本疑似记错：MySQL 5.7 官方文档写明 innodb_adaptive_hash_index_parts 引入于 5.7.2（默认 8、上限 512），不是 5.7.8。

4. 【2.3.3|版本时效】"3.0 的 Broker 可以和 0.11 的客户端对话"是兼容性的好例子，但没交代下限，容易让读者以为"多老的客户端都陪"：Kafka 4.0（2025 年 3 月）已按 KIP-896 首次删除最老一批 API 版本（如 Fetch v0–v3），协议下限抬到约 2.1 时代的客户端。2026 年出版语境下，这句该加个"兼容下限在移动"的注脚。

5. 【2.6|逻辑论证】小结写"MySQL 范围扫描多所以用 B+ 树"，与 2.2.2 的论证换了口径——2.2.2 明明说 MySQL 要的是"通用查询能力"，B+ 树同时覆盖点查/范围/排序。我维护的 MySQL 负载绝大多数是 OLTP 点查，"范围扫描多"这个事实断言立不住；同一因果链章首章尾两个版本，应统一回"通用性"的说法。

## 五个建议
1. 【2.2.3/2.3.3|深度广度】在"批量优先"处正面补一段吞吐-延迟旋钮的讨论：batch.size/linger.ms 与消费端 fetch.min.bytes/fetch.max.wait.ms 就是"把延迟卖给吞吐"的显式参数，最好给一组参考数字。我们把转码事件流的 linger 从默认压到 5ms 以下就是延迟预算逼的——这类抉择正是本书反复主张的"取舍"，缺了可惜。

2. 【2.2.2|表达可读】"一次 I/O 取一页（16KB）""必须对齐磁盘的 16KB 页"整节把默认值写成了物理定律。加一句"16KB 是默认，innodb_page_size 可配 4K–64K"即可，免得读者拿"铁律"去对生产参数时困惑。

3. 【第2章导读与2.6|案例示例】排行榜案例首尾都讲了 MySQL 输在哪，却没讲挪到 ZSET 之后新付出什么：整个榜常驻内存有物理上限、重启恢复时长随榜增长、冷榜照样占内存。补上这一面，开篇故事才把本书自己主张的"取舍"演完整，还能顺手勾连第 4 章的内存话题。

4. 【2.2.3 表2-1|案例示例】建议给表 2-1 加一列"字段为谁服务"：61 字节头部里 producerId/producerEpoch/baseSequence 共 14 字节是无条件存在的，不开幂等/事务的每个 Batch 照样付这笔"演进税"。这比单说"差值编码省开销"更能让读者看见格式演进的真实成本。

5. 【2.3.2|深度广度】MySQL 协议节把"省带宽"全归给二进制结果集，其实协议层的连接压缩（CLIENT_COMPRESS，zlib/zstd）对跨机房场景收益通常远大于行级二进制编码——我们跨 DC 拉结果集时基本靠连接压缩扛带宽，值得一句话带过。
