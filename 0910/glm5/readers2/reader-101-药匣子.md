# 读者101 · 药匣子
身份：.NET 医疗行业开发，9年，爱好：养龟
主读：第 1 章

## 五个问题
1. 【1.4.3|版本时效】版本状态提示写"MySQL 8.0 已于 2026 年 4 月转入 Oracle Sustaining Support"，但按 Oracle 公布的生命周期政策，8.0 在 2026-04 后进入的应是 Extended Support（错误修正支持延续到 2031 年前后），Sustaining 是更晚的阶段。这个差别直接影响选型判断——按书里说法，读者会以为 8.0 连安全补丁都快没了，建议核对 Oracle 官方生命周期表。
2. 【1.1.3|技术事实】说 Redis 的代价是"复杂聚合要靠客户端多次网络往返拼出来"，说得太满：Lua 脚本（EVAL）、pipeline、MULTI/EXEC 都能把多步计算并成一次往返在服务端完成，我在 .NET 里用 StackExchange.Redis 挂 Lua 做过原子扣减。而且 1.4.3 自己还提到 7.x 引入了 Function（函数），前后口径打架；1.2.1 的说法（"把数据拉回应用层处理"）也和这句不完全一致。
3. 【1.2.2|术语使用】1.2.2 括注 redo log"记录物理修改"，翻到 1.3.3 又变成"严格说是物理到页、逻辑到操作的混合日志"，两处相隔十来页，我合上书已经不知道该记哪个定义。术语首次定调就该给准确口径，把"严格说"的修正留给第 8 章，不等于第 1 章可以先给一个会自我否定的简化版。
4. 【1.2.2|表达可读】"在每次提交都刷盘的配置下，事务提交需要等待日志落盘，可通过 fsync 等机制把缓冲的写强制刷到磁盘"——这句读了三遍才猜出主语："可通过 fsync"读起来像给读者的可选项，实际说的是引擎在提交点强制调用 fsync 刷盘。我从 SQL Server 转 MySQL 那两年恰恰被这套提交刷盘配置坑过，初读这句仍分不清"谁在什么时机刷盘"。
5. 【1.1.1|逻辑论证】把分布式锁归进"对持久化的要求往往是'尽力而为'或'可以重建'"一类，我不服：锁一旦因丢数据而失效，破坏的是互斥性本身，不是事后"重建"能兜住的。我们 HIS 里两个护士站并发改同一份医嘱就靠这把锁，丢一次就是双写事故，这个场景对可靠性的要求并不比订单低。

## 五个建议
1. 【1.1.1|案例示例】从 1.1.1 的购物车/库存计数到 1.3.3 的"订单已创建"事件广播，全章案例清一色电商。建议在关键范式处至少并列一个非互联网场景——比如医疗 LIS 的仪器结果批量回传（典型的 Kafka 型异步流转）、医保对账流水（典型的 MySQL 型可靠存储），让被书名吸引进来的跨行业读者也能对号入座。
2. 【1.2.2|深度广度】MVCC 那段（Read View、版本链、RR/RC 生成时机）信息密度很高，但对大量 SQL Server 转 MySQL 的读者，一句跨库对照就能点通：SQL Server 的 RCSI/快照隔离是同一思想，只是版本链放 tempdb、InnoDB 放 undo log。加个脚注成本极低，还能反证本书"同一问题、不同载体"的主线。
3. 【1.2.4 表 1-1|表达可读】"关键取舍/可舍弃"一行三家粒度不一致：Redis 填"内存容量与复杂聚合"（资源+能力），MySQL 只填"写性能"两个字，Kafka 填"低延迟与灵活查询"，且 MySQL 那格与同行"性能取向：延迟让位于一致性"信息重复。建议按 1.1.3 的口径统一成具体代价（如"写放大与事务开销"）。
4. 【1.3.3|结构导航】"每条命令落盘、每秒落盘、还是交给操作系统决定何时刷盘"这三个选项其实就是 Redis appendfsync 的 always/everysec/no，但第 1 章没标出处，只拿 Redis 当缓存、没配过 AOF 的读者对不上号。建议括注一次参数名，这与"详见第 4 章"的留白不冲突。
5. 【1.4.3|版本时效】"Redis Open Source 的 7.2、7.4 分支仍列在官方支持范围内"这句，对没跟过 2024 年许可变更（RSALv2/SSPL，后来 8.0 又加 AGPL）和 Valkey 分叉的读者信息量不足。2026 年做缓存选型绕不开 Valkey（主流云厂商都已提供），建议补一两句来龙去脉，版本基线一节才算对当下选型真正负责。
