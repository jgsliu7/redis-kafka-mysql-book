# 读者103 · Go布道
身份：Go 开源组件作者，8年，爱好：腰旗橄榄球
主读：第 1 章

## 五个问题
1. 【1.2.1|逻辑论证】正文说「一套原语就能支持 Redis 承担缓存、排行榜、消息队列、计数器、分布式锁这些角色」，把分布式锁列为正当角色；但 1.1.1 刚说这类能力「对持久化的要求往往是尽力而为」，而锁恰恰是语义一旦被破坏（主从切换丢锁、过期误删）并发保护就失效的场景。我维护过并发原语库，深知锁语义和「尽力而为」不兼容——这里不提跨范式借用的风险（Redlock 争论正出在此），读者会以为一把 SET NX 就有了锁。

2. 【1.3.2|深度广度】看约束一节把 Redis 单线程的理由归为「免去数据竞争和锁协调」，这只讲了性能面；没点破 1.2.1 里「每条命令都是原子操作」这条承诺正是单线程免费送的红利——所有命令天然线性化，MULTI/EXEC 和 Lua 脚本的原子性全押在这上面。并发模型决定语义保证，这层因果没接上，是本章「架构视角」最该给的一课。

3. 【1.2.4 表 1-1|表达可读】表 1-1 和图 1-1 都写 MySQL「可舍弃：写性能」，与 1.1.3 的代价清单（写放大、事务开销、调优门槛）和 1.2.2 正文（提交延迟、undo 积累、横向扩展难）口径不一致；而且「舍弃写性能」容易被读成 MySQL 写慢是本质属性——批量提交下 InnoDB 写吞吐并不差，我压测过的库裸写能到每秒几十万次插入。

4. 【1.3.1 表 1-2|读不懂】表 1-2「MySQL 日志」行的架构视角问题写着「日志作为数据正本，边界到哪为止？」——按本章语境（1.2.2、1.3.3）redo log/binlog 是恢复与复制的影子，数据正本是 B+ 树页，「日志是数据正本」是 Kafka 那套模型。这行是笔误还是指「能否干脆以日志为正本把页当缓存」（LSM 思路），我复原不出来。

5. 【1.4.3|版本时效】版本状态提示（2026 年 9 月）提到 MySQL 8.0 转 Sustaining、Kafka 4.0 移除 ZooKeeper，却对 Redis 只说「7.2、7.4 分支仍在支持范围」——漏了 Redis 8.x 已发布一年多，以及 2024 年许可证变更引发的 Valkey 分叉还在主流厂商手里演进。对一本教「选型即取舍」的书，许可与生态分叉本身就是约束，做开源组件的人对这个最敏感。

## 五个建议
1. 【1.2.1|深度广度】在「数据结构服务器」处补一小段「抽象的边界」：Stream 的 consumer group、XACK 与 Redis Function 已经超出「结构上的一次原子操作」，是消息队列与过程式语义混进了数据结构抽象。语言设计的经验是好抽象的标志不是能加多少而是拒绝加什么——这正是第 2 章前最好的引子。

2. 【1.3.3|图示】第三层追问「日志记的到底是什么」目前用三段文字叙述，对比力道弱于前两问；建议改成三行小表：Redis AOF / MySQL redo+binlog / Kafka 日志即数据，各一行「记什么、恢复时做什么、要不要重放器」。Kafka 那行「不需要重放器、日志本身就是数据」是三者最深的一道分水岭，值得从段落里提出来单列。

3. 【1.4.3|版本时效】版本状态提示补两句话：Redis 8.x 已发布（含许可回归 AGPL 一事），2024 年许可证变更后 Valkey 成为 Linux 基金会下的替代实现。读者学到的是 Redis 的设计，部署时却可能要在发行版之间做选择——这本身就是一次现成的「取舍」案例。

4. 【1.2.2|深度广度】三段概览粒度不齐：MySQL 一节深到「Read View 生成时机与隔离级别的关系、沿版本链从新到旧找可见版本」，而 Redis 节对 RDB/AOF 只有一句、Kafka 节对 ISR 也只到半层。建议把 Read View 时机这类实现级细节后移到第 9 章，第 1 章三节保持同一海拔，读者节奏会稳很多。

5. 【1.1.2|案例示例】「3 台廉价机约 200 万次写入/秒（0.8.1、2014）」标了出处很好，但建议补一句今天的量级感（NVMe 加万兆网卡下单机顺序写能到什么数量级），否则读者拿 2014 年的基准去对标现役集群会低估一个量级——我的库每次被人拿五年前的 benchmark 数字问「为什么达不到」都要重讲一遍。
