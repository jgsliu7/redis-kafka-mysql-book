## 五个问题

1. 【8.3.2|读不懂】"回滚段则管理 undo log（回滚日志）所用的多个表空间段，两者不是同一级概念"——这句我读了三遍仍无法确定"两者"指谁（索引段与回滚段？undo 表空间与段？），且按我的理解层级应是 undo 表空间 → 回滚段 → undo log，这句的从属关系像是写反了。请拆成两句，把层级和指代分别写明。

2. 【8.1.1|逻辑论证】本节末说"第 5 章讲过分层思想是软件应对复杂性的通用手段，本章把这套思想用到了磁盘上那一层字节"，但本章实际的骨架是"格式即契约 + 四个矛盾"，"分层"这条线此后再没出现（8.4.6 引的是第 5 章另一句"可替换"）。开头挂靠一个后文不兑现的框架，读者会白等一场。

3. 【8.1.3|表达可读】"关键数字"框里"V0 单条消息固定开销约 14 字节、V1 约 22 字节，均不含最外层 12 字节消息框，同口径计入外框为 26/34 字节"——一个括号塞进版本×口径的四重映射，读者得自己算 14+12=26、22+12=34 再对应回 V0/V1，而且此时还没讲过消息框长什么样（布局在 2.2.3 表 2-1 与 8.4.3）。读起来像内部勘误注记，不像面向读者的正文。

4. 【8.1.3|技术事实】"Redis RDB 压缩比：1GB 内存实例（字符串/列表型负载，典型场景）≈ 300–500MB 快照"没有出处和测量条件，却与 16KB、61 字节这类可查证常数并排放在同一"关键数字"框里同等权威地呈现；归因也存疑——对字符串负载，文件远小于内存的主因是去掉了 dict/sds 等内存对象开销，"变长整数 + LZF"只是次因。这个数字我不敢转引。

5. 【8.6.5|术语使用】"把向前兼容想清楚再谈别的"把"向前兼容"当承重术语用，但全书没定义哪个方向是向前、哪个是向后——8.1.1 只把两种场景并列举例，没贴标签。中文技术圈这两个词的映射恰好是分裂的，我只能靠导读的报错例子反推作者用"旧代码读新格式＝向前兼容"这套约定，读到 8.6.5 时停顿了一次。

## 五个建议

1. 【8.2.3–8.2.4|结构导航】图 8-3（讲 7.0 之前的双缓冲重写）排在 7.0 manifest 机制之后，且其后那段叙述（管道传增量→子进程追加→父进程补写→rename）与 8.2.3 末段几乎逐句重复。建议把图 8-3 连同这段收进 8.2.3（"7.0 起的替代方案见下节"之前），8.2.4 从 4.0 混合格式直接接到 7.0 manifest，时间线一遍走完，重复也消掉。

2. 【8.4.3|结构导航】本章是"磁盘存储格式"专章，但 RecordBatch 的字段布局整体外放到 2.2.3 表 2-1，正文列了字段名却没给宽度，"61 字节"这个数字在本章无法就地核对。做 API 文档的原则是 schema 跟着讨论走：建议在 8.4.3 加一行紧凑字节条（baseOffset 8B｜batchLength 4B｜……），完整细节仍留表 2-1。

3. 【8.1.1|术语使用】在 8.1.1 首次并举两种兼容场景时加一行明示约定，例如"旧代码读新格式＝向前兼容；新代码读旧格式＝向后兼容"。成本一句话，导读与 8.6.5 两处承重用法就都有了锚。

4. 【8.4.5|表达可读】表 8-1 已是三代格式的对照主场，建议增加一行"单条固定开销"（V0≈14B／V1≈22B／V2 批头 61B），把"关键数字"框里那串括号收编进表——数字进了结构化表格，框里只留一句结论，问题 3 的密度问题随之化解。

5. 【图8-1/8-3/8-7|图示】三张图都是"图题一句 + 紧跟一段'这张图……'的复述"：图 8-7 的段落（拆成三步：追加／上传／清理）几乎就是把图题展开一遍。建议图题只管自含的结论性一句话，正文段落只讲图传达不了的动态、例外与代价，删去互相重复的部分。
