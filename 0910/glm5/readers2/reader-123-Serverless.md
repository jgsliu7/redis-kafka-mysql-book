# 读者123 · Serverless

身份：FaaS 平台研发，5年，爱好：独轮车
主读：第 5 章

## 五个问题

1. 【5.2.1|逻辑论证】「一旦放开并发，要么大面积加锁……这一句话也解释了为什么 7.x 默认仍然关闭多线程 I/O」——因果错位。多线程 I/O 只拆走 read/write 系统调用和大块 buffer 拷贝，命令执行仍在主线程，从头到尾没碰那个「单线程修改」的内存模型；它默认关闭（io-threads=1）的真实原因是收益场景有限，官方 redis.conf 注释明说小流量下开线程反而更慢。我拆冷启动路径时也把协议解包挪到别的线程，理由恰恰是它不碰执行状态——所以这个论证说服不了我。

2. 【5.2.1|技术事实】客户端输出缓冲区「超限就强制关闭连接」把机制砍掉了一半。`client-output-buffer-limit` 实际是 hard limit（超了立即断）加 soft limit（持续 N 秒才断）两档，如 replica 256mb 64mb 60。软限是给慢客户端留收敛窗口、硬限才杀连接——这正是背压设计的精髓，我们给函数实例的输出缓冲同样分两档。写成一刀切，读者会以为 Redis 对慢消费者没有任何缓冲余地。

3. 【5.5|逻辑论证】表 5-1「核心抽象」一行里，Redis 填 robj、Kafka 填追加日志，都是机制/接口层的抽象，唯独 MySQL 填「关系表 + 索引」——这是数据模型，不是抽象边界；而 5.6 启示二又明确说 MySQL 最成功的抽象是 Handler API。同一章两张口径打架，读到启示二时我得自己脑内换算一次。

4. 【5.4.4|结构导航】本章主线是三段式，5.4 把 Kafka 扩成「交互+API+存储+协调」四段，5.5 图 5-7 又压回三段、把 ReplicaManager/Controller 塞进「主要环节与接口」一格，Redis Cluster 槽路由和 MGR 投票只一句「也属于类似的关注点」带过。我读到 5.4.4 停了很久：三段式到底是不是普适框架？既然分布式协调是普遍的第四种关注点，为什么只有 Kafka 单列一节、另外两个折进接口行？

5. 【5.4.3|版本时效】「3.9 起 Tiered Storage 正式 GA」疑与官方口径不符：Apache Kafka 3.9 的升级文档仍把它标为 early access（3.6 引入的 EA 状态延续），官方叙事里转正是 4.x 线上的事，4.0 发布的头条 GA 是 KIP-848 新消费者协议。第三方厂商（Instaclustr）在 3.9 托管平台上自行宣布 GA，可能是这个说法的来源。

## 五个建议

1. 【5.6|深度广度】导读那句「分层能做多薄，就看一件事：这次抽象带来的延迟，你愿不愿意付」是极好的杠杆，但整章的延迟账只有定性没有量级。做冷启动的人最清楚：分层决策的真功夫是把每层开销写成预算表（协议解析、命令分派、handler 虚函数各占多少微秒，p99 怎么摊）。建议在 5.6 补一小段三个软件单请求跨层开销的量级对照，哪怕只是数量级估计，这句金句才算兑现。

2. 【5.5|图示】建议表 5-1 加一行「会话上下文对象」：Redis 的 client、MySQL 的 THD、Kafka 的 RequestChannel.Request。5.2.2 说 client「与 MySQL 的 THD 是同一种思路」，这是全章我最喜欢的观察，但这个最精彩的类比没落进对比表，Kafka 那一格还空着。补齐后「用贯穿对象替代层层传参」这个手法三种形态才算集齐——我们 FaaS 的 invocation context 也是同一手法，网关、调度器、实例全程一个对象。

3. 【5.6 启示四|案例示例】三种反模式（镜像分层、空洞透传、循环依赖）每条只有一句话，读者很难对号入座。以我评审分层方案的经验，「镜像分层」最典型的病灶是三层函数签名一模一样、IDE 自动生成的 Service→Manager→Dao 转发链；建议每条配一个 3-4 行的最小调用链示意，读者一眼就能认出自己项目里那层该删的代码。

4. 【5.2.1|深度广度】RESP 只讲了 RESP2 的五种前缀，6.0 同一版本引入的 RESP3（push 类型、客户端缓存 tracking 的失效广播）一字未提——而这恰好是「交互层演进、逻辑层不动」的活案例：服务端主动推送只改协议层语义，命令执行层照旧。5.2.1 既然专门讲了 6.0 的多线程 I/O，同一个 6.0 的另一半协议演进缺席，有点可惜。

5. 【5.4.1|深度广度】RequestChannel 背压只讲了「队列满→Processor 阻塞」收益的一半，没讲代价的一半：一个 Processor 管一批连接，队列满时这批连接的读写全部停摆，一条慢 FETCH 会放大成同批无辜连接的队头阻塞；Kafka 后续把等待中的请求挂进 purgatory 摘出业务线程，正是给这个粗粒度背压打补丁。背压点选在哪层、粒度多粗的连带伤害，是本章背压讨论缺的另一半，建议补上。
