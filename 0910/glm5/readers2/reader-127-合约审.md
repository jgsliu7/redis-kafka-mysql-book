# 读者127 · 合约审
身份：智能合约审计，4年，爱好：德州扑克
主读：第 6 章

## 五个问题

1. 【6.2|深度广度】6.2 只给 Redis 一家点了"无盐、不迭代的裸 SHA-256 有字典攻击和彩虹表风险"，另外两家的凭证落盘却没交代：caching_sha2_password 存的是加盐、5000 轮迭代的 SHA-256（`$A$005$` 格式），SCRAM 凭证自带盐和迭代轮数。于是表 6-1"凭证存储"一行三家并列却不可比——我读完最想知道的"凭证库被拖走后离线猜解成本差几个数量级"，书里只有一半答案。

2. 【6.5|技术事实】"ACL LOG（记录被拒命令的详情，包括时间戳、客户端 IP、被拒命令，不含命令参数）"说得过强：官方文档里 object 字段记录的是"用户试图访问而无权访问的资源"，键模式越权（reason=key）时被拒的键名会写进日志，而键名正是命令参数。对拿 ACL LOG 做轻量取证的人，"能否看到越权者试图摸哪个键"是关键差别。

3. 【6.3|深度广度】正文与图 6-3 把 FLUSHALL 被拒归因为"属于 @dangerous，alice 的规则里没有授予"，但 FLUSHALL 同时属于 @keyspace/@write/@slow/@dangerous 四个类别，ACL 的判定是"任一已授类别命中即放行、规则按书写顺序求值"。这层语义不点破，读者会形成"一命令一类别"的心智模型——配了 +@keyspace 或 +@slow 的用户照样能 FLUSHALL，`-@dangerous` 防不住它。

4. 【6.7|逻辑论证】启示二"我评审一套系统的安全设计，先数它有几层：只押一层的方案，无论多厚，我都打回"——层数是个可以被刷高的弱指标：同质冗余堆十层并不扩大覆盖，我做合约审计见过十几道权限检查全挤在同一个入口、绕一次全绕的设计。该数的是互异失效模式的覆盖（网络、身份、加密、留痕各拦不同路径），筹码堆得高不代表牌力强。

5. 【6.2|读不懂】"Kafka 3.5.0 也加入了 Broker 到 Controller 的 SCRAM 支持；这与 Controller 之间的共识连接不是同一条路径。后者在 3.5.1、3.6.0 曾出现用 SCRAM 启动集群失败的问题"——这段密度失控：两条链路此前没有任何铺垫，"后者"指代要回读两遍，版本号堆叠又无出处。我自己查了 KIP-900（`--add-scram` 写入 bootstrap.checkpoint）和 KAFKA-15513 才拼出全貌：凭证存在元数据日志里，而形成 Raft 共识又要先互认证的循环依赖。

## 五个建议

1. 【6.6|深度广度】把表 6-1"凭证存储"行扩成三列小对比：Redis 无盐 SHA-256（靠口令熵硬扛）vs MySQL caching_sha2（盐+5000 轮迭代）vs Kafka SCRAM（盐+迭代轮数），各配一句"拖库后离线猜解成本与口令策略"。这是三家安全对比里最值得横向拉平的一维，也是攻击面评审必问的第一条。

2. 【6.2|案例示例】把"未授权 Redis 写 SSH 公钥、写定时任务导致 RCE"从一句话展开成具体链条（CONFIG SET dir/dbfilename → SET 写入公钥 → SAVE，变体是 SLAVEOF+MODULE LOAD），并对照二维 ACL 逐项标注：真正切断链条的是命令类别维（CONFIG/MODULE 都在 @admin+@dangerous），键模式维其实挡不住（SET 是普通写命令）。攻击面思维要的是权限模型与攻击链的对位关系，不只是"历史上出过事"。

3. 【6.4|深度广度】社区版 keyring_file 的密钥文件与数据同机存放，防"磁盘整盘被盗"但防不了"主机失陷后直接读密钥文件"——建议补一句企业版接 Vault/KMS 的本质是密钥与数据分离加托管轮换，否则读者容易以为社区版 TDE 与企业版能力等价。

4. 【6.5|深度广度】"审计在生产级部署中几乎总是外挂的"之后建议补两级证据强度：客户端侧 ProducerInterceptor 写审计主题可被绕过（攻击者不必走你的 producer），服务端 Authorizer 日志/Ranger 这类统一管控层才是抗抵赖的取证点。事后追责时这两类日志的可信度完全不同，选型依据就在这。

5. 【6.2|表达可读】KRaft SCRAM 启动段补出处编号（KIP-900、KAFKA-15513），并用半句话点破循环依赖——"凭证写在元数据日志里，而形成共识要先通过认证"——或把版本细节下沉为脚注，正文只留结论"控制面认证优先采用双向 TLS"。
