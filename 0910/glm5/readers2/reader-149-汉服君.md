# 读者149 · 汉服君
身份：汉服爱好者后端程序员，5年，爱好：汉服
主读：第 10 章 + 全书结构（序言/后记/抽读第2、5章导读）

## 五个问题
1. 【10.2.1 规律一|读不懂】规律一在 Kafka（分区日志）上明说了正本在哪，MySQL 也点了"数据页与已持久化 redo"，唯独 Redis 段只说"内存键空间是运行时处理命令的依据"、RDB/AOF 是恢复材料，绕开了"Redis 自己的正本到底是内存还是 AOF"这一问。读到后记库存事故"正本由 MySQL 承担"我才反应过来：正本之争发生在业务系统层面，而非常驻在软件内部——这个从"软件内哪份数据"到"系统里哪个组件"的视角切换，书里没点破。名分不明，读者就得自己补这层推演。

2. 【第5章 导读/5.2.1|逻辑论证】导读断言"分层能做多薄，就看一件事：这次抽象带来的延迟，你愿不愿意付"，但 5.1 自己立的三个验收指标里有"可替换性"，5.2.1 结尾也承认 Redis 薄分层的代价是"没法独立演进、不可能像换 MySQL 引擎那样换掉网络层"——那分明是可替换性的账，不是延迟的账。"就看一件事"这句口号被本章自己的论述推翻了。

3. 【2.2.1 SDS|技术事实】"网络层读客户端命令缓冲（querybuf）的大参数是个例外：走 sdsMakeRoomForNonGreedy 按需扩容"——我印象里 Redis 恰好相反：超过 32KB（PROTO_BIG_ARG）的 bulk 参数是直接读进 argv 元素的独立缓冲、绕开 querybuf 的，非贪婪扩容用的正是那条旁路。括号里注成 querybuf，是不是把"例外发生在哪个缓冲区"注反了？

4. 【10.3.2 图10-2|逻辑论证】10.3.1 立了五个权衡维度，图 10-2 和正文却只问四个问题，第五个"通用 vs 专用"既没进图，也没说明为什么被排除（是不好落成提问，还是选型时最不重要？）。五减成一没有任何交代，我翻回去数了两遍确认不是自己看漏。

5. 【后记·一个真实的故事|表达可读】"网络恢复后，这部分写入被新主的数据覆盖了，库存多卖了"——两句之间压着一整段因果：被覆盖丢掉的恰是那批扣减，扣减丢了库存才虚高，库存虚高才多卖。复盘如修史，中间环节省了，读者只能自己脑补；补半句"丢掉的正是已确认的扣减"就顺了。

## 五个建议
1. 【第10章/10.5 与序言|结构导航】序言以"术/道"立论（先辈方案是术、条件受限时的设计思路是道），第 10 章五条规律分明就是那个"道"，但 10.5 只回收了"三个层次"。建议在 10.5 或后记用一句话点破"九章机制是术、五条规律是道"，让开篇的立意在结尾有着落——首尾对上，全书才算织完一整匹。

2. 【第10章/10.4.1 表10-2|案例示例】12 问 checklist 的"你的答案"列现在只有提示语，建议附一份填好的示范——就用后记那个库存系统把 12 问各答一遍。图样比口诀传得快：读者照着一份填好的表模仿，比对着提示语空想要快得多。

3. 【第10章/10.2.3 或 10.3.3|案例示例】第 2 章开篇的排行榜是全书最好的案例（改分、查名次两难倒逼换结构），但第 10 章收束时它再没出场，10.4.2 只剩"跳表、B+树"两个名词。建议在 10.2.3（顺序与批量）或 10.3.3 练习里用半句回收它——压轴该让最经典的形制再登一次台。

4. 【第10章/10.2.4 与 10.3.1 维度一|深度广度】可靠性代价全书停在定性（"有代价"），没有一个数量级锚点。建议给一两组典型参考（如 appendfsync always 与 everysec 的吞吐差、双 1 与双 0 在 SSD 上的提交延迟差距），注明随硬件浮动即可。10.4.3 的实验设计很好，但读者动手前需要一个预期值，否则观察到数字也无从判断正不正常。

5. 【第10章/10.3.2 图10-2|图示】图 10-2 的八个叶子框都落到了具体设计（"MySQL 双1、Kafka acks=all"），但没有一处标章节号，无法顺图翻回对应章。建议在叶子框加"→第4章/第7章"式回链，并补上维度五的处理（入图，或在图注交代为何不入），让这张图兼作全书的导航总图。
