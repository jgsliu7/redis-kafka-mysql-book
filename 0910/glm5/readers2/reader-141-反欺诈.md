# 读者141 · 反欺诈
身份：反欺诈系统工程师，9年，爱好：威士忌
主读：第 9 章

## 五个问题
1. 【9.2|技术事实】全量同步第 1 步写"Redis 7.0 默认启用 `repl-diskless-sync`"，与我升级 Redis 集群时的记忆不符：7.0 里该参数默认仍是 no，默认改为 yes 是 7.4/8.0 时代的事。默认值归属错一版，会直接误导读者判断"今天的实例默认走有盘还是无盘"。
2. 【9.3|技术事实】半同步一节说"副本 I/O 线程把事件写入 relay log 并落盘后即回 ACK"，图 9-5 里也标注"已写 relay log 并落盘"——relay log 的真实刷盘由 `sync_relay_log`（默认 10000）控制，半同步 ACK 并不等每个事件 fsync。在我们这行，ACK 的含义就是数据丢失边界的定义，"落盘"二字给出的持久性保证过强。
3. 【9.4|版本时效】"并行处理时后一条先完成，不能越过前面还没处理完的记录去提交，否则重启后那条消息会被直接跳过"——这在 2.4 之前成立，但 2.4 起（KIP-447）客户端已支持乱序提交，提交历史会被保留、回退提交会被校验，不会"直接跳过"。作者顺序处理再提交的保守结论我认同，但机制描述不加版本限定，会让读者以为乱序提交在今天的客户端上仍是禁区。
4. 【9.4|逻辑论证】"宁可写失败让业务立刻感知，也不要超时后静默降级"把 MySQL 的降级预设成"静默"，可 9.3 刚强调 MySQL 把降级次数与状态暴露成可观测变量、要求配告警。半同步+告警+人工介入在 7×24 交易风控链路里同样是正当解（写失败等于交易被拒，也是真金白银的损失），这个对比对 MySQL 不太公平。
5. 【9.7|深度广度】导读抛出"缓存和数据库不一致时该以谁为准、怎么对齐"，9.7 只用一句"数据库是正本、缓存是可重建的派生数据"收束。以我排查过的缓存不一致案例，"以谁为准"从来不是难点，难点是删缓存失败、并发写窗口下怎么收敛（重试+过期兜底）——导读把期待拉满，结尾只兑现了一句定性结论。

## 五个建议
1. 【9.4|深度广度】"不同分区之间并没有由 offset 建立的统一顺序"点了跨分区无全序，但没说另一半：同一业务实体要有顺序，必须靠生产者按 key 路由到同一分区。对拿 Kafka 做实时事件流（特征计算、交易流回放）的读者这是第一条要立的规矩，建议在"传播单元"小节补两三句 key→分区的映射与顺序边界。
2. 【9.4|案例示例】幂等一节"它不负责识别应用重新发送的相同业务内容，也不保证消费处理只执行一次"点到即止。建议补半页消费端业务幂等的落地案例（交易号做唯一键/去重表，rebalance 与重启导致的重复消费是常态）——重复消费在风控里意味着重复计分、重复拦截，这段是全书离我最近的一节，恰恰在最痛的地方停了笔。
3. 【9.3|图示】图 9-5 一张图同时承担异步链路、半同步 ACK 等待、GTID 补发三条线索，中部的 binlog 数据流连线还要斜穿两条泳道。建议拆成两张：一张讲收流/回放两段式链路，一张专讲半同步 ACK 的两档时点（AFTER_SYNC 与 AFTER_COMMIT 正好做对比），GTID 并入 GTID 小节。
4. 【9.1|案例示例】"关键数字"框的三条都是系统参数默认值，建议再加一个把参数翻译成业务预算的对照：半同步超时默认 10 秒，对下单链路意味着客户端早已超时、降级几乎必然发生——反过来提醒读者"默认值不是设计值，要按业务等待预算改"。这也与 9.6 启示四呼应，提前到 9.1 给读者量级感。
5. 【9.2|表达可读】"WAIT 是对已发出写入追加的确认等待"建议补一句返回值语义：超时后返回的是当前实际确认数（可能小于 N 甚至为 0），客户端不检查返回值等于没等。我们封装 WAIT 时第一件事就是强制校验返回值，这个坑值得一句话点破。
