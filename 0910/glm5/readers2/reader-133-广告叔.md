# 读者133 · 广告叔
身份：广告 RTB 系统开发，11年，爱好：斗蛐蛐
主读：第 7 章

## 五个问题

1. 【7.4.1|结构导航】「没有 key 时，Kafka 2.4 经 KIP-480 引入默认粘性分区；在本章的 3.9 基线中……」——读到「3.9 基线」我第一反应是找 3.9 小节，本章根本没有。它应该指本书的 Kafka 3.9 版本基线，但本章内无交代；第 9 章「3.9 的 Tiered Storage 已可用于生产」同样是光秃的版本号。写法统一成「Kafka 3.9 版本基线」并在首次出现处说明，否则必然有读者当成小节引用。

2. 【7.1|读不懂】CAP 段末句「它不是『数据是否落盘』，也不能直接换算成产品的快慢排序」，后半句我没读懂：一致性怎么「换算成快慢排序」？是说三个软件不能按一致性强弱排出一条全序，还是说一致性与响应速度不挂钩？这句压缩得太狠，含义接不住，希望展开或删掉。

3. 【7.4.2|深度广度】「慢副本移出后，不再需要等待它确认；但移出前仍可能拖慢写入」——缺量级。副本被剔出 ISR 要等 `replica.lag.time.max.ms`，默认 30 秒（第 9 章关键数字框给了这个数，本章没用上），等于一个 GC 抖动的 follower 能把 `acks=all` 的尾延迟拖到几十秒量级才被踢出去。做毫秒级竞价链路的人看到「等 ISR 全部确认」，第一个问题就是「最慢副本定 p99、能定多久」，这个数字应该在 7.4.2 就摆出来，不该拖到第 9 章。

4. 【7.4.3|技术事实】本章说 Redis「提供 `WAIT` 等待此前写入的副本确认」，漏了「本连接」限定；第 9 章 9.2 的准确说法是「等待至少 N 个副本确认本连接此前写入所对应的复制偏移量」。两章口径不一致，而且这个差别是要命的：走连接池的应用在连接 A 上扣减、连接 B 上发 WAIT，等于没等。照第 7 章的写法，很容易把 WAIT 误用成全局确认。

5. 【7.1|深度广度】「哈希分片分布均匀，但加节点就要重分片、大量数据需要重新分布」——这是把 `hash(key) % N` 当成了哈希分片的全部。一致性哈希（Dynamo/Cassandra 一脉）正是为「加节点只搬邻段数据」发明的，而 Redis 的槽本质上就是固定槽数的一致性哈希变体，7.2.3 讲槽时也承认了「加节点只是迁移部分槽」。2026 年的架构书把分片策略收窄成范围 vs 取模二分，会让读者以为哈希分片必然伴随海量重分布。

## 五个建议

1. 【7.4.3/7.6|深度广度】全章反复说「等待更多副本可能增加延迟」，但从头到尾没有一个数量级数字：半同步大约多等一个副本 RTT，MGR 认证多等组内一轮共识，`acks=all` 的延迟受 follower fetch 节奏支配，WAIT 多等副本 RTT。本章「关键数字」框只收了规模数字（16384 槽、9 成员），建议补一版延迟数字——我排延迟预算时，旋钮不给刻度就没法选档。

2. 【导读/7.6 启示五|案例示例】开头的库存超卖事故是全章最有说服力的案例，但没有闭环：大促之后到底改了什么——关键路径加 WAIT、订单号幂等加对账、还是把扣减挪回 MySQL？建议在导读末尾或启示五花两三句交代事后补救，把「做好预案」落成具体一招，否则读者记住了事故、记不住解法。

3. 【7.3.4|逻辑论证】「模块化、可组合，胜过大一统」的代价面只写到「使用上不那么省事：得自己把 MGR 和分片中间件拼起来」。真实拼装成本主要在数据路径上：跨分片事务（账务、预算这类跨分片扣减正是重灾区）、跨分片查询与二级索引、再平衡时的数据迁移。补一小段代价分析，「胜过大一统」这个结论才立得住。

4. 【7.5|深度广度】表 7-1 六个维度都齐了，唯独缺「故障恢复时长」这一行：Sentinel 是 down-after-milliseconds 加选举，Cluster 是 cluster-node-timeout（默认 15 秒）加选举延迟，MGR 数秒级，Kafka 是 Controller 切换加逐分区选主。对定 SLA 的读者，从故障发生到恢复写入的时长比机制差异更决定选型，建议补这一维，哪怕只给量级。

5. 【7.4.4|图示】KRaft 成熟度一段连出 3.3/3.4/3.5/3.6/3.9/4.0 六个版本号和 Early Access/preview/GA 三档状态，纯文字很难在脑内排出先后。建议画一条时间线小图（2.8 预览 → 3.3 新集群生产可用 → 3.5 ZK deprecated → 3.6 迁移 GA → 3.9 bridge release → 4.0 移除 ZK），一眼看清，也省得正文反复括号注版本。
