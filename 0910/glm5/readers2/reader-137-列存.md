## 五个问题
1. 【8.6.6 图 8-8|图示】图 8-8 第二个菱形"需要按索引读写数据页？（页式访问需求）"把"随机定位"和"页式"捆在一起了：一个"不原地改、但要按 key 随机点查"的系统——我手上的列存正是这个画像——顺着图会被引到页式框；可正文 8.6.6 明说"Kafka 的稀疏索引"也是随机定位的例子。菱形里"数据页/页式访问需求"几个字预设了答案，图和正文第二问的口径没对齐。

2. 【8.1.1|逻辑论证】"明天升级的代码要能读懂今天写的文件，今天没升级的代码也可能要面对明天新格式写的文件"把向前、向后兼容并列为长期债务，但三个样本实际都只做"新读旧"：旧 Redis 加载 7.4 写的 RDB 直接报 "Can't handle RDB format version 12"（GitHub redis#14064 的回滚失败就是这场景），老 Broker 对不认识的 Magic 也是拒绝。旧代码遇新格式在三家都是"拒绝加载"而非"兼容"，8.1.1 的双向表述是不是口径不一？拒绝的真实代价——升级后不可回滚——书里没点破。

3. 【8.1.2|深度广度】"CPU 越快、I/O 越慢，越值得为省 I/O 而耗 CPU"这条经验法则在 NVMe 上会被反过来：盘顺序读好几 GB/s 时 zstd 单核解压只有约 1GB/s，瓶颈从盘挪到了解压——ClickHouse 默认选 LZ4 而不是压缩比更高的 zstd，就是因为解压带宽跟不上盘。这一节连同 8.4.3 讲解压代价，都没提"解压速度本身可能成为吞吐上限"这层。

4. 【8.2.4 图 8-3|术语使用】图 8-3 标题"AOF 重写与混合持久化双缓冲协作时序"里的"双缓冲"我停了半天：图里画的缓冲只有 aof_rewrite_buffer 一个，"双"指旧 AOF 文件加重写缓冲，还是新旧两个文件？"双缓冲"惯指两块可交换的缓冲，这里更像"双写"。另外这张图画的是 7.0 之前的单文件机制，却排在 8.2.4 讲 Multi-Part AOF 的正文之后，读这节时在新旧两套机制之间来回跳。

5. 【8.5.2|逻辑论证】"另一项代价是定长页的空间浪费……半空的页在所难免"这个归因我不认同：半空页来自 B+ 树随机插入与删除留下的低填充率，换变长块一样会有；定长本身的代价是页内对齐与尾部碎片，量级小得多。我们列存的 part 刚落盘时同样稀疏，靠后台 merge 把空间收敛回去——页式没有后台整理这招，所以半空才"难免"，但那是"原地改且无合并"的代价，不是"定长"的。

## 五个建议
1. 【8.6.3|案例示例】"稀疏索引+局部顺序扫描"现在只有两处样本（Page Directory、Kafka 偏移量索引），建议补第三处：列存引擎的稀疏主键索引——ClickHouse MergeTree 默认每 8192 行一个 granule 记一条主键 mark，查询二分 mark 后整块扫描。同一手法横跨"页内—段内—引擎级"三个尺度，启示三的普遍性会硬得多，做 OLAP 的读者也能立刻接上自己的系统。

2. 【8.4.3|深度广度】讲"解压边界=Batch 边界"的代价时，建议点一句：压缩块大小本身就是可调的解压粒度旋钮——Kafka 的 batch.size、列存的压缩块、Parquet 的 row group 是同一维度的选择，块小则单条读便宜、块大则扫描吞吐高。现在只说"批量大可以分摊解压"，没说这个粒度可以按访问模式设计，而这恰是读者自己定格式时最能带走的参数。

3. 【8.4.2 与 8.4.4|结构导航】图 8-6 下面那段（相对偏移量 4 字节、超范围要切段、定长条目便于二分）和 8.4.4 开头几乎是同一批事实讲了两遍，只隔两页。建议 8.4.2 只留"三类文件配套、文件名即起始偏移量"，把条目构成与切分约束整体收进 8.4.4，顺带消掉"条目的具体构成……见第 8.4.4 节"这个前指。

4. 【8.3.2|表达可读】"回滚段则管理 undo log 所用的多个表空间段，两者不是同一级概念"这句我读了三遍：前一句讲的是索引的叶子段/非叶子段，"两者"指哪两者（叶子段与非叶子段？索引段与回滚段？）全靠猜。建议拆成两句：先说回滚段是另一种段、管的页不一样，再说不与叶子/非叶子那组划分同级。

5. 【8.5.1 表 8-2|深度广度】表 8-2 有"损坏检测"行（CRC64/页校验/Batch CRC），却没有"压缩发生在哪个粒度"这一行：RDB 是值级 LZF、InnoDB 默认不压缩（可选页压缩）、Kafka 是 Batch 级。加上这行正好与校验粒度互相呼应，也把 8.1.2"空间与时间"的矛盾落进对比表里。
