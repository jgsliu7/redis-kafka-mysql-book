# 读者114 · 物联网
身份：工业物联网平台开发，8年，爱好：无人机航拍
主读：第 3 章

## 五个问题

1. 【3.2｜逻辑论证】3.2 说"存不存数据"由用户通过 SHUTDOWN SAVE/NOSAVE 显式指定，图 3-3 侧栏也写"落盘由用户显式指定并承担后果"，可书里自己说 systemd stop、容器编排的滚动重启"最终都落到这条信号路径上"——SIGTERM 路径带不了任何参数，落不落盘实际由 save 配置决定（3.4 才补上"只要配了 save 点、出厂默认就配"就会在退出前全量落盘）。我们网关上的 Redis 全走 systemd stop，发版窗口没人能发 SHUTDOWN NOSAVE，那"由用户决定"的决定权到底在哪个入口？3.2 的框架与 3.4 的现实没接上，单读 3.2 会误以为信号关闭能秒退。

2. 【3.3｜读不懂】前文说"大事务一旦在崩溃点未提交，启动期的 undo 回滚会非常慢"，后文又说 InnoDB 定下事务边界后"逐条回滚可以留给后台线程，实例不必等它走完"、ready for connections 打印后回滚可能仍在进行。我没读懂：大事务回滚到底拖不拖慢"打到 ready"的时间？同步部分（redo 重放、定事务边界）与后台回滚的界限在崩溃点怎么划，两段合读拼不出确定答案，前一句"启动期回滚非常慢"很容易被读成到-ready 耗时。

3. 【3.4｜深度广度】受控关闭的前提写的是"Controller 必须可达"，那正要下线的 Broker 自己就是 Controller 时（KRaft combined 模式，我们边缘三节点小集群就这么部署）谁来协调它的 Leader 迁移？是先移交控制器领导权再受控关闭，还是直接退化为普通关闭？普通关闭步骤里的"停控制器"一步对 combined 节点又意味着什么，书里没交代。

4. 【3.6 启示四｜逻辑论证】"配置 → 基础设施 → 核心服务 → 数据恢复 → 对外服务"这条通用线，我拿 3.2–3.4 的实际顺序去套对不上：Redis 四段里没有独立的"核心服务"段，Kafka 的副本管理/控制器/注册（更像"核心服务"）明明排在日志恢复之后，MySQL 的网络层也在 InnoDB 恢复之后。三家实际上都是数据恢复先于核心服务就绪，启示四把这两步的先后写反了，或者"核心服务"指什么需要先定义清楚。

5. 【3.4 追加写日志｜技术事实】"写了一半的残缺尾部靠 CRC 找出来直接截掉，不存在需要回滚的中间状态"隐含一个前提：介质断电只丢尾部、已落盘的部分不会坏。玩无人机航拍的人对这点最有体会——SD/eMMC 突然断电时 FTL 映射表回滚，丢的常常不是尾部而是更早的块，CRC 截尾救不了这种洞；网关现场跑单副本 Kafka/Redis 时这个前提并不自动成立，建议点明"截尾恢复语义依赖介质断电原子性"这层假设。

## 五个建议

1. 【3.4｜深度广度】补一小段"Broker 重启时客户端看到什么"：生产者收到 NOT_LEADER_OR_FOLLOWER 后靠元数据刷新与重试续命、消费者触发重平衡、以及大量客户端同时重连的风暴。我们 MQTT 平台每次 broker 发版，几万网关同时重连能把刚接任的 Leader 再打趴——服务端优雅了不等于系统优雅，重连退避必须加抖动，这层客户端视角书中完全空白。

2. 【3.4 容器化｜案例示例】preStop + BGSAVE 方案请落到可抄的命令：怎么"停写"（CLIENT PAUSE <ms> WRITE）、怎么确认快照完成（轮询 INFO persistence 的 rdb_bgsave_in_progress 归零或 LASTSAVE 时间戳变化），最后再 SHUTDOWN NOSAVE。现在只有"fork 前停写、确认完成"的原则性描述，值守同事照抄不了，而这恰恰是全章最该 runbook 化的一段。

3. 【3.3 表 3-1｜图示】把"关闭速度/启动速度"两行升级成一条时间轴图：同一档位的关机耗时＋开机恢复耗时拼成"总停服窗口"，三档画三条杠对照。选档的本质是最小化总停服窗口而不是两段各自快慢，表里分离的两行"快/中/慢"评级要读者自己做心算，一条总窗口图直观得多。

4. 【3.4｜深度广度】3.2 已点到"systemctl stop 背后其实就是发一个 SIGTERM"，建议把这半步补全：systemd 的 TimeoutStopSec（发行版默认 90 秒）超时后同样 SIGKILL，与 K8s 的 terminationGracePeriodSeconds 是同构旋钮，可并列成小对照。工业现场大量部署没有编排系统，裸 systemd＋看门狗、断电是常态——"多数生产部署如今跑在 Kubernetes 上"在我们行业只对云端半区成立。

5. 【3.6 启示五｜表达可读】"可观测性是状态机的外显"建议配一张三行小表，把三家就绪日志（Ready to accept connections / ready for connections / [KafkaServer id=0] started）的原文、所在日志文件、grep 姿势集中起来。这节的价值就在能直接抄进运维手册和就绪探测脚本，现在三条日志散落在 3.2–3.4 三个小节，读者还得自己回头翻。
