# 读者118 · Mongo叔
身份：MongoDB DBA，9年，爱好：卡丁车
主读：第 4 章

## 五个问题
1. 【4.1 表4-1|表达可读】表头声明"延迟以内存为 1"，但 SSD/机械盘"顺序写吞吐"两行的"相对内存"列突然改比"单线程内存随机读吞吐（几百 MB/s）"——这个参照数在表里根本没有，要翻到 4.4"作为参照，内存随机读单线程约几百 MB/s"一句才能拼上。一张表延迟、吞吐两种口径来回切，我第一遍读翻回去对了三遍才确认没看错行。
2. 【4.1|技术事实】"同价位下，磁盘容量通常是内存的上百倍"——按我这两年采购的价格，NVMe SSD 约 $0.08/GB、DDR5 约 $3/GB，差距是 30–40 倍；能到上百倍的只有机械盘。做容量规划的人拿 SSD 对账会发现数字对不上，建议拆开说或放宽成"几十到上百倍"。
3. 【4.3|技术事实】change buffer 的 merge 写成"等这个页因为别的原因被读入缓冲池时，再把缓存的修改合并进去"，漏了主动路径：后台线程周期性 merge、缓冲池空间紧张需要腾页时的 merge、实例关闭时的全量 merge。生产上大量 merge 是后台主动做的，不是"顺便"。
4. 【4.6 启示二|逻辑论证】"Redis 和 MySQL 自己管理内存，是因为内核的 PageCache 策略无法满足它们在淘汰精度上的需求"——对 Redis 这个归因不成立：Redis 的数据本身就驻留内存，不是任何文件的缓存，压根不存在"交给内核管"这个被否决的选项。拿 MySQL（真是磁盘页的缓存）的理由去并排解释 Redis 的选择，是倒果为因。
5. 【4.6 启示三|逻辑论证】把 `innodb_flush_log_at_trx_commit=2` 与 Redis `everysec`、Kafka `acks=1` 并列为"很多时候的中间档"——我 9 年 DBA 几乎不这么推荐：2 只防 MySQL 进程崩溃，掉电/内核崩溃照样丢约 1 秒已提交事务，而组提交加现代 NVMe 下 2 对 1 的吞吐差距已经很小。这一段至少应标明 2 的保护边界，否则读者会当成三家的等价三选一。

## 五个建议
1. 【4.4|深度广度】"为什么不做自己的缓冲池"给了三个理由，还缺最有 Java 特色的第四个：Kafka 官方设计文档明说交给 PageCache 同时避免了 JVM 堆内缓存的 GC 压力，并把可用缓存尺寸从 Xmx 解耦到整机内存。这是这个决定里工程味最重的一环，值得补上。
2. 【4.6|深度广度】三种范式的光谱里没点 LSM：memtable 把随机写收进内存、顺序刷成 SST 再 compaction，正是启示四"随机写改造"的另一条路线（RocksDB、Cassandra、MongoDB 都在这条线上）。建议在启示四用三五句话把 LSM 作为变体点到，否则读者拿着三种范式去对生产系统，一半对不上号。
3. 【4.3|深度广度】InnoDB 默认缓冲 I/O 下数据文件也过 PageCache、与缓冲池形成双份缓存，这层与 `O_DIRECT` 的取舍只在 4.4 顺带提 MySQL 的一小句里出现。建议在 4.3 正式讲一小段——这是"缓存磁盘范式"与"相信 PageCache 范式"之间真正的灰色地带，也是我调 WiredTiger 缓存时天天面对的同一道题。
4. 【4.1|图示】图 4-1 只画了延迟对数轴，但 4.4 讨论 Kafka 用的全是吞吐口径（顺序带宽 vs 随机 IOPS 上限）。建议配一张"顺序/随机 × SSD/HDD"的吞吐对比小图，或在图 4-1 上并列标出吞吐层，两张图就能把本章依赖的两组核心数量级一次立住。
5. 【4.5|案例示例】导读里"缓存用 Redis 还是 MySQL"的选型争论是好素材，可惜到 4.5 只剩一张六维对比表收尾。建议把那场争论展开成一个带数字的完整案例（数据量、QPS、命中率假设、延迟测算），演示"从访问模式倒推范式"的具体算法——现在启示一只给了要列的清单，没有演示清单怎么用。
