# 读者110 · JDBC姨
身份：数据库驱动研发，10年，爱好：缝纫
主读：第 2 章

## 五个问题
1. 【2.3.1|技术事实】"也能用 nc 手工发送简单命令"被列为 RESP 人眼可读的佐证，但 nc 里手敲 `SET key value` 走的是 Redis 服务端的 inline command 通道（空格分隔的纯文本，另一套解析路径），不是 RESP——RESP 请求要编码成 `*3\r\n$3\r\nSET\r\n...`，在 nc 里手敲 `\r\n` 和 `$` 前缀并不比敲二进制友好多少。我读过驱动侧的请求分发代码，这两套格式是明确分开的两个分支，书里把它们混为一谈了。
2. 【2.3.2|深度广度】预编译语句被立为"MySQL 协议在效率上的关键设计"，但没提生态现实：MySQL Connector/J 的 useServerPrepStmts 默认是 false，绝大多数 JDBC 应用里 PreparedStatement 在客户端拼好字符串走 COM_QUERY 文本协议，"解析只做一次"的收益要显式打开服务端预编译（通常还得配 cachePrepStmts）才兑现。我十年里接得最多的工单就是"为什么 PreparedStatement 没变快"，协议能力与实际使用之间的这道落差，这一节完全没有交代。
3. 【2.3.2|技术事实】握手阶段"客户端回传加密后的凭证"这个概括不对：MySQL 4.1 起是挑战-应答（客户端用服务端随机数 scramble 出响应），8.0 默认的 caching_sha2_password 也不是把凭证加密后回传。native 方案的握手包被截获后可以离线字典爆破，和"加密后的凭证"给人的保密语义正好相反——写过认证握手代码的人会在这里被绊一下。
4. 【2.4 表 2-2|逻辑论证】"核心数据结构"一行把 SDS/跳表（内存容器结构）、B+ 树（磁盘索引结构）、RecordBatch V2（消息封装与落盘的字节布局）并排放：前两者有算法复杂度语义，RecordBatch 是帧格式，谈不上什么 O(log N)。三家放在同一行对比却没有点破这层抽象错位，读者容易以为在比较同一层的东西，"目标决定结构"的因果链反而被稀释了。
5. 【2.3.2|深度广度】讲变长整数时专门提了 0xFB 在行里标记 NULL，却停在最关键的 0xFE 前一步：首字节 0xFE 既是 8 字节长度前缀、又可能是 EOF 包，驱动实现要靠包上下文区分，这是 MySQL 协议史上最著名的坑，CLIENT_DEPRECATE_EOF（5.7.5 起）正是为消除它而生。既然本节主题是能力标志驱动的版本演进，错过了这个最现成的实例很可惜，我只读到了半截。

## 五个建议
1. 【2.3.2|案例示例】补一小段 JDBC 现实：Connector/J 默认客户端模拟预编译（useServerPrepStmts=false），连接池厂商（如 HikariCP）的推荐配置里打开它才有"解析一次"。这个案例能把"协议设计了能力"与"生态用了多少"接起来，比单纯讲协议字段更有架构书的味道。
2. 【2.3.2|深度广度】表 2-2 里 MySQL 的版本演进方式只写了"能力标志（握手时交换）"一个名词。建议用 CLIENT_DEPRECATE_EOF 展开成有头有尾的实例：0xFE 双义 → 5.7.5 新标志 → 新客户端收 OK 包替代 EOF——正好和 Kafka 的 api_version 形成对照，让"演进能力做进格式本身"这句论断落到具体字节上。
3. 【2.4 图示】图 2-8 三家的实例段建议各标注真实字节数：RESP 那段 `SET key value` 是 32 字节，MySQL 预编译两次往返、Kafka 请求头各是多少。作者文中已有"三十多个字节"的定性说法，把数字画进图里，"RESP 体积大、二进制省带宽"就从论断变成读者看得见的差距。
4. 【2.3.3|深度广度】"双方用彼此都支持的最高版本号做协商"缺了入口一环：客户端连上 Broker 先发 ApiVersionsRequest 探明各 API 支持的版本区间，之后每个请求才好定 api_version。补这一句，版本协商就从抽象描述变成可操作的流程，也解释了为什么客户端从不"赌"版本号。
5. 【2.5|表达可读】"熟手一下午就能写出一个能用的 Redis 客户端"建议划清"能用"的边界：一下午写出来的是 PING/GET 有往返的 demo 级客户端；生产级要处理连接池化、超时重试、RESP3 协商和集群重定向，是另一个量级的工程。我写过驱动，这句不限定范围容易被读者当真。
