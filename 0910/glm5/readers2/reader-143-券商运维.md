# 读者143 · 券商运维
身份：证券交易系统运维，14年，爱好：木雕
主读：第 9 章

## 五个问题

1. 【9.4|逻辑论证】「`acks=all` + `min.insync.replicas` 与 MySQL 半同步在降级语义上存在关键差别」这段，拿半同步代表 MySQL 阵营去对比 Kafka，却把 MGR 漏掉了：MGR 在凑不齐多数派时宁可整组不可写也不静默降级，才是与 Kafka「拒写」语义对等的选项。我们在核心库上选 MGR 图的就是这个「宁拒不降」，作者由此得出「写路径碰钱时我站 Kafka 这边」的结论，对 MySQL 阵营不公平，也容易让读者误以为 MySQL 生态里没有同款保护。

2. 【9.4|读不懂】Tiered Storage 那段「若所需数据已移到远程层，副本会从远程段恢复 leader epoch、生产者快照等辅助状态，再从对应远程段之后继续拉取本地日志」，我读了三遍没读懂：副本能直接读远程段的数据吗？「远程段之后」之前那段缺口由谁补，是否要把远程数据回补到 Leader 本地？一句话压缩了一整套机制再甩给第 8 章 8.4.6 节，本章读者在这里就断了线。

3. 【9.2|术语使用】WAIT 一节说「在可阻塞的执行上下文中，它等待至少 N 个副本确认」，「可阻塞的执行上下文」指什么没有任何解释：MULTI/EXEC 里能用吗？Lua 脚本里呢？我正打算在事务里给关键写补一道 WAIT 确认，这句话没给我边界，还得自己去查文档。

4. 【9.7|深度广度】导读把「缓存和数据库不一致时该以谁为准」立为本章引子，9.1 还预告「本章小结与第 10 章会给出答案」，结果 9.7 只用一句「数据库是正本、缓存是可重建的派生数据」收尾。先写库还是先删缓存、删缓存失败怎么补偿、不一致窗口怎么监控，这些我们行情和持仓缓存天天踩的坑全没展开，答案的分量配不上导读立的题目。

5. 【9.3|技术事实】半同步一节说副本「把事件写入 relay log 并落盘后即回 ACK」——这个「落盘」是写入文件还是 fsync 持久化？relay log 的 `sync_relay_log` 默认并不对每个事件 fsync；若只是进了 OS 缓冲，副本 ACK 后掉电事件照样丢，「至少一个副本收到」在掉电场景的含义就完全不同。我们做机房掉电演练时这正是要害，希望把「收到」与「已持久化」的边界说清。

## 五个建议

1. 【9.5|深度广度】表 9-1 六个维度建议加一行「确认条件不满足时的行为」：Redis 门槛不到拒写 / MySQL 半同步超时降级为异步（可观测）、MGR 拒写 / Kafka ISR 不足拒绝写入。正文 9.4 自己都强调「降级语义上存在关键差别」，横向对比表里却没有这一行；对做开盘前检查清单的人来说，这一行比六行机制描述都实用。

2. 【9.3|案例示例】「降级必须可观测」给了原则没给抓手，建议补上具体变量与接法：`Rpl_semi_sync_source_status` 看当前是否半同步，`Rpl_semi_sync_source_no_tx` 与 `times_yes_tx` 计数此消彼长就是降级信号，配一条告警阈值示例更好。原则进不了检查清单，变量名才能。

3. 【9.4|版本时效】KRaft 小节停在「3.3 对新集群达到生产可用」，建议补一句 Kafka 4.0（2025 年 3 月）已彻底移除 ZooKeeper。2026 年买书的读者多半在 3.x/4.x 上做升级规划，「替代」已是完成时，这个里程碑一句话就能交代完整。

4. 【9.1|案例示例】作者「主从延迟导致下单后查不到订单」的案例与我经历几乎同款，但解法「加了一个写后读一致的路由层」一笔带过。建议展开一两句方案形态：关键业务键在窗口期内强制读主，或 MySQL 端用 `WAIT_FOR_EXECUTED_GTID_SET` 等从库追平再读——券商的「委托后立即查成交」就是这个问题的高频放大版，读者要的正是路由层怎么落地。

5. 【9.3|术语使用】9.3 的说明框只列了半同步变量的改名（`rpl_semi_sync_master_*` → `source_*`），没提运维最先撞上的命令改名：`SHOW SLAVE STATUS` → `SHOW REPLICA STATUS`、`CHANGE MASTER TO` → `CHANGE REPLICATION SOURCE TO`。我们从 5.7 升 8.0 时批量改的就是这些脚本命令名，补一句能省后来人不少事。另外图 9-4 标题用「从节点」而正文通篇用「副本」，术语也宜统一。
