# 读者113 · SOC夜班
身份：安全运维分析师，6年，爱好：夜跑
主读：第 3 章

## 五个问题

1. 【3.3|技术事实】原文说"`SHOW PROCESSLIST` 在关闭期的输出，对着这四类根因看，就能定位卡点"。作为常年值夜班的人这句必须拦：关闭期的 mysqld 已停监听，新连接基本进不来；而且四类根因里"脏页待刷""FTS 优化"是后台线程行为，processlist 里根本没有对应行。真实排查靠 error log 的 shutdown 日志和（还连得上时的）`SHOW ENGINE INNODB STATUS`，这句照做会浪费时间。

2. 【3.2|逻辑论证】关闭第一步"直接杀掉重写子进程——优雅关闭优先缩短关闭耗时"，第三步 `SHUTDOWN SAVE` 又让主进程同步全量写 RDB（大实例分钟级），从头写的总耗时大概率超过等半成品快照跑完。两步放在一起，"快"的动机互相打架，也没解释为什么不能复用进度（临时文件 rename 前不完整？）；我拿这节估 Redis 滚动重启的停机窗口，得不出结论。

3. 【3.2+3.6|深度广度】启示二说优雅关闭第一件事是"完成已接受的请求"，MySQL 有事务回滚交代、Kafka 有"处理完在途请求"，唯独 Redis 关闭五步里没有对应环节——第四步直接"关闭所有客户端连接"。半夜 `SHUTDOWN` 一个 Redis，正在执行的命令、没返回的 MULTI/EXEC、阻塞在 BLPOP 上的客户端各自什么命运，正文没交代，通用流程在自己讲得最细的软件上反而缺一环。

4. 【3.3|读不懂】3.3 前面说未提交事务回滚"可以留给后台线程，实例不必等它走完"（`ready for connections` 先打印），紧接着又说"崩溃恢复的耗时取决于……有多少未提交的事务，大事务未提交启动期回滚会非常慢"。回滚到底算启动耗时还是恢复期后台耗时，两段合起来拿不准——这直接决定崩溃后多久能接流量、接了之后哪些表会被回滚持有的锁卡住。

5. 【3.4|案例示例】"preStop hook 可以先触发 `BGSAVE`，确认本次快照成功完成后再执行 `SHUTDOWN NOSAVE`"——`BGSAVE` 返回的只是"后台保存已启动"（下文自己也承认了），那 hook 脚本里到底拿什么确认"成功完成"？LASTSAVE 时间戳前后比对还是轮询日志，书里没落地，照抄写脚本会卡死在"确认"这一步。

## 五个建议

1. 【序言|其他】序言的读者画像只有"后端工程师、软件架构师、技术负责人"，但第 3 章近一半篇幅在讲 grace period、K8s 三类探针、"mysqld 关不掉"排障——这是标准运维/SRE 语言。建议把"有运维/SRE 背景的工程师"写进目标读者，别让这批读者在序言就被劝退。

2. 【3.4|案例示例】导读用作者自己的 Redis 事故开篇，效果很好；3.4 容器化一节却全是参数处方（grace period 给多少、重试调多大），没有一个真实复盘。建议补一条"Controller 高负载 → 受控关闭重试预算耗尽 → 退化为普通关闭 → 选举抖动 → 上游超时"的时间线案例，夜班对照时间线处理故障最有效率。

3. 【3.6|结构导航】启示四给出"配置→基础设施→核心服务→数据恢复→对外服务"五段模板，但 Redis 四段、MySQL 四段、Kafka 八阶段与这条线的映射全靠读者自己脑补。建议补一张映射小表（行为通用五段、列为三家各自的阶段名），让"殊途同归"一眼坐实。

4. 【3.6|表达可读】可观测性一节只列了三条"启动完成"日志，但排障的另一半信号在关闭侧（MySQL 的 "Shutdown complete"、Redis 的 shutdown 日志、Kafka 的 "shutting down"/"started"）。建议做成三家的启动/关闭里程碑日志对照表，顺带提示 grep 就绪日志的坑（一机多实例同文案、就绪打印后后台仍在回滚），这节对运维读者的价值会翻倍。

5. 【3.3|深度广度】"为什么 mysqld 关不掉"给了四类根因，但每类该看哪里没下文——error log 该 grep 什么关键字、`SHOW ENGINE INNODB STATUS` 看哪个段、performance_schema 查哪张表。既然点名这是高频排障场景，建议给一张"根因→定位手段"对照，把这条排障路径做实到可执行。
