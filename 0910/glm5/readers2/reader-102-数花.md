## 五个问题

1. 【1.2.4 表1-1 及 图1-1|逻辑论证】表 1-1 和图 1-1 都写 MySQL「可舍弃：写性能」，但 1.1.3 明明说代价是「写放大、事务开销和调优门槛」，1.2.2 说的是「提交延迟」。我拿 pandas 往 MySQL 批量灌过几百万行（to_sql / LOAD DATA），单机每秒几万行毫无压力——MySQL 舍的不是「写性能」，是「每次提交都刷盘的那种写延迟」。压成三个字，转行的读者会得出「MySQL 写入很慢」的错误结论。
2. 【1.2.2|读不懂】「一致性读根据 Read View 判断版本是否可见：视图记录当时的活跃事务集合，读取时沿版本链从新到旧寻找可见版本。Read View 的生成时机与隔离级别有关……」这段我在引言章就卡死了。三段概览里 Redis 和 Kafka 都是一百来字讲抽象，唯独 MySQL 这段直接下钻到 Read View 建立时机和两种隔离级别的差异，而且没说这部分后面哪章会展开，按我「卡了就跳」的习惯，这里差点直接翻到第 2 章。
3. 【1.3.3|逻辑论证】这一节先发给我一把尺子：日志分「记做了什么操作（逻辑）」和「记哪个字节改成什么样（物理）」两类，紧接着又说 MySQL redo「严格说是物理到页、逻辑到操作的混合日志」。结果是三家谁都不是纯粹的那把「物理」尺子上的例子——Redis 是逻辑，Kafka 根本不重放，MySQL 是混合。刚建立的二分立刻作废，我没明白这个分类到底想让我理解什么。
4. 【1.3.3（对照第 3 章 3.2）|技术事实】第 1 章说 Redis AOF「记的是『执行了什么命令』，重放即重新执行命令」，第 3 章 3.2 却讲 Redis 7.0 起 Multi-Part AOF 的 base 文件默认是 RDB 二进制、只有 incr 是命令重放。书自己声明的版本基线就是 Redis 7.x，第 1 章这个概括在基线版本下已经不完整，两章连读时我等于先接受「AOF=命令重放」、再到第 3 章被修正一遍。
5. 【图 1-2|图示】雷达图「低延迟」维度得分越高代表延迟越低，可轴旁小注写的是「越小越快」（说的是延迟毫秒数），刻度 1/3/5 又是往外越大。我平时用 pandas 画图都要先想清楚坐标轴方向，这三层方向拧在一起，我停了半分钟才确认「5 分=延迟小=快」，怕硬核的读者大概率直接看错。

## 五个建议

1. 【1.2.2|深度广度】引言章的 MySQL 概览向 1.2.1 / 1.2.3 两节的颗粒度看齐：Read View 生成时机、两阶段提交这类细节压成一句话，留给后面深讲的章节并标注「详见第 X 章」。概览的任务是让我记住「不丢、不错排在快前面」，不是在引言里就把 InnoDB 手册背一遍。
2. 【序言|结构导航】序言里「如果你对某些知识点不熟悉，多用 AI 帮你快速了解」这句，建议改成书内兜底：给 1.4.1 点名的前置概念（跳表、I/O 多路复用）加半页附录小词典或边栏。非科班读者（比如我，pandas 出身）对哈希表、树还有印象，对「跳表」是真零印象——花钱买书，结果缺口被推给另一个 AI，观感不好。
3. 【1.2.1|案例示例】「数据结构服务器」是全书抛出的第一个核心抽象，建议配 3 行 redis-py 实例：排行榜一条 `ZINCRBY` 原子完成，对照 Memcached 式「GET→改→SET 还得加锁」三步。对只会 get/set 的读者，这一小段代码比 `ZADD`/`ZRANGEBYSCORE` 一串命令名更能让「抽象的价值」落地。
4. 【1.3.3|图示】三层追问（先刷日志还是先刷数据页 / 粒度多细 / 记什么）是全章的高潮，但现在全是文字。建议加一张「三家 × 三个问题」的小对照表，顺带把「物理日志=哪个字节改成什么样」的定义改成能对上 redo 实际形态的表述（页级修改 vs 字节级），消除定义与例子对不上的问题。
5. 【1.4.4|结构导航】路径 C 说横向对比在「多数章在偏后的小节」，我核了下目录：第 2 章是 2.4/2.5，第 3–9 章是 x.5/x.6——与其含糊说「多数章」，不如在图 1-3 每章框里直接标注对比节号，或给一张「每章对比节号」小表。像我这种准备跳读的读者，最需要的就是这个路标。
