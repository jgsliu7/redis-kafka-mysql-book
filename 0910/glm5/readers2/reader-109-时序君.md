# 读者109 · 时序君
身份：时序数据库平台工程师，6年，爱好：风筝
主读：第 2 章

## 五个问题
1. 【2.2.1|深度广度】「选跳表而非红黑树，是因为实现更简单、范围操作更直接」这个论证我不服：我在写多读少场景干了六年，跳表在工业界最大的主战场是 LSM 系引擎的 memtable（LevelDB/RocksDB，包括我运维的 InfluxDB TSM 内存索引），选它的核心理由是无再平衡、插入只改局部指针、对高写入吞吐和顺序刷盘友好——这些一条都没出现。只按书里给的两条理由，解释不了为什么写密集引擎放着红黑树不选取跳表。
2. 【2.2.3|技术事实】「原样追加的前提是生产者的压缩类型与 topic 的 compression.type 一致」不准确：compression.type 的默认值就是 producer，取默认时无论生产者用不用压缩、用哪种算法，Broker 都原样落盘；只有 Broker 端显式配了具体压缩类型且与生产者不同时才逐批解压重压。我们的指标管道 Telegraf 侧用 snappy、Broker 端从没配过「一致」，照样原样存储——照书里的说法，读者会去对齐两端配置，而生产上的正确姿势恰恰是别动 Broker 默认值。
3. 【2.5 启示四|读不懂】「我自己设计新协议，会先从第二个版本开始——第一个版本很少有人能把边界想全」这句话我读了三遍没懂：是首个上线版本直接标 v2？还是设计 v1 时就假设 v2 必然存在、按此预留字段？与前句「留出能力标志或版本字段」连起来猜是后者，但「从第二个版本开始」的字面动作始终说不通。
4. 【2.2.1|技术事实】intset 编码升级写做「（int16→int32 或 int32→int64）」容易被读成只能逐级升；实际源码（intsetUpgradeAndAdd 按 _intsetValueEncoding 取值）是按新值所需宽度一步到位，int16 集合插一个超出 int32 范围的值时整个数组直接升到 int64，中间不经过 int32。照书里的写法理解，会误判升级的次数和每次搬迁的开销。
5. 【2.2.1|深度广度】字典扩容阈值写「通常为 1」，漏掉了生产上最要命的分支：有 BGSAVE/AOF rewrite 子进程期间 dict 扩容被抑制，负载因子要冲到 5（dict_force_expand_ratio）才强制扩容。我处理过写入高峰撞上 BGSAVE、哈希桶链变长、命令延迟上涨的实例，根因正是这个机制。同一段都细讲了「子进程运行期间定时搬迁暂停」，这条更常见的雷却只字未提。

## 五个建议
1. 【2.2.3|深度广度】RecordBatch 的差值编码（每条记录只存与 baseOffset/baseTimestamp 的差值）建议点破它的普适性：这与时序数据库时间戳压缩的 delta-of-delta（Gorilla）是同一思想——批内共享基准、成员只存增量。加一句话，做日志管道和指标系统的读者就能把这套手法直接迁移走。
2. 【2.4|结构导航】表 2-2 建议增加一行「写路径代价」：Redis 是摊还式 rehash+惰性释放，MySQL 是页分裂加二级索引删旧插新，Kafka 几乎为零（顺序追加）。全章的对比维度偏读路径，写路径的代价散落在各小节，聚齐之后「目标→结构→代价」这条因果链才算闭环，写多读少场景的读者尤其需要这张总账。
3. 【导读+2.6|案例示例】排行榜案例建议补一个反向边界：什么时候不该用 ZSET。比如按时间窗口回溯重算的历史榜单（我做的时序榜单数据 append-only、按小时窗批量重算，走 Kafka 加批处理比 ZSET 合适）、或需要持久化审计的榜单。现在「MySQL 输、Redis 赢」的单向叙事，容易教出「排行榜=ZSET」的机械结论，反而和 2.6 自己说的「先列访问模式再选结构」打架。
4. 【2.2.1|图示】图 2-2 建议给前进指针标上 span（跨度）值。正文说「span 逐层累加就是名次，ZREVRANK O(log N)」，导读的核心痛点也是查名次，但图上一个 span 都没画，读者无法顺着红色查找路径把名次亲手算一遍。只需在两三个节点旁补上 span 数字，这条最重要的路径就能在图上落地。
5. 【2.3.3|版本时效】Kafka 一节建议交代成书版本基线。正文以「3.0 的 Broker 可以和 0.11 的客户端对话」为例，但 2025 年 Kafka 4.0 已 GA（KRaft-only），且分层存储（KIP-405）落地后，从远端层拉取旧段时数据要先落回 Broker 本地缓存，「零拷贝直接从页缓存送网卡」这段就不再无条件成立。标注一句「以 3.x 为基线描述」，后续读者不会被时效问题绊住。
