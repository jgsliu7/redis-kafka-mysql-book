# 读者125 · 外企温
身份：外企 Senior Engineer，11年，爱好：飞镖
主读：第 5 章

## 五个问题

1. 【5.2.1|版本时效】本节把 RESP 讲成"`+`/`-`/`:`/`$`/`*` 五种前缀"，这是 RESP2 的类型集，但全文没有出现"RESP2/RESP3"字样。RESP3（6.0 起，HELLO 握手、map/boolean/double/push 等新类型）恰是交互层的协议大事，同一节大谈 6.0 的多线程 I/O，协议侧的 6.0 变更却一字未提——按规范读文档的人第一反应就是：这一节的对口协议版本到底是哪个？

2. 【5.2.1|逻辑论证】"一旦放开并发……要么大面积加锁……要么重写全部数据结构。这一句话也解释了为什么 7.x 默认仍然关闭多线程 I/O"——这条因果焊缝不成立：命令执行必须单线程，解释不了"协议 I/O 多线程"为什么默认关闭，redis.conf 注释里给的理由是它只在 QPS 很高、连接数大时才划算。两个各自成立的事实焊成一条因果链，就变成了第三个未经证明的事实。

3. 【5.3.1|技术事实】线程池"切换开销低但慢查询会队头阻塞（一条慢查询拖住队列里后面的所有请求）"表述过强：企业版线程池是按 thread group 分组的（thread_pool_size 个组），一条慢语句只挡住分到本组的连接，且 stall 检测（thread_pool_stall_limit）判定阻塞后还会为本组加开线程。原文的写法把分组建模读成了单队列建模，读者会高估队头阻塞的实际范围。

4. 【5.4.3|逻辑论证】段末"Kafka 把存储做得极薄……索引、复制、压实的复杂度都在上层解决"与本节前文自相矛盾：稀疏索引就是 LogSegment 自带的 `.index` 文件（两段之前刚把它讲成存储层读取路径的一部分），LogCleaner 压实也是直接在日志段上重写，两件事都发生在存储层内部而非"上层"。作者想表达的大概是"在追加写路径之外"，但"上层"这个词与本章自己的层次划分打架。

5. 【5.4.4|结构导航】三段式在 5.1 立为主线、导读也点名"三段式主线"，5.4.4 却宣布 Kafka 是"交互 + API + 存储 + 协调"四段；到了 5.5，图 5-7 的 Kafka 列只有三格（协调层不见踪影），表 5-1 又把它折进"主要环节与接口"一栏。同一章里协调层一会儿是"层"、一会儿是"职责"，我合上书说不清 Kafka 到底按几层算、这个四段算不算本章框架的正式修订。

## 五个建议

1. 【5.2.1|版本时效】给协议描述锚定版本：或声明"本节按 RESP2 描述"，或补一小段 RESP3 速览（HELLO 握手、map/push 新类型、客户端怎么协商）。它和多线程 I/O 同在 6.0 引入、同属交互层，两者对照着讲反而是本章的现成亮点。

2. 【5.5|图示】图 5-7 的 Kafka 列建议补第四格（ReplicaManager/Controller 协调职责）和一条跨机虚线（跨 Broker 协议）：表 5-1 里这两项都在，图里却把 Kafka 画成与另外两家完全对称的三层，恰好抹掉了正文花大力气论证的"Kafka 多出来的那一层"。若再把三种层间通信形态（函数调用 / 虚函数 / 队列+网络）用不同线型画出，一图能省半页文字。

3. 【5.5|深度广度】表 5-1 建议加一行"过载时的行为"：Redis 靠 client-output-buffer-limit 断连、MySQL 靠线程排队加 max_connections 拒绝、Kafka 靠有界队列阻塞入队做背压。5.4.1 把背压讲得很好，但横向对比只对了"层间怎么通信"，没对"通信满了怎么办"——这是三家用同一问题给出三种答案的整齐对照组，弃之可惜。

4. 【5.3.1|案例示例】"MySQL 顶上的分层边界是虚的"是全章最锋利的判断之一，但只有断言、没有证据。建议落一个可核实的例证：比如企业版线程池插件为绕开 THD 共享状态付出的具体约束，或一处连接层代码直接读写 THD 字段的源码位置——锋芒判断要有抓物，才立得住。

5. 【5.1|其他】建议章首或 5.1 末尾加一行三软件的版本基线（Redis 7.x、MySQL 8.0.x、Kafka 具体版本与源码快照）。本章精确到小版本的事实密度很高——"8.0.30 前后 redo log 文件名""Kafka 3.9 Tiered Storage GA"（我核对过 3.9 这条，与 Apache 官方发布公告一致）——给出基线，读者才知道哪些论述跟随哪个版本。
