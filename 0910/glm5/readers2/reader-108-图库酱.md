# 读者108 · 图库酱
身份：Neo4j 图数据库工程师，5年，爱好：狼人杀
主读：第 2 章

## 五个问题

1. 【2.2.1|技术事实】"跳表的缓存局部性确实不如红黑树"这个断言下得太满。我天天在图遍历里做指针追逐 profiling，局部性主要取决于节点分配布局和单节点内指针是否连续，不是"跳表 vs 红黑树"这个类目：Redis 的 zskiplistNode 是单块连续分配、前向指针内嵌在 level 数组里（平均 1.33 个），红黑树节点自带父指针和颜色位、插入旋转还会把同批节点在地址空间打散——谁更局部在工程上两说。而且这句话还被 2.5 启示一原样复用（"跳表在缓存局部性上付出了代价"），从让步变成了定论，建议加限定词或给出处。

2. 【2.2.2|版本时效】"5.7.8 起拆成 8 个分区"疑似小误。我查了 MySQL 5.7 官方手册的系统变量页，`innodb_adaptive_hash_index_parts` 标注 Introduced 5.7.7（默认 8、最大 512），不是 5.7.8。出版前请核对一下这个小版本号。

3. 【2.2.1|深度广度】渐进式 rehash 一节讲了 fork 子进程期间"定时搬迁暂停"，却没讲同一个场景的另一半：fork 期间 `dictResize` 被整体禁用，扩容阈值实际从 1 抬到 5（load factor 超过 dict_force_resize_ratio 才强制扩）。"通常为 1"的"通常"背后就是这个例外，它恰恰是生产上 RDB fork 期内存/COW 尖峰的著名来源——书里讲了 fork 的一支略了另一支，我读到"（通常为 1）"时停下来找了半天没找到下文。

4. 【图2-2|图示】图 2-2 的红色查找路径在第 2 层的 9 处选择继续下沉，而不是横向走到同层明明已画出的 17——这只在 Redis 严格小于的比较语义（`x->forward->score < score`，为 span/rank 计数服务）下才成立，教科书跳表（≤）会先在第 2 层跳到 17 再下沉。SVG 源码注释里写了"符合 Redis 严格 < 比较"，但读者在书页上看不到注释，正文和图注也没解释，懂跳表的读者第一眼会以为这条路径画错了。

5. 【2.3.3|技术事实】"零拷贝让一批消息不进用户态，直接从页缓存送到网卡"缺了两个关键限定：这只发生在 Broker→消费者的 Fetch 方向（sendfile），且仅在无需格式转换时成立——老客户端要降级转换时数据仍要进用户态。这句话紧跟在 Produce/Fetch 混述的段落里，前文刚讲过生产方向 Broker 要解压校验，拼在一起容易让人以为双向都零拷贝。

## 五个建议

1. 【2.5|深度广度】2.2.1 里"单一结构顾不全，就并联两个，各管一条访问路径"（ZSET 的 dict+跳表）是全章最有迁移价值的一条洞察，却只埋在结构描述中间一句带过。建议在 2.5 把它升为独立启示——图数据库一份邻接表并联属性索引与全文索引、搜索引擎倒排索引并联正排文档，都是同一模式——这比现有的启示一"结构服务目标"更能让读者带走可复用的设计动作。

2. 【2.2.2|案例示例】"一个 16KB 页就能容纳几百个键，两层内部节点、每叶几十行，千万行的表整棵树也只有三层"建议把账算出来一步：fanout ≈ 16KB/(键+子页指针)，500×500×50 ≈ 1250 万。"树极矮"从结论变成可复算的推导，读者换大键、小页或 SSD 4K 对齐时才能自己推出树高——这种算式正是本章"结构对齐介质"主题最该教的手艺。

3. 【2.2.1|结构导航】五个 Redis 结构是"名词+头部字段+策略+配图"同一节奏连排五遍，开头宣布了"偏查询效率/偏内存密度"两极分组（SDS/跳表/字典 vs listpack/intset）却没有落成结构。建议按两极拆成两个小标题，或至少在两极之间加一句过渡，阅读节奏立刻有变化，分组宣言也不浪费。

4. 【2.3.3|技术事实】零拷贝那句建议补上"仅消费方向、且无需格式转换时"两个限定词，并与 2.2.3 的"老版本客户端降级转换触发 CPU 尖刺"互相呼应——两处现在各说半句，接起来正好是一个完整的"零拷贝何时失效"闭环。

5. 【2.4 表2-2|深度广度】表 2-2 建议补一行"随机点查能力"：Redis O(1) 哈希点查 / MySQL 走 B+ 树 2-3 次 I/O / Kafka 不支持、只能按偏移量顺序消费。2.2.3 正文已经写了"随机按 key 点查完全做不到"，补进对比表后，"核心目标→数据结构→能力边界"这条 2.4 声称要展示的因果链才真正闭合。
