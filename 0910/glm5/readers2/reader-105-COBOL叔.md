# 读者105 · COBOL叔
身份：银行核心系统老开发，25年，爱好：评书
主读：第 1 章

## 五个问题
1. 【1.2.2｜技术事实】"它 1995 年起源于瑞典 MySQL AB"——1995 年发布的是 MySQL 这个软件，MySQL AB 这家公司 2001 年才由 Widenius 等人注册成立，软件和公司是两本账，时间线对不上；表 1-1"出身"行同样写"1995，MySQL AB"，一起改了才干净。
2. 【1.3.3｜技术事实】第三层追问先把物理日志定义成"记'哪个字节改成什么样'"（原文如此），紧接着 MySQL 一段又承认 redo 是"物理到页、逻辑到操作的混合日志"——二分框架在自家例子里就破了，且"哪个字节"把物理日志的粒度说绝了，InnoDB 这类页级日志并不记到字节。
3. 【1.3.1｜读不懂】表 1-2 MySQL 行"架构视角"栏里那句"日志作为数据正本，边界到哪为止？"没头没尾：什么是"数据正本"？"边界"指什么的边界？同格前半句问两阶段提交清清楚楚，这半句我读了三遍也没懂它想问什么。
4. 【1.2.2｜表达可读】"在每次提交都刷盘的配置下，事务提交需要等待日志落盘，可通过 fsync 等机制把缓冲的写强制刷到磁盘"——主语半路换车：先说提交等待，又跳到"可通过 fsync 刷盘"，因果绕了一圈。这本是讲"代价"的段落，读起来却要自己拆装句子。
5. 【1.1.2｜结构导航】"单分区吞吐的量级见第 7 章关键数字"不挂节号，读者翻到第 7 章也不知道"关键数字"藏在哪一节；1.3.3 的"详见第 8 章"同病。要么给节号，要么删掉这半句，别让人扑空。

## 五个建议
1. 【1.3.3｜深度广度】序言主张"这些问题几十年前的计算机底层设计早已出现过"，那讲 WAL 与两阶段提交时不妨点一笔血统：大型机 DB2/IMS 的双路日志、CICS 的 syncpoint 两阶段提交，上世纪 80 年代就在银行生产上跑了。一句"祖师爷"交代既坐实序言论点，也照顾我这种大型机出身读者的旧记忆。
2. 【1.1.1｜案例示例】"异步解耦与流转"这类能力，在银行里以"文件接口 + 日终跑批"的形态存在了几十年，Kafka 本质是把同一件事实时化。建议在 1.1.1 补一句老形态对照，帮转型读者把旧经验挂到新范式上，也呼应序言"先辈早已给出方案"的主题。
3. 【1.2.2｜表达可读】上面第 4 条那句建议拆成两句：先给结论——每提交必刷盘的配置下，提交延迟里就多一段等日志落盘；再说机制——这一步靠 fsync 把缓冲的写强制刷下去。先账后因，老读者才顺。
4. 【1.1.1｜表达可读】1.2 节三家各有一句加粗的"定场诗"（"宁可慢，不可错"这类），好记好背；建议 1.1.1 三类范式也各配一句一句话定性，读者合上书至少能带走三句口诀——说书人开场也得先立人物。
5. 【1.2.4｜图示】雷达图一段行文先把五维图长篇描述完，再回头说"图 1-1 里每家标的那行'舍弃'"，然后才见图 1-2——两张图挤在一段话里，读者眼睛来回跳。建议把图 1-1 的呼应挪到图 1-2 之后或干脆删去，让文字与图一一对应。
