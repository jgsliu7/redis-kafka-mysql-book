# 读者117 · PG酱
身份：PostgreSQL 深度用户，8年，爱好：骑行台
主读：第 4 章

## 五个问题

1. 【4.4|逻辑论证】"为什么不做自己的缓冲池"的第二条理由只说"自己管内存会和 PageCache 形成双份缓存"，把重复当成了不言自明的坏处，没有论证代价是什么。PostgreSQL 就是长期跑在 shared_buffers + OS PageCache 双份缓存上，而且是官方推荐姿势（shared_buffers 通常只给约 25% 内存）——同一份数据确实占两处，但换来的是 OS cache 的灵活调度。双份缓存本身是可以成立的取舍，书里的推理在懂 PG 的读者这里不闭环。

2. 【4.3|技术事实】双写缓冲一段写"redo log 也救不回来，因为它记录的是'怎么改这个页'，前提是这个页本来是好的"——这是 InnoDB physiological redo 的性质，却被表述成 redo log 的通则。PG 的 WAL 开启 full_page_writes 后，checkpoint 后首次修改某页会把整页镜像写进 WAL，恰好就能从"页写到一半"的损坏中恢复。不点明"没有整页镜像的 redo 才救不了撕裂页"，读者会带走一个错误的一般化结论。

3. 【4.5|深度广度】表 4-3 和 4.5 说 MySQL 崩溃恢复是"重放 redo log + 恢复脏页"、"重放 redo log 较快"，全章没有出现 undo log 的回滚阶段：崩溃时未提交的大事务要靠 undo 反向回滚，这一步可以远慢于 redo 重放（大事务回滚以小时计并不罕见），开 binlog 后还有内部 XA 的恢复判定。"MySQL 恢复快"的印象对做容量规划的人是有误导的。

4. 【4.3|表达可读】`innodb_flush_log_at_trx_commit=1` 那句"存储系统正确履行刷盘请求，是掉电后保留这些日志的前提"读起来像免责声明，读不出所指。它背后其实是盘端易失写缓存这个经典坑——没有电容保护的 SATA 盘可能对 fsync 撒谎。不展开半句，多数读者不明白为什么设成 1 了还需要"前提"。

5. 【4.2|技术事实】小节标题是"内存淘汰的真实实现"，正文给的却是 Redis 2.x 语义："随机采样 N 个，从中淘汰最久未用的那一个"。3.0 起采样键先进一个容量 16 的淘汰池（eviction pool），淘汰是从池中挑最差者，候选可以跨多轮淘汰存活——被淘汰的键未必来自本轮样本。图 4-2 左半"采样池→淘汰最差"画的同样是老模型，标题承诺与内容不符。

## 五个建议

1. 【4.3|深度广度】双写缓冲处值得加一句同题对照：PG 面对同一个撕裂页问题选了另一条路——full_page_writes，在 checkpoint 后首次改页时把整页镜像写进 WAL，用日志膨胀换掉双写区。同一故障、两种行业解法、两份不同代价，正好是全书"取舍"主题最硬的注脚，也给懂 PG 的读者一个锚点。

2. 【4.4|逻辑论证】给"双份缓存"这条理由补上真正的代价：Kafka 跑在 JVM 上，堆内缓存意味着一份 OS 无法复用的堆内存、额外的 GC 压力，以及内核到用户态的一次多余拷贝。点破这层，"不自建缓冲池"才从直觉升级成推理，也解释了为什么同样的双份缓存在 PG（原生 C、堆外共享内存）那里代价可接受。

3. 【4.6|深度广度】启示二"缓存建在哪一层"的三分法（Redis 进程内 / MySQL 进程内 / Kafka 内核）建议加一条中间档的脚注：PG 故意两层都建——进程内 shared_buffers 用 clock-sweep 低精度淘汰，其余交给 OS cache，用淘汰精度换内存利用率和实现简单。这样"需要淘汰精度才自管内存"的因果就有了反例参照，规律从三选一变成一条谱线。

4. 【4.1|图示】图 4-1 用红框强调"顺序 vs 随机：差距在吞吐（带宽 vs IOPS）"，但整张图只有延迟柱，没有任何吞吐信息，论点无图可依。建议并排补一个小图：同一块 SSD 的顺序写 GB/s 与随机写 IOPS（按 4KB 折算成 MB/s）对比，4.1 的核心论点"SSD 上差距移到吞吐"才能一眼看懂。

5. 【导读|版本时效】导读选型争论里有人坚持"MySQL 有内存表和 Query Cache，够用了"，建议加半句注说明 Query Cache 已于 MySQL 8.0 移除（5.7.20 起废弃）。故事本身生动，但 2026 年的读者按字面理解会以为这仍是站得住的论据，而这恰是那个论点里最过时的一块。
