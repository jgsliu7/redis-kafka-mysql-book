# 读者107 · 搜索客
身份：ES/Lucene 工程师，7年，爱好：目视观星
主读：第 2 章

## 五个问题
1. 【2.2.1|技术事实】"上面几层是抽稀的索引层，每隔几个节点保留一个指针"与 Redis 实现矛盾：层高是插入时按 p=1/4 几何分布随机掷出来的，不存在"每隔 N 个"的规律，而图 2-2 第 2 层恰好 9/17/25 隔一留一，视觉上又强化了等距索引的错觉。后文虽有"逐层独立抛硬币"，但这句事实性描述是错的，两段并存让我停下来怀疑作者是否清楚实现。
2. 【2.2.1|逻辑论证】"跳表的缓存局部性确实不如红黑树"这个断言我不认同：两者都是堆上离散节点加指针追逐，红黑树并没有像数组/B 树那样把数据排进连续内存，谈不上局部性优势；红黑树真正的优势是每节点固定左右指针加色位，比跳表平均约 1.33 个前向指针再加 backward 和 span 更省空间。这句更像流传的教科书套话，不是论证。
3. 【2.2.1|技术事实】渐进式 rehash 只说 RDB/AOF 子进程期间"定时搬迁暂停"，漏了同一开关的另一半：此期间 dict_can_resize 关闭，命令触发的搬迁同样冻结，且扩容阈值从 1 跳到强制值 5（负载因子要涨到 5 倍才扩）。生产上 RDB 窗口内哈希表桶数不涨、链变长，正是这条分支，只讲定时那一路，读者拿书对不上现象。
4. 【2.2.2|读不懂】"长度信息按与字段相反的顺序存放，解析时从记录头附近读取这些长度"——为什么逆序？逆序后记录头处第一个长度对应的是最后一个变长列，这半句只描述了排列、没给任何设计动机（各长度值本身还是小端字节，正文也没提），我读完仍不知道 Dynamic 格式为什么值得这么排。
5. 【2.2.1（图 2-5）|技术事实】图 2-5 把 listpack 标为"List/Hash/ZSET 小数据底层编码"，但 List 类型自 3.2 起无论数据量大小都用 quicklist，listpack 只是 quicklist 节点的编码，不存在"小数据用 listpack、大了升级"的切换；把 List 与 Hash/ZSET 并列会让人去找 List 的升级路径，且全节五种结构里 quicklist 完全缺席，List 类型的底层实际被讲漏了。

## 五个建议
1. 【2.2.2|深度广度】"换哈希索引点查更快，但范围和排序完全做不到"把磁盘世界收窄成 B+ 树与哈希二选一；建议补一小段第四条路线：写多读少的目标会推出 LSM 或有序倒排（RocksDB、Lucene），同样是磁盘页约束下的另一种答案。我做 7 年倒排索引，读到这节的第一反应就是"我的结构不在这张地图上"，一句话点到即可，还能反证"目标→结构"的方法论。
2. 【2.3.3|深度广度】零拷贝建议补上前提：sendfile 遇 TLS 连接失效，Broker 只能退回用户态加解密与拷贝。现在写成无条件收益，读者给集群开 TLS 后吞吐掉一截，会回头怀疑这本书。
3. 【2.4|逻辑论证】表 2-2 与启示四把 MySQL 能力标志和 Kafka api_version 并列为两个例证，却没点破差别：位标志数量有限、表达不了同一 API 的多版本 Schema，这正是 Kafka 改用 per-API 版本号要解决的问题。补上这层对照，启示四才从"举两个例子"升级为论证。
4. 【本章导读|案例示例】排行榜案例建议补 ZSET 的代价边界：member 在 dict 和跳表里存了两份、全内存驻留，给出百万 member 量级的内存直觉，以及榜大到内存放不下时回到磁盘结构的翻盘点——"Redis 赢"是有条件的赢，条件正是本书反复讲的取舍。
5. 【2.2.1（图 2-2）|图示】正文用 span 讲名次（"span 逐层累加就是名次"），图 2-2 却一个 span 都没画；建议在横向箭头上标跨度数字（如 head→9 标 3），并在图注补"晋升概率 1/4、平均每节点约 1.33 个前向指针"，让图与正文的概率机制、rank 原理对得上。
