# 读者129 · 保险嫂
身份：保险行业 IT 安全，13年，爱好：十字绣
主读：第 6 章

## 五个问题
1. 【6.5|逻辑论证】书里把"自定义 ProducerInterceptor / ConsumerInterceptor 在客户端拦截并写审计主题"列为 Kafka 审计的外挂补全方案之一，但审计点放在被审计方自己的客户端进程里，被审计者完全可以不加载拦截器或改写逻辑，审计主题若还在同一集群、有写权限的主体也可能动它——按内控"审计与被审计分离"的原则这不能算合规审计。希望作者说明这个方案的适用边界（信任内部客户端的场景），或把 Ranger/服务端方案作为主推荐。
2. 【6.3|逻辑论证】"授权检查时，从全局到列逐层收窄，命中即停"（图 6-4）只描述了检查路径，很容易让读者误以为列级、表级权限能在全局授权之下继续收紧。实际上 MySQL 权限只有加法没有 DENY：账号一旦在 mysql.user 全局层有 SELECT，任何下层的列级限制都形同虚设，想收紧只能回收全局再逐库补授权——我们做权限清理时最头疼的遗留问题就是这种"藏在全局层的旧授权"。作者讲了"越细越慢"的代价，却没讲这个语义陷阱。
3. 【6.5|深度广度】"社区版用户通常只能用 General Log 做近似替代"说得太绝对：Percona Server（开源、MySQL 兼容发行版）自带 audit_log 插件，MariaDB 有 server_audit，金融行业大量使用 Percona 正是冲着免费审计插件去的。一句"只能"把我们这些不买企业版也要过审计的用户的路堵死了。
4. 【6.4|深度广度】TDE 一节只覆盖了"磁盘被盗也无法直接读取"这一个威胁，没讲清边界：TDE 对所有走 SQL 进程的正常查询是透明的，DBA 直查、备份导出、SQL 注入拿到的都是明文。保险行业身份证、银行卡号这类字段的加密要求（个保法/密评）必须靠应用层加密或脱敏落地，TDE 单独过不了检查——威胁模型只画了一半。
5. 【6.5|深度广度】"务实的选择是异步写入审计日志、对日志采样"——采样会破坏操作序列的完整重建，等保 2.0 安全审计控制点和行业监管检查都要求日志完整可追溯，《网络安全法》第二十一条还要求日志留存不少于六个月。把"采样"不加限定地列为务实选择，金融行业读者照做是要在检查时挨批的，至少应注明适用边界和留存要求。

## 五个建议
1. 【6.5|结构导航】审计一节没有像 6.2/6.3/6.4 那样分 Redis/MySQL/Kafka 三个小标题分述，篇幅不到加密的一半，四维里明显虎头蛇尾。建议对齐结构补足，并加一小段"外挂之后怎么办"：日志独立采集到专用平台、留存期限、防篡改（WORM/独立权限）——这对金融、保险读者是硬需求，不是锦上添花。
2. 【6.4|深度广度】在 TDE 之后补一个"磁盘加密 vs 字段级/应用层加密"的分工说明或小表：各自防什么、不防什么（离线窃取 vs 在线查询/导出），敏感字段两类要叠加使用。选型评审时这张表能直接抄进安全设计文档。
3. 【6.6|案例示例】"从姿态对比到生产底线"一节建议落成可勾选的加固 checklist（Redis：处理 default nopass、按应用建账号、限定键前缀、ACL LOG 外采；MySQL：--initialize、清理匿名账号、FILE 等高敏权限审查；Kafka：三重点已列出）。6.7 说启示"能直接拿去对照"，但现在的散文形态不好搬，从监管检查角度看 checklist 才是能贴在巡检单上的东西。
4. 【6.2|图示】图 6-2 图注"内部 SASL_SSL、外部 SASL_SSL、控制面 KRaft 三条路径并行"——第三条只写"KRaft"没标协议与认证方式，而正文说控制面可用双向 TLS 也可用 SCRAM（3.5.0 起），对着图分不清这条线到底是什么。建议三条路径统一标注"协议+认证机制"，让"按网络域分级信任"一眼可读。
5. 【序言|结构导航】序言的读者定位只有"后端工程师、架构师、技术负责人"，但第 6 章"我做安全评审先看两件事"这类内容对企业安全、合规岗位同样直接可用，可能是全书最贴近安全评审实务的一章。建议在序言的读者段补一句安全/运维/SRE 读者的对号入座指引，别让这本书被当成纯开发书错过。
