# 读者128 · 公链喵
身份：区块链公链开发，6年，爱好：养鹦鹉
主读：第 6 章

## 五个问题

1. 【6.4|逻辑论证】6.1 给存储加密立的威胁模型是"磁盘被盗也无法直接读取"，6.4 又说社区版可用本地文件型 `keyring_file`——密钥文件和密文在同一台机器的磁盘上，整盘被盗时两者一起到手，恰好击穿 6.1 立的模型。书里只提醒了"密钥丢失导致数据不可读"这一半，没提密钥与密文同盘共址这一半（MySQL 文档自己也声明 keyring_file 不适用于合规场景）。做密码学应用的人读到这两节会对不上。

2. 【6.2|读不懂】"Kafka 3.5.0 也加入了 Broker 到 Controller 的 SCRAM 支持；这与 Controller 之间的共识连接不是同一条路径。后者在 3.5.1、3.6.0 曾出现用 SCRAM 启动集群失败的问题"——全段没有挂任何 KIP/JIRA 编号，我读完只留下两个版本号，读不懂三件事：到底哪条路径允许 SCRAM、启动失败的具体机制是什么、现在还能不能上生产。我自己回头查到 KIP-900（kafka-storage.sh 的 --add-scram）和 KAFKA-15513 才拼起来，正文至少应挂一个编号。

3. 【6.2|图示】图 6-2 里 INTERNAL 和 EXTERNAL 两个监听器协议都写着 SASL_SSL，"监听器分层"的教学点是不同网络域配不同信任等级，但图里两条路径连协议都相同，只差证书与颜色，第一眼看不出"分层"到底分掉了什么；且控制面框写"协议：SSL"是单向，正文说的是"启动前备好证书的双向 TLS"，差一个 mTLS 字样，关键差别丢了。

4. 【6.2|逻辑论证】"把组角色这类复杂语义留给外部的身份管理系统（IAM），是 Redis 一贯划分边界的做法"——开源 Redis 根本没有让外部 IAM 挂进认证/授权决策的接口（MySQL 的可插拔认证插件才是真扩展点），外部身份体系现实里只能落在代理层或 Redis Enterprise 上。把"没做"说成"主动留给外部"，再把 MySQL 插件接口拉来类比为同一种工程哲学，这个类比我不服。

5. 【6.5|技术事实】"自定义 ProducerInterceptor / ConsumerInterceptor 在客户端拦截并写审计主题"被列为生产环境的补全手段，但客户端拦截器只能看到客户端自己发出/收到的消息——Broker 端被 ACL 拒绝的请求根本不经过它，而"谁被拒了"恰是同段承认 Authorizer 日志在默认级别下覆盖不到的部分。拿客户端拦截器补审计，补不上的正是最需要审计的那一块。

## 五个建议

1. 【6.2/表6-1|深度广度】把三家凭证存储的密码学属性并排讲透：Redis 是裸 SHA-256（无盐、无迭代）、MySQL caching_sha2_password 的 authentication_string（`$A$005$` 前缀）是盐加 5000 轮迭代、Kafka SCRAM 是 RFC 5802 的盐加迭代。三个事实书里分别都摸到了，就差一张小表把"存口令必须加盐慢哈希"这条贯穿三家的同款教训钉死——这正是本章横向比较方法最出彩的落点。顺带补一句 Redis AUTH 的密码是明文过网络、所以必须配 TLS，正好与 Kafka PLAIN 那句对仗。

2. 【6.2|深度广度】6.1 承诺"节点对节点、控制面对数据面都要做身份认证"，MySQL 有 REPLICATION SLAVE 权限、Kafka 有 inter-broker SASL，唯独 Redis 的 masterauth 共享密码和 Cluster 总线认证全章一字未提——而"诱导受害副本向伪造主节点同步"正是无认证复制的经典攻击面。给 Redis 节点间认证哪怕两三句，6.1 立的四类身份才算闭环。

3. 【6.5|案例示例】"社区版只能用 General Log 近似替代"会把读者堵死：Percona Server 的开源 Audit Log 插件、MariaDB 的 audit 插件都是兼容生态里的现成方案，值得点名。Kafka 侧若推荐拦截器写审计主题，应同时说明它覆盖不了 Broker 端拒绝事件，需要 Authorizer 日志或 Broker 端插件配合，否则读者照做会留下审计盲区。

4. 【6.6 表6-1|版本时效】对比表把 Kafka 钉在 3.x：Kafka 4.0（2025-03）已删除 ZooKeeper 模式，表里"ZooKeeper 模式的 AclAuthorizer"在 4.x 只剩历史意义；MySQL 侧 mysql_native_password 在 8.4 默认禁用、9.0 移除，而正文停在"8.0.4 改默认"。建议表下加一行版本基线与成书时点说明，不然 2027 年的读者会对着 3.x 的表去配 ZK 集群。

5. 【6.7 启示四|深度广度】身份跨跳传递的设计空间画少了一个角：委托令牌、服务账户、代理传递之外，还有"每操作端到端签名"——公链每笔交易自带签名，中间任何一跳都无法伪造或降级原始身份，Web 侧的对应是 SPIFFE 短期证书加请求级 HMAC。既然设问是"身份如何在跳与跳之间安全传递且不被伪造"，这个最硬的答案值得占一句。
