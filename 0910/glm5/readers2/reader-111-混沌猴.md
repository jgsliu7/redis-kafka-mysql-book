# 读者111 · 混沌猴
身份：混沌工程工程师，5年，爱好：蹦床
主读：第 3 章

## 五个问题
1. 【3.6（呼应本章导读）|逻辑论证】导读说事故是「敲下 kill -9」丢了数据，结尾复盘却说「没等 AOF 刷完就杀了进程」「问题出在我没给它落盘的时间」。kill -9 是 SIGKILL，Redis 根本没有任何机会刷 AOF，不存在「给它时间」的问题；「没等 AOF 刷完」描述的更像是优雅关闭进行到一半被补刀强杀。这是两种不同的故障注入（直接 SIGKILL vs 优雅关闭中途打断），丢数据面不同（everysec 下前者约丢 1 秒，后者可能更多），全章的定盘事故归因应当说清是哪一种。
2. 【3.2|读不懂】「关闭：两种触发，一套流程」说无论哪种触发只是「存不存数据」这一步的选择不同，并说这一步「由你通过 SHUTDOWN SAVE / NOSAVE 显式指定」。但 SIGTERM / systemctl stop / K8s 滚动重启这条最常见的路径根本带不了参数，此时到底走 SAVE 还是 NOSAVE，本节没有交代；答案（等价于不带参数的 SHUTDOWN，按 save 配置决定）要等到 3.4 容器化一节才间接补出，「由用户显式指定」的说法与默认行为相互矛盾。混沌平台注入 SIGTERM 前最需要的就是这个预期：注入后 Redis 会不会先做一次同步全量 SAVE。
3. 【3.4|技术事实】启动第 3 阶段说「每个分区都要单独校验、单独重建索引，没有批量恢复这种捷径」，未区分干净关闭与崩溃后启动：受控关闭后的正常重启，recovery point 已在日志末尾，不需要 CRC 校验和重建索引，耗时大头是打开海量段文件、加载索引；只有脏关闭才触发校验与截断。滚动重启与崩溃恢复的启动耗时是两个量级，我们做演练基线必须分开测，书中表述会让人高估日常重启的恢复成本。
4. 【3.3|深度广度】全章用 kill -9 贯穿（导读、3.4 容器化、表 3-1 档位 2「近乎 kill -9」），但从未区分 kill -9（进程级故障：OS page cache 还在，文件不会半写）与断电（节点级故障：OS 缓冲一并丢失，可能产生 torn page）的破坏面差异。而这正是图 3-4「redo 无差别重放」能成立的前提——物理重放要求页本身完整，InnoDB doublewrite 就是为这个边界存在的；不点破这条边界，读者会误以为 kill -9 也能造成物理页损坏。
5. 【3.3|表达可读】「崩溃恢复的耗时取决于崩溃那一刻 redo log 里有多少未落盘的修改」有歧义：按字面读是「redo 本身尚未落盘的部分」，而那部分恰恰已经丢失、根本不参与重放；真正决定重放量的是「已写入 redo 但对应数据页尚未刷回数据文件」的修改，即 checkpoint 之后的 redo 积压。图 3-4 步骤②「收集未落盘的页修改」是同一表述；预估恢复时长时这个变量必须指准。

## 五个建议
1. 【3.5|结构导航】导读用「同样是 kill -9，三个软件后果不同」开场立钩子，但表 3-2 的六个维度里没有「非优雅终止（kill -9）的后果」这一行。建议补上（Redis 丢最近一次 fsync 之后的写入 / MySQL 下次启动走完整崩溃恢复 / Kafka 靠心跳超时触发重选举），把导读的承诺在横向对比表里兑现。
2. 【3.3|案例示例】「崩溃恢复的耗时取决于……」与「大事务回滚非常慢」都缺量级锚点。建议补一两个实践数字：多少 GB 的 redo 积压或多大的未提交事务大致对应几分钟恢复、回滚与正向执行的速度比大概是几倍。容灾演练和 RTO 评估都靠基线数字反推，读者拿到数字才能算自己的 grace period。
3. 【3.2|图示】图 3-2 画了启动四段，但四段都没标耗时量级。建议给每段标注（配置、基础设施为毫秒到秒级，数据恢复随数据量线性、是唯一分钟级显著段），让读者一眼看出「就绪时间 ≈ 数据恢复时间」，几十 GB 实例的就绪预估才有抓手。
4. 【3.6|深度广度】3.4 末尾的「实践清单」只有两条，而正文的实操数字散落三大段（Redis 的 30 秒 grace period 陷阱、MySQL 建议 120 秒以上、Kafka 建议 60–120 秒并调大重试、startup probe 兜底慢启动）。建议扩成一张可勾选清单，把三家的 grace period 与探针做法集中排列，发版/演练前照单核对，不必往回翻正文拼数字。
5. 【3.4|表达可读】实践清单里「preStop hook 主动检查条件而非 sleep」说得太一刀切：sleep 的正当场景是等 endpoints 摘除传播（摘流是异步的，主动检查落盘救不了流量继续打进正在退出的 Pod），主动检查适合确认落盘、迁移这类自身状态。建议改成按目的选手段，并各配一个例子。
