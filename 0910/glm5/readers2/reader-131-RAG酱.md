# 读者131 · RAG酱
身份：LLM 应用工程师，3年，爱好：盲盒
主读：第 7 章

## 五个问题
1. 【7.4.1|版本时效】"没有 key 时，Kafka 2.4 经 KIP-480 引入默认粘性分区；在本章的 3.9 基线中，默认逻辑向一个分区累计发送至少 batch.size 字节后再切换"——按我的理解，"累计 batch.size 再切换"且粘住的是 broker（跨主题合批）是 3.3 的 KIP-794 行为，2.4 的 KIP-480 只是主题内粘住、批满即换。书里不提 KIP-794，读者容易把 3.3 之后的行为记成 2.4 就有，建议核对这半句的版本归属。

2. 【7.3|逻辑论证】本章开头说"MySQL 的集群目标是'不丢数据'，从异步复制到组复制始终没变"，但 7.3.1 又自己承认异步复制"主节点宕机后转移到从节点时，可能缺少已经提交的事务"。这句话到底想说"演进方向是不丢数据"还是"MySQL 复制一直不丢数据"？按现在的写法，跳读者很容易读成后者，与后文自相矛盾。

3. 【7.2.3|技术事实】16384 的折中论证给了两个规模锚：正文说"按约 100 个主节点平均分配……每个主节点分到约 160 个槽"，"关键数字"框又说"官方建议的最大规模约为 1000 个节点"（1000 主时每主只剩约 16 个槽）。设计时真正的锚是 100 还是 1000？两个口径并列又没有调和，这个"折中"折的是哪头，我没读懂。

4. 【7.1 / 7.6 启示一|深度广度】"分片解决扩展、副本解决可用性、两者正交"在非 key 寻址的负载上边界不清：做向量检索时（我们生产用 Milvus/Qdrant 这类），ANN 查询要扇出到所有分片再归并，分片数直接决定单查询 P99——最慢分片说了算，分片不只是扩容量/吞吐，还重塑延迟形态。7.1 只用"请求能否并行处理"一句带过，就把"分片=扩展"当普适规律放进启示一，我认为需要标注适用边界。

5. 【表 7-1 / 7.3|深度广度】表 7-1 的 MySQL 列实际是拿 MGR 代表整个 MySQL："故障检测与 Leader 选举"行只写 XCom/Paxos 协调与自动选 Primary，而 7.3 讲的异步/半同步路线的故障转移靠什么（MHA/Orchestrator 这类外部工具、云厂商托管 HA）全章一句没提。存量大量"MySQL 半同步 + Orchestrator"的团队对着这张表找不到自己，也容易误以为不上 MGR 就没有自动故障转移。

## 五个建议
1. 【7.4.1|案例示例】"扩分区后同一个 key 的新旧消息可能分在两个分区"值得升级成半页案例：以 doc_id 为 key 的文档更新流，扩分区那一刻起每次更新落到哪个分区就像开盲盒，消费端可能拿旧 chunk 覆盖新 chunk（我们 RAG 管线真踩过，索引里留了旧向量）。建议画出具体走线（旧消息在 P3、新消息在 P7、消费组按分区并行看到的交错顺序），再给实践中"规划死分区数/新 topic 重灌"的对策。

2. 【7.4.3 / 7.6 启示四|深度广度】启示四讲"把确认条件做成可调参数"，建议再分一层：请求级旋钮（Kafka acks 按生产者、Redis WAIT 按次调用）与集群级约束（min.insync.replicas、半同步插件）。向量库已把这一步走到极致——Milvus 允许每次查询指定 Strong/Bounded/Session/Eventually 一致性级别；补上"旋钮暴露在哪一层，决定业务开发还是运维来做取舍"，启示会从三家经验上升成通用规律。

3. 【表 7-1|结构导航】建议在表 7-1 增加一行"扩容时存量数据怎么动"：Redis 槽迁移会搬存量（ASK 兜底、客户端大体无感）、Kafka 扩分区只改新消息落点（旧数据原地不动不重分布）、MySQL 分片交给上层中间件。这是三条路线分歧最大的维度之一，也是选型最常被问到的，现有六行没有覆盖。

4. 【图 7-2|图示】MOVED 框标题"MOVED：迁移已完成"把 MOVED 的触发面收窄到了 resharding：生产里更常见的 MOVED 其实来自故障转移后槽随新主搬家、客户端映射过期。建议在 MOVED 框补一行小字；另外 ASK 框"此 key 已迁至节点 A"与"槽 8000 仍归 B"的关系（槽未动、key 先行）最好在图注点一句。

5. 【7.4.1|表达可读】"在本章的 3.9 基线中"首次出现时没有任何就地解释：我跳读第 7 章、序言里也没见过版本基线约定，第一反应是"Kafka 3.9？"，要读到 7.4.4 的 KRaft 时间线才反应过来。建议首次出现处就地括注（指 Kafka 3.9，版本基线约定见第 1 章），照顾跳读读者。
