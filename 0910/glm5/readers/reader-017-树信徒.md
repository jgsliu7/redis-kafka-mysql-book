# 读者017 · 树信徒
身份：数据库内核爱好者，6年，爱好：乐高
主读：第 2 章

## 五个问题
1. 【2.2.3|术语使用】表 2-1 和图 2-7 把批内时间戳基准字段写作 `baseTimestamp`，但 Kafka 官方协议文档与 KIP-98、Java 侧 `RecordBatch` 接口里这个字段叫 `firstTimestamp`（每条记录存的是相对它的 `timestampDelta`）。61 字节头部的算法没错，可字段名和官方对不上，读者拿书去对源码或 tcpdump 抓包时会找不到这个字段。

2. 【2.2.1|技术事实】渐进式 rehash 一节说扩容阈值"通常为 1"，又专门提到"生成 RDB/AOF 的子进程运行期间定时搬迁暂停"，却漏了同一动机的另一半：子进程期间 `dict_can_resize` 被关闭，负载因子要超过 5（`dict_force_resize_ratio`）才强制扩容，为的正是防 copy-on-write 放大。只讲"暂停搬迁"不讲"提高阈值"，读者会推出"子进程期间字典仍按 1 扩容"的错误模型。

3. 【2.2.2|深度广度】"点查（从根走到叶，两到三次 I/O）"是全冷缓存口径；InnoDB 内部节点总量很小（千万行表的全部非叶页通常就几 MB 到十几 MB），实际常态是上层页常驻缓冲池、命中时点查 0 次磁盘 I/O。书里"热点页进缓冲池"一句带过，容易让读者把"三层树"记成"每次查询三次 I/O"——缓冲池命中率 99.99% 回答的恰恰是这件事，B+ 树的真正实力是"树+缓冲池"组合。

4. 【第2章导读 / 2.6|逻辑论证】把"改分的高频写"与"查名次"并列归为"B+ 树不擅长的路径"，归因不完整：单看条目移动，Redis 侧改分同样是跳表删旧插新加 dict 改值，双方单次都是 O(log N)；真正拉开差距的是 MySQL 每次改分要同时动两棵树（二级索引删插 + 聚簇行更新），还要付 redo 刷盘的钱（双 1 配置下逐事务 fsync）。结论我认，理由链少了两环。

5. 【2.3.3|技术事实】"零拷贝让一批消息不进用户态，直接从页缓存送到网卡"是无前提的绝对表述：老客户端 down-conversion、Broker 端重压缩、TLS 加密都会把数据拉回用户态、零拷贝失效——而前两类正是 2.2.3 刚点名的"Broker 端 CPU 尖刺的常见来源"。两段信息书里都有，就是没连起来，读者会把零拷贝当成 Kafka 的无条件属性。

## 五个建议
1. 【2.2.1|图示】图 2-2 画了多层链和查找路径，一条 span（跨度）都没标，而正文刚讲完"span 逐层累加就是名次、ZREVRANK 靠它 O(log N)"。建议给前进指针标上 span 值，再加一条"查找路径上 rank 累加"的示例线，让排行榜案例的另一半在图上闭环。

2. 【2.2.2|深度广度】"一个 16KB 页几百个键、每叶几十行、千万行三层"是三个孤立数字，建议把树高算术摆出来：16KB ÷（键+子指针）≈ 扇出，千万行 ÷ 每叶行数 ≈ 叶子页数，两层内部节点刚好覆盖。读者换成自己的行宽键宽就能算自己的树高——这是我做容量评审时真正在用的公式，比记住"三层"有用。

3. 【第2章导读|案例示例】排行榜案例建议补两刀堵住 MySQL 侧的退路：`SELECT COUNT(*) WHERE score > x` 走覆盖索引仍要逐条数（B+ 树叶层没有区间基数聚合），把名次反规范化成一列又引入高并发改分下的一致性维护。把"为什么不在 MySQL 里自救"讲完，"访问方式与结构不匹配"的结论才无懈可击——这是 MySQL DBA 的第一反问。

4. 【2.2.3|深度广度】"差值编码把每条记录的元数据开销降到个位数字节"只有结论没有账。建议给 V1 与 V2 的字节对照：V1 每条消息约 34 字节固定头（offset/size/crc/magic/attributes/timestamp/keyLen/valueLen）对 V2 单条 record 摊薄后的字节数，或在图 2-7 旁加一列 V1 布局做参照——字节账是"批量+差值"最硬的证据。

5. 【2.2.1|术语使用】intset 的两条路径都叫"升级"（编码升级/类型升级），但第一条是 intset 自身的整数加宽，第二条是整个底层结构换掉（源码里是 encoding 转换），共用一词容易让读者当成同一机制。建议第二条改叫"底层编码转换"；图 2-5 同时可把升级终点用箭头连回第一行的 hashtable/skiplist 卡片，不必全靠绿色文字框转述。
