身份：K8s 平台工程师，6年，爱好：皮划艇
主读：第 3 章

## 五个问题

1. 【3.4|逻辑论证】「实践清单」里「preStop hook 主动检查条件而非 sleep」我不认同：preStop 里 sleep 几秒对冲的正是 endpoint 摘除传播与 SIGTERM 几乎并发这个竞态——摘流后客户端连接池里的长连接照样把新请求送进来。书里没解释 sleep 在对冲什么就否定它，也没给「检查条件」的落地路径（查本 pod IP 是否还在 Endpointslice 需要 RBAC 权限，普通业务 pod 拿不到），照清单做的人反而会掉进更深的坑。

2. 【3.4|结构导航】「容器化环境下的生命周期」小节（terminationGracePeriodSeconds、preStop、探针、三家各自的 grace period 建议）内容覆盖 Redis/MySQL/Kafka 三家，却整个埋在 3.4「Kafka 的做法」内部。我在 3.4 里读到 Redis 的 RDB 落盘分析和 MySQL 的 innodb_fast_shutdown 时非常错位，按目录找容器内容也找不到——这段是全章统合，不该挂在任何一家名下。

3. 【3.6|逻辑论证】结尾事故复盘说「没等 AOF 刷完就杀了进程」「Redis 本来是会落盘的，问题出在我没给它落盘的时间」，但导读说的是敲了 `kill -9`——kill -9 根本不给进程任何清理机会，丢数据是必然结果而不是「没等够时间」的问题，「给它时间」只对 SIGTERM 优雅关闭路径成立。两处对 kill -9 语义的表述互相矛盾，复盘结论没有准确归因。

4. 【3.1|技术事实】「Redis 的 `kill -9` 之所以『只是丢几秒数据』」断言过强：出厂默认只有 RDB save 点（如 3600 1 300 100 60 10000），没开 AOF 时，kill -9 丢的是自上次快照以来的全部写入，最长可达小时级。导读 7 行明明说了「丢多少取决于持久化配置」，15 行却拿「几秒」当通例解释，默认配置下严重低估丢失窗口。

5. 【3.4|读不懂】Redis 的 preStop 方案（186-188 行）我拼不出完整时序：先说「preStop hook 可以先触发 BGSAVE」，紧接着说「必须在 fork 前停写」——那停写应该发生在触发 BGSAVE 之前，句子顺序是反的；「确认本次快照成功完成」要怎么确认（轮询 INFO persistence 的 rdb_bgsave_in_progress 还是比 LASTSAVE 时间戳）、「停写」用什么手段（CLIENT PAUSE WRITE？）一个都没给。我是要拿这段去写 hook 的人，读完还是不知道步骤怎么串。

## 五个建议

1. 【3.4|结构导航】把「容器化环境下的生命周期」从 3.4 拆出来升级为独立一节（如 3.5），并进目录。如今多数生产部署在 K8s 上，这段是全书对平台工程师最有用的内容之一，值得一个能被目录索引到的位置；顺带也解决 3.4 标题叫「Kafka 的做法」却装了三家内容的错位。

2. 【3.4|案例示例】Redis 的 preStop 方案给出可直接落地的命令序列：CLIENT PAUSE WRITE 停写 → 触发 BGSAVE → 轮询 INFO persistence 直到 rdb_bgsave_in_progress:0 且 rdb_last_bgsave_status:ok → SHUTDOWN NOSAVE。现在 186-188 行只说了目标（停写、确认完成）不说手段，平台工程师拿到就能用和拿到还得自己查文档，是两种读者体验。

3. 【3.4|深度广度】194 行探针段讲了三类探针的职责区分，但没讲 readiness 到底查什么：MySQL 从库只做 SELECT 1 会把延迟几小时的从库当就绪，应该查复制状态（Seconds_Behind_Master）；Kafka broker 端口通不等于元数据/controller 就绪。「进程活着」≠「服务就绪」是 K8s 上跑数据库最深的一层坑，作者已经写了 liveness 误用的真实案例，再往前一步就是检查内容。

4. 【3.6|案例示例】事故复盘补齐当时的持久化配置与丢失边界：AOF 开没开、fsync 策略是什么、恢复后丢的时间窗多大，让「十几条订单」可归因；同时把「没等 AOF 刷完」改成与 kill -9 语义一致的表述（比如当时根本没开 AOF，丢的是整个快照间隔）。导读、3.1、3.6 三处对这次事故的描述就能对上口径。

5. 【3.4|深度广度】Kafka/MySQL 的容器化建议补上编排层的关键一半：这两类服务在 K8s 上靠 StatefulSet 按 ordinal 反序逐 pod 终止（配合 PodDisruptionBudget 兜底）保证同一时刻只关一个实例，这才是「关闭是集群事件」在 K8s 上的另一半实现。只调 grace period 和受控关闭参数、缺了串行重启这个开关，滚动更新照样可以同时杀掉多个 broker。
