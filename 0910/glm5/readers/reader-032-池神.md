# 读者032 · 池神
身份：MySQL DBA(buffer pool 方向)，12年，爱好：功夫茶
主读：第 4 章

## 五个问题
1. 【4.3|技术事实】"核心假设"一节写"没命中就要读磁盘，延迟会高出两三个数量级"，但 4.1 正文说"内存访问与磁盘随机访问的延迟相差三到五个数量级"，关键数字框又说"高三个数量级"——同一事实全书三种口径。按表 4-1 自家基准（内存 ~100ns、SSD ~100μs、机械盘 ~10ms）验算：SSD 是 3 个数量级、机械盘是 5 个数量级，"两三个"偏低，跟我这种拿数字对表的读者第一眼就撞上。
2. 【4.3|版本时效】"三个辅助结构"一节给双写加了"MySQL 8.0.20 起独立成文件"的版本注记，但对修改缓冲和 AHI 只字不提版本变动。我查证过：MySQL 8.4 LTS（2024-04）已把 `innodb_change_buffering` 标记废弃且默认关闭、`innodb_adaptive_hash_index` 默认改为 OFF，2026 年出版的书照 8.0 口径平铺直叙，读者拿 8.4/9.x 生产环境对照会产生"我库里怎么看不到这结构在干活"的困惑。
3. 【4.6 启示三|逻辑论证】不认同把 MySQL `innodb_flush_log_at_trx_commit=2` 与 Redis `everysec` 并列成"很多时候答案是各自的中间档"。everysec 崩溃丢的是缓存写、多数可从源库重建；=2 在 OS 崩溃时丢的是已提交事务，两者后果完全不对称。我 12 年经手的交易/账务类 OLTP 清一色默认 1，=2 只敢给日志表和测试库用，把 2 当常规推荐对新手 DBA 是个坑。
4. 【4.1 表 4-1|表达可读】"相对内存（延迟以内存为 1）"这一列前四行是延迟倍数（0.01×/1×/~1000×/~100000×），到两行吞吐却换成了文字化的吞吐对比（"约相当于单线程内存随机读""进入一个数量级以内"）。同一列混两种口径、单位还是隐含的，我泡茶的工夫对了两遍才确认它想说什么，建议拆开。
5. 【第4章导读|版本时效】导读选型争论里同事的论据"MySQL 有内存表和 Query Cache，够用了"，作者用访问模式反驳了，却没点破 Query Cache 在 MySQL 8.0（2018 年）就已移除、MEMORY 引擎也是遗留特性。留着这个 8 年前就退役的特性当论据而不加注，2026 年的新读者可能真以为 Query Cache 还能选。

## 五个建议
1. 【4.3|深度广度】缓冲池一节讲了三分链表和 midpoint，但 DBA 最需要的两个落点没讲：`innodb_buffer_pool_size` 怎么定（工作集估算 vs 老的"物理内存 50–75%"经验法，多实例/容器时代比例法已失效），以及命中率去哪看（`SHOW ENGINE INNODB STATUS` 里的 Buffer Pool Hit Rate，或 `Innodb_buffer_pool_read_requests` 与 `_reads` 之比，经验健康线 99.9%+）。4.7 都说命中率是"需要持续关注的核心指标"了，读者却不知道去哪看。
2. 【4.3|版本时效】给修改缓冲补一句"8.4 起废弃且默认关闭，官方理由正是现代 SSD 让随机 I/O 变便宜"、给 AHI 补一句"8.4 起默认关闭"。顺手把这件事用起来：它恰好是 4.1"这套设计诞生于机械盘时代，到 SSD 上收益变化"的活案例——官方在用硬件演化反过来回收旧取舍，比单纯讲参数更有"观察笔记"的味道。
3. 【4.6 启示三|深度广度】建议把"中间档"从并列改成按丢失后果分层：加一张小对照表写清各中档崩溃时丢的到底是什么（Redis everysec 丢缓存写、可重建；MySQL=2 丢已提交事务、通常不可接受；Kafka acks=1 丢未复制的消息、可靠生产者重发补救），并明确一句"交易类负载 MySQL 应默认 1"。这比"很多时候答案是中间档"一句带过更可操作，也保住了作者自己强调的"不能等同"的严谨。
4. 【4.1 表 4-1|表达可读】把第三列拆成"延迟比（×内存）"与"吞吐比（×单线程内存随机读）"两列，或在表头显式声明两种口径。"内存 1 秒→SSD 17 分钟→机械盘 28 小时"这组换算我验过、非常好，建议照同样风格给"顺序写 vs 随机写"再补一个换算锚点，全书数字就都能一眼对表了。
5. 【4.3|案例示例】"跑一次大报表之后整体延迟上升"这个现象讲得很准，但没有数字。建议补一个可复现的一手案例（例：64GB 缓冲池、1TB 库，报表扫过 200GB 冷数据后命中率从 99.9% 掉到 9x%，P99 从几毫秒涨到几十毫秒，热数据回温要数小时），再接上"midpoint 只能缓和、挡不住 I/O 带宽被占"那句结论——4.2 有选型争论、4.4 有零拷贝路径，唯独 MySQL 侧缺同等颗粒度的实战案例，这恰是我这类读者最有代入感的部分。
