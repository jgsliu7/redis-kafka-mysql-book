# 读者088 · 弱网
身份：边缘计算研发，5年，爱好：桨板
主读：第 9 章

## 五个问题
1. 【9.2|逻辑论证】增量同步末段给了追赶公式 `B/(C-W)`，也点明"C 小于 W 时副本越落越远，调大 backlog 只能延后问题"，但之后就没了下文——净追赶能力为负的系统到底该做什么（限主写入、把副本摘掉重建、还是接受降级读），一句处方都没有。我维护的边缘节点常年处于 C<W 的状态，这段读下来是诊断书却没有药方。
2. 【9.3|技术事实】GTID 一节写"副本把已经接收或提交的 GTID 集合告诉新主"。按 MySQL 手册，AUTO_POSITION 握手里副本上报的是已执行（executed）GTID 集合，已收进 relay log 尚未回放的事务并不在其中；"接收或提交"的并列表述让我以为 retrieved set 也参与定位，会推出与实际不符的重发行为。
3. 【9.3|读不懂】分布式恢复里"`group_replication_clone_threshold` 的默认值是 GTID 事务序号上限，实际上不会仅因缺口大而触发 clone"这两句我反复读了三遍没懂：默认值究竟是多少、既然默认不触发那这个参数在什么条件下才生效、为什么要把默认设成一个事实上永不触发的值。
4. 【9.4|读不懂】Tiered Storage 段说副本"从远程段恢复 leader epoch、生产者快照等辅助状态，再从对应远程段之后继续拉取本地日志"——副本到底要不要去远程存储把缺的数据段读回来？按 KIP-405 我的理解是 follower 可以直接从远程层补拉历史段，书里的读法像是只对齐元数据、不读远程数据，这和"本地保留窗口覆盖副本落后量"的建议对不上。
5. 【导读|结构导航】导读用"缓存和数据库不一致时该以谁为准"加上作者自己的双写顺序案例开篇，但那是双写路径的原子性问题，不是本章讲的复制同步；冲着缓存一致性翻进来的读者，读完一整章只在 9.7 拿到"数据库是正本、缓存是可重建的派生数据"一句话，钩子和正文没有对上。

## 五个建议
1. 【9.6|深度广度】建议在启示或反模式之后补一小段"这套模型的边界"：三个软件对历史分叉的处理全是截断/覆盖、以主为准，前提是单写者；一旦两端都能写（多主、离线双写），位点模型里就没有合并的位置，需要 LWW/CRDT/向量时钟另一套工具。做边缘离线同步的读者拿本书对照自己系统时，最需要的就是这句边界声明——GTID 那句"不同源节点的 GTID 不构成一条全局递增序列"其实已经摸到偏序历史的门边了，可惜停在那里。
2. 【9.2|深度广度】backlog 的关键数字框只覆盖"秒级断线"的算术，建议补一个按断线时长分档的决策指引：秒级靠 backlog、分钟级靠调大窗口加写限流、小时级以上只能持久化位点加基线重建；顺带把 C<W 场景的处置（限写、摘副本、还是接受全量重建）写清，接住公式那段留下的悬空。
3. 【9.7|结构导航】导读的缓存一致性问题要么在正文单独成一小节（延迟双删、订阅 binlog 失效缓存、正本-派生数据的重建顺序），要么把导读钩子换成与复制直接贴题的场景——9.1 里"下单后查不到订单"的主从延迟案例就贴得多，完全可以提到导读当开篇。
4. 【9.3|版本时效】半同步改名说明框说"旧名变量在过渡期仍可用但已标记弃用"——这个过渡期到 MySQL 8.4 LTS 就结束了，旧名变量和旧语句已被移除，2026 年用 8.4/9.x 的读者按旧名去查会扑空，建议补一句版本界限。另外"不是隔离级别意义上的幻读"处最好点明 MySQL 手册把 AFTER_COMMIT 故障切换时的这个现象就叫 phantom read，免得对照手册的读者以为书与手册矛盾。
5. 【9.5|图示】图 9-3、9-5、9-7 分散在三节里各自画各家的续传流程，建议在 9.5 横向对比处补一张三者"断线重连对账对话"的并排对比图（PSYNC2 的 replid+offset 核对 / GTID 集合差集补发 / leader epoch 分叉检查），把"位点必须带历史核对"这个共同抽象在一张图里立起来——表 9-1"位点语义"一行的文字密度承载不了这层对比。
