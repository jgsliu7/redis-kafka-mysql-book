## 五个问题

1. 【2.3.2|深度广度】小节标题是"二进制封帧"，但真正的帧格式从头到尾没出现：MySQL 每个报文都是 3 字节小端长度 + 1 字节序列号打头，单包 16MB 封顶。我在 Wireshark 里切 MySQL 流量第一步就是按这 4 个字节分帧，序列号还管着请求/响应配对；书里两套整数编码讲得很细，"封帧"这个词反而落空了。

2. 【2.3.2|技术事实】"握手（服务端发送能力标志和认证随机数、客户端回传加密后的凭证）"两处不准：能力标志是双向交换，客户端在 HandshakeResponse 里也要回自己的 capability flags，走不走 SSL、用不用新行为都是那一步谈定的；另外 native_password 的凭证是 SHA1 挑战-应答哈希（scramble），不是"加密"，抓包看 mysql.auth 的响应字段就清楚了。

3. 【2.3.1|技术事实】正文用"也能用 nc 手工发送简单命令"来佐证五种前缀够用，但 nc 里直接敲的 `SET key value` 是 inline command——空格分隔、无类型前缀，和五个前缀走的是服务端两条不同的解析路径。真实客户端的命令方向全是 `*n` 数组帧，应答方向才见 +、-、:、$、*；两种线上形式被揉成了一团。

4. 【2.3.3|技术事实】"`min_bytes` + `max_bytes` 控制拉取量"把两个目标不同的参数捏在一起了：max_bytes 是拉取量上限，min_bytes 是"攒不够就等"的长轮询门槛（配合 fetch.max.wait.ms 拿延迟换批量）。调过消费者 lag 的人都清楚它是延迟旋钮，不是容量参数。

5. 【2.5|读不懂】启示四"我自己设计新协议，会先从第二个版本开始——第一个版本很少有人能把边界想全"读了三遍没敢确定意思：是"设计 v1 时就按必有 v2 的心态预留版本字段"，还是别的什么主张？这句是全章启示的落点，值得把话挑明。

## 五个建议

1. 【2.3.2|案例示例】RESP 有完整的字节串示例，MySQL 一节却全是抽象描述。建议补一段真实字节，比如 COM_QUERY 的 `1b 00 00 00 03 53 45 4c 45 43 54 ...`（4 字节报文头 + 命令字 0x03 + SQL 文本），一处示例就能把封帧、序列号、文本载荷同时讲透，也补上帧格式缺失的坑。

2. 【2.3.3|深度广度】正文说"双方用彼此都支持的最高版本号做协商"，但没讲协商是怎么发生的：客户端连上后第一件事是发 ApiVersions（api_key=18）拿各类请求的版本区间，之后每个请求的 api_version 都以此为准。讲版本化协议的章把这个 API 点一句，链条才算闭合。

3. 【2.3.3 图 2-8|图示】图里 MySQL 一栏只画了 PREPARE→EXECUTE→二进制结果集，扫一眼会以为 MySQL 协议全是二进制，和正文"经典查询的结果行走文本"及表 2-2"半可读"的口径不一致，建议该栏补一行"经典查询：文本结果集"。另外图中 `api_version=9` 是 Kafka 4.0 的版本，与正文"3.0 Broker 对 0.11 客户端"的举例时代对不上。

4. 【2.2.3 表 2-1|术语使用】attributes 的作用写"压缩类型 + 时间戳类型 + 事务标记"，漏了控制批位（isControlBatch）：事务的 commit/abort 标记恰恰是靠控制批次区分的，"事务标记"一个词盖不住。建议按位拆开：bit0-2 压缩、bit3 时间戳类型、bit4 事务、bit5 控制批。

5. 【本章导读|逻辑论证】开篇排行榜案例把"查名次"说成 B+ 树的死穴，但工程实践里给 score 加计数器列、分段桶或定时物化名次表都是常见绕法。建议先承认应用层能绕，再论证把名次内建进结构（ZSET 的 span）在实时性与一致性上为何仍占优，案例会更硬。
