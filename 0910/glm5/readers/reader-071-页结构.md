# 读者071 · 页结构
身份：存储引擎研发，9年，爱好：抱石
主读：第 8 章

## 五个问题

1. 【8.1.3 关键数字框（对照 8.2.2）|技术事实】"1GB 内存实例 ≈ 300–500MB 快照"把原因归给"紧凑二进制编码（变长整数 + LZF）使磁盘文件远小于内存实际占用"，这笔账不对：RDB 比内存小的大头是内存态每个键值对的元数据开销不落盘——dictEntry、robj、sds 头、分配器对齐，小键值对光这些就上百字节，而 RDB 只写类型码加键值净荷。且 LZF 只对超过最小长度阈值的较长值启用，短字符串根本不触发压缩；照现在的归因，读者会高估压缩、低估内存数据结构的开销。

2. 【8.5.2|逻辑论证】"定长页的空间浪费：一页里哪怕只剩几行 100 字节的记录，也要占整整 16KB，半空的页在所难免"——半空页是 B+ 树分裂与删除打洞的结果，不是"定长"的代价：顺序插入可以接近全满（InnoDB 对递增键有顺序分裂优化），随机插入平均才六七成，这是树结构的填充率属性，换变长存储单元照样有内部碎片。把树结构的账记到定长页头上，"页式管理的代价"和"B+ 树的代价"就混在一起了；何况 InnoDB 还有 COMPRESSED 行格式和透明页压缩做缓解。

3. 【8.6.6 图 8-8|图示】决策树里"需要更新磁盘中的已有记录？→否"再接"需要按索引读写数据页？→是"，最终也落到"页式范式（MySQL）"，而终点框写的是"原地改 + WAL + 双写"：一条以"不需要更新"为前提进来的路径，落点却标着专为更新付出的机制，和 8.6.6 正文"第一问决定空间管理与恢复机制"的说法对不上。这条入边要么单独标注"只读页式、无需 WAL/双写"，要么删掉。

4. 【8.4.2（对照 8.1.3 框）|术语使用】8.1.3 的框里写 LSM 的"后台合并（compaction）"，8.4.2 又定义 Kafka 的"压实（compaction）：按 key 逐步清理旧值、保留最新状态"——同一个词在相邻小节是两种机制：LSM 的 compaction 是多层有序文件归并重写，Kafka 的 log compaction 是按 key 留最新值的日志段重写，连空间回收的粒度和触发条件都不一样。我正是做 compaction 的，两个东西被同名并列，第一反应就是去想差别，书里却没有一句辨析，不熟悉的读者很容易当成一回事。

5. 【8.2.2（对照图 8-2）|表达可读】正文说"结尾是 8 字节 CRC64 校验和"，图 8-2 图注也是"magic / version / metadata / db-selector / entries / CRC64 footer"，但图里 CRC64 前明明画了一个"EOF 0xFF"框，正文对 EOF 操作码只字未提。对照图读到这里会卡在"这个 0xFF 是什么、为什么图有正文没有"，补半句"entries 结束后先写 1 字节 EOF 操作码（0xFF）再写 CRC64"就闭合了。

## 五个建议

1. 【8.2.2|案例示例】建议给 RDB 的"内存占用 vs 落盘字节"算一笔明白账：拿一个小键值对（比如 SET user:1 abcd）逐项列出内存侧 dictEntry/robj/sds 头/分配器对齐各占多少字节，再对照 RDB 侧（类型码 + 长度前缀 + 净荷）总共十几字节，一张小表就能让"为什么快照通常只有内存的三到五成"变成可推导的结论，而不是一个要背的区间。

2. 【8.3.3 / 图 8-4|图示】图 8-4 把 User Records 画成 rec1 到 rec5 的整齐队列，视觉上暗示物理有序，而正文明确说"按索引键顺序链接，物理位置不必按键排序"——页内布局最反直觉的正是"物理无序、逻辑有序"。建议把记录画成插入后的真实乱序（如 rec3、rec1、rec5……），用 next_record 箭头串出逻辑顺序，Page Directory 槽指向各组尾记录，一张图同时讲清三个部件怎么咬合。

3. 【8.3|深度广度】页分裂与页合并全章只有半句带过（8.3.1"可能触发页内重组或页分裂"），但 8.5.2 拿"半空页在所难免"当页式范式的核心代价——空间放大到底多大，取决于分裂点怎么选（InnoDB 会参考相邻页空闲量）、顺序/随机插入的填充率差异、删除打洞后何时合并页。建议补一小节或一个框把这笔空间账算出来，否则 8.5.2 的论断没有出处。

4. 【8.5.1 表 8-2|术语使用】"演进机制"一行 MySQL 格目写"行格式与页内格式标记"，与 RDB 版本号、Magic 并列显得对等，实际行格式是建表时静态指定、老表保持老格式，并没有逐文件/逐记录的版本协商。建议改为"行格式按表静态指定 + redo/undo 格式版本"，并顺手点破：MySQL 靠"数据字典描述 + 新代码读旧格式"而不是文件自带版本号，这个差异本身就是值得写的干货。

5. 【8.4.3|结构导航】RecordBatch 头部"固定 61 字节"是本章 Kafka 部分的核心数字，但 61 的构成要翻回 2.2.3 的表 2-1 才能看到。存储格式章节里建议给一行明细（baseOffset 8 + batchLength 4 + partitionLeaderEpoch 4 + magic 1 + CRC 4 + attributes 2 + lastOffsetDelta 4 + firstTimestamp 8 + maxTimestamp 8 + producerId 8 + producerEpoch 2 + baseSequence 4 + 记录数 4 = 61），让读者在本章内就能验算，不必跨章翻表。
