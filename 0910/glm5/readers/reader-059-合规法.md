# 读者059 · 合规法
身份：数据合规工程师，8年，爱好：逛博物馆
主读：第 6 章

## 五个问题

1. 【6.2|逻辑论证】书中说 Redis 不做 RBAC 是"把组角色这类复杂语义留给外部的身份管理系统（IAM），是 Redis 一贯划分边界的做法"。我专门核实过：开源 Redis 根本没有对接外部身份源的接口，LDAP/OIDC 都是 Redis Enterprise/云托管的能力，开源侧只能靠应用层自持密码或前置代理。"留给 IAM"读起来像有一条标准交接通道，实际对开源用户是空头支票；而"统一身份源、账号生命周期管理"恰恰是等保和内审的硬性检查项，这句"边界划分"叙事会误导受监管环境的选型。

2. 【6.2|读不懂】"Kafka 3.5.0 也加入了 Broker 到 Controller 的 SCRAM 支持；这与 Controller 之间的共识连接不是同一条路径。后者在 3.5.1、3.6.0 曾出现用 SCRAM 启动集群失败的问题"——这两句我读了三遍仍分不清："Broker 到 Controller"和"Controller 之间"各自走哪个监听器？图 6-2 里 CONTROLLER 监听器只标了"协议：SSL"，与正文"SCRAM 可用"对不上号，只能靠猜。KRaft 的三条连接（Broker↔Broker、Broker↔Controller、Controller↔Controller）各自能用什么认证，值得一张小图或对照表说清。

3. 【6.5|逻辑论证】"务实的选择是异步写入审计日志、对日志采样，或外接专用审计系统"把"采样"与完整审计并列为等效选项。但 6.1 给审计下的定义是"事后能否查清谁在什么时候做了什么"——采样恰恰保证不了这一点：被漏采的请求在取证时永久无法还原。做等保测评和内控审计时，采样日志只能算性能监控数据，不能算审计轨迹；这里应区分哪些事件可采样（如 DEBUG 级放行记录）、哪些必须完整（如授权拒绝、管理操作）。

4. 【6.4|深度广度】TDE 一节的代价讨论只落在"密钥丢失、轮换与备份"，没有讨论"密钥在谁手里"这个威胁模型问题：社区版 keyring_file 的密钥文件与数据同机存放，防的只是 6.1 说的"磁盘被盗"那一种主体；对 DBA、托管云厂商这类内部越权读取几乎无效，需要外部 KMS/Vault 才覆盖。我做数据托管与出境评估时这是两种完全不同的结论，而本章存储加密只给了一种威胁叙事。

5. 【6.2|术语使用】"密码以 SHA-256 摘要形式保存，不存明文。这是凭证落盘的最小安全要求"——技术解释没错，但"最小安全要求"这个措辞在合规语境会被当成达标线：等保和密评（密码应用安全性评估）对口令存储的要求是加盐慢哈希（政企场景还常要求 SM3），无盐快哈希是明确不符合项。紧接的"靠密码本身的熵来补无盐的短板"更像设计方自辩而非测评口径，两句之间应提示"受监管部署需另行加固"。

## 五个建议

1. 【6.5|深度广度】给 6.5 补一个"审计的取证底线"收尾：三家原生审计都没有防篡改设计、也没有保留期概念，而监管对日志的要求（如网络安全法不少于六个月、日志不可篡改）正是合规评审必开的不符合项。建议把"外挂审计"从性能叙事升级为取证叙事——外部汇聚、只读/WORM 存储、时间同步，三五行就能点透，对生产读者价值很大。

2. 【6.2|案例示例】开篇爬虫事件只讲到"被当成免费缓存"，建议扩成完整小案例：公网 6379 → 未授权写 crontab/SSH 公钥 → RCE 的利用链条画成路径图（正好呼应图 6-1"缺哪段开哪段"），再补"事后取证能拿到什么"——ACL LOG/SLOWLOG 各能看到什么、看不到什么。安全章的开篇案例配一节"事后怎么查"才闭环，也是合规读者最需要的部分。

3. 【6.1|结构导航】四维模型（认证/授权/加密/审计）建议挂靠标准框架：在 6.1 或表 6-1 附近加一小段映射，如对应等保 2.0"安全计算环境"的身份鉴别/访问控制/数据完整性与保密性/安全审计控制项，或 ISO 27001 相应控制点。受监管行业的读者都是拿着测评表来读的——我自己就在手工做这个映射，加四行对照，本章就能直接进合规工作底稿。

4. 【6.3|深度广度】MySQL 权限一节建议补 8.0.16+ 的动态权限体系（SYSTEM_USER、BACKUP_ADMIN 等把 SUPER 拆开，SUPER 已废弃）：权限审计里"应用账号还挂着 SUPER"是头号发现项，动态权限正是启示三"最小权限"在 8.0 的落地工具。现在书中把 SUPER 列为管理类高敏权限却不提它已被拆分废弃，容易让读者沿用旧粒度授权。

5. 【6.6|深度广度】横向对比建议增加"留存与删除"维度：承载个人数据时，Redis TTL、MySQL 的 binlog 与备份、Kafka 的时间保留日志/压实主题，在"删除特定主体数据"上的能力差异巨大（Redis 最容易，Kafka 按时间保留的日志几乎做不到），GDPR/个保法的删除权会直接撞上这些机制。现有四维对比都是"防进来"，缺"能出去"，这是我从这一章最想拿到的一张对比表。
