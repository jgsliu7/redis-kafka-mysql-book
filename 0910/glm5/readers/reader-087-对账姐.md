# 读者087 · 对账姐
身份：支付系统开发，10年，爱好：韩剧
主读：第 9 章

## 五个问题
1. 【导读与9.1|逻辑论证】导读承诺"断了重连之后怎么把漏掉的部分补上而不重复"，但 9.1 的四个子问题只有"断了怎么办"（续传），没有"不重复"的位置；全章只有 9.4.8 讲了 Kafka 生产者幂等，Redis 命令流与 MySQL binlog 重放"靠什么保证不重复执行"始终没有正面回答。做对账十年的直觉是：补漏易、防重难，重复比丢失更难轧平，被丢掉的这半个问题恰是我最想看的。
2. 【9.3.3|技术事实】"副本 I/O 线程把事件写入 relay log 并落盘后即回 ACK"——按我的理解，半同步 ACK 只要求事件写入 relay log，默认并不等待 fsync（`sync_relay_log` 默认 10000 次才刷）。"落盘"二字会让资金场景读者高估保证：副本整机掉电（而非仅进程崩溃）时，ACK 过的事务仍可能丢，请核对此处"落盘"的确切含义。
3. 【9.4.2|版本时效】"3.9 的 Tiered Storage 已可用于生产"——我印象中 KIP-405 是 2025 年 3 月的 4.0 才宣布生产可用，3.9 仍标 early access，建议核对。另外 KRaft 一节没提 4.0 已彻底移除 ZooKeeper，2026 年的读者大概率按 4.x 部署。
4. 【导读与9.7|逻辑论证】导读用亲历案例"删缓存和写库先后顺序不一致"引出"以谁为准"，但 9.7 的答案"数据库是正本、缓存是可重建的派生数据"只回答了分歧时信谁，没有回答顺序怎么定——知道了以正本为准，那个顺序 bug 照样发生。这就像对账里"以谁为准"和"差错怎么调"是两个环节，答案只给了前一半。
5. 【9.4.8|术语使用】"能提交的只有已交付记录中处理完成的前缀"——"交付"全书首次出现且未定义：消费者拉到消息算交付，还是处理回调返回算交付？我读了三遍，要靠后半句"并行处理时后一条先完成"倒推才猜出语义。这条规则恰是我最有共鸣的（对账日切同样要求流水按严格前缀对齐、中间不能有洞），值得先把"交付"一词定义清楚。

## 五个建议
1. 【9.4.8|案例示例】"第三种在 Kafka 之外"一句带过的地方，建议补一个消费端幂等案例：以唯一业务流水号建幂等表（或状态机判重），说明 offset 提交与业务落库跨两个存储、重启后重复消费不可避免。我处理过的重复扣款几乎全落在这个缝隙里，这段是全章离资金安全最近的段落，不该只有三行。
2. 【9.7|深度广度】给"正本-派生数据"的答案补上写侧顺序：先提交正本、再失效派生（或订阅 binlog 失效缓存），并回访导读那个"改资料看到旧值"的案例做首尾呼应。支付行业的通用解法恰恰是拿本章讲的 MySQL binlog 流做异构分发（对账明细、缓存失效都靠它），同构副本之外这条最大的异构同步出路，讲"数据同步"的一章不提可惜。
3. 【9.3.3|技术事实】把半同步 ACK 的边界写准（写入 relay log 即 ACK，fsync 由 `sync_relay_log` 另行控制），并加一句"防进程崩溃还是防整机掉电"的差别。资金系统选半同步前问的第一个问题就是这个，现在这句"落盘后即回 ACK"会让人以为掉电也安全。
4. 【9.4.5|深度广度】"碰钱站 Kafka、宁可写失败"的表态我完全认同，建议再补半句承接：写失败只让损失可见，业务侧还需要补单重试闭环和日终对账兜底（对账要能发现并轧平未闭合单据），这个判断才落成完整方案，也呼应导读里"重复转账"的警示。
5. 【图9-1与表9-1|结构导航】图 9-1 的四个子问题建议补上"重了怎么办"这一维，或在表 9-1 加一行"防重手段"，让导读承诺的"不重复"在正文结构里安个家：Redis 把命令改写成确定性效果、MySQL ROW 事件按最终状态回放、Kafka 序列号+事务，三家其实都有答案，只是目前散在各节看不出来。
