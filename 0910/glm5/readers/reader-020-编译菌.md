# 读者020 · 编译菌
身份：编译器方向工程师，7年，爱好：电音
主读：第 2 章

## 五个问题

1. 【2.3.2|技术事实】「0xFB 不是长度编码，在结果集行里它标记 NULL」这只对文本结果集行成立；预编译走的二进制结果集行（Binary Resultset Row）里 NULL 是行首的 null_bitmap 位图，根本不用 0xFB。书里这句夹在通用编码讲解和二进制结果集两段之间、未区分行类型，照着它去解析二进制行必然解错，想补一句话点明两者的 NULL 表示差异。

2. 【2.3.1|深度广度】书里强调 RESP「天然二进制安全」「参数也能包含二进制数据」，但二进制安全只属于 `$`/`*` 这类带长度前缀的类型；`+`/`-` 是 `\r\n` 定界、值里不能含 `\r\n`。既然断言「熟手一下午就能写出一个能用的 Redis 客户端」，这恰恰是手写客户端最先踩的坑（拿 `+` 回显含换行的用户数据就废了），书里没点破这个边界。

3. 【2.2.1|逻辑论证】「跳表的缓存局部性确实不如红黑树」被当成公认事实直接下断，但红黑树节点同样是离散分配、指针追踪一样随机，这个结论本身有争议（跳表每层期望访问的节点数并不多于平衡树）；紧接着的「实现更简单、范围操作更直接」才是站得住的取舍，这句局部性断语依据不足，删掉论证反而更干净。

4. 【2.2.2|深度广度】自适应哈希索引一段先写成 InnoDB 随访问模式自动调整的聪明设计，末尾突然一句「生产上仍常常直接关掉」，中间缺了「什么负载下它从资产变负债」的判据——是 btr_search_latch 竞争还是内存占用，命中率用什么观测。读者记住的只会是「关掉」这个动作，没法对照自己的系统做判断。

5. 【2.5|读不懂】启示四「我自己设计新协议，会先从第二个版本开始——第一个版本很少有人能把边界想全」，读了两遍仍不确定操作含义：是「设计 v1 时就按 v2 的标准预留版本字段」，还是「版本号从 2 开始编」？这句是全章协议演进讨论的收束箴言，不该留歧义。

## 五个建议

1. 【2.2.3|深度广度】讲 RecordBatch V2 时建议补一句 CRC 的覆盖范围：从 magic 算到批尾，baseOffset/batchLength/partitionLeaderEpoch 刻意留在覆盖之外——导航字段必须能独立于校验被读到，否则坏了的批都定位不到。这是序列化格式设计的经典手法（ELF/DWARF 的校验同理），点一句能让「格式可演进」的论证深一层。

2. 【2.3.2|图示】三家协议里 RESP 有逐字节实例、Kafka 有图 2-7 的字段布局，唯独 MySQL 只用文字描述 LengthEncodedInteger 的分档规则。建议补一张「同一行数据的文本行 vs 二进制行」字节级对照小图，二进制结果集「数值与日期列越密集省得越多」立刻可见。

3. 【2.4|结构导航】表 2-2 有 12 个维度但全是定性词，建议加一行「单帧元数据开销」的量化对比：RESP 每条命令约 20 字节分帧开销（导读里 SET 语义载荷 13 字节、编码后 33 字节）、MySQL 每报文 4 字节包头、Kafka 61 字节头部摊到整批。「目标→结构→协议」这条因果链落到数字上才真正可感。

4. 【2.3|术语使用】「封帧」与「分帧」章内混用：2.1 和 2.3.2 写「二进制封帧」，表 2-2 写「RESP 分帧」、图 2-8 标题也是「分帧」。同一概念两个译名，对格式较真的读者很硌眼，建议统一为更通行的「分帧（framing）」并在首次出现时注英文。

5. 【2.5|表达可读】与上面第 5 个问题对应：把「先从第二个版本开始」改写成实义句，例如「设计第一版时就假定第二版一定会来：预留版本字段或能力位」。把个人口诀落成读者可执行的检查项，箴言才真正可迁移。
