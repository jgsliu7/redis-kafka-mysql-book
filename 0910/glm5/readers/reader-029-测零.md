# 读者029 · 测零
身份：自动化测试工程师，4年，爱好：千片拼图
主读：第 3 章

## 五个问题

1. 【3.4|深度广度】正文写"受控关闭也有前提：Controller 必须可达，且 Leader 迁移要在超时阈值内完成"，漏了第三个前提：待迁移分区在 ISR 里还有别的存活副本。单副本 topic（或同分区其余副本恰好都已下线）时 Leader 无处可迁，受控关闭注定重试耗尽、退化为普通关闭——我编排缩容演练时，"明明走了受控关闭集群还是抖"的头号根因就是环境里混进了单副本 topic。

2. 【3.4|图示】图 3-6 只画了"抖动小得多"和"分区短暂不可用"两个定性色块；普通关闭路径里"Controller 靠心跳/会话超时才发现"这个发现窗口是几秒还是几十秒（取决于会话超时参数），图和正文都没给数量级。排障时最实际的问题是"普通关闭到底抖多久、值不值得为受控关闭多等"，合上书我答不出来。

3. 【3.6|逻辑论证】启示二断言"移交要放在停止服务之前"，但按 3.4 节自己的流程口径（普通关闭第一步是"标记停服（停收新请求）"，受控关闭之后 Broker 才"执行完整的刷盘退出流程"），受控迁移发生在停收新请求之后、刷盘退出之前。若"停止服务"指停收新请求，两节矛盾；若指进程退出，"放在退出之前"又近乎同义反复——对照图 3-6 也找不到"停收新请求"画在哪一步，两个口径我拼不到一张图上。

4. 【3.4|读不懂】preStop hook 一节先说"触发 BGSAVE，确认本次快照成功完成后再执行 SHUTDOWN NOSAVE"，紧接着又说"BGSAVE 返回成功只表示后台保存已启动"——那到底用什么手段确认完成？书里没给。而按 3.2 节关闭流程第一步，SHUTDOWN 时若 BGSAVE 子进程还在跑会被直接杀掉、半成品作废；这个边界不点破，照字面写 hook 反而会白做一次快照。

5. 【3.3|技术事实】表 3-1 把 innodb_fast_shutdown=2 类比为"近乎 kill -9"，我不完全认同：档位 2 仍完整刷 redo log、有序走完关闭流程，下次崩溃恢复从一个日志完整的起点开始；真 kill -9 连 redo 的完整性都不保证。两者都要走崩溃恢复，但恢复工作量与丢数据风险不是一个量级，"近乎"二字在应急决策时容易把这层差别抹掉。

## 五个建议

1. 【3.4|结构导航】"容器化环境下的生命周期"讲的是三家共同的 K8s 约束（grace period 计时起点、三类探针、preStop），是全章对运维侧读者操作价值最高的一段，却埋在"3.4 Kafka 的做法"末尾。建议升格为独立的横向小节（并入 3.5 或单设一节），只关心 Redis/MySQL 的读者才不会漏掉这块拼图。

2. 【3.4|图示】在图 3-6 的时间轴上给两条路径标注典型量级：受控关闭的 Leader 迁移通常秒级完成，普通关闭的发现窗口是会话超时参数量级再加选举时间。把"抖动小得多"从定性色块变成可比较的数字，缩容窗口规划才有依据。

3. 【3.2|案例示例】给 Redis preStop 方案补一行可操作细节：轮询 INFO persistence 直到 rdb_bgsave_in_progress=0 且 rdb_last_bgsave_status=ok 再发 SHUTDOWN NOSAVE，并点破"没等完成就发 SHUTDOWN，bgsave 子进程会被关闭流程第一步杀掉、快照作废"。现在 3.2 讲流程、3.4 讲编排，中间缺的正是这个衔接件。

4. 【3.6|案例示例】五条启示都是"要遵守的纪律"，缺一段"怎么验证纪律被遵守"。建议把 3.4 末尾两行"实践清单"扩成一小节关停演练方法：注入 SIGTERM/删 Pod 后对照三家里程碑日志（Ready to accept connections / ready for connections / KafkaServer started）测量关闭耗时，再用 SIGKILL 做丢数据窗口的对照实验——要写启停编排的读者，最缺的就是这份验收清单。

5. 【3.5|术语使用】表 3-2"关闭时的数据保证与可配置性"一行，Kafka 格写"强制刷盘，无选项"——无的只是"存不存盘"这一个选项，controlled.shutdown.enable 明明是关闭路径本身的开关（下一行维度里也提到了受控关闭）。一格塞了两个维度，容易被读成"Kafka 关闭没有任何可配项"，建议注明"无的是存盘选项；迁移路径可配（见下行）"。
