# 读者092 · DDIA粉
身份：工程师，7年，爱好：天文摄影
主读：第 10 章 + 全书结构（序言/后记/抽读第 7、9 章导读）

## 五个问题
1. 【第10章/10.2.4 规律四|逻辑论证】规律四给 Redis 的证据只有本地刷盘旋钮 appendfsync，而 MySQL、Kafka 给的都是复制确认旋钮（半同步、acks）。但 9.1 明明写过 Redis 的 min-replicas，且后记作者自己的库存事故恰恰是异步复制丢写而非刷盘丢失——规律四的 Redis 证据与全书最重的教训错位，三软件对照并不平行。
2. 【第10章/10.2.3 规律三|技术事实】"机械盘寻道、存储 I/O、网络往返和系统调用，都有值得摊薄的固定开销"把机械盘和 SSD 混为一谈：HDD 随机与顺序差约三个数量级，NVMe 上缩小到几倍，规律三在 SSD 上的主要支柱其实是系统调用与网络往返的摊薄。不区分介质，读者会在全闪存部署上过度套用寻道逻辑，这正是 DDIA 第 3 章讲 LSM 时专门处理过的边界。
3. 【第10章/10.3.1 维度一|读不懂】"断电恢复还依赖操作系统和存储设备正确履行刷盘承诺"（10.2.2 还有同款前提）——"刷盘承诺"具体指哪些失效场景（如无电容的磁盘写缓存、设备向 OS 谎报落盘）全书没展开。这个前提出现两次却零解释，我没法判断双 1 在什么硬件上不再是保证。
4. 【第10章/10.4.1 表 10-2|术语使用】RPO 行 Redis 答案写"每秒 AOF 可能丢约一秒写入"——"每秒 AOF"不是参数名，我第一遍没认出是 appendfsync=everysec。这张表定位为动手前自检工具、要被照抄进方案文档的，参数名不写全容易抄错。
5. 【序言|深度广度】序言把市面资料二分为"怎么用"和"底层原理"，却没回应 DDIA 恰好占据"为什么这么设计/取舍"这一格、且与第 10 章五条规律大面积重叠（正本、顺序与批量、可靠性代价、CAP）的事实。我是读到 9.1 唯一一处 Kleppmann 引用和 10.2 的"并非本书首次发现"才自己拼出差异点（生命周期/安全/存储格式三章+源码级机制+12 问 checklist），书的差异化价值始终没有明说。

## 五个建议
1. 【序言|结构导航】加一段"如果你读过 DDIA"的定位说明，最好配一张附录映射表：本书 8 主题 × DDIA 对应章节，标出本书独有（生命周期、安全、磁盘存储格式、三软件源码级机制）与 DDIA 更强（分布式事务、共识细节、批/流处理）的部分，让两本书配着用。
2. 【第10章/10.2.3 规律三|深度广度】补一行 HDD/SSD/NVMe 三档介质上随机/顺序差距的数量级对比，并说明规律三在 SSD 时代成立的主要支柱从寻道变为系统调用与网络往返的摊薄，给规律划清使用边界。
3. 【第9章/9.1 关键数字框|案例示例】backlog 框里"覆盖时长 = backlog 大小 ÷ 写入字节速率"是全书少见的可代入自己数字的粗算公式。建议在第 10 章或附录收一个"估算公式"小集合（backlog 覆盖时长、RDB/AOF 恢复时间、复制带宽=写速率×副本数、ISR 追赶时间）——设计者阶段最缺的就是这种 back-of-envelope 能力。
4. 【第10章/10.3.2 图 10-2|图示】选型问题图只有"从约束找设计"的正向分支，建议加一条反例分支：从"库存主存储放 Redis Cluster"出发标注它违反了哪条约束（交易数据 RPO≈0 vs 异步复制），把后记的大促故事变成图上的警示路径。DDIA 读者习惯从故障模式反推设计边界，目前图只覆盖了正向一半。
5. 【第10章/10.3.3 练习一|案例示例】答案只说"最终派单仍需核验订单状态"，没有处理 Redis 筛选候选与 MySQL 落单两步之间的并发窗口——同一司机可能同时被两单选中。建议补一句怎么关这个跨存储竞态（MySQL 侧唯一约束或司机版本号乐观锁），这正是 DDIA 第 5 章"读己之写/跨系统写"的经典难题，也是这个练习最值得教的一步。
