# 读者003 · Ken
身份：互联网架构师，8年，爱好：胶片摄影
主读：第 1 章

## 五个问题

1. 【1.1.3|术语使用】"MySQL：用 B+ 树 + WAL + MVCC 换强一致与通用查询"——这个"强一致"没有限定。MySQL 默认异步复制下主从切换会丢已确认事务，第 10 章 10.3.1 讲 CAP 时自己也细分了（MGR 拿不到多数派就不能确认写入）；第 1 章说的其实是单机 ACID/隔离性，与 CAP 语境的线性一致性不是一回事，读过 DDIA 的读者会在这里停下来较真。

2. 【1.2.4|图示】图 1-2 评分表给"数据容量"MySQL 5 分、Kafka 4 分，正文断言"MySQL 在强一致、数据容量与查询灵活度三个维度领先"。我运维过 PB 级留存的 Kafka 集群（3.9 起还有分层存储），"能存多少"恰恰是 Kafka 的设计目标，而 1.2.2 自己承认 MySQL"横向分库分表代价不菲"——若口径是"单实例可高效随机访问的在线数据规模"应写明，否则这格结论与一线体感相反。

3. 【1.3.3|逻辑论证】"Kafka 把数据本身存成日志……不需要再把命令重放成另一套业务数据结构"——这只在 broker 侧成立。Kafka Streams 的 state store 崩溃后正是靠整段重放 compacted changelog 重建另一套数据结构，CDC 下游数仓回放同理；日志抽象没有消灭重放，是把重放成本转嫁给了消费端。三家的真分歧是"重放发生在哪一层"，这半句把它说没了。

4. 【1.1.2|逻辑论证】"能同时满足'成熟、典型'的并不多"，但为什么是 MySQL 而不是 PostgreSQL 一句都没交代。PG 同样有 MVCC、WAL 和完整演化史，近两三年我们新项目默认 PG；选样本是全书合法性的根基，最显眼的反例不排除（给一句"InnoDB 装机量最大、MGR 演化线最完整"之类的理由就够），这个论证在 DBA 读者面前站不稳。

5. 【1.2.2|表达可读】"在每次提交都刷盘的配置下，事务提交需要等待日志落盘，可通过 fsync 等机制把缓冲的写强制刷到磁盘"——"可通过 fsync 等机制"是半截解释，也没点名参数。读到 10.3.1 才发现 innodb_flush_log_at_trx_commit=1 与 sync_binlog=1 在 8.0 里本来就是默认值（"双 1"），而 1.2.2 的措辞像在描述一种可选的特殊配置，我对着两章愣了一下才对上口径。

## 五个建议

1. 【1.1.2|深度广度】给"三种范式，为什么恰好是这三个实现"补 2-3 句排除法：为什么不是 PostgreSQL 做可靠存储代表、为什么不是 Pulsar/RabbitMQ 做流式代表。读者是带着最显眼的备选进来的，第 1 章就把门关上，后面九章的对比才有公信力。

2. 【1.2.4|图示】雷达图"数据容量"维度要么给出定义口径（单实例在线可随机访问数据 vs 集群总留存），要么换成"可扩展性"这类无歧义维度；图注现在只有"作者主观量级判断，仅作示意"，建议每个维度补一句判据，让正文断言与评分可对质。

3. 【1.1.3|案例示例】"写放大（同一份数据被物理写入多次）"的括号解释偏抽象。建议落成一笔 UPDATE 的落盘清单：redo log、binlog、doublewrite、脏页，同一份数据至少写到几处——第 1 章就把这个全书反复出现的高频术语数字化。

4. 【1.4.3|版本时效】"版本状态提示"从一段话升级为一张三行小表：基线版本 vs 2026-09 当前 GA（MySQL 8.4 LTS/9.7、Kafka 4.x、Redis 8.x）vs 对各章内容的影响（按 3.x 讲的操作在 4.x 上是否仍成立）。在读读者需要随时自查"手里环境和书说的差多远"。

5. 【1.3.1|案例示例】表 1-2 的对照框架很好，但"架构视角"列全是问句，停在悬空处。建议配一个真实事故的正反复盘：同一个 Redis 大 key 卡顿，使用视角的复盘是"拆 key、换命令"，架构视角的复盘是"单线程约束下的设计边界与免责项"——方法论第一次亮相就用案例立住，比问句有力。
