# 读者002 · 老周
身份：Java 后端，3年，爱好：海钓
主读：第 1 章

## 五个问题

1. 【1.2.3|读不懂】"未启用 TLS 时的零拷贝（sendfile）"——为什么一开 TLS 零拷贝就没了？正文一个字没解释。我没碰过 sendfile，这个括号等于塞给我一个新疑问而不是一条信息，卡在这儿反复读了两遍。

2. 【1.3.1 表 1-2|表达可读】"redo 与 binlog 为何要两阶段提交？日志作为数据正本，边界到哪为止？"后半句我完全对不上号："数据正本"指什么、"边界到哪为止"是在问数据还是问日志？我平时只是开过 binlog 配主从，这句话在表里没有任何铺垫，读起来像写给已经懂的人看的。

3. 【1.2.4 表 1-1|逻辑论证】表 1-1 里 MySQL 的"可舍弃"只写"写性能"，图 1-1 也写"舍弃：写入性能"，可 1.2.2 正文列的代价明明是提交延迟、调优门槛、"横向分库分表代价不菲"，表和正文口径对不上。而且以我三年 CRUD 的体感，MySQL 配好 redo log 之后写入很少是第一瓶颈，说它舍的是"写性能"我不服——感觉它真正舍掉的是水平扩展能力。

4. 【1.2.2|技术事实】"1995 年起源于瑞典 MySQL AB"疑似把软件发布和公司成立混在一起了：我记得 MySQL 这个软件 1995 年发布，MySQL AB 这家公司是 2000/2001 年前后才注册成立的，2008 年才被 Sun 收购。表 1-1 的出身栏同样写"1995，MySQL AB"，两处一起改。

5. 【1.3.3|逻辑论证】三层追问的前两层（先刷日志还是先刷数据页、落盘粒度多细）显然决定丢数据的窗口，但第三层"记逻辑还是记物理"和"数据不丢"之间的因果关系书里没接上。按我自己的理解，物理/逻辑日志影响的是恢复快慢和格式兼容，好像不直接影响丢不丢数据——为什么它算"保证不丢"的第三层追问而不是"恢复怎么做"的问题？

## 五个建议

1. 【1.2.1|案例示例】给"数据结构服务器"这个抽象补一个 before/after 的小例子。我三年里只用 Redis 存过字符串，ZADD/ZRANGEBYSCORE 对我是生词；拿排行榜或库存计数演示"纯 string 方案 GET→改→SET 有并发覆盖风险 vs Redis 一条原子命令搞定"，像我这种只用过缓存字符串的读者才能真正体会这个抽象值多少——超卖这种坑我是真踩过。

2. 【1.2.2|结构导航】1.2.2 把 MVCC、Read View 生成时机、两阶段提交这些细节全压进引言章，和 1.4.1"相关知识会在用到时补到'够用'的程度"的承诺自相矛盾，第一次通读到这儿差点被劝退。建议这段收敛成两三句能带走的结论（比如"靠 MVCC 实现读不阻塞写"），细节留给对应主题章再展开。

3. 【1.2.3|术语使用】acks 在 1.2.3 和表 1-2 出现了两次，都没说它是个什么参数、能取哪些值、0/1/all 差别在哪。我完全没碰过 Kafka，建议首次出现处给一行取值说明，不然"写入确认还要结合 acks 与最低 ISR 数配置"只能囫囵吞下去。

4. 【1.5|表达可读】我的习惯是先读小结再回头读正文，但 1.5 里"三层追问（先刷日志还是先刷数据页、落盘粒度多细、记逻辑还是记物理）"对还没读 1.3.3 的人是三个黑箱短语，起不到"先给地图"的作用。建议小结写得更自包含，比如把第三层落成"记执行的命令还是记页面的修改"这样一句话就能懂的表述。

5. 【1.2.4 图 1-2|图示】雷达图会诱导读者比面积：我第一反应就是看谁圈的地盘大，MySQL（2/2/5/5/5）面积明显最大，很容易读出"MySQL 综合最强"，这跟全书"没有全能冠军、只有取舍"的主张拧着。建议在图注或正文里明确"五个维度各自独立看、不要加总比面积"，或者干脆换成 5 行×3 列的高/中/低粗粒度标注，避免假精度。
