# 读者096 · 跃迁者
身份：架构师成长焦虑者，8年，爱好：写日记
主读：第 10 章 + 全书结构（序言/后记/抽读导读：第 1 章、第 7 章）

## 五个问题
1. 【后记|逻辑论证】库存事故改后的方案"Redis 只做预扣减的前置层，账只认 MySQL"就收笔了，可 Redis 预扣减成功而 MySQL 事务失败（或 DB 提交后补偿失败）时两层不一致怎么办，对账/回补只字未提。我做过秒杀系统，这道两层之间的缝隙才是真正翻车的地方，故事偏偏在最难处留白。

2. 【10.1 表10-1|术语使用】第 2 章 MySQL 的关键决策写成"文本/二进制协议 + Dynamic 行格式"：MySQL 客户端/服务端协议是二进制帧，"文本"的只是走 COM_QUERY 的 SQL 语句本身，这个并列让我读不出指什么；Dynamic 也只是 Compact/Redundant/Dynamic/Compressed 四种行格式之一，为何拿它当 MySQL 的代表决策，总结表里看不出理由。

3. 【10.4.1 表10-2|深度广度】"扩容是否停机"一行 MySQL 的答案只给 MGR 一条路（还塞了"全员全量、无数据再均衡、Router 分摊"三个限定），但我待过的两家公司 MySQL 扩展走的都是分库分表中间件，这条 checklist 在真实评审会上借不到力；Kafka 也只说"加分区受限"，最常见的扩盘/迁移 Broker 动作没提。

4. 【10.2.4|技术事实】appendfsync=always 被描述为"每批写命令追加后刷盘"，而 redis.conf 官方注释是"every time a new command is appended"——每条命令一次 fsync。一字之差直接决定 always 的延迟量级（每条一个 fsync 还是攒批共享），我拿书里的表述去面试会被 challenge，望核对。

5. 【序言与10.5|结构导航】序言第三层承诺"根据周期、成本、团队状况、遗留系统、公司硬约束组合出能落地的整体"，但第 10 章收束时第三层的落点是三道单点选型练习（放 Redis 还是 MySQL、要不要事务、要不要分片）和 12 问自检，练习的约束变量里再没出现过团队状况、遗留系统、上线周期——三层承诺里最值钱的第三层兑现得最薄。

## 五个建议
1. 【10.4.2|深度广度】"从使用者到设计者"四阶段里，设计者的三项核心能力只给了定义，建议每项配一个可提交的最小练习（如权衡能力：给自己系统写一页"为什么不选另一个方案"的决策记录），并把 10.4.3 的三条学习路径与三能力对齐——像我这样卡在"理解者→设计者"之间的读者，缺的正是这种有产出物、能自检的台阶。

2. 【10.1|结构导航】表 10-1 一行挤五列决策，纸质排版必然缩成小字，而读者最想抄进笔记本的是"一句话共性启示"那一列。建议把九条启示单独抽成一张窄表或章末列表，大表只保留三软件决策对照。

3. 【后记|案例示例】库存复盘建议补三两句"改后方案的边界"：预扣减层与 MySQL 正本之间靠什么对齐（失败补偿、定时对账、幂等键）。不补的话，照抄"Redis 预扣 + MySQL 正本"的读者会在两层不一致时重蹈覆辙，而这恰恰是这个故事最该教的一课。

4. 【第7章本章导读|表达可读】第 7 章导读和 7.1 用弯引号（"单点不够用""数据是否落盘"），第 10 章、第 1 章用直引号（"如何在约束下做出取舍"），序言里两种混用；出版前应统一中文标点。我有摘抄习惯，标点混用会让笔记里的前后引用不一致。

5. 【10.3.3|案例示例】三道判断练习全是"选型/要不要"类判断，建议加一道"复盘类"：给一个已上线系统的约束描述，让读者指出当年哪个决策错了、该怎么改。接手遗留系统的人（8 年 CRUD 大多是这类）日常是"改"而不是"选"，后记的库存故事本身就是现成素材，遮住答案就是练习四。
