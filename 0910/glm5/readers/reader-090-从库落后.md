# 读者090 · 从库落后

身份：普通后端，4 年经验，技术背景是"从库延迟受害者"（读写分离踩过多次坑），爱好追新番，阅读习惯疑问驱动型——看到断言就想查证，看到案例就想问"后来呢"。
主读：第 9 章 数据同步机制（辅读序言、导读）。

## 五个问题

1. 【9.3|深度广度】半同步小节写明 ACK 时点是"副本 I/O 线程把事件写入 relay log 并落盘后即回 ACK，不等本地回放"，也补了"事务还未在副本上回放，并不等于它已经丢失"，却始终不点破对读写分离的后果：半同步挡的是"丢"，挡不住"读到旧值"——把读流量挂到半同步从库上，写后读照样是旧数据。作为被从库延迟坑过多次的人，这是半同步最容易被误解的一点，书里绕着它走了。

2. 【9.3|案例示例】GTID 一节只讲"简化很直接"：换主不用人工对偏移、多源好管理，风险面只提"所需日志已被清理"。我实战里最疼的一次是 errant transaction：有人在从库上直接改数据产生了本地 GTID，主从切换后复制直接报错卡住，比手工对偏移的旧时代更隐蔽——位点机制讲得这么细，却没有一个"位点上长出脏东西"的反例，我不服这个纯正向叙事。

3. 【9.4|逻辑论证】"达到最低数量后，all 仍要求当前 ISR 全部确认"——想跟作者确认我的理解：ISR 从 3 收缩到 2 后，acks=all 等的就只剩这 2 个副本，保证强度随 ISR 收缩"静默变弱"，直到跌破 min.insync.replicas 才拒绝写入。如果对，这个点值得点破，我身边不少人都以为 all 永远等 3 个副本。

4. 【9.7|结构导航】导读说"缓存和数据库谁为准……本章小结与第 10 章会给出答案"，但 9.7 只有一句"数据库是正本、缓存是可重建的派生数据"；而作者自己在导读里踩的那个坑——"删缓存和写数据库的先后顺序在不同代码路径里不一致"——从头到尾没有回收。"谁为准"和"顺序怎么定"是两个问题，后者才是那个 bug 的病根。

5. 【9.4|版本时效】"这个默认值自 0.11 起就由 true 改为 false，KIP-106"——我专门去查了，公开资料自己打架：KIP-106 的资料页写着 Kafka Version 1.0，实现工单 KAFKA-5257 的 fixVersion 又是 0.11.0.0。书选了 0.11 却没给可核对的出处，较真读者会像我一样查半天没结果，建议补个锚点（工单号或当版本文档）。

## 五个建议

1. 【9.1|案例示例】"后来我们加了一个写后读一致的路由层"——这是我这种从库延迟受害者最想抄的作业，建议展开半页：是"用户最近 N 秒写过就粘主库"的会话粘性，还是比对从库位点等追平？规则、失效条件、失败兜底各一两句就够。

2. 【9.5|深度广度】全章围绕延迟讲机制，却没讲延迟怎么量。建议在 9.5 对比表或"关键数字"框里补一格：Redis 看主从 offset 差（9.2 已提一句）、MySQL 的 Seconds_Behind_Master 在 IO 线程断开/长事务下会失真（pt-heartbeat 的思路）、Kafka 看 consumer/replica lag 指标——延迟受害者的第一课是先让窗口可见。

3. 【9.3|深度广度】并行复制只讲了机制没讲代价与调参：默认 4 个 worker 在写密集主库下常常不够；WRITESET 扩大并行范围的代价（主库要算写集）只字未提。建议补半段"worker 怎么估、WRITESET 什么时候值得开"。

4. 【9.2|案例示例】fork/COW/出口带宽的代价是分开讲的，建议合并成一个"主库重启后 N 个从库同时全量"的风暴场景：backlog 覆盖不住短断线时，一次抖动变成 N 份 RDB 传输，出口带宽打满又拖慢追赶。顺带一提 Redis 对并发全量本有合并设计（一次后台保存服务多个并发请求、repl-diskless-sync-delay 等后续从到齐），正对着风暴，值得写出来。

5. 【9.7|结构导航】把导读的"先后顺序"案例在 9.7 回收 3-5 句：先写库后删缓存为什么仍有窗口、跨代码路径统一顺序为什么比顺序本身更要紧——或者明说这个话题在第 10 章哪一段展开，别让读者带着案例进章、出章时它还悬着。
