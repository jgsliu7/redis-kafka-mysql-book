## 五个问题

1. 【2.2.1|技术事实】书里写"Redis 按长度分 sdshdr5/8/16/32/64 共五种，短字符串用小头省内存。其中 sdshdr5 最省"，格式描述本身没错，但源码 `_sdsnewlen` 创建字符串时会把 SDS_TYPE_5 无条件提升为 SDS_TYPE_8（注释明说 type5 没有 alloc 字段、不适合会追加的字符串），所以 sdshdr5 在运行期几乎不出现。我面候选人时就爱拿这个细节考人，照书里这句背答案会翻车，建议补一句"实际动态创建的字符串最短也从 sdshdr8 起步"。

2. 【2.2.1|技术事实】渐进式 rehash 一节说扩容阈值"通常为 1"，但漏了关键的另一半：有 BGSAVE/BGREWRITEAOF 子进程期间阈值跳到 5（dict_force_resize_ratio），目的正是少触发 copy-on-write。书里写了"子进程运行期间定时搬迁暂停"，却没写阈值本身会变——排查"RDB 期间内存翻倍、rehash 停滞"恰恰靠这半边，两半合起来机制才完整。

3. 【2.3.3|术语使用】表 2-1 和图 2-7 把时间戳字段写成 `baseTimestamp`，但 Kafka 官方 message format 文档（0.11 起至今）和 Java 源码常量（FIRST_TIMESTAMP_OFFSET）都叫 `firstTimestamp`；`recordsCount` 也与官方 `records` 的写法对不上。读者拿书对照官方文档逐字段核时会卡在这里，建议统一成官方命名或加注。

4. 【2.5 启示四|读不懂】"我自己设计新协议，会先从第二个版本开始——第一个版本很少有人能把边界想全"这句读不懂：是"设计 v1 时就按'迟早有 v2'预留版本字段"，还是"首发就把版本号定成 2"？两种读法都说得通但意思完全不同，跟前一句"留出能力标志或版本字段"的衔接也含糊，建议改成一句没有歧义的话。

5. 【2.5 启示二|逻辑论证】"MySQL 动辄返回几十列几万行"和 2.3.2"收益集中在高并发 OLTP"两处口径打架：单次返回几万行是导出、报表、游标批处理的形态，OLTP 核心路径一次几十到几百行才是常态。拿"几万行"去论证二进制结果集的带宽收益，我作为面试官会当场追问场景，建议把例子换成贴近 OLTP 的行数并补上量化。

## 五个建议

1. 【第2章导读|案例示例】排行榜引子目前是 MySQL 单向挨打，建议补一句 ZSET 自己的代价：每个 member 在 dict 和跳表各存一份、内存约双份，百万级榜单常驻内存的容量与成本也不小。开篇案例就示范"两边各付了什么"，跟第 1 章立的"取舍"方法论才对得上——这也是我面试时的标准反问："为什么不用 ZSET？用了之后你付了什么？"

2. 【2.2.1|深度广度】五大类型里 List 的底层 quicklist 整章缺席：正文五种结构没提，图 2-5 的 listpack 卡片还写着"List/Hash/ZSET 小数据底层编码"，读者会误以为 List 小数据直接落在 listpack 上，实际 3.2 起 List 的编码是 quicklist（双向链表串 listpack 节点）。建议补一小段或在图 2-5 加一行，把"类型↔底层结构"闭环。

3. 【图 2-2|图示】正文把"查名次 O(log N)"的关键压在"span 逐层累加"上，但图 2-2 只画了前进指针、后退指针和查找路径，一条 span 标注都没有，图文脱节。建议在层间指针旁标上 span 数字（如 head→25 的顶层指针 span=7），让"span 累加就是名次"在图上看得见。

4. 【2.3.2|案例示例】全章协议开销都有数字锚点（RESP 编码 SET 是 37 字节、RecordBatch 头 61 字节、zstd 常见 2–6 倍），唯独 MySQL 二进制结果集只停留在"体积更小"的定性描述。建议给一个对照实例：同一条返回 N 行的查询走文本协议和二进制协议各多少字节，让"省带宽"也落到数字上，读者过目才记得住。

5. 【2.6|深度广度】建议章末小结后附 3–5 个自测问题（如"ZSET 为什么同时要 dict 和跳表""intset 为什么只升不降""预编译语句省的是 CPU 还是 RTT"）。这章的内容天然是面试题库，但读者合上书往往只记得结论、记不住取舍链，几个问题能把"目标→结构→协议"的因果链固定住。
