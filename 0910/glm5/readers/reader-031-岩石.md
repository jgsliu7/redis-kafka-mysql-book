# 读者031 · 岩石
身份：RocksDB 调优工程师，7年，爱好：室内攀岩
主读：第 4 章

## 五个问题
1. 【4.1|技术事实】"同价位下，磁盘容量通常是内存的上百倍"这句对 SSD 不成立：近年企业 NVMe 大约 $0.1/GB 量级、DRAM 大约 $2–3/GB，差距是几十倍，能到上百倍的是机械盘。表 4-1 前面专门声明"不是硬件基准"，这句却既不分介质也不给口径，按我"数字要有出处"的习惯，这里第一个被我用笔圈了出来。

2. 【4.1|图示】表 4-1"相对内存"一列口径混用：列头写"延迟以内存为 1"，前几行填的是延迟倍数（0.01×/1×/~1000×），到"SSD 顺序写吞吐""机械盘顺序写吞吐"两行突然变成吞吐类比（"SATA 档约相当于单线程内存随机读"）。我第一遍读到这两行停下来反复确认到底在比什么，建议延迟倍数与吞吐类比拆成两列，或至少加脚注说明切换了口径。

3. 【4.6|逻辑论证】启示三先强调"不能把这些档位按'每条都落盘'到'交给 OS'一一对应"，隔了两段又给出"很多时候答案是各自的中间档"的处方，把 MySQL 的 innodb_flush_log_at_trx_commit=2 与 Redis everysec 并列推荐。=2 在掉电/OS 崩溃时丢的是已提交事务，直接破 ACID 的 D，而掉电恰是这类参数要防的常态故障——跟"缓存丢一秒"不是一个量级的决定，处方写得比警告更响，读者容易只记住前半句。

4. 【4.3|深度广度】崩溃恢复只写了 redo 重放这半边："InnoDB 用 redo log 重放，把缓冲池里没来得及刷盘的修改补回磁盘的数据页"，没提另一半——undo 回滚崩溃时未提交的事务，长事务场景这一阶段常常比 redo apply 更久。4.5 又据此说"MySQL 重放 redo log 较快"，读者拿表 4-3"崩溃恢复代价"一行去评估故障恢复预案（RTO）会系统性偏乐观。

5. 【4.4|逻辑论证】"不做自己的缓冲池"三理由第一条把话说满了："预读机制能把消费者将要读的下几 MB 提前加载进 PageCache，命中率天然就高"。这只在消费者贴着日志尾部时成立；回溯消费、单 broker 上百个分区流交错时，PageCache 照样按近似 LRU 淘汰、预读互相稀释——4.5 自己也把"消费者追不上（fetch 落到磁盘）"列为典型故障，同一章前后力度对不上。

## 五个建议
1. 【4.6|深度广度】启示四"顺序写是跨范式的共性手段"是最好的钩子，建议在此加一小段或一个框：把这条规律推到极致就是 LSM-tree——WAL+memtable 吸收写、后台 compaction 把随机写摊销成顺序写（RocksDB/Cassandra/HBase 都在此列），代价换成写/读/空间三个放大率的三角。我每天调的就是这三个旋钮，而本章给的概念恰好是理解它们的全部前置，不点破可惜了。

2. 【4.1|深度广度】"写放大"在 4.1 和启示四出现了两次，但本章没有一处解释它是什么。建议在 4.1 首次出现处补两三句机制加量级：NAND 要按数 MB 的块擦除后才能改写，4KB 随机覆盖写会触发读改写与 GC，典型写放大 2–10 倍——这样"顺序写对闪存更友好"才从口号变成可推算的结论。

3. 【4.2|案例示例】Redis"进程内管内存"的代价清单缺了碎片这条：表 4-3 把内存管理主体写成"jemalloc + 淘汰策略"，fork/COW 的代价讲了，分配器碎片（mem_fragmentation_ratio 飙到 1.5+、4.0 起的 active defrag）没讲。这是我见过 Redis 容量"凭空消失"最常见的原因，补一小段或表 4-3 加一行，取舍画面才完整。

4. 【4.4|深度广度】Kafka 取舍总结说"没有按主键点查……只能按偏移量区间顺序消费"，边界划得略窄：还有 cleanup.policy=compact 的 log compaction 这一档，支持按 key 取最新值（状态机/KTable 式消费），而且它本身就是"顺序日志+后台重写"，与 LSM compaction 同构。若第 8 章再展开，此处至少留一句，免得读者把顺序日志范式理解得比实际更窄。

5. 【导读|图示】导读里那次选型争论是全章最好的案例——"我花了一下午把两者的访问模式列成了一张表……表摊开之后争论就停了"，但这张关键的表只存在于文字复述里。建议把它真画成一张"访问模式对照表"（数据量/访问频率/延迟要求/事务与查询需求几行），它同时就是启示一"先列读写比例、访问是否随机"的操作模板，读者开自己团队的选型会可以直接抄走。
