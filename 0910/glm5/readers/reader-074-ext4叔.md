# 读者074 · ext4叔
身份：文件系统爱好者，15年，爱好：夜钓
主读：第 8 章

## 五个问题

1. 【8.3.4|版本时效】把"自动关闭双写"的唯一文档路径落在 Fusion-io 的 NVMFS 上——这家公司被 SanDisk 收购后该文件系统停更多年，2026 年的读者按图索骥只会扑空。Linux 6.11 起块层原子写（NVMe/SCSI）已合入主线，ext4 在 6.13 也跟进了单块原子写；8.6.4 那句"这类故障下层有没有更便宜的解法"如今有了活的答案，书里却只留一个死例子。

2. 【8.3.4|读不懂】"512 字节是日志块的组织与对齐粒度，本身不构成掉电时的原子写保证"——既然不保证原子，为什么偏偏对齐到 512？我读 ext4/JBD2 时知道这个数字背后是"传统磁盘单扇区写入事实原子"的老假设，配套的是日志块自身的校验和：撕裂块校验不过，恢复就停在那里。书里没讲 redo 块校验与恢复截断，"从可用日志中重放"的"可用"二字悬在半空，读者无法判定边界在哪。

3. 【8.6.6 图 8-8|图示】正文第一问是"数据会被原地改吗？"，图 8-8 里却写成"需要更新磁盘中的已有记录？"——这两个问题不等价：btrfs/ZFS 这类 CoW 文件系统天天更新已有数据，但从不原地改页。按图上第一问答"是"，一棵 CoW 式设计会被误路由进"页式范式（MySQL）"，图的措辞把正文刻意分开的"更新"与"原地改"又合回去了。

4. 【8.3.2|深度广度】页大小权衡只讲"较大的页有利于某些顺序访问、较小的页减少读入无关数据"——"某些顺序访问"含糊其辞，而且漏了 B+ 树最要命的一端：页越大扇出越大、树越矮、单次点查 I/O 越少。我调 ext4 块大小时两端是吞吐对碎片，InnoDB 对应的另一半"半空的页在所难免"要等到 8.5.2 才出现，8.3.2 本节的取舍论证是残缺的。

5. 【8.3.3|读不懂】"变长字段的长度信息按与字段相反的顺序存放"只述不释——为什么反序？我在纸上按 Compact 记录布局推了半天也没推出反序的收益在哪。本书 2.2 节讲 ziplist 连锁更新时把"为什么"讲得透亮，到 InnoDB 行格式这里突然只剩现象，落差明显。

## 五个建议

1. 【8.3.4/8.6.4|深度广度】防半写其实有三条路：应用层双写（InnoDB）、把数据页写进日志随事务整体提交（ext4 data=journal 的做法）、格式本身不覆盖旧页（btrfs/ZFS 的 CoW；Kafka 追加式天生只有尾部风险，表 8-2"截断残缺尾部"已隐含此点）。建议在 8.6.4 用半页点破这层对称，"下层有没有更便宜的解法"就有了结构化答案。

2. 【8.3.2|深度广度】补齐页大小取舍的两端：B+ 树扇出/树高对半空页浪费，并可加一条跨域注脚——文件系统块大小（ext4 支持 1K–64K、默认 4K，大块利大文件吞吐、小块省小文件碎片）与数据库页是同一条取舍曲线，正合本书"横切找共性"的立意。

3. 【8.2.3/8.2.4|表达可读】7.0 之前单文件 AOF 重写的双缓冲时序讲了三遍：8.2.3 末段、8.2.4 前两段、图 8-3 的图题加图内说明，内容高度重叠。建议 8.2.3 只留一句"增量怎么接上见下节"，机制连同时序图集中到 8.2.4 一次讲完。

4. 【8.6.5|深度广度】演进机制清单列了"版本号、保留字段、Magic、编码切换"，建议补第四件标配：特性位图（ext4 superblock 的 compat/incompat/ro_compat 三组 feature bits）。单一版本号把演进串行化，特性位允许不同能力独立组合上线——RDB 的类型码其实已是它的雏形，点一句即可让"格式即契约"的工具箱完整。

5. 【8.4.4|案例示例】稀疏索引一节已与 Page Directory 互认，建议再加一个文件系统锚点：ext4 的 extent（一段连续块只记一条元数据）与目录 htree（槽位二分加局部扫）就是同款"稀疏元数据+局部处理"手法，对存储/文件系统背景读者是秒懂级类比，也等于把"三个软件之外的第四个样本"自然带到读者眼前。
