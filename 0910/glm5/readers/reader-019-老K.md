# 读者019 · 老K
身份：游戏服务端开发，8年，爱好：主机游戏
主读：第 2 章

## 五个问题
1. 【2.2.1|逻辑论证】「跳表的缓存局部性确实不如红黑树」这个「确实」我不服：两者查找都是逐节点追指针的随机内存访问，局部性差别更多取决于节点大小和分配器行为，而 antirez 当年选跳表给的理由（p=1/4 时平均每节点 1.33 个指针更省内存、范围操作直接、实现好写好调，见 t_zset.c 头部注释）里并没有「局部性吃亏」这条。我调过 skynet 里类似指针追逐的热点路径，这句更像顺手采信的网上共识，要么给实测依据，要么去掉「确实」。
2. 【2.2.3|技术事实】「Broker 收到后把整个 Batch 原样追加到日志段末尾。不对单条消息做任何拆分或索引」——「任何索引」说得太满：Kafka 日志段配的是稀疏 offset 索引和时间索引（默认每 4096 字节一个条目），按 offset 定位恰恰靠它，我做帧回放 seek 时用的就是这套。这句应写成「不做逐条索引、只做段级稀疏索引」，否则读者会误以为消费定位是顺序扫描。
3. 【2.2.1|术语使用】intset 小节先讲「第一条是编码升级」「第二条是类型升级」，两个近义词的区分标准没交代，我读了三遍才对上：前者是 intset 数组内部加宽（intsetUpgradeAndAdd），后者是 Set 对象换底层结构（setTypeConvert）。后文和图 2-5 又把两者统称「升级路径」，两套叫法打架，建议统一成一个术语并各标一句源码函数名。
4. 【2.3.3|技术事实】「零拷贝让一批消息不进用户态，直接从页缓存送到网卡」被写成无条件成立——Broker 一开 TLS，sendfile 这条快路径就断了，数据要回用户态加密后再进 socket，CPU 和吞吐立刻变脸。「安全换吞吐」本是呼应全书取舍主题的活案例，现在这样写，照抄上生产的人会被坑。
5. 【2.3.2|读不懂】「解析只做一次，执行计划则在每次执行时按当时的统计信息重新生成」跟我的既有理解对不上：我以为 MySQL 预编译是 prepare 时定好计划、EXECUTE 复用，只有表结构等元数据变化才触发 re-prepare。若按书中说法优化器每次执行都重跑，那省下的只是词法语法解析的 CPU？这句需要给出版本出处或讲清重优化的触发条件，不然容易和社区主流说法打架。

## 五个建议
1. 【2.2.3|深度广度】RecordBatch V2 的差值编码请把编码方式点名：records 用的是 protobuf 同款 unsigned varint + zigzag（有符号差值映射成无符号再变长），KIP-98 本来就是奔着这套去的。我天天写 protobuf，看到「降到个位数字节」第一反应就是「用的什么编码」；补一句还能顺带交代 varint 解码是分支密集的 CPU 活，为第 8 章磁盘格式留个钩子。
2. 【导读|案例示例】排行榜案例请补「上量之后」的账单：百万 member 的 ZSET 是 dict+跳表并联，每个 entry 除 member 本体外还有 dictEntry、多层前向指针、span/backward，一百字节上下的固定开销——全内存软件里这是最贵的一笔；而 128 个元素以内 ZSET 的编码还是 listpack，跟跳表无关。做游戏排行榜选型时这笔内存账是老板必问的，现在书里只写了「动几个指针」的爽，没写住这么大房子的钱。
3. 【2.3.1|案例示例】「SET key value 编码成上面那串字节，有三十多个字节」建议拆成逐字节账单：`*3\r\n` 4 字节、每个参数头的 `$N\r\n` 各 4–5 字节、每个参数尾 `\r\n` 各 2 字节，合计 35 字节；再放一个同义的 protobuf message（field tag + varint 长度，约 17 字节）对照。「文本 vs 二进制」从口号变成手感，关心序列化开销的读者会专门翻这页。
4. 【2.2.2|图示】MySQL 侧的写代价「页满时一拆为二，级联向上」只有一句话，而它是本节结尾与跳表对照（「跳表插入只做局部的指针更新，没有页分裂」）的另一半论据：建议配一张页分裂前后的小图，画出半数键迁去新页、分隔键上提一层，和图 2-2 的跳表并排看，否则「磁盘 16KB 页约束下特有的代价」停留在概念。
5. 【2.6|案例示例】小结把方法论收在「先列最热的两三种访问模式，再对着结构核对」，建议再加一道读者能动手的选型练习：例如帧同步战斗的回放日志（append-only、按回合拉取）该抄哪家、玩家属性的实时读写该抄哪家、战绩统计报表该抄哪家。让方法从三家的故事变成读者手上的动作，也顺手验证它跨出存储中间件的普适性。
