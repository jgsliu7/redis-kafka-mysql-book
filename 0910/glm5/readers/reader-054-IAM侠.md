# 读者054 · IAM侠
身份：云安全工程师，7年，爱好：集换式卡牌
主读：第 6 章

## 五个问题
1. 【6.3|版本时效】「在 Kafka 3.9 中……allow.everyone.if.no.acl.found 默认为 false」只对 Apache Kafka 自建发行版成立；我日常运维的 Amazon MSK 和 Google Managed Kafka 这个开关默认都是 true（无 ACL 即放行所有人）。书里不区分自建与托管，按"默认拒绝"的认知迁到云上集群，配齐 ACL 之前整集群其实是裸奔的。
2. 【6.7|逻辑论证】启示一收尾说「面向公网的服务应默认收紧，内部工具可以更开放」，两页之后启示五又说零信任「不因请求来自内网就默认信任」。这两句在安全评审里是对立立场（边界信任 vs 零信任），书里没有说明前者指默认配置的宽容度、后者指运行时的信任评估，直接并列，读者拿哪句给自己背书都能找到依据。
3. 【6.5|逻辑论证】把「自定义 ProducerInterceptor / ConsumerInterceptor 在客户端拦截并写审计主题」列为生产审计补全手段，与审计的取证目的矛盾：被审计方自报的记录在取证上不可采信，恶意或被入侵的客户端不会替你装拦截器，而且这还要给客户端额外授审计主题的 Write 权限。它与 Ranger 这种服务端权威审计并列出现，弱审计和强审计看起来成了同档选项。
4. 【6.6 表 6-1|术语使用】「凭证存储」一行里 Redis 写「SHA-256」、MySQL 写「mysql.user 中的 SHA-256 认证信息」，同一个词抹平了正文 6.2 刚讲清的本质差别：Redis 是无盐不迭代的裸哈希，MySQL caching_sha2 存的是 `$A$005$` 格式的加盐迭代哈希，抗离线猜解差着量级。横向对比表本该让差别一目了然，这里反而被读成"两家差不多"。
5. 【6.4|深度广度】6.1 用「磁盘被盗也无法直接读取」定义存储加密，6.4 随即介绍社区版 keyring_file，但没点破其防护边界：密钥文件就放在数据目录旁，整盘镜像或云盘快照泄露（云上更常见的威胁模型）时密钥与密文一起到手，TDE 形同虚设。做应急响应这些年，我处理过的泄露几乎全是快照和备份，不是物理拔盘。

## 五个建议
1. 【6.3|表达可读】「保护模式……是否绑定全部网卡不是这一判断的条件」与 Redis 官方安全文档（写的是"绑定所有网卡且无密码"才触发）相抵触，我核对了 7.0 源码 clientAcceptHandler 才确认运行时确实只查 protected_mode + nopass + 非本地连接。这种反官方文档口径的结论请给出处，或补一句「官方文档与 7.0 实现有出入」，否则多数读者会当笔误跳过。
2. 【6.3|深度广度】Kafka 资源类型列举（Topic、Group、Cluster、TransactionalId、DelegationToken）漏了 USER：6.2 刚讲完委托令牌，而 CreateToken/DescribeToken/DropToken 恰恰授权在 USER 资源上，两节本来正好在这里衔接，现在各讲一半、接缝断了。
3. 【6.7|结构导航】凭证生命周期（TDE 密钥轮换、委托令牌续期、MySQL 改密清认证缓存、SCRAM 凭证更换）散落在 6.2/6.4 各处，建议在 6.7 收拢成第六条启示，或在表 6-1 加一行「轮换/撤销成本」——轮换与撤销是四维模型之外安全评审必查、也最容易事后补课的一项。
4. 【6.2|深度广度】OAUTHBEARER 在 SASL 机制列表里只有一个名字，后文推荐只走 SCRAM 加 TLS。但云托管与零信任路线上 OAuth/OIDC 越来越主流，值得展开一小段：JWT 验证与 JWKS、无状态认证的好处，并与 6.7 零信任段打通——我给 Kafka 做工作负载身份联邦时最先翻的就是这段，结果只有一行。
5. 【图 6-2|图示】CONTROLLER 监听器标注「协议：SSL」，而正文 6.2 对应处写的是「双向 TLS」；节点互信靠 mTLS（双向证书校验），单向 TLS 与之在安全上含义不同，图上应写明 mTLS。另外「ACL 存储」框只画了「KRaft 元数据日志」，正文说 ZooKeeper 模式存 ZK，图注补一句可免读者以为只有一种形态。
