# 读者052 · 等保姐
身份：安全合规审计，10年，爱好：八段锦
主读：第 6 章

## 五个问题

1. 【6.5|深度广度】"务实的选择是异步写入审计日志、对日志采样，或外接专用审计系统"——把"采样"与异步、外挂并列为可选方案且不提示边界，这在合规现场是过不去的：等保 2.0 安全审计要求审计覆盖到每个用户的重要行为，网络安全法第 21 条要求相关网络日志留存不少于六个月，采样等于主动丢弃审计记录，测评时是直接不符合项。作者至少该写明"采样只适用于性能诊断场景，满足留存要求时不可用"。

2. 【6.5|技术事实】"社区版用户通常只能用 General Log 做近似替代"把 MySQL 生态窄化了：Percona Server 自带开源的 audit_log 插件，MariaDB 有 server_audit 插件，生产上相当比例的"社区版"MySQL 其实跑在这两个分支上，语句级审计并不需要企业版或 General Log。这个说法会直接误导读者的加固选型决策。

3. 【6.2|读不懂】"后者在 3.5.1、3.6.0 曾出现用 SCRAM 启动集群失败的问题"我反复读了三遍没读懂：是这两个版本都有 bug，还是 3.6.0 修复了 3.5.1 的坑？没有工单号（KAFKA-xxxx）、没有影响面、没有是否已修复的交代。读者读完仍无法判断今天用 SCRAM 起 KRaft 控制面到底安不安全，这句话等于没说。

4. 【6.3|表达可读】保护模式那段（"是否绑定全部网卡不是这一判断的条件"）用括号套否定句来澄清一个常见误解，我要回读三次才能确认作者在纠正"绑定全部网卡会触发保护模式"这个流传说法。这种"X 不是条件"的表述不如直接给正向生效条件：保护模式拒绝连接 = 开启 + default 用户带 nopass + 非本地连接，一眼即明。

5. 【表6-1|术语使用】表 6-1"审计能力"行把 SLOWLOG 与 ACL LOG 并列——SLOWLOG 是按耗时阈值的性能诊断采样，与"事后查清谁在什么时候做了什么"的审计定义无关。把它列进审计能力反而稀释了 Redis 的真实缺口：成功操作零记录。这一格写"仅记录被拒命令"比"ACL LOG 加 SLOWLOG（弱）"诚实得多。

## 五个建议

1. 【6.6|深度广度】"从姿态对比到生产底线"点了"要满足金融、电信等场景的合规要求"就没有下文了。建议补一小段合规底线清单并做三行映射：审计留存≥6 个月（网安法第 21 条）、三级系统远程管理双因子认证（等保 2.0 身份鉴别控制项）、默认账号清理与密码轮换，每条注明三家各自靠什么落、落不了靠什么外挂。作者已经把"生产底线"四个字写进小节标题，就该给出有牙齿的底线。

2. 【6.5|图示】6.4 与 6.5 连续两节没有图，而审计恰恰是最难凭空想象覆盖面的小节。建议加一张"审计事件覆盖矩阵"：横轴为认证成功、认证失败、授权拒绝、数据读写、管理操作五类事件，纵轴为三家，空格即缺口——"成功操作"一列三家几乎全空，测评师和读者都能在三秒内看清要外挂什么补什么。

3. 【6.6|案例示例】导读里作者自己的公网 6379 爬虫事件讲了一半就再没回收，可惜了本章最可信的资产。建议在 6.6"生产底线"或 6.7 复盘补完整：当时若 protected-mode、ACL、网络隔离各自在位，事件是否可避免；若已有审计留痕，多久能发现。等保方法论里事件复盘要成闭环，第一人称案例前后呼应才立得住。

4. 【6.4|深度广度】TDE 只说了"必须配套密钥轮换与备份策略"就停笔。密钥管理在审计里是最高频的不符合项，建议补一小段实操：keyring 的主密钥与表空间密钥两级结构、ALTER INSTANCE ROTATE 轮换的实际操作、备份恢复时密钥文件必须随备份同步——这三点才是落 TDE 的真实门槛，也是社区版 keyring_file（明文密钥落盘）这一方案必须让读者知情的局限。

5. 【6.2|深度广度】6.1 承诺认证要解决"防暴力破解"，但 6.2 三家认证小节都没回收这个话头，connection_control 到 6.6 才一笔带过。建议在 6.2 末尾补三行对比：Redis 无原生失败锁定机制、MySQL 有 connection_control 递增延迟、Kafka 的 SCRAM 依赖 TLS 与网络隔离兜底——登录失败处理是等保身份鉴别的硬控制项，读者会拿这一节去对照自家测评报告。
