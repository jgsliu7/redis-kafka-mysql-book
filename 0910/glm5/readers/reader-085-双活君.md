# 读者085 · 双活君
身份：异地多活架构师，12年，爱好：画国画
主读：第 9 章

## 五个问题

1. 【9.2 全量同步|技术事实】"Redis 7.0 默认启用 repl-diskless-sync"疑似版本错误：我查了官方发布说明与 GitHub issue #9992，无盘复制默认值从 no 改为 yes 是 8.0 才落地的，7.x 各版本默认仍是有盘。同段"Redis 7.0 共享复制缓冲块"没说错，唯独这句把大版本说早了一代，按 7.0 部署的读者会发现默认行为与书不符。

2. 【9.2 增量同步|深度广度】PSYNC2 一节讲"故障转移后新主把老 replid 存为 replid2，放宽了续传限制"，但没说 replid2 只保留最近一段复制历史。我们做容灾演练时 A→B 切完、副本还没追平又切 B→C 是常有时序，此时仍拿着最老 replid 的副本两头都不匹配，只能全量——"放宽"不是无限放宽，这个边界应该写出来。

3. 【9.3 GTID|深度广度】GTID 一节只讲了收益（自动定位、多源复制好管理），一字未提 errant transaction：副本本地写入会产生自己的 GTID，切换后会回灌新主，GTID 与复制过滤混用的坑更多。双向复制恰恰是各类双活方案的地基，只讲甜头不讲风险，读者真上双主时最先踩的就是这个坑。

4. 【导读与9.7|结构导航】导读第一段点名"多机房多活"是本章动机，小结兑现了"缓存和数据库谁为准"，多机房却没有下文：跨机房 RTT 下半同步基本必降级、Kafka 跨机房靠另一套 MirrorMaker 2 而非本章讲的分区复制。我带着"异地场景怎么选同步机制"的期待进来，这一路从头到尾没接住。

5. 【9.4 acks|逻辑论证】"写路径碰钱和库存，宁可写失败也不静默降级"这个一边倒的倾向我不完全同意：跨机房部署下副本天然按机房分布，`min.insync.replicas` 拒写就意味着整个机房的写路径中断，这正是双活设计要消灭的故障模式。而且它与 9.3 自己强调的"降级必须可观测"自相矛盾——可观测降级加对账兜底，在碰钱场景是另一条成熟路线，不该被"静默降级"一个词盖掉。

## 五个建议

1. 【9.5/9.6|深度广度】建议补一节（或横向对比表加一列）"跨机房/跨集群"：Kafka 的 MirrorMaker 2（offset 重建、防循环复制）、MySQL 跨机房半同步不可行改异步+对账、Redis 跨机房层级复制。单集群机制到异地形态之间就差这半页，补上后本章对多活读者才是完整的。

2. 【9.2 WAIT|版本时效】WAIT 一节说"返回确认也不等于副本已落盘"，这个遗憾新版本已有官方答案：WAITAOF 让副本分别上报已处理偏移与已 fsync 偏移，把确认细化到落盘层面。建议补一句，顺带把"确认语义三档（收到/应用/fsync）"点破，并把全章 Redis 口径从 7.0 对到 8.x（见问题 1 的 diskless 默认值）。

3. 【9.3 半同步|案例示例】AFTER_COMMIT"其他会话已经能读到、切换后看见数据消失"只用两句话带过，这是我在演练复盘里讲一次大家才真懂的窗口。建议补一个两客户端时序小例（会话 B 读到、主崩、新主没这笔、B 再查为空），最好配一幅窄时序图。

4. 【9.5 表 9-1|表达可读】"确认与协调"一行塞了三套机制的分号长句，而降级行为差异（Redis 达不到门槛拒写 / MySQL 超时降异步 / Kafka ISR 不足拒写）恰是 9.3、9.4 反复对比的核心。建议拆成"确认语义"与"降级/失败行为"两行，让全书最有比较价值的一格真正可读。

5. 【9.5 解读二|图示】位点是本章最好的洞见（replid+offset / GTID 集合 / offset+leader epoch），现在只有三行文字。建议做一张三列小图对照"位点构成、换主后如何延续、续传失效条件"，比图 9-2 的抽象模型更值得占一页版面——好构图要留给最值得看的地方。
