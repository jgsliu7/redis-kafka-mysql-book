# 读者040 · OS老师
身份：高校教师(操作系统课)，16年，爱好：集邮
主读：第 4 章

## 五个问题

1. 【4.2|深度广度】小节标题叫「内存淘汰的真实实现」，但近似 LRU 只讲了「随机采样 N 个、从中淘汰最久未用的那一个」——这是 Redis 2.x 的行为；3.0 起引入了 eviction pool（约 16 项的候选池，样本中最差者入池、淘汰发生在池上、可跨轮保留），正是这个池让小样本逼近真实 LRU。我在 OS 课上讲页面置换时常拿 Redis 当工程案例，精髓恰在池化这一步，缺了它，「真实实现」名不副实。

2. 【4.2|技术事实】「fork 一个子进程，子进程拿到父进程内存的副本（依赖操作系统的写时复制 COW 机制）」这句与 COW 语义相悖：fork 时恰恰不复制物理内存、只复制页表——同段后文「fork 拷贝页表」和图 4-3 说明「哪一页被改到才复制哪一页」都写对了，唯独这句「拿到副本」会坐实初学者「fork 会复制整个内存」的经典误解，前后精度不一致。

3. 【4.3|表达可读】「没命中就要读磁盘，延迟会高出两三个数量级」：4.1 说内存与磁盘随机访问「相差三到五个数量级」，关键数字框说「高三个数量级」，这里又成了「两三个」，同一事实三处口径不一，读者不知道该记哪个数。若「两三个」是把 NVMe 快档（约 20μs）也算进去，至少应加半句交代。

4. 【4.4|图示】图 4-6 标题「生产-存储-消费的零拷贝数据流」以偏概全：sendfile/transferTo 零拷贝只作用于 broker→消费者的读方向，生产者写入路径（网卡→broker 进程→write 进 PageCache）并不是零拷贝。图与说明文字全程只画磁盘→网卡方向，标题里「生产」二字会把零拷贝误推到写入侧。

5. 【4.5|逻辑论证】表 4-3 把「生产者 acks + 副本」列进 Kafka 的「持久化机制」行，与 4.4/4.6 反复强调的「acks 控制的是写入确认、不等于落盘」自相矛盾；副本兜的是节点故障（reliability），兜不了机房级掉电（durability），4.5 正文「本地可能丢但靠副本兜底」的措辞把这两个概念又搅在了一起。

## 五个建议

1. 【4.2|深度广度】讲近似 LRU/LFU 时补一句与 OS 页置换 clock/second-chance 算法的对照：「用近似换开销」在内核页置换和 Redis 淘汰是同一思想的两处落地。4.6 启示五已把 CPU 缓存/缓冲池/PageCache 拉成跨层线索，此处是最自然却错过的一处，一句话就能让 OS 背景读者会心。

2. 【4.1|图示】表 4-1 的「相对内存」一列把延迟倍数（0.01×/1×/1000×）与吞吐参照（「相当于单线程内存随机读」）混在同一列，且 SSD 随机读括号给了 100–500μs、倍数却只写 1000×。建议把「单次延迟」与「顺序吞吐」拆成两组行、倍数只留给延迟行（SSD 补 1000–5000×）——这种数量级表最容易被读者拍照当速查表，口径必须一眼读对。

3. 【4.3|案例示例】全章把「命中率支配延迟」讲透了，却没给读者任何观测手段。建议加一行指标出处：`SHOW ENGINE INNODB STATUS` 的 BUFFER POOL AND MEMORY 段（hits/s）或 `information_schema.INNODB_BUFFER_POOL_STATS`。4.7 说命中率是「持续关注的核心指标」，学生/读者的第一个问题一定是「去哪儿看」。

4. 【4.4|图示】把图 4-6 拆成「生产写路径」与「消费读路径」两条泳道：写入侧的高吞吐来自顺序追加＋内核批量回写（普通 write、数据过用户态），读侧才是 sendfile 零拷贝。两件事分开画，读者就不会把零拷贝误推到写入方向，图题也不必以偏概全。

5. 【4.1|结构导航】「关键数字」框（fork 开销/缓冲池命中/vm.dirty_* 三条）放在 4.1，读者尚未读到 4.4 就先撞上 vm.dirty_background_ratio 的细节，导读位置跳跃感明显。建议拆到 4.2/4.3/4.4 各节就近放置，或整体挪到 4.5 横向对比之前，让 4.1 只保留介质层的数量级事实。
