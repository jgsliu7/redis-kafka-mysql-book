# 读者058 · CTF少女
身份：研究生 CTF 选手，研一，爱好：音乐节
主读：第 6 章

## 五个问题

1. 【6.3|技术事实】「在 Redis 7.0 的实现中，保护模式开启且 default 用户带有 nopass 标记时，会拒绝非本地连接，是否绑定全部网卡不是这一判断的条件」这句与官方文档口径直接冲突：redis.io 安全文档写的是 protected mode 在「默认配置（binding all the interfaces，即未显式配 bind）且无密码」时触发，显式 `bind 0.0.0.0`（同样绑全部网卡）按文档不满足触发条件、不会拦远程。这句还决定了一个部署上要命的判断——显式 bind 0.0.0.0 + nopass 时远程到底拦不拦——书里现在的写法没法回答；若作者核对的是 7.0 源码另有结论，应给出处。

2. 【6.2|技术事实】「凭证存储上，密码以 SHA-256 摘要形式保存，不存明文」紧跟在 requirepass 介绍之后，但没区分两种凭证：SHA-256 摘要只对 ACL 用户密码成立，requirepass 至今是明文写在 redis.conf 里的，`CONFIG GET requirepass` 直接回显明文（官方文档原话 "in clear text inside the redis.conf file"）。实战里拿到 Redis 执行权后第一件事就是 CONFIG GET 捞明文密码横向打内网其他机器，照书里的写法，读者会误以为 requirepass 也捞不到明文。

3. 【6.2/6.4|深度广度】6.1 说认证要解决「凭证的存储、传输、校验和防暴力破解」，但 Redis 部分只讲了存储（无盐 SHA-256）和校验，「传输」整段缺位：官方文档明确说 AUTH 与其他命令一样未加密发送、防不了网络嗅探，图 6-3 也明晃晃画着 `AUTH alice <密码>`，可正文（含 6.4 TLS 小节）从没把「不开 TLS 时 AUTH 密码明文过网、且哈希存储防不了重放」这层说破。

4. 【6.2 Kafka|读不懂】「Kafka 3.5.0 也加入了 Broker 到 Controller 的 SCRAM 支持；这与 Controller 之间的共识连接不是同一条路径。后者在 3.5.1、3.6.0 曾出现用 SCRAM 启动集群失败的问题」——「后者」指的「Controller 之间的共识连接」在前文从未铺垫（前文只列了客户端→Broker、Broker 间副本、Broker→控制面三跳）；「曾出现……问题」也没说是 bug 还是有意限制，没有 KIP/issue 号可查。读完我不知道这是在提醒我避坑，还是一句历史注脚。

5. 【图 6-2|图示】图 6-2 三条路径的「信任级别」标注我拼不出来：INTERNAL 是「高（内网互信证书）」、CONTROLLER 是「最高（节点互信，专网）」、EXTERNAL 是「最低（公网最不可信，证书强校验）」——这个「信任级别」指对端网络域的可信度还是这条链路要求的认证强度，图上没定义；且内部只写「内网互信证书」、外部写「证书强校验」，内部监听器的校验到底弱在哪（不同 CA？不做双向？）看不出，只能对照 6.2 正文猜。

## 五个建议

1. 【6.2|案例示例】「历史上未授权 Redis 写 SSH 公钥、写定时任务导致 RCE 的案例非常多见」建议把机制讲透而不是只列现象：CONFIG SET dir/dbfilename 改 RDB 落盘路径 + SAVE 写任意文件（官方文档 Code security 一节明说这个风险）。更值得补的是实战里更通用的第三条链：4.0+ 主从复制 RCE（REPLICAOF 指向恶意服务器 + MODULE LOAD 加载恶意 .so），不依赖猜目标路径；MODULE LOAD 按 Redis 文档属于 @dangerous 类别，印象中 7.0 还加了 enable-module-command 默认禁用（建议核实），正是厂商对这条链的回应——补上它，6.3 讲 ACL 为什么把 CONFIG/REPLICAOF/MODULE 这类命令单独管控就有了落点。

2. 【6.3|案例示例】FILE 权限是全书离「权限→RCE」最近的一句，但只举了读敏感文件。建议补 UDF 提权历史链（FILE 写共享库进 plugin 目录 → CREATE FUNCTION → 命令执行），再讲 8.0 默认 secure_file_priv 与 plugin 目录不可写如何斩断它——这正是启示一「默认安全策略要与部署环境匹配」的现成教材，比「高敏权限的典型」四个字让人记得住。

3. 【6.1|深度广度】6.1 说「缺了哪一段，攻击面就开在哪一段」，但每一段防的是什么攻击，正文基本让读者自行脑补。建议四维各配两三行「攻击者视角」对照：不开 TLS 的 Redis=AUTH 可嗅探、未授权=主从 RCE、SQL 注入+FILE=读文件/UDF、PLAINTEXT 监听器=凭证明文过网。对基础不均匀的学生读者，这种对照是整章最能留住人的部分。

4. 【6.2|结构导航】Kafka 认证一小节连续七段挤了六个话题：SASL 机制清单、SCRAM 原理、KRaft 启动凭证与 3.5.x 问题、委托令牌、监听器分层、配置矩阵故障，而 Redis、MySQL 两块篇幅约其一半且主线单一。建议 Kafka 段内加小标题或拆成「机制选型 / 控制面凭证 / 委托令牌 / 监听器分层」四小块，否则读到 advertised.listeners 那段时注意力已经被 SCRAM 细节耗光。

5. 【6.5|深度广度】Redis ACL LOG「不含命令参数」说完就停了，没讲设计动机：参数里常含密码等敏感值，原样进审计日志等于二次泄露，这是「审计记什么/不记什么」的典型取舍，值得一句点破。另外 Kafka 的 ProducerInterceptor/ConsumerInterceptor 外挂方案只给了一句，可补其盲区：客户端拦截器只能审计自己收发的数据流，Broker 端管理操作（ACL 变更、配置变更）它看不见，这类仍得靠 Authorizer 日志或 Ranger。
