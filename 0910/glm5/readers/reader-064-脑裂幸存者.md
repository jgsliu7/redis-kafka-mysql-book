# 读者064 · 脑裂幸存者
身份：MySQL MGR DBA，10年，爱好：阳台种菜
主读：第 7 章

## 五个问题
1. 【7.3.2（并见 7.3 总述）|技术事实】7.3 总述写半同步"等待指定数量的副本将日志接收并刷盘"、7.3.2 写从节点"写入 relay log 并落盘后就回 ACK"——半同步 ACK 的真实语义是事件已写入从库 relay log 文件，并不要求 fsync（relay log 刷盘由 sync_relay_log 等控制，主机掉电时这部分仍可能丢）。有意思的是 7.4.3 对 Kafka 特意补了"收到确认不等于每条消息都已在各副本上执行 fsync"，到 MySQL 这边反而用了更粗的"落盘/刷盘"，两边口径不一致。
2. 【7.3.3|深度广度】"当网络分区后无法联系多数派时……成员后续如何退出或进入只读状态，还取决于故障处理配置"——作为处理过 MGR 分区现场的人，这句正是我最想要而没得到的答案：group_replication_unreachable_majority_timeout 默认 0（少数派无限期僵持），设了之后超时退出组、单主旧主进只读。前文对 Redis Cluster 连 cluster-node-timeout 默认 15 秒都给了，MGR 这边一个数字都没有，详略失衡。
3. 【7.4.1|读不懂】"在本章的 3.9 基线中，默认逻辑向一个分区累计发送至少 batch.size 字节后再切换"——"3.9 基线"首次出现毫无解释，本章小节号只到 7.7，猜是指 Kafka 3.9 版本，但"本章的"三个字更让人糊涂：版本基线是全书约定还是本章特例？读到这卡了一下。
4. 【7.1 关键数字框|技术事实】"组大小可取 3/5/7/9 个成员，当前实现最多支持 9 个"会被读成"只许奇数"。MGR 实际允许 2–9 的任意数目成员，我做过 4 成员滚动扩到 5 的窗口期，偶数组一样正常服务（只是容错数与 3 相同、白多花一台机器）。下一句解释了奇数更省没错，但"可取 3/5/7/9"这个枚举本身不准确。
5. 【7.5 表 7-1|逻辑论证】MySQL 的"数据分片策略"行老实承认生态分工（"分片交给上层中间件"），但"故障检测与 Leader 选举"行只写 MGR 的 XCom/Paxos——我这十年在生产上见到的 MySQL 高可用，多数还是异步/半同步加 MHA 或 Orchestrator 切换，MGR 反而是少数派。同一张表一行用"生态口径"、一行只给"官方口径"，读者会误以为 MySQL 生态的自动选主只有 MGR 一条路。

## 五个建议
1. 【7.3.2|技术事实】把半同步 ACK 的语义精确为"事件已写入从库 relay log 文件、不含 fsync"，与 7.4.3 对 Kafka 的"确认≠fsync"注记保持同一口径；顺带补上 rpl_semi_sync_master_timeout 默认 10 秒超时降级异步——降级才是半同步最常咬人的行为，比"确认落盘"更值得进正文。
2. 【7.3.3|深度广度】给 MGR 补一条分区时间线硬数字：unreachable_majority_timeout 默认 0（无限僵持）、设置后 N 秒退出组、退出后 exit_state_action 默认置只读、auto-rejoin 重试行为。选 MGR 的人就是冲着这几个数字来的，没有它们，"取决于故障处理配置"等于没说。
3. 【7.4.1|表达可读】"在本章的 3.9 基线中"改成明确说法，如"本书以 Kafka 3.9 为讨论基线"，并在首次出现处（或 1.4 如何读本书）交代版本基线约定，别让读者把 3.9 当成小节号来回翻。
4. 【7.5|深度广度】表 7-1 建议增设一行"分区后到停写/退出的窗口"：Redis 约 cluster-node-timeout（默认 15 秒）、MGR 取决于 unreachable_majority_timeout（默认无限）、Kafka 无可用 ISR 时 acks=all 写入直接失败。高可用怀疑论者选型就看这行数字，比"行为"描述有用得多。
5. 【7.6 启示五|案例示例】启示五讲了"由业务需求倒推"，建议再补一步"怎么验证所选方案在分区时真的按预期停写"：给出三个软件各自的分区注入验证入口（iptables 切断 Redis 少数派主观察停写、断 MGR 多数派观察退出与只读、停 Kafka Follower 观察 ISR 收缩与 acks=all 失败）。没演练过的容错方案等于没有——这正是导读里库存超卖案例的反面教材。
