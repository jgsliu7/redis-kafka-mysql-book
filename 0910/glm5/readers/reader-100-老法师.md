# 读者100 · 老法师
身份：退休返聘技术专家，从业30年，爱好：下象棋
主读：第 10 章 + 全书结构（序言/后记/抽读导读：第 3 章生命周期、第 8 章磁盘存储格式）

## 五个问题
1. 【序言/10.2|结构导航】序言把"道"的来源立了两块：存储层次的设计、并发任务的处理（多核 CPU），但第 10 章五条规律只用图 10-1 正式收了存储层次这一条线；并发那条线在 10.3.1 维度四里只剩"Redis 单线程难以利用多核"一句带过。序言开的支票兑了一半，通读骨架的人会在这儿停下翻回去找。
2. 【10.3.1/10.3.2 图 10-2|逻辑论证】10.3.1 讲了五个权衡维度，图 10-2 的选型问题图里 Q1–Q4 各自标了四个维度的括号注，唯独维度五"通用 vs 专用"没有分支，正文也没说明它为何不进图。读者分不清这一维是选型工具还是理论装饰——五个维度在收口处掉了一个。
3. 【3.2|技术事实】"AOF 优先是因为它携带的信息严格多于单独的 RDB"——"严格多于"这个数学口吻的措辞太绝对。手动 BGSAVE 刚完成而 AOF 最后一笔刷盘落后近一秒（everysec 窗口）的时序里，dump.rdb 反而比 AOF 尾部新；而 Redis 的加载规则是 AOF 优先、并不比较两者新旧，极端窗口下会恢复到更旧的状态。"严格"二字应留出"通常"的缝。
4. 【10.2.4/10.3.1|深度广度】"存储系统正确执行刷盘请求，是这一保证成立的前提"在 10.2.4 和 10.3.1 出现了两次，但全书没有展开这句话背后几十年的公案——磁盘写缓存回写、RAID 卡电池、所谓 fsync 谎言。我这一代人知道这是拿事故换来的前提，新读者会当一句免责套话滑过去：话的分量立住了，给读者追下去的线索没给。
5. 【10.2.3 图 10-1|图示】图注承诺"两侧比较访问延迟、容量与职责"，但图内只有"更快·更小 / 更慢·更大"的定性箭头，一个量级数字都没有。存储层次这条"道"的全部说服力在 10^3 到 10^6 的量级差上（寄存器约 1ns、内存百余 ns、SSD 百微秒级、机械盘毫秒级），定性箭头把最有力的证据丢了，等下象棋的人自己脑补车马炮的子力差。

## 五个建议
1. 【10.4.1 表 10-2|深度广度】"是否跨地域容灾"一行三个软件的答案颗粒度不一：Kafka 给了具体工具（MirrorMaker / Cluster Linking），Redis 只给了一句态度"Cluster 跨机房复杂"，MySQL 居中。建议 Redis 栏补主流做法（异地主从加客户端切换、或 redis-shake 类同步），MySQL 栏补 InnoDB Cluster / 异步副本加 Router 的组合——checklist 是全书落点，三栏要对得起序言第三层"能落地的整体"的承诺。
2. 【8.1.3|深度广度】"本书为什么没讲 LSM 树"的框注理由我认，但 10.3.1 的维度三（空间 vs 时间）和维度五（通用 vs 专用）恰是 LSM 对 B+ 树最经典的对照场景。建议在 8.5 横向对比或 10.3 框架里给 LSM 一句对照落点（用写放大和后台合并换顺序写吞吐），否则读者拿五维框架去对 RocksDB/TiDB 时缺了第四种范式，只能自己补课。
3. 【10.2.4|案例示例】把"存储正确执行刷盘是前提"落成一个老兵案例框：企业级 SSD 的掉电保护电容、RAID 卡回写缓存与电池单元、为什么数据库机器的采购单上这两项历来是硬条件。这句话值得一个具体案例撑住，不然它只是两句正确的话。
4. 【10.3.3 练习一|案例示例】网约车练习把司机位置放 Redis GEO 的判断我赞成，建议补一句落地坑：GEO 底层是 zset，member 没有过期语义，司机下线后位置残留，"附近司机"会召回僵尸司机，业务侧必须自己做心跳过滤或定期清理。练习重在决策没错，但正走到"设计者阶段"的读者需要看见理想路径之外的第一颗钉子。
5. 【10.1 表 10-1|表达可读】表 10-1 一张表收九章（9 行 6 列、每格都是压缩表述），是全书的总账，建议表后补两三句"怎么用这张表"的导读：先纵向按一列看三个软件的个性，再横向按一行看八个主题的共同骨架。我这把年纪的人能自己啃下来，两年经验的读者多半当速查表翻过去，可惜了这张表。
