# 读者070 · CAP迷糊
身份：普通后端，6年，爱好：综艺
主读：第 7 章

## 五个问题
1. 【7.1|读不懂】CAP 那段我卡了两遍："也不能直接换算成产品的快慢排序"这句完全没看懂——是说不能拿一致性强弱给三个软件比谁快吗？"保留真实时间先后"我猜是"先返回成功的写，之后开始的读必须能看到"，但不敢确定。我这种背了就忘的读者，这段两三个从句下来就散了。
2. 【7.4.3|深度广度】"收到确认不等于每条消息都已在各副本上执行 fsync"把我这几年对 acks=all 的理解直接掀翻——不等 fsync 凭什么说"已提交消息有相应的保留保证"？我猜是靠多副本冗余替代单机落盘，但书里一句不解释就引去第 9 章；正拿着 acks=all 做方案的人最需要在这里给两三句机制。
3. 【7.4.1|结构导航】"在本章的 3.9 基线中"——第 7 章里没有 3.9 节，我第一反应是翻小节号，没找到；猜是"本书以 Kafka 3.9 为版本基线"，但这个约定在哪交代过没印象。版本基线这类全书约定最好用固定说法（如"本书基线 Kafka 3.9"）并显式声明一次。
4. 【7.2.3|技术事实】"少数派主节点……在 cluster-node-timeout 触发的超时判定后停止写入"——我在生产分区故障里看到的是少数派对它管的槽读写一起报 CLUSTERDOWN，不止停写（后来才发现有 cluster-allow-reads-when-down 开关且默认关闭，恰好说明默认连读也不给）。只写"停止写入"会让人以为少数派还能读旧数据，跟 7.3.3 MGR"读取可能陈旧"的口径不对称，希望作者核实。
5. 【7.3.1|术语使用】小节标题"单向、异步、行流"——"行流"这个词我在 MySQL 官方文档和其他书里都没见过，正文也没正面定义，只在后文顺带说 binlog 是"变更流的载体"。自造词放标题，读者第一眼就卡住，不如直接叫"基于 binlog 的异步复制"。

## 五个建议
1. 【本章导读|案例示例】开头的库存超卖事故讲到"要为故障转移可能丢数据做好预案"就断了：后来到底怎么改的——上 WAIT、库存挪去 MySQL、还是加对账兜底？建议补一段"事故后日谈"，与 7.6 启示五"别因为手里有 Redis 就拿它存交易记录"闭环。读者最能带走的是改法，不只是事故。
2. 【7.1|图示】CAP 段建议配一张双节点分区小场景图（或小表）：分区发生→两边各自还能不能读/写→谁返回旧数据→恢复后哪边数据留下。我是背了就忘型选手，文字定义记不住，一张"分区那十几秒两边各自能干什么"的图能把 C 和 A 到底在换什么钉死。
3. 【7.2.2|结构导航】"共识算法一分钟直觉"盒子建议挪到 7.1 难题二第一次出现"Raft 这类共识协议"的位置——线性读到那里我已经被多数派、选主、日志复制拦住了，盒子却藏在 7.2.2 Sentinel 小节里。另外"可以读 Raft 的原始论文"建议直接给论文名（In Search of an Understandable Consensus Algorithm）或 raft.github.io，不然读者没法搜。
4. 【7.4.4|表达可读】KRaft 成熟度一段塞了 3.3/3.4/3.5/3.6/3.9/4.0 六个版本号，我读了两遍才理清"哪个版本敢上生产"。建议改成一条时间线小图或"版本|事件|能不能上生产"三列小表，把 3.3（新集群生产可用）和 3.6.2+/3.7.1+（迁移工具 GA）两个决策分界点亮出来。
5. 【7.5|案例示例】表 7-1 建议补一小块"生产起步组合"：Redis 3 主 3 从+按需 WAIT、MySQL MGR 3 成员+Router（即 InnoDB Cluster）、Kafka 3 副本+acks=all+min.insync.replicas=2——三家各自的最小"抄作业"配置和适用前提。对比表停在机制层面，我这种读者最后一步需要的是能直接落地的起步参数。
