# 读者028 · 云仔
身份：云厂商 SaaS 后台开发，5年，爱好：滑板
主读：第 3 章

## 五个问题
1. 【3.4|读不懂】「preStop hook 可以先触发 BGSAVE，确认本次快照成功完成后再执行 SHUTDOWN NOSAVE。BGSAVE 返回成功只表示后台保存已启动。」——那到底用什么确认快照完成？书里没给机制（轮询 LASTSAVE 时间戳变化？等 RDB 子进程退出？），紧接着两段又全在讲这个方案为什么不可靠（停写难保证、grace period 不够）。我平时给租户编排写 preStop 脚本，读完整段只知道「难」，不知道作者推荐的正确姿势是什么。
2. 【3.2|逻辑论证】正文说「第三步是否写入 RDB 由用户决定」，图 3-3 也标注「决定权交给用户」，但最常见的恰恰是 SIGTERM 路径（systemd stop、K8s 滚动重启），这条路径上没人能附带 SAVE/NOSAVE。真实默认行为——「只要配了 save 点（出厂默认就配）且不走 NOSAVE，主进程就会在退出前同步做一次全量 RDB 落盘」——直到 3.4 容器一节才倒叙揭晓。3.2 和图 3-3 都没画这个默认分支，读者在 3.2 建立的心智模型到 3.4 被推翻重来。
3. 【3.3|深度广度】关闭慢根因第 3 条说「主库关闭则直接断开 dump 线程，并不等从库把 binlog 拉完」，只给现象不给后果：从库缺的那段 binlog 靠什么补齐（重连后按位点增量追）？binlog 已被清理时是不是要全量重建？更关键的是，按 3.6 启示二「优雅关闭=兑现保证+交还职责」的标准，主库的优雅关闭并没有兑现「从库不缺数据」这个保证，MySQL 为什么可以接受，书里没有交代。
4. 【3.5|表达可读】表 3-2 里 Kafka 的「关闭时的数据保证与可配置性」一栏写「强制刷盘，无选项」，与 3.4 正文刚讲完的 controlled.shutdown.enable / max.retries / retry.backoff.ms 三个可调参数相抵触，第一遍读会误以为 Kafka 关闭没有任何旋钮——实际只是「落盘行为无开关，集群协调行为有多档」。
5. 【3.6|逻辑论证】启示四声称三家启动都遵循「配置 → 基础设施 → 核心服务 → 数据恢复 → 对外服务」，但拿 3.4 自己列的 Kafka 八阶段去对：日志恢复是第 3 阶段，网络层第 4、副本管理器/控制器第 5/6——数据恢复排在「核心服务」之前，与共性线的顺序直接矛盾；Redis 的四段里「核心服务」对应哪段也说不清（预分配数据库数组算基础设施还是核心服务？）。这条共性规律有事后归纳的嫌疑。

## 五个建议
1. 【3.4|案例示例】把 Redis 容器化退出方案补成一份能抄的闭环：CLIENT PAUSE WRITE（停写）→ BGSAVE → 轮询 LASTSAVE 时间戳变化确认快照完成 → SHUTDOWN NOSAVE，并给出 grace period 估算式（停写等待 + fork 页表拷贝 + 全量写盘 + 30 秒余量）。现在有方向、有两段风险警告，独缺能落地的操作序列。
2. 【3.4|深度广度】补一小段「编排侧的并发纪律」：Kafka 受控关闭要串行（PDB / maxUnavailable=1，节点排水时防止两个 broker 同时进入终止、抖动叠加）；MySQL 滚动重启从库先、主库后。书里反复讲「关闭是集群事件」，编排系统如何响应这个事件，正是我这号做启停编排的读者最想看的半章。
3. 【3.3|深度广度】主库/从库关闭差异处补两句后果与预案：从库重连后按位点增量追赶、所需 binlog 已清理时触发全量同步、关主库前先看 Seconds_Behind_Master，让根因 3 和根因 1、2 一样有取舍解释，而不是一句带过。
4. 【3.2|图示】图 3-3 在「② 刷 AOF 缓冲」之后增加默认分支框：SIGTERM / 无修饰 SHUTDOWN 时，配置了 save 点则走 ③a（阻塞式落盘），把 3.4 才倒叙的默认行为提前到建立心智模型的位置。
5. 【3.3|案例示例】表 3-1 或正文给一两组真实量级数据：比如数百 GB 缓冲池、写入密集的库，档位 0 的 purge + change buffer 合并与档位 1 的关机耗时各在什么量级。现在只有「几十分钟甚至更久」一句话，DBA 没法校准自己的库该定多长的 grace period。
