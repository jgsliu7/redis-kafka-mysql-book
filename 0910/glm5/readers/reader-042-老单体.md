# 读者042 · 老单体
身份：单体系统维护者，20年，爱好：水族养鱼
主读：第 5 章

## 五个问题

1. 【5.1（含本章导读）|逻辑论证】导读说「加一个新特性要在五六个地方重复改动」等所有痛「归根到底都指向同一件事：系统没有分好层」，这个归因过头了。我维护的老单体 Controller/Service/DAO 分得清清楚楚，照样一个需求改五六个文件——切分维度是技术层、变化方向是业务功能，散弹式修改在分层良好的系统里照样发生；而且导读自己的案例（改 Controller 三行、订单 SQL 和导出逻辑混在同一个 DAO）里系统分明有 Controller、DAO 这些层，问题出在 DAO 层内职责没切开，这恰恰是「分了层也照样烂」的证据，拿它论证「没分层」之痛有点自打脸。

2. 【本章导读|逻辑论证】「分层能做多薄，就看一件事：这次抽象带来的延迟，你愿不愿意付」把分层决策压缩成延迟单一变量，可 5.5 表 5-1 自己列的三家首要目标是低延迟、兼容性与生态、水平扩展三样。对我这种业务系统维护者，分层的货币是维护成本和团队协作，跟亚毫秒延迟毫无关系；开篇用延迟当唯一标尺，等于先把三分之二的读者挡在门外。

3. 【5.3.3|技术事实】「如果你只用 InnoDB，这笔开销就是纯成本」不成立：InnoDB 原本是 Innobase 公司的独立产品（2005 年被 Oracle 收购，2010 年才成为 MySQL 默认引擎），Handler API 的价值不只是运行时换引擎，更是隔离组织边界、让 server 与引擎由两家公司按各自节奏独立演进——只用一个实现时这份价值也在。这也和 5.6 启示二「核心抽象延续、具体实现可演进」自相矛盾：接口既然支撑了 InnoDB 十几年的独立演进，怎么算纯成本。

4. 【5.4.3|版本时效】「3.9 起 Tiered Storage 正式 GA（3.6 起以早期版本引入）」版本号疑误：Kafka 4.0.0 官方发布公告（2025-03-18）才宣布 Tiered Storage（KIP-405）GA，3.6 为 Early Access，3.9 没有宣布 GA。第 8 章若沿用「详见第 8 章」的同口径，请一并核对。

5. 【5.2.2|技术事实】同一段前面刚说「Redis 7.0 重构后，命令表改由 commands/ 目录下的 JSON 描述文件自动生成到 commands.c」，紧接着说「加一个新标志位意味着要改遍所有命令的声明」——JSON 描述里 flags 是数组字段，新增标志位对不受影响的命令无需改动，这个论断描述的是 6.x 静态 C 表时代的情况，放在 7.0 之后的语境里前后矛盾，至少应限定版本。

## 五个建议

1. 【5.1|深度广度】在 5.1 或 5.6 补一小段「水平分层 ≠ 垂直切分」：导读列的「一个特性改五六个地方」主要靠按业务边界垂直切分（模块化）解决，水平分层管不住跨层的同业务改动。我见过太多按技术分层分得规整、业务却全搅在一起的老系统，一句话点破能救不少读者拿「分层」当散弹式修改的万灵药。

2. 【5.6 启示四|案例示例】把导读的导出按钮案例在启示四回收：那个系统不是没有层，而是 DAO 层里订单查询和导出两个职责没切开——正好说明「层内内聚」比「层数」更要紧。现在导读案例讲完就丢，读者读到反模式三条时早忘了它，串起来正好形成闭环。

3. 【5.2.1|深度广度】Redis「整个内存模型都建立在单线程修改的前提上」这段把性能面讲透了，但薄分层的隐性可维护性代价没点破：全局共享可变状态靠的是小核心团队和极高的代码纪律，同样的结构放到普通团队维护十年的单体上就是没人敢动的泥球。建议在 5.2.1 或启示部分补一句适用条件——设备越少的裸缸越稳定，前提是你真会养鱼。

4. 【5.3.3|案例示例】Handler API 一节建议补一笔 InnoDB 与 MySQL 分属两家公司、被 Oracle 收购后仍按自己节奏演进的史实：可插拔接口一半的价值在组织边界（康威定律），对架构师读者这比 vtable 开销更值钱，也顺手化解「只用 InnoDB 就是纯成本」的绝对化表述。

5. 【5.4.4 与图 5-7|图示】5.4.4 刚讲完 Kafka 是「交互 + API + 存储 + 协调」四段、协调层「不属于交互层、不属于 API 层、也不属于存储层」，紧接着的图 5-7 却把 Kafka 列画成整齐三段，ReplicaManager/Controller/KRaft 不见踪影，正文也没交代它归并到哪段。建议图 5-7 给 Kafka 列加一个虚线「协调（跨 Broker）」侧框或脚注，让图的口径和 5.4.4 的四段说法对得上。
