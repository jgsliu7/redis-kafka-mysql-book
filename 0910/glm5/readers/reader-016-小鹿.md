## 五个问题
1. 【2.3.2|技术事实】书里说预编译语句"执行计划则在每次执行时按当时的统计信息重新生成"。我平时用 ORM 的 prepared statement，印象里 MySQL 的计划是 prepare 后缓存复用、只有 DDL 或相关系统变量变化等触发条件才重新优化；若真如书中所写每次重新生成，"解析只做一次"的收益叙事也讲不完整。这段请核对，我不想拿它去跟同事讲错。
2. 【本章导读|技术事实】导读说没索引时"每次刷新排行榜要把整张表捞出来排序（filesort）"。我 EXPLAIN 排查慢查询时记得 ORDER BY ... LIMIT 会走优先队列（top-N）优化：全表扫描逃不掉，但并不把整张表完整排序；百万级秒级慢主要慢在扫全表。"捞出来排序"这个机制描述我觉得不准。
3. 【2.2.1|读不懂】"span 逐层累加就是名次"这句我没接住：顺着图 2-2 的前进/下沉路径查找我会了，但正文从头到尾没给过一个 span 的具体数值，我想拿纸笔照图复算一遍 ZREVRANK 都无从下手。查名次可是本章开头排行榜例子的另一半卖点，值得一个带数字的算例。
4. 【2.2.1|术语使用】dict 一节在括号里甩出"SipHash、哈希洪泛攻击、随机种子"三个黑话，一句解释都没有。我在前端听说过 V8 给对象哈希加随机种子也是防这类攻击，所以特别想读懂这段，但书里连"攻击者怎么把所有键挤进同一条链"都没讲，只能中断阅读跳出去查。
5. 【2.2.1|逻辑论证】同一段先说跳表上层是"每隔几个节点保留一个指针"，段末又说"层数逐层独立抛硬币"，这两句我合不上：索引层到底是规律抽稀还是每个节点随机定层？前一句是不是为了直观牺牲了严格性？两处至少该有一处说清。

## 五个建议
1. 【2.2.1|案例示例】ziplist/listpack、intset 的"内存密度高"从头到尾是形容词，建议给一个可复算的数字例子：比如一个 100 个短字段的小 Hash，listpack 编码与升级成 hashtable 后各占多少字节（真实跑一下 MEMORY USAGE 即可）。有了数，"小数据用紧凑结构、膨胀后切换"这条升级规则才立得住。
2. 【2.2.2|深度广度】"一个 16KB 页容纳几百个键、两层内部节点、千万行整棵树三层"这组数字建议落成一遍可复算的算术（键长多少、每页几个键、扇出多少、每叶几十行），并顺带解释上层页常驻缓冲池所以点查是"两到三次 I/O"怎么来的。我数据结构底子弱，能自己算一遍的结论才记得住。
3. 【2.3|图示】图 2-8 三协议对比里，RESP 给了 SET 的真实字节、Kafka 给了请求头字段，正文对 MySQL 段只交代"那两步是预编译的两次往返"。建议给 MySQL 侧也补一小段字节级样本（COM_STMT_PREPARE 返回 statement_id、COM_STMT_EXECUTE 带占位值），三家同一粒度，这张图才真正对照得起来。
4. 【2.5|案例示例】启示四"我自己设计新协议，会先从第二个版本开始"是全章我最想抄进手账的一句，但它现在只有断言。建议配一个第一版没留版本字段、生态铺开后被迫推倒重来的真实或化名案例，这条最锋利的判断才有落地形状。
5. 【第2章|结构导航】建议在每章"本章导读"后加一个很小的"前置知识自检"框（本章：O 记号、哈希冲突、磁盘页概念），给跨背景读者一条自查路径。序言里说"多用 AI 帮你快速了解"，但书内给锚点更稳，不至于读到一半才发现自己缺地基。
