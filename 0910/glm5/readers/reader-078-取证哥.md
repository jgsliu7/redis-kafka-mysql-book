# 读者078 · 取证哥
身份：数据恢复技术员，13年，爱好：业余无线电
主读：第 8 章

## 五个问题
1. 【8.3.4|读不懂】「512 字节是日志块的组织与对齐粒度，本身不构成掉电时的原子写保证」这句把常见误区点破了（很多人拿『扇区=512B 所以原子』糊弄），但炮响之后没下文：redo 尾部写一半的块靠什么被发现、恢复重放到哪里停？我判读半写的 redo 尾巴靠的是日志块头里的数据长度字段，恢复扫描停在最后一个自洽块——书里把这一句补完整才算闭环。
2. 【8.1.3 关键数字框（另见 8.4.3）|逻辑论证】「每批元数据约 61 字节」与「V0 单条固定开销约 14 字节」不是同一口径：61 里含 BaseOffset(8B)+batchLength(4B) 这 12 字节外框字段，而 14/22 明说不含最外层 12 字节消息框；括注只给 V0/V1 补了含框值 26/34，V2 的 61 没做同样处理。同口径应是 61 对 26、或去框后 49 对 14，否则拿这组数字做容量估算的读者会高估 V2 的批头开销。
3. 【8.5.2|技术事实】「一页里哪怕只剩几行 100 字节的记录，也要占整整 16KB」这个例子没考虑页合并：页占用率低于 MERGE_THRESHOLD 时 InnoDB 会把记录并入兄弟页、腾空的页回收复用，「只剩几行」的空壳页不会长期独立占着 16KB。定长页最小分配单元是 16KB、表空间文件不收缩、空间只在段内复用——这才是浪费的真实形态，现在这个例子打偏了靶子。
4. 【8.2.2 与图 8-2|图示】正文把文件组成列为「魔数版本 / metadata / db-selector / entries / CRC64」，图注同样如此，但图 8-2 里明明画了 EOF 0xFF 框。对写解析器的人来说 0xFF 是终止遍历的信号，正文和图注却把它跳过了，我无法确定哪份清单才是完整的。
5. 【8.2.2|深度广度】「校验失败会中止恢复」——中止之后呢？RDB 损坏时 Redis 是拒绝启动还是空库拉起（实际是报错退出），运维下一步该改用 AOF 还是重建实例？AOF 侧有 --fix 专段，RDB 侧却在最关键的处置行为上戛然而止。

## 五个建议
1. 【8.1.1 与表 8-2|深度广度】8.1.1 自己把「字节序」列为格式契约的要素之一，但全章没有一处交代三家格式是大端还是小端。建议在表 8-2 加一行「字节序」：Kafka 消息与 .index 条目大端、InnoDB 页字段在常见 x86/ARM 平台小端、RDB 的长度与整数大端——手工解析任何一家的文件，这都是第一个要确认的字段。
2. 【8.2.2 与图 8-2|图示】导读说「字节怎么排列是个非常关键的问题」，建议给 RDB 和 Kafka .index 各配一段真实文件的十六进制 dump 节选（十几字节即可）：REDIS 魔数加 ASCII 版本号、一条 entry 的首字节、尾部 CRC64；.index 的大端定长条目一眼可见。顺带把 metadata/db-selector/EOF 背后的单字节操作码（0xFA/0xFE/0xFF）点名，读者就能照着写出解析器。
3. 【8.4|结构导航】表 8-2 给 Kafka 崩溃恢复的半行「以日志为正本，校验并截断残缺尾部」在正文 8.4 没有任何落点：MySQL 有整节 8.3.4、Redis 有校验与修复专段，唯独 Kafka 的恢复流程缺席。建议补一小段 broker 启动时的日志恢复（从 recovery checkpoint 起逐批校验 CRC、截断残尾、重建 .index/.timeindex），并点破「索引是衍生物、删了可重建，.log 才是正本」——这是恢复工程师对 Kafka 最实用的一条性质。
4. 【8.2.2 与 8.2.3|案例示例】损坏处置不对称：AOF 有 redis-check-aof/--fix 的处置段落，RDB 侧连 redis-check-rdb 这个现成工具都没出场。建议补上工具用法（可定位损坏发生的位置）和「载入失败后的拉起决策」（改用 AOF，还是接受丢快照重建），把「检测—定位—处置」三步凑齐。
5. 【8.3.4|深度广度】双写区自身的完整性没讲：双写文件里的页同样可能半写，恢复时 InnoDB 会先校验双写区内的页、只有完好的副本才拿去覆盖正式页。建议在 8.3.4 补一两句这层「兜底本身的兜底」，否则读者会以为双写区天然完好，也理解不了双写区要按批集中顺序写的用意。
