# 读者056 · 风控爷
身份：支付风控开发，12年，爱好：古典音乐
主读：第 6 章

## 五个问题
1. 【6.3|技术事实】书断言"Kafka 3.9 中 ZooKeeper 模式的 AclAuthorizer 和 KRaft 模式的 StandardAuthorizer 都将 allow.everyone.if.no.acl.found 默认为 false"，这对社区版成立，但托管发行版是反着来的：AWS MSK 和 Oracle 托管 Kafka 的官方文档都写明无 ACL 资源默认对所有人开放（默认等价 true）。我评审的多是云上托管集群，书不注明"这是社区版行为、托管云常见反转"，读者把"启用授权器=默认拒绝"直接套到 MSK 上，会漏掉一个默认放行的大洞。
2. 【6.3|技术事实】保护模式的生效条件与官方文档冲突：书说"在 Redis 7.0 的实现中，保护模式开启且 default 用户带有 nopass 标记时，会拒绝非本地连接，是否绑定全部网卡不是这一判断的条件"，而 redis.io 官方安全文档的表述是"以默认配置（绑定所有网卡）且无密码运行时进入保护模式"。两个口径下加固清单完全不同——显式 bind 0.0.0.0 加 nopass 时 7.0 到底拒不拒远程连接？请给出处并统一口径，这直接决定我加固清单里"检查 bind"这一条留不留。
3. 【6.5|逻辑论证】不服"审计排最后、可采样"的倾向。书说"务实的选择是异步写入审计日志、对日志采样"——支付场景里资金变动类操作采样审计等于没有审计，出险那天恰好漏采那一笔，取证链就断了；PCI-DSS Req 10、等保对敏感数据访问是全量留痕的硬性要求。"如果每条操作都同步写审计日志……甚至让系统不可用"也是个假两难，顺序追加、异步落盘、独立管道采集是标准做法，至少应加"高危操作必须全量"的限定。
4. 【6.4|逻辑论证】TDE 的威胁模型画到一半：6.1 自己把存储加密定义为防"磁盘被盗"，6.4 讲 MySQL TDE 时却不点破它对 SQL 层拖库（合法账号、SQL 注入、FILE 权限读文件）零防护，而支付行业实际出险大多走 SQL、备份、从库这三条路。讲到了 binlog/redo/undo 加密，却没提 mysqldump/XtraBackup 逻辑备份天然是明文——加密边界没有闭环，读者会高估 TDE 的防护面。
5. 【6.2|深度广度】caching_sha2_password 一节只把认证缓存讲成性能优化（"缓存减少了高频建连时的重复认证开销"），没讲它的安全面：快速路径靠内存里缓存的摘要应答挑战，这份缓存等效于一张可直接认证的中间凭证，服务端内存/转储泄露的后果与 mysql.user 里加盐哈希泄露完全不在一个量级。风控评审必问"凭证在内存里躺成什么样"，这层风险是漏的还是我理解有偏差？

## 五个建议
1. 【6.6|案例示例】"从姿态对比到生产底线"是全章最贴近实操的一节，但现在是三段散文，评审现场没法直接用。建议落成每家 8–10 条可勾选的清单：Redis 的 default 用户处置与每应用独立 ACL 用户、MySQL 的最小权限加 connection_control 加 FILE 权限审查、Kafka 的三重点之外补 SCRAM 凭证轮换与监听器配置模板——我做十二年评审靠的就是 checklist，散文记不住也带不走。
2. 【6.4|深度广度】MySQL 存储加密补"备份与恢复链路"一小段：表空间、redo/undo、binlog 都加密了，mysqldump 与 XtraBackup 出来的备份以及挂载的从库仍是明文，密钥丢失等于数据不可读，所以配套的轮换与备份策略必须包含密钥备份和恢复演练。一句话点破"TDE 不防 SQL 层拖库"，读者才不会把存储加密当成拖库保险箱。
3. 【6.5|深度广度】补"审计日志自身的防篡改"：集中采集、append-only/WORM 存储、与 DBA 权限分离（职责分离）。管理员可删改的审计在合规取证里没有证据效力——这其实是三家审计"几乎总是外挂"的另一半原因（不只是性能），补上后本节"接受现实再务实选择"的结论才完整。
4. 【6.1|深度广度】加一个"四维 ↔ 合规条款"映射小框：认证/授权对应 PCI-DSS Req 7/8、传输与存储加密对应 Req 4、审计对应 Req 10，再挂上等保 2.0 安全计算环境对应项。金融支付读者拿这章做评审时必须把技术维度翻译成条款，现在全书只有"金融、电信等场景的合规要求"一句带过，四维模型的实战价值差最后一公里。
5. 【图6-1|图示】图里审计的虚线采集点只从"执行"和"存储加密"两处拉出，与图注"审计以旁路贯穿全程"以及 6.5 的实际审计源不符——ACL LOG 和 Authorizer 日志记录的主要是认证与授权环节的被拒事件。建议把采集点画到认证、授权阶段（或标注"任意环节可采集"），否则读者会误以为审计只发生在执行与落盘附近。
