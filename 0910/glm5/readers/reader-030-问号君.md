# 读者030 · 问号君
身份：普通后端，4年，爱好：播客
主读：第 3 章

## 五个问题
1. 【3.2|技术事实】"AOF 优先是因为它携带的信息严格多于单独的 RDB"——"严格多于"说得太满。运行时 `CONFIG SET appendonly no` 后 AOF 文件仍留在磁盘，之后再落一个更新的 RDB 并崩溃，重启时只要配置里 appendonly 还是 yes，Redis 会照样加载这份过期 AOF 而不是更新的 dump.rdb；everysec 下 fsync 停滞时，刚完成的 BGSAVE 落盘也可能新于 AOF 文件。"严格"只在"AOF 一直开启且 fsync 正常"的前提下成立，书里没交代这个前提。
2. 【3.2|结构导航】正文和图 3-3 都把关闭第三步画成 SAVE/NOSAVE 二选一（"落盘由用户显式指定并承担后果"），可我最关心的"裸 SIGTERM / 不带参数的 SHUTDOWN 到底存不存"——也就是 `systemctl stop redis` 的默认行为——在 3.2 没有答案，要翻到 3.4 容器段一句括号（"只要配了 save 点（出厂默认就配）且不走 NOSAVE……同步做一次全量 RDB 落盘"）才拼出来。默认路径恰恰是运维最高频的那条，不该缺席主流程图。
3. 【3.5|逻辑论证】"单机的'存不存盘'不构成问题（日志在 Leader 迁移后还能从其他副本恢复）"——对 RF=1 的 topic 不成立：唯一副本就在下线 Broker 上，Leader 无处可迁，这次"强制刷盘"就是数据最后的防线。我们测试环境一堆 RF=1 的 topic，这句话需要加"RF≥2 且 ISR 里有存活副本"的前提。
4. 【3.6|逻辑论证】启示五说"3.3 节 MySQL 关闭慢的排障……都依赖这些里程碑日志"，但 3.3 给出的排障工具是"SHOW PROCESSLIST 在关闭期的输出，对着这四类根因看"，跟里程碑日志对不上；且 `ready for connections` 是就绪日志，与"关不掉时定位卡点"是两回事。到底关不掉时看进程列表还是状态日志，两处说法需要对齐。
5. 【3.6|案例示例】导读说事故是"敲下 kill -9 想快速重启服务"，3.6 复述成"没等 AOF 刷完就杀了进程"——kill -9 之下 AOF 根本不会开始刷，两次讲述咬合不上。而且"丢了十几条订单数据"：订单主数据是放 Redis 了吗？若只是缓存，丢缓存不丢订单；若真以 Redis 为主存，这个架构前提值得一句交代，否则这个贯穿全章的案例说服力打折。

## 五个建议
1. 【3.4|图示】容器化 Redis 那段——BGSAVE/COW 耗时、grace period 倒计时、SIGKILL 截止线在同一条时间轴上赛跑——是全章最难在脑中成像的部分，却只有文字。建议加一张"K8s 终止时间轴"图：倒计时开始 → preStop(BGSAVE) → fork/保存 → SHUTDOWN NOSAVE → 距 SIGKILL 的余量，把这场景观化。
2. 【3.4|案例示例】"选举期间分区短暂不可用，客户端会看到抖动"——建议补一次客户端视角的具体样态：producer 端会看到什么（NOT_LEADER_FOR_PARTITION？TimeoutException？）、consumer 会不会触发 rebalance、retries/delivery.timeout.ms 能否把抖动兜成无感。第一次认真想优雅停机的读者，最想在自己应用的日志里认出这个"抖动"长什么样。
3. 【3.3|深度广度】讲崩溃恢复耗时那句之后，建议补一句 redo log 容量与恢复窗口的关系：调大 innodb_redo_log_capacity（旧版 innodb_log_file_size）的人大多冲着写入吞吐去，很少意识到 checkpoint 可以因此更旧、崩溃恢复窗口随之变长——这正是 3.1"速度 vs 确定性"矛盾落在具体参数上的实例，一句话就够。
4. 【序言|案例示例】丢订单事故在导读和 3.6 各讲一次，是全章的情感锚点，但缺架构上下文：订单在 Redis 里是主存还是缓存、十几条是怎么发现的、事后怎么补救的。补两三句让案例立住，还能顺带示范"什么数据不该只放 Redis"。
5. 【3.4|结构导航】前向引用密度偏高：3.3"第 4 章详述"、3.4"第 7 章有一分钟直觉讲解""完整编年史见第 7 章 7.4.4""第 5 章会再次回到这个设计"，3.7 又接连指向第 4、5 章——读到第 3 章时这些目的地都还没建立概念。建议每节只保留最必要的一处（如 KRaft→第 7 章），其余删去或集中挪到小结。
