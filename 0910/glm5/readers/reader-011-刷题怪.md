# 读者011 · 刷题怪
身份：后端工程师，2年，爱好：Switch
主读：第 2 章

## 五个问题
1. 【2.2.1|技术事实】"跳表的缓存局部性确实不如红黑树"这句我不服：红黑树每个节点同样是独立分配、查找同样是一路指针乱跳，两者的访存模式没有本质差别；通常说局部性差是跳表跟 B+ 树（整页连续）或数组比。书把"局部性差"安到红黑树头上又没给依据——我刷过 leetcode 1206 手写过跳表，实在想不出红黑树局部性更好的理由。
2. 【2.3.2|案例示例】这一节 int<1>/int<2>、0xFB/0xFC/0xFD/0xFE 分档、LengthEncodedString 全是干规则，正文里没有一个像 2.3.1 节 `*3\r\n$3\r\nSET\r\n...` 那样能逐字节对照的完整报文（图 2-8 里 MySQL 那格是预编译两步流程，不是字节流），我读完只记住 0xFB 是 NULL，其他分档关系合上书就忘。
3. 【2.5 启示四|读不懂】"我自己设计新协议，会先从第二个版本开始——第一个版本很少有人能把边界想全"读了好几遍没懂：第一个版本还没发布，怎么"从第二个版本开始"？是先设计出 v2 再回头定 v1，还是 v1 发出去就当作废？它和前一句"留出能力标志或版本字段"的关系也没接上。
4. 【2.2.2|深度广度】自适应哈希这段刚说它是自动优化、"数据结构会随访问模式自动调整"，紧接着一句"生产上仍常常直接关掉"——为什么自动的东西在生产常被关、什么负载该关、关了损失什么，只有"竞争集中在保护锁上"半句带过。像我这种没碰过 InnoDB 调优的读者，这个疑问到章末都没闭合。
5. 【2.2.3 与 2.3.3|逻辑论证】2.2.3 说压缩类型不一致时 Broker 要逐批解压重压、老客户端拉取触发降级转换；2.3.3 又说零拷贝让一批消息"不进用户态，直接从页缓存送到网卡"。两处没互相点破：零拷贝是不是只有压缩一致且无需降级转换时才成立？读到 2.3.3 我没法判断自己项目里客户端版本混杂的集群到底吃不吃得到零拷贝。

## 五个建议
1. 【2.3.2|案例示例】给 MySQL 协议补一个逐字节的完整报文示例，比如一条文本结果集行或一次 COM_STMT_PREPARE 的返回，把 0xFB/0xFC 分档直接标在字节上。2.3.1 节 RESP 那串 33 字节的 `SET key value` 示例效果就极好，MySQL 这节该同等对待——我习惯先看代码块再看文字，这一章到现在没见到一个真正的代码块。
2. 【2.2.1|深度广度】导读把"查名次一条 ZREVRANK"立为全章卖点，但正文里 span 出名次只有"span 逐层累加就是名次"一句话。建议用一个 3 层小跳表演示一遍 ZREVRANK 的回溯路径和 span 相加过程——这是跳表最巧的设计，一笔带过太可惜。
3. 【2.2.2|案例示例】"一个 16KB 页就能容纳几百个键，两层内部节点、每叶几十行，千万行的表只有三层"建议把算式摆出来：16KB ÷ (8B 键 + 6B 页指针) ≈ 1000+ 扇出，1000 × 1000 × 每叶几十行 > 千万。可复算的推导比背诵结论有说服力，我这种读者真会拿计算器按一遍。
4. 【2.5|表达可读】启示四的"会先从第二个版本开始"建议改写成可执行的做法，例如"发布 v1 前，先把假想的 v2 改动列出来，确认 v1 预留的版本字段或能力标志装得下，再冻结 v1"。现在这句金句式的写法把意思藏住了。
5. 【导读/全章|结构导航】导读的排行榜案例非常好，建议章末加一个 10 分钟能复现的"动手验证"小节：redis-cli 里 ZADD/ZREVRANK 与 MySQL `ORDER BY score LIMIT` + EXPLAIN 各跑一遍，让读者亲手看到改分和查名次两条路径的差别。技术书里能上手的实验比十页论述记得牢。
