# 读者006 · 老许
身份：C++ 服务器开发，15年，爱好：围棋
主读：第 1 章（另通读序言、细看了图 1-1/1-2/1-3 的 SVG 源文件）

## 五个问题
1. 【1.3.3|逻辑论证】末尾把三家统一成"一条共同主线：日志为故障恢复提供依据"，对 Kafka 是因果倒置——上一段刚说"Kafka 把数据本身存成日志"，日志是正本，故障恢复（截断尾部、重建索引）只是正本的伴生问题；Redis AOF、MySQL redo 才真是为恢复而设的旁路日志。写 WAL 长大的人看这个归纳，像是为了排比硬凑的。
2. 【表1-1|技术事实】"关键取舍/可舍弃"给 MySQL 填"写性能"，同一张表的"性能取向"行又写"延迟让位于一致性"，两行自己打架，图 1-1 里也标着"舍弃：写入性能"。延迟和写吞吐是两码事：InnoDB 靠 redo 顺序写加组提交，批量写吞吐并不弱，贵的是每事务 fsync 的确认延迟——正文 1.2.2 自己说的也是提交延迟，怎么到表里就成了"舍弃写性能"。
3. 【图1-2|图示】雷达图评分表"数据容量"给 MySQL 打 5 分、Kafka 4 分。正文 1.2.2 刚说完 MySQL"单机扩展有上限……横向分库分表则代价不菲"，而 Kafka 加盘加分区就能把日志容量线性堆到 PB 级。图注虽声明"主观量级判断"，但主观示意不该跟自家正文顶牛。
4. 【1.2.2|表达可读】"可通过 fsync 等机制把缓冲的写强制刷到磁盘"——这个"可"字读起来像给读者的操作建议，实际是在描述既有行为；"等机制"也不知道指什么（fdatasync？O_DSYNC？组提交？）。在 Linux 上跟 fsync 打了十几年交道的人看这句很别扭：明明写明"innodb_flush_log_at_trx_commit=1 时每次提交 fsync 一次"就完了，绕开参数名反而内行看着含糊、外行看不懂归属。
5. 【1.2.2|技术事实】"1995 年起源于瑞典 MySQL AB"（表 1-1"出身"行同写"1995，MySQL AB"）——MySQL AB 公司 2001 年才成立，1995 年发布 MySQL 的实体是 Michael Widenius 所在的瑞典公司 TCX DataKonsult。史实小错，但 1.2.2 明明拿"演化史"当主线讲，起点年代最好考证准。

## 五个建议
1. 【1.2.1|案例示例】1.1.1、1.2.1、表 1-1 三处把"分布式锁"列为 Redis 典型场景，却没有一个字的边界警示。主从切换瞬间可能两个客户端同时持锁、Redlock 那场著名论战，是"拿可靠性换延迟"最鲜活的取舍案例——我在生产上真见过因此双扣库存。一本通篇讲取舍的书，正该在这儿补两三句。
2. 【1.4.3|版本时效】版本状态提示点了 MySQL 支持周期、Kafka 去 ZooKeeper，独独漏了 Redis 2024 年许可证风波与 Valkey 分叉。2026 年做选型的读者几乎必然要回答"Redis 还是 Valkey"（主流云厂商已大量转投），基线一节补一句，免得读者拿书里的"Redis Open Source"对不上自家运维目录里的 valkey-server。
3. 【1.2.2|结构导航】"先认识三个软件"的概览节深潜太猛：Read View 可见性判断、RR/RC 建视图时机、redo/undo/binlog 三日志分工、两阶段提交，四层信息量挤在一节。这些是第 4/8/9 章的正餐，第 1 章留机制名字加一句话定位即可，第一次读的人不该在"认识软件"的门口就被呛一嘴。
4. 【1.2.1|深度广度】"网络层采用事件驱动模型"一句带过太可惜。ae 事件循环就是 epoll/kqueue 的封装、单线程 Reactor，这恰是"为什么单线程够用"的底层支撑——命令极短、多路复用让单核也撑得住上万连接。1.4.1 已把 I/O 多路复用列为前置知识，这里点破一层，比"事件驱动模型"这种谁都能说的泛称更配"架构视角"的自我定位。
5. 【本章导读|结构导航】导读用"面试考不倒"开场可以理解，但全书方法论最锋利的展示——1.3.3 那三层追问（先刷日志还是先刷页、落盘粒度多细、记逻辑还是记物理）——埋在章中。建议导读末尾加一句预告把三问亮在门口：读者在书店翻书试读时，最先看到的应该是这种真家伙，而不是又一个面试故事。
