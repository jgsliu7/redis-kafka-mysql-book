# 读者039 · 内存紧张
身份：Android 开发，8年，爱好：徒步
主读：第 4 章

## 五个问题
1. 【4.2|技术事实】近似 LRU 的动机只算了 CPU 账（"每次访问都要动链表指针……CPU 开销不可忽视"，图 4-2 也写"维护教科书双向链表代价大"），但 Redis 官方 LRU 文档说明弃精确 LRU 的首要动机是内存：每个对象要多 3 个指针约 24 字节，亿级键就是 GB 级开销。我平时每个对象 16 字节的对象头都要算，24B/键这笔账远比链表指针操作的 CPU 开销扎眼；何况本节开头自己说"Redis 的一切取舍围绕内存前提"，这里偏偏不算内存账。
2. 【4.6|逻辑论证】启示二把"Redis 自己管理内存"归因于"内核 PageCache 的淘汰精度满足不了它"，这对 MySQL 成立、对 Redis 不成立：Redis 的主存本身就是进程内数据结构（跳表/哈希表），磁盘上只有序列化快照（4.2 明说"两条路径的产物都只是内存状态的备份"），根本不存在把缓存建到 PageCache 上的选项——不是精度不够，是无从借力。
3. 【4.1|逻辑论证】表 4-1 拿"磁盘顺序写吞吐"去比"单线程内存随机读（几百 MB/s）"，得出"顺序吞吐进入内存一个数量级以内"；但内存的顺序带宽是几十 GB/s（我做内存 profiling 时流式读 10GB/s+ 很平常），同口径下机械盘 ~150MB/s 差着两个数量级。这个跨口径参照（4.4 也自认"跨口径"）没解释为什么这样选基准，读者会高估顺序盘、也高估"顺序 I/O 接近内存"的定性结论。
4. 【4.4|结构导航】acks 三档在第 4 章从头到尾没有一句语义解释，就要读者接受它"不能与 appendfsync 等同"（"完整语义见第 7 章……见第 9 章 acks 参数一节"）；4.5 表 4-3 又把"生产者 acks"直接列进"持久化机制"一行——不知道 acks 是什么就没法做这行对比，且表格画法恰好在诱导正文反对的类比；4.6 还说"4.4 节已把 acks 三档和另外两家的刷盘参数对照过一次"，翻回 4.4 只有免责声明，没有对照。
5. 【4.2|版本时效】混合持久化一段写"`aof-use-rdb-preamble` 在 5.x–6.x 中默认即为 yes"，恰好停在 6.x；而前文刚讲完 7.0 多部分 AOF（appendonlydir/manifest）。那 7.x/8.x 下这个参数还存在吗、base 文件还能配成纯 AOF 格式吗？用现役版本的读者到这里对不上号。

## 五个建议
1. 【4.2|深度广度】补一笔 Redis 的内存峰值预算：正文只算了 fork 的时间代价（阻塞数百毫秒）和"写密集时内核要复制大量页"，没算空间账——COW 写密集期间实例 RSS 可逼近 2 倍，大实例开 RDB/AOF 重写要按峰值预留内存，再加上碎片率与 THP 放大（4.1 关键数字提了 THP 影响 fork 时长，没提它对 COW 内存量的放大）。我们做 App 内存预算看的是 high-water mark 不是均值，缺了这段读者回答不了"48GB 机器到底能放多大的 Redis"。
2. 【4.4|案例示例】把 4.1 关键数字框里的 vm.dirty_background_ratio=10% / vm.dirty_ratio=20% 落成 Kafka 的可操作调参建议：什么症状该动它（写延迟尖峰）、往哪个方向调（社区实践常调小 background ratio 换平滑刷盘）、配合什么指标观察（脏页占比、刷盘吞吐）。我在移动端调 swappiness/zram 的经验是：内核参数不给"何时动它"的判据就只是知识点，而 4.5 刚说完"Kafka 运维重心转到调 OS 参数"，却一条路径都没给。
3. 【4.6|案例示例】给启示一加一个客户端侧对照：Android 的 LruCache/Glide 用 LinkedHashMap 精确 LRU，因为键只有千到万级、指针开销可忽略；Redis 键在亿级才被迫近似采样。"键的数量级决定缓存实现选型"正是"先问访问模式再选范式"的绝佳注脚，也能让客户端/嵌入式这类跨界读者对号入座——现在全书启示都落在服务端。
4. 【4.4|结构导航】在第 4 章就地给 acks 一句话定义（all=等 ISR 全部副本确认、1=只等 Leader、0=不等），再做"不能与刷盘档位等同"的声明，把"见第 7/9 章"降级为细节指引；同时修正 4.6"4.4 已对照过一次"的失实回指，并考虑把表 4-3"持久化机制"行拆成"本地刷盘"与"复制保证"两行，与 4.6 自己"控制的环节不同"的论断对齐。
5. 【4.1|表达可读】表 4-1 补一行"内存顺序带宽（单线程 ~10GB/s 量级）"或加表注说明为何拿"单线程内存随机读"当磁盘顺序吞吐的参照，让读者自己看到两种口径的差距；否则"顺序 I/O 进入内存一个数量级以内"的结论建立在一个未说明的口径选择上，较真的读者会翻回去质疑。
