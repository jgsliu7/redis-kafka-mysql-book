# 读者049 · 蜗牛
身份：Java 后端(转架构中)，8年，爱好：纸质书
主读：第 5 章

## 五个问题
1. 【5.2.2|技术事实】「代价是表项的字段（命令标志位）一旦定下就很难改。加一个新标志位意味着要改遍所有命令的声明」——这句我不认同。命令标志是按位/集合式的，新增一个 flag 只需要在用到它的命令上声明，其余命令默认不设、完全不用动；如果加一个标志位真要「改遍所有命令」，那前一段夸的「把命令做成数据、加一行就能加命令」的可扩展性就自相矛盾了。
2. 【5.2.1|逻辑论证】「这一句话也解释了为什么 7.x 默认仍然关闭多线程 I/O」——因果对不上。前一句说的是内存模型要求命令执行必须单线程，但 I/O 线程恰恰不碰数据结构、只做 read/write 和大块 buffer 拷贝；多线程 I/O 默认关闭的更直接原因是多数负载下收益不明显、默认配置保守，拿「逻辑层不能放开并发」来解释「I/O 多线程默认关」是错位的。
3. 【5.3.1|技术事实】「线程池……切换开销低但慢查询会队头阻塞（一条慢查询拖住队列里后面的所有请求）」说得太绝对。我们生产上用 Percona 线程池，它有 stall 检测，跑久了的语句会被移出线程池单独执行；MariaDB 也用 transaction staging 分组来缓解队头阻塞。把「队头阻塞」当成线程池模型的固有缺陷，与实际实现不符。
4. 【5.4.1|结构导航】同一套 Kafka 网络层，第 3 章图 3-5 数作 Acceptor/Processor/Handler 三级，本章又数四级，且正文刚强调「RequestChannel 不是线程，而是共享的请求队列」——一个队列被计入标题就叫「Reactor 多线程模型」的层级里，口径是混的。我读到 5.5 横向对比时得自己记两套数法，不知道该按哪套对账。
5. 【5.4.4|逻辑论证】协调层只给 Kafka 单列成第四段，而正文自己承认「Redis Cluster 的槽路由、MySQL 组复制（MGR）的多数派投票也属于类似的关注点」，但它们的协调职责在三段式里归到哪一层始终没交代（图 5-7 里 Kafka 也只画了三段，协调层在图里消失了）。「什么算一层」在三个软件上用了两套标准——而这个判据恰恰是我这种转架构的读者最想从这章学走的。

## 五个建议
1. 【5.5 表 5-1|图示】表 5-1「层间通信机制」一行：MySQL 只列了「THD 对象 + handler 虚函数」两种形态，而 5.3.4 明明讲了三种（还有引擎到操作系统的 pread/pwrite 与 Native AIO），Kafka 一格却三种齐全。同一张表口径不齐，建议补齐 MySQL 那格，或加表注说明本行只列「层与层之间」的形态、引擎到 OS 不算。
2. 【5.5 表 5-1|深度广度】建议增加一行「会话上下文对象」：Redis 的 client 结构体 / MySQL 的 THD / Kafka 的 RequestChannel.Request。5.2.2 和 5.3.1 用了两大段加两张图铺垫「贯穿对象」这个三者同构的手法（正文还明说「与 Redis 的 client 结构体是同一手法」），到横向对比却断了线，加一行成本极低、收口价值很大。
3. 【5.6 启示四|案例示例】「镜像分层」反模式直接点名了 Service/Manager/Dao/Mapper——我们这种被阿里规范约束多年的团队天天在写。识别反模式大家都会，缺的是删层的落地路径：建议补一个小案例讲 Manager 层并回 Service 时事务边界放哪、调用方怎么迁移、分几步上线。导读里「改三行 Controller 首页挂掉」那个第一人称案例非常好，启示四值得同等待遇。
4. 【5.2.1|结构导航】5.2.1 用一整段复述了 RESP 的五种前缀字符（+ - : $ *），这属于第 2 章 2.3「通信协议」的领地（本章还后向引用过 2.2.1 的连锁更新，证明第 2 章讲得够细）。建议压缩成两句带过，省出的篇幅给 6.0 的 RESP3 一句话定位——本章把 6.0 的多线程 I/O 讲透了，同一版本的协议侧变化却只字未提，读者会问。
5. 【图 5-1|图示】图 5-1 的⑤框标题是「慢查询 / MONITOR 钩子」，副文案却是「耗时统计、复制传播（写命令）」——复制传播（propagate 到 AOF/副本）是命令执行里的独立路径，跟 MONITOR 无关，且⑥框又出现「AOF/RDB」，同一件事散在两框。另外钩子框排在存储框（⑥）之前，容易读成「先跑钩子再存取」，实际是 proc 执行时同步做存取、事后跑钩子，建议调整框序或合并。
