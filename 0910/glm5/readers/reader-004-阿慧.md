# 读者004 · 阿慧
身份：技术公众号主笔，6年，爱好：烘焙
主读：第 1 章

## 五个问题

1. 【1.1.3|技术事实】说 Redis 的代价是「复杂聚合要靠客户端多次网络往返拼出来」（1.2.1 的「要做就得把数据拉回应用层处理」同义）。我写 Redis 科普时专门写过这个题：MULTI/EXEC、Lua 脚本、7.0 的 Function 都能把多步逻辑打包成一次网络往返在服务端完成，「多次往返」这个机制描述不成立。真正的短板是它没有声明式查询和跨键关联，且服务端脚本会阻塞单线程——建议按这个口径改。

2. 【1.2.2|技术事实】「1995 年起源于瑞典 MySQL AB」（表 1-1 出身列同）。我写 MySQL 历史稿时查到：MySQL 1995 年发布时开发方是瑞典 TCX DataKonsult，MySQL AB 公司一般考据为 2001 年前后才正式创立，「1995 年 MySQL AB」是中文资料里常见的以讹传讹。两说并存，建议作者亲自核对一遍，这种年份是较真读者最爱挑的地方。

3. 【1.2.2|读不懂】MVCC 那一段不到 150 字塞进了 undo log、Read View、版本链，以及 REPEATABLE READ 与 READ COMMITTED 的视图生成时机差异。1.4.1 明说「至少实际用过三者之一」就能读本书，那我这种只重度用过 Redis 的读者，读到这段直接卡住——这是「先认识一下」的概览节，却在干第 9 章细读章的活。

4. 【1.3.3|结构导航】1.3.3 标题宣称「一个贯穿全书的例子」，讲的是「数据怎么不丢」；可 1.1.1 的电商订单例也被 1.2.1、1.2.3 两次回指（「1.1 节那个购物车与库存计数」「还是 1.1 节那笔订单」），同样是贯穿线。读完第 1 章我分不清哪条是主线，订单这个例子在第 2–9 章还会不会回来，1.5 小结只收了前者。

5. 【1.1.1|图示】图 1-1 第三行「电商下单链路」把 Redis→MySQL→Kafka 首尾相连，箭头标「读/写/发/消」：Redis→MySQL 那支「写」第一眼像「Redis 把数据写给 MySQL」，MySQL→Kafka 那支「发」像「MySQL 主动发事件」。真正执行者是被省略的订单服务，四个动词主语各不相同，首读很容易误解成存储间直通（那得是 Debezium CDC 的画法，而正文说的是应用广播）。我给自己的公众号画链路图从不敢省掉中间的「服务」框。

## 五个建议

1. 【1.1.1|案例示例】订单例现在只有一句话带过，却要承担 1.2.1、1.2.3 的两次回指。建议在 1.1.1 用三五句把它讲成具体小故事：一笔下单先读 Redis 校库存、MySQL 落单、Kafka 发事件，再各点一句三家分别挂掉会发生什么。案例驱动的读者会被这个故事钩住，后文每次回指才有落点，也能顺带回答「为什么三个都得用」。

2. 【1.1.3|深度广度】三段核心设计对比里，只有 Kafka 拿到了「3 台廉价机约 200 万写/秒」的数字锚点，Redis 的「低延迟」和 MySQL 的「宁可慢」全是定性词。建议三家各配一个带条件的量级数字（如 Redis 单实例 10 万级 QPS、MySQL 双 1 配置下单次提交毫秒级），并同样注明出处和前提。做过传播的都知道，读者对引言章的信任一半就建立在这种数字上。

3. 【1.4.4|结构导航】路径 B 让读者「先读第 1 章和第 10 章建立全局观」，但第 10 章开篇是「前九章核心启示复盘」——没读过 2–9 章的跳读者面对复盘基本是空转。建议在路径 B 里写明读法，比如「第 10 章先读 10.2/10.3 的规律与框架，复盘留到补完主题章再看」，别让读者按顺序硬啃 10.1。

4. 【1.4.3|版本时效】版本基线与现实的落差（Kafka 4.0 已 KRaft-only、MySQL 8.0 转 Sustaining）只集中在 1.4.3 一处说明，而本书主推的路径 B/C 恰恰是按章跳读、未必经过 1.4.3。建议在第 7、9 章这类受 ZooKeeper→KRaft 影响最大的章首加一行版本提示，跳到那里的读者才看得到。

5. 【序言|表达可读】序言倒数第三段已经用「我面试架构师和开发工程师时的判断依据」收尾，第 1 章导读又以「我面试过数百名候选人……很少人谈取舍」开场，连读时立意撞车、第二个钩子失效。建议第 1 章导读换一个切入点（比如直接抛三家各自的一次真实故障场景），面试故事只留在序言讲一次。
