# 读者033 · 键盘侠
身份：Redis 重度用户，4年，爱好：网文
主读：第 4 章

## 五个问题

1. 【4.2|技术事实】"教科书里的 LRU……每次访问都要动链表指针"把 Redis 弃用精确 LRU 的理由全押在 CPU 开销上，漏了更要命的内存账：哈希表加双向链表的方案每个键要多挂两个指针（16 字节），百万键就是几十 MB 纯管理开销。antirez 当年改近似 LRU 的第一动机就是省这份 per-key 内存，对按 MB 计费的 Redis 来说这比 CPU 更硬，只写一半归因读着不过瘾。

2. 【4.2|版本时效】"从全部键里随机采样 N 个（默认 5），从中淘汰最久未用的那一个"描述的是 2.x 的行为：3.0 起加了淘汰池（eviction pool，默认 16 槽），采样候选先并入池、再从池里挑最差，跨轮次积累让结果明显更接近真实 LRU。现在线上没有 2.x 了，照书里的单轮采样去理解 3.0+ 的实际行为，等于学了个旧版本，图 4-2 的"采样 + 比较最差者"也跟着旧了。

3. 【4.2|深度广度】整节讲"内存满了怎么办"，却没讲淘汰的计量单位是键、不是字节：近似 LRU/LFU 按键数采样，我们站把一整本书章节塞成的大 hash（几十万 field、上百 MB）和一个 100B 计数器被采中的概率一样，回收慢得像挤牙膏。表 4-3 把"淘汰风暴"列为 Redis 典型故障，机制解释却拖到 4.5 括号里补了半句，4.2 正文没铺。

4. 【4.2|逻辑论证】"`noeviction` 是内存满了直接报错、不淘汰，适合'数据不能丢'的场景"这个判断我不服：它挡住的只是"被静默淘汰"，代价是写命令直接返回 OOM 错误——客户端不做错误处理和重试，数据照样没写进去，不过是把丢法从服务端静默换成客户端可见报错，和真正的"不丢"（那是 AOF 那一节的事）之间还隔着业务代码一层。

5. 【4.4|表达可读】"acks 不能与 appendfsync、innodb_flush_log_at_trx_commit 的本地刷盘档位等同"这个论点，4.4 末尾原样说了一遍，4.6 启示三又几乎原话再展开一遍（"不能把这些档位按'每条都落盘'到'交给 OS'一一对应"），同一章内复读。第二遍读到时我直接跳段了，两处留一处就够。

## 五个建议

1. 【4.2|案例示例】fork 段"告警间隔正好等于 save 规则的触发周期就能确定根因"这个排查锚点写得真好，是我见过最实战的一句。建议照这个手法把表 4-3 里悬空的"OOM"也接上：写密集时 bgsave 的 COW 会让内存占用逼近两倍，maxmemory 配到物理内存七八成的实例一触发 save 就可能被 OOM killer 干掉——补个案例，再给"给 COW 留余量"的配置数字（如 maxmemory 不超过物理内存六成）。

2. 【4.2|深度广度】建议补一小段释放路径：淘汰或过期选中键之后，同步 free 一个大 Key 本身会阻塞主线程，4.0 的 UNLINK 和 lazyfree-lazy-eviction / lazyfree-lazy-expire 就是为此而生。这和近似 LRU 是同一块拼图——小节标题叫"内存淘汰的真实实现"，释放恰恰比采样更容易踩坑，现在却一个字没有。

3. 【4.2|图示】图 4-2 副标题说要看清"LFU 计数器衰减的内存布局"，建议真画到字段级：RedisObject 里那个 24bit lru 字段的复用——LRU 模式整段存秒级时钟（约 194 天回绕），LFU 模式高 16 位存分钟级衰减时钟、低 8 位存对数计数器。正文只说"只用 8 位"，不画出这个字段，读者根本不知道这 8 位是从哪抠出来的、衰减时钟又存在哪。

4. 【4.2|案例示例】八种策略那段讲了 volatile-* 组是给"缓存+持久存储混用"场景的，建议补上它最经典的翻车点：全库一个带 TTL 的键都没有时，内存打满后 volatile-lru 找不到任何淘汰对象，行为直接退化成 noeviction 写报错——明明配了淘汰策略照样 OOM，半夜容量告警时排查半小时起步，这是混合场景下最容易挨的一刀。

5. 【4.5|术语使用】表 4-3"持久化机制"行 Kafka 列把"生产者 acks"和 OS 异步刷盘并排写在一格，和 4.4、4.6 反复强调的"acks 是复制确认、不等同本地刷盘"口径打架。建议这格拆成两层写（本地：OS 异步刷盘；兜底：acks + 副本），别让表格把正文刚刚划清的界限又糊回去。
