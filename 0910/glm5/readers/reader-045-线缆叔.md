# 读者045 · 线缆叔
身份：老网工，22年，爱好：露营
主读：第 5 章

## 五个问题

1. 【5.3.1|技术事实】「线程池：固定线程服务所有连接……慢查询会队头阻塞（一条慢查询拖住队列里后面的所有请求）」这个说法过头了。企业版/Percona/MariaDB 的线程池都是分组模型：连接被分进若干线程组（thread group），每组一个 worker 配高低优先级两个队列，还有 stall 检测会在卡住时临时加开 worker，慢查询只堵自己那个组，不是「所有请求」。队头阻塞的波及范围恰恰是线程池设计的核心，这里简化到失真。

2. 【5.2.1|逻辑论证】「整个内存模型都建立在『单线程修改』的前提上……这一句话也解释了为什么 7.x 默认仍然关闭多线程 I/O」——因果链接不上。多线程 I/O 本来就只动 read/write 和 buffer 拷贝，不碰命令执行，并不违反单线程前提；它默认关闭更多是因为多数负载（低 QPS、小包）下线程协调开销盖过收益。这段我读了两遍，还是没明白到底在解释什么。

3. 【5.2.2 与表 5-1|逻辑论证】5.2.2 说 Modules API 可以往命令表里注册新命令，表 5-1 又断言 Redis「未提供可插拔引擎接口」，两处放一起读着别扭。模块其实还能注册自定义数据类型（module type，RedisJSON、RediSearch 挂进来的就是自己的存储格式），这已经算半个可插拔存储了，书里至少该补一句边界划在哪。

4. 【5.2.2 图 5-1|图示】图 5-1 把「⑥ robj 存取 + AOF/RDB」画在「⑤ 慢查询/MONITOR 钩子」下游，纵向读下来就成了每条命令先执行、再跑钩子、最后才碰存储层——顺序不对：robj 读写发生在④执行内部，AOF 与复制传播紧跟执行做，RDB 更是根本不在每命令流水线上（fork 出去后台做的）。刚建立三层印象的读者会被这张图带偏。

5. 【5.5|结构导航】5.4.4 专门立了「协调层」、明说 Kafka 是四段，可图 5-7 的 Kafka 列只有 SocketServer/KafkaApis/Log 三个框，协调层在统一视角图上消失了；Redis Cluster 槽路由、MGR 投票也只是 5.4.4 一句带过。要么把「协调」升格为第四段统一维度，要么在图上明示它只对分布式形态成立——现在三段对四段，对比口径不对称。

## 五个建议

1. 【5.1（或 5.6）|案例示例】整章讲分层，却从头到尾没提 OSI 七层/TCP-IP 四层——这可是「分层」这个题目的祖案例。OSI 的教科书七层输给务实的 TCP/IP 四层、会话/表示两层沦为空壳，正是启示一「不追求标准层数」和启示四「空洞透传」的现成历史判例；5.1 的「语义映射」跟我们网络人把真实协议往 OSI 上映射也是同一件事。补上这面镜子，本章启示的分量会重一个量级。

2. 【5.4.3|图示】零拷贝建议配一张路径图：一条横线分用户态/内核态，左边磁盘、右边网卡，「传统四次拷贝」与「sendfile 两次」两条路径并排画，并标出「省两次拷贝」依赖网卡 scatter-gather DMA 这个前提。纯文字数拷贝次数，我这种干了二十二年网络的人都要数两遍，普通读者更容易晕。

3. 【5.4.1|深度广度】背压这段建议补三个数和一个代价：队列的界是 queued.max.requests（默认 500），新版还把控制类请求分到独立队列；更要紧的是 Processor 被阻塞时它名下所有连接的读写一起停摆——这与 5.3.1 批 MySQL 线程池队头阻塞是同一笔账，Kafka 这边只唱了「天然背压」的赞歌，没把账单亮出来。

4. 【5.2.1|技术事实】「超限就强制关闭连接」简化过头：client-output-buffer-limit 是硬限立即断、软限持续超过 N 秒才断的两级机制；且普通客户端默认 0 0 0 根本不设限，真正被它管住的是副本连接（默认 256mb/64mb/60）和订阅者（32mb/8mb/60）。拿现在这句当单开关用的读者，上生产会配错。

5. 【表 5-1|结构导航】建议表 5-1 加一行「贯穿会话的上下文对象」：Redis 的 client、MySQL 的 THD、Kafka 的 Request 对象。5.2.2 和 5.3.1 都点了「一个贯穿对象替代层层传参」的同构手法（正文明确说 client 与 THD 是同一思路），这是本章最漂亮的一条共性线，横向对比表里反而看不见它。
