# 读者066 · NewSQL
身份：TiDB 用户，5年，爱好：拼高达
主读：第 7 章

## 五个问题
1. 【7.3.4|深度广度】「这是 MySQL 生态的分工……模块化、可组合，胜过大一统」这个判词没有对照组。我是从 MySQL 迁到 TiDB 的，另一条路线——Range 动态分裂加每个 Region 一个 Raft 组——把分片和副本容错在同一内核里原生解决，生产上跑了多年；书里点名 ShardingSphere/Vitess/MyCAT，却只字不提 NewSQL 已把这两件事合起来，「胜过」从何比起？
2. 【7.1|逻辑论证】「哈希分片分布均匀，但加节点就要重分片……范围分片支持范围查询，但容易产生热点」这组二分我不服：动态 Range 分裂（TiKV 的 Region、HBase）加中心调度，加节点只是把一部分 Region 调度走，不做全空间重分布——书里给 Redis 槽的评价（加节点只迁部分槽）对它同样成立，热点也能靠分裂加打散缓解。二分法把「范围=易热点」说成了宿命。
3. 【7.4.1|读不懂】「Kafka 2.4 经 KIP-480 引入默认粘性分区；在本章的 3.9 基线中，默认逻辑向一个分区累计发送至少 batch.size 字节后再切换」——「本章的 3.9 基线」是什么？全章没宣布过版本基线，我第一反应是找 3.9 节，翻了一圈没有；另外「累计满 batch.size 再切换」是后来 KIP-794（3.3 起）才改成的行为，与 2.4 的原始行为压在同一句里，看不出差别从哪个版本开始。
4. 【7.3.2|术语使用】「默认等待点下，主节点将 binlog 刷盘后，至少等一个从节点确认，再提交到存储引擎」——既然写了「默认等待点」，就说明还有别的等待点，但全节不给名字（AFTER_SYNC / AFTER_COMMIT），也不说两者在故障切换时的丢失语义差别、为什么默认前者。当年我在 MySQL 上选半同步就栽在等待点上，这里悬空一个「默认」，读者没法比较。
5. 【7.5 表 7-1|逻辑论证】「横向扩展能力」一行，Redis 格带限定语「效果受负载分布影响」，MySQL 格写明「扩容量靠上层分片」，唯独 Kafka 格「分区与 Broker 提供吞吐和容量扩展空间」没有任何但书——可 7.4.1 自己说了扩分区后同一 key 新旧消息分家、按键顺序失效，「扩分区是一次语义迁移」。同一张对比表里三家的限定标准不一致，Kafka 这格显得偏乐观。

## 五个建议
1. 【7.3.4|深度广度】加一段 NewSQL 旁注作对照：TiDB/CockroachDB 用 Range 动态分裂加每 Region 独立 Raft 组，把书里拆成「MGR 副本组 + 中间件分片」的两件事合在一个系统里；顺带点出中间件路线的隐性代价（跨分片事务、在线扩容要迁数据），「模块化 vs 大一统」这个结论才有得比。
2. 【本章导读|案例示例】开头的库存超卖事故讲到「吃过这个亏，我才真正理解 CAP」就断了，缺善后：事后是加了 WAIT / min-replicas、改了部署拓扑，还是把库存挪去了强一致存储？补一两句，读者才能对照自己的预案——我自己就是靠把库存挪出 Redis Cluster 才睡安稳的。
3. 【7.6 启示三|深度广度】「元数据管理决定集群的上限」目前只给了 Gossip 与共识日志两端，建议补第三条生产主流路线——集中式调度服务（TiDB 的 PD、HBase 的 Master）：元数据集中存放、数据分片各自复制调度，正好给「选错方案，整个集群的上限就卡在这一层」多一个注脚。
4. 【7.4.1|表达可读】把「本章的 3.9 基线」改成显式说法（如「本书以 Kafka 3.9 为版本基线」），并补半句「自 3.3 的 KIP-794 起改为累计满 batch.size 再切换分区」，免得读者把切换条件记成 2.4 就有的行为。
5. 【图 7-5|图示】三条故障转移决策路径只画了决策链，建议每列补典型时间量级（Redis 要等 cluster-node-timeout 默认 15 秒才判 FAIL 再选举；MGR 的成员失效检测加 View Change；Kafka 的检测加 Controller 选举加元数据传播）——运维最关心的「不可用窗口多长」恰是三家差异最大的维度，现在图和正文都没给量级。
