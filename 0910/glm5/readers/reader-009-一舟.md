# 读者009 · 一舟
身份：独立开发者，7年，爱好：帆船
主读：第 1 章

## 五个问题
1. 【1.2.1/1.4.3|版本时效】Redis 这两年最大的变局——2024 年 license 改 RSALv2/SSPL 引发 Valkey 分叉、2025 年 Redis 8 回归 AGPL——全书只字未提。我自托管 Redis，选哪个发行版（7.x、8 还是 Valkey）是真实做过的决策，而 1.4.3 的版本状态提示里 MySQL、Kafka 的大事都点了，Redis 只一句「7.2、7.4 分支仍列在官方支持范围内」，恰好绕过了最需要选型判断的部分。
2. 【1.4.3|版本时效】书自己写明 MySQL 8.0 已于 2026 年 4 月转入 Sustaining Support，却仍以 8.0.x 为全书基线且不给理由。我正在把自己那几台 MySQL 升 8.4 LTS，8.4 起默认值有实际变化（redo log 改按 innodb_redo_log_capacity 配置、一批参数废弃），照 8.0 基线讲的默认值到 8.4 上对不上，拿去实操会踩坑。
3. 【1.2.1/1.1.3|技术事实】「复杂聚合要靠客户端多次网络往返拼出来」「要做就得把数据拉回应用层处理」说得太死：我用 Redis + Lua（EVAL）做过原子扣库存，读-改-写在服务端一次往返完成，Redis 7 的 Function 更是官方特性——1.4.3 自己也提了「7.x 带来 Function」，前后口径打架。真正的限制是聚合仍受单线程执行约束，跟「必须拉回应用层」是两回事。
4. 【1.4.4|结构导航】路径 B 让我「先读第 1 章和第 10 章建立全局观」，但第 10 章的标题就是「前九章核心启示复盘」。我这种只挑用得上的章节跳读的人恰恰要走这条路：没读过 2–9 章直接读复盘章，会不会满篇回指悬空？书里没交代第 10 章对未读前文的人是否自足。
5. 【1.3.1 表 1-2|读不懂】表 1-2 的 Kafka 行「设 acks=all、min.insync.replicas=2（ISR 至少有 2 个副本，并等待当前 ISR 全部确认）」，一个括号把两个参数的语义揉在一起。我 Kafka 只碰过 acks，读完分不清哪个参数管「等谁确认」、哪个管「ISR 不够就拒绝写入」。

## 五个建议
1. 【1.2.2|深度广度】1.2 三节深度失衡：MySQL 一节把 Read View 生成时机、版本链、两阶段提交全讲了，像第 4/8 章的预演；Redis 一节六段就完，「单线程为什么反而快」只有一句带过。建议概览节拉平深度——MySQL 的 MVCC 细节留给正文章节，给 Redis 补两三句机制（无锁竞争、无上下文切换、内存操作快于网络往返）。
2. 【1.4.3|版本时效】建议在版本基线处加一张「2024–2026 三家大事与选型影响」小表：Redis license 变更与 Valkey 分叉、Kafka 4.0 全面 KRaft、MySQL LTS 化节奏，各配一句「对自托管者意味着什么」。版本变局本身就是一次活的取舍案例，跟全书主题正搭，比一句「以官方文档为准」有用得多。
3. 【1.1.1|案例示例】贯穿案例是电商订单系统（购物车/库存/履约链路），但序言和 1.4.1 的目标读者全是「公司里的人」——独立开发者和小团队没被覆盖，而这本书讲的恰是我们最疼的问题：没人商量，选型全靠自己拍板。建议在 1.1 或 10.4 补一个轻量案例（一人 SaaS：Redis 会话+限流、MySQL 主数据、要不要上 Kafka 的判断）。
4. 【表 1-1 与图 1-1|逻辑论证】表 1-1 和图 1-1 都写 MySQL「舍弃：写性能」，与正文 1.1.3 的「写放大、事务开销和调优门槛」口径不一致，且容易读成「MySQL 写入弱」——开了 group commit、innodb_flush_log_at_trx_commit=2 时写吞吐并不低，舍的其实是强一致刷盘配置下的提交延迟。建议统一成「强一致配置下的提交延迟与写放大」。
5. 【图 1-2|图示】雷达图下方三张解读卡片（「Redis：得分集中在低延迟」）基本在复读图例，信息量为零。建议每张卡片换一行量级锚点：低延迟轴配「Redis 亚毫秒 / MySQL 毫秒级 / Kafka 毫秒到百毫秒（批量）」，数据容量轴配「Redis 受内存约束 / MySQL 单机 TB 级」——读者要的是量级手感，不是形状。
