# 读者068 · 穷CTO
身份：创业公司 CTO，13年，爱好：遛狗
主读：第 7 章

## 五个问题

1. 【7.4.1|读不懂】"在本章的 3.9 基线中"第一眼看成"3.9 节"（本章只有 7.x 小节）；翻回第 1 章 1.4.3，版本基线写的是"Kafka 3.x（分层存储相关讨论以 3.9+ 为准）"，并没说第 7 章也以 3.9 为准。本章行为描述到底基于 3.9 还是 3.x？两处口径对不上，我只能靠猜。

2. 【7.2.2|深度广度】正文说 quorum"不必是多数派"就停了，配错的后果没讲：我们 5 个哨兵、quorum 配 2，两台哨兵与主之间网络抖一下就凑成 ODOWN 触发切换，而 leader 选举的多数派投票并不复核主是不是真挂。"配小了误切换、配大了判不了"这个风险边界恰恰是小团队最容易踩的一半，书里只给了定义。

3. 【7.3.2|深度广度】半同步只说"默认等待点下，主节点将 binlog 刷盘后……再提交到存储引擎"，通篇没提还有 AFTER_SYNC / AFTER_COMMIT 两档 wait point。5.7 把默认改为 AFTER_SYNC 就是为了修"主库崩溃切换后，已在主库被读到的事务在新主上不存在"的幻读——半同步最核心的一档取舍缺位，"默认等待点"这个词让读者无从知道它是可选项。

4. 【7.5 图7-5|图示】7.4.4 刚讲清"3.3 起 KRaft 对新集群生产可用、4.0 彻底移除 ZK"，图 7-5 Kafka 列第一步却写"（ZK session 失效 / KRaft 心跳超时）"并列。这张对比图画的是哪套模式的流程？按 1.4.3 的 Kafka 3.x 基线，新读者该把哪条当默认路径？图与正文的版本口径没对齐。

5. 【导读|逻辑论证】库存事故归因"一次网络分区触发了主从切换"太干净。大促高压下我复盘过的"疑似分区"十有八九是主节点负载过高导致 gossip 心跳超时被误判（cluster-node-timeout 默认 15 秒在高负载下并不宽裕），与真分区对策完全不同：误判要调超时和资源隔离，真分区只能做丢写预案。案例不交代当时的超时配置与复盘证据，读者学到"分区会丢写"，学不到"怎么区分"。

## 五个建议

1. 【7.2.3|案例示例】补一张"最小拓扑成本账"小表：方案（主从+Sentinel / Cluster / MGR）× 最少机器数 × 丢写风险 × 扩容路径。哨兵是轻量进程可和从库混部，1 主 1 从 + 3 哨兵两台机器就能起步，这些"穷人组合"正文一句没提；对预算敏感的读者，"3 主 3 从是工程惯例"之后第一个问题就是"我最少花几台机器"。

2. 【7.3.4|案例示例】ShardingSphere、Vitess、MyCAT 点名即止。建议补两三句形态与坑：client/JDBC 模式 vs proxy 模式的运维边界、跨分片 join 与分布式事务的限制、社区活跃度（MyCAT 基本停更，我在它上面交过跨分片查询的学费后迁去 ShardingSphere-JDBC）。真要上分片的读者，这段才是决策依据。

3. 【7.5|深度广度】表 7-1"分区或副本不足时的行为"一行是出事故那晚最要命的一行，但一格一句话装不下机制。建议展开成三个小场景：Redis 少数派停写窗口多长（跟着 cluster-node-timeout 走）、MGR 少数派成员如何进入只读、Kafka ISR 不足时 acks=all 写入报什么错（NotEnoughReplicas）。现在读者只能背结论，出事时没法照着复盘。

4. 【7.2.3|深度广度】"加节点只是把部分槽迁移到新节点，大部分 key 不动"只讲了美好的一半，图 7-2 也只画了 MOVED/ASK 的成功路径。建议补一段 resharding 实操代价：逐 key MIGRATE 期间该 key 阻塞、大 key 迁移造成明显卡顿（我们大促前扩容就是因此不敢动手）。"槽可迁"这笔账要算上迁移中的痛才算完整。

5. 【7.2.3|版本时效】2026 年选"Redis Cluster"绕不开 license 分叉：2024 年 Redis 改 RSAL/SSPL 引出 Valkey，2025 年 Redis 8 又加回 AGPLv3。第 1 章 1.4.3 的版本状态提示交代了 MySQL 8.0 与 Kafka 4.0 的大事，唯独 Redis 的 license 变局一字未提。对预算和供应链敏感的团队这是真实选型题，建议补两三句口径，说明本书讨论对 Valkey 是否直接适用。
