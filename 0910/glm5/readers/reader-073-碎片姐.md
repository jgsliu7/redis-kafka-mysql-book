# 读者073 · 碎片姐
身份：InnoDB 深度用户，10年，爱好：插花
主读：第 8 章

## 五个问题
1. 【8.3.3|深度广度】页分裂在导读、8.3.1（"记录变长等情况也可能触发页内重组或页分裂"）和 8.5.2 反复被点名，但整章没有一处真正展开：分裂点怎么选（随机插入下的中点分裂与顺序插入时的优化路径）、为什么随机主键表的页填充率长期徘徊在一半上下、MERGE_THRESHOLD 一个字没出现。讲了 16KB 七段布局，却不讲页放不下之后发生什么，页式范式的"代价"断了一截。

2. 【8.5.2|逻辑论证】"一页里哪怕只剩几行 100 字节的记录，也要占整整 16KB，半空的页在所难免"——这句我不服。半空页的主因是页分裂和删除空洞，是可治理的工程问题：MERGE_THRESHOLD 可调、在线重建可回收、8.0 的 innodb_defragment 能做页内整理；定长页真正免不了的只有每页百余字节（38+56+26+8B 加槽位）的结构开销。把可治理的碎片写成页式的宿命，会让读者误以为空间浪费只能认命。

3. 【8.1.3|表达可读】"关键数字"框里 InnoDB 那条没有一个数字："页头、页尾、虚拟记录和页目录占用一部分空间……随行宽、记录数与页内空闲情况变化"——同一个框里 Kafka 给了 61 字节、Redis 给了 300–500MB，InnoDB 只给了定性套话。我心里的账是 FIL Header 38B、Page Header 56B、两条虚拟记录约 26B、FIL Trailer 8B、每槽 2B，读者要拿着这些才能估算一页实际能放多少行。

4. 【8.3.2|深度广度】讲 innodb_page_size 选型只谈"较大页一次容纳更多记录、较小页少读无关数据"，漏了 DBA 选型时真正的硬约束：Compressed 行格式（KEY_BLOCK_SIZE 页压缩）只在 16K 页下可用，选了 4K/8K 就与页压缩无缘，32K/64K 的限制更多。只讲 I/O 权衡不讲功能阉割，读者照这一节选 8K 页是要踩坑的。

5. 【8.4.6|版本时效】"Kafka 3.9 起正式 GA 的 Tiered Storage（KIP-405）"与我了解的发布节奏对不上：3.6 引入的是 Early Access，转正 GA 我记得是 4.0。我是搞 InnoDB 的，不敢说死，但这个年份级别的口径建议对着 Apache 官方 release notes 再核一遍再付印。

## 五个建议
1. 【8.3.3|深度广度】补一小节（半页也够）讲页内空间动态：User Records 从 Infimum 之后向下生长、Page Directory 从页尾向上生长、Free Space 被两头挤压，直到放不下触发重组或分裂；并给图 8-4 加两个生长方向箭头。这是碎片问题的第一性原理，比七段静态罗列更能解释"为什么会分裂、为什么删除会留洞"。

2. 【8.5.2|案例示例】把"半空的页在所难免"换成一个可复现的对比案例：同一张表随机主键与自增主键各插百万行，用 innodb_space 或 information_schema.INNODB_BUFFER_PAGE 看两种页填充率差多少，再带一句 MERGE_THRESHOLD 与在线重建的治理手段。让"代价"从断言变成读者自己能跑出来的现象。

3. 【8.1.3|表达可读】关键数字框把 InnoDB 各段开销写实（38/56/26/8B、每槽 2B、COMPACT 记录头 5B 起），与 Kafka 61 字节那条同等待遇；顺手加一行"16KB 页扣掉开销后约能放多少条 100 字节的行"的估算，页分裂与半空页的成本就有了直观锚点。

4. 【8.3.2|术语使用】"段初期逐页分配空间，增长后再整区申请"建议点出术语和数字：每个段最初的 32 个页是碎片页（frag array，来自共享区），这正是小表空间回收难、碎片化的根源。补上它，"改善数据的连续性"的动机才完整，读者也能顺着这个术语去查资料。

5. 【8.3.3|表达可读】"变长字段的长度信息按与字段相反的顺序存放"只有规则没有动机，我读到也要停半天才确认说的是长度列表按列逆序排。建议补一句为什么：长度列表紧贴记录起点、逆序存放，解析器从记录头处一次读出全部长度即可逐列定界，不必预知记录总长。规则加动机，读者不必像我一样停下来倒推。
