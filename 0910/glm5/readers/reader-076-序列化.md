# 读者076 · 序列化
身份：protobuf 研发，8年，爱好：德式桌游
主读：第 8 章

## 五个问题
1. 【8.4.5|逻辑论证】「这种‘格式自带版本号’的做法，是支持混合版本部署与平滑升级的标配」这个判断过强：同节自己写了「老 Broker 收到不支持的 Magic 版本直接拒绝」，说明 Magic 提供的是版本识别而非兼容能力——新格式恰恰不能被旧代码读。且现实中 Kafka 已通过 KIP-724 在 3.0 弃用 V0/V1（produce 路径直接拒绝），新旧格式共存是有明确期限的，书里没提这条退役线，容易让读者以为版本号机制等于无限期平滑共存。
2. 【8.1.1|术语使用】导读的亲身案例（旧代码读到新格式报错）和 8.1.1 的「明天升级的代码要能读懂今天写的文件，今天没升级的代码也可能要面对明天新格式写的文件」两处分别用到了向前/向后兼容，但全书没给这两个词下定义。按 protobuf 业界惯例（旧代码读新数据=向前兼容），导读踩的坑是缺向前兼容；中文技术社区这两个词的用法经常打架，并列出现却不指认，读者很容易记反。
3. 【8.2.2|深度广度】讲了 RDB v9/v10/v11/v12 的版本对应，却没有回答兼容性读者必问的问题：高版本写的 RDB（如 7.4 的 v12）能否被低版本 Redis（如 7.0）加载？实际是不能——版本号高于加载器上限直接拒载，即 RDB 只保证「新读旧」、不保证「旧读新」，升级后降级回滚没有格式出路。导读里吐槽的正是「旧代码读新文件报错」，到 8.2.2 却没回扣 Redis 自己的策略是什么、为什么这个不对称在运维上可以接受。
4. 【8.5.1 表 8-2|技术事实】「演进机制」一行把 MySQL 写成「行格式与页内格式标记」，但 InnoDB 的行格式并不记录在页内（在数据字典里），FIL 页类型字段也不是严格的版本判别依据；把它与 RDB version、Kafka Magic 并列，三格对比里有一个并不是「字节里自带的版本机制」，横向对比口径不齐。
5. 【8.3.3|读不懂】「普通记录组通常由 4–8 条记录组成，首尾组有例外」——「例外」指什么没说清。我停下来翻源码才确认：首槽永远对应 Infimum、末槽对应 Supremum，各自成组不遵守 4–8 的范围，中间组满 8 条才分裂新槽。这句话对没写过页内代码的读者是个悬空指针。

## 五个建议
1. 【8.4.5|深度广度】建议补一段「格式演进的两大流派」：整版本切换（RDB version / Kafka Magic，靠新旧解析器双侧共存）与字段级自描述（TLV / 字段编号 + 未知字段跳过，protobuf、Avro 的路线，加字段不必升版本）。本章三个样本恰好全走前者，读者会误以为版本号是演进的唯一答案；而 RDB 长度编码的 `11` 特殊编码、Kafka V2 的 headers 字段其实已带有后者的影子，点破这一层对设计自己格式的读者价值很大。
2. 【8.4.3|案例示例】把 61 字节批头的字段构成列成小表（baseOffset 8 + batchLength 4 + partitionLeaderEpoch 4 + magic 1 + crc 4 + attributes 2 + lastOffsetDelta 4 + firstTimestamp 8 + maxTimestamp 8 + producerId 8 + producerEpoch 2 + baseSequence 4 + recordsCount 4 = 61），让读者能自己加出来。「关键数字」框对 V0/V1 都给了同口径的开销分解，唯独 V2 的 61 字节没有拆解，较真的读者无法验证。
3. 【8.2.4|结构导航】本节开头承诺「只讨论文件布局的变化」，但 8.2.3 和图 8-3 已经铺开了 7.0 之前 rewrite 的管道传增量、收尾补写等机制细节，读者要在「7.0 前双缓冲」与「7.0 后 manifest 切换」两套机制间来回切换。建议把图 8-3 改成左右对照（左：7.0 前双缓冲，右：7.0 后 manifest 原子切换），或以 7.0 后机制为主图、旧机制缩为角注。
4. 【8.1.1|术语使用】给向前/向后兼容一行明确定义（建议直接采用「新代码读旧数据=向后兼容，旧代码读新数据=向前兼容」的业界惯例），并在导读案例处点名缺的是哪一种。这两个词在中文资料里对号入座的错误率极高，一本讲「格式即契约」的书值得先把契约术语钉死。
5. 【8.6.5|案例示例】「很多自研系统第一版格式图省事，没留版本号……」是泛例，说服力远弱于导读里那个亲历的「迁移脚本折腾一周」；建议二选一补齐：要么换可查证的具体案例（Kafka V0/V1 从引入到 KIP-724 弃用的完整生命周期就是现成好料），要么把导读案例展开到字节级——旧解析器具体在哪一步报错、迁移脚本那一周在迁什么。
