# 读者018 · 微秒哥
身份：高频交易系统开发，13年，爱好：马拉松
主读：第 2 章

## 五个问题
1. 【2.4 表2-2|技术事实】核心目标一行写 Redis「极低延迟（微秒级）」，没有任何测量条件；隔壁 Kafka 列给了「每秒几十万条」的量化锚点，Redis 却只有一个含糊的「微秒级」——1μs 还是几百μs？跨机一次 TCP 往返，光内核协议栈加 syscall 就吃掉几微秒到几十微秒，Redis 官方基准的 P99 通常在亚毫秒级。不给同机/跨机、值大小、QPS 条件，这个数字没法校准。
2. 【2.2.2|技术事实】「点查（从根走到叶，O(log N)，两到三次 I/O）」把树高直接当成了磁盘 I/O 次数：根页和内部节点几乎总在缓冲池里，热表点查常态是 0–1 次物理 I/O，而同小节讲自适应哈希时也说「热点页进缓冲池」，前后口径打架。「两到三次」是页访问次数，不是 I/O 次数，这两者在延迟上差三个数量级。
3. 【2.2.1|技术事实】跳表一节前文说「每隔几个节点保留一个指针」（确定性等距抽稀），后文又说「层数逐层独立抛硬币」（随机），两种说法互相矛盾，且都不是 Redis 的实现：ZSKIPLIST_P=0.25，上一层节点数平均只有下一层的 1/4。等距的说法会让人把跳表当成确定性索引结构，也就理解不了紧接着那句「随机反而不会失衡」凭什么成立。
4. 【2.3.3|技术事实】「零拷贝让一批消息不进用户态，直接从页缓存送到网卡」没有划清路径边界：sendfile 只在 Fetch（Broker→消费者）响应路径成立，Produce 路径数据必须进 Broker 用户态做 CRC 校验和日志追加，一次都省不了。做行情分发时这正是关键认知——消费端零拷贝、生产端多拷贝，两端延迟与 CPU 特征完全不对称；读者若以为收发都零拷贝，会把 Kafka 端到端延迟估计得过于乐观。
5. 【2.2.3|逻辑论证】本章主线是取舍，但 RecordBatch 一节只讲了批量的「得」（压缩 2–6 倍、差值编码、整批 CRC），攒批的「舍」——端到端延迟下限被 linger.ms 抬高——只字未提，表 2-2 里 Kafka 的「最大代价」也只写「协议复杂性、学习曲线」。默认 linger.ms=0 是延迟优先，调大才是拿尾延迟换吞吐，这是 Kafka 最经典的一根旋钮；取舍之「舍」恰恰在这里，不讲等于取舍只讲了一半。

## 五个建议
1. 【2.3.1|深度广度】「协议这层开销不构成延迟的主要来源」这句断言建议配一张延迟拆解表：一次 SET 往返里网络 RTT、内核协议栈+syscall、RESP 逐字节解析、命令执行各占多少（数量级即可，注明同机/跨机）。延迟论断读者信不信全看拆解——一根堆叠柱状图顶十句断言。
2. 【2.2.3|深度广度】在攒批处补一小段「吞吐-延迟旋钮」：端到端延迟下限 ≈ linger.ms + 网络 + 追加落盘，batch.size 与 linger.ms 怎么配合，哪些场景应该 linger=0（对尾延迟敏感的交易、告警类）。给读者一个可操作的公式，而不只是「批量优先」的定性结论。
3. 【2.2.1|图示】图 2-2 建议把 span（跨度）画出来：正文说「span 逐层累加就是名次」，这是本章开头排行榜案例里 ZREVRANK O(log N) 的机械核心，但我核了 SVG 源码，图里只有前向指针和查找路径，没有任何 span，那句话悬在半空。可在红色查找路径上逐步标注 span 值，顺带演示一次「名次 = 沿途 span 求和」。
4. 【2.3.2|案例示例】预编译语句建议补连接池场景的实践提示：statement_id 是连接级状态，池化部署里连接切换/重置会让「解析只做一次」的收益被反复重准备稀释，句柄泄漏还会顶爆 max_prepared_stmt_count。我们在交易网关上踩过这个坑——协议层的优雅设计和真实部署的收益之间，隔着一层连接管理。
5. 【2.2.1|结构导航】建议在 2.2.1 开头点明「Redis 单线程事件循环」这个前提：SDS 惰性释放、渐进式 rehash「每次只搬一个桶」、listpack 搬移 O(n) 也认了，全是「主线程不能卡」这同一条约束的推论，但这条主线在文中只以「阻塞主线程」四个字闪现一次。点破了，五个结构的选择逻辑就从五件事变成一件事。
