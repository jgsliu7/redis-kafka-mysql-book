# 读者063 · 迁移侠
身份：Redis Cluster 生产用户，6年，爱好：登山
主读：第 7 章

## 五个问题
1. 【7.2.3|逻辑论证】论证 16384 取值时说"按约 100 个主节点平均分配，每个主节点分到约 160 个槽"，而 7.1 的"关键数字"框又说"官方建议的最大规模约为 1000 个节点"——真到 1000 节点每主只剩约 16 个槽，"槽粒度/迁移粒度"的论证还站得住吗？两个口径并排出现却没交代它们的关系，我在这儿停了挺久。

2. 【7.2.3|深度广度】按书里的机制推演一个最常见的故障组合：3 主 3 从，某主连同它唯一的从一起挂（同宿主机/同机架掉电很常见），这个分片无主可提升——此时其余两个健康分片还能不能写？cluster-require-full-coverage 默认开启时全集群拒写，这种"一个分片拖垮整个集群"我在生产里真见过，比书里讲的少数派停写常见得多，但正文没给这条推演的答案。

3. 【7.3.2|技术事实】书里两处说半同步的从节点"写入 relay log 并落盘后就回 ACK"（7.3 开头写作"接收并刷盘"），据我了解 I/O 线程把事件写入 relay log 即确认，是否 fsync 取决于 sync_relay_log（默认 10000），并非逐事务落盘。想跟作者确认"落盘"的口径——按默认配置从库整机断电时"已确认"事务仍可能丢，现在的写法会让读者高估半同步的持久性。

4. 【7.4.1|表达可读】"在本章的 3.9 基线中"这句第一遍读以为指本章 3.9 小节（第 7 章根本没有这个小节），回头翻第 1 章 1.4.3 才看到版本基线是"Kafka 3.x（分层存储以 3.9+ 为准）"，而第 7 章凭什么单独立一个"3.9 基线"也没交代。按顺序读的读者解不开这个引用。

5. 【7.2.1|逻辑论证】7.2.1 说主从复制"读可以分担到从节点"，但 Redis 这条线从头到尾没提从节点读的陈旧性——复制延迟下客户端读不到自己刚写的值，这是我们用从库分担读流量时天天处理的读己之写问题；对照 MySQL 部分 7.3.3 明确写了"读取仍可能继续返回旧数据"，唯独 Redis 不提，是有意取舍还是遗漏？

## 五个建议
1. 【7.2.3|深度广度】补一小段"槽迁移怎么真的执行"：`CLUSTER SETSLOT` 的 MIGRATING/IMPORTING 两态加 `MIGRATE` 逐 key 搬运，点明 ASK 正是这个窗口的产物，以及 MIGRATE 是阻塞命令——迁一个大 key 能把源主节点卡住秒级、打穿 P99，这是每次扩容真正要排期评估的风险。现在讲了 ASK 的语义却没讲 ASK 从哪来，等于讲了病症没讲病程。

2. 【本章导读|案例示例】开头的库存超卖事故只讲到"疼"：网络分区→丢写→超卖，然后一句"要做好预案"就收了。建议补三五行政方的"善后"：当时是把扣减挪回了 MySQL、加了 WAIT/幂等补偿，还是缩短 cluster-node-timeout 缩窗口？7.4.3 已经提到 WAIT 和 min-replicas，正好接上，否则读者学不会"预案"两个字具体长什么样。

3. 【7.2.3|案例示例】hash tag 只讲了好处（强制同槽以支持多键命令），没讲代价。tag 选错会把大量 key 钉死在一个槽上：比如拿 {user} 或按月份 {202609} 做 tag，等于人为制造热点槽，还让这个槽成为扩容时最难搬的一块——这是我做迁移时见过最多人踩的坑，加一行反例就够。

4. 【7.5|深度广度】表 7-1 建议加一行"扩容/再均衡时搬什么、能否在线"：Redis 在线搬槽但 MIGRATE 阻塞源节点，Kafka 分区重分配是整段搬日志、要限速慢慢来，MySQL 加副本是全量 clone。这一格是做扩缩容选型时最常查的信息，比现有"横向扩展能力"一行的抽象概括实用得多。

5. 【图 7-2|图示】图 7-2 的迁移场景设定是"槽 8000 正在从 B 迁移到 A"，两个老节点之间倒槽看着像负载均衡操作；但正文卖点是"加节点只是把部分槽从老节点迁移到新节点"。建议改成新增节点 D、从 B 切走 8000 一段，与"扩容"语境一致，还能顺带画出 D 侧 IMPORTING 的语义。
