### Q1【P0|4人共鸣|覆盖4条原始意见】protected-mode 生效条件与官方文档口径冲突，且只钉死 7.0 不提 6.x 差异

- 摘要：书的断言与 redis.io 官方安全文档/redis.conf 注释口径对不上（官方写的是「绑定所有网卡且无密码」触发，书说 bind 不是条件），且未给源码出处；四名读者分别核了源码或官方文档，有人确认 7.0 实现确如书所说、但 6.2 及更早版本条件不同（显式 bind 后保护整体失效）。在「显式 bind 0.0.0.0 + nopass 时远程到底拦不拦」这个加固要命判断上，读者无法从书中得到答案，直接决定加固清单里「检查 bind」一条的去留。
- 代表意见：「两个口径下加固清单完全不同——显式 bind 0.0.0.0 加 nopass 时 7.0 到底拒不拒远程连接？请给出处并统一口径，这直接决定我加固清单里『检查 bind』这一条留不留。」（读者056·风控爷）
- 其他提出者：051·红队（指出 6.2 及更早版本条件里还有 `server.bindaddr_count == 0`，线上大量 6.x 读者会误以为仍受保护）、055·证书猫（与官方 redis.conf 注释对不上，停很久不知信哪边）、058·CTF少女（若核对的是 7.0 源码另有结论，应给出处）

### Q2【P0|4人共鸣|覆盖4条原始意见】TDE/存储加密威胁模型前后不闭环：6.1 立「磁盘被盗也读不了」，6.4 的 keyring_file 兑现不了
- 定位：6.1 存储加密定义 vs 6.4 MySQL TDE/keyring_file 段
- 摘要：6.1 用「数据落盘后即使磁盘被盗也无法直接读取」定义存储加密，但 6.4 介绍的社区版 keyring_file 主密钥明文放在同一台机器上——整盘镜像、云盘快照、备份泄露时锁和钥匙一起到手，威胁模型只有企业版（Vault/KMS）才兑现。同章前后自拆，且没点破 TDE 对 SQL 层拖库（合法账号、注入、FILE 权限）零防护、逻辑备份天然明文，读者会高估 TDE 的防护面。
- 代表意见：「6.4 讲 MySQL TDE 时却不点破它对 SQL 层拖库（合法账号、SQL 注入、FILE 权限读文件）零防护，而支付行业实际出险大多走 SQL、备份、从库这三条路。讲到了 binlog/redo/undo 加密，却没提 mysqldump/XtraBackup 逻辑备份天然是明文——加密边界没有闭环，读者会高估 TDE 的防护面。」（读者056·风控爷）
- 其他提出者：054·IAM侠（云盘快照泄露时密钥与密文一起到手，处理过的泄露几乎全是快照和备份）、055·证书猫（同章前后自拆，至少该先把两处口径对齐）、059·合规法（「密钥在谁手里」没讨论，对 DBA/托管云厂商内部越权无效）

### Q3【P0|3人共鸣|覆盖3条原始意见】审计「采样」与全量留痕要求及本章自己的审计定义矛盾
- 定位：6.5 审计小节（「务实的选择是异步写入审计日志、对日志采样，或外接专用审计系统」）vs 6.1 审计定义
- 摘要：书把「采样」与异步、外挂并列为等效选项且不提示边界，但 6.1 给审计下的定义是「事后能否查清谁在什么时候做了什么」——漏采的请求取证时永久无法还原；等保 2.0、网安法第 21 条（留存不少于六个月）、PCI-DSS Req 10 对敏感操作都是全量留痕硬要求，采样在测评中是直接不符合项。「同步写审计会让系统不可用」也被指为假两难（顺序追加、异步落盘是标准做法）。
- 代表意见：「支付场景里资金变动类操作采样审计等于没有审计，出险那天恰好漏采那一笔，取证链就断了；PCI-DSS Req 10、等保对敏感数据访问是全量留痕的硬性要求。『如果每条操作都同步写审计日志……甚至让系统不可用』也是个假两难，顺序追加、异步落盘、独立管道采集是标准做法，至少应加『高危操作必须全量』的限定。」（读者056·风控爷）
- 其他提出者：052·等保姐（采样等于主动丢弃审计记录，测评时直接不符合项）、059·合规法（应区分哪些事件可采样、哪些必须完整）

### Q4【P0|3人共鸣|覆盖3条原始意见】Redis 凭证存储「SHA-256 摘要、不存明文」的表述抹平关键差异
- 定位：6.2 Redis 凭证存储句 + 表 6-1「凭证存储」行
- 摘要：三个角度同一主题：正文「密码以 SHA-256 摘要形式保存，不存明文」紧跟 requirepass 介绍之后，但该说法只对 ACL 用户密码成立，requirepass 至今明文写在 redis.conf、`CONFIG GET` 直接回显（实战拿执行权后第一件事就是捞明文横向打内网）；「无盐快哈希是凭证落盘的最小安全要求」的措辞在合规语境会被当达标线（等保密评要求加盐慢哈希）；表 6-1 里 Redis 写「SHA-256」、MySQL 写「SHA-256 认证信息」，无盐不迭代与加盐迭代抗离线猜解差着量级，被读成「两家差不多」。
- 代表意见：「SHA-256 摘要只对 ACL 用户密码成立，requirepass 至今是明文写在 redis.conf 里的，`CONFIG GET requirepass` 直接回显明文（官方文档原话 “in clear text inside the redis.conf file”）。实战里拿到 Redis 执行权后第一件事就是 CONFIG GET 捞明文密码横向打内网其他机器，照书里的写法，读者会误以为 requirepass 也捞不到明文。」（读者058·CTF少女）
- 其他提出者：054·IAM侠（表 6-1 同一个词抹平了正文 6.2 刚讲清的本质差别）、059·合规法（「最小安全要求」在密评语境是明确不符合项，两句之间应提示「受监管部署需另行加固」）

### Q5【P0|2人共鸣|覆盖2条原始意见】allow.everyone.if.no.acl.found「默认 false」只对自建成立，托管发行版常见反转未注明
- 定位：6.3 Kafka 授权（「在 Kafka 3.9 中……默认为 false」）
- 摘要：书的断言对 Apache 自建发行版成立，但 Amazon MSK、Google Managed Kafka、Oracle 托管 Kafka 的官方文档都写明无 ACL 资源默认对所有人开放（等价 true）。读者把「启用授权器=默认拒绝」的认知迁到云上集群，配齐 ACL 之前整集群实际是裸奔的。
- 代表意见：「只对 Apache Kafka 自建发行版成立；我日常运维的 Amazon MSK 和 Google Managed Kafka 这个开关默认都是 true（无 ACL 即放行所有人）。书里不区分自建与托管，按『默认拒绝』的认知迁到云上集群，配齐 ACL 之前整集群其实是裸奔的。」（读者054·IAM侠）
- 其他提出者：056·风控爷（MSK/Oracle 托管默认开放，不注明「社区版行为、托管云常见反转」会漏掉默认放行的大洞）

### Q6【P0|2人共鸣|覆盖2条原始意见】「证书即身份」（mTLS）路径缺失或被抹平
- 定位：6.2 Kafka 认证（认证=SASL、加密=TLS 的二分）+ 图 6-1 + 表 6-1「推荐生产认证」行
- 摘要：书把 Kafka 认证全归 SASL、TLS 严格限定为加密，漏掉了纯 mTLS 这条一等公民路径（`ssl.client.auth=required` 时客户端证书本身就是认证，Principal 取证书 DN）；图 6-1「先 TLS 隧道、后认证」的接力模型在 mTLS 场景不成立——认证发生在握手里。同时表 6-1 把 Redis 的「ACL 用户与必要的 TLS 证书校验」并排放置，会让人以为证书能映射 ACL 用户，而 Redis 的 tls-auth-clients 只是全局开关、不映射任何 ACL 用户，与 MySQL REQUIRE X509、Kafka ssl.principal.mapping.rules 在「证书即身份」上差异巨大，这层差异被并排写法抹掉了。
- 代表意见：「Kafka 的 SSL 监听器配 `ssl.client.auth=required` 时客户端证书本身就是认证，Principal 直接取证书 DN（可用 `ssl.principal.mapping.rules` 映射），不配任何 SASL 也能跑纯 mTLS。书中『认证=SASL、加密=TLS』的二分漏掉了这条一等公民路径，连带图 6-1『先 TLS 隧道、后认证』的接力模型在 mTLS 场景也不成立——认证发生在握手里，不是隧道之后的一段。」（读者055·证书猫）
- 其他提出者：051·红队（表 6-1 并排写法把三家「证书即身份」的差异抹掉了）

### Q7【P0|1人共鸣|覆盖1条原始意见】auth_socket「本机进程免密登录」表述不准确
- 定位：6.2 MySQL 可插拔认证 auth_socket 处
- 摘要：auth_socket 依赖 Unix socket 的 SO_PEERCRED，把操作系统用户名与 MySQL 用户名匹配，两者一致才免密成功（这正是 `sudo mysql` 能直进的原因）；「本机进程免密」会被理解成任意本机进程都能无密码连入，该误解在提权评估报告里引发过风险判定争议。
- 代表意见：「auth_socket 依赖 Unix socket 的 SO_PEERCRED，把操作系统用户名与 MySQL 用户名匹配，两者一致才免密成功（这正是 `sudo mysql` 能直进的原因——OS 的 root 对应 root@localhost）。『本机进程免密』的说法会被人理解成任意本机进程都能无密码连入，我在提权评估报告里见过因这个误解引发的风险判定争议。」（读者051·红队）

### Q10【P0|1人共鸣|覆盖1条原始意见】表 6-1「最细粒度」写「键模式加命令」漏了通道权限，与正文及所引规则自相矛盾

### Q11【P0|1人共鸣|覆盖1条原始意见】启示一「内部工具可以更开放」与启示五零信任「不因内网就默认信任」对立并列、未辨析

### Q12【P0|1人共鸣|覆盖1条原始意见】「默认值错配的洞更难被发现」与开篇「当天就会被扫到」自相矛盾
- 定位：6.7 论断 vs 导读/开篇案例
- 摘要：公网 default nopass 恰恰是最容易被暴露面测绘（Shodan/FOFA）发现的一类，本章开头自己说「当天就会被扫到」；真正难被发现的是内网可横向到达的 default nopass。断言不收窄限定条件就与开篇冲突。
- 代表意见：「公网 default nopass 恰恰是最容易被暴露面测绘（Shodan/FOFA）发现的一类，攻击者和防守方的扫描当天都能找到（本章开头自己就说『当天就会被扫到』）；真正难被发现的是内网可横向到达的 default nopass（无外部暴露特征、又没有审计）。这句断言需要收窄限定条件，否则与开篇案例自相矛盾。」（读者051·红队）

### Q13【P0|1人共鸣|覆盖1条原始意见】Redis 不做 RBAC 是「留给外部 IAM」对开源用户是空头支票
- 定位：6.2 Redis 授权边界划分叙事
- 摘要：开源 Redis 根本没有对接外部身份源的接口，LDAP/OIDC 都是 Redis Enterprise/云托管的能力，开源侧只能靠应用层自持密码或前置代理；「留给 IAM」读起来像有一条标准交接通道，而「统一身份源、账号生命周期管理」恰是等保和内审的硬性检查项，这句叙事会误导受监管环境的选型。
- 代表意见：「开源 Redis 根本没有对接外部身份源的接口，LDAP/OIDC 都是 Redis Enterprise/云托管的能力，开源侧只能靠应用层自持密码或前置代理。『留给 IAM』读起来像有一条标准交接通道，实际对开源用户是空头支票……这句『边界划分』叙事会误导受监管环境的选型。」（读者059·合规法）

### Q14【P0|1人共鸣|覆盖1条原始意见】MySQL 权限「逐层收窄、命中即停」漏了「无 DENY」语义，会让读者自信地配错
- 定位：6.3 及图 6-4（MySQL 权限层级）
- 摘要：MySQL 没有 DENY，全局层命中 SELECT 之后列级根本无法再收紧，真实语义是「从粗到细找到第一个授予权限的层级就停」而非越往下越严；读者亲历想用列级权限限制已有全局 SELECT 的账号、完全不生效。书不点破这层语义，权限新手读完会自信地配错。
- 代表意见：「MySQL 没有 DENY，全局层命中 SELECT 之后列级根本无法再收紧，真实语义是『从粗到细找到第一个授予权限的层级就停』，而不是越往下越严。我踩过的坑正是想用列级权限去限制一个已有全局 SELECT 的账号，发现完全不生效——书里不点破这层语义，像我这样搞不清权限模型的读者读完反而会自信地配错。」（读者060·RBAC难）

### Q15【P1|7人共鸣|覆盖7条原始意见】KRaft SCRAM 启动凭证段读不懂：「后者」指代未铺垫、版本号无 KIP/JIRA 可查、无图
- 定位：6.2 Kafka 认证小节（「Kafka 3.5.0 也加入了 Broker 到 Controller 的 SCRAM 支持；这与 Controller 之间的共识连接不是同一条路径。后者在 3.5.1、3.6.0 曾出现用 SCRAM 启动集群失败的问题」）及图 6-2
