### Q1【P0|5 人共鸣|覆盖 5 条】「加一个新标志位要改遍所有命令的声明」与命令表机制及本书前文矛盾
- 定位：5.2.2「把命令做成数据」代价段（关联第 2 章命令表叙述）
- 摘要：五位读者从不同角度指出同一句话站不住：技术上，标志位是指定初始化器/JSON 描述里的按位或数组字段，新增标志只需改用到它的命令，轮不到「改遍所有声明」；结构上，这句话与同节前文「7.0 起命令表由 commands/ 下 JSON 描述文件生成」直接矛盾，也与前段夸的「加一行就能加命令」的可扩展性自相矛盾。多位读者认为这是为了给优点硬配一个对称缺点而造出来的失真取舍。
- 代表意见：「『加一个新标志位意味着要改遍所有命令的声明』这个代价站不住：命令表行是 C 的指定初始化器，加标志位只需在结构体加字段、改用到它的那几行命令，轮不到『改遍所有声明』；7.0 起标志位更是维护在 commands/ 的 JSON 描述文件里。为了给『运行时可扩展性』配一个对称的『代价』，硬造出来的取舍反而失真。」（读者041·层层）
- 其他提出者：042·老单体、043·拆拆、047·低码、049·蜗牛

### Q3【P0|4 人共鸣|覆盖 4 条】MySQL 线程池「一条慢查询拖住队列里所有请求」绝对化失真
- 定位：5.3.1 连接层线程池段
- 摘要：企业版/Percona/MariaDB 线程池实为 thread group 分组多队列模型，配有 stall/长语句检测与兜底线程，一条慢查询只拖住所在组，不会饿死全池。四位读者（含两位 Percona/MariaDB 生产用户）指出把队头阻塞说成「所有请求」被拖住是把简化模型当现实，会被懂行的人挑战；其中一位点明「队头阻塞的波及范围恰恰是线程池设计的核心，这里简化到失真」。
- 代表意见：「企业版/Percona/MariaDB 的线程池都是分组模型：连接被分进若干线程组（thread group），每组一个 worker 配高低优先级两个队列，还有 stall 检测会在卡住时临时加开 worker，慢查询只堵自己那个组，不是『所有请求』。队头阻塞的波及范围恰恰是线程池设计的核心，这里简化到失真。」（读者045·线缆叔）
- 其他提出者：043·拆拆、046·浏览器、049·蜗牛

### Q4【P0|4 人共鸣|覆盖 4 条】「单线程内存模型解释了 7.x 默认关闭多线程 I/O」因果错位
- 定位：5.2.1 多线程 I/O 段
- 摘要：书中先说多线程 I/O 下「命令执行依然在主线程串行」，又说内存模型建立在单线程修改前提上、并称这句话「解释了」7.x 默认关闭多线程 I/O——但 I/O 线程只做 read/write 与 buffer 拷贝，不碰命令执行与数据结构，单线程前提并不因此受威胁，解释不了默认关闭。四位读者认为真实原因是多数负载下线程协调/同步开销超过收益、收益场景窄（大 value、大 pipeline 才显著），这段因果链需要重接，有读者读两遍仍不明白在解释什么。
- 代表意见：「多线程 I/O 只拆走 read/write 系统调用，命令执行仍在主线程串行，内存模型并不因此受威胁。默认关闭的直接原因是收益场景窄（大 value、大 pipeline 负载才显著），官方文档的口径也是『仅在特定负载下建议开启』，不是『不敢开』。」（读者047·低码）
- 其他提出者：045·线缆叔、048·数仓君、049·蜗牛

### Q6【P0|3 人共鸣|覆盖 3 条】Query Cache 案例归因「放错层」不成立，「缓冲池就是引擎内缓存」类比错位
- 定位：5.3.2 查询缓存案例结尾
- 摘要：三位读者指出缓冲池缓存的是物理页（失效靠 LRU 与脏页回写），Query Cache 缓存的是结果集（失效靠表写广播），两者失效机制与命中语义根本不是一回事，拿缓冲池佐证「缓存本应做在引擎层内部」是类比错位；Query Cache 的死因是失效粒度太粗（SQL 文本做 key、按表失效）加一把全局互斥锁，不是「放错了层」，把这个案例当层级宿命论的论据论证链搭不起来。
- 代表意见：「缓冲池是页缓存，失效靠 LRU 与脏页回写；查询缓存是结果缓存，失效靠表写广播，两者的失效机制完全不同。Query Cache 的死因是失效粒度太粗（SQL 文本做 key、按表失效）加一把全局互斥锁，不是『放错了层』——SQL Server 的计划缓存就放在服务层活得好好的。」（读者041·层层）
- 其他提出者：043·拆拆、048·数仓君

### Q8【P0|3 人共鸣|覆盖 3 条】分层判据体系前后打架：同一手法两个结论、判据与自家案例冲突、启示四「补」的判据是 5.1 已有的一问

### Q10【P0|2 人共鸣|覆盖 2 条】「全程无序列化、无虚函数」与「函数指针就是一次跳转」自相矛盾，对 Redis/MySQL 同类间接调用两套记账口径
- 定位：5.2.4（对照 5.3.3 handler 虚函数）
- 摘要：书先断言 Redis 层间「全程无序列化、无虚函数」，紧接着写命令分派用函数指针 cmd->proc(client)——函数指针跳转与 vtable 间接调用开销同量级，vtable 本来就是一张静态函数指针表，「静态表跳转」的辩解套在 MySQL 头上同样成立；同一章里 MySQL 的 handler 虚函数被记为固有开销，Redis 的函数指针却被记作零抽象，同一间接跳转两套口径。两位读者（一位从 JIT 内联视角）都指出结论没错但论据口径会被较真的读者抓住；Redis 真正省掉的是参数打包与跨线程交接，不是间接跳转本身。
- 代表意见：「vtable 本来就是一张静态函数指针表，『静态表跳转』这个辩解套在 MySQL 头上同样成立。做过 JIT 内联视角优化的人都会看调用点形态：cmd->proc 这一个调用点要承接所有命令，恰恰是最『多态』的调用点；Redis 真正省掉的是参数打包和跨线程交接，不是间接跳转本身。结论没错，但论据口径自相矛盾，会被较真的读者抓住。」（读者046·浏览器）
- 其他提出者：043·拆拆

### Q11【P0|2 人共鸣|覆盖 2 条】「如果你只用 InnoDB，这笔开销就是纯成本」算错账，与启示二自相矛盾
- 定位：5.3.3 Handler API 开销段（对照 5.6 启示二）
- 摘要：Handler API 的价值不只是运行时换引擎，更是隔离组织边界——InnoDB 原是 Innobase 公司的独立产品（2005 年被 Oracle 收购，2010 年才成 MySQL 默认引擎），接口让 server 与引擎由两家公司按各自节奏独立演进、独立测试，只用一个实现时这份价值也在。按「纯成本」的算法，接口隔离带来的演进收益被记成了零，这也与启示二「核心抽象延续、具体实现可演进」矛盾：接口既然支撑了 InnoDB 十几年的独立演进，怎么算纯成本。
- 代表意见：「InnoDB 原本是 Innobase 公司的独立产品（2005 年被 Oracle 收购，2010 年才成为 MySQL 默认引擎），Handler API 的价值不只是运行时换引擎，更是隔离组织边界、让 server 与引擎由两家公司按各自节奏独立演进——只用一个实现时这份价值也在。这也和 5.6 启示二『核心抽象延续、具体实现可演进』自相矛盾：接口既然支撑了 InnoDB 十几年的独立演进，怎么算纯成本。」（读者042·老单体）
- 其他提出者：050·评审员

### Q12【P0|2 人共鸣|覆盖 2 条】5.4.2 对 Kafka「逻辑层」的刻画撑不住三段视角：槽位放的不是逻辑、分开原因的论据与源码不符
- 定位：5.4.2 / 表 5-1「语义映射」
- 摘要：（a）书自己写明 KafkaApis「只做协议适配加请求分派」、领域逻辑在更下层的 Log/ReplicaManager/GroupCoordinator/Controller 里——那「逻辑层」槽位放的根本不是逻辑（DDD 意义上的端口适配器），三段统一视角在 Kafka 身上恰好断在最核心的一层，表 5-1 却仍拿它与 MySQL 的「解析/优化/执行」并排对齐，「语义映射」读起来成了同构比较；（b）「分开的原因是协议版本演进和领域逻辑演进节奏不同……副本管理算法可能半年调一次」这一论据与源码和社区经验对不上——副本与选举语义（ISR、epoch、unclean election）恰是 Kafka 最不敢动的兼容性重灾区，KafkaApis 薄的根本原因是它无状态；且 handleProduceRequest 里本身揉着 purgatory 等领域逻辑，「只做协议适配和分派」在源码里也没那么干净。
- 代表意见：「书里自己写明 KafkaApis『只做协议适配加请求分派』、『领域逻辑在更下层的 Log、ReplicaManager、GroupCoordinator、Controller 里』——那『逻辑层』这个槽位放的根本不是逻辑，用 DDD 的话说是个端口适配器，真正的领域层被压进了存储层和协调层。三段统一视角在 Kafka 身上恰好断在最核心的那一层，表 5-1 却仍拿它与 MySQL 的『解析/优化/执行』并排对齐，『语义映射』读起来就成了同构比较。」（读者041·层层）
