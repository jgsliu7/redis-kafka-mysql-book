### Q1【P0|5人共鸣|覆盖5条原始意见】贯穿案例的丢数据归因矛盾：kill -9 语义与复盘口径对不上（兼案例配置上下文缺失）
- 定位：本章导读 vs 3.6 结尾事故复盘（兼及 3.1）
- 摘要：导读说事故是「敲下 kill -9」，3.6 复盘却说「没等 AOF 刷完就杀了进程」「问题出在我没给它落盘的时间」。五位读者一致指出 kill -9 不可捕获、进程根本没有落盘机会，不存在「等/给时间」的问题，两处机理互相矛盾、归因错误；其中两位进一步指出案例缺 appendfsync 策略、丢失窗口推算和「订单只落 Redis 无双写兜底」的架构上下文，读者无法把教训对号入座。
- 代表意见：「kill -9 根本不给进程任何清理机会，丢数据是必然结果而不是『没等够时间』的问题，『给它时间』只对 SIGTERM 优雅关闭路径成立。两处对 kill -9 语义的表述互相矛盾，复盘结论没有准确归因。」（读者023·舟叔）
- 其他提出者：022·老盖（「当时是直接 kill -9，还是发了 SIGTERM 没等住又补了刀？……机理和教训都不一样，读者对不上号」）、025·稳如山（「kill -9 是不可捕获信号，Redis 从头到尾没有落盘机会，不存在『给时间』的问题……教训到底是『选对信号』还是『留足时间』，读者会学拧」）、026·开服匠（「『没等刷完就杀』更像优雅关闭走到一半被补刀，和直接 SIGKILL 的丢数据窗口……完全是两回事」）、030·问号君（「kill -9 之下 AOF 根本不会开始刷，两次讲述咬合不上」）

### Q3【P0|3人共鸣|覆盖3条原始意见】表 3-1 将 innodb_fast_shutdown=2 类比为「近乎 kill -9」抹掉了关键界线
- 定位：3.3 表 3-1（innodb_fast_shutdown 档位对比）
- 摘要：三位资深 MySQL 读者一致指出：档位 2 仍走完 server 层优雅关闭（binlog 完整收尾、连接正常断开），撕裂 binlog 事件组、写一半数据页是 kill -9 的独有风险；「近乎」二字把应急决策里「敢用 =2、绝不敢 kill -9」的那条界线抹掉了，表格无法判断「近乎」近到什么程度。
- 代表意见：「=2 仍是走完 server 关闭路径的干净退出：binlog 完整收尾、不会留下写了一半的页，重启后已提交事务不丢；kill -9 连 binlog 缓冲都可能缺尾巴、数据页可能写一半要靠 doublewrite 修。『近乎』二字抹掉的正是我们紧急停机敢用 =2 而绝不敢 kill -9 的那条界线。」（读者027·慢查询姐）
- 其他提出者：021·值班狗（「档位 2 下 server 层（binlog 正常收尾、连接正常断开）走的仍是优雅关闭，真正模拟崩溃的只是 InnoDB 层；撕裂 binlog 事件组、坑掉从库的是 kill -9 的独有风险」）、029·测零（「=2 完整刷 redo log、有序走完关闭流程，下次崩溃恢复从一个日志完整的起点开始；真 kill -9 连 redo 的完整性都不保证……『近乎』二字在应急决策时容易把这层差别抹掉」）

### Q4【P0|3人共鸣|覆盖3条原始意见】「SHOW PROCESSLIST 定位关闭卡点」的排障路径在实战中走不通，且与启示五口径不一

- 摘要：两位深耕 MySQL 的读者指出关闭期几乎不存在能连上 mysqld 执行 SHOW PROCESSLIST 的窗口，且四类根因里多数（脏页刷盘、复制线程、FTS 优化）是内部线程，processlist 里根本看不见，实战靠的是 error log 阶段日志；第三位读者发现 3.6 启示五声称 3.3 排障「依赖里程碑日志」，与 3.3 实际给出的 processlist 工具对不上，两处说法需要对齐。

### Q6【P0|2人共鸣|覆盖2条原始意见】Redis 关闭第一步「直接杀掉重写子进程」：默认路径下理由说不通，且「不破坏正确性」绝对化
- 定位：3.2 关闭流程第一步（杀 RDB/AOF 重写子进程）
- 摘要：一位读者指出逻辑矛盾：3.4 明确默认配置下 SIGTERM 关闭会同步做一次更久的全量阻塞 SAVE，那把快完成的 bgsave 杀掉、进度作废、再从头做更久的阻塞 SAVE，与「优雅关闭优先缩短关闭耗时」的依据相抵触；另一位指出「这不会破坏正确性」按官方文档有例外（AOF 刚开启首次重写、副本全量重同步后重建 AOF 时 Redis 会拒绝关闭），「优雅关闭被拒绝、进程关不掉」恰是变更窗口里最要命的分支。
- 代表意见：「默认配置（出厂就带 save 点）下 SIGTERM 关闭会同步做一次全量阻塞 SAVE。那在默认路径上，把快完成的 bgsave 杀掉、进度作废、再从头做一次更久的阻塞 SAVE，『优先缩短关闭耗时』说不通。为什么不等子进程做完？书里没有解释这条取舍。」（读者021·值班狗）
- 其他提出者：025·稳如山（「AOF 刚开启触发首次重写、或副本全量重同步后重建 AOF 时，Redis 会拒绝关闭以避免整个数据集丢失（除非加 FORCE）。『优雅关闭被拒绝、进程关不掉』恰是变更窗口里最要命的分支，这里表述不应绝对化」）

### Q7【P0|2人共鸣|覆盖2条原始意见】普通关闭后 Controller 的发现机制混淆 ZK 与 KRaft，且发现窗口无数量级
- 定位：3.4 普通关闭路径 + 图 3-6「心跳超时才发现」
- 摘要：一位读者指出「Controller 通过心跳/会话超时才发现 Broker 没了」把 ZK 模式与 KRaft 模式混成一句：ZK 下进程退出主动断会话、临时节点立刻删除，几乎实时感知；靠超时发现的只是 KRaft 心跳（45 秒量级），两者差一个量级，直接影响排障时对客户端抖动窗口的预估。另一位读者指出图 3-6 只有「抖动小得多」的定性色块，发现窗口到底是几秒还是几十秒没有数量级，合上书答不出「普通关闭到底抖多久」。
- 代表意见：「ZK 模式下进程退出会主动断开 ZK 会话、临时节点立刻删除，Controller 几乎实时感知；靠超时才发现的是 KRaft 心跳机制（broker.session.timeout.ms 默认 45 秒量级）。两种模式的感知延迟差一个量级，排障时对客户端抖动窗口的预估会对不上，我盯盘时吃过告警时点对不上的亏。」（读者026·开服匠）
- 其他提出者：029·测零（「普通关闭路径里『Controller 靠心跳/会话超时才发现』这个发现窗口是几秒还是几十秒（取决于会话超时参数），图和正文都没给数量级。排障时最实际的问题是『普通关闭到底抖多久、值不值得为受控关闭多等』，合上书我答不出来」）

### Q8【P0|2人共鸣|覆盖2条原始意见】Redis 加载期「整个实例不可用」不精确：端口先开、命令回 LOADING
- 定位：3.2 启动数据恢复段（「这期间整个实例不可用」）+ 图 3-2；兼及「grep 日志判就绪」的坑
- 摘要：两位读者以实操表现纠偏：监听端口在基础设施阶段就打开，加载期 TCP 能建连、数据类命令回 -LOADING 错误，而不是 connection refused。「不可用」到底是拒连还是连得上不响应，直接决定 readiness 探针与客户端重试怎么配；只探 TCP 通不通的探活会在数据未就绪时报假绿，书里缺「端口开≠数据就绪」这半句。
- 代表意见：「按启动四阶段（图 3-2），监听端口在基础设施段就打开了，早于数据恢复段。我碰到的实际表现是 TCP 能建连、命令回 -LOADING 错误（而不是 connection refused）。『不可用』到底是拒绝连接还是连得上不响应？这直接决定 readiness 探针和客户端重试怎么配，书里该说破。」（读者021·值班狗）
- 其他提出者：025·稳如山（「Redis 端口在数据加载完成前就已监听，加载期连接能建立、数据类命令报 LOADING 错误，只探 TCP 通不通的探活会在数据未就绪时报绿——我们的 HAProxy 就这么绿过。且 3.2 开头说加载期『整个实例不可用』也不精确」）

### Q9【P0|1人共鸣|覆盖1条原始意见】Kafka 启动「每分区单独校验、无批量恢复捷径」不区分受控关闭后重启与崩溃后重启
- 定位：3.4 启动阶段 3（日志恢复/索引重建）
- 摘要：读者指出受控关闭后重启有恢复位点检查点（恢复点已在日志末尾），恢复实际基本跳过校验；只有崩溃后的重启才付全量校验成本。书中不区分两种情形，读起来像万分区集群每次重启都逐段全量校验，与滚动重启万分区集群的实操体验不符。
- 代表意见：「受控关闭后重启，Broker 会写恢复位点检查点（恢复点已在日志末尾），恢复实际基本跳过；只有崩溃后的重启才付全量校验的成本。我滚动重启过上万分区的集群，干净重启明显比崩溃重启快得多。书中不区分这两种情形，到底哪种对？」（读者021·值班狗）

### Q10【P0|1人共鸣|覆盖1条原始意见】3.1「kill -9 只是丢几秒数据」断言过强，默认配置下丢失窗口可达小时级

- 代表意见：「出厂默认只有 RDB save 点（如 3600 1 300 100 60 10000），没开 AOF 时，kill -9 丢的是自上次快照以来的全部写入，最长可达小时级。导读 7 行明明说了『丢多少取决于持久化配置』，15 行却拿『几秒』当通例解释，默认配置下严重低估丢失窗口。」（读者023·舟叔）

### Q11【P0|1人共鸣|覆盖1条原始意见】「ibdata1 里剩下的主要是修改缓冲」说得太满

### Q12【P0|1人共鸣|覆盖1条原始意见】「AOF 携带的信息严格多于单独的 RDB」的「严格」缺前提
- 定位：3.2（AOF 优先于 RDB 的理由）
- 摘要：读者给出反例：运行时 CONFIG SET appendonly no 后 AOF 文件仍留盘，之后再落一个更新的 RDB 并崩溃，重启时只要 appendonly 仍为 yes 就会加载过期 AOF 而不是更新的 dump.rdb；「严格多于」只在「AOF 一直开启且 fsync 正常」前提下成立，书里没交代。
- 代表意见：「运行时 `CONFIG SET appendonly no` 后 AOF 文件仍留在磁盘，之后再落一个更新的 RDB 并崩溃，重启时只要配置里 appendonly 还是 yes，Redis 会照样加载这份过期 AOF 而不是更新的 dump.rdb……『严格』只在『AOF 一直开启且 fsync 正常』的前提下成立，书里没交代这个前提。」（读者030·问号君）

### Q13【P1|4人共鸣|覆盖4条原始意见】Redis preStop 方案「确认快照完成」无落地信号，时序拼不出，照字面写会卡住甚至白做快照
