### Q1【P0|5人共鸣|覆盖5条原始意见】零拷贝被写成无条件属性，前提、路径与失效条件全缺
- 定位：2.3.3（与 2.2.3 降级转换、图 2-7 相邻段落）
- 摘要："零拷贝让一批消息不进用户态，直接从页缓存送到网卡"这句绝对表述被 5 人分别指出缺边界：TLS 加密会断快路径、老网卡缺 SG-DMA 送不到"直接"、down-conversion/重压缩会拉回用户态、且零拷贝只在 Fetch（消费）方向成立、Produce 方向一次也省不了；压缩不一致时是否还成立书里没点破。读者一致认为照抄上生产会出事。
- 代表意见：「『零拷贝让一批消息不进用户态，直接从页缓存送到网卡』被写成无条件成立——Broker 一开 TLS，sendfile 这条快路径就断了，数据要回用户态加密后再进 socket，CPU 和吞吐立刻变脸。『安全换吞吐』本是呼应全书取舍主题的活案例，现在这样写，照抄上生产的人会被坑。」（读者019·老K）
- 其他提出者：011·刷题怪（压缩/降级转换与零拷贝关系没点破）、014·铁蛋（缺 SG-DMA 硬件前提）、017·树信徒（down-conversion/重压缩/TLS 三种失效，且与 2.2.3 点名的 CPU 尖刺来源没连起来）、018·微秒哥（只在 Fetch 路径成立，Produce 必进用户态做 CRC 和追加）

### Q2【P0|4人共鸣|覆盖4条原始意见】跳表索引层"等距抽稀"与"逐层抛硬币"两种描述并存矛盾，且都不是 Redis 实现
- 定位：2.2.1 跳表段
- 摘要：同一小节先写"上面几层是抽稀的索引层，每隔几个节点保留一个指针"（确定性等距抽稀），几行后又写"层数逐层独立抛硬币"（随机层数），四种读者都认为两句合不上；其中两人进一步指出两种说法都不是 Redis 实际实现（zslRandomLevel 晋升概率 ZSKIPLIST_P=0.25、上限 32 层），等距说法还会让人把跳表当成确定性索引、理解不了"随机反而不会失衡"。
- 代表意见：「跳表一节前文说『每隔几个节点保留一个指针』（确定性等距抽稀），后文又说『层数逐层独立抛硬币』（随机），两种说法互相矛盾，且都不是 Redis 的实现：ZSKIPLIST_P=0.25，上一层节点数平均只有下一层的 1/4。等距的说法会让人把跳表当成确定性索引结构，也就理解不了紧接着那句『随机反而不会失衡』凭什么成立。」（读者018·微秒哥）
- 其他提出者：012·松鼠、014·铁蛋（先读的那句会让人把索引层画成均匀网格）、016·小鹿（前一句是否为直观牺牲了严格性，至少该说清一处）

### Q3【P0|3人共鸣|覆盖3条原始意见】"跳表缓存局部性确实不如红黑树"断语依据不足
- 定位：2.2.1 跳表与红黑树对比处
- 摘要：三名读者均不服"确实"二字：红黑树节点同样独立分配、查找同样逐指针随机访存，两者局部性没有公认差距；antirez 选跳表的源码注释理由里也没有"局部性吃亏"这条。要么给实测依据，要么删掉断语，"实现更简单、范围操作更直接"才是站得住的取舍。
- 代表意见：「『跳表的缓存局部性确实不如红黑树』这个『确实』我不服：两者查找都是逐节点追指针的随机内存访问，局部性差别更多取决于节点大小和分配器行为，而 antirez 当年选跳表给的理由（p=1/4 时平均每节点 1.33 个指针更省内存、范围操作直接、实现好写好调，见 t_zset.c 头部注释）里并没有『局部性吃亏』这条。……要么给实测依据，要么去掉『确实』。」（读者019·老K）
- 其他提出者：011·刷题怪（书把"局部性差"安到红黑树头上又没给依据）、020·编译菌（依据不足，删掉论证反而更干净）

### Q4【P0|3人共鸣|覆盖3条原始意见】"sdshdr5 最省"造成错觉：运行期动态创建的字符串几乎不用 sdshdr5
- 定位：2.2.1 SDS 小节
- 摘要：三种读者（含两位核过源码、一位面试官）指出 `_sdsnewlen` 会把 SDS_TYPE_5 无条件升级为 SDS_TYPE_8（type5 没有 alloc 字段、无法预分配），所以 sdshdr5 在正常路径几乎不出现；书里"短字符串用小头省内存，sdshdr5 最省"会让读者以为 32 字节以下的串都在用 sdshdr5，照书背答案会翻车。
- 代表意见：「格式描述本身没错，但源码 `_sdsnewlen` 创建字符串时会把 SDS_TYPE_5 无条件提升为 SDS_TYPE_8（注释明说 type5 没有 alloc 字段、不适合会追加的字符串），所以 sdshdr5 在运行期几乎不出现。我面候选人时就爱拿这个细节考人，照书里这句背答案会翻车，建议补一句『实际动态创建的字符串最短也从 sdshdr8 起步』。」（读者015·楠姐）
- 其他提出者：012·松鼠、014·铁蛋（运行期会增长的字符串几乎见不到这个 1 字节头）

### Q5【P0|3人共鸣|覆盖3条原始意见】dict 扩容阈值只讲了一半：子进程期间禁扩容、阈值跳 5 这半边缺失
- 定位：2.2.1 渐进式 rehash 段
- 摘要：书写了扩容阈值"通常为 1"、也提了"子进程运行期间定时搬迁暂停"，但漏了同一个开关（dict_can_resize 置 0）管制的另一半：BGSAVE/BGREWRITEAOF 期间负载因子要冲到 dict_force_resize_ratio=5 才强制扩容，动机是少触发 copy-on-write。三人一致认为排查"RDB 期间内存翻倍、rehash 停滞"恰恰靠这半边，只讲一半会让读者推出错误模型。
- 代表意见：「渐进式 rehash 一节说扩容阈值『通常为 1』，但漏了关键的另一半：有 BGSAVE/BGREWRITEAOF 子进程期间阈值跳到 5（dict_force_resize_ratio），目的正是少触发 copy-on-write。……排查『RDB 期间内存翻倍、rehash 停滞』恰恰靠这半边，两半合起来机制才完整。」（读者015·楠姐）
- 其他提出者：012·松鼠（同段末尾提了暂停搬迁，却漏了同一开关管制的禁扩容）、017·树信徒（只讲暂停不讲提高阈值，读者会推出"子进程期间仍按 1 扩容"的错误模型）

### Q6【P0|2人共鸣|覆盖2条原始意见】预编译"执行计划每次执行时重新生成"与 MySQL 社区主流理解相悖
- 定位：2.3.2 预编译语句段
- 摘要：两名有实践经验的读者都对"解析只做一次，执行计划则在每次执行时按当时的统计信息重新生成"提出质疑：主流理解是 prepare 后计划缓存复用、仅 DDL/元数据/系统变量变化才触发 re-prepare；若按书中说法，省下的只是词法语法解析的 CPU，"解析只做一次"的收益叙事也讲不完整。要求给版本出处或讲清重优化触发条件。
- 代表意见：「『解析只做一次，执行计划则在每次执行时按当时的统计信息重新生成』跟我的既有理解对不上：我以为 MySQL 预编译是 prepare 时定好计划、EXECUTE 复用，只有表结构等元数据变化才触发 re-prepare。若按书中说法优化器每次执行都重跑，那省下的只是词法语法解析的 CPU？这句需要给出版本出处或讲清重优化的触发条件，不然容易和社区主流说法打架。」（读者019·老K）
- 其他提出者：016·小鹿（用 ORM 的印象是 prepare 后缓存复用，这段请核对，不想拿它去跟同事讲错）

### Q7【P0|2人共鸣|覆盖2条原始意见】"不对单条消息做任何拆分或索引"与第 8 章稀疏索引直接打架
- 定位：2.2.3 RecordBatch 追加日志段（对照第 8 章 8.4.4）
- 摘要："任何"二字把稀疏索引也否掉了：第 8 章明确讲 `.index` 偏移量稀疏索引（默认约每 4KB 一条）和 `.timeindex`，按 offset 定位消费恰恰靠它。作者本意大概是"不为每条消息单独建稠密索引"，但现表述跨章对不上，还会让人误以为消费定位是顺序扫描。
- 代表意见：「『不做任何索引』和第 8 章直接打架：8.4.4 明确讲了 `.index` 偏移量稀疏索引（`log.index.interval.bytes` 默认约每 4KB 一条）和 `.timeindex` 时间戳索引。作者意思大概是『不为每条消息单独建稠密索引』，但『任何』二字把稀疏索引也否掉了，两章对不上，读到第 8 章我回头翻了半天这句。」（读者012·松鼠）
- 其他提出者：019·老K（做帧回放 seek 用的就是这套稀疏索引，应写成"不做逐条索引、只做段级稀疏索引"）

### Q8【P0|2人共鸣|覆盖2条原始意见】"点查两到三次 I/O"把树高当磁盘 I/O 次数，与同节缓冲池口径打架
- 定位：2.2.2 B+ 树点查处（与同小节自适应哈希"热点页进缓冲池"）
- 摘要："两到三次 I/O"是全冷缓存口径：非叶页总量通常仅几 MB 到十几 MB、常态常驻缓冲池，热表点查是 0-1 次物理 I/O，"两到三次"是页访问次数不是 I/O 次数，两者延迟差三个数量级；同小节又自己讲了"热点页进缓冲池"，前后口径不一致，容易让读者把"三层树"记成"每次查询三次 I/O"。
- 代表意见：「『点查（从根走到叶，O(log N)，两到三次 I/O）』把树高直接当成了磁盘 I/O 次数：根页和内部节点几乎总在缓冲池里，热表点查常态是 0–1 次物理 I/O，而同小节讲自适应哈希时也说『热点页进缓冲池』，前后口径打架。『两到三次』是页访问次数，不是 I/O 次数，这两者在延迟上差三个数量级。」（读者018·微秒哥）
- 其他提出者：017·树信徒（缓冲池命中率 99.99% 回答的恰恰是这件事，B+ 树的真正实力是"树+缓冲池"组合）

### Q9【P0|1人共鸣|覆盖1条原始意见】"新旧格式可以共存"没加版本边界，Kafka 4.0 后已不成立
- 定位：2.2.3 结尾 magic 字段段（对照 2.3.3 "3.0 Broker 对 0.11 客户端"）
- 摘要：v0/v1 旧消息格式在 Kafka 4.0（2025，KIP-896）中被直接移除，"新旧格式共存"有明确保质期；书 2026 年出版仍只拿 3.0 当最新时间点、不给共存句加版本边界，上生产的人会被这句坑。
- 代表意见：「前者在 Kafka 4.0（2025 年发布，KIP-896）之后已经不成立：v0/v1 旧消息格式被直接移除，旧格式新格式的『共存』是有明确保质期的。书 2026 年出版还只拿 3.0 当最新时间点、不给共存句加版本边界，上生产的人会被这句坑。」（读者014·铁蛋）

### Q10【P0|1人共鸣|覆盖1条原始意见】MySQL 握手描述两处不准：能力标志是双向交换、凭证是挑战-应答哈希不是"加密"
- 定位：2.3.2 握手段
- 摘要：握手不是服务端单向发能力标志——客户端在 HandshakeResponse 里也要回自己的 capability flags，SSL 与新行为都在那一步谈定；native_password 的凭证是 SHA1 挑战-应答哈希（scramble），不是"加密"。
- 代表意见：「能力标志是双向交换，客户端在 HandshakeResponse 里也要回自己的 capability flags，走不走 SSL、用不用新行为都是那一步谈定的；另外 native_password 的凭证是 SHA1 挑战-应答哈希（scramble），不是『加密』，抓包看 mysql.auth 的响应字段就清楚了。」（读者013·抓包侠）

### Q11【P0|1人共鸣|覆盖1条原始意见】min_bytes 被当成容量参数，实际是长轮询延迟旋钮
- 定位：2.3.3 消费者拉取参数处
- 摘要："min_bytes + max_bytes 控制拉取量"把两个目标不同的参数捏在一起：max_bytes 是拉取量上限，min_bytes 是"攒不够就等"的长轮询门槛（配合 fetch.max.wait.ms 拿延迟换批量），是延迟旋钮不是容量参数。
- 代表意见：「max_bytes 是拉取量上限，min_bytes 是『攒不够就等』的长轮询门槛（配合 fetch.max.wait.ms 拿延迟换批量）。调过消费者 lag 的人都清楚它是延迟旋钮，不是容量参数。」（读者013·抓包侠）

### Q12【P0|1人共鸣|覆盖1条原始意见】"0xFB 标 NULL"只对文本结果集行成立，二进制行用 null_bitmap
- 定位：2.3.2 NULL 标记与二进制结果集之间
- 摘要：0xFB 标 NULL 是文本结果集行的规则；预编译的二进制结果集行里 NULL 由行首 null_bitmap 位图表示，不用 0xFB。这句夹在通用编码与二进制结果集两段之间未区分行类型，照它解析二进制行必然解错。
- 代表意见：「『0xFB 不是长度编码，在结果集行里它标记 NULL』这只对文本结果集行成立；预编译走的二进制结果集行（Binary Resultset Row）里 NULL 是行首的 null_bitmap 位图，根本不用 0xFB。……照着它去解析二进制行必然解错，想补一句话点明两者的 NULL 表示差异。」（读者020·编译菌）

### Q13【P1|4人共鸣|覆盖4条原始意见】启示四"会先从第二个版本开始"歧义，全章落点句读不懂

### Q14【P1|2人共鸣|覆盖2条原始意见】MySQL 协议节停留在抽象规则：无完整报文示例，"封帧"落空
- 定位：2.3.2 全节

- 代表意见：「小节标题是『二进制封帧』，但真正的帧格式从头到尾没出现：MySQL 每个报文都是 3 字节小端长度 + 1 字节序列号打头，单包 16MB 封顶。我在 Wireshark 里切 MySQL 流量第一步就是按这 4 个字节分帧，序列号还管着请求/响应配对；书里两套整数编码讲得很细，『封帧』这个词反而落空了。」（读者013·抓包侠）
- 其他提出者：011·刷题怪（读完只记住 0xFB 是 NULL，分档关系合上书就忘；图 2-8 MySQL 格是流程不是字节流）

### Q15【P1|2人共鸣|覆盖2条原始意见】自适应哈希"生产上常直接关掉"缺判据，疑问到章末不闭合

- 代表意见：「中间缺了『什么负载下它从资产变负债』的判据——是 btr_search_latch 竞争还是内存占用，命中率用什么观测。读者记住的只会是『关掉』这个动作，没法对照自己的系统做判断。」（读者020·编译菌）

### Q16【P1|2人共鸣|覆盖2条原始意见】表 2-1/图 2-7 字段名 baseTimestamp、recordsCount 与 Kafka 官方命名对不上
