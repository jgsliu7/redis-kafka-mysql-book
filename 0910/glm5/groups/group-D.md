### Q1【P0|6人共鸣|覆盖6条原始意见】表 4-1「相对内存」列混用延迟倍数与吞吐口径，参照基准未说明
- 定位：4.1 表 4-1「相对内存（延迟以内存为 1）」列；连带 4.4「跨口径的参照」句
- 摘要：列头声明的是延迟口径，前几行填延迟倍数，到「SSD/机械盘顺序写吞吐」两行却换成文字化吞吐类比，且对比基准换成「单线程内存随机读」。多位读者指出这个基准本身依赖式指针追逐、远低于内存真实带宽，使「顺序吞吐进入内存一个数量级以内」的结论被质疑有挑基线之嫌；新人则直接读不懂、把口径混排当排版错误。表头声明与行内容矛盾，且结论有误导风险。
- 代表意见：「前几行是延迟比值（0.01×/1×/1000×），到顺序吞吐那两行突然换成"约相当于单线程内存随机读（几百 MB/s）"——这个基线实际是依赖式指针追逐的吞吐……一般读者只会当成排版错误；而且换成真正的内存带宽口径（单核顺序拷贝十几 GB/s），SATA 的几百 MB/s 就差两个数量级以上，"进入一个数量级以内"的结论有挑基线之嫌。」（读者037·纳秒姐）

- 定位：4.6 启示二；对照 4.2 Redis 定位、4.4「避免双份缓存」理由、4.5 表 4-3「内存管理主体」行

### Q6【P0|2人共鸣|覆盖2条原始意见】关键数字框把 writeback 讲成「攒满再批量刷」的全局突发模型，「64GB 机器约 6.4GB 异步写缓冲」算术不成立
- 定位：4.1 关键数字框（vm.dirty_background_ratio/dirty_ratio）
- 摘要：内核方向读者指出现代内核（bdi 带宽估计 + balance_dirty_pages 按比例节流、5s 周期回写、脏页 30s 过期）稳态下脏页量远到不了 10%，写者按盘带宽被平滑限速而非攒满才阻塞；且回写是 per-bdi 的，Kafka JBOD 多盘下按全局 10% 算 6.4GB 不成立——单块日志盘实际能吃到的异步回写窗口远小于此，会高估「相信 OS」的缓冲深度。
- 代表意见：「现代内核（bdi 带宽估计 + balance_dirty_pages 按比例节流，dirty_writeback_centisecs 默认 5s 周期回写、脏页 30s 过期）稳态下脏页量远到不了 10%，写者是按盘带宽被平滑限速而不是攒满才阻塞；而且回写是 per-bdi 的，Kafka JBOD 多盘部署下"64GB 机器约 6.4GB 异步写缓冲"的算术根本不成立。」（读者034·页小姐）
- 其他提出者：037·纳秒姐

### Q8【P0|1人共鸣|覆盖1条原始意见】表 4-1 SSD 顺序写 ~2–14GB/s 给的是伪 SLC 缓存突发值，非持续值
- 定位：4.1 表 4-1 SSD 顺序写行
- 摘要：SSD 固件读者指出该数字是 SLC 缓存内突发值；持续写满缓存后消费级 TLC 直写常跌到 1GB/s 上下、QLC 更低，而 Kafka 不停歇追加负载吃到的恰是后一个数，拿突发值做容量规划会差出一个盘位。
- 代表意见：「SSD 顺序写行给的 ~2–14GB/s 是伪 SLC 缓存内的突发值；我做了 14 年 SLC 缓存，持续写满缓存后消费级 TLC 直写常跌到 1GB/s 上下、QLC 更低，Kafka 这种不停歇的追加负载吃到的恰是后一个数。表里把突发值当"典型"直接用于吞吐论证，拿去做容量规划会差出一个盘位。」（读者036·FTL叔）

### Q9【P0|1人共鸣|覆盖1条原始意见】「磁盘始终在做顺序写」论断太满：多分区交错下 SSD 看到的 LBA 序列并不顺序
- 定位：4.4 段清理/追加写论述
- 摘要：该论断只在单分区单活跃段时成立；一个 broker 几十个分区就是几十条追加流交错落盘，真正救吞吐的是写被攒成大块加 FTL 自身日志结构。多流 TRIM 这类特性正为交错场景而生。
- 代表意见：「一个 broker 几十个分区就是几十条追加流交错落盘，SSD 看到的 LBA 序列并不顺序，真正救吞吐的是每次写被攒成大块、加上 FTL 自身就是日志结构。多流 TRIM（stream identifier）这类特性正是为这种交错场景而生，书里"始终顺序"说得太满。」（读者036·FTL叔）

### Q10【P0|1人共鸣|覆盖1条原始意见】「磁盘容量通常是内存的上百倍」对 SSD 不成立
- 定位：4.1 表 4-1 前文
- 摘要：企业 NVMe 约 $0.1/GB、DRAM 约 $2–3/GB，差距是几十倍；能到上百倍的是机械盘。表 4-1 前面声明「不是硬件基准」，这句却既不分介质也不给口径。
- 代表意见：「近年企业 NVMe 大约 $0.1/GB 量级、DRAM 大约 $2–3/GB，差距是几十倍，能到上百倍的是机械盘。表 4-1 前面专门声明"不是硬件基准"，这句却既不分介质也不给口径，按我"数字要有出处"的习惯，这里第一个被我用笔圈了出来。」（读者031·岩石）

### Q13【P1|2人共鸣|覆盖2条原始意见】弃用精确 LRU 的动机只算 CPU 账，漏了更要命的 per-key 内存账
- 定位：4.2 近似 LRU 动机段、图 4-2
- 摘要：两位读者独立引 Redis 官方文档指出首要动机是内存：精确 LRU 每键要多挂指针（16–24 字节），百万键即几十 MB、亿级键 GB 级；只写 CPU 开销是只写一半归因，且与本节开头「Redis 的一切取舍围绕内存前提」自相失谐。
- 代表意见：「Redis 官方 LRU 文档说明弃精确 LRU 的首要动机是内存：每个对象要多 3 个指针约 24 字节，亿级键就是 GB 级开销……何况本节开头自己说"Redis 的一切取舍围绕内存前提"，这里偏偏不算内存账。」（读者039·内存紧张）
- 其他提出者：033·键盘侠

### Q14【P1|2人共鸣|覆盖2条原始意见】近似 LRU 描述停在 2.x 单轮采样，缺 3.0 起的淘汰池（eviction pool）
- 定位：4.2「内存淘汰的真实实现」、图 4-2
- 摘要：书中「随机采样 N 个（默认 5）、从中淘汰最久未用」是 2.x 行为；3.0 起加了默认 16 槽淘汰池，采样候选先入池、跨轮次积累再挑最差，才让小样本逼近真实 LRU。线上已无 2.x，照书理解等于学旧版本，「真实实现」名不副实。
- 代表意见：「3.0 起引入了 eviction pool（约 16 项的候选池，样本中最差者入池、淘汰发生在池上、可跨轮保留），正是这个池让小样本逼近真实 LRU。我在 OS 课上讲页面置换时常拿 Redis 当工程案例，精髓恰在池化这一步，缺了它，「真实实现」名不副实。」（读者040·OS老师）
- 其他提出者：033·键盘侠

### Q15【P1|2人共鸣|覆盖2条原始意见】崩溃恢复只写 redo 重放这半边，缺 undo 回滚；「恢复较快」或令 RTO 评估系统性偏乐观
- 定位：4.3 崩溃恢复段、4.5 表 4-3「崩溃恢复代价」行
- 摘要：崩溃恢复还有 undo 回滚未提交事务的另一半，长事务场景常比 redo apply 更久；恢复时长取决于上次 checkpoint 后累积的 redo 量，有读者经历写入高峰掉电后 InnoDB 恢复半个多小时。拿「较快」一行评估故障恢复预案会偏乐观。
- 代表意见：「没提另一半——undo 回滚崩溃时未提交的事务，长事务场景这一阶段常常比 redo apply 更久。4.5 又据此说"MySQL 重放 redo log 较快"，读者拿表 4-3"崩溃恢复代价"一行去评估故障恢复预案（RTO）会系统性偏乐观。」（读者031·岩石）
- 其他提出者：035·倾斜哥

### Q16【P1|2人共鸣|覆盖2条原始意见】Kafka「消费者追不上（fetch 落到磁盘）」的归因与一线排序不符；「预读命中天然高」说得太满
- 定位：4.4「不做自己的缓冲池」三理由、4.5 表 4-3「典型故障模式」行
- 摘要：运维读者称 lag 头两号原因是分区倾斜与消费端自身（GC 停顿、rebalance 风暴、处理慢），「拉取落到磁盘读」主要出现在重放/补数场景，书里说成「最典型」与一线对不上；「预读使命中率天然就高」只在消费者贴着日志尾部时成立，回溯消费、多分区流交错时 PageCache 照样淘汰——与 4.5 自列的典型故障前后力度不搭。
- 代表意见：「我 6 年处理 lag 告警的经验里，头两号原因是 key 哈希分区倾斜把单分区打满（消费者怎么追都追不上，PageCache 反而是热的），以及消费端自身（GC 停顿、rebalance 风暴、处理逻辑慢）；"拉取落到磁盘读"主要出现在重放历史/补数场景。书里把它说成"最典型"，和运维一线的排序对不上。」（读者035·倾斜哥）
- 其他提出者：031·岩石

### Q17【P1|2人共鸣|覆盖2条原始意见】修改缓冲/AHI 照 8.0 口径平铺直叙，未标 MySQL 8.4 起废弃/默认关闭
