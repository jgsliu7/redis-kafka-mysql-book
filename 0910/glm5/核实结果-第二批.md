### W01 AHI 分区版本号互斥考证（§2.2.2）

- **质疑内容**：书断言自适应哈希索引（AHI）「5.7.8 起拆成 8 个分区」；两位读者互斥考证——一方主 5.7.2，一方主 5.7.7／5.7.8 一侧。提出者：106、108（B-Q2 多人簇）。
- **书中原文关键句**：§2.2.2「哈希表要多占一块内存，高并发点查的竞争又集中在它的保护锁上，5.7.8 起拆成 8 个分区，生产上仍常常直接关掉。」（chapters/02-data-structures-protocols/chapter.md:104；第 4 章 ch4:174 另有一段讲 AHI 但不带版本号）。

**语境核实（存疑，高）**：书对 AHI 的版本号断言全书仅此一处且语义无歧义——「5.7.8 起」绑定的行为明确是「为分散保护锁竞争把自适应哈希拆成 8 个分区」；全书及 book-bible 中「5.7.2」「5.7.7」零出现。两位读者不存在误读、断章或引用失真，争的是版本号事实本身，无法从原文语境内部裁决，须交官方文档视角核对 changelog。

**技术事实核实（书无误，高）**：MySQL 5.7.8 官方 release notes「Functionality Added or Changed」条目（Bug #20985298）原文："The adaptive hash index search system is now partitioned, with each index bound to a specific partition, and each partition protected by a separate latch. Partitioning is controlled by the innodb_adaptive_hash_index_parts configuration option. Prior to MySQL 5.7.8, the adaptive hash index search system was protected by a single latch (btr_search_latch)… innodb_adaptive_hash_index_parts is set to 8 by default."（https://dev.mysql.com/doc/relnotes/mysql/5.7/en/news-5-7-8.html）。反证两位读者：5.7.2 release notes（https://dev.mysql.com/doc/relnotes/mysql/5.7/en/news-5-7-2.html）全文无 AHI 分区条目，唯一 AHI 相邻变更是 Bug #21198396「移除字段前缀上的自适应哈希」，与分区无关（系 5.7.2 一方读者的混淆源）；5.7.7 release notes（https://dev.mysql.com/doc/relnotes/mysql/5.7/en/news-5-7-7.html）同样无 AHI 分区条目。5.7 参考手册载 innodb_adaptive_hash_index_parts 默认 8、范围 1–512，与书一致。

**官方文档核实（书无误，高）**：同一 5.7.8 官方 release notes 逐字原文（含 "Prior to MySQL 5.7.8, the adaptive hash index search system was protected by a single latch (btr_search_latch) which could become a point of contention. To reduce contention, innodb_adaptive_hash_index_parts is set to 8 by default. The maximum setting is 512."，https://dev.mysql.com/doc/relnotes/mysql/5.7/en/news-5-7-8.html）——官方明写 5.7.8 之前为单锁、分区自 5.7.8 起、默认 8 个，与书逐点吻合。反证：5.7.2 官方 release notes 中 adaptive hash／innodb_adaptive_hash_index_parts／btr_search_latch 均零命中，主张 5.7.2 的读者疑与 Bug #21198396（5.7.2 移除字段前缀 AHI）混淆；5.7.7 无官方 AHI 分区记录。现行手册（https://dev.mysql.com/doc/refman/8.4/en/innodb-adaptive-hash.html）确认 innodb_adaptive_hash_index_parts 默认 8、上限 512。

**综合终判与改法方向**：书无误（技术事实＋官方文档 2 票同向定案；语境存疑系主动让位事实侧）。书「5.7.8 起拆成 8 个分区」与官方 release notes 完全一致；读者 106 的 5.7.2 判断定为与 Bug #21198396 混淆，读者 108 的 5.7.7 一侧无官方依据。**不改**。

### W02 粘性分区行为版本归属：KIP-480 vs KIP-794（§7.4.1）

- **质疑内容**：书提 KIP-480（2.4）引入默认粘性分区，随后描述「累计至少 batch.size 字节后再切换」；读者指该字节阈值行为是 KIP-794（Kafka 3.3 起）才有，全书不提 KIP-794，读者会把 3.3 之后的行为记成 2.4 就有；另称「批满才换且粘在同一 broker」。提出者：131·RAG酱、132（G-Q2 多人簇）。
- **书中原文关键句**：§7.4.1「没有 key 时，Kafka 2.4 经 KIP-480 引入默认粘性分区；在本章的 3.9 基线中，默认逻辑向一个分区累计发送至少 `batch.size` 字节后再切换，以改善成批发送的效率。」（chapters/07-cluster/chapter.md:156）。

**语境核实（部分成立，高）**：原句第二支有显式版本限定语「在本章的 3.9 基线中」——批满才换的行为描述锚定在 3.9 基线，书并未说它是 2.4／KIP-480 带来的，不存在版本错归属；且原文是「向一个分区」（分区级），全书无「粘在同一 broker」任何表述，读者引语后半句是自己带入的内容，属引用失真。但 §1.4.3 承诺「涉及版本差异时我会显式说明」，粘性分区从 2.4 到 3.9 基线间的行为变化确未显式说明——粗读读者可能把「2.4 引入」与「3.9 基线行为」混同为同一套逻辑，这一层遗漏属实，但与「书中把 3.3 行为记成 2.4 就有」的指控不是一回事。

**技术事实核实（读者成立，高）**：读者核心主张成立——「累计至少 batch.size 字节再切换」是 KIP-794（Kafka 3.3.0 起）的字节阈值语义，不是 KIP-480（2.4）的行为，而全书只引 KIP-480（KIP-794 零出现）。一手证据：(1) Kafka 3.9 官方 ProducerConfig 原文 "choose the sticky partition that changes when at least batch.size bytes are produced to the partition"，且 partitioner.adaptive.partitioning.enable 默认 true（https://raw.githubusercontent.com/apache/kafka/3.9/clients/src/main/java/org/apache/kafka/clients/producer/ProducerConfig.java）——书句对 3.9 基线的机制描述本身准确，但该语义出自 KIP-794。(2) KIP-794（Strictly Uniform Sticky Partitioner，https://cwiki.apache.org/confluence/display/KAFKA/KIP-794:Producer+Scalability+Improvement+for+Large+Number+of+Partitions ，随 3.3.0 发布，见 Confluent 公告 https://www.confluent.io/blog/apache-kafka-3-3-0-new-features-and-updates/ ）明写 "switch partitions every time batch.size bytes got produced to partition...regardless of what happens with batching"，并定性 KIP-480 "neither uniform nor sufficiently sticky"——2.4 的粘性在新批次创建时即结束（2.4 源码：tryAppend 返回 null（批满或 linger 关闭后队列排空）→ KafkaProducer 调 partitioner.onNewBatch 换分区，https://raw.githubusercontent.com/apache/kafka/2.4/clients/src/main/java/org/apache/kafka/clients/producer/KafkaProducer.java L928-943）。(3) 书中第一分句（2.4／KIP-480 是粘性分区起点）本身无误，错在缺 3.3／KIP-794 版本边界，违反 book-bible §2「标注版本差异时显式说明」及 §7.4.3/§7.4.4 自身范式。读者措辞小疵不影响结论：「批满才换」实为字节阈值（batch.size 字节产出而非 batch 满）；「粘在同一 broker」过度表述——正式实现仍是粘分区、按负载偏向较快 broker。

**官方文档核实（部分成立，高）**：「批满才换」确属 KIP-794（Kafka 3.3.0）：KIP 官方页 Proposed Changes 原文「Instead of switching partitions on every batch creation, switch partitions every time batch.size bytes got produced to partition. Say we're producing to partition 1. After 16KB got produced to partition 1, we switch to partition 42.」（https://cwiki.apache.org/confluence/display/KAFKA/KIP-794%3A+Strictly+Uniform+Sticky+Partitioner ）；官方 upgrade guide「Notable changes in 3.3.0」原文「The partitioner used by default for records with no keys has been improved to avoid pathological behavior when one or more brokers are slow…See KIP-794」（https://raw.githubusercontent.com/apache/kafka/3.3.0/docs/upgrade.html L87-90）。而 KIP-480（Kafka 2.4.0，https://cwiki.apache.org/confluence/display/KAFKA/KIP-480%3A+Sticky+Partitioner ）原文是「By "sticking" to a partition until the batch is full (or is sent when linger.ms is up)…」，2.4.0 官方 upgrade guide 亦为批就绪（满或 linger.ms 到）即换——低吞吐下远不满 batch.size 也会换，与「累计至少 batch.size 才切换」不同；2.4.0 release notes 含 KAFKA-8601 Sticky Partitioner（https://archive.apache.org/dist/kafka/2.4.0/RELEASE_NOTES.html ）。书句 batch.size 行为与 3.9 基线官方文档逐字吻合（ProducerConfig.java @3.9.0：「This strategy send records to a partition until at least batch.size bytes is produced to the partition」，https://raw.githubusercontent.com/apache/kafka/3.9.0/clients/src/main/java/org/apache/kafka/clients/producer/ProducerConfig.java ），且书已用「在本章的 3.9 基线中」区隔，故非硬错；但全书未提 KIP-794/3.3，读者把批满才换记成 2.4 就有的风险确实存在。读者「粘在同一 broker」不成立：粘性对象是单个分区（KIP-480/794 均如此），KIP-794 的 broker 层变化是按负载自适应选下一分区（选择概率与队列长度成反比），3.3.0 BuiltInPartitioner.nextPartition 为随机／加权选择而非粘同一 broker。

**综合终判与改法方向**：部分成立（语境＋官方文档 2 票同向定案；技术事实 1 票判读者成立、方向更重，但三票对「书句已被 3.9 基线显式限定、2.4/KIP-480 归属无误」无异议，共同指向同一件事：缺 3.3／KIP-794 版本边界）。读者「粘在同一 broker」表述不采纳。改法（三视角方向一致）：在 §7.4.1「引入默认粘性分区」后补版本边界一句，仿 §7.4.3 acks 写法，如「2.4 经 KIP-480 引入粘性分区（批就绪即换）；自 Kafka 3.3（KIP-794）起默认逻辑改为向一个分区累计发送至少 batch.size 字节后才切换」，使字节阈值语义明确归属 3.3+ 而非 2.4。对应行动清单 N11，从「核实轮定案后」升为「定案可施工」。

### W03 SDS 例外括号注「querybuf」疑注反（§2.2.1）

- **质疑内容**：预分配段「网络层读客户端命令缓冲（querybuf）的大参数是个例外：走 sdsMakeRoomForNonGreedy 按需扩容」——读者问括号是不是把「例外发生在哪个缓冲区」注反了（疑实际绕开 querybuf、读进参数自身的独立缓冲）。提出者：149·汉服君（J-Q9 强证据单发）。
- **书中原文关键句**：§2.2.1 预分配段「**预分配**：追加触发的扩容默认走翻倍策略……网络层读客户端命令缓冲（querybuf）的大参数是个例外：走 `sdsMakeRoomForNonGreedy` 按需扩容，知道读多少就分配多少，不为单个大参数白占一倍内存。」（chapters/02-data-structures-protocols/chapter.md:35）。

**语境核实（读者成立，高，仅文本层）**：读者引用逐字准确、无断章——该句完整位于预分配段内、自居翻倍策略的「例外」，语境不改变句义；句法上括号把「大参数」绑在 querybuf 读入路径上；全书 grep 仅此一处涉及 querybuf／大参数／NonGreedy，不存在能为括号注提供另一种读法的旁路描述（ch5 只提 argv/argc 是执行流水线产物）。读者没有误读，其前提（书把例外绑在 querybuf 上）就是该句的字面陈述——是否技术性注反留源码视角裁定。

**技术事实核实（书无误，高）**：Redis 源码 src/networking.c 的 processMultibulkBuffer 大参数分支（ll >= PROTO_MBULK_BIG_ARG，即原 PROTO_BIG_ARG，32KB）实际调用为 `c->querybuf = sdsMakeRoomForNonGreedy(c->querybuf, ll+2-sdslen(c->querybuf));`（紧邻注释 "Hint the sds library about the amount of bytes this string is going to contain"）——操作与回写对象均为 c->querybuf；该函数在 networking.c 全文件只对 querybuf 调用，从不对 argv 对象或其他缓冲区调用（7.0/7.4/8.0 分支一致核对）。src/sds.c 中 sdsMakeRoomForNonGreedy = `_sdsMakeRoomFor(s, addlen, 0)`，跳过翻倍/加 1MB 的贪心扩容、"just grows to the necessary size"，与书「按需扩容、知道读多少就分配多少、不白占一倍内存」逐点吻合。读者可能将同分支下游的零拷贝优化（createObject(OBJ_STRING, c->querybuf) 把 querybuf 移交 argv）误当作例外发生地，但该移交不做扩容决策，且移交的内存恰是 querybuf 本体。来源：https://raw.githubusercontent.com/redis/redis/7.4/src/networking.c 、https://raw.githubusercontent.com/redis/redis/7.4/src/sds.c （7.0/8.0 分支同验）。

**官方文档核实（书无误，高）**：核对 Redis 官方源码（7.0）：全源码树中 sdsMakeRoomForNonGreedy 仅两处调用，对象均为 c->querybuf——① readQueryFromClient 中「if (!(c->flags & CLIENT_MASTER) && (big_arg || sdsalloc(c->querybuf) < PROTO_IOBUF_LEN)) { /* When reading a BIG_ARG we won't be reading more than that one arg into the query buffer, so we don't need to pre-allocate more than we need, so using the non-greedy growing. */ c->querybuf = sdsMakeRoomForNonGreedy(c->querybuf, readlen); }」——非贪心扩容恰发生在 querybuf；② processMultibulkBuffer 解析到 ll >= PROTO_MBULK_BIG_ARG（server.h 第 167 行 #define PROTO_MBULK_BIG_ARG (1024*32)，32KB 大参数阈值）时同样作用于 c->querybuf。sds.c 第 297-300 行函数注释「/* Unlike sdsMakeRoomFor(), this one just grows to the necessary size. */」与书句逐字对应。7.2/7.4/8.0 各版两处调用同样均作用于 c->querybuf。例外缓冲区就是 querybuf 本身，括号注方向正确、未注反。附注：读者引用的宏名 PROTO_BIG_ARG 是 5.x 及更早旧名，6.0 起官方源码改名 PROTO_MBULK_BIG_ARG；书稿未点名宏名，不受影响。来源：https://raw.githubusercontent.com/redis/redis/7.0/src/networking.c 、https://raw.githubusercontent.com/redis/redis/7.0/src/sds.c 、https://github.com/redis/redis/blob/8.0/src/networking.c 。

**综合终判与改法方向**：书无误（技术事实＋官方文档 2 票同向定案）。语境票的「读者成立」系「读者未误读原文」的文本层裁定，其预设的改法条件（源码证实大参数绕开 querybuf 直读 argv 独立缓冲）经两票源码视角证伪、未触发。括号注（querybuf）方向正确。**不改**；行动清单 N15 结案。

- **质疑内容**：书断言「Redis 7.0 默认启用 repl-diskless-sync」；读者主张 7.0 默认仍是 no、7.4/8.0 才改 yes。提出者：141·反欺诈（I-Q5）；另 H-Q15（139）为相邻提问（「复制仍可能读取持久化文件」指哪种条件），不构成版本质疑、不并入。

- **书中原文关键句**：后记「## 版权与勘误」（chapters/10-epilogue.md:63）「© 2026 本书作者。本书采用知识共享署名-非商业性使用-禁止演绎 4.0 国际许可协议（CC BY-NC-ND 4.0）授权，未经许可不得用于商业用途。」；:65「2026 年 7 月第 1 版」；:71「本书勘误与版本更新见 https://gitee.com/flainliu/redis-kafka-books，欢迎读者反馈……」。

**语境核实（部分成立，高）**：原句属实（协议名与原文一致、指向对象为「本书」整本、无限定语），但「与『动员读者传播』的表述自相矛盾」半个论据是引用失真——全书检索「传播/分享/转发/推荐/转载/免费开放」仅命中序言「我在本书里分享三个层面的内容」（作者自述）与参考文献「Gossip 元数据传播」（技术术语），后记是「欢迎读者反馈」而非动员传播；书内也 grep 不到任何「商业出版/出版社/销售」表述，「与商业出版矛盾」是外部前提推断，不是书内文本自相冲突。

**出版合规核实（部分成立，高）**：声明对象是「本书」整体（全书唯一许可条款，未区分正文/示例代码/源文件；本书无可下载代码资产，Gitee 仓库即书稿源文件，根目录无 LICENSE）。冲突半面成立：法律上 CC 属非专有授权、作者可另行签出版合同，并非绝对不能商业出版；但出版实务中出版社要求专有出版权，而此声明已向公众授予不可撤销的免费非商业复制/传播权（全文转发合法且出版方无法阻止），且定价书版权页印「未经许可不得用于商业用途」使图书馆采购/企业内训是否属商业使用变得模糊，与 Gitee 免费书稿同库共存加剧「付费买免费授权物」质疑——采购法务打回的预判属实，**现措辞不可付印**。「动员读者传播」半面不成立：全书无任何动员传播表述，且 BY-NC-ND 本就允许非商业转发，该子项无文本依据。

**综合终判与改法方向**：部分成立（2/2 视角同向定案）：「动员读者传播自相矛盾」驳回；「NC 条款与后续商业出版的结构性冲突」成立，现措辞不可付印。改法（出版合规视角；升级 N14 原「加一句二次创作授权边界」方案——仅补授权边界句不能解决 NC 与商业销售的结构性冲突）：改「版权与勘误」节该句本身而非补句——纸书/电子版改为「© 2026 本书作者，保留所有权利，未经出版方书面许可不得复制/传播」；若作者坚持开放共享，则将公开授权对象限定为仓库版本：「作者在 gitee.com/flainliu/redis-kafka-books 以 CC BY-NC-ND 4.0 公开本书草稿与勘误，正式出版版本以出版合同为准」。此改属出版决策而非文本错误，留作者与出版方裁决。
