# 序言

十年前我就想写这本书，一直拖到现在。当时已经用了不少年的 Redis、MySQL、Kafka，也觉得它们的设计有相通之处，却说不清这些相通之处究竟能帮助我做什么。后来做系统、处理故障、重新审视自己的决定，才逐渐有了一些可以写下来的观察。

最初整理笔记时，我按软件分别写。Redis 的持久化写在 Redis 里，Kafka 的日志写在 Kafka 里，各自看都能说清，放在一起却看不出它们处理了哪些相同的问题。后来改成按主题组织，内存、文件、复制、恢复这些事情才有了可以直接比较的位置。这本书保留了这种写法。

我想追问的事情并不复杂。一个决定解决了什么问题？它依赖哪些条件？如果换一种实现，会失去什么，又会得到什么？这些问题常常在软件已经选定之后才出现。例如，低延迟满足了，但容量增长以后怎么办；主节点可以自动切换，但先前返回成功的写是否还在；查询可以从缓存返回，但缓存里的状态凭什么算数。

只知道功能存在，无法回答这些问题。知道实现名称也不够。“用了日志”“有三个副本”“支持事务”都还只是论证的开始。日志要保存哪些内容，副本何时确认，事务包括哪些状态，才决定这些功能能为业务承担什么责任。

所以书里记录三层内容。首先是具体机制。Redis 怎样表示一组数据，InnoDB 怎样组织页，Kafka 怎样追加和读取一段日志，都需要讲到操作过程。省去这些细节，后面的取舍就没有依据。其次是机制之间的比较。同一个要求，可以在不同层实现；一个系统里合理的成本，换到另一个系统里可能无法接受。最后是组合后的决定。当数据库、缓存和消息同时参与一次请求时，各组件单独成立的保证，并不会自动成为整个请求的保证。

第10章因此安排了一个完整的设计推演。它从库存问题出发，列出假设、比较候选、确定成功响应的含义，再检查提交、重试和故障切换。这是用于说明判断过程的设计示例，不是对我当年项目细节的补写。

现实中的决定比示例还受更多条件约束：什么时候交付，谁来维护，现有系统能改多少，业务愿意接受怎样的失败。把这些条件补齐以后，也未必只剩一个答案。两个方案都能满足要求时，维护成本、迁移风险和团队已有能力就可能改变选择。这类判断可以有明确立场，也应允许不同意见。

我把这三个软件作为观察样本，沿着一次请求、一次提交或一次恢复追查它们承担的责任。Redis 的低延迟不能回答所有缓存一致性问题，MySQL 的事务不能自动覆盖另一个服务的写入，Kafka 的副本也不等于业务处理恰好发生一次。

这里也保留一些失败后的认识。记录这些认识，是为了检查原来的假设，并说明不同条件怎样影响选择。我会把确定的事实、据此作出的判断和仍受条件限制的部分尽量分开。

本书面向有两年以上开发经验、用过三款软件中至少一款的后端工程师，也面向需要参与选型、维护和故障处理的人。它不是完整的使用手册。为了理解机制，必要的数据结构、操作系统和事务概念仍会解释；命令和配置用来说明具体行为，不能脱离版本、环境和故障假设作为生产配置直接套用。

本版以 Redis 7.x、MySQL 8.0.x 和 Apache Kafka 3.9.0 为观察基线。采用固定基线是为了使讨论可以核对，并不表示这些版本适合所有新项目。涉及特定小版本的行为会单独说明，关键机制也尽量给出能够继续追查的官方资料。

我对架构的兴趣，始终落在这些具体的决定上。读懂一个实现之后，再问一句它为什么这样安排；准备借用一个做法之前，再检查自己是否具有相同条件。如果这份笔记能帮助你把某个原本含糊的决定说明白，它就完成了很实际的一件事。
