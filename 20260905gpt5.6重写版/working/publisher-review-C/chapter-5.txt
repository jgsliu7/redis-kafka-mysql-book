[0001 #chapter-5] 第 5 章 分层架构设计 — 存储层 / 逻辑层 / 交互层

[0002 #s115] 本章导读

[0003 #s115] 我接手过一个运营后台，需求只是加一个导出按钮。我改了 Controller 三行代码，结果部署后首页打不开了。原来订单查询的 SQL 和导出逻辑混在同一个 DAO 里，我动的那几行不小心改了 SQL 拼接的顺序。我只动了三行，但影响的边界根本不在这三行里。

[0004 #s115] 这个项目已经有 Controller 和 DAO。名称上的分层存在，查询和导出之间的依赖却没有因此消失。仅凭这次事故，还不能断定多加一层就能解决问题：两项功能也许确实需要共享查询条件，问题可能出在共享了不该共享的可变状态，或者把不同用途的 SQL 拼装合在了一处。分层能不能改善修改风险，要看它隔离的究竟是什么。

[0005 #s115] 这一章从请求进入服务端开始，分别观察 Redis 的命令与对象、MySQL 的 SQL 与存储引擎、Kafka 的请求与分区日志。它们都有接收输入、执行操作、访问数据的职责，但职责边界未必是线程边界，更未必是网络边界。我关心的是一次变化到哪里为止，以及为了限制这次变化，系统又增加了哪些接口、状态和等待。

[0006 #section-5.1] 5.1 问题的本质：一项变化会穿过哪些边界

[0007 #s117] 职责、执行和部署是三件不同的事

[0008 #s117] 一个服务可以把协议解析、业务判断和数据访问分成三个模块，再把三个模块放在同一个线程中执行。它也可以不改变模块职责，只把网络读写交给另一个线程。两种情况下，代码都分了层，线程安排却不同。如果再把数据访问移到独立进程，就出现了进程间通信；放到另一台机器，才进一步涉及网络超时、连接中断和独立故障。

[0009 #s117] 因此，“多了一层”本身不能告诉我们多了多少延迟。一次方法调用、一次队列交接、一次远程请求产生的成本不同。方法调用可能被编译器优化，也可能触发昂贵的数据复制；队列交接可能只增加很短的等待，也可能在负载上升后成为主要延迟来源；远程请求需要处理序列化与失败，但服务拆开以后也可能获得独立扩容的收益。只有把边界上的动作写清楚，讨论代价才有对象。

[0010 #s117] 本章用交互、逻辑、存储三个名称标识职责。交互处理连接和报文，逻辑解释操作的含义，存储维护数据及其访问方法。这是观察时采用的分类，不声称三个项目的源码目录都严格按这个结构组织。认证、事务上下文、复制和资源限制还可能同时影响几项职责，不能仅把它们归入某个模块，就认为依赖已经处理完了。

[0011 #s118] 接口要隐藏实现，也要暴露必要的限制

[0012 #s118] 设想上层只需要“根据订单号找订单”。底层从内存哈希表换成数据库索引，只要返回的字段、找不到时的含义、错误处理和并发约定不变，上层就有机会保持不动。但是，原来一次调用不会等待，后来却可能超时；原来对象返回后可直接修改，后来修改需要单独提交。即使函数名和参数表没变，契约也已经变了。

[0013 #s118] 接口不是函数签名的同义词。它还包括谁拥有返回的数据，调用失败后是否产生了副作用，调用能否重试，结果在什么时间点有效。把这些条件藏起来，上层表面上少知道一些细节，却不得不在出错时猜测下层行为。能够隐藏的通常是实现方法，不能随便隐藏的是影响调用者正确性的语义。

[0014 #s118] 这种区别也是评价可替换性的起点。两个实现都能响应同一个方法，不等于替换后系统行为相同。内存与磁盘、事务与非事务、同步与异步都有可能被包装成相近的接口，但包装不能自动补齐语义。一个可插拔边界的价值，在于明确哪些差异允许存在，哪些能力必须由所有实现兑现。

[0015 #s119] 判断分层，要落到具体修改

[0016 #s119] 我看分层方案时，会先找几项已经可以指认的变化。例如，协议要增加一个字段，存储表示要随数据量转换，某个调用要由同步改为异步，或者一种实现要退出使用。然后沿着这项变化检查：哪个模块首先需要知道，哪些调用者必须修改，哪些测试会因此改变。

[0017 #s119] 如果上层必须知道下层每一种内部表示，接口并没有隐藏这项变化。反过来，如果为了替换一个很少变化的部件，所有正常请求都要维护复杂的适配状态，也需要解释这笔成本为什么合理。分层不是越多越稳，也不是越少越快；判断的对象是具体的依赖及其代价。

[0018 #s119] 还有一类边界不直接服务替换，却仍然有价值。测试替身让业务逻辑脱离真实网络运行；资源隔离让慢任务只占用指定队列；兼容层使旧客户端可以逐步退出。这些收益不一定表现为一种新的领域概念。只用“有没有新抽象”作为硬门槛，会误删有明确工程用途的层。

[0019 #section-5.2] 5.2 Redis：同一线程内也有需要维护的边界

[0020 #section-5.2.1] 5.2.1 交互层先把不完整的字节变成完整命令

[0021 #section-5.2.1] 客户端通过 TCP 发送数据时，一次写入和一次读取并不一一对应。服务端可能只读到命令的一部分，也可能一次读到多条命令。Redis 的查询缓冲区保存已经收到但还没消费的字节，RESP 解析器根据类型标记、长度和元素个数判断报文是否完整。这里复用的是第 2 章介绍的协议边界，而不是依赖网络恰好按命令交付。

[0022 #section-5.2.1] 解析可以随着字节到达逐步推进，但命令不能因为读到一行就立即执行。以数组形式发送的命令，需要收齐对应参数后才能形成一次完整调用。若把“增量解析”误当成“参数尚未到齐即可执行业务”，就会混淆报文处理与命令执行两个阶段。解析器负责保留进度，执行器接受的是已经形成的命令参数。

[0023 #section-5.2.1] Redis 7.x 的普通命令执行主要在主线程串行进行。事件循环把就绪的连接交给处理函数，处理函数读入数据、推进解析，再进入命令分派。网络 I/O 可以按配置使用额外线程，部分后台工作也有自己的线程或子进程；因此“Redis 是单线程”适合说明主要命令执行路径，不适合说明整个进程只有一个执行单元。

[0024 #section-5.2.1] 这种安排减轻了键空间并发修改时的协调负担，但没有消除所有等待。某条命令执行很久，其他命令仍需等待主线程；一次响应很大，即使数据查询很快，输出缓冲和网络发送也会占用资源。性能问题不能仅由层数解释，操作复杂度、响应规模和后台任务同样会影响延迟。

[0025 #section-5.2.2] 5.2.2 输出缓冲区把执行完成和发送完成分开

[0026 #section-5.2.2] 命令完成后，客户端未必能够立即收完结果。Redis 把待发送内容放入客户端输出缓冲，随后在连接可写时继续发送。这样，命令处理不必一直等着慢客户端；但尚未送出的数据仍占内存，解耦的代价并没有消失，只是从等待变成了缓冲。

[0027 #section-5.2.2] client-output-buffer-limit 按客户端类型设置限制，硬限制针对当前占用，软限制还结合持续时间。Redis 7.x 示例配置中普通客户端的该项默认值为零，含义是没有由这项配置施加的输出缓冲上限；不能概括为所有客户端默认都会在同一阈值被关闭。实际配置与客户端类别要一起看。R5-01

[0028 #section-5.2.2] 这个边界值得保留，因为命令执行速度与客户端接收速度本来就可能不同。但边界的正确性还包括资源归属：待发送结果算谁的内存，积压何时结束，超限以后是断开连接还是限制生产。除了缓冲区，还需要明确积压受什么约束。

[0029 #section-5.2.2] 在有管理权限的测试实例上，CLIENT LIST 中的输出缓冲相关字段，可以帮助区分“命令还没执行完”与“结果已产生但发送滞后”。这项观察不需要先改线程模型。若主要开销来自响应数据量，增加 I/O 线程与缩小单次响应解决的是不同部分的问题，不能互相代替。

[0030 #section-5.2.3] 5.2.3 命令表把共同行为从处理函数中分离出来

[0031 #section-5.2.3] 完整命令进入分派阶段后，Redis 根据命令名找到命令描述，再进行必要的参数、权限和执行条件检查，最后调用相应处理函数。命令描述不仅包含函数入口，还包括参数数量规则、命令属性和键位置等元数据。Redis 7.x 的命令描述由相应数据文件参与生成；查看具体实现时应使用对应版本源码，不能继续把早期版本的表位置当作固定目录契约。

[0032 #section-5.2.3] 命令表的好处，是把“怎样找到处理函数”和“怎样检查一类命令”集中起来。权限系统不必为每条命令独立发明识别方式，集群路由也能够利用键位置信息。但新增命令并不等于只加一行声明：如果命令访问多个键、有阻塞行为，或者需要传播到 AOF 和副本，处理函数与描述必须共同满足相关约定。

[0046 #section-5.2.4] 5.2.4 type 与 encoding 隔离的是表示变化

[0047 #section-5.2.4] redisObject 区分对象的类型与编码。类型说明对象提供什么操作语义，编码说明当前使用哪一种内存表示。例如，一个哈希对象可以在数据较小时采用 listpack，在超出适用条件后转换为哈希表。用户仍调用同一组哈希命令，但内部访问和存储的方法改变了。

[0048 #section-5.2.4] 第 2 章已经解释 listpack 怎样减少紧凑结构的更新依赖。本章关心另一件事：这种替换影响哪些代码。对客户端而言，命令名称、字段和值的语义可以保持；对服务端而言，转换、迭代、查找和释放等类型操作必须处理相应编码。不能据此说“逻辑层只看 type，所有命令代码都不关心 encoding”。边界减少了编码知识的传播，但没有让编码知识从实现中消失。

[0073 #section-5.2.5] 5.2.5 内存、释放和持久化不必合成一个可插拔引擎

[0074 #section-5.2.5] Redis 的对象存储围绕内存数据结构组织。内存分配器负责申请与归还空间，对象生命周期决定何时释放，淘汰策略在容量约束下选择哪些键退出，持久化则保存恢复所需的数据。这些职责彼此有关，却不是一件事。更换分配器不能给对象增加磁盘访问语义，开启 AOF 也不会把键空间自动变成可以按需读取任意规模数据的磁盘引擎。

[0075 #section-5.2.5] 大对象释放展示了职责与执行边界怎样分开。某些删除路径可以先把键从可见键空间移除，再将昂贵的内存释放工作交给后台线程；具体是否异步，取决于命令、配置和对象释放成本。UNLINK 与 DEL 的差别因此不是删除后能否再查到键，而是释放工作怎样安排。逻辑删除完成与内存全部归还之间，允许有一个时间差。R5-02

[0076 #section-5.2.5] 持久化也有自己的选择。RDB 和 AOF 可以按部署目标配置，关闭两者会改变重启后的恢复来源；开启 AOF 则还要决定刷盘策略。everysec 讨论的是特定故障下未持久化写入的窗口，不是“整个实例一秒钟就能恢复”。恢复耗时取决于数据量、文件形态和设备性能，这部分在第 3、4 章处理。

[0077 #section-5.2.5] Redis 没有提供 MySQL Handler 那样的通用存储引擎接口，这是其现有边界的事实。把原因归结为“内存只有一种，所以无需抽象”却过于简单：同一介质可以承载多种语义，不同介质也能实现相近接口。这里更具体的选择，是围绕既定键类型、内存表示及操作路径维持实现，而把模块扩展、持久化和复制放在各自的约定中。

[0078 #section-5.2.6] 5.2.6 直接调用节省了什么，没有节省什么

[0079 #section-5.2.6] 在主要命令路径上，许多职责之间通过函数、函数指针和对象指针交接，不需要把同一个请求再次编码成网络报文。这样减少的是中间序列化与跨执行单元交接，并不是“零抽象”。命令表和类型操作本身就是抽象；函数指针分派也是真实的间接调用。

[0080 #section-5.2.6] 低延迟不能反过来证明每个间接调用都应该删除。若一次命令主要时间消耗在遍历大集合，减少一次函数分派可能并不改变总体表现；若某条极短路径在高负载下反复执行，分派成本才可能值得单独量化。我更愿意把直接调用看成一种执行选择，再通过性能证据判断其重要性，而不把它升格为所有内存服务都应遵守的层数规则。

[0081 #section-5.3] 5.3 MySQL：可替换性要连同能力差异一起说明

[0082 #section-5.3.1] 5.3.1 连接上下文与工作线程不是同一个概念

[0083 #section-5.3.1] MySQL 服务端接收连接、完成协议握手和认证，再处理会话中的 SQL。常见的默认执行模型为连接分配工作线程；线程缓存和可选线程池机制又会改变线程的复用方式。因此，连接有独立状态，不等于它必须永久占有一个新建的操作系统线程。讨论线程池时还需要区分产品发行版和组件，不能把企业版或其他分支的能力写成所有 MySQL 8.0 安装的默认能力。

[0084 #section-5.3.1] THD 是观察会话状态的重要对象。当前数据库、字符集、会话变量、语句诊断、事务相关上下文和执行状态，都可能经它到达后续处理路径。连接处理使用客户端身份，SQL 层使用当前执行信息，引擎操作又需要相应事务信息。共享上下文使这些信息能够被使用，而不必在每个函数之间展开一份完整的参数清单。

[0105 #fig-5-3_title] 但共享一个对象也会扩大修改影响。一个字段究竟属于会话、语句还是事务，清理时点不同。如果执行失败后保留了不该延续的状态，后续语句就可能继承错误条件。这里需要讨论的是状态生命周期，而不是把共享对象简单评为“边界是虚的”。在同进程系统中，职责边界完全可以通过受约束的对象访问维持，未必需要靠复制或序列化证明存在。

[0106 #fig-5-3_title] 连接池还会让这个问题到达应用侧。物理连接被多个业务请求轮流复用，上一请求改变的会话设置若未恢复，下一请求就可能受到影响。这不是 MySQL 必然会出的问题，而是连接复用必须遵守的接口条件。服务端的会话抽象与应用的请求抽象并不天然一致，适配层需要明确如何归还连接。

[0107 #section-5.3.2] 5.3.2 SQL 的中间表示让不同阶段处理不同问题

[0108 #section-5.3.2] SQL 文本首先需要被解析成可以处理的结构，再经过语义准备、优化和执行。解析与准备关心语法、对象和表达式能否成立；优化阶段选择可行的访问路径与算子安排；执行阶段依据计划取数并产生结果。这几项职责可以在内部交织，但不能因为都在服务层，就当成同一种工作。

[0109 #section-5.3.2] 中间表示的价值，是让后续阶段不再反复解释原始字符串。优化器处理的是表、谓词、连接关系与访问候选，执行器处理的是已经选择的计划。这样，语法增加一种写法时，有机会在准备阶段转换成既有表达形式；引擎增加一种访问能力时，也可以通过能力和代价信息参与计划选择。是否真能局部修改，还取决于该特性有没有改变语义。

[0110 #section-5.3.2] 这与 Redis 命令表形成了有用的差异。Redis 的一条命令往往已经指出具体操作，MySQL 的查询需要从关系描述推导执行方法。差异在于输入保留了多少执行选择，并不意味着 SQL 天生只能逐行、永远无法批量处理。MySQL 8.0 的不同算子和优化存在版本演进，不能从某个典型的逐行调用循环推出声明式语言的性能上限。

[0111 #section-5.3.2] 在排查中，计划与实际执行之间的差距同样重要。估计行数、访问索引和连接顺序可以帮助解释为什么一次查询产生大量行读取；仅看到 Handler 接口有虚函数，不能把查询慢的原因直接归给多态。若访问行数相差几个数量级，先查计划通常比争论一个调用指令更有解释力。这里的判断依据是工作量，而不是语言特征。

[0112 #section-5.3.3] 5.3.3 Handler 隐藏页布局，但不统一全部语义

[0113 #section-5.3.3] MySQL 的存储引擎接口让服务层能够以相对统一的方式打开表、请求索引或扫描访问、读写记录，并参与事务协调。InnoDB 在内部处理页、索引、锁、MVCC 和 redo log；服务层不需要在每条 SQL 中直接实现这些细节。不同表使用不同引擎，是这一边界支持的能力之一。R5-03

[0114 #section-5.3.3] 这里有两个层次需要分开。handler 对象提供表和行访问相关操作，handlerton 则提供引擎级注册及相关回调。把所有方法都列为某一个对象的成员，容易使人误解实现。本书保留这些名称用于对应官方接口，不列出一份看似完整但随版本演进的函数清单。

[0124 #fig-5-4_arrow] InnoDB 支持事务、崩溃恢复和行级并发控制；MyISAM、MEMORY 等引擎具有不同约束。接口允许它们接入，不代表把表换成任意引擎之后，原来的事务、锁或恢复承诺还能自动成立。应用若依赖回滚，就不能只依据“SQL 能执行”判断替换成功。

[0125 #fig-5-4_arrow] 引擎差异还会向优化器传播。哪些索引访问可用，统计信息能提供到什么程度，某些条件能否下推，都会影响计划。好的抽象不是完全屏蔽差异，而是让差异通过明确的能力和约束表达。否则服务层只能假定所有引擎相同，再在执行失败时补救。

[0126 #fig-5-4_arrow] 因此，可插拔的代价不仅是调用开销。接口要维护兼容性，优化要尊重能力组合，测试要覆盖不同实现，用户还要理解替换后的行为。只有把这些成本纳入，才有依据评价一个扩展点值不值得。现有多种实现确实需要接入时，这些成本可能合理；只有一个实现，也仍可能为了测试或隔离频繁变化而保留接口。

[0127 #section-5.3.4] 5.3.4 Query Cache 说明协调成本，不证明缓存只能放一层

[0128 #section-5.3.4] MySQL 5.7 及更早版本曾提供 Query Cache，MySQL 8.0 已移除。它缓存的是查询结果：符合缓存条件的相同查询可以复用已有结果，而不必重新完成整个执行过程。相关表发生变化后，依赖这些表的缓存结果需要失效。该机制与全局同步相结合，在并发和写入频繁的负载中会产生明显维护成本。R5-04 R5-05

[0129 #section-5.3.4] 这个案例不能推出“结果缓存本应放在引擎内部”。InnoDB 缓冲池缓存的是页，命中后仍可能需要执行查询、判断可见性和构造结果；结果缓存试图复用的是另一个层次的工作。两者的失效条件和收益不同，不能把一种缓存的存在当成另一种缓存应该移到哪里的证明。

[0130 #section-5.3.4] 更有解释力的问题是：缓存项依赖哪些可变数据，变化怎样通知它，失效粒度有多大，读命中节省的工作能否抵消写维护和同步成本。如果结果很少变化、相同查询大量重复，缓存仍可能有收益；如果每次更新都会使大量结果失效，命中率再高也不能独立说明整体收益。

[0131 #section-5.3.4] Query Cache 被移除，是一个功能在产品演进中退出的事实，不是整个服务层被删除。它提示我们重新评价一项机制，而不是把“删层”作为预定答案。实现可以退出，相关问题却还在：应用缓存、代理缓存和物化结果同样需要明确数据依赖与失效条件，只是把责任放到了其他地方。

[0132 #section-5.3.5] 5.3.5 上下文共享与引擎接口各自限制不同的变化

[0133 #section-5.3.5] THD 与 Handler 不能合并成一个“标准化程度”排名。前者让一次会话及语句所需的信息可被相关执行路径访问，后者使服务层能够与不同引擎交互。共享上下文主要处理状态传递，可插拔接口主要处理实现差异。它们都在减少某些重复，但也分别引入状态耦合和能力组合的复杂度。

[0134 #section-5.3.5] 当一个系统要支持第二种存储实现时，我会先检查服务层有没有直接使用页格式、锁类型或引擎私有返回值。如果已经依赖这些细节，补一个接口名称不足以完成替换。需要决定哪些依赖确属业务要求，哪些只是实现便利；前者应进入契约，后者才有机会被隐藏。

[0135 #section-5.3.5] 同样，若问题只是单元测试难以运行，未必需要建设一个完整引擎插件体系。一个范围很小的访问接口，可能已经能够隔离真实数据库依赖。MySQL 的经验说明复杂接口能够支持什么，也说明为了这种能力需要长期维护什么，不能只取“支持可插拔”这一项好处。

[0136 #section-5.4] 5.4 Kafka：把线程交接与分布式协调分开观察

[0137 #section-5.4.1] 5.4.1 网络线程与请求处理线程之间有队列

[0138 #section-5.4.1] Kafka 3.9.0 Broker 的网络服务由不同角色协作。Acceptor 接收新连接，Processor 管理连接的网络事件，请求通过 RequestChannel 交给请求处理线程，再进入相应 API 处理。一个角色可能对应多个线程，队列本身则不是线程。不能把这些名称机械相加，再与另一个系统的源码模块数比较层数。

[0139 #section-5.4.1] RequestChannel 使网络事件处理与业务处理可以采用不同数量的线程。网络侧处理大量等待 I/O 的连接，业务侧执行校验、追加、读取等工作；两侧不必以同一个比例扩容。但这并不保证它们互不影响。请求队列有容量，业务侧持续处理不过来时，入队会受到限制，影响网络侧继续接收请求。队列把短时速度差转换成排队，不能把长期超载转换成额外处理能力。

[0151 #fig-5-5_arrow] 一个 Broker 可以同时承载多个分区和多类请求，多线程使这些工作有机会利用多个处理器核心。但不能据此说 Kafka 的每次请求延迟一定高于 Redis，或吞吐必然高一个数量级。请求大小、确认条件、访问介质和批量方式不同，直接比较数字没有意义。本章只确认一项结构差异：这里显式安排了网络与业务线程间的交接，而 Redis 的普通命令路径主要围绕主线程组织。

[0152 #fig-5-5_arrow] 队列还能帮助拆分延迟来源。请求在队列里等待的时间，与处理线程实际执行的时间不是同一个指标。若队列持续增长但执行时间没有改变，可能是到达速度超过了处理能力；若执行本身变慢，则还需检查磁盘、锁、配额或等待副本等条件。只增加队列长度往往把拒绝推迟，却让请求在系统中停留更久。

[0153 #section-5.4.2] 5.4.2 API 适配不等于没有业务判断

[0154 #section-5.4.2] Kafka 协议用 API 标识和版本描述不同请求。KafkaApis 根据请求类型进入对应处理路径，并与分区、副本、消费组等组件协作。协议版本的不同字段要转换成内部能够处理的输入，身份与资源权限需要核对，配额和错误要转换成相应响应。这些工作并不等于完整的领域逻辑，但也不是毫无判断的转发。R5-06

[0155 #section-5.4.2] 把协议适配与领域操作分开，有助于让多个协议版本使用相近的内部能力。然而，并非所有协议变化都能在适配层内处理。如果新请求增加了新的事务或一致性要求，内部状态和执行规则也必须改变。接口隔离的是可被表达转换消除的差异，无法隔离语义本身的增加。

[0156 #section-5.4.2] 请求还会带着上下文继续处理：来自哪个连接、认证后的主体是谁、使用哪个 API 版本，以及怎样关联响应。这与 Redis 的 client、MySQL 的 THD 有相似问题，但生命周期并不完全相同。跨线程以后，谁能修改什么、对象何时可以释放，需要比普通同步调用更明确；不能因为都叫上下文，就假定它们具有相同共享方式。

[0157 #section-5.4.3] 5.4.3 分区日志提供稳定的操作语义

[0158 #section-5.4.3] Kafka 的本地日志按分区组织，并拆成日志段。3.9.0 源码中的日志实现又区分统一日志视角与本地文件管理。上层需要的是按 offset 追加、定位、读取、截断和清理等操作，并不应该在每次请求中重新管理所有文件细节。这里的抽象价值，在于把分区日志的行为与具体文件操作分开。

[0159 #section-5.4.3] 追加路径仍有校验、索引和状态更新，后台 compaction 还可能重写数据，所以“追加日志”不等于系统没有写放大，也不等于所有读写都是常数成本。它说明常见写入按日志次序进行；保留、压实、事务状态和异常恢复则增加了其他工作。用一个简洁的数据模型描述主路径，与忽略其余工作是两回事。

[0160 #section-5.4.3] 消费者 Fetch 和副本 Fetch 可以复用读取分区日志的基础能力。它们都需要根据 offset 定位记录，都可能利用页缓存和文件传输路径；但是，可见范围、调用身份、复制进度和异常处理不同。普通消费者的读取还要结合隔离级别，副本则需要推进自身日志并处理主节点历史变化。共享读取组件不能推出“复制就是消费者换一个标志”或“无需独立状态机”。

[0180 #fig-5-6_title] 这种复用的收益是局部而清楚的。定位文件和读取记录的优化，不必在两套完全独立的基础组件中各做一次；但某项改动是否同时改善消费者和副本，要看它们是否经过相同分支。测试不能因为“代码共享”就只验证其中一种调用者，尤其是边界 offset、事务可见性和主节点切换时的行为。

[0181 #section-5.4.4] 5.4.4 零拷贝路径有前提

[0182 #section-5.4.4] 对于适合直接从本地文件发送的记录，Kafka 可以利用文件到网络的传输能力，减少数据在用户态缓冲中的往返复制。第 4 章已经解释页缓存，这里还涉及接口条件：若后续处理需要改变字节，或者网络层必须在用户态完成加密，就不能把所有数据都当作原样转发。R5-07

[0183 #section-5.4.4] Kafka 3.9 文档明确说明，启用 SSL 时不使用所描述的 sendfile 路径。记录格式转换等工作也可能影响具体读取路径。因此，“日志中的消息不再修改”不足以保证端到端始终零拷贝。不可变记录有利于复用和传输优化，但链路中的协议和安全要求同样参与决定。

[0184 #section-5.4.4] 这个例子说明，性能优化往往依赖多个层共同保持一个条件。存储层保持适合传输的布局，读取层避免不必要的转换，网络层提供合适的发送能力。把这些条件写成接口约束，比笼统评价“存储层很薄，所以快”更有用。条件变化时，优化可能退出，业务语义仍然必须正确。

[0185 #section-5.4.5] 5.4.5 远程存储扩大实现边界，不取消日志语义

[0186 #section-5.4.5] Kafka 3.9.0 的分层存储允许在满足配置和实现条件时，把符合条件的历史段保存到远程存储。相关组件负责远程段与元数据管理，本地与远程读取需要协调。这个变化保留了客户端按分区和 offset 访问记录的主要使用方式，却不是“整个上层和复制层完全无感”。恢复与异常处理确实需要确定数据位于哪里。R5-08

[0187 #section-5.4.5] 本章不展开远程段状态与追赶流程，它们分别属于第 8、9 章。这里可以得到一个较窄的观察：稳定的日志语义允许存储实现演进，但为了守住这种语义，内部接口和状态管理可以发生显著变化。

[0188 #section-5.4.5] 这也有助于区分接口层次。保持外部协议兼容、保持内部方法签名、保持文件格式，是三种不同的稳定性。某项功能做到第一种，不证明后两种都没有变化。面向使用者的兼容承诺越明确，内部才越有依据决定哪些部分可以重构。

[0189 #section-5.4.6] 5.4.6 协调职责不等于又多出一层网络

[0190 #section-5.4.6] Broker 需要获取分区归属与副本状态，消费组需要获取成员与分配信息，Controller 则处理集群元数据。KRaft 使元数据通过控制器仲裁组管理；本书以 3.9.0 的 KRaft 部署为主，ZooKeeper 只作为演进对照。不同协调职责有不同状态，不能合成一个“保证一致性”的黑盒。

[0191 #section-5.4.6] 在 Broker 内部，API 处理与本地日志、副本管理之间存在对象调用；网络线程与请求线程之间存在队列；跨 Broker 或独立 Controller 的通信才涉及网络。独立部署使相应服务可以单独发生故障，并不意味着每个逻辑模块都必须拆成独立进程。Redis Cluster 和 MySQL Group Replication 也有协调问题，只是不能据此把它们的源码组织硬套成相同层数。

[0192 #section-5.5] 5.5 横向对比：同一项变化，由谁承担

[0193 #section-5.5] 三个系统的共同之处，不是都能被数成三层或四层，而是都要把外部请求转换成受约束的数据操作。真正可比的是：输入变化到哪里结束，状态怎样传递，实现差异怎样表达，以及异步交接后谁承担积压。

[0222 #table-5-1] | 不能从边界直接推出什么 | 不能推出无抽象成本或任意命令低延迟 | 不能推出换引擎后全部语义相同 | 不能推出所有层都跨网络或所有路径都零拷贝

[0223 #table-5-1] 这些替换能力没有统一的优劣排名。Redis 把同一种类型的表示变化局部化，MySQL 支持具有不同能力的引擎，Kafka 维持日志访问语义并演进其内部实现。三者替换的对象不同，维护的契约也不同。只有先指定变化，再比较影响范围，才不会把某一种扩展能力当成所有系统的必选项。

[0224 #table-5-1] 这里还存在一个容易被忽略的反向成本：接口过于通用，会迫使实现暴露大量能力开关；接口过于专用，则会让新增场景不断绕过它。哪一种更合适，需要看实际变化分布。一个稳定而频繁使用的共同操作值得抽象，一批只有名称相似、语义不同的操作未必适合合并。

[0225 #section-5.6] 5.6 架构启示

[0226 #section-5.6.1] 5.6.1 先判断要隔离的变化，再选择交接方式

[0227 #section-5.6.1] Redis 的类型与编码说明，表示变化可以被限制在一组相关操作里；MySQL 的引擎接口说明，统一入口仍要表达能力差异；Kafka 的队列说明，执行速度不同可以通过有限积压协调。三个机制解决的问题不同，不能都缩成“增加一层”。

[0228 #section-5.6.1] 回到导出功能，如果共享的是同一套查询条件，那么完整复制查询代码可能增加维护成本；如果共享的是会被导出逻辑改写的状态，那么增加一个只做转发的 Service 也不会自动消除风险。需要先区分共同规则与特定处理，再决定用函数、对象还是独立任务交接。

[0229 #section-5.6.2] 5.6.2 稳定的是契约，不必是每一份内部实现

[0230 #section-5.6.2] 接口稳定对调用者有价值，但“十年没变”不是可以在设计当下验收的条件。更具体的检查，是列出已经确定的变化，观察它们能否在约定范围内完成。新增一种编码会不会改变命令语义，替换引擎会不会失去回滚能力，改为异步执行会不会使超时含义变化，这些问题现在就能讨论。

[0231 #section-5.6.2] 有些稳定需要通过版本演进实现。旧调用者继续使用原行为，新能力通过显式版本或新增操作提供；也有些变更必须承认不兼容，并给出迁移路径。为了保持方法名不变而让同一个参数在不同情境下偷偷改变含义，反而会使接口更难依赖。

[0232 #section-5.6.3] 5.6.3 共享上下文要有字段和生命周期的约束

[0233 #section-5.6.3] client、THD 和 Kafka 请求上下文都减少了重复传递，但共享对象会扩大可见范围。评价它们时，不能只数省掉多少参数，还要看一次操作结束后哪些状态仍然有效。会话、事务、请求三个生命周期重叠时，清理职责尤其重要。

[0234 #section-5.6.3] 如果一个模块为了使用两个字段，必须理解几十个无关状态，这个共享对象可能已经超过了当前边界所需的范围。改进未必是复制整个对象，可以是提供更窄的访问接口、分离可变状态，或明确只读视图。跨线程后还需说明发布和回收规则；靠约定“大家不要乱改”不足以支撑并发正确性。

[0235 #section-5.6.4] 5.6.4 异步边界必须带上容量、取消与失败语义

[0236 #section-5.6.4] 有界队列能够限制一处积压，但端到端还可能存在客户端缓冲、内核 socket 缓冲和输出缓冲。某个队列满了以后，上游是等待、拒绝还是重试，直接影响系统负载。如果拒绝触发无退避重试，局部保护也可能变成新的流量来源。

[0237 #section-5.6.4] 取消同样需要沿着路径追踪。客户端已经超时，不代表服务端尚未执行；请求仍在队列中与已经完成数据修改，是不同状态。接口如果只返回一个笼统超时，上层就需要额外的方法确认结果，或者用幂等标识容纳重复。这些问题会在第 10 章的组合案例中再次出现，分层不能自动确定这些业务行为。

[0238 #section-5.6.5] 5.6.5 删除不合算的机制，要先说明它承担过什么

[0239 #section-5.6.5] 我仍会用“这一层挡住了什么变化”追问分层，但不会因为答不出一个新领域名词，就立刻删除它。兼容、测试、限流、故障隔离都可能是明确职责。只有确认这些职责不存在、已经移交，或者成本超过收益，删除才有依据。

[0240 #section-5.6.5] Query Cache 提供了一个具体提醒：被移除的是结果缓存机制，缓存依赖与失效问题并没有一起消失。删除之后由谁承担原来的工作，调用者会失去什么，回退怎样进行，都属于修改的一部分。把“去掉一层”当作简化的证明，和把“加一层”当作解耦的证明一样不充分。

[0241 #section-5.7] 5.7 小结

[0242 #section-5.7] 导出事故里的问题，不是缺少几个标准层名，而是修改依赖没有被限制在预期范围。三个软件展示了不同的限制方法：Redis 用命令元数据和类型操作组织处理，MySQL 用中间表示与引擎接口容纳实现差异，Kafka 则让请求适配、线程交接、日志操作与集群协调各自承担明确工作。

[0243 #section-5.7] 这些边界都有成本。共享对象需要约束状态，接口需要维护能力契约，队列需要限制积压，远程调用需要处理不确定的结果。分层的收益要与这些成本放在同一次判断中。一个设计能把某类修改局部化，已经是具体价值，不必再证明它具有最少层数或最大的可插拔程度。

[0244 #section-5.7] 下一章继续检查访问边界。职责分开以后，还要知道谁能调用、允许改哪些数据，以及一次越界操作能否被阻止和追踪。第 7 章再把执行范围扩到多台机器，讨论分片、复制与控制面分别解决什么问题。
