[0001 #chapter-9] 第 9 章 数据同步：确认、历史与续传

[0002 #s257] 本章导读

[0003 #s257] 我处理过一次下单后查不到订单的告警。订单已在主节点写入，查询却落到尚未回放这次修改的从节点。写入成功和随后读到之间有一个窗口，用户不会因为系统采用了读写分离，就把这个窗口当成正常结果。后来我们增加了写后读的路由安排，但先要承认：复制在运行，不等于每个读取位置都已经具有相同状态。

[0004 #s257] 第 7 章讨论谁负责数据、谁能成为新的主节点。本章进一步追问它们之间的内容：一条修改传到哪里了，副本确认了什么，断线后还能从哪里继续。一次换主之后，两个节点的 offset 即使相同，也可能属于不同历史；一份日志即使没有损坏，也可能已经删除了落后副本需要的部分。

[0005 #s257] Redis 用复制命令流同步数据集，MySQL 用 binlog 事件推进副本，Kafka 用分区日志复制记录。它们都需要保存历史和进度，但这些标识不能合成一个通用的“越大越新”数字。下面按传播、确认、断线和换主四个问题展开，版本范围仍为 Redis 7.x、MySQL 8.0.x 与 Kafka 3.9.0。

[0006 #section-9.1] 9.1 先把“已经同步”拆开

[0007 #section-9.1.1] 9.1.1 同步到了哪一步

[0008 #section-9.1.1] 一条修改到达副本，可能只是进入网络缓冲，也可能已经写入本地日志、刷盘、应用到数据结构，或成为允许对外读取的状态。这些时刻并不重合。一个 ACK 若没有说明对应哪一步，就不足以推导故障后的行为。

[0009 #section-9.1.1] 以数据库复制为例，副本可以先把事件保存到 relay log，之后再回放到表。网络接收很快、回放很慢时，数据已经在副本机器上，却还不能由普通查询看到。Kafka 副本追加到日志后，记录是否进入消费者可见范围还涉及复制与事务边界。Redis 的复制确认也不能自动视为副本完成了持久化。

[0010 #section-9.1.1] 这不是文字上的细分。主节点等待哪一个时刻，决定成功响应前必须付出的延迟；主节点故障后，哪一个副本可以接替，决定已经确认的内容是否仍在；读取路由则决定客户端能否观察到相应状态。三项安排需要配合，不能只调一个等待参数就把它们全部解决。

[0013 #section-9.1.1] | 到达哪里 | 接收、写日志、刷盘、应用、对外可见 | 收到ACK就等于所有副本已提交

[0034 #section-9.1.2] 9.1.2 相同输入需要怎样的执行条件

[0035 #section-9.1.2] 状态机复制提供一种分析方式：从相同初始状态出发，按相同顺序执行具有确定效果的输入，副本才能得到相同结果。随机数、本地时间、外部服务返回值和不同初始内容，都可能破坏这个前提。

[0036 #section-9.1.2] 因此系统往往传播已经确定的效果，或在输入中明确必要信息。随机删除一个集合成员时，主节点可以把实际删除了谁表达出来，而不是要求副本再随机选一次；数据库可以记录受影响行的变化，而不是让每个副本重新执行含有不确定条件的查询。

[0037 #section-9.1.2] 即使采用效果记录，副本也仍需具有相容的结构和先前状态。目标行不存在、表定义不同、应用顺序被破坏，都可能使回放失败。效果复制减少了一类不确定性，没有消除数据维护、版本兼容和错误处理。

[0050 #section-9.1.3] 9.1.3 历史身份、进度和数据范围

[0051 #section-9.1.3] 假设节点 A 保存历史 H 中位置 100 之前的数据，节点 B 保存同一历史到位置 120。只要所需变化仍在，A 有机会获取差额。现在节点 C 也到位置 120，却来自另一条历史 J；相同数字不说明 B 与 C 内容相同。

[0052 #section-9.1.3] 历史身份标明“这是谁的哪段变化”，进度标明“已经走到哪里”。还需要第三项：发送方是否仍保留进度之后的内容。A 保存着位置 100，并不意味着 B 还存着 101 到 120。日志清理或缓冲覆盖可能使历史内容不再可得，位点元数据却仍然完好。

[0053 #section-9.1.3] 分开三项，就能解释不同恢复分支。身份相容、进度可衔接、内容仍在，才可能部分续传；身份分叉，需要识别共同前缀并处理冲突尾部；内容已过期，需要新的基础状态或其他恢复来源；元数据损坏，则连“应该从哪里开始”都可能要重新确定。

[0054 #section-9.2] 9.2 Redis：复制流怎样接续

[0055 #section-9.2.1] 9.2.1 从写入效果到复制流

[0056 #section-9.2.1] Redis 主节点把引起数据集变化的命令效果通过复制连接传播给副本，副本应用这些变化。默认复制异步推进，普通写命令的成功响应不要求等待每个副本完成相应位置。主节点仍维护副本进度，用于监控和需要等待的操作。R9-01：Redis 复制机制

[0057 #section-9.2.1] 复制流与 AOF 的传播机制存在复用，但目的不同。AOF 服务于本机的持久化恢复，复制流服务于其他实例的数据集；两条路径的缓冲、传输和确认不会因此完全相同。一条命令已经进入复制流，不直接说明 AOF 已刷盘，反过来也一样。

[0058 #section-9.2.1] Redis 7.x 的脚本采用效果复制，传播脚本执行产生的写入效果，而不是要求副本任意重新执行同一段脚本并自行取时间或随机值。命令传播也会根据操作语义改写。这样可以减少副本再次求值导致的差异。R9-02：Redis 脚本复制说明

[0059 #section-9.2.1] 普通异步复制减去了成功响应前的副本等待，但不意味着复制没有成本。命令编码、缓冲占用、网络发送、慢副本处理和全量同步仍会消耗主节点资源。一个慢副本可以间接造成内存或带宽压力，不能从“写命令不等ACK”推出副本状态对主节点性能完全没有影响。

[0060 #section-9.2.2] 9.2.2 全量同步先建立共同起点

[0061 #section-9.2.2] 新副本没有可用的共同历史，或部分同步条件不满足时，需要获得一份完整数据集。Redis 可以生成 RDB 状态并将它传给副本，再补上生成与传输期间发生的变化。带磁盘中转和无盘传输的具体路径不同，但共同任务都是把一个快照时刻与随后复制流衔接起来。

[0062 #section-9.2.2] 这个过程可以拆成基础状态、增量保留和副本追赶三部分。基础状态提供某个时刻的数据集；增量保留确保快照之后主节点继续接受的修改没有遗漏；副本加载完成后继续应用这些修改，逐步追到正在变化的主节点。

[0063 #section-9.2.2] 如果只把 RDB 文件传完就宣布同步完成，会遗漏快照之后的写入。如果先向副本发送后续命令，却没有确保它在正确基础状态上执行，也可能得到错误结果。因此“传输文件”和“使副本进入可继续复制的状态”不是同一件事。

[0064 #section-9.2.2] 全量同步的成本随数据量、写入速率和副本加载能力变化。生成快照要使用 CPU 与 I/O，fork 与写时复制可能影响暂停和内存，传输占用带宽，副本加载期间的可服务状态也受配置与实现限制。写时复制不等于 fork 瞬间必然复制整个地址空间；后续被修改的页才会形成相应额外内容。

[0086 #section-9.2.3] 9.2.3 replid 与 offset 共同标识历史

[0087 #section-9.2.3] Redis 的复制 offset 以复制流字节为单位。比较同一历史中的 offset，可以知道两个实例在这条流上的进度差；它不是命令计数，也不是键数量。一个大值写入与多个很小的写入，可能产生相近字节量而有不同命令数。

[0088 #section-9.2.3] replid 标识一段复制历史。副本请求部分同步时，发送自己所依据的历史身份和位置；主节点需要判断它是否属于可接受的历史，以及请求范围是否仍在保留窗口中。只判断 offset 是否小于当前值还不够，因为另一条历史也可能使用相同数字。

[0089 #section-9.2.3] 故障转移后，新主生成新复制身份，同时可以保留先前身份及其有效边界。其他副本若持有的是旧身份，在仍然相容的边界内可能继续部分同步。这不是无限期接受旧历史：边界之后可能已经出现分叉，不能把旧主后来独自接受的修改当成新主历史的组成部分。

[0090 #section-9.2.3] 设旧历史 H 在位置 1000 前为各节点共有，新主从这里继续形成新历史 J。另一副本只到 H 的位置 900，只要新主仍保留相应内容，便可能从共同部分追赶。旧主若在隔离期间把 H 推到 1100，这额外一百字节不能仅凭数字较大就覆盖新历史 J。示例位置只用于说明身份与边界，不模拟真实协议逐字节握手。

[0091 #section-9.2.3] 这个设计降低了某些换主后的全量同步需求，但不会把分叉自动合并成业务上正确的状态。重新加入的旧主需要接受当前权威历史，它此前独有的写入可能不再保留在服务数据集中。应用若把这些写入当成已经完成的交易，还需要独立处理业务后果。

[0092 #section-9.2.4] 9.2.4 backlog 保存的是可重传内容

[0093 #section-9.2.4] 复制积压缓冲区 backlog 保留近期复制流，为断线后的部分同步提供内容。它在逻辑上是一个随新写入移动的窗口，旧数据会退出可重传范围。窗口大小决定能够保留多少字节，能够覆盖多少时间则取决于这段时间的复制流速率。

[0094 #section-9.2.4] 一个明确标为估算的例子：假定复制流平均每秒生成 2MiB，计划覆盖 60 秒断线，单就这段历史需要约 120MiB。若高峰速率升到每秒 8MiB，同样容量只能覆盖约 15 秒。实际配置还要考虑突发、复制流附加内容、实现分配和其他内存用途，不能把平均速率估算当成硬保证。

[0114 #fig-9-4_title] 发生一次短断线后，能部分同步也不代表能瞬间追平。如果落后量为 B 字节，副本有效处理速率为 C，主节点继续产生写入的速率为 W，只有 C 大于 W，才有净追赶能力。用 B/(C-W) 可以得到稳定速率假设下的粗略时间估算；C 不大于 W 时，单纯增大 backlog 只能延后问题。

[0116 #section-9.2.5] 9.2.5 准入门槛与等待确认

[0117 #section-9.2.5] min-replicas-to-write 与 min-replicas-max-lag 为主节点写入设置条件：需要足够数量、最近有确认活动的副本，条件不足则拒绝写入。这里的 lag 门槛不是逐条证明“当前这条写入已经在 N 个副本上”。它根据副本状态作入口判断，随后的写入仍然要经历复制过程。

[0118 #section-9.2.5] WAIT N T 则针对同一客户端连接此前的写入，等待指定数量副本确认相应复制位置，超时返回实际确认数量。应用必须检查返回值，不能只因为命令结束就当成目标已经满足。WAIT 也不等于副本 AOF 刷盘，更不会自动把所有故障切换变成无损。R9-04：WAIT 的范围与限制

[0119 #section-9.2.5] Redis 7.2 增加的 WAITAOF 可以等待本地及副本的 AOF 持久化条件，它与普通 WAIT 的等待对象不同，且依赖相应持久化配置。即使等待完成，仍需另外考虑后续选主、多个故障及应用事务边界，不能把一个命令名称直接翻译成系统级强一致。R9-05：WAITAOF

[0120 #section-9.2.5] 假设应用先写入，再等待副本确认，等待超时。此时原写入可能已经执行，并且某些副本稍后仍会收到它。把超时当作“写入未发生”，然后以新的业务请求重复扣减，就可能制造业务重复。等待用于满足确认条件，不会回滚先前已经执行的操作。

[0121 #section-9.2.5] 入口检查、复制等待、持久化等待可以组合，但各自增加的保证必须逐项表达。还有一项不能遗漏：故障后究竟允许哪个副本成为新主。如果被提升的节点没有相应历史，先前在另一节点取得的确认并不会自动转移成新主的数据。

[0122 #section-9.3] 9.3 MySQL：接收事件与回放事务

[0123 #section-9.3.1] 9.3.1 binlog 事件保存什么

[0124 #section-9.3.1] MySQL 复制可以使用不同 binlog 格式。ROW 格式记录行变化及必要元信息，STATEMENT 格式记录语句，MIXED 在规定条件下选择。这里以 ROW 为主要观察对象，它可以避免由副本重新执行同一语句时出现的一部分非确定性问题。R9-06：binlog 格式

[0125 #section-9.3.1] ROW 并不简单等于“每行一条独立事件”。事件可以包含多行，记录哪些列还受行映像等配置影响；表映射、事务边界和其他事件共同组成可解释的复制内容。比较日志大小时，要看被修改行数、字段宽度和行映像，不能只数 SQL 条数。

[0126 #section-9.3.1] 例如，一条批量 UPDATE 影响很多行，语句文本可能很短，而行变化表示较大。这份额外内容减少了副本重新计算影响集合的工作。它没有免除副本查找、修改索引、执行约束和持久化的代价，也不能保证一个已经被人工改坏的副本必然继续回放成功。

[0127 #section-9.3.1] 传输的是逻辑变化还带来结构约束。副本需要相容的表定义和可应用状态；升级或 DDL 的顺序不当，可能使后续事件无法解释。复制遇到错误时停止，并报告错误，通常比静默跳过错误更容易保住数据关系，但恢复还需要查明究竟缺了哪一段变化。

[0128 #section-9.3.2] 9.3.2 relay log 将接收与应用分开

[0129 #section-9.3.2] 传统复制中，副本接收线程从源端获取 binlog 事件并写入 relay log，应用线程或协调器与工作线程再执行这些事件。接收与应用分开，使网络传输可以先推进，暂时不必等待每一条事件都完成引擎操作。R9-07：复制线程

[0153 #fig-9-5_title] 接收与应用的这种分离，正是导读事件的机制来源。订单变化可能已经到达副本日志，但尚未应用到查询使用的表。把查询切回主节点可以避开这一特定副本延迟，但还需要事务隔离、连接路由和故障切换保证读到合适状态；“读主”不是所有一致性问题的通用解法。

[0154 #section-9.3.3] 9.3.3 GTID 让事务身份跨文件保留

[0155 #section-9.3.3] 传统复制位置使用 binlog 文件名和文件内位置。文件轮转或更换来源后，需要把物理位置与事务历史对应起来。GTID 给事务分配由来源标识与序号组成的身份，使副本能够表达自己已执行了哪些事务，而不只说明读到了某个文件字节。R9-09：GTID 格式与存储

[0156 #section-9.3.3] GTID 的全局唯一性，不等于跨来源存在一个可以直接比较大小的总序。A:1-10 表示来源 A 的一段事务集合；A:1-8,B:1-3 则包含两个来源的范围。前者多了 A 的 9、10，后者多了 B 的 1、2、3，不能说其中一个简单“大于”另一个。

[0157 #section-9.3.3] 自动定位需要比较集合关系，找出副本缺少而来源能够提供的事务。如果某些必需事务已经从源端日志清理，知道它们的 GTID 仍然不等于能把内容发送出来。这里再次出现身份元数据与数据可获得范围的区别。R9-10：GTID 自动定位

[0158 #section-9.3.3] 还要警惕额外事务。某个副本上独立产生了源端没有的修改，即使它能继续接收后续事务，数据也不因此自动重新一致。GTID 集合提供发现历史差异的线索，却不替业务决定冲突修改是否保留。错误地跳过事务或注入空事务可以改变进度表象，但不能证明表里的内容正确。

[0159 #section-9.3.3] GTID 因而既带来便利，也增加约束。它使迁移与换源时可以按事务身份推理，同时要求维护人员知道哪些操作会产生本地独有历史。只盯着“复制线程在运行”，无法证明所有节点拥有相同事务集合和相同业务数据。

[0160 #section-9.3.4] 9.3.4 半同步确认的准确位置

[0161 #section-9.3.4] MySQL 半同步复制在满足配置条件时等待副本 ACK。副本确认的是事务事件已经写入 relay log 并刷到磁盘，不要求相应事务已经在副本引擎中应用。这里比“副本收到网络字节”多了持久化条件，又比“副本查询已经能看到”少了应用阶段。R9-11：半同步复制

[0162 #section-9.3.4] AFTER_SYNC 与 AFTER_COMMIT 改变源端等待的位置。前者在源端 binlog 同步后、引擎提交前等待相应确认；后者先完成引擎提交，再等待确认。后者的等待期间，其他会话可能已经看到事务结果，但副本尚未确认接收。在特定故障切换路径中，新主可能没有这笔此前已被读到的事务。R9-12：半同步等待点与可见性

[0163 #section-9.3.4] 故障切换后先前可见事务可能消失，与 SQL 隔离级别里的幻读是两类问题。幻读讨论一个事务中重复范围查询看见新的匹配行，两者的问题边界不同。术语分清，读者才不会误以为提高隔离级别就能修复复制确认窗口。

[0164 #section-9.3.4] 等待指定数量的副本，也不等于等待所有副本。系统按配置要求取得确认，故障转移方案必须选择具有适当历史的候选。副本已经收到日志但尚未应用时，恢复还要处理回放；确认不应该被误读成所有读取位置都即时可见。

[0165 #section-9.3.4] 半同步超时可以退回异步运行。这改变了后续写入的确认条件，不只是增加一个告警数字。观察半同步时，要区分功能被配置为启用、当前实际处于等待确认状态，以及曾经发生过多少次降级。配置存在不能证明每笔事务都取得了相同确认。

[0166 #section-9.3.4] 本书使用 source/replica 命名说明 MySQL 8.0 较新版本的相关变量；这些名称在 8.0.26 起替代对应的 master/slave 名称。复制拓扑的组织与组复制另见第 7 章，不把传统异步、半同步和组复制压成一个只由延迟决定的档位表。

[0167 #section-9.4] 9.4 Kafka：复制位置之外还有有效历史

[0168 #section-9.4.1] 9.4.1 Follower 获取记录，Leader 判断进度

[0169 #section-9.4.1] Kafka 的 Follower 按分区从 Leader 获取日志记录，带着自身的获取位置请求后续内容。Leader 因而能够观察副本的追赶进度。拉取安排让副本按自身节奏继续获取，但不能据此简单认定拉取比推送更解耦；Leader 仍要处理每个副本的状态和请求，慢副本也影响复制集合。

[0170 #section-9.4.1] 一段分区日志有若干不同的位置。日志末端表示本地已经追加到哪里；高水位 HW 表示复制协议认可的提交边界；事务消费还要考虑未完成事务限制形成的稳定边界。通常以“下一个 offset”表达边界，因此可读取范围的端点要注意是否包含该位置，不能把图中的边界数与最后一条记录编号随意混用。

[0171 #section-9.4.1] 对于普通非事务消息，可消费范围受 HW 限制；对于 read_committed 消费，未完成事务还可能使可见范围停在更早位置。一个 Follower 物理文件中已经有某条记录，不代表当前消费者就一定能得到它。这是复制追加、提交和事务可见性三个阶段的差别。

[0192 #section-9.4.2] 9.4.2 ISR 与 acks 必须连着解释

[0193 #section-9.4.2] ISR 是当前满足同步条件的副本集合，不是“系统里所有副本”的别名。副本长时间不能跟上，会失去集合成员资格；恢复追赶后可以按协议重新加入。集合随运行状态变化，是复制确认与故障选择的重要依据。

[0194 #section-9.4.2] acks=all 要求按当前同步集合完成相应确认条件，min.insync.replicas 规定接受这类写入所需的最小 ISR 数量。两者配合才表达“至少保有多少同步副本时继续写”的意图。只设 acks=all 而让 ISR 收缩到很小，实际确认覆盖也会随之变化。R9-13：生产者 acks、R9-14：最小 ISR 配置

[0195 #section-9.4.2] 以三副本分区、最小 ISR 为 2、生产者使用 acks=all 为设定。三者正常时，可以继续写；一个副本暂时落后并被移出后，剩余两个同步副本仍可能满足要求；如果同步集合进一步不足两个，对应写入将无法按该条件成功。这个例子说明门槛，并不覆盖所有请求到达与ISR变更的竞态，也不表示每次错误都证明日志未追加。

[0196 #section-9.4.2] 最小 ISR 是下限，不是“只等这两个就行”的固定副本名单。确认范围与当前 ISR 及协议状态有关。它也不等于多数派公式：给不同副本数配置相同门槛，含义会变。只有把副本数量、ISR状态、确认方式和选主规则一起看，才知道当前系统在何种故障下选择继续或拒绝。

[0197 #section-9.4.2] 不干净选举允许不满足通常同步资格的副本接任时，可能以丢失部分历史换取恢复服务。这个选择属于故障策略，不能被一个生产者参数掩盖。第 7 章已经讨论候选资格；这里关心的是新 Leader 的有效日志到底包含哪些记录。

[0198 #section-9.4.3] 9.4.3 leader epoch 识别分叉，不靠长度猜测

[0199 #section-9.4.3] 假设旧 Leader 与一个 Follower 原先都有 offset 0 到 99。随后旧 Leader 又追加了 100 到 109，其中某些记录没有达到提交条件，便与集群失去联系。新的 Leader 从它拥有的有效前缀继续写入，也可能产生编号 100 之后的记录。旧节点回来后，两边日志长度相同也不代表内容相同。

[0200 #section-9.4.3] leader epoch 为不同 Leader 任期的历史提供区分。副本通过相关协议查询某个 epoch 的结束位置，从而识别共同前缀与需要截断或补齐的部分。相比仅比较 HW，这使恢复能够利用更明确的历史边界，而不是把一个提交位置同时当成任期识别信息。R9-15：KIP-101 的恢复问题与方案

[0201 #section-9.4.3] epoch 不是业务时间戳，也不能跨分区给所有消息排序。它服务于某个分区的 Leader 历史。一个分区的新 epoch 与另一个分区的旧 epoch，没有“哪个业务事件更晚”的直接比较意义。

[0218 #section-9.4.4] 9.4.4 远程历史与本地续传的衔接

[0219 #section-9.4.4] 第 8 章介绍了 Kafka 3.9.0 的远程存储恢复路径。Follower 需要的 offset 早于 Leader 本地日志起点时，不能立刻以“本地没有”认定全部历史已经丢失；对应远程段与元数据可能仍在。

[0220 #section-9.4.4] 实现可以获取远程辅助状态，建立 leader epoch 信息与生产者快照，然后从对应后续位置进入本地日志获取流程。这里恢复的是继续工作的必要状态，不要求把历史远程 .log 全部变成 Follower 本地日志。R9-16：3.9.0 TierStateMachine 与恢复条件

[0221 #section-9.4.4] 这条路径仍然受约束：远程存储必须启用并可访问，所需元数据和段须存在，状态恢复必须成功。远程与本地保留策略不合理、插件失败或权限变化，都可能阻止恢复。监控只看本地磁盘空间和复制延迟，已经不足以覆盖这组依赖。

[0222 #section-9.4.4] “Follower 获取由本地日志服务”这一运维经验受实现版本限制，不能直接作为永久规则。更稳妥的概括是：续传必须有可解释的历史及所需状态来源；来源究竟在本地还是远程，由具体版本实现决定。

[0223 #section-9.4.5] 9.4.5 消费进度不能由消息内容推导

[0224 #section-9.4.5] Broker 保存消息，消费者读取消息并产生业务结果。消费者的当前读取位置、已提交 offset 和外部业务系统的处理结果，是三种状态。一次 poll 返回消息，只说明客户端已经取到；提交 offset，只说明下次从哪里继续的进度被保存；外部数据库是否提交，Kafka 不能单靠消息内容判断。

[0225 #section-9.4.5] 设消息表示“为订单发送通知”。日志中能看见这条消息，无法由此推断通知是否已经发送，发送成功但响应丢失时也一样。删除消费者进度后重新读日志，会再次遇到同一条消息；是否能安全重做，取决于通知服务的业务幂等与结果记录。R9-17：KafkaConsumer 的位置与提交说明

[0226 #section-9.4.5] 因此，消费者 offset 不能被概括为“丢了再从日志算出来”。某些纯派生计算可以从规定起点重新计算，但需要输入历史仍然完整、计算规则可复现，并正确重建输出状态。已经产生不可撤回副作用的业务，通常还要单独保存处理标识和结果。

[0227 #section-9.4.5] Kafka 事务可以把特定 Kafka 读写流程中的输出记录与消费 offset 纳入协议协调，但不会自动包含任意外部数据库事务或短信发送。把产品中某个范围的 exactly-once 称谓搬到端到端业务，往往遗漏最关键的外部边界。第 10 章会用一个业务事件处理流程说明怎样保留这条边界。

[0228 #section-9.5] 9.5 用相同故障比较不同机制

[0229 #section-9.5.1] 9.5.1 同样是确认，条件不同

[0230 #table-9-1] 表 9-1　确认对象与尚未覆盖的工作

[0231 #table-9-1] | 机制 | 当前等待或检查的对象 | 不应据此推出

[0232 #table-9-1] | Redis 副本准入门槛 | 最近满足条件的副本状态 | 当前写入已经复制到这些副本

[0233 #table-9-1] | Redis WAIT | 本连接此前写入对应的复制确认 | 所有副本落盘、任意换主都无损

[0234 #table-9-1] | Redis WAITAOF（7.2起） | 规定的本地/副本AOF持久化条件 | 自动获得完整业务事务和故障选主保证

[0235 #table-9-1] | MySQL 半同步 | 所需副本的relay log接收并刷盘确认 | 副本表已经应用，超时后仍按原保证运行

[0236 #table-9-1] | Kafka acks=all配合最小ISR | 复制协议及当前ISR条件 | 每条独立刷盘、消费者外部操作已完成

[0237 #table-9-1] 这些机制无法用一个“弱、中、强”顺序完整表达。某个机制等待副本日志落盘，另一个依赖多个副本的复制状态；某个机制超时后继续，另一个返回写入错误。比较时应先给出相同故障和相同业务要求，再判断哪个安排满足它。

[0238 #section-9.5.2] 9.5.2 网络断开后的三个问题

[0239 #section-9.5.2] 断线恢复可依次检查历史身份、可用内容和追赶能力。这个顺序避免一上来就调大超时，或直接重建副本。

[0240 #section-9.5.2] | 观察结果 | 主要问题 | 下一步证据

[0241 #section-9.5.2] | 身份相容、所需历史仍在 | 可能继续增量 | 获取与应用速率是否足以净追赶

[0242 #section-9.5.2] | 身份相容、历史内容已清理 | 已知进度无法取回对应变化 | 新基础状态、备份或远程历史是否可用

[0243 #section-9.5.2] | 同一数字位置对应不同任期或来源 | 历史可能分叉 | 共同前缀与不相容尾部的边界

[0244 #section-9.5.2] | 进度元数据本身缺失或损坏 | 起点不明确 | 可验证的检查点、事务集合与恢复工具

[0245 #section-9.5.2] | 网络已恢复，落后仍持续增加 | 容量或执行瓶颈 | 接收、写日志、应用各阶段耗时

[0246 #section-9.5.2] Redis backlog 被覆盖、MySQL 所需 binlog 被清理、Kafka 远程元数据不可用，在实现上不同；共同点是恢复需要的依据不再完整。把它们全部叫作“位点丢了”，会使排查方向错开：有时位置非常清楚，只是内容不在了。

[0247 #section-9.5.3] 9.5.3 主节点故障后的确认写

[0248 #section-9.5.3] 考察一条客户端已经收到成功的写入。先找出成功响应发生时系统承诺了什么，再判断新主是否包含这项承诺所依赖的历史。异步复制中，成功可能早于副本接收；带等待的复制中，还要检查等待是否超时降级，以及候选副本是否属于取得确认的范围。

[0249 #section-9.5.3] 如果客户端没有收到成功，问题反而更不确定：请求可能尚未到达，也可能已经提交只是响应丢失。服务端复制日志能够帮助恢复状态，却不能替客户端区分这两种情况。业务请求标识、结果查询与幂等处理，是端到端协议的一部分。

[0250 #section-9.5.3] 这里没有哪一个产品名称可以直接替代推理。MySQL 的本地事务保证不等于异步副本无损，Redis 的低延迟不等于所有写都必须容忍丢失，Kafka 的复制确认不等于下游数据库结果已经持久化。真正的比较对象是带有配置、拓扑和故障假设的一段写入路径。

[0251 #section-9.6] 9.6 架构启示：把恢复要求写进运行方式

[0252 #section-9.6.1] 9.6.1 拒写与降级是两种业务选择

[0253 #section-9.6.1] 我在涉及金额或库存的写路径上，更在意系统是否悄悄降低了确认条件。MySQL 半同步超时可以退回异步；Kafka 在 acks=all 且最小 ISR 条件不满足时，会使相应写入失败。前者保留服务能力的方式与后者不同，不能只比较正常情况下谁的延迟低。

[0254 #section-9.6.1] 这个偏好并不是建议所有系统故障时停机。日志采集可能更愿意继续接收并记录损失风险；交易状态可能宁愿暂时拒绝新的确认。业务要决定允许丢哪类记录、允许等待多久以及拒绝后如何回应用户。技术方案则需要使这些选择真的成为运行行为。

[0255 #section-9.6.1] 降级如果被选择，必须有可观察的开始和结束，也要知道降级期间产生了哪些业务结果。只在仪表盘显示一个红点，而入口仍向用户给出同样承诺，不能算完成了风险处理。恢复正常也不意味着降级期间的历史差异已经自动消失。

[0256 #section-9.6.2] 9.6.2 写后读需要一个可检查的目标

[0257 #section-9.6.2] 导读中的订单查询问题，可以有不同处理方式。写后短时间路由到主节点是一种办法，但时间窗口只是经验值；等待副本应用到某个事务位置，则把条件写得更明确，却增加等待和超时分支。返回写入结果供页面直接显示，可以减少即时查询，但不替代后续状态读取。

[0258 #section-9.6.2] 我还排查过一次外观相似的问题：用户修改资料后，数据库已经写入，刷新页面仍看到旧值。查到最后，是不同代码路径里删缓存与写数据库的先后顺序不一致，缓存没有按预期失效。那次问题与订单读取落后副本不同：等待数据库副本追平，不能修复另一条缓存失效路径。

[0259 #section-9.6.2] 选择依赖操作语义。用户刚保存资料时，希望立即看到刚才的结果；排行榜允许几秒延迟；后台离线统计可以接受更长时间。把所有读取都叫最终一致，既不说明窗口，也不说明超时后行为。设计应落到某个读操作所需的最低状态，而不是全系统一句统一口号。

[0260 #section-9.6.2] 如果用固定等待时间保证可见性，必须承认它不是进度证据。平时几十毫秒能追上，不代表大事务、暂停或故障期间也能追上。需要严格写后读的操作，要么获得适当的读取位置，要么明确等待到哪个可验证条件；条件不能满足时应返回可理解的状态。

[0261 #section-9.6.3] 9.6.3 恢复预算由历史保留与净追赶能力共同决定

[0262 #section-9.6.3] 我查看副本恢复方案时，会把历史保留和追赶速度放在一起。保留一天日志却需要两天才能重建的实例，恢复过程中仍可能越过保留边界；把网络恢复了当成故障结束，也可能使长期落后的副本继续占用系统资源。

[0263 #section-9.6.3] 一次完整恢复应统计基础状态生成、传输、加载、增量追赶和对外就绪。每段都可能成为最长阶段，重试还会放大资源消耗。特别是在多个副本同时重建时，源节点要一边处理正常请求，一边提供恢复数据，不能用空载传输速度估算整体完成时间。

[0264 #section-9.6.3] 有些恢复可以通过限流降低前台影响，但恢复变慢又要求更长历史保留。这是明确的循环约束：恢复速率影响窗口，窗口影响容量，容量又影响保留和维护。把这组关系写清后，才能决定是增加资源、减少入口，还是改变恢复来源。

[0265 #section-9.6.4] 9.6.4 进度保存要与副作用对应

[0266 #section-9.6.4] 如果消费者把 offset 提交在业务修改之前，崩溃后可能跳过尚未完成的工作；如果在业务修改之后提交，响应丢失或崩溃可能导致同一记录重做。两种顺序都没有解决跨系统原子性，只是选择了不同失败窗口。

[0267 #section-9.6.4] 对可安全重做的派生计算，重复通常可以通过覆盖写或带版本更新处理。对扣款、发货等操作，需要业务标识、唯一约束、结果状态，或由目标系统提供适当的幂等接口。保存消费进度与保存业务结果，至少要有一条明确的衔接规则。

[0268 #section-9.6.4] 我不会因为一条消息已经落在 Kafka，就认为后续状态都能从它“重算”。有些状态表达的正是消息之外的事实：第三方是否执行、用户是否确认、重复请求对应哪一次结果。重放输入不能替代这些事实的记录。

[0269 #section-9.6.5] 9.6.5 用故障轨迹验收，而不是只看连通状态

[0270 #section-9.6.5] 同步链路全绿只能说明当前监控条件满足，不证明每个故障窗口都符合业务要求。有效的检查应选择明确时点：请求已执行但响应未送达，副本已接收但尚未应用，主节点确认后立即失联，副本断线超过本地历史窗口，以及恢复期间再次中断。

[0271 #section-9.6.5] 每个检查都需要记录输入标识、已确认结果、节点历史和恢复后可见内容。否则只能得到“集群又起来了”，无法知道哪几笔操作保留下来。实验环境可以缩小规模，但不能把故障注入影响范围与生产安全混为一谈；这些检查应在隔离环境执行并记录所用版本和配置。

[0272 #section-9.6.5] 验证还要检查错误路径本身。请求返回错误之后是否继续重试、是否换了新的业务ID、是否可能重复执行，往往比正常路径多一个副本更影响最终结果。第 10 章把这项检查放进一个完整的库存预留设计中。

[0273 #section-9.7] 9.7 小结

[0274 #section-9.7] Redis 的 replid 与 offset、MySQL 的 GTID 集合、Kafka 的 leader epoch 与分区 offset，分别为历史与进度提供证据。它们不具有相同的比较规则。部分续传还需要对应内容仍然存在，以及副本具有净追赶能力；保留一个位置数字不会让被清理的数据重新出现。

[0275 #section-9.7] 确认也有不同阶段。Redis 的入口门槛、WAIT 与 7.2 起的 WAITAOF，MySQL 的 relay log 刷盘确认与等待点，Kafka 的 ISR 与提交边界，都要按自身条件解释。默认异步、超时降级、候选选择、本地持久化和外部副作用，不能被一个“强一致”标签合并。

[0276 #section-9.7] 同步协议帮助副本维持和恢复有效历史，业务仍需决定成功响应意味着什么、读操作需要看到哪里、超时后如何查询和重试。下一章将这些问题与数据结构、生命周期、持久化和分层放到同一个设计里，检查多个局部合理的选择，组合之后是否仍然成立。
