## 一、compaction 在本书术语体系中的位置（应该是什么）

1. **归「中文已充分沉淀，用中文」档，译名＝压实**。ch1:208 两档制（工程通行术语用英文 / 中文沉淀词用中文）下，compaction 走中文档；首现处标注英文：ch1:100「启用压实（compaction）时……」已按此执行。
2. **契约依据**：`docs/book-bible.md:125` 术语表规定 compaction →「compaction（压实）」，中英两档皆可；本书自始执行中文档。
3. **与 compression 构成必须区分的最小对立对**：compression 同样走中文档、译「压缩」。两个概念在 Kafka 中并存（见 §三），译名必须一词一义。
4. **「压缩」在本书的三处合法身份**：① compression（Kafka 生产者压缩、InnoDB 页压缩、RDB 的 LZF）；② Redis 固定结构名「压缩列表（ziplist）」；③ 工作文档里泛指"压缩篇幅"（不入书）。compaction 不属于其中任何一类。
5. **边界说明（外部惯例席核实后修订）**：「压实」是中文沉淀名单里基础最弱的一个——其阵地在 LSM/HBase/InfluxDB/RocksDB 圈；**Kafka 圈的主流译法恰是「日志压缩」**（阿里云、博客园等多数文章），不译次之，「日志压实」近乎检索不到。即：在 Kafka 语境里选「压实」是少数派选择，但 Kafka 圈主流译法本身就是一词两义（Red Hat 官方示范，见 §四），本书为区分两概念借用 LSM 系的区分性译名，理由反而更硬。若作者嫌生僻，合法替代是全书统改英文 compaction（契约允许的另一档），但不推荐——ch4:233「段被删除/compaction 时」等处中文语感受损；且一词一义的目标下，「压实」仍是最优解。

## 三、为什么必须一词一义（技术依据）

1. **同系统双机制并存**：Kafka 的 compression（compression.type＝none/gzip/snappy/lz4/zstd，RecordBatch attributes 压缩位，成批压缩换吞吐）与 compaction（cleanup.policy=compact，按 key 保留最新值、重写日志段清理旧记录、墓碑标记删除）是两个独立机制，配置项、线程、触发条件互不相干。
2. **同段双现**：ch8:277 前半「RecordBatch 把多条记录放在一起压缩」（算法）、后半「由 compaction（压实）逐步清理旧记录」（清理）——若共用「压缩」一词，一词两义零距离。
3. **可逆性不同**：压缩可逆（解压还原原字节）；压实有损（被新值替代的旧值永久消失，删除也是墓碑）。用「压缩」称呼 compaction，暗示体积变小来自压缩算法且数据可还原，双重误导。
4. **近距对照段落**：ch8:185「压实是另一种清理路线」与同节 8.4「成批压缩」并列对照；ch2:110 整段讲 compression.type 与逐批解压/重压——这些段落可读的前提就是两词分开。
